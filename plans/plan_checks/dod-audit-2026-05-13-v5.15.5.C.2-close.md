### MEDIUM-2 — `OmsStateFlagRegistry.hpp` lacks the `_pad_*` field after `uint8_t oms_state_flags` (struct padding determinism)

- **Symptom:** `oms_state_flags` is followed by `FPN<F> ks_min_balance` (8-byte aligned), creating 7 bytes of implicit padding. - **Cross-refs:** existing explicit `_pad_*` fields elsewhere in OrderManagerState (e.g., `_pad_lepb[3]`, `_pad_lepa[]`).

### LOW-1 — `OMS_PERSIST_COMMIT_BIT` macro emits `} while (0);` with INTERNAL trailing semicolon; harmless but inconsistent with `do {} while (0)` idiom
- **Surface:** `MemHeaders/OmsPersistFieldRegistry.hpp:117-121`
- **Pattern:** `x-macro-registry-with-presence-dispatch.md` (macro hygiene).
- **Symptom:** Standard `do {} while (0)` macro idiom is to OMIT the trailing semicolon at the macro definition so callers can write `MACRO();` naturally. Current shape emits `do {...} while (0);` (semicolon inside macro), which means the X-macro expansion yields `do {} while(0);` (double semicolon-equivalent). Compiles cleanly because the second `;` is a null statement. No bug today; pattern drift.
- **Suggested fix:** drop the trailing `;` after `while (0)` in OMS_PERSIST_COMMIT_BIT; rely on the FOREACH-row syntactic flow. Sister DIRECT variant uses `state->oms->name = tmp_##name;` — that one DOES need the semicolon (single-statement form). The DO_SAVE macro uses balanced `{ ... }` block (no semicolon needed). Inconsistency is the smell.
- **Effort:** 2 minutes.
