## Design pivots (each one surfaced something worth remembering)

### Pivot 1: Original v5.14.9 plan was stale — "binary kill switch" framing wrong

**Trigger:** Pre-coding verification of the v5.12.1.D math (StrategyParameters.hpp:1291-1322). Original 2026-05-08 plan claimed v5.12.1.D was "always multiplies by 1.0 = no-op until composite confidence wired"; actual code has logic that's broken-for-composite-scale (compares conf_now ∈ [0.001, 0.3] against ml_buy_threshold ∈ [0.5, 0.7] → factor=0 silently).

The "binary kill switch" framing in the master plan came from a DIFFERENT layer — `confidence_hard_block_threshold` at StrategyParameters.hpp:1248-1265. v5.14.9's ladder doesn't replace this layer; it replaces the broken L3 (sizing) math.

**Decision:** Three confidence-driven layers exist orthogonally:
- L1: `confidence_threshold_scale` damped threshold (modifies entry threshold)
- L2: `confidence_hard_block_threshold` HARD CLIFF (catastrophic safety net; default off)
- L3: `risk_scale_by_confidence` sizing factor (broken for composite; v5.14.9 fixes)

v5.14.9 fixes L3 only. L1 + L2 stay as orthogonal axes. NOT merged.

**Codified in:** new plan's "Why this ship exists" section + Q1 design discussion in postmortem.

**Going-forward rule candidate:** when a master plan describes a feature in shorthand ("binary kill switch"), pre-coding verification must MAP shorthand to concrete code locations. Compaction-degraded handoffs collapse this mapping.

### Pivot 2: cfg field rename — `risk_scale_by_confidence` → `risk_degradation_curve`

**Trigger:** Existing enum modes (1=linear, 2=quadratic) use broken-for-composite math. Caramel's structural-fix-preferred rule + "defer is last-ditch" memory: don't preserve broken modes for back-compat; fix structurally.

**Decision:** Rename + replace math. Old `risk_scale_by_confidence` → `risk_degradation_curve` (registry-aligned naming). Back-compat parser shim translates legacy `risk_scale_by_confidence=N` → `risk_degradation_curve=N` (values map 1:1; modes 1+2 get NEW math = ladder linear/exp; mode 3 = ladder step is added).

**Trade-off:** legacy operators who explicitly set `risk_scale_by_confidence=1` get NEW math instead of old broken math. CHANGELOG documents the change. Reasoning per Caramel's "ACTIVATION GATED on Phase 4.B paper-test" comment in code: no operator has activated this yet (gate hasn't fired), so rename is safe.

**Going-forward rule candidate:** cfg rename + structural-fix replaces broken-but-tolerated behavior cleanly when no operator depends on the broken behavior. Verify "no dependency" via comment-archeology + grep before renaming.

### Pivot 3: Composite-required-for-ladder boot REFUSE — engine-wide vs per-core

**Trigger:** Per-core override pattern (`core_N_*`) is supported for ladder cfg fields. But composite_enabled is GLOBAL only (no per-core override exists). Question: per-core REFUSE check or engine-wide?

**Decision:** Engine-wide REFUSE. If ANY core has ladder enabled (global OR per-core override), composite_enabled must be on globally. Reasoning: composite is global; partial activation isn't possible without adding per-core composite override (unjustified cfg surface creep).

Caramel's pushback ("what do you mean, is the simpler option actually better? does it fit with the design philosophy?") prompted the framing: option (b) is mechanically correct given the constraint, not just simpler. Constraint forces the answer; no design wiggle room.

**Going-forward rule candidate:** when justifying "simpler is better" design choices, articulate the underlying CONSTRAINT (not just "fewer cfg fields"). Constraint-driven simplicity is honest; preference-driven simplicity needs more justification.

**Trigger:** Caramel asked "should we make a skill that checks for concurrency issues, cache alignment, cache misses, branchless implementations, bit packing, bit field dispatchers, and that references past design docs?".

## Design pivots — late-sprint additions (.F-.F.6 + .G + .H)

### Pivot 7: SCOPE COLUMN vs DOMAIN SPLIT for cfg-flag registries

**Trigger:** v5.14.9.B.0 used a SCOPE COLUMN registry (`FOREACH_SLOW_PATH_GATE` with `axis` column dispatching `HANDLE_GEN_<axis>` macros). For cfg-flag refactor, the next question: same SCOPE COLUMN form, or split into 5 DOMAIN registries (LIFECYCLE/GATE/ML/RISK/OPS)?

**Decision:** DOMAIN SPLIT. Each domain owns its bitmap field (`lifecycle_cfg_flags`, `gate_cfg_flags`, `ml_cfg_flags`, `risk_cfg_flags`, `ops_cfg_flags`) + per-domain audit/test boundary + per-domain storage class freedom (ML promoted to uint16_t for 7 flags + headroom; others uint8_t).

**Why DOMAIN SPLIT over SCOPE COLUMN here:** scope-axis is the same across all cfg flags (they're all engine-wide cfg booleans), so a SCOPE COLUMN would be a tautology. Domain ownership IS the meaningful axis. Captured in `DESIGN_SPECS/heterogeneous-registry-pattern.md` Form 2.

**Going-forward rule:** when SCOPE/AXIS column would be tautological (single value), prefer DOMAIN SPLIT. Form 1 vs Form 2 distinction matters.

### Pivot 8: MVP rationalization caught + reversed (.F.2)

**Trigger:** I drafted .F.2 as "minimum viable" — defer Y3 dispatch extension for FOREACH_STAMP_BOUND_CFG (only one entry is stamp-bound; defer the registry generalization to future ship).

**Caramel's pushback:** "why are we doing minimum viable".

**Decision:** Reversed. Did full Y3 dispatch extension with `emit_source` column (DIRECT_FIELD vs BITMAP_BIT) per the original plan + DESIGN_SPECS HYBRID Form 3. Captured in memory `feedback_no_mvp_for_plumbing_only_for_unknown_unknowns.md`.

**Going-forward rule:** plumbing work (registry extensions, infrastructure) gets full design, not MVP. Reserve MVP framing for genuinely-new features with unknown unknowns.

### Pivot 9: lat_enabled NOT cfg-flag-eligible — eligibility criteria emerged

**Trigger:** Pre-coding audit subagent for .F flagged `lat_enabled` as cfg-flag candidate. Step 0 verification revealed it's a per-Tick local var with compile-time elision via `template<bool LAT_ENABLED>` + `if constexpr`.

**Decision:** Reject migration. Cfg-flag-eligibility requires: (a) runtime-mutable, (b) doesn't already have compile-time elision, (c) ≥1 hot-path branch saved by bitmap. `lat_enabled` fails (a)+(b) — migration would add 1-2ns/tick perpetually for no win.

**Codified in:** TECH_DEBT-023 as explicit eligibility criteria. Reframed domain from speculative "OMS_CFG_FLAG" → grounded `LIFECYCLE_CFG_FLAG` (3 entries: partial_exit + 2 breakeven).

**Going-forward rule candidate:** audit subagent flags may be false positives; Step 0 verification on every flagged item before scope-locking the ship.

### Pivot 10: Replace_all mangling, Shape A + Shape B (.F.1 + .F.3)

**Trigger:** Two distinct shapes of replace_all mangling caught mid-ship:
- **Shape A (chained prefix):** `config.gate_enabled` replace_all mangled `ctrl->config.gate_enabled` (chain prefix not protected).
- **Shape B (variable suffix):** `cfg.kill_switch_enabled` replace_all mangled `fake_cfg.kill_switch_enabled` and `small_cfg.kill_switch_enabled` (test-local variables with `_cfg` suffix).

**Decision:** Replace_all is unsafe for member-access on cfg-like identifiers; use targeted Edit operations instead. Strengthened memory `feedback_avoid_substring_replace_all_on_member_access.md` to capture both shapes.

**Going-forward rule candidate:** for member-access refactors across a codebase, prefer targeted Edit + verify-each over replace_all. The 1-tool-call efficiency isn't worth the silent-mangling cost.

### Pivot 11: Option D 5-col tuple expansion — registry IS source of truth (.F.5)

**Trigger:** Caramel asked "whats the most future thinking and maintainable solution?" for GUI integration. Options A (manual GUI entries), B (registry generates JUST the bitmap), C (hybrid w/ GUI-facing meta in a separate place), D (5-col tuple with display_label + section + doc embedded in the registry).

**Decision:** Option D. Registry tuple becomes the SINGLE SOURCE OF TRUTH for cfg parsing + GUI rendering + per-core override + stamp-binding + documentation. Adding the next cfg flag = 1 row in the registry; cfg parse + GUI field + override + docs all auto-flow.

**Going-forward rule:** when a registry feeds N consumers each needing meta, embed meta in the tuple (Option D); don't have parallel meta tables (Option C). Captured in `DESIGN_SPECS/heterogeneous-registry-pattern.md` Option D section.

### Pivot 12: Per-bit per-core override — branchless bit-select (.F.6)

**Trigger:** Existing per-core override pattern was field-by-field (`core_N_partial_exit_enabled`). For 5 domain bitmaps, that would be 21 cfg fields × N cores. Wasteful.

**Decision:** `PER_CORE_OVERRIDE_BITMAP_DOMAINS` macro: per-core gets 2 bitmaps per domain (`override_set` + `override_values`). Branchless bit-select at slow-path: `(override_set & override_values) | (~override_set & global_values)`. Single mask AND per domain dispatches all flags simultaneously.

**Going-forward rule:** when per-core override applies to a bitmap field, override pattern is `set+values` not `replicate every bit as cfg field`. Branchless bit-select stays hot-path-friendly.

### Pivot 13: Mid-sprint /dod-audit gates — audit→ship pattern

**Trigger:** Caramel mid-sprint asked for "/dod-audit before .F.5" and "/dod-audit before .G". I'd been running pre-coding audits per ship; mid-sprint audits between sub-ships of a sprint emerged organically.

**Decision:** /dod-audit between any sub-ship if (a) scope significantly differs from previous sub-ship, (b) DESIGN_SPECS introduced new pattern, (c) cache-locality changed. Codified as a CLAUDE.local.md going-forward rule.

**Going-forward rule:** Claude suggests mid-sprint audit when downstream sub-ships impact a new surface; Caramel greenlights or skips. Already added to CLAUDE.local.md.

## Architectural surprises — late-sprint (.F-.H)

### Surprise 6: HMAC byte-equivalence via if-else ternary (.F.2)

**Caught by:** /dod-audit for .F.2. Y3 dispatch BITMAP_BIT branch had to emit the EXACT same byte as the DIRECT_FIELD branch for stamp-body wire compatibility.

**Specifics:** `BITMAP_IS_SET(...) ? 1 : 0` — the ternary normalizes bool-promotion ambiguity to a guaranteed `int 0` or `int 1`, matching DIRECT_FIELD's bool-promotion behavior byte-for-byte. Without the ternary, HMAC chain would break on bitmap-bit-extracted fields.

**Lesson:** when emit-source diverges, wire-format byte-equivalence requires explicit normalization. Captured in `DESIGN_SPECS/wire-format-byte-preservation-discipline.md`.

### Surprise 7: alignas(8) for hot-cluster bitmap (.F first ship)

**Caught by:** /dod-audit for .F. Hot-cluster cache line analysis flagged the new `lifecycle_cfg_flags uint8_t` could land mid-cache-line, causing partial-word load on hot read.

**Specifics:** Added `alignas(8)` on lead bitmap field. All 5 domain bitmaps cluster together at start of cache line. Cross-thread hot/slow access stays clean.

**Lesson:** every bitmap field on hot-cluster gets explicit `alignas(8)` review. Captured in `DESIGN_SPECS/heterogeneous-registry-pattern.md` cache-layout discipline section.

### Surprise 8: FakeCfg test struct false migration (.F.3)

**Caught by:** Test compilation errors after replace_all. Test file uses local `FakeCfg` struct with same field names as real `ControllerConfig`. Replace_all incorrectly migrated those references.

**Specifics:** FakeCfg fields stay direct (boolean), not bitmap — they're test-local mock struct. Targeted Edit reverted the false migrations.

**Lesson:** during member-access refactors, scan for test-local mock structs that REUSE field names. They're false-positive migration sites. Captured in `feedback_avoid_substring_replace_all_on_member_access.md`.

### Lessons synthesis

**1. Audit→ship pattern works at multiple scales:** pre-coding audit before sprint + mid-sprint audit between sub-ships + post-ship audit (/dod-audit Step 8). Three checkpoints, each catches different surprises. None should be skipped on plumbing sprints.

**2. Registry tuple is the single source of truth — fully realize it:** v5.14.9.F.5 demonstrated registry tuple feeds cfg + parser + GUI + override + stamp-binding + docs. Every future registry should aim for this completeness; partial-mirror is a tech-debt smell.

**3. DOMAIN SPLIT > SCOPE COLUMN when scope is tautological:** if every entry has the same axis value, the axis isn't real; DOMAIN SPLIT respects ownership boundaries.

**4. Replace_all on member-access is unsafe:** two distinct mangling shapes (Shape A chained prefix, Shape B variable suffix). Use targeted Edit for member-access refactors.

**5. MVP rationalization is anti-pattern for plumbing:** Caramel's "why are we doing minimum viable" caught a mid-sprint MVP regression. Plumbing gets full design; MVP is for unknown-unknowns features.

**6. Cfg-flag eligibility has hard criteria:** runtime-mutable + no existing compile-time elision + ≥1 hot-path branch saved. Compile-time-elided template params are NOT cfg-flag candidates.

**7. /dod-audit registry-driven dispatch is a force multiplier:** detected cache layout sensitivity, HMAC byte-equivalence concerns, mangling shapes, eligibility violations. Worth integrating with /readiness as a sprint-end check too.
