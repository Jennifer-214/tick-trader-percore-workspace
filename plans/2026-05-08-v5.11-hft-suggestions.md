# v5.11 Sidecar: HFT Design Suggestions

**Purpose:** This document captures architectural suggestions bridging the `v5.10` Design Notes / Deferred Items and the strict HFT invariants defined in the `v5.11` Latency Optimization Audit.

When implementing deferred features, apply these HFT-first principles rather than standard software engineering patterns.

---

### 1. Execute "Idea 5: Feature Mask Cfg" entirely Branchlessly via AVX-512

**Context:** The v5.11 Deferred Items (#5 Feature mask cfg per-core) proposes a `uint64_t` bitmap to enable/disable features per core, suggesting an `if (mask & 1)` check before calling each feature compute function.

**HFT Suggestion:** Do NOT use `if` statements to skip feature computation. Instead, evaluate **all** features unconditionally, pack them into your 256-bit or 512-bit registers, and then use the `feature_mask` as the literal hardware mask in an AVX-512 blend instruction (`_mm512_mask_blend_epi64`). 

This zeros out the disabled features in a single clock cycle, satisfying the new operator workflow without introducing a single branch-prediction penalty on the slow path.

---

### 2. Elevate the `strcmp` Refactor to a Core HFT Invariant

**Context:** The v5.11 Deferred Items lists the "If/else strcmp chain → switch/lookup audit" as a code-style polish for `ControllerConfig.hpp` and `verify_model_stamp`, claiming it is "boot-time-only (performance irrelevant)".

**HFT Suggestion:** In a true HFT system, configuration hot-reloading (via SIGHUP or admin commands) happens while the engine is live. A 30-clause `strcmp` chain is an `O(N * K)` parsing penalty. If the controller thread spends microseconds doing scalar string scans, it risks polluting the L1 cache or delaying atomic permission flag updates. 

Elevate this from a "style audit" to a required latency optimization. Replace the string literals with compile-time `constexpr` FNV-1a hashes and use standard `switch/case` statements. This compels the compiler to generate an `O(1)` jump table.

---

### 3. "Idea 3: Drift Detection" as an Asynchronous Lock-Free Signal

**Context:** The v5.10 Design Notes (Idea 3: Drift detection / model retirement) proposes calculating a rolling IC score and triggering an `auto_kill_on_drift`.

**HFT Suggestion:** When implementing the automated trigger, ensure the rolling IC computation runs purely on the slow path or a background analytics thread. When drift falls below the threshold, it should toggle a single atomic bit in a cache-aligned control block (similar to the `permission` flag moved to `alignas(64)` in Audit Part 1). 

Because the hot path already uses bitwise gate logic (e.g., `return (order_book_state & kill_mask) == kill_mask`), the hot path will automatically and instantaneously stop trading without ever executing a branch or context-switching to handle the drift detection event.
