### Step 3 — Reconcile_ApplyMissedFills helper

File: `CoreFrameworks/Reconcile.hpp`

```cpp
// Given parsed myTrades (post-disconnect window) + current OMS
// portfolio state, identify trades we DIDN'T see and replay them
// through OMS_HandleFill to restore portfolio.
//
// Returns count of fills replayed.
template <unsigned F>
inline int Reconcile_ApplyMissedFills(
    OrderManagerState<F>* oms,
    const ReconcileTrade* trades, int n_trades,
    uint64_t our_last_seen_trade_id) {
    int replayed = 0;
    for (int i = 0; i < n_trades; ++i) {
        if (trades[i].trade_id <= our_last_seen_trade_id) continue;
        // Synthesize an Order from the trade record + push through
        // HandleFill (existing path) to update portfolio + balance
        Order<F> synth;
        Order_Init(&synth, trades[i].order_id, trades[i].core_id,
                    trades[i].order_type);
        synth.is_maker = trades[i].is_maker;
        synth.qty      = trades[i].qty;
        // ... populate other fields from ReconcileTrade ...
        OrderManager_HandleFill(oms, &synth,
                                 trades[i].fill_price, trades[i].qty);
        replayed++;
    }
    return replayed;
}
```

### Step 5 — Boot integration (mode dispatch)

File: `CoreFrameworks/EngineSharded.hpp` (boot reconcile site)

```cpp
ReconcileResult result = Reconcile_Run(...);
switch (cfg.reconcile_mode) {
    case RECONCILE_STRICT:
        if (result.has_mismatch) {
            fprintf(stderr, "[reconcile] STRICT mode + mismatch detected; "
                "engine boot REFUSED\n");
            exit(1);  // hard refuse boot
        }
        break;
    case RECONCILE_WARN:
        if (result.has_mismatch) {
            fprintf(stderr, "[reconcile] WARN mode: %d cancel(s), %d "
                "missed fill(s) detected; continuing\n",
                result.cancel_actions, result.missed_fill_count);
        }
        break;
    case RECONCILE_AUTO_SYNC:
        int replayed = Reconcile_ApplyMissedFills(&oms,
            result.trades, result.n_trades, oms->last_seen_trade_id);
        int cancelled = Reconcile_AutoCancelStale(&oms,
            result.exchange_orders, result.n_exchange_orders);
        fprintf(stderr, "[reconcile] AUTO_SYNC: %d fill(s) replayed, "
            "%d zombie order(s) cancelled\n", replayed, cancelled);
        break;
}
```

**SUB-SPLIT RATIONALE (audit-driven decision 2026-05-09):**

Original .B was ~150 LOC monolith (ApplyMissedFills + AutoCancelStale +
boot dispatch in one ship). During implementation surfaced a scope
question: helpers have asymmetric risk (replay = OMS-state-only mutation;
cancel = real exchange writes that mutate exchange-side state). Operator
chose sub-split for max future-proofness:

- **Risk asymmetry honored:** replay (lower-risk) ships first; operator
  validates on testnet in isolation; THEN cancel (higher-risk) ships.
  Two smaller validation cycles vs one big bundle.
- **Independent rollback:** if AutoCancelStale has a bug, ApplyMissedFills
  doesn't roll back with it. Each sub-tag has its own commit boundary +
  is independently revertable.
- **`git bisect`-friendly:** regression hunting can isolate replay vs
  cancel bugs.
- **Future-proof framing:** establishes the pattern "AUTO_SYNC = composition
  of N independent helper-actions" — when v5.X+ adds auto-rebalance /
  auto-recreate-stops / etc., they slot in as additional sub-tags or
  helpers without re-architecture.
- **X-macro registry stays clean:** rejected the alternative "defensive
  opt-in cfg flag inside AUTO_SYNC" because it would dirty the 3-mode
  registry shape with an implicit 4th mode (AUTO_SYNC-but-cancel-off).
  Per CLAUDE.md item 19, structural decomposition (sub-tag boundary)
  preferred over runtime gates (cfg flag).

**Behavior between .B.1 and .B.2:**
- Post-.B.1 ship: AUTO_SYNC mode runs ApplyMissedFills only; logs
  "[reconcile] AUTO_SYNC partial — cancel stale orders deferred to .B.2;
  N orders left as-is" if cancel_actions > 0.
- Post-.B.2 ship: AUTO_SYNC mode runs both helpers; full functional.

**Cross-ship coordination:** v5.14.7 also originally claimed to add
BinanceOrderAPI_CancelOrder. Master plan ordering: v5.14.4 (Phase 2)
ships before v5.14.7 (Phase 3). v5.14.4.0 creates the cancel API
exactly once; v5.14.7 reuses it via the existing function. v5.14.7
plan updated to reflect this (removed BinanceOrderAPI_CancelOrder
from its NEW claims).
