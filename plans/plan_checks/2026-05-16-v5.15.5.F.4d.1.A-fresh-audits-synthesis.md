### CRIT-2 — `FOREACH_REGISTRY` tuple shape mismatch (Class 14 plan API drift)

**Source:** trace-deps + dod-audit F-1 + readiness F1 (all converged)

Plan body line 260 + sidecar lines 451-457 specify a **7-8 column tuple** for the `FOREACH_REGISTRY` row:
```cpp
X(DERIVED_FILTER, "CoreFrameworks/DerivedFilterRoster.hpp", 1, ROOT,
  "metadata-bit-driven-derived-filter-framework.md", Class_21, MIXED, "...")
```

Verified at HEAD (`CoreFrameworks/MetaRegistry.hpp:35-105`): tuple is **4-col**: `X(registry_name, LEVEL, PARENT_NAME, description)`. Plus:
- Row name must be `FOREACH_DERIVED_FILTER` (matches `#define FOREACH_DERIVED_FILTER(X)`), NOT `DERIVED_FILTER`
- PARENT_NAME for Level-1 = `FOREACH_REGISTRY` (token, not literal `ROOT`); `ROOT_NONE` is the sentinel for Level-0 (only `FOREACH_REGISTRY` itself uses it)

The 8-col schema migration is TECH_DEBT-057 deferred work; `.A` MUST add the row in the existing 4-col shape. Correct row:
```cpp
X(FOREACH_DERIVED_FILTER, 1, FOREACH_REGISTRY, "Cohort-meta managing cfg-derived filters; .F.4d.1.A first canonical STAMP_BOUND_CFG via WIRE_FORMAT_TWO_SOURCE")
```

**Effort:** 5 min (mechanical; sidecar Step 4 + plan body 4 propagation sites).

### STRUCTURAL-1 — Runtime walker DUPLICATES existing `cfg_compute_mask` + `CFG_FIELD_FOR_EACH_SET_BIT` infrastructure

**Source:** merge-scan M-1 BLOCKING (verified via `CfgFieldRegistry.hpp:1020-1159` + `GUI/SettingsPanel.hpp:1100,1136`)

The plan body proposes building a runtime walker that iterates `g_*_cfg_field_descriptors[]` filtering on `metadata_flags & METADATA_BIT` (sidecar Step 1 lines 62-83). Per-row branch check + per-row fn-pointer callback.

The codebase **already has** the compile-time, branchless equivalent at `CfgFieldRegistry.hpp:1020-1159`:

1. **`FOREACH_METADATA_BIT`** at `:1064-1075` — X-macro registry of metadata bits (currently 11 rows; STAMP_BOUND is already enrolled but STAMP_BOUND_CFG_DERIVED is not)
2. **`cfg_compute_mask<Bit>(arr)`** at `:1039` — `constexpr` mask computation (walks descriptor array at compile time; produces `CfgMaskArray<N_WORDS>` constant in `.rodata`; ZERO runtime init cost)
3. **`g_global_cfg_<lname>_mask` + `g_per_core_cfg_<lname>_mask`** auto-generated arrays via `X_GEN_GLOBAL_MASK` + `X_GEN_PER_CORE_MASK` at `:1079-1088`
4. **`CFG_FIELD_FOR_EACH_SET_BIT(mask, idx, body)`** at `:1150-1159` — branchless iteration via `__builtin_ctzll` (single TZCNT on Haswell+) + `word &= word - 1` next-bit-clear
5. **Live consumer** at `GUI/SettingsPanel.hpp:1100,1136` — both global + per-core walkers in production GUI Settings panel

**The comment at `CfgFieldRegistry.hpp:1020-1022` literally states the framework discipline:**
> "Per CLAUDE.md framework discipline (item 31): adding a new metadata bit = 1 row in FOREACH_METADATA_BIT below; mask arrays auto-generate for BOTH registries via X-macro instantiation pass."

**What `.A` should land** (per existing framework discipline):
1. Add **1 row** to `FOREACH_METADATA_BIT` at `CfgFieldRegistry.hpp:1075`:
   ```cpp
   X(stamp_bound_cfg_derived,  STAMP_BOUND_CFG_DERIVED)
   ```
2. `g_global_cfg_stamp_bound_cfg_derived_mask` + `g_per_core_cfg_stamp_bound_cfg_derived_mask` **auto-generate** as `.rodata` constants
3. `StampBoundDerivedFilter.hpp` canonical body emit uses `CFG_FIELD_FOR_EACH_SET_BIT(g_*_cfg_stamp_bound_cfg_derived_mask.words, idx, { ... })` — branchless iteration
4. Layer 5b structural invariant tests (Option F) work the **same way** — they assert on the canonical body that the existing iteration produces

**Trade-offs:**

| Property | Plan body (parallel walker) | **Recommended (reuse existing infrastructure)** |
|---|---|---|
| LOC at `.A` | ~80 LOC `DerivedFilterFramework.hpp` + ~30 LOC Roster + ~50 LOC consumer | **~5 LOC** (1 FOREACH_METADATA_BIT row + canonical body emit fn + invariants) |
| Latency | Runtime iteration; per-row branch | **Compile-time mask + branchless TZCNT iteration** (strictly better) |
| Init cost | Runtime descriptor scan | **Zero** (`.rodata` compile-time constant) |
| Class 18 mirror surface | YES — runtime walker mirrors existing CFG_FIELD_FOR_EACH_SET_BIT infrastructure | **None** — single source of truth = FOREACH_METADATA_BIT registry |
| Framework discipline alignment (CLAUDE.md item 31) | Violates ("don't duplicate the walker") | **Aligned** (the canonical way per `:1020-1022` comment) |
| GUI metadata cohort sister apps (`.F.4e`) | Would need to thread through Variant 1 macro per app | **Same shape** — 5 rows in FOREACH_METADATA_BIT (already partially enrolled — RESTART_REQUIRED / SAFETY_CRITICAL / DEPRECATED / HIDDEN_BY_DEFAULT / IS_SECRET all in FOREACH_METADATA_BIT today; their masks already auto-generate); `.F.4e` consumers would use existing masks directly |
| 3 macro variants needed? | Yes (GUI_ONLY / WIRE_FORMAT / WIRE_FORMAT_TWO_SOURCE) | **No** — each consumer site directly invokes `CFG_FIELD_FOR_EACH_SET_BIT` against the right mask + does its own emit/render logic |

**This is the most important finding.** It's the exact Class 18 mirror anti-pattern the framework is structurally closing at other surfaces — but at the framework layer itself. Per the "Registries optimize for ADDING; principle + sweep optimizes for ELIMINATING" rule (set 2026-05-15 at .F.4c.3 WIP2d-1.B.0c), building a parallel runtime walker entrenches the wrong shape.

**Note on Option F invariants:** the invariant test discipline (I1-I7) is **orthogonal** to the walker mechanism. Whether `.A` builds a parallel walker or reuses existing infrastructure, the structural invariant tests still encode the canonical body's intent. Option F survives either way.

**Operator decision required.** Two paths:
- **Path α (refactor):** redesign `.A` to use existing FOREACH_METADATA_BIT + CFG_FIELD_FOR_EACH_SET_BIT infrastructure; `StampBoundDerivedFilter.hpp` becomes ~5 LOC consumer + invariant test fns; framework macros (DerivedFilterFramework.hpp) NOT needed at all
- **Path β (keep walker):** stay with parallel walker design; document the discipline tension; accept Class 18 mirror at framework layer

Per Caramel's codified rules + the explicit CLAUDE.md item 31 framework discipline already in the code at the line referenced, **Path α is the clearly principle-consistent choice.** But sequencing carries: does the framework macro abstraction provide value for `.F.4e` 5 GUI metadata consumers that justifies the duplication?

(Answer per analysis: NO. The 5 consumers in `.F.4e` will each be a few-LOC `CFG_FIELD_FOR_EACH_SET_BIT` invocation against the existing pre-computed mask + their domain-specific logic. Framework macro adds no value when the iteration is already trivial.)
