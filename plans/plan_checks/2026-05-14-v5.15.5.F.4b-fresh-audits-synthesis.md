## Critical findings (must resolve before coding)

### CRITICAL-1 — FPN<F>-vs-double type dispatch is broken
**Sources:** `/trace-deps` BL-1 (independent finding); `/merge-scan` #3 (related pattern alignment).

**The flaw:** Plan Step 2's `tt::cfg_parse_field<KIND_DOUBLE>` uses:
```cpp
*reinterpret_cast<double*>(reinterpret_cast<char*>(dst) + offset) = v;
```
But ~38 of ~40 KIND_DOUBLE/_PCT cfg fields are actually `FPN<F>` (24-byte fixed-point), not raw double. Writing 8 bytes of double into the first 8 bytes of a 24-byte FPN destroys mantissa words → silent corruption → backtest determinism breaks → train-serve parity breaks.

**The fix:** Reuse the validated CLAUDE.md item 23 pattern from `tt::stamp_parse_field<T>` (`ML_Headers/StampBoundModelConstRegistry.hpp:86-99`). Dispatch on **destination type T** via `if constexpr (is_FPN_v<T>) / is_floating_point_v<T> / is_array_v<T>`, not on Kind enum. Caller passes field by reference; T is deduced. Kind enum stays as descriptor metadata (slider range, GUI format, clamp coercion) but doesn't drive type dispatch.

**Plan amendments needed:**
- Step 2: Replace Option A (offsetof + reinterpret_cast) with **Option D: X-macro extractor with templated callee**. Each row's X expands to `tt::cfg_parse_field(cfg->X, desc, val)` — T deduced from field.
- Step 4/5: Same change applied to save dispatch.
- Descriptor design: confirm Kind enum stays metadata-only (the registry tuple doesn't need to encode destination type — the X-macro extractor passes the field directly).

### CRITICAL-2 — False function-name claims throughout plan
**Sources:** `/readiness` RED #1 (5 missing functions); `/trace-deps` BL-2 (actual API surface identified).

**The flaw:** Plan references `CfgParser_HandleKV`, `Cfg_Save`, `Cfg_LoadFromString`, `Cfg_LoadFromFile`, `parse_csv_engine_config` — **none exist**. Step 4's `rg "void.*Parse.*Cfg.*const char" CoreFrameworks/` yields zero hits.

**Actual API surface (verified):**
- **Parser:** inline body of `ControllerConfig_Load<F>` at `CoreFrameworks/ControllerConfig.hpp:1798` (single function; no extracted KV handler)
- **Save:** per-field text-splice via `cfg_write_field(path, key, value)` at `GUI/SettingsPanel.hpp:472`. Comment-preserving (operator-friendly UX); NOT a monolithic `Cfg_Save(FILE*)`
- **Roundtrip test in Step 6:** `Cfg_LoadFromString` doesn't exist; tests would need different harness (e.g., write to tmpfile + Load)

**Plan amendments needed:**
- Step 4: Rewrite parser migration against `ControllerConfig_Load<F>` inline body (lines ~1798-2381 + tail). Document the if-else chain location precisely (it spans hundreds of lines).
- Step 5: Rewire `cfg_write_field`'s value-formatting through `tt::cfg_save_field<K>` — preserves the splice/comment-preserving UX. Don't replace cfg_write_field wholesale.
- Step 6: Rewrite test harness against actual API; use `ControllerConfig_Load(filepath)` + tmpfile round-trip rather than `Cfg_LoadFromString`.

## High findings (should resolve before coding)

### HIGH-1 — Descriptor cache-line budget contradicts itself within the plan
**Sources:** `/parity-check` F4 + `/dod-audit` FINDING-2 + `/readiness` RED #3.

Step 1 says `<= 128`; Step 6 test code + "If something goes wrong" recovery section say `<= 64`. The 128B budget is correct per DESIGN_SPECS (universal-cfg-field-registry-pattern.md:165-168). Mechanical search-replace: `64` → `128` in test code + recovery prose. ~5 min.

### HIGH-2 — X-macro tuple arity inconsistency (7-arg code vs 12-arg spec)
**Sources:** `/readiness` RED #2.

Plan's body code samples (Step 3-5 EMIT_* macros) use 7-arg tuple (`kind_token, name, label, section, meta, payload, tooltip`); the full descriptor design + umbrella table specify 12-arg (adds `applies_to_strategy_cat`, `applies_to_op_mode_cat`, `applies_to_regime_cat`, `applies_to_risk_cat`, `lives_in_struct`). Consumer macros will silently drop trailing args if not reconciled.

**Fix:** Plan body's EMIT_* macros expanded to 12-arg.

### HIGH-3 — Layer 5b hash lock is premature at .F.4b
**Sources:** `/parity-check` F1.

`LOCKED_STAMP_BOUND_DERIVED_HASH_V5_15_5_F4` cannot meaningfully lock at .F.4b because `FOREACH_CFG_FIELD` only contains DOUBLE entries; the existing `FOREACH_STAMP_BOUND_CFG` (`ML_Headers/StampBoundCfgRegistry.hpp:99-176`) has 24 rows with 11 `int`-typed entries that don't migrate until .F.4c. Hash rotates at .F.4c → defeats Layer 5b's "lock against accidental reorder" intent.

**Options:**
- **(A)** Defer derived filter swap to .F.4c when all STAMP_BOUND fields are in FOREACH_CFG_FIELD. .F.4b implements the descriptor + dispatch infrastructure but doesn't flip `FOREACH_STAMP_BOUND_CFG` to derived view.
- **(B)** Pre-populate FOREACH_CFG_FIELD at .F.4b with no-op stub INT entries for the .F.4c-bound fields (lock now, fill payload at .F.4c).

Recommend (A) — cleaner separation; the derived filter is a structural win independent of when it lands. Update plan Deliverable A to reflect.

### HIGH-4 — Locale pinning missing from registry save path
**Sources:** `/parity-check` F2.

Status-quo SettingsPanel save (`GUI/SettingsPanel.hpp:472, 791-797`) + parser `atof` (`CoreFrameworks/ControllerConfig.hpp:1879, 1887, 1908`) are not locale-pinned today. Plan Step 2 + Step 5 for `tt::cfg_save_field<KIND_DOUBLE>` doesn't add `uselocale(LC_NUMERIC_MASK=C)`. Carries forward a status-quo bug.

**Fix:** Plan Step 2: tt::cfg_save_field<KIND_DOUBLE> + tt::cfg_parse_field<KIND_DOUBLE> use `parse_double_fast` (precedent: `StampBoundCfgRegistry.hpp:195`) + `newlocale` pinning per `MemHeaders/RunHistory.hpp:87-89`.

### HIGH-5 — Stretch goal "X-macro generates Cfg struct fields" infeasible
**Sources:** `/trace-deps` BL-3.

Depends on CRITICAL-1 type-dispatch resolution + risks bytewise-incompatible struct layout if registry ordering doesn't match existing struct line order.

**Fix:** Drop from .F.4b. Re-evaluate at .F.4d after KIND_INT/_BOOL validates the storage-discriminator pattern. .F.4d's reverse-drift CI script remains the documented fallback.

### HIGH-6 — SettingsPanel.hpp field_defs[] has hand-tuned operator prose
**Sources:** `/merge-scan` #1.

Pre-existing `CfgFieldDef` + `field_defs[]` at `GUI/SettingsPanel.hpp:35-306` has **109+ entries with multi-line tooltips, Discord/Telegram setup examples, operator-facing prose**. Migration must preserve BYTEWISE. Lines 297-303 already auto-extend via 5 domain CFG_FLAG registries — confirm coexist-during-transition for .F.4b (KIND_BOOL not migrated until .F.4c).

**Fix:** Plan Step 3: Add explicit migration table mapping each existing field_defs[] entry to its registry row + verify tooltip text byte-identical. Section-order merge spec needed (5 FOREACH_*_CFG_FLAG auto-extends + manual field_defs[] + new FOREACH_CFG_FIELD).

### HIGH-7 — `INFERENCE_CFG_AUTOPOPULATE` orthogonality concern
**Sources:** `/merge-scan` #2.

`FOREACH_CFG_DERIVED_INFERENCE_CFG` (v5.15.5.A.7, 11 entries) reads same cfg fields but writes to inf.inference_cfg_* for stamp emit. Overlaps ~7 cfg fields (`confidence_hard_block_threshold`, `held_out_fraction`, `bandit_blend_ratio`, `fee_rate_*`, `ml_tp_pct`, `ml_sl_pct`, `barrier_blend_mode`). Different consumer.

**Fix:** Document orthogonality in CfgFieldRegistry.hpp header design comment + queue CI parity check at .F.4d (no .F.4b code change required).
