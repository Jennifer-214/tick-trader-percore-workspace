## Mid-coding discoveries + design refinements (NOT in plan body v1.1)

### Discovery 1: Step 3 + Step 5 must defer to `.B.3` (PARITY-020 regression risk)

Plan body Step 3 described "1-line swap at StampHelper.hpp:183" as "behavior equivalent since legacy registry not deleted until .B.3". This was wrong — the swap WOULD lose 14 fields of inf population (new walker is 0-row at `.B.1`; legacy walker walks 14 active rows). Same logic for Step 5 (controller_test.cpp:24962-25047 A.7 tests).

**Resolution:** Both Steps deferred to `.B.3` Step 1.5 (newly-added; updates `.B.3` skeleton). At `.B.3`, legacy registry deletion forces the swap — by then new walker is non-empty (validated at `.B.2`).

### Discovery 2: X-macro filtered walker requires template fn wrapper (correct C++ if-constexpr discard)

Original Step 2 design used direct macro expansion `FOREACH_PER_CORE_CFG_FIELD(X_INFERENCE_CFG_POPULATE_PER_CORE)` with `if constexpr ((meta) & ...)` filter. Build verified at Step 6 testing: failed because **if-constexpr false branch must be SYNTACTICALLY VALID at non-template scope** — `inf.inference_cfg_<name>` for arbitrary row name caused name-resolution errors when `<name>` doesn't exist on StampInferenceCfgInputs (and won't, even after `.B.2` cohort migration adds 24 fields — master registry has 80+ rows).

**Resolution:** Wrap consumer macros in TEMPLATE FNs (`InfT`/`HandleT` template-dependent → if-constexpr false branch properly discarded from name resolution at instantiation). Macros become thin wrappers. Build clean.

**Future-oriented:** This shape is correct for the WHOLE framework, not a one-time syntax patch. Future consumer macros (`.F.4e` 5 GUI metadata consumers, etc.) inherit the template-fn-wrapper pattern. Caramel's question "is this the future-oriented fix?" — yes, both correctness + structural.

### Discovery 3: FAILURE_MASK_cfg_inference_drift doesn't exist (right symbol: FAILURE_MASK_cfg_binding_drift)

Plan body referenced `FAILURE_MASK_cfg_inference_drift` for drift check. Build verified: that symbol doesn't exist; correct mask per `CfgDriftCheckRegistry.hpp:104+162` is `FAILURE_MASK_cfg_binding_drift` (INFERENCE_CFG drift category maps to cfg_binding_drift).

**Resolution:** DRIFT_CHECK_FROM_DERIVED macro updated to use `FAILURE_MASK_cfg_binding_drift`. Caller context must have `MemHeaders/FailureModeRegistry.hpp` included.

### Discovery 4: FPN<F> doesn't have operator==

Test T4 + T6 originally used `inf_dst == cfg_src` for FPN<64> equality. Build verified: FPN<F> doesn't define operator==. Mirrors existing `cfg_diff_field<T>` for FPN which uses `!(current == default_fpn)` — that branch was never instantiated with FPN<F> until my new code exercised it.

**Resolution:** `tt::cfg_drift_compare<T>` FPN<F> branch uses `memcmp` (byte-exact integer-limb compare; H4 — never float math on accounting types); test T4 uses `memcmp(&inf_dst, &cfg_src, sizeof(FPN<64>))` directly.

### Discovery 5: Path γ #3 considered + rejected at Batch 3

`/merge-scan` meta-self-audit at Batch 3 flagged FOREACH_CFG_GATE sparse sidecar as potential Path γ #3 (single-column annotation in separate sidecar; could fold into master tuple). `/anti-spaghetti` at Batch 3 said GREEN.

**Resolution:** Caramel reviewed both verdicts. Initial recommendation flip-flopped (chose fold, then unflipped after deeper analysis). Final answer: KEEP sparse sidecar (boundary-stable + H18 single-column-sidecar is canonical per the pattern; master-tuple fold would be wide cascade). Banked TECH_DEBT entry "Evaluate fold-into-master tuple for cfg-derived gate_when as future structural" for `.F.4f` cleanup ship if it bothers operator later.

## Lessons captured

### Lesson 1 — Plan body Steps are HYPOTHESES, not gospel
3 of the 9 Steps in plan body v1.1 turned out to need correction at coding time:
- Step 3 + 5 deferred to `.B.3` (regression risk)
- Step 6 walker shape pivoted to template fn wrappers (correct C++)
- Step 4 enrollment count corrected (+2 not +5; consumer macros aren't FOREACH-shaped)

**Pattern:** plan body draft + audit gate verify the DIRECTION; coding time validates the SHAPE. Both phases produce findings. Postmortem captures coding-time discoveries; plan body amendments retroactively if structural.

### Lesson 2 — Template fn wrapper is the canonical shape for X-macro filtered walkers
Without template-dependent param types (InfT/HandleT), if-constexpr false branches require name resolution → fail when struct fields don't exist for filtered-out rows. Template fn wrapper defers analysis to instantiation → discard properly.

This applies to EVERY future X-macro filtered consumer. `.F.4e` 5 GUI metadata consumers will use this pattern. Document in `cfg-derived-consumer-framework.md` for future reference.

### Lesson 3 — The discipline gates caught + corrected what they should
- Path γ #1 caught at `.A` (`/merge-scan` Batch 0)
- Path γ #2 caught at `.B` Batch 1
- Path γ #3 candidate considered + rejected at `.B.1` Batch 3 (after operator deliberation)
- Step 3 + 5 regression risk caught at coding time (mid-Step verification)
- Walker shape issue caught at Step 6 build (~14 tests exercised the infrastructure)
- FPN<F> operator== issue caught at Step 6 build
- FAILURE_MASK symbol name caught at Step 6 build
- Plan body self-violation (missing "Canonical sister registries considered") caught at Batch 3 readiness audit

8 catches across the cycle. Each is a save. Compounds.

### Lesson 4 — Postmortem-deferred amendments are bankable scope
`.B.1` shipped with Step 3 + 5 explicitly deferred to `.B.3`. The `.B.3` skeleton was UPDATED at coding time (Step 1.5 added with deferral rationale + 30-min effort estimate). When `.B.3` codes, it has the deferral spec already; no surprise scope.

This is the per-sub-ship cycle working — defer doesn't lose work; it moves work to the right sub-ship.
