## Design pivots (each one surfaced something worth remembering)

### Pivot 1: Per-struct prefix (Option 2) → Full unification (Option 1)

**Trigger:** Mid-coding discovery that asymmetric naming was THREE-WAY across structs (ModelStampResult / StampInferenceCfgInputs / ModelHandle), not two-way as prior audits documented. ModelHandle's prefix policy was inconsistent across groups (`stamp_inf_` / `stamp_xgb_` / `stamp_label_` / `stamp_` / no-prefix).

**Decision:** Caramel chose Option 1 (full unification across all 3 structs to canonical wire-key names) over Option 2 (per-struct prefix in registry). Reasoning: Option 1 is the only choice that closes TECH_DEBT-006 entirely. Options 2/3/4 leave residual asymmetry → TECH_DEBT-014 surfaces in 6-12 months with same recurring-class shape.

**Caramel framing:** "this level of engineering is good though, because it reduces the complexity a lot when adding new stuff". Codified as `feedback_overengineering_boundary_when_future_easier.md` in memory.

**Cost:** ~14 files mechanical migration (vs ~6-8 for Option 4). Extra ~6-8 files are ModelHandle's caller-side accessors going from `m->stamp_inf_X` → `m->X`. All find-replace.

**Going-forward rule candidate:** When a design decision is borderline overengineered today but makes future work substantially easier, weight future-work-simplification heavily. Sister to `feedback_structural_fix_for_recurring_class.md` but applies even without recurring bug — pure forward-looking maintainability is enough justification.

### Pivot 2: Separate sub-tags A.2-A.5 → Coupled v5.14.8.A.merged

**Trigger:** `/merge-scan` audit recommended coupling because parser/emitter pair share 70%+ body overlap. Single registry refactor drives struct + parser + emitter + bit-pack from one X-macro pass. Wire-format provable in ONE diff.

**Decision:** Couple A.2+A.3+A.4+A.5 into v5.14.8.A.merged. Saves ~60 LOC, makes wire-format byte-for-byte preservation provable in single diff. Pre-flight ship v5.14.8.A.0.b inserted as foundation.

**Trade-off accepted:** Larger blast radius if anything goes wrong. Mitigated by: pre-tag rollback anchor before A.merged starts; A.7 round-trip HMAC test verifies wire format post-merge.

### Pivot 3: PRESENCE bitmask column → Token-paste dispatch

**Trigger:** Mid-implementation realization that preprocessor arithmetic on bitmask integers can't conditionally suppress macro expansion (struct member declarations aren't `constexpr` expressions).

**Decision:** Token-paste dispatch via INCLUDE / SKIP_HANDLE markers. Same end-state behavior; cleaner implementation; extends to new markers via single `STAMP_HANDLE_GEN_<MARKER>` macro definition.

**Documented in:** `DESIGN_SPECS/x-macro-registry-with-presence-dispatch.md` (DESIGN_SPECS doc 1).

### Pivot 4: STAMP_MODEL_CONST_PARSE_<type> macros → `if constexpr` type dispatch

**Trigger:** Adding the 3 missing registry entries surfaced that legacy per-type PARSE macros were incomplete (no uint8_t / uint32_t / char_array variants).

**Decision:** Use C++17 `if constexpr` + `std::is_array_v` / `std::extent_v` / `std::is_floating_point_v` / `std::is_unsigned_v` for compile-time type dispatch in the AUTOPOPULATE macro. New type addition = 1 new `if constexpr` branch; no per-type STAMP_MODEL_CONST_PARSE_<X> proliferation.

**Bonus:** char[N] string fields become first-class via `tt::stamp_str_N` typedefs. Detection via `std::is_array_v` is bulletproof.

### Pivot 5: STANDALONE list (2-site maintenance) → Per-entry has_* mechanical derivation

**Trigger:** While planning A.merged Commit 2 (struct migration), realized the STANDALONE list was a parallel maintenance surface (1 row in FOREACH + 1 row in STANDALONE = 2-site update per addition). Same N-site bug class we're trying to extinguish.

**Decision:** Drop STANDALONE list entirely. Standalone entries' has_* names mechanically derived from entry name (e.g., `has_inference_cfg_bandit_blend_ratio` instead of short `has_bandit`).

**Trade-off:** Verbose has_* names for some standalones. Accepted because:
- Mechanically discoverable; no mental lookup table
- IDE auto-completes; verbosity is one-time annoyance at write
- Eliminates 2-site maintenance bug class

**Going-forward rule candidate:** Multi-site maintenance is the bug class we extinguish via X-macro patterns. Don't introduce NEW multi-site lists when designing a registry; mechanical derivation is mandatory.

### Pivot 6: Per-entry has_* (Option C) vs Group has_* (Option B) for storage

**Trigger:** When defining the bit allocation for the unified `has_flags` uint64_t, two valid designs:
- Group bits (~13 total): one bit per group, set when ANY entry in group is populated
- Per-entry bits (~25 total): one bit per entry, AUTOPOPULATE sets each independently

**Decision:** Option B (group bits). Reasons:
- Wire-format byte-for-byte preservation: emit semantics unchanged (5 inference_cfg lines emit together iff has_inference_cfg=1)
- Smallest data-oriented footprint (13 bits)
- Caller migration minimal (existing has_<group> sites match canonical)
- AUTOPOPULATE_ONE dispatches via token paste on group column (clean macro infrastructure)

**Future flexibility preserved:** If a future ship needs per-entry granularity (Option C semantics), it's a registry-driven migration. No architectural lock-in.

**Documented in:** This postmortem + `DESIGN_SPECS/x-macro-registry-with-presence-dispatch.md`.

## Going-forward rule candidates (extract to CLAUDE.local.md at v5.14.8.F)

1. **Multi-site maintenance is the bug class to extinguish** — when designing a registry, ANY parallel maintenance surface (sub-FOREACH, STANDALONE list, etc.) is a future bug. Mechanical derivation is mandatory; verbose names are an acceptable cost.

2. **Compaction-degraded handoffs lose precision** — verify every concrete claim (function signatures, struct field paths, registry contents, file:line citations) against current code state before acting. Already in `feedback_compaction_degrades_treat_handoffs_as_hints.md`; reinforced by Surprises 3, 4, 5.

3. **Run `/parity-check` post-data-population** — registry data ships separately from registry consumers. Always re-verify data completeness vs canonical wire format BEFORE consumers compile.

4. **Plan code snippets need compilation verification** — plan-text snippets with concrete signatures should be smoke-checked against current headers. Especially for plans inherited across compacted sessions.

5. **DESIGN_SPECS captured DURING the work, not after** — extract reusable patterns to `DESIGN_SPECS/` as they're solved. Cheaper than reconstructing from chat logs.

6. **Audit-driven pre-coding gate** — for ships closing recurring bug classes structurally, run 4 audits in parallel (parity-check + trace-deps + readiness + merge-scan) on the plan BEFORE coding. Each catches a different class of gap. Worth ~10 min vs hours of mid-coding redirects.
