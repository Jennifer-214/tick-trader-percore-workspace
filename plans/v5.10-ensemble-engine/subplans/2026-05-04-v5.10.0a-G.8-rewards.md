# v5.10.0a.G.8 — Dual-source reward wiring (slow-path lookback + trade-close)

**Date:** drafted 2026-05-04
**Branch:** `feat/v5.10-foundation`
**Predecessor:** v5.10.0a.G.7
**Effort estimate:** ~3h
**Hot path:** UNTOUCHED (rewards computed in slow-path / drainer paths)

## Theme

Bandits learn from observed outcomes. Two reward streams:
1. **Slow-path lookback (DENSE):** every poll_interval, walk a ring
   buffer of recent predictions. For records old enough that
   `forward_ticks` have elapsed: reward each arm based on whether
   its prediction direction matched the actual price move.
2. **Trade-close (SPARSE, HIGH-FIDELITY):** when a position closes
   (TP/SL exit), look up the entry-time prediction record. Reward
   each arm based on REALIZED P&L direction. Higher weight than
   slow-path (real money, includes fees + slippage).

Both feed `Bandit_Update` per arm; weights compound. Regime ID
attribution uses the regime AT PREDICT TIME (stored in prediction
record), not the current regime.

## Items

### #1 — Prediction ring buffer (~45min)

New per-core ring in `EnsembleModelZoo`:

```cpp
struct EnsemblePredictionRecord {
    uint64_t tick_index;        // global tick at prediction time
    int      regime_id;         // regime at prediction time
    float    predictions[ENSEMBLE_HORIZON_MAX];   // per-arm raw output
    float    sample_price;      // price at prediction time (for delta calc)
};

#define ENSEMBLE_REWARD_RING_SIZE 256   // typical: forward_ticks/poll_interval + slack
```

Add to `EnsembleModelZoo<F>`:
```cpp
EnsemblePredictionRecord reward_ring[ENSEMBLE_REWARD_RING_SIZE];
int reward_ring_head;       // next write slot
int reward_ring_count;      // populated entries (< RING_SIZE)
```

Per BuySignal call (post-prediction): write to reward_ring at head,
advance head modulo RING_SIZE.

### #2 — Slow-path lookback reward computation (~1h)

New helper, called from MLStrategy_Adapt or slow-path rebuild:

```cpp
template <unsigned F>
inline void EnsembleModelZoo_TickRewardsFromLookback(
    EnsembleModelZoo<F>* ezoo,
    uint64_t current_tick,
    float current_price,
    int forward_ticks);   // from cfg
```

Walks ring backward from head. For each record where
`current_tick - record.tick_index >= forward_ticks` AND record
hasn't been processed yet (track via `last_rewarded_ring_idx`):

```cpp
double price_delta = (current_price - record.sample_price) / record.sample_price;
int regime = record.regime_id;
for (int arm = 0; arm < n_arms; ++arm) {
    double pred = record.predictions[arm];
    // Binary case: prediction > 0.5 = "buy", < 0.5 = "sell" (or "no-buy")
    // Reward = +1 if direction matched price move, 0 otherwise
    int correct = ((pred > 0.5) == (price_delta > 0)) ? 1 : 0;
    double reward_bps = correct ? 1.0 : 0.0;
    Bandit_Update(&ezoo->bandits[regime], arm, reward_bps);
}
```

Track `last_rewarded_ring_idx` to avoid double-rewarding.

**Edge cases:**
- Insufficient lookback (current_tick < forward_ticks): no rewards yet
- Regression labels: use sign of (pred) vs sign of (price_delta) instead

### #3 — Trade-close reward hook (~45min)

Hook into the post-fill drainer (`OrderManager_DrainPostFill` or
similar). When a position closes:
1. Look up the entry-time prediction record (match by entry tick_index)
2. Compute reward from realized P&L direction
3. Apply higher weight (×4 default) to this reward
4. `Bandit_Update` per arm using stored predictions

```cpp
// In drainer / post-fill handler:
if (position_closed && ezoo->active) {
    EnsemblePredictionRecord* record = lookup_by_entry_tick(ezoo, entry_tick_index);
    if (record) {
        double pnl_dir = realized_pnl > 0 ? 1.0 : -1.0;
        double reward_mult = cfg.ensemble_trade_reward_mult;  // default 4.0
        for (int arm = 0; arm < n_arms; ++arm) {
            double pred = record->predictions[arm];
            // Same direction match logic as lookback path
            int correct = ((pred > 0.5) == (pnl_dir > 0)) ? 1 : 0;
            double reward = correct ? reward_mult : 0.0;
            Bandit_Update(&ezoo->bandits[record->regime_id], arm, reward);
        }
    }
}
```

**Position-close hook location (verified 2026-05-04 via /plan-check):**
- **Live + backtest:** `EventLoop_DrainPostFill` at
  `CoreFrameworks/ControllerEventLoop.hpp:983` (wrapper that iterates
  per-core; consumes FillRecords + masks populated by
  `OrderManager_HandleFill`).
- Hook fires after `OrderManager_HandleFill` writes a SELL fill
  record (position close); `EventLoop_DrainPostFill` is the natural
  per-core post-close callback site.
- Per-core: each call processes one core's fill queue; per-core
  ezoo lookup via core_id index.
- Backtest path: `ShardedBacktestDriver::on_tick` calls
  `EventLoop_DrainPostFill` after `OrderManager_Tick` (mirrors live
  per v4.7.15's drainer pattern).

### #5 — Per-horizon drift watchdog (~1h, perf optimization #3)

Every horizon tracks rolling 24h IC (Information Coefficient). If a
horizon's IC tanks below `confidence_ic_floor` (cfg from v5.10.0e),
fast-demote that horizon's weight to ~0 across ALL regimes. Operator
escape from a horizon that's gone bad without manual intervention.

```cpp
// EnsembleModelZoo extension (G.7 struct + this):
struct PerHorizonDriftState {
    float    ic_history[CONFIDENCE_IC_HISTORY_MAX];
    int      ic_history_count;
    float    ic_24h_avg;
    int      demoted;                  // 1 = weights forced to 0; sticky
    uint64_t demoted_since_tick;       // for ML Status panel display
};
PerHorizonDriftState drift[ENSEMBLE_HORIZON_MAX];

// On reward (slow-path lookback or trade-close), update per-arm IC:
double ic_contribution = correct ? 1.0 : -1.0;
ezoo->drift[arm].ic_history[ezoo->drift[arm].ic_history_count++ %
                              CONFIDENCE_IC_HISTORY_MAX]
    = (float)ic_contribution;
ezoo->drift[arm].ic_24h_avg = compute_rolling_avg(...);

// Check for demote condition:
if (ezoo->drift[arm].ic_24h_avg < cfg.confidence_ic_floor &&
    !ezoo->drift[arm].demoted) {
    // Force this horizon's weight to ~0 in ALL regimes
    for (int r = 0; r < NUM_REGIMES; ++r) {
        Bandit_ForceWeight(&ezoo->bandits[r], arm, 0.001);
    }
    ezoo->drift[arm].demoted = 1;
    ezoo->drift[arm].demoted_since_tick = current_tick;
    fprintf(stderr, "[ensemble] DRIFT-WATCHDOG: horizon %d demoted "
                    "(IC=%.4f below floor %.4f); weights forced to 0 "
                    "across all regimes.\n",
            ezoo->horizon_ticks_at_idx[arm],
            ezoo->drift[arm].ic_24h_avg,
            cfg.confidence_ic_floor);
}

// Recovery: if IC recovers above floor + 0.02 hysteresis margin,
// allow re-promotion (un-demote). Manual reset (G.10 button) also
// clears demoted flag.
if (ezoo->drift[arm].demoted &&
    ezoo->drift[arm].ic_24h_avg > cfg.confidence_ic_floor + 0.02f) {
    ezoo->drift[arm].demoted = 0;
    fprintf(stderr, "[ensemble] horizon %d recovered (IC=%.4f); "
                    "weight allowed to re-learn.\n", ...);
}
```

**Coordinates with v5.10.0e** (drift detection sub-ship; defers to its
`confidence_ic_floor` cfg). Once v5.10.0e ships, the watchdog is
turn-key.

**New helper needed in BanditLearning.hpp:** `Bandit_ForceWeight(state,
arm, value)` — overrides the bandit's natural exp-update with a
forced weight. Used only for demote/promote.

## Risk register

| Risk | Mitigation |
|---|---|
| Ring buffer overflow when poll_interval × RING_SIZE < forward_ticks | RING_SIZE = 256 with default poll_interval=100, forward_ticks=1000 → 256 × 100 = 25600 ticks of lookback. More than enough. WARN at boot if ring_size < forward_ticks/poll_interval. |
| Reward attribution race (record cleared before reward computed) | last_rewarded_ring_idx tracks per-record; record stays in ring until overwritten by N more predictions. With RING_SIZE=256, plenty of slack. |
| Trade-close reward fires for every fill (multi-position double-counting) | Hook only on position CLOSE (TP/SL exit), not entry. Only one close per position. |
| Lookback reward fires per slow-path: O(ring_size) check per slow-path | RING_SIZE=256, slow-path frequency = poll_interval (≈100 ticks). 256 checks per 100 ticks = 2.56 checks/tick. Negligible vs feature compute. |
| Bandit_Update with reward=0 still counts as update (warmup gate) | Bandit warmup tracks N_updates; reward=0 IS an update (just doesn't shift weights up). Test G.8.3 verifies. |
