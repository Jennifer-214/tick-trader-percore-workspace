## Theme

Add `FPN<F=32>` template specialization (2048-bit total = 32 uint64
words = half the cache footprint of F=64 4096-bit). Opt-in per call
site; non-precision-critical sites (regime signals, flow features,
GUI display copies) can shrink to 2x cache density.

**Boundary policy** (per CLAUDE.local.md "boundary-stable refactors"
rule + memory file `feedback_reduce_touch_sites.md`): keep `F=64` at
all PUBLIC boundaries (TradeEvent, GateParameters, Position struct,
snapshot fields). Convert to `F=32` ONLY inside slow-path
computations where memory bandwidth dominates over precision.
Conversion at boundaries via existing `FPN_FromFP64` /
`FPN_ToFP64` (`FixedPoint/FixedPointN.hpp:400`, `:414`) + new
`FPN_Convert<F_from, F_to>` template helper.

**Cascade count:** ~3 conversion sites (slow-path inputs from
RollingStats; regime classify body; back-conversion to
GateParameters). Within the 1-3 file rule. NO cascade.

**Step 0:** Add to `FixedPointN.hpp` end-of-file:

// v5.12.2.C: explicit instantiations to verify F=32 compiles.
// Slow-path opt-in only; gated by cfg.slow_path_use_fpn32.

Verify each template at F=32 (sites already verified in master plan

- `FPN_MagAddN<32>` at `:85` → 32 words instead of 64; AVX-512 path

**Tests** (+5):
1. `FPN<32>` compile-test (template instantiation succeeds; static

## Phase B — `FPN_Convert<F_from, F_to>` boundary helper (`v5.12.2.C.2`)

**Goal:** Single template helper for F=32 ↔ F=64 conversion at
boundary sites. Uses `FromDouble`/`ToDouble` round-trip through
double — acceptable for slow-path tolerance.

**Step 0:** Add to `FixedPointN.hpp` adjacent to existing
`FPN_FromFP64` / `FPN_ToFP64` at `:400` / `:414`:

```cpp
// v5.12.2.C: F-to-F cross-conversion via double intermediate.
// Acceptable for slow-path tolerance (precision loss bounded by F_to
// fractional bits). NOT for hot path — hot path stays F=64 throughout.
template <unsigned F_to, unsigned F_from>
inline FPN<F_to> FPN_Convert(FPN<F_from> v) {
    return FPN_FromDouble<F_to>(FPN_ToDouble<F_from>(v));
}
```

Specializations at compile-time guarantee:
- `FPN_Convert<64, 64>(x)` = `x` (no-op via constexpr `if`)
- `FPN_Convert<32, 32>(x)` = `x` (no-op)
- `FPN_Convert<32, 64>(x)` = lossy (F=32 has 9 fewer decimal digits;
  fine for slow-path)
- `FPN_Convert<64, 32>(x)` = lossy back-conversion

**Tests** (+3):
1. F=32 → F=64 → F=32 round-trip preserves value within F=32 ulp
2. Identity convert (same F) is no-op (compiler should optimize via
   constexpr)
3. Conversion at boundary numbers (max int, min frac, negative)
   stays within tolerance

**Tag:** `v5.12.2.C.2`.

## Phase C — Cfg-gated F=32 at 3 slow-path sites (`v5.12.2.C.3`)

**Goal:** Add `cfg.slow_path_use_fpn32` (default 0). When 0, all
slow-path math stays F=64 (current behavior, bytewise unchanged).
When 1, 3 specific sites use F=32 internally with boundary
conversions.

**Cfg field:**
```cpp
// CoreFrameworks/ControllerConfig.hpp adjacent to other slow-path
// optimization flags
int slow_path_use_fpn32;  // 0 = use F=64 throughout (default)
                          // 1 = use F=32 in slow-path internal math
```

**3 conversion sites** (the entire cascade):

**Site 1: `Regime_ComputeSignals` (`Strategies/RegimeDetector.hpp`).**
Inputs come from RollingStats at F=64; signals are output at F=64.
INTERNAL math (variance, slope, EMA spread, etc.) can be at F=32.

```cpp
// Strategies/RegimeDetector.hpp inside Regime_ComputeSignals
if (cfg.slow_path_use_fpn32) {
    // Convert inputs to F=32; do internal math; convert outputs back
    auto rs32 = FPN_Convert<32, 64>(rs->price_avg);
    auto stddev32 = FPN_Convert<32, 64>(rs->price_stddev);
    // ... internal math in F=32 ...
    out->slope = FPN_Convert<64, 32>(slope32);
    out->variance = FPN_Convert<64, 32>(variance32);
    // ... etc.
} else {
    // existing F=64 path unchanged (bytewise baseline preserved)
    // ... existing code ...
}
```

**Site 2: `FlowState_Push` (`ML_Headers/FlowFeatures.hpp:156`).**
Already uses double internally per v5.10.0b boundary-stable refactor.
At F=32 mode, the flow EWMAs convert to F=32 storage but math stays
double. Memory savings only.

**Site 3: GUI display copy `TUISnapshot_Build`
(`DataStream/EngineTUI.hpp` near `:1719`).** PerCoreSnap fields that
ARE displayed as decimals (price, balance, ratio) can be stored as
F=32 in the snapshot; converted from F=64 source. Cuts snapshot
struct size by ~30%.

**Tests** (+5):
1. cfg=0 → output bytewise identical to v5.11.65 baseline (Phase C
   preserves baseline at default)
2. cfg=1 → regime classification matches baseline within tolerance
   (regime histogram comparison; document tolerance)
3. cfg=1 → flow features match baseline within F=32 ulp
4. cfg=1 → snapshot displays correct values (no obvious drift in GUI)
5. Operator-validation gate: replay 10M ticks at cfg=1 → final P&L
   within 0.05% of cfg=0 baseline (parity-tolerable; actual tolerance
   threshold to be set during validation)

**Tag:** `v5.12.2.C.3`.

## Accounting for prior ships

**v5.12.2.A (AVX-512 RollingStats):** vectorized F=64 paths. F=32
gets scalar by default; if profiling shows F=32 is hot enough to
warrant its own AVX-512 path, that's a future phase (4×8 = 32 words
= 4 `__m512i` loads — easier than F=64's 8 loads). Captured as
follow-up note.

**v5.12.2.B (lazy rebuild):** orthogonal. F=32 affects what's
computed when rebuild fires; lazy affects whether rebuild fires.
Wins compound.

**v5.12.1.X:** orthogonal — Phase 1 doesn't touch FPN math.

## Accounting for next ships

**v5.12.2.D (Treelite AOT):** orthogonal — AOT replaces XGBoost C
API; doesn't see FPN math.

**Phase 3:** features pack reads RollingStats at F=64 boundaries;
F=32 internal use is invisible above the boundary. No interaction.
