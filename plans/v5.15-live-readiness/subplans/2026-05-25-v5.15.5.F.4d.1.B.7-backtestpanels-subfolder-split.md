## Design space + future-oriented choices

### Decision A — Sub-file boundary (panel-per-file vs other shapes)

| Option | Description | Verdict |
|---|---|---|
| **(a) Panel-per-file** (one sub-file per Backtest panel) | TrainModel / WalkForward / MultiHorizonCollect / MultiHorizonTrain / Replay / Optimizer / HeldOut + Common | **CHOSEN** |
| (b) Worker-fn-per-file (one sub-file per worker thread) | walkforward_worker / train_model_worker / train_multi_horizon_worker / etc. | rejected — workers are dispatch units; panels are operator-visible units; panel-cohesion > worker-cohesion |
| (c) Single-page subfolder (panels grouped by GUI page / tab) | Training-tab / Validation-tab / Optimization-tab | rejected — pages cross-cut panels; less natural |
| (d) By concern (Cfg / Render / Worker) horizontally across panels | One sub-file per concern dimension; each contains snippets from each panel | rejected — fragments per-panel cohesion; harder to reason about a panel as a unit |

**Rationale for (a):** Panels are the operator's mental model ("the Train Model panel does X"); workers are implementation detail. Future panel additions slot into NEW sub-file naturally. Each panel sub-file owns its ImGui state + dispatch + worker — cohesive unit.

### Decision B — Multi-Horizon split granularity (Collect vs Train)

Multi-Horizon has 2 distinct modes:
- **Collect Features** — generates feature CSV from historical ticks per horizon grid
- **Train Multi-Horizon** — trains XGBoost models per horizon grid + emits per-horizon stamps (post-`v5.15.3` `.B.4` fixes)

Each is likely ~800-1500 LOC. Decision rule:

| Combined LOC | Action |
|---|---|
| ≤ 1,500 | Single `MultiHorizon.hpp` containing both |
| 1,500 - 2,000 | Single file with TRIM evaluation (remove cruft to fit under threshold) |
| > 2,000 | **Split into `MultiHorizonCollect.hpp` + `MultiHorizonTrain.hpp`** |

Default plan assumes > 2,000 LOC (per current monolith structure); decided at Phase B Step B.1 after measuring.

### Decision C — Shared helpers placement (Common.hpp scope)

Shared across panels:
- `WorkerArgs` struct family (each worker has its own args struct; some commonality)
- Progress-reporting state (operator-visible progress bar state)
- XGBHyperparams struct + apply helper (used by Train Model + WalkForward + Multi-Horizon + Optimizer)
- Dispatch helpers (worker thread spawn / join / cleanup utilities)

**Common.hpp scope:** ONLY truly-universal helpers. Panel-specific helpers stay with their panel. Estimated size: 300-700 LOC.

**Anti-pattern to avoid:** Common.hpp becoming the "junk drawer" sub-file containing anything not obviously panel-specific. Phase B audit: every Common.hpp entry must be used by ≥ 2 panels OR be a foundational primitive (XGBHyperparams).

### Decision D — Include order in shim (dependency-driven)

Expected dependency graph (verified at Phase B Step B.1):
1. `Common.hpp` — shared helpers; NO internal deps
2. `TrainModel.hpp` — depends on Common
3. `WalkForward.hpp` — depends on Common
4. `MultiHorizonCollect.hpp` — depends on Common
5. `MultiHorizonTrain.hpp` — depends on Common (maybe MultiHorizonCollect for shared state)
6. `Replay.hpp` — depends on Common
7. `Optimizer.hpp` — depends on Common (likely depends on WalkForward — sweeps multiple WF runs)
8. `HeldOut.hpp` — depends on Common

Shim include order: `Common.hpp` first, then panels in arbitrary order (no cross-panel deps expected; verified at Phase B).

If cross-panel deps surface (e.g., Optimizer reuses WalkForward worker), include `WalkForward.hpp` before `Optimizer.hpp`. If circular dep (Optimizer ↔ WalkForward), refactor by extracting shared worker to `Common.hpp`.

### Decision E — Foxml_suite linkage discipline

`foxml_suite` binary (GUI suite build) links BacktestPanels.hpp. Post-split:
- Shim re-export preserves `#include "Backtest/BacktestPanels.hpp"` at foxml_suite TU
- foxml_suite's CMakeLists.txt target list shouldn't change (still depends on the .hpp via include)
- Verify foxml_suite builds clean post-split (Phase C Step C.3 — already in standard verification)

### Decision F — Decoupling positioning (informational)

Per `plans/_future/2026-05-12-decoupling-endgoal-roadmap.md`: at v6.0 decoupling, runtime + viewer + training binaries split. BacktestPanels currently lives in `foxml_suite` binary (training-side). Post-split, `Backtest/BacktestPanels/` becomes the natural training-binary boundary — cleaner API surface for v6.0.

**Positioning:** ⬆️ POSITIVE for v6.0 viewer split.

## Pre-coding concerns

1. **ImGui widget ID collisions** — panel widgets use `PushID`/`PopID` for unique IDs. Splitting panels into sub-files shouldn't affect ID stack (per-panel scope), but verify at Phase B that no panel's ID stack relies on inclusion-order side effects.
2. **Worker thread lifetime** — worker threads spawned by panel dispatch logic outlive the panel render. State structs (e.g., `WalkForwardWorkerArgs`) must remain accessible after panel hides. Post-split: state struct definitions move with their panel; worker fn definitions too; storage allocation (likely heap via `make_shared` or static) unchanged.
3. **XGBHyperparams shared across panels** — Train Model + WalkForward + Multi-Horizon + Optimizer all use this struct. Common.hpp ownership. Verify Phase B B.3 extracts cleanly.
4. **Cross-panel dispatch** — Optimizer panel may spawn WalkForward workers (Hyperparam Sweep iterates over WF configs). If Optimizer.hpp depends on WalkForward.hpp, include WalkForward first in shim; verify no circular dep.
5. **foxml_suite linkage** — foxml_suite is the primary consumer; verify GUI builds clean after each panel extract (Phase B Step Bx verify includes foxml_suite build).

## Risks + mitigations

### R1 — Biggest single header in codebase; extract sequence has most steps

**Mitigation:** Per-panel incremental discipline (Phase B Steps B.4-B.10 each handles one panel + verify); 8 panel extracts vs `.B.6`'s 4 sub-file extracts. Build cost per step low; cumulative time manageable.

### R2 — foxml_suite GUI rendering regression

**Mitigation:** Phase C Step C.3 manual GUI verification (operator launches foxml_suite + clicks through each panel). If post-split panel doesn't render, rollback to per-panel pre-tag (Phase B per-step git commits enable surgical rollback).

### R3 — ImGui state struct discipline at split

**Mitigation:** Panel state structs stay with their panel sub-file (DOD discipline preserved). `/dod-audit` Phase A + Phase C verifies cluster alignment intact.

### R4 — Worker thread cross-references after split

**Mitigation:** Worker fns move with their panel; shared WorkerArgs family go to `Common.hpp`. Phase B per-step build verify catches any orphan reference.

### R5 — Optimizer panel cross-dep on WalkForward

**Mitigation:** Shim include order — `WalkForward.hpp` before `Optimizer.hpp`. If true circular dep surfaces (rare; would indicate design flaw not just split issue), extract shared worker to `Common.hpp`.

### R6 — Multi-Horizon mode merge-or-split decision (Decision B)

**Mitigation:** Phase B Step B.1 LOC measurement + Decision B rule (combined > 2,000 → split). Decision deterministic given measurement.
