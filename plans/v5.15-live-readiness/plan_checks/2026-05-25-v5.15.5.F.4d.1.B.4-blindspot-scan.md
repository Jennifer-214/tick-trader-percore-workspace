# /blindspot-scan — v5.15.5.F.4d.1.B.4 (train-serve execution-layer parity structural extract)

M4 IMPLEMENTATION-DETAIL-layer audit of the .B.4 plan body, fired AFTER /precoding-audit-gate (SHAPE-layer audits). SHAPE audits answer "is the design right?"; THIS audit answers "will the code compile/run without surprise at implementation-detail layer?".

**Verdict:** YELLOW-with-amendments. Plan body v1.0 is structurally sound; the 12-category walk surfaces 4 SILENT-RISK issues + 2 LOUD-but-late issues that warrant plan-body amendments BEFORE Phase B helper-body extract.

## Headline findings (top 5; punch-list at bottom)

1. **B11 SILENT-RISK** — Helper signature `template <unsigned F>` is OK for `if constexpr` body filtering, BUT `EngineCommon_BootPerCore` body inherits 50+ `static` storage-class objects (g_user_data / g_notify_state / g_tick_rec / g_depth_shared / g_init_arena / g_reconciler / etc.) currently inlined in EngineSharded_Run. These cannot move into the helper body — they're file-scope statics. Helper must accept these by-pointer OR plan must explicitly carve out a separate `EngineCommon_BootGlobalAsync` helper.

2. **B14 (NEW; train-serve execution parity) SILENT-RISK** — Backtest's `fc_ctx.regime_state` (BacktestSharded.hpp:541-548) is a SINGLE shared regime state used by the feature collector lambda (line 607-612), distinct from per-core `state.cores[i].regime_state` (line 211). Plan body Pre-coding concern #6 mentions making `fc_ctx.regime_state` a `[MAX_EXECUTION_CORES]` array but does NOT address that the feature collector lambda CAPTURES `fc->regime_state` by-pointer and uses ONE regime classification per feature row. If we just turn it into an array, which index does Features_PackAll consume? Plan amendment needed: either (a) feature collector takes regime from `state.cores[c].regime_state` directly (canonical sister; closes PARITY-031 properly), OR (b) document why the feature collector intentionally uses a global regime (and how that pairs with per-core regime_class_onehot training).

3. **B7 SILENT-RISK** — `CoreFrameworks/EngineCommon.hpp` proposed as NEW header that both `EngineSharded.hpp` (CoreFrameworks/) AND `BacktestSharded.hpp` (Backtest/) include. Currently `BacktestSharded.hpp` includes `../CoreFrameworks/ShardedBacktestDriver.hpp` and `EngineSharded.hpp` includes `../Strategies/StrategyLifecycle.hpp`. New helper needs `EventLoopState<F>*` + `OrderManagerState<F>*` types + `ControllerConfig<F>` cfg + `Strategy_InitPerCore` + `EventLoopState_ConfigureKillSwitch` + `ConfidenceScorer_BindCompositeCfg` + `RollingTurnover_Init` + `CoreModelZoo_LoadFromDir` + `EnsembleModelZoo_AutoDetectFromDir` + `CoreModelZoo_PostLoadSetup` + `CoreModelZoo_ValidateAgainstCfg` + `FeatureOverlay_PostLoadVerify` + `BITMAP_IS_SET` + cfg flag macros. Include surface is LARGE. Plan amendment: enumerate required includes in plan body Step A.1 BEFORE skeleton lands.

4. **B1 LOUD-but-LATE** — Helper signature uses `OrderManagerState<F>* oms` as nullable. But EngineSharded_Run boot code reads `&oms.ws_result_queue` (line 777), `oms.trade_log = &g_sharded_trade_log` (line 712), `oms.on_entry_fill_emit = ...` (line 716-717), `oms.ezoo_refs[i]` (line 1078), `oms.core_cfg_refs[i]` (line 1079) — all of which presuppose `oms != nullptr`. If backtest passes oms (which it does per BacktestSharded.hpp:160-189), nullable-arg semantics don't reduce per-call-site exemptions. Either (a) make `oms` non-nullable (helper requires OMS) OR (b) plan body must enumerate which call paths through the helper assume nullability vs not.

5. **B5 SILENT-RISK** — Template instantiation: `EngineCommon_BootPerCore<F=64>` will instantiate ~150-250 LOC of body for both `<F=64>` (live) AND `<BACKTEST_FP>` (backtest, currently also =64 per BacktestSharded.hpp BACKTEST_FP define). Need to verify BACKTEST_FP value at .B.4 coding time — if same as live (64), only ONE instantiation. If divergent, TWO instantiations + per-site verification. Plan amendment: explicit assertion in plan body Step A.1 that `BACKTEST_FP == F` for the canonical case.

### B11 — Context-dependent C++ construct (if-constexpr template-context requirement)

**Verdict:** SILENT-RISK (HIGH severity for code organization).

Helper signature `template <unsigned F> void EngineCommon_BootPerCore(...)` IS template-context, so `if constexpr` body filtering works fine.

**BUT** — boot body inherits ~50 function-scope `static` storage objects from EngineSharded_Run:

```
static ShardedTradeLog g_sharded_trade_log; (line 710)
static BinanceUserDataState g_user_data; (line 767)
static NotifyState g_notify_state; (line 794)
static NotifyCommandState g_notify_cmd_state; (line 795)
static TickRecorder g_tick_rec; (line 826)
static DepthRecorder g_depth_rec; (line 834)
static DepthSharedState<F> g_depth_shared; (line 835)
static pthread_t g_depth_tid; (line 836)
static ReconciliationLoopState<F> g_reconciler; (line 861)
static InitArena g_init_arena; (line 731)
static SPSCRing<Tick<F>, EXECUTION_CORE_TICK_RING_SIZE> tick_rings[MAX_EXECUTION_CORES]; (line 877)
static ExecutionCore<F> cores[MAX_EXECUTION_CORES]; (line 878)
... plus many more
```

These CANNOT move into helper body verbatim because:
- Function-scope static in template fn = ONE static per template instantiation (per-F). If helper is instantiated for `<F=64>` (live) AND `<BACKTEST_FP=64>`, you get TWO sets of these statics with one set per F-value — but they're the SAME F-value type, so the C++ compiler will actually merge them at the same address (single instantiation), masking the gotcha.
- BUT: if `BACKTEST_FP != F`, you get TWO INDEPENDENT static sets, and live engine's `g_user_data` becomes detached from backtest's `g_user_data`. Subtle.
- More critically: these statics are CURRENTLY scoped to EngineSharded_Run. Moving them into a helper-fn-scope static means EngineSharded_Run's OTHER references to them (e.g., line 1078 `oms.ezoo_refs[i]` setup happens INSIDE helper but later code at line 1418+ references `g_shared`, `g_engine_sharded_shutdown`, etc. that live OUTSIDE helper) need pointer-passing OR these statics must STAY in EngineSharded.

**Concrete amendment:** Plan body Decision A needs sub-decision: "What scope do per-core boot statics live at after extract?"

Options:
- (a) Helper takes pointers to all required static objects (large signature; mechanical)
- (b) Helper has its own statics (different storage; backtest gets DIFFERENT instances of g_*; verify no asymmetry)
- (c) Statics STAY in EngineSharded_Run; helper only does the per-core-LOOP work and is called UNDER the static initialization (cleanest; minimizes signature growth)

Recommend (c). Verify boot order: helper called per-core after `static` initialization at line 731-878.

This is the LARGEST implementation-detail concern not addressed in plan body v1.0.
