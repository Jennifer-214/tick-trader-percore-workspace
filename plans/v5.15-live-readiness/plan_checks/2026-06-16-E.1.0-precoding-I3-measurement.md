# I3 — Measurement-reality audit of the E.1.0 H8 ratchet + H10 determinism gate

Re-derived from LANDED code (not the plan body's assumptions). All file:line vs HEAD 572c978.

## (a) H8 LATENCY RATCHET — verdict: **RESHAPE** (substrate is not ratchet-ready as written)

### What the plan body assumes
Phase A.0/D: `./build.sh latency` → run the replay → parse `EngineSharded_DumpLatency` per-core `p99` (hot) + the Phase-7.B histogram (slow p99 ≤100µs) → ratchet-down. Open question #3 flags "baseline stability" but treats the substrate as sound.

### What the code actually is — 6 substrate gaps the plan glosses

1. **`build.sh latency` sets `LATENCY_PROFILING` ONLY, never `LATENCY_BENCH`** (`build.sh build_latency()` ~:209 → `cmake -B build_lat -DLATENCY_PROFILING=ON`). The `[OMS_BENCH] drainer cycle: p50/p99/max cy` line is gated `if constexpr (BENCH)` (`Run.hpp:2437-2447`) = `LATENCY_BENCH`. **There is NO build.sh target that sets `-DLATENCY_BENCH=ON`.** So the plan's "parse `LATENCY_BENCH` stderr from `build.sh latency`" cannot fire — `build_lat/` emits the DumpLatency TUI table but not the BENCH drainer line. (The sharded engine IS BENCH-aware — `EngineSharded_Run<64, BENCH=true>` at `main.cpp:280` — but only when the build defines the macro.)

2. **The `[BENCH] hot: avg/min/max | slow: avg` line the plan names is the LEGACY SINGLE-CORE path, ELIDED for the sharded engine.** It lives under `#ifndef MULTICORE_TUI` (`main.cpp:1221-1236`) reading `tui.hot_*`/`tui.slow_*`; the `engine` target compiles `MULTICORE_TUI` (`CMakeLists.txt:12`). On the sharded path it never compiles. The plan's parse target does not exist for the sharded binary.

3. **Hot p99 is a 256-sample SLIDING WINDOW, not a lifetime stat.** `DumpLatency` prints `s.p99_ns` from `CoreLatencyStats_Snapshot` (`Run.hpp:325`), which sorts only `recent[256]` (`CoreLatencyStats.hpp:219-233`; header banner line `Run.hpp:313` = "p-stats from 256 most recent ticks"). The struct ALSO computes a lifetime-histogram `lifetime_p99_ns` (`CoreLatencyStats.hpp:116-118, 240-256`) — but **DumpLatency does not print it.** A ratchet keyed on the printed p99 ratchets against the last-256-ticks tail = non-stationary, run-length-dependent.

4. **The synthetic producer is `sleep_for(300ms)`-throttled (~3 ticks/sec) and runs FOREVER until SIGINT** (`Run.hpp:1343-1354`: `while (!g_engine_sharded_shutdown) { … sleep_for(milliseconds(300)); }`). No fixed tick count, no bounded run, no run-duration flag. At 3 ticks/s, filling the 256-window takes ~85 s, and the printed p99 = whatever the last 256 ticks looked like when the operator/CI killed it. **A CI ratchet has nothing deterministic to parse** — the sample set is a function of kill timing + scheduler jitter, not hot-path work. (Price sawtooth is deterministic; sample COUNT/p99 is not.)

5. **"Slow p99 ≤100µs" has NO emit.** The only slow-ish histogram is the DRAINER cycle (`g_engine_drainer_cycle_hist`, `Run.hpp:1465-1525`), whose budget is the **≤10µs drainer cadence**, not the ≤100µs slow-path REBUILD. The H8 slow-path-rebuild p99 the plan wants is measured nowhere. The plan conflates two different budgets/paths.

6. **Units + floor are unreconciled.** Hot p99 = ns (tsc-converted via `tsc_ghz`, `Run.hpp:622`); the drainer `[OMS_BENCH]` line is **raw CPU CYCLES** (`p99=%llu cy`) with the conversion factor NOT on that line. And neither path floor-subtracts the ~25-30 ns rdtsc bracket — `Run.hpp:328-329` is an operator-manual NOTE; `Snapshot` does no subtraction. On a ~100 ns hot path an un-subtracted 25-30 ns floor + sub-256 window + preemption tail makes a 500 ns gate either meaningless-pass or noise-trip.

### Constructive: what a WORKING ratchet needs (the reshape)
A reliable H8 CI ratchet is FEASIBLE but **not at E.1.0 against this substrate**. It needs a small, real (non-paralleled) measurement-harness increment first:
- **A bounded, headless, fixed-tick-count sharded bench run** (drive N ticks with the throttle DISABLED, exit on tick-count) — so the sample population is fixed run-to-run. (`sharded_force_synthetic` exists, `Run.hpp:530`; needs a tick-limit + no-sleep bench knob.)
- **Emit the LIFETIME-histogram p99** (already computed at `CoreLatencyStats.hpp:240-256`), not the 256-sliding-window p99 — make DumpLatency print `lifetime_p99_ns`, or add a BENCH-only line that does. Lifetime is the stationary statistic a ratchet can compare.
- **A `build.sh` bench target** that sets `-DLATENCY_BENCH=ON` (or wire the ratchet to a `cmake … -DLATENCY_BENCH=ON` lane directly).
- **Floor-subtract in code** (or ratchet on a floor-inclusive baseline consistently) + **one unit** (ns) for both hot and slow.
- **A real slow-path-rebuild histogram** if "slow p99 ≤100µs" is to be gated (today only the ≤10µs drainer cycle exists).
- **median-of-N-runs + margin** (plan's Phase D already notes this — correct, but insufficient on top of a non-bounded run).

**Recommendation:** RESHAPE H8 at E.1.0 to ship the ABSOLUTE-budget assertion against a *fixed-tick bounded bench* emitting the *lifetime* p99 (hot ≤500 ns; defer the ≤100µs slow gate until a slow-rebuild histogram exists), OR DEFER the ratchet-down delta to E.1.2 (its first SoA-AVX relayout is the first thing that could regress the kernel anyway) and at E.1.0 only land the bounded-bench + lifetime-p99 emit as the baseline-capture substrate. Do NOT ship a ratchet that parses the 256-window p99 off an unbounded sleep-throttled run — it will false-fail or be vacuous. This is the #1 thing for the A-class to confirm.

## (b) H10 SIMD-FALLBACK DETERMINISM GATE — verdict: **NON-VACUOUS on this host; add a runner guard**

- **`-march=native` DOES compile the `__AVX512F__` arm here.** `gcc -march=native -dM -E` defines `__AVX512F__ 1` (host = i7-11850H, `/proc/cpuinfo` shows `avx512f avx512vl avx512bw avx512dq avx512cd avx512ifma avx512vbmi`). So `×{-march=native, -march=native -mno-avx512f}` is AVX-512-arm vs scalar-`#else` (`RidgeBlender.hpp:493/517`, `:59`; BanditLearning `:52/204/247`) — a **genuine, non-vacuous** byte-compare on this machine. The plan's Phase-C compile-2-ways shape is sound.
- **The kernels ARE run-to-run deterministic.** The AVX-512 arms are written to byte-match scalar by construction: `_mm512_div_pd` (NOT reciprocal-mul) + `_mm512_fmadd_pd` for `a*b+c`, documented at `BanditLearning.hpp:213-218, 249-252`; no RNG inside the kernel (caller passes the uniform draw, `:265`); fixed reduction order (`avx512-byte-determinism-pattern.md` is the cited discipline). `memcmp` of the two builds' fixture outputs is stable. The H10 invariant is real and testable.
- **THE vacuity risk is the CI RUNNER, not this host.** On any non-AVX-512 runner, `-march=native` would NOT define `__AVX512F__`, both arms collapse to the scalar `#else`, and the gate silently becomes scalar-vs-scalar = always-GREEN-and-meaningless. **The gate MUST hard-assert that the "native" build actually compiled the AVX-512 arm** (e.g. emit + check a `__AVX512F__`-gated sentinel/marker, or `#error` if the native TU lacks `__AVX512F__`) and fail loudly otherwise. Without that guard the gate is non-vacuous HERE but provides a false sense of coverage on shared/cloud CI. Add it to Phase C.

## Bottom line
- **H8: RESHAPE.** A reliable ratchet is feasible but the substrate isn't ratchet-ready — no BENCH build target, the named `[BENCH]` line is the dead single-core path, hot p99 is a 256-sliding-window (lifetime p99 exists but isn't printed), the synthetic run is unbounded + 300ms-throttled (no fixed sample population), "slow p99 ≤100µs" is emitted nowhere (only the ≤10µs drainer cycle, in cycles not ns), and the rdtsc floor is operator-manual. Land the bounded-bench + lifetime-p99 emit substrate first; ship absolute-budget assertion at E.1.0, defer the ratchet-down delta (E.1.2 is its first real consumer).
- **H10: NON-VACUOUS here** (host has AVX-512; `-march=native` compiles it; kernels deterministic by construction) — but ADD a "native arm actually compiled `__AVX512F__`" hard-assert so a non-AVX-512 runner can't make it silently scalar-vs-scalar.
