# v5.9.5h — Full stamp ↔ runtime observability (hyperparams + inference cfg + ML Status)

**Date:** 2026-05-02
**Branch:** `feat/v5.9-ml-hardening`
**Predecessor:** v5.9.5g (tree_method=hist hardcoded)
**Effort estimate:** ~7-8h (bundled scope)
**Hot path:** UNTOUCHED

## Theme

**"Full stamp ↔ runtime observability across all stamp-bound fields."**
v5.9.2b through v5.9.5g shipped 14 stamp body fields but with
asymmetric load-time treatment — only `feature_registry_hash`,
`engine_version` cross-major, `model_num_outputs`,
`training_poll_interval`, and `scaler_sha256` get compared at load.
The 9 inference cfg fields are stamp-recorded but never compared
(v5.10 Idea #12 noted this gap). v5.9.5h closes the loop AND adds
the 8 XGBoost hyperparams as the same shape (cfg-bound + stamp-bound +
load-time WARN + GUI display).

Bundled three previously-deferred items:

- **Hyperparam ownership** — operator-tunable cfg/GUI fields, stamp
  binding, load-time WARN. (Original v5.9.5h.)
- **Idea #12** — load-time enforcement (WARN-only) of the 9
  v5.9.2b inference cfg fields.
- **Idea #16** — ML Status panel row showing stamp-recorded cfg vs
  runtime cfg (live drift visibility).

## Context

After Jenny shipped a model + raised the question of operator control:
"someone using this may want higher control... I have users who would
want things like this." Currently 5 XGBoost hyperparams are hardcoded
across 3 training sites:

- `subsample=0.8`, `colsample_bytree=0.8`, `min_child_weight=5`
- `seed=42`, `tree_method=hist` (v5.9.5g)

3 are operator-tunable via Train Model panel UI but **never recorded
in the stamp** (so drift between training-time tuning and the deployed
model is invisible):

- `max_depth`, `learning_rate`, `n_estimators`

This ship: **full ownership** — all 8 hyperparams become cfg fields,
GUI inputs in Training panel, stamp-bound via Surface G pattern,
load-time WARN on cfg-vs-stamp mismatch (operator audit).

## Why this matters

1. **Operator control** — power users want to tune subsample for
   variance reduction, colsample for feature-importance bias, seed for
   reproducibility runs, tree_method for speed/accuracy trade.
2. **Drift tracking** — currently if hardcoded values change in v5.10
   (e.g., we bump subsample to 0.9), old stamps have no record of what
   trained them. Stamp-binding closes this.
3. **Reproducibility** — operator can re-train with the recorded
   hyperparams to reproduce a model bytewise.
4. **Forensics** — Verify Stamp shows what trained the model — distinguishes
   "production-vetted run" from "experimental sweep."

## Scope

### Phase 1: Single source of truth (~1h)

Extract `XGBHyperparams` struct that all 3 training sites read from.

**File:** new `Backtest/XGBHyperparams.hpp`

```cpp
struct XGBHyperparams {
    // Operator-tunable today (Train Model panel)
    int   max_depth         = 6;
    float learning_rate     = 0.05f;
    int   n_estimators      = 300;
    // Pre-v5.9.5h hardcoded; now operator-tunable
    float subsample         = 0.8f;
    float colsample_bytree  = 0.8f;
    int   min_child_weight  = 5;
    int   seed              = 42;
    char  tree_method[16]   = "hist";  // hist | exact | approx | auto
};

// Apply to a booster handle (3 callsites use this)
void XGBHyperparams_Apply(BoosterHandle b, const XGBHyperparams& hp);

// Defaults match the v5.9.5g hardcoded values exactly so operators
// who don't tune get bytewise-identical training output to v5.9.5g.
XGBHyperparams XGBHyperparams_Defaults();
```

Used by:
- `BacktestPanels.hpp:train_model_worker_fn`
- `BacktestEngine.hpp:Backtest_RunWalkForward` (per-fold training)
- `BacktestEngine.hpp:HeldOutSplit_TrainEval`

### Phase 6: Load-time WARN on mismatch (~30 min)

In `CoreModelZoo._TryLoadRole`, after the existing
training_poll_interval check, compare cfg's tunable fields vs stamp's:

- subsample, colsample_bytree, min_child_weight, seed, tree_method —
  these have cfg fields, so we can compare.
- max_depth, learning_rate, n_estimators — no cfg field; skip.

WARN format:
```
[xgb_hyperparams] WARN: model.bin stamp claims xgb_subsample=0.5 but
cfg.xgb_subsample=0.8. Set acknowledge_cross_binary_version_drift=1
to suppress (or update cfg to match).
```

Same suppression cfg flag as v5.9.4 cross-binary handshake. No refuse —
hyperparams don't affect inference; WARN is purely operator
observability.

## Rollback

If load-time WARN is too noisy (operator complaints), revert to
`pre-v5.9.5h`. Stamp emit + Verify Stamp display are
display-only (no behavior change without operator action). The
load-time WARN is the only behavior-affecting addition; if disliked,
gating on a separate cfg flag would let operators opt out.

## Why ship now (vs defer to v5.10)

- Closes a real operator-control gap Jenny's users would benefit from
- Stamps need this for drift tracking — not just nice-to-have
- v5.10 Idea #1 (parallel grid search) builds ON TOP of v5.9.5h's
  hyperparam-as-first-class-citizen foundation
- Risk-bounded: cfg defaults match current hardcoded values →
  bytewise-identical training output for non-tuning operators
- Sprint discipline: closes the v5.9 ML hardening theme cleanly

## Out of scope (v5.10 candidates)

- Parallel grid search (Idea #1) — operator picks ranges; engine
  trains N models in parallel, picks best validated. Built on v5.9.5h's
  hyperparam struct.
- Hyperparam quality bounds (e.g., refuse load if max_depth>20 +
  no override flag) — opinionated, defer.
- Per-core hyperparam overrides — interesting for multi-strategy
  ensembles.
