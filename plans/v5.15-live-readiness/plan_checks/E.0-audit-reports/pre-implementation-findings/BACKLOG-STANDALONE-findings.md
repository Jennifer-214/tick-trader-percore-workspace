### [MEDIUM] `det-2` — Fingerprint_Compute raw-byte SHA-256 over an un-zero-initialized, mixed-alignment ControllerConfig — uninitialized padding enters the model lineage fingerprint (H12/H9 hash non-determinism)
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `determinism-xcut` · fix: standalone — either zero-init config_used before populate (cheap mitigation: makes within-binary deterministic but still layout-fragile) OR (correct) replace raw-byte hash with a canonical field-by-field serializer mirroring the FeatureStandardizer scaler-hash pattern. Fits an ML-lineage / wire-format hardening ship.
- **Where:** Backtest/Fingerprint.hpp Fingerprint_Compute() ~line 180 (SHA256_Update(&s, cfg_ptr, cfg_size) — raw struct bytes); caller Backtest/BacktestPanels.hpp:3157-3159 (Fingerprint_Compute<64>(fp_hex, &results->config_used, sizeof(results->config_used), ...) then XGBoosterSetAttr(booster,"foxml_fingerprint",fp_hex)); struct CoreFrameworks/ControllerConfig.hpp:359+ (template ControllerConfig with interleaved FPN<F>/uint32_t/int/double/char[N] fields, no _padding discipline); construction CoreFrameworks/ControllerConfig.hpp:1470 `ControllerConfig<F> cfg;` (default-constructed, NO `= {}` zero-init); read-back ML_Headers/ModelInference.hpp:509-512 (XGBoosterGetAttr -> m->training_fingerprint).
- **What:** Fingerprint_Compute hashes sizeof(config_used) RAW bytes of a ControllerConfig<64>. That struct interleaves fields of differing alignment (e.g. uint32_t pay_fees_in_bnb at :381 immediately before FPN<F> risk_pct forces 4 padding bytes; char[256]/char[128]/char[16] fields interleaved with int/double throughout), so the compiler inserts padding. The result is bound to the trained model as the 'foxml_fingerprint' XGBoost attr and read back at load into m->training_fingerprint.
- **Why:** The file's own comment claims 'same config -> same hash' and the fingerprint exists to detect train/serve config drift (lineage). Raw-byte hashing of a padded, non-zero-initialized struct defeats reproducibility: two runs of the same binary can produce different fingerprints (whatever was on the stack), and a compiler/struct-layout change shifts the padding. This is an H12 violation (struct in a SHA-256 byte-equivalence context lacks explicit zero-init padding) and an H9-adjacent hash-input determinism break. The codebase already demonstrates the CORRECT pattern next door: FeatureStandardizer scaler-SHA (FeatureRegistry.hpp ~319-336) and FEATURE_REGISTRY_HASH (~611-625) both serialize field-by-field with explicit widths and never hash raw struct bytes — making Fingerprint_Compute a clear deviation.

Canonical fingerprinting must walk the registry and emit per-field, not memcmp/hash the struct image.
- **CI check:** grep CI check: flag SHA256_Update/sha256_bytes/memcmp called with (struct_ptr, sizeof(struct)) where the struct is not a designated POD-with-explicit-padding wire type — require canonical serialization helpers in hash/persist contexts.
- **Test to add:** Add a reproducibility test: build two ControllerConfig instances with identical field values via independent code paths (or memset 0xAA then 0x55 the padding before populate), run Fingerprint_Compute on each, assert equal hex. Currently zero tests exercise Fingerprint_Compute determinism.
- **Anti-pattern:** Hashing/persisting a raw struct image (sizeof + SHA/memcmp) for a value meant to be reproducible, when the struct mixes field alignments (=> compiler padding) and/or is not zero-initialized — should be a canonical field-by-field serialization instead.
