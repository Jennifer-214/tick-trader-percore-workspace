## Design pivots (each one surfaced something worth remembering)

### Pivot 1: Original v5.14.9 plan was stale — "binary kill switch" framing wrong

**Trigger:** Pre-coding verification of the v5.12.1.D math (StrategyParameters.hpp:1291-1322). Original 2026-05-08 plan claimed v5.12.1.D was "always multiplies by 1.0 = no-op until composite confidence wired"; actual code has logic that's broken-for-composite-scale (compares conf_now ∈ [0.001, 0.3] against ml_buy_threshold ∈ [0.5, 0.7] → factor=0 silently).

The "binary kill switch" framing in the master plan came from a DIFFERENT layer — `confidence_hard_block_threshold` at StrategyParameters.hpp:1248-1265. v5.14.9's ladder doesn't replace this layer; it replaces the broken L3 (sizing) math.

**Decision:** Three confidence-driven layers exist orthogonally:
- L1: `confidence_threshold_scale` damped threshold (modifies entry threshold)
- L2: `confidence_hard_block_threshold` HARD CLIFF (catastrophic safety net; default off)
- L3: `risk_scale_by_confidence` sizing factor (broken for composite; v5.14.9 fixes)

v5.14.9 fixes L3 only. L1 + L2 stay as orthogonal axes. NOT merged.

**Codified in:** new plan's "Why this ship exists" section + Q1 design discussion in postmortem.

**Going-forward rule candidate:** when a master plan describes a feature in shorthand ("binary kill switch"), pre-coding verification must MAP shorthand to concrete code locations. Compaction-degraded handoffs collapse this mapping.

### Pivot 2: cfg field rename — `risk_scale_by_confidence` → `risk_degradation_curve`

**Trigger:** Existing enum modes (1=linear, 2=quadratic) use broken-for-composite math. Caramel's structural-fix-preferred rule + "defer is last-ditch" memory: don't preserve broken modes for back-compat; fix structurally.

**Decision:** Rename + replace math. Old `risk_scale_by_confidence` → `risk_degradation_curve` (registry-aligned naming). Back-compat parser shim translates legacy `risk_scale_by_confidence=N` → `risk_degradation_curve=N` (values map 1:1; modes 1+2 get NEW math = ladder linear/exp; mode 3 = ladder step is added).

**Trade-off:** legacy operators who explicitly set `risk_scale_by_confidence=1` get NEW math instead of old broken math. CHANGELOG documents the change. Reasoning per Caramel's "ACTIVATION GATED on Phase 4.B paper-test" comment in code: no operator has activated this yet (gate hasn't fired), so rename is safe.

**Going-forward rule candidate:** cfg rename + structural-fix replaces broken-but-tolerated behavior cleanly when no operator depends on the broken behavior. Verify "no dependency" via comment-archeology + grep before renaming.

### Pivot 3: Composite-required-for-ladder boot REFUSE — engine-wide vs per-core

**Trigger:** Per-core override pattern (`core_N_*`) is supported for ladder cfg fields. But composite_enabled is GLOBAL only (no per-core override exists). Question: per-core REFUSE check or engine-wide?

**Decision:** Engine-wide REFUSE. If ANY core has ladder enabled (global OR per-core override), composite_enabled must be on globally. Reasoning: composite is global; partial activation isn't possible without adding per-core composite override (unjustified cfg surface creep).

Caramel's pushback ("what do you mean, is the simpler option actually better? does it fit with the design philosophy?") prompted the framing: option (b) is mechanically correct given the constraint, not just simpler. Constraint forces the answer; no design wiggle room.

**Going-forward rule candidate:** when justifying "simpler is better" design choices, articulate the underlying CONSTRAINT (not just "fewer cfg fields"). Constraint-driven simplicity is honest; preference-driven simplicity needs more justification.

### Pivot 4: Mega-bundle vs split — go bundled

**Trigger:** Plan was growing to absorb TECH_DEBT-004 + TECH_DEBT-013 (5 candidates) + TECH_DEBT-015 + skill infrastructure. I proposed splitting into 5 ships (skill micro + .9 charter + .10 cleanup + Thompson + online corr).

Caramel: "i accidentally interrupted you, and its ok if this phase gets big, i actually woke up in the morning today" — confirmed go-big.

**Decision:** Mega-bundle. Same shape as v5.14.8 closing TECH_DEBT-006 fully. Closes 3 TECH_DEBT items in one ship + establishes BITMAP_* universally across remaining surfaces.

Skill infrastructure (`tools/dod-audit-v0.1`) ships as separate micro-ship BEFORE v5.14.9.A — not because it's logically separate but because v5.14.9's pre-coding gate USES /dod-audit. Skill must exist before audit runs.

**Going-forward rule candidate:** "biggest viable ship" trade-off — when adjacent debt naturally clusters AND operator has the bandwidth, bundle. Defer is last-ditch; effort-avoidance is anti-philosophy.

### Pivot 5: /dod-audit skill design — registry-driven, distinct from /hft-audit

**Trigger:** Caramel asked "should we make a skill that checks for concurrency issues, cache alignment, cache misses, branchless implementations, bit packing, bit field dispatchers, and that references past design docs?".

**Decision:** New skill `/dod-audit` distinct from existing `/hft-audit`. Boundary:
- `/hft-audit`: GENERIC HFT principles (universal, project-agnostic)
- `/dod-audit`: OUR-PROJECT-SPECIFIC pattern library (registry-driven via DESIGN_SPECS/*.md)

Same shape as `/bug-check` vs `/hft-audit` — `/bug-check` is OUR codebase's recurring bug history; `/hft-audit` is generic HFT principles. Co-exist with clear boundaries.

**Implementation:** Layer 2 skill per SKILLS_HIERARCHY.md. Registry-driven (reads DESIGN_SPECS/*.md catalog dynamically). 8 baseline check categories. Severity-classified output to `plans/plan_checks/dod-audit-<date>-<surface>.md`. Auto-writes deferred findings to TECH_DEBT.md per auto-write contract.

`/readiness` Check 27 invokes `/dod-audit` by-reference (compose-by-reference per SKILLS_HIERARCHY.md, NOT by-spawning).

**Going-forward rule candidate:** new skills should explicitly document distinct-from-sister-skills boundaries. Prevents skill bloat + clarifies when each fires.

### Pivot 6: Major/minor skill hierarchy — by-reference NOT by-spawning

**Trigger:** Caramel asked "analyze the hierarchy to figure out what skills should be called by the major skills, like a major/minor layout type thing".

**Decision:** Existing SKILLS_HIERARCHY.md already establishes the model:
- Layer 1 (orchestration): main session OR orchestrator skills (/finding-analyzer, /patch-planner, /ship)
- Layer 2 (execution): focused skills (/dod-audit, /readiness, /trace-deps, etc.)
- NO Layer 3 — skills compose by-REFERENCE (read another's spec + execute inline) NOT by-SPAWNING (which causes recursion traps)

Updated SKILLS_HIERARCHY.md per-skill table with /dod-audit + clarified existing skills' major/minor roles.

**Going-forward rule candidate:** treat compose-by-reference as the canonical pattern for skill orchestration. Skills calling skills via spawning is a recursion trap. Document the model in every new skill spec via a `## Execution model` section.

## Architectural surprises (caught at audit time, not at ship time)

### Surprise 1: PerCoreSnap cache layout sensitivity

**Caught by:** Q3 follow-up analysis at Caramel's prompt (cache alignment / concurrency / cache miss risk for new ml_confidence_factor field).

**Specifics:** PerCoreSnap is large (>1KB; ~16 cache lines) + cross-thread (slow-path writes, GUI reads). Synchronization via existing double-buffered TUISnapshot mechanism. Adding 1 double field is safe IF placed adjacent to existing ml_* cluster (~lines 1067-1098); avoids cache-line span change.

**Resolution:** Plan documents field placement at .B sub-tag. TECH_DEBT-013 candidate (3) folds in PerCoreSnap state_flags migration which migrates 3-5 existing booleans to uint16_t bitmap (further memory savings + bitmap pattern consistency).

**Lesson:** every PerCoreSnap layout change requires explicit cache-locality analysis. CLAUDE.md item 12 (display↔execution invariant) + TECH_DEBT-011 codify this; was nearly missed in original 2026-05-08 plan.

### Surprise 2: Legacy `confidence_freshness_tau` is half-dead, not fully dead

**Caught by:** Pre-coding grep for `confidence_freshness_tau` (legacy, not `_secs`).

**Specifics:** field is mathematically inert in production (data_age=0 always; freshness formula is `exp(0/tau) = 1.0` regardless of tau value), BUT operationally live: cfg field, parser, default 300.0s, range [60, 3600], per-core override, stamp-bound via FOREACH_STAMP_BOUND_MODEL_CONST inference_cfg group, manual drift check at boot (parallel to registry — TECH_DEBT-003 territory).

**Resolution:** TECH_DEBT-004 hard close is more involved than initial 1-3h estimate. Path A (hard delete) requires ~10-15 caller updates + manual drift check deletion + ConfidenceScorer_Init signature simplification. Plan estimates ~120 LOC. Adjusted from 1-3h → 4-6h additional in v5.14.9.D sub-tag.

**Lesson:** "field is unused" verification requires checking ALL of: parse path, default, per-core override, stamp body, drift check (manual + registry), Init signature, all callers. Lift-and-shift one path doesn't extinguish the field; all must align.

### Surprise 3: Master plan tag summary stale (Phase 1 + 2 ships marked PENDING)

**Caught by:** Master plan update task. Tag summary at lines 322-378 had v5.14.0 / .1 / .2 / .3 / .4 / .5 all marked [PENDING] but CHANGELOG shows all shipped 2026-05-09.

**Resolution:** Updated tag summary to reflect actual shipped state. Aligns with /readiness Check 22 (auto-trigger downstream re-audit after umbrella ships).

**Lesson:** master plan freshness audit should run automatically after each umbrella ship per Check 22. Cross-checked CHANGELOG vs master plan status markers; future Check 22 invocations should be more proactive.

### Surprise 4: Phase 4 master plan had orphan Maker MVP cruft in v5.14.12 description

**Caught by:** Reading master plan lines 274-298 to update v5.14.12 entry.

**Specifics:** v5.14.12 (online corr) description had ~15 lines of Maker MVP content (limit_price, BinanceAdapter POST_ONLY, etc.) — leftover from Phase 3 deferral that wasn't fully cleaned. Deleted the orphan content as part of the renumbering pass.

**Lesson:** when a phase defers, walk every cross-reference site to ensure leftover content is cleaned.

### Surprise 5: SKILLS_HIERARCHY.md is at workspace path, not engine-DOCS path

**Caught by:** Bash search for the doc.

**Specifics:** CHANGELOG mentioned `DOCS/SKILLS_HIERARCHY.md` — implicitly engine repo path. Actually exists at workspace path (`tick-trader-percore-workspace/DOCS/SKILLS_HIERARCHY.md`); engine repo `DOCS/` doesn't symlink workspace `DOCS/`.

**Resolution:** edits go to workspace path; engine repo accesses via skill specs that reference workspace paths.

**Lesson:** workspace symlinks are per-directory (plans/, .claude/skills/), not whole-tree. New documents that need engine-side access must either symlink explicitly OR live in engine-tracked paths.

## Going-forward rule candidates (extract to CLAUDE.local.md at v5.14.9.I)

1. **Master plan freshness audit on every umbrella ship close** — Check 22 should fire automatically; CHANGELOG vs tag summary cross-check is a one-liner.

2. **PerCoreSnap layout change requires explicit cache-locality analysis** — every new field placement should cite item 12 + TECH_DEBT-011 + adjacent-field cluster reasoning. Codified in /dod-audit Step 3a.

3. **Legacy field "deletion" requires multi-site verification** — parse path + default + per-core override + stamp body + drift check (manual + registry) + Init signature + all callers. /dead-code-trace style multi-stage verification before "delete" is safe. Worth strengthening /dead-code-trace skill spec.

4. **Compose-by-reference is the canonical skill orchestration pattern** — every new Layer 2 skill spec should have an `## Execution model` section pointing at SKILLS_HIERARCHY.md. Already in /readiness, /trace-deps, /parity-check; now in /dod-audit.

5. **Master plan absorption notes (e.g., "RESERVED — bundled into v5.14.X") are sealed historical record** — don't mutate; if the slot is reused (like v5.14.10 was renumbered to Thompson), preserve the absorption note + add reuse explanation.

6. **DESIGN_SPECS auto-detection convention** — DESIGN_SPECS docs should add `## Audit detection` sections so /dod-audit can dispatch grep patterns / AST shapes mechanically. Symptom-based fallback works but explicit is faster + more accurate.
