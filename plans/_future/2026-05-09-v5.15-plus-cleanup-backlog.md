### CLEANUP-001 — verify_model_stamp parser if-else chain refactor

- **Surface:** `ML_Headers/ModelInference.hpp:1492+` (the `verify_model_stamp`
  parser body — `else if (strcmp(key, "...") == 0)` chain)
- **Current state:** ~30 known stamp body keys, each handled by a
  separate `else if (strcmp(...) == 0)` branch. v5.13+ added several
  Surface G fields (label_params, xgb_train_nthread); v5.14.1.B.3
  adds 12 more (Ridge + composite). Pattern still readable but
  approaching the size where data-driven dispatch wins.
- **Why deferred:** boot-time code; perf cost is negligible
  (`~1µs total` to parse the whole stamp). Refactor would be a
  pure code-quality / maintainability win; no functional change,
  no parity impact. Not worth holding up the v5.14 parity ships.
- **Suggested refactor:** key→handler table pattern. Static array
  of `{key_str, parser_fn}` entries; lookup via linear scan or
  hash. Each handler takes `(ModelStampResult* r, const char* val)`.
  Adding a new field becomes ONE table entry instead of one parser
  branch + one zero-init line + one zero-init in the result struct
  default constructor.
  - Variant A (linear scan): simplest; ~30 entries × strcmp = ~1µs.
    No allocation. Direct port.
  - Variant B (hash): faster; ~50ns. Worth it only if parser becomes
    hot.
- **Effort estimate:** M (~150 LOC refactor + ~50 LOC test for
  round-trip parity with current parser; full test suite run to
  verify no regression).
- **Trigger to revisit:** when parser hits ~50 keys, OR when
  Caramel/operator wants to do a maintainability sweep on the
  verify path, OR when adding the next batch of Surface G fields
  feels tedious.
- **Cross-ref:** RECURRING_BUG_PATTERNS Class 16 (naming convention
  drift) — table-driven dispatch makes the prefix discipline
  enforceable at the table level.

### CLEANUP-002 — bash tools/stamp_model.sh field catch-up

- **Surface:** `tools/stamp_model.sh`
- **Current state:** Bash CLI is missing emit support for several
  Surface G stamp body fields shipped to the in-process emitter:
  - v5.11.41 `label_params` (label_lookahead_ticks/tp_pct/sl_pct)
  - v5.11.41 `xgb_train_nthread`
  - v5.14.1.B.3 `has_ridge_*` + 5 Ridge fields
  - v5.14.1.B.3 `has_composite_*` + 5 composite confidence fields
- **Why deferred:** In-process emitter (BacktestEngine RFV +
  Multi-Horizon worker) covers the production path. Bash CLI is
  used only when operator manually invokes `tools/stamp_model.sh`
  (rare; mostly for tests + ad-hoc validation). Catching up only
  the v5.14.1.B.3 fields would leave bash still inconsistent with
  the in-process emitter for label_params + xgb_train_nthread.
- **Suggested fix:** Catch up all missing fields at once. For
  v5.14.1.B.3 fields, add 10 CLI flag pairs (`--has-ridge-params=1`,
  `--ridge-lambda=0.15`, etc.) gated by `--has-*` boolean flag.
  Round-trip parity test in tests/ verifies bash + in-process
  produce identical canonical body.
- **Effort estimate:** M (~80 LOC bash + 1 round-trip test).
- **Trigger to revisit:** when next operator workflow needs bash
  CLI for stamp ops, OR during a v5.15+ tooling sweep.
- **Cross-ref:** PARITY-004 + PARITY-005 (stamps emitted via
  in-process path are protected; bash-emitted stamps inherit the
  protection only if bash gets caught up).
