## .F.1 — Hold-time persistence across program restart

**Problem (operator-reported 2026-05-13):** Positions display Hold = "5m T" uniformly after engine restart days later. Positions were genuinely held longer than 5 minutes — `entry_timestamp_us` is being reset on load.

**Investigation findings (audit-confirmed):**

- `Position.entry_timestamp_us` IS persisted in PORTFOLIO_SNAPSHOT_VERSION=5+ wire format (Portfolio.hpp:127 offset lock).
- However, on this session the SHARDED snapshot was REFUSED (file v7 vs current v8 — `[snapshot] data/sharded_snapshot.dat version 7 != current 8 — refusing load`).
- Positions were instead restored via `OrderEventLog replay` (8 events loaded from `logging/order_events.bin`).
- **Hypothesis:** the OrderEventLog replay path calls `Portfolio_OpenSlot` which sets `entry_timestamp_us = clock_gettime(CLOCK_REALTIME)` — i.e., NOW — losing the original wall-clock entry time.

**Where to look:**

- `CoreFrameworks/Portfolio.hpp:322` — `entry_timestamp_us = clock_gettime(...)` write site
- OrderEventLog replay code (need to grep; likely in `CoreFrameworks/OrderEventLog.hpp` or similar)
- The original entry event in the log presumably has the original timestamp — replay should restore it, not overwrite with NOW.

**Fix approach:**

1. Find OrderEventLog replay → identify where it calls Portfolio_OpenSlot.
2. Modify replay to pass the LOGGED entry timestamp (not NOW) into Portfolio_OpenSlot.
3. Either:
   - Add an overload `Portfolio_OpenSlot_FromReplay(..., uint64_t logged_entry_ts_us)` that uses the logged timestamp.
   - OR add a separate field on Position that distinguishes "live entry" vs "replayed entry" semantics.

**Risk:** LOW. Replay-path-only change; live entry path untouched.

**Test:** Open paper-test session → wait 10m → close → wait 1m → re-open → verify Hold column shows ~11m (not 5m or 1m).

## .F.2 — Per-core "Budget -100%" display bug

**Problem (operator-reported 2026-05-13):** PER-CORE P&L panel shows "Budget -100%" for all 4 cores after small losses ($-17 to $-19 on $1500 alloc). Display math is wrong — should be ~-1.1%.

**Where to look:**

- `GUI/DashboardPanels.hpp:983` — PER-CORE P&L panel
- `GUI/DashboardPanels.hpp:1001` — Budget column setup
- `GUI/DashboardPanels.hpp:1088-1101` — Budget computation + tooltip ("Budget used: $%.2f / $%.2f")

**Hypothesis:** Budget formula has wrong scale OR wrong sign for the loss case. Likely:
- Should be `core_realized / core_alloc * 100` → -17/1500 = -1.13%
- Currently outputting -100% suggests divide-by-100 mistake OR field-swap

**Fix:** read the actual computation; identify + fix the math.

**Risk:** LOW. Display-only.

**Test:** verify Budget column shows realistic percentages on next paper-test session.

## .F.3 — STRUCTURAL: FOREACH_MODEL_HEALTH_FLAG registry

**Problem (operator-reported 2026-05-13):** ML Status panel says "Model Health: clean (no drift across cores)" + "Stamp + scaler + cfg + HMAC + age all aligned with runtime" when in fact engine boot logged 4 `[held-out gate] WARN: feature-registry-hash mismatch (retrain required)` for the multi-horizon ensemble.

The boot-time stamp-verification result is NOT propagated to runtime observability — engine log says one thing, GUI says the opposite.

**Structural answer (per CLAUDE.md item 19 + DESIGN_SPECS/structural-fix-preferred-decision-framework.md):**

Define `FOREACH_MODEL_HEALTH_FLAG` X-macro registry. Single source of truth for:
- Per-handle bitmap field (`uint8_t health_flags` on ModelHandle or equivalent)
- Per-core aggregated bitmap (OR of all this core's handles' flags)
- Snapshot field for GUI publish
- ML Status panel display (registry-driven; render per-set-bit with doc string)
- Engine log refactored to USE the registry's doc strings (closes Class-18 mirror between log + GUI text)
- `/readiness` Check 26+ scans flags before live mode enters

**Registry entries** (initial; expandable):

```cpp
#define FOREACH_MODEL_HEALTH_FLAG(X)                                                          \
    X(FEATURE_HASH_MISMATCH,    "feature_registry_hash mismatch (retrain required)")           \
    X(SCALER_HASH_MISMATCH,     "scaler feature_registry_hash mismatch")                       \
    X(STAMP_HMAC_INVALID,       "HMAC not verified (held_out_stamp_secret empty or check failed)") \
    X(MODEL_AGE_EXCEEDED,       "model age exceeds model_max_age_hours")                       \
    X(GRID_MEMBER_COUNT_MISSING,"pre-v5.10.0a.G.2 ensemble metadata (consistency check skipped)") \
    X(MODEL_FORMAT_LEGACY,      "model_format_version older than current")                     \
    X(CFG_DRIFT_TIER_1,         "Tier-1 cfg drift detected (live REFUSE)")                     \
    X(CFG_DRIFT_TIER_2,         "Tier-2 cfg drift detected (live WARN)")
// 8 flags fits uint8_t bitmap. Future expansion → uint16_t.
```

**Storage:**
- `uint8_t model_health_flags` field on ModelHandle (per-handle granularity)
- `uint8_t core_model_health_flags` aggregated to CoreContext (per-core OR) — placed in WARM cluster or via existing FOREACH_DISPLAY_META_FIELD registry extension (cleaner: DisplayMeta sibling)
- PerCoreSnap.model_health_flags published from CoreContext

**Auto-populate sites:**
- Boot-time stamp verify (currently logs `[held-out gate] WARN`) — set FEATURE_HASH_MISMATCH bit on the affected handle.
- Boot-time scaler binding — set SCALER_HASH_MISMATCH bit on mismatch.
- HMAC check — set STAMP_HMAC_INVALID bit on failure.
- Model age check (model_max_age_hours) — set MODEL_AGE_EXCEEDED at boot + periodic refresh (if any).
- Etc.

**GUI:**
- ML Status panel: when ANY bit in any per-core core_model_health_flags is set, replace the lying "all aligned" subtext with per-flag doc string lines.
- Color: yellow/orange for issues; green for clean.
- Per-core breakdown if multiple flags differ across cores.

**Engine log refactor:**
- Define `[held-out gate] WARN: model_health_flag=FEATURE_HASH_MISMATCH path=... details=...` using registry doc strings.
- Closes Class-18 mirror between log message string + GUI display string.

**NEW DESIGN_SPEC:** `model-health-flag-registry-pattern.md` documenting the pattern. Per pattern-codification-lifecycle.md Stage 2 (write spec ahead of first reference).

**Per /readiness:** add Check 26 or 27 that scans for any per-core model_health_flags non-zero → flags YELLOW unless acknowledged via cfg flag (e.g., `acknowledge_model_health_warnings=1`).

**Risk:** MEDIUM. Touches GUI + engine + cfg + stamp verify + persistence (the snapshot's per-core fields gain a uint8_t). Per-sub-step rollback anchors.

**Test:** Load with stale models → verify ML Status panel shows the flags + retrain text. Load with fresh models → verify "clean" message.

## .F.4 — SettingsPanel cfg surface audit + extension

**Problem (operator-reported 2026-05-13):** Settings panel shows many 0.00 values (Filter Scale, R² Threshold, Slope Scale, Vol Min/Max, Hold Score, Trail TP/SL, etc.). Caramel: "i feel like we forgot a lot of settings items."

**Audit scope:**

1. Walk `CfgFieldRegistry.hpp` / `StampBoundCfgRegistry.hpp` / `MlCfgFlagRegistry.hpp` / `CfgDriftCheckRegistry.hpp` — list ALL parseable cfg fields.
2. Walk `SettingsPanel.hpp` — list what's currently rendered.
3. Diff: identify missing fields. Categorize:
   - **Thompson sampling** (added v5.14.10) — likely missing: `bandit_algorithm`, Thompson posterior params, `core_N_bandit_algorithm`
   - **Ridge blending** (v5.14.11) — likely missing: `ridge_within_horizon_*`, `ridge_across_horizons_*`, `exit_blender_*`
   - **Composite confidence** (v5.14.1) — likely missing: composite components, MlCfgFlag bits
   - **Soft risk degradation** (v5.14.9) — likely missing: degradation_curve, soft_risk_*
   - **Drift detection** (v5.10.0e) — likely missing: drift_auto_kill, confidence_ic_floor_*
   - **Per-horizon barrier blending** (v5.15.5.A) — verify exposure: barrier_blend_mode, per_horizon_barrier_blend

**Structural pattern preference:**

If SettingsPanel currently uses a hardcoded list (the `{"bandit_blend_ratio", "Bandit Blend", ...}` style at line 425), it's a Class-18 mirror candidate — every new cfg field needs adding to BOTH parser AND panel. The right structural fix:

- Extend the existing **`FOREACH_STAMP_BOUND_CFG`** or define **`FOREACH_SETTINGS_PANEL_FIELD`** X-macro registry that drives both parsing AND display. Per CLAUDE.md item 13 + 21.
- AUTOPOPULATE companion: `SETTINGS_PANEL_RENDER_AUTOPOPULATE(panel, cfg)` auto-generates rendering rows from the registry.

If the cfg fields are already in existing registries (FOREACH_STAMP_BOUND_CFG etc.), the SettingsPanel just needs to ITERATE the existing registry — minimal touch.

**Risk:** LOW. Pure GUI extension. No engine behavior changes.

**Test:** Settings panel shows all currently-meaningful cfg values. Run engine → modify cfg → restart → verify changed values reflect in panel.
