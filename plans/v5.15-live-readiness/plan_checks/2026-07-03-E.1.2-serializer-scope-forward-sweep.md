## The reframe (operator Q1/Q2) — RECOMMENDED: born-registry-generated `NodeState`

**Q1 — does a static full-census freeze account for future changes? NO.** It freezes today's fields and stays brittle; the next field-add post-freeze hits the same drift.

**The fix — design the greenfield `NodeState` BORN registry-generated (the Position gold-standard).** Confirmed at code: `FOREACH_POSITION_FIELD` (`MemHeaders/PositionFieldRegistry.hpp:9,29-33,49-59`) **generates the struct + drives the serializer + backs the size-pin** from one 5-column source; its header states the goal — *"Future field = 1-line addition; encoded once, enforced at compile time; closes the version-bump class."* Existing spec: `persisted-struct-with-ephemeral-field-coexistence-pattern.md` + CLAUDE.md item 19.

- Design `NodeState` as **per-cluster sub-registries** (`hot` / `slow_account` / `drainer` / `kill`), each generating its struct cluster + serializer projection. Then **any future field-add (now / E.1.3 / E.5 / a new strategy or ML feature) = 1 row → struct + serializer + pin auto-flow → can't drift → version-managed.** That is "easy to modify going forward."
- **This DISSOLVES ①:** no perfect one-time census needed — incremental adds are 1-row + version-bump, so enumerate what's known now and the future is safe by construction.
- **Greenfield (0-hit NEW symbol)** → we design it right from scratch, not retrofit the legacy hand-struct → the born-right moment is E.1.2 (open-once).
- **Unifies with BLK-1:** BLK-1's "compose-sub-registries" instinct was right for the *serializer*; pushing it up to *generate the struct clusters too* closes the whole struct↔serializer drift class, not just the save/load half.
- So the real fork is **"born registry-generated" (dominant) vs the static A/B options.** `FOREACH_NODE_FIELD` = pattern application (canonical sister `FOREACH_POSITION_FIELD`), enrolled per H15.

**Q2 — codification owed (DRAFT; land at ship-close per § 11.5).** The FIX pattern exists (for Position). Missing, and to be closed:
