## Why this ship exists

Per `DESIGN_SPECS/doc-disciplines/file-size-split-discipline.md` § Thresholds: source headers over 1,500 lines require split. `EngineSharded.hpp` is 3,793 lines pre-`.B.4`, ~3,000 LOC post-`.B.4` (EngineCommon extract removes ~700-800 LOC). Still 2× over threshold.

Per `feedback_no_defer_for_effort`: full close, not partial. Per `feedback_motivated_collaborator_for_caramel`: best-software path.

**Why subfolder over flat-sibling for this header specifically:**
- 4-5 logical sub-units (Run / Async / HotSwap / Boot / Helpers) — at flat-sibling shape would create `EngineShardedRun.hpp` + `EngineShardedAsync.hpp` + `EngineShardedHotSwap.hpp` + `EngineShardedBoot.hpp` siblings, all prefix-repeating "EngineSharded"
- Expected to grow further (v6.0 decoupling adds runtime/viewer boundary at this surface)
- `CoreFrameworks/` would have 5+ `EngineSharded*` siblings polluting alphabetical sort
- Subfolder pattern provides explicit "multi-file unit" signal + clean sub-names

**Pattern codification rationale (NEW addition to file-size-split-discipline.md):**

The current `file-size-split-discipline.md` v1.0 codifies flat-sibling shape only (examples use `DOCS/tech-debt/{open,closed,in-flight}.md` — which IS subfolder for docs but the pattern doc cites flat-sibling header examples like `EngineShardedRun.hpp`). The two shapes coexist legitimately:
- **Subfolder** when header has 4+ logical sub-units AND/OR expected to keep growing
- **Flat-sibling** for simpler 2-3 way splits where prefix repetition isn't a problem

This ship codifies the decision rule + first source-code canonical. `.B.7`-`.B.10` apply.

## Design space + future-oriented choices

### Decision A — Sub-file boundary (5 sub-files? 4? 3?)

| Option | Sub-files | Verdict |
|---|---|---|
| (a) 3 sub-files (Run + Async + HotSwap; Boot folds into Run) | Boot is ~200-400 LOC; folds naturally into Run if Run < 1500 post-fold | rejected — Run + Boot fold may push Run over threshold; lose clarity of boot phase |
| **(b) 4 sub-files (Run + Async + HotSwap + Boot)** | Helpers fold into Run if small | **CHOSEN** if Helpers < 100 LOC post-`.B.4` |
| (c) 5 sub-files (Run + Async + HotSwap + Boot + Helpers) | Helpers separate | conditional — apply if Helpers > 100 LOC |
| (d) Per-thread-body sub-files (Run + BinanceWS + DepthWS + Recorder + Notify + GuiPublish + HotSwap + Boot) | Maximal granularity | rejected — over-fragmented; thread bodies share state structures + cleanup; cohesive group |

**Default:** Option (b) 4 sub-files. If Helpers post-`.B.4` is > 100 LOC, escalate to (c) 5 sub-files. Decided at Phase B Step B.1 after measuring post-`.B.4` actual LOC distribution.

### Decision B — Top-level shim shape

| Option | Shim content | Verdict |
|---|---|---|
| **(a) Pure re-export** | Just `#include` directives for sub-files in dependency order + doc comment block explaining the pattern | **CHOSEN** |
| (b) Re-export + thin wrapper | `#include`s + small `EngineSharded_Run` shim wrapper that forwards to sub-file | rejected — adds indirection without payoff; sub-file already exports the function |
| (c) Re-export + version constant | `#include`s + version/build-flag definitions | rejected — those belong in `Version.hpp` |

**Rationale for (a):** Pure re-export preserves include-line stability (external callers don't change). Doc comment in shim documents the pattern application + cross-refs `file-size-split-discipline.md` for future-Claude orientation.

### Decision C — Source-side analog of `parent_index:` / `splits_into:` frontmatter + direct-include enforcement (H1 + M5 amended 2026-05-25)

Source headers lack YAML frontmatter. Codify EXACT comment-block convention + ENFORCE direct-include-of-sub-file prevention.

**Shim file convention (EXACT format; codified in `file-size-split-discipline.md` v1.1 § Source-side analog):**
```cpp
// SPDX-License-Identifier: AGPL-3.0
//
// INDEX shim — re-exports CoreFrameworks/EngineSharded/{Run,Async,HotSwap,Boot}.hpp
// Pattern: subfolder split per DESIGN_SPECS/doc-disciplines/file-size-split-discipline.md v1.1
// Split established: 2026-05-XX (v5.15.5.F.4d.1.B.6)
//
// SPLITS_INTO (dependency order):
//   - CoreFrameworks/EngineSharded/Boot.hpp        — boot-time globals (no internal deps)
//   - CoreFrameworks/EngineSharded/HotSwap.hpp     — hot-swap dispatchers (depends on Boot)
//   - CoreFrameworks/EngineSharded/Async.hpp       — async thread bodies (depends on Boot + HotSwap)
//   - CoreFrameworks/EngineSharded/Run.hpp         — main EngineSharded_Run (depends on all above)
//
// External callers continue: #include "CoreFrameworks/EngineSharded.hpp" (no change)

#pragma once

#define ENGINESHARDED_VIA_SHIM 1
#include "EngineSharded/Boot.hpp"
#include "EngineSharded/HotSwap.hpp"
#include "EngineSharded/Async.hpp"
#include "EngineSharded/Run.hpp"
#undef ENGINESHARDED_VIA_SHIM
```

**Sub-file convention (EXACT format; H1 direct-include-enforcement included):**
```cpp
// SPDX-License-Identifier: AGPL-3.0
//
// PART_OF: CoreFrameworks/EngineSharded.hpp (INDEX shim)
// Pattern: subfolder split per DESIGN_SPECS/doc-disciplines/file-size-split-discipline.md v1.1
// Section: <Run / Async / HotSwap / Boot — single word identifying this sub-file's concern>
//
// Direct inclusion of this sub-file is FORBIDDEN — callers MUST include the shim.
// Reason: shim establishes correct #include order; sub-files have ODR + template dependency
// requirements satisfied only via shim discipline.

#pragma once

#ifndef ENGINESHARDED_VIA_SHIM
#error "Direct #include of CoreFrameworks/EngineSharded/<sub>.hpp is forbidden — use CoreFrameworks/EngineSharded.hpp shim instead"
#endif

// ... sub-file content ...
```

**Codified at this ship's pattern amendment** to `file-size-split-discipline.md` v1.1 § Source-side analog + § Direct-include enforcement.

### Decision F — Friend declaration audit at Phase A (M1 amended 2026-05-25)

If types in EngineSharded reference each other via `friend` declarations + those types end up in different sub-files post-split, friend visibility breaks (`friend X;` only visible to types in same TU).

**Phase A audit task:** `/dod-audit` + grep for `friend` declarations in current `EngineSharded.hpp`. For each:
- Identify both sides of the friend relationship
- Determine which sub-file each side ends up in per Decision A (Run / Async / HotSwap / Boot)
- If split into different sub-files: REFACTOR (extract shared sub-section into earlier-included sub-file so both sides see it) OR move the friend pair to same sub-file
- If friend pairs span 3+ sub-files: re-evaluate sub-file boundaries

**Expected outcome:** Low friend usage in EngineSharded.hpp (it's an orchestrator, not a class with heavy friend coupling); most likely zero friend issues. Phase A audit verifies.

### Decision G — Macro definition ordering discipline (M2 amended 2026-05-25)

X-macro registries + `#define`d helpers have strict definition→consumption order. Splitting EngineSharded.hpp across sub-files preserves this ONLY IF shim include order matches.

**Discipline rule:** Macro DEFINES go in earlier-included sub-files; macro CONSUMERS go in later-included sub-files. Specifically:
- `Boot.hpp` (included first) — define any helpers consumed elsewhere
- `HotSwap.hpp` (second) — may consume Boot.hpp helpers; defines hot-swap-specific helpers
- `Async.hpp` (third) — may consume Boot.hpp + HotSwap.hpp helpers
- `Run.hpp` (fourth) — orchestrator; consumes all above; may define orchestration-specific helpers used nowhere else

**Phase A audit task:** grep for `#define` in current EngineSharded.hpp + identify consumer sites. Decision A sub-file boundaries adjust if needed.

### Decision H — CMake configure + CI tool path discipline (M3 + M4 amended 2026-05-25)

**CMake handling:** Headers (`.hpp`) are include-driven; no compile units added → no CMakeLists.txt edit required for the split itself. BUT:
- If build uses GLOB patterns (e.g., `file(GLOB ENGINE_HEADERS CoreFrameworks/*.hpp)`), new subfolder headers may be missed. **Verify at Phase A:** `grep -r "GLOB" build.sh CMakeLists.txt` returns hits → update GLOB patterns to include subfolder paths.
- If GLOB pattern is NOT used (explicit listing), no change needed.

**CI tool path discipline:** Tools that walk source file paths may have hardcoded patterns. Phase A audit:
- `tools/calls_graph_diff.sh` — verify it handles subfolder paths gracefully (uses `find` typically; should work but verify)
- `tools/check_meta_registry.py` — scans for `FOREACH_*` macro registrations; uses recursive walk; verify subfolder paths included
- `tools/check_per_core_registry_integrity.py` — same
- Other Python tools in `tools/` — `grep -l "CoreFrameworks/EngineSharded" tools/*.py tools/*.sh` to find hardcoded refs

**Update at Phase B:** any CI tool with hardcoded paths gets updated alongside the split.

### Decision D — Include order in shim (dependency-driven)

Sub-files have dependencies. Include order matters when sub-files contain definitions that other sub-files reference.

Expected dependency order (verified at Phase B Step B.1):
1. `Boot.hpp` — boot-time globals; depended on by Run + Async + HotSwap
2. `HotSwap.hpp` — depended on by Run (Run dispatches hot-swap via its API)
3. `Async.hpp` — thread bodies; depended on by Run (Run spawns these threads)
4. `Run.hpp` — main orchestrator; depends on all above

**Tiebreaker rule:** if dependency-graph is ambiguous, alphabetical. If circular dependency surfaces, REFACTOR sub-files to break cycle (pattern application reveals coupling that should be cleaned up).

### R2 — Include-line breakage (external callers point at original path)

**Mitigation:**
- Top-level shim `EngineSharded.hpp` re-exports all sub-files (decision B option (a))
- `rg "EngineSharded.hpp"` post-split verifies zero caller-side diff
- Build catches any breakage immediately

### R3 — Cross-sub-file dependency cycle

**Mitigation:**
- Phase B Step B.1 dependency-graph analysis BEFORE extract
- Circular dependency = REFACTOR sub-file boundary (don't paper over via forward decls)
- Build catches cycle at compile time

### R4 — Template instantiation cost regression

**Mitigation:**
- Build time measured pre-split (baseline) + post-split (verification)
- If regression > 10%, escalate to explicit template instantiation in one .cpp file per template
