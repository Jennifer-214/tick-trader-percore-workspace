# SWAR digit-extraction parser — design-ahead seed (task #6)

Fast digit-extraction for tick ingestion: the "1-cycle digit extraction" perf axis. SEPARATE from #11 — it's the *accelerator* of #11's exact decimal `FromString` (#11 = correct; #6 = fast). The win is biggest **because** of #11 (the decimal scaled-integer target; fuse the digit fold with the decimal-scale step, skip float — `from_chars` is float-targeted; `simdjson` is vendored-but-unused).

## Verification verdict (2026-05-31): WORKS + GENERALIZES
- **Fold sound** (canonical Lemire/Langdale technique) with 3 traps pinned (below).
- **Multi-venue generalizes cleanly:** digit-extraction separable from framing in current code AND in the planned D-123 adapter contract; new venue = 1 FOREACH_EXCHANGE row (D-3/D-106) + 1 adapter, SWAR core untouched.
- **Determinism airtight:** pure int64 → deterministic + portable, no `#if AVX512` gate; H10 SHA-256 dual-build harness reusable (becomes an algorithm-equivalence lock; FP rules N/A); locale-immune → rides `.E.0.1`.
- **Scope note (honest):** the integer-tick venue path (scale-from-venue-config-as-parameter) is ASSERTED but NOT designed — the whole core is decimal-string-shaped today. Defer per D-58 (FIX/IBKR optional-future), but STATED not assumed.

## The fold mechanics (framed; full derive = D-94 pass)
1. **Load + endianness (Trap A — the silent-wrong-money risk):** `memcpy` 8 digit-bytes → `u64`; little-endian puts the string's first char in the LOW byte but the fold wants MSD in the MSB → **`__builtin_bswap64` after load** (clean choice over mirrored constants). LOCK with a byte-significance test (`"00000001"`→1, `"10000000"`→10000000) — proven, not assumed.
2. **Subtract `'0'`:** `x -= 0x3030303030303030` → each lane = digit 0–9 (if valid).
3. **Validate (Trap C — range, NOT nibble):** branchless both-bounds: `c<'0'` underflows `(x-0x30·)`, `c>'9'` underflows `(0x39·-x)`; OR borrow high-bits & `0x8080…`; any bit → bail. NOT `(c & 0xF0)==0x30` (wrongly accepts `':'..'?'` = 0x3A–0x3F).
4. **The fold (3 multiply-shifts, no loop):**
   - `x = (x*2561)>>8` & `0x00FF00FF00FF00FF` → 4× 2-digit (2561 = 256·10+1)
   - `x = (x*6553601)>>16` & `0x0000FFFF0000FFFF` → 2× 4-digit (= 65536·100+1)
   - `x = (x*42949672960001)>>32` → the 8-digit integer (= 2³²·10000+1)
   - (99999999 < 2²⁷ → no overflow in u64.)
5. **Variable-width + bail (Trap B — fixed-8 vs real variable fields):** the fold is fixed-width-8 (D-85: "1-cycle/branchless is fixed-width-only"). Adapter frames the digit run; ≤8-digit run → left-pad `'0'` (zero-pad invariant → contributes 0) + fold; irregular (>8 digits, `.`/`-`/`e`, short) → branchless `__builtin_expect`-rare **bail to #5's scalar accumulate** (byte-identical twin). `"D.F"` → fold D and F as separate ≤8 runs, combine via #5's decimal scale.

- **A4 (MED→HIGH-on-BNB)** — commission DROPPED on non-USDT asset (BNB-pay, a common account default) → a fabricated `notional×rate` fee booked instead; AND the reconcile-replay path (`Reconcile_ParseMyTrades`→`ApplyMissedFills`) drops the parsed `t.commission` entirely (`HandleFill` called with no commission args, `Reconcile.hpp:546`). The contract must carry `commission` + `commissionAsset` source-exact through BOTH the WS and reconcile paths.
- **A5 (MED, Knight-shaped)** — WS fill side never cross-checked vs venue `"S"` (taken from local order type only). Cheap defense-in-depth: parse `"S"`, assert == local side, warn/skip on mismatch.
