#### HIGH.1 — Cache-line layout of 5 domain bitmap fields on ControllerConfig

- **Surface:** Plan .F-.F.3 + ControllerConfig.hpp struct definition
- **Pattern(s):** bitmap-flag-api.md (cache-line awareness), CLAUDE.md item 4 (per-core SoA)
- **Symptom:** The 5 new domain bitmap fields (oms_cfg_flags, gate_cfg_flags, ml_cfg_flags, risk_cfg_flags, ops_cfg_flags) = 1+1+2+1+1 = 6 bytes total. Plan does not specify their placement or alignment on ControllerConfig struct. Current ControllerConfig is large (~2-3 KB); unclear whether:
  1. All 5 are placed adjacently → share single cache line (locality win)
  2. Scattered across struct → multiple cache lines (scattered access cost)
  3. Adjacent to hot-path-read fields (drainer reads cfg.oms_cfg_flags every cycle) → false-sharing risk with mutations elsewhere
- **Example of concern:** If oms_cfg_flags is placed next to a mutable field (e.g., a per-core state counter), and drainer thread reads oms_cfg_flags while slow-path writes to the counter, cache-line bounce occurs (false-sharing penalty ~40-400ns). This is NOT a bug (reads are read-only), but a perf regression if not managed.
- **Suggested fix:** In .F implementation:
  1. Audit ControllerConfig struct layout to find the "hot-path-read" cluster (fields read by drainer in hot inner loop)
  2. Place all 5 domain bitmap fields ADJACENT to that cluster, OR on separate cache line if cluster is full
  3. Use `alignas(64)` on the bitmap block if separating onto own line
  4. Add explicit comment block in ControllerConfig.hpp explaining cache-line placement rationale
  5. Bench gate drainer p99 latency post-.F to verify no regression
- **Effort estimate:** ~2h (audit + placement decision + bench)
- **Cross-references:** 
  - DESIGN_SPECS/bitmap-flag-api.md "## Cache-line awareness" section (implicit; not explicitly stated in current draft)
  - CLAUDE.md item 4 (per-core data plane, SoA discipline)
  - CLAUDE.md item 18 (slow-path latency; drainer is "slow" in name but runs in hot outer loop at ~100ns target)
- **Severity rationale:** Not a bug, but a perf optimization visible from the amendment. Drainer touches oms_cfg_flags every cycle in hot path. False-sharing would show up post-ship in paper testing latency. Better to design cache layout during coding than debug latency regression later.

#### HIGH.2 — STAMP_CFG_AUTOPOPULATE bit-extract emit variant integration concerns

- **Surface:** Plan .F.2 (FOREACH_ML_CFG_FLAG + stamp-binding) + ML_Headers/StampBoundCfgRegistry.hpp
- **Pattern(s):** 
  - x-macro-registry-with-presence-dispatch.md (partial-mirror + stamp emit)
  - wire-format-byte-preservation-discipline.md (HMAC chain preservation)
  - autopopulate-pattern-for-production-caller-class.md (bit-extract variant mechanics)
- **Symptom:** Plan .F.2 proposes a NEW "bit-extract emit variant" of STAMP_CFG_AUTOPOPULATE. Instead of reading `cfg.confidence_enabled` directly, the new path reads `BITMAP_IS_SET(cfg.ml_cfg_flags, MASK_ML_CFG_CONFIDENCE_ENABLED)` and emits that bit's value as the cfg key. This is sound in theory (bit-packing should preserve wire format), but the implementation path interleaves TWO distinct wire-format sources in ONE registry walk:
  1. Existing FOREACH_STAMP_BOUND_CFG entries read from classic cfg scalar fields (e.g., cfg.risk_degradation_curve)
  2. New entries read from bitmap bit-extracts (cfg.ml_cfg_flags bit 0 = confidence_enabled)
  
  If a future .F.X sub-ship adds a STAMP_BOUND entry that is ALSO a bitmap domain (e.g., a new RISK_CFG_FLAG that is stamp-bound), the registry walk now has 3 sources. Adding a 4th, 5th source scales complexity linearly. Plan does not document an explicit dispatch shape for "how to emit multiple bitmap domains + scalar fields in a single-registry walk without drift."

- **Concrete concern:** The bit-extract emit logic must be defined SOMEWHERE so that:
  1. All 3+ emission sources are coordinated in one walk (STAMP_CFG_AUTOPOPULATE)
  2. Emit order is preserved (HMAC-locked)
  3. Adding a new bitmap domain doesn't break existing emission paths
  
  Current plan says "extend STAMP_CFG_AUTOPOPULATE with a bit-extract emit variant" but doesn't define the dispatch shape. Is it:
  - Option A: Add a per-entry `emit_source` column (SCALAR / BITMAP_<DOMAIN>) + token-paste dispatch?
  - Option B: Inline bit-extract helper macros within the main FOREACH_STAMP_BOUND_CFG walk?
  - Option C: Separate pre-walk (bitmap entries) + main walk (scalar entries) + post-walk (more bitmap)?
  
  Without explicit dispatch shape, the implementation risks:
  - Code duplication (each bit-extract entry copy-pastes the emit logic)
  - Emit-order drift (maintenance burden: add a new bitmap domain → manually reorder registry lines to preserve HMAC-locked order)
  - Silent test failure (round-trip emit→parse works BUT diverges from reference stamp HMAC due to emit-order change)

- **Suggested fix:**
  1. **Before .F.2 coding starts:** define the dispatch shape explicitly in plan section .F.2.
     - Recommended: Option A (per-entry `emit_source` column) + token-paste `STAMP_CFG_AUTOPOPULATE_EMIT_<SOURCE>` variants. This mirrors SCOPE COLUMN pattern from heterogeneous-registry-pattern.md and is clean to extend.
  2. Add explicit test in .F.2 test suite:
     - Emit new stamp with confidence_enabled from bit-extract
     - Parse legacy stamp with confidence_enabled from scalar field
     - Verify both parse to same runtime state (bit-extract produces same parsed value as scalar source)
     - Verify round-trip emit→parse→re-emit produces byte-for-byte identical stamp (HMAC chain preserved)
  3. Document the dispatch shape in DESIGN_SPECS/heterogeneous-registry-pattern.md "Hybrid form" section (currently draft; update at .I closes).

- **Effort estimate:** ~3h (dispatch design ~0.5h + code ~1h + tests ~1.5h)
- **Cross-references:**
  - DESIGN_SPECS/heterogeneous-registry-pattern.md line 183-186 (hybrid form section — currently vague on dispatch mechanics)
  - DESIGN_SPECS/x-macro-registry-with-presence-dispatch.md (Option C: token-paste dispatch is proven pattern)
  - DESIGN_SPECS/wire-format-byte-preservation-discipline.md (HMAC chain is test-driven; round-trip test catches divergence)
  - Plan .F.2 section lines 610-638 (stamp-binding integration)
- **Severity rationale:** Not ship-blocking if implementation is tested rigorously, but CRITICAL to get the design right BEFORE coding to avoid a costly refactor at .F.3/.F.4 if stamp emit order drifts undetected.

#### HIGH.3 — AUTOPOPULATE branchless mask-compute verification

- **Surface:** Plan .F-.F.6 domain registry AUTOPOPULATE macros
- **Pattern(s):** bitmap-flag-api.md (branchless access), CLAUDE.md item 18 (branchless slow-path preferred)
- **Symptom:** Plan section .F proposes AUTOPOPULATE macro that uses:
  ```cpp
  _new_flags |= ((cfg).legacy_field ? MASK_OMS_CFG_##name : 0u);
  ```
  This is a classic branchless idiom: `condition ? MASK : 0` → compiler emits cmov (conditional move, ~1 cycle, no branch). However, the plan does NOT verify (via inspection or disassembly mention) that the C++ compiler actually generates cmov vs a real branch. If the compiler is conservative (e.g., -O1 or certain GCC versions), it might emit a branch instead (misprediction cost ~10-25 cycles).
  
  The alternative branchless form uses the "-mask trick":
  ```cpp
  _new_flags |= (-(uint64_t)(cfg).legacy_field) & MASK;
  ```
  This forces all-ones (if true) or zero (if false) via arithmetic negation, then AND with mask. Guaranteed branchless on all compilers + architectures. More obscure but more predictable.

- **Suggested fix:**
  1. In each domain registry header (.F-.F.6 implementation), add ONE comment block explaining branchless choice:
     ```
     // v5.14.9.F — AUTOPOPULATE branchless mask compute per item 18.
     // Original: _new_flags |= ((cfg).field ? MASK : 0);
     // Emits cmov (branch-free) on x86-64 with -O2/-O3.
     // Verify with: objdump -d | grep -A5 OMS_CFG_FLAG_AUTOPOPULATE
     ```
  2. Add a post-.F.6 bench gate in the verification section:
     - Disassemble AUTOPOPULATE to confirm NO branch instructions in the inner loop
     - If branch found, replace with `-mask` form or file TECH_DEBT for future micro-opt

- **Effort estimate:** ~1h (compile + disassemble check)
- **Cross-references:**
  - CLAUDE.md item 18 (slow-path latency reduction; branchless preferred)
  - DESIGN_SPECS/bitmap-flag-api.md (mentions branchless access but doesn't cover mask compute idioms)
- **Severity rationale:** Not a bug (compiler usually gets it right), but a verification step that costs 1h now vs discovering a 10-25ns latency regression during paper testing.

#### MEDIUM.1 — Per-core override resolution branchless evaluation

- **Surface:** Plan .F.6 (PER_CORE_OVERRIDE auto-flow) + override resolution logic
- **Pattern(s):** bitmap-flag-api.md (branchless), CLAUDE.md item 18(d)
- **Symptom:** Plan .F.6 section describes per-bit override resolution as:
  ```cpp
  uint8_t effective_oms_flags = ((cfg.cores[c].oms_cfg_flags_override_set & cfg.cores[c].oms_cfg_flags_override) |
                                  (~cfg.cores[c].oms_cfg_flags_override_set & cfg.oms_cfg_flags));
  ```
  This is the standard "select-if-set" pattern: `(override_set & override_value) | (~override_set & global_value)`. Branchless ✓. However, the pattern uses TWO intermediate masks (override_set in both arms), which is semantically correct but not the most compact form.
  
  Alternative form (single-evaluation):
  ```cpp
  uint8_t effective_oms_flags = cfg.oms_cfg_flags ^ ((cfg.oms_cfg_flags ^ cfg.cores[c].oms_cfg_flags_override)
                                                       & cfg.cores[c].oms_cfg_flags_override_set);
  ```
  Or using a SELECT macro (if defined elsewhere):
  ```cpp
  effective_oms_flags = SELECT(cfg.cores[c].oms_cfg_flags_override_set,
                               cfg.cores[c].oms_cfg_flags_override,
                               cfg.oms_cfg_flags);
  ```

- **Suggested fix:** Plan form is CORRECT and clear; defer this as a micro-opt opportunity (TECH_DEBT-0XX). If profiling reveals per-core override resolution is a bottleneck (unlikely, runs once per slow-path), revisit. No action needed for .F.6 ship.

- **Effort estimate:** 0h (defer to TECH_DEBT)
- **Cross-references:** CLAUDE.md item 18(d) (branchless micro-opts)
- **Severity rationale:** MEDIUM because it's a micro-opt opportunity (1-2ns), not a functional issue or macro-level perf gap.

#### MEDIUM.2 — Cross-domain bitmap collapse opportunity

- **Surface:** Plan .F-.F.3 (5 separate uint8_t/uint16_t domain bitmap fields on ControllerConfig)
- **Pattern(s):** bitmap-flag-api.md (memory + false-sharing trade-offs), CLAUDE.md item 20 (BITMAP_* trade-off section)
- **Symptom:** The amendment proposes 5 separate bitmap fields:
  - oms_cfg_flags: uint8_t (2 flags; 6 bits headroom)
  - gate_cfg_flags: uint8_t (6 flags; 2 bits headroom)
  - risk_cfg_flags: uint8_t (3 flags; 5 bits headroom)
  - ops_cfg_flags: uint8_t (2 flags; 6 bits headroom)
  - ml_cfg_flags: uint16_t (7 flags; 9 bits headroom)
  - **Total: 5 fields, 20 bytes on cache-aligned struct** (4+4+4+4+4 or 1+1+2+1+2 depending on packing; need to verify actual layout)
  
  Alternative design: collapse into ONE uint64_t with bit-position partitioning:
  ```
  uint64_t cfg_flags = 0;
  // Bits [0:1]   = OMS (2 flags)
  // Bits [2:7]   = GATE (6 flags)
  // Bits [8:10]  = RISK (3 flags)
  // Bits [11:12] = OPS (2 flags)
  // Bits [13:19] = ML (7 flags)
  // Bits [20:63] = RESERVED (44 bits headroom for future domains)
  ```
  
  **Trade-off analysis:**
  - **Current (5 fields):** +20 bytes ± cache-line alignment padding; per-domain cache-line granularity (if each domain is separate CL); false-sharing protection (mutations to risk_cfg_flags don't bounce oms_cfg_flags cache line)
  - **Collapsed (1 field):** -16 bytes; single load for "any cfg flag set?" check; single atomic for multi-domain updates; loss of per-domain false-sharing protection (if drainer reads oms while slow-path writes to a different slow-only domain, they still bounce same CL)
  
  **Assessment:** Current design (5 fields) is CORRECT for v5.14.9.F because:
  1. OMS domain is read by drainer (hot path adjacent) — separate from slow-only domains (RISK, OPS) avoids false-sharing
  2. ML domain is stamp-bound + hot-path-adjacent (confidence checks) — separate field makes sense
  3. GATE domain reads cached on slow-path entry — separate from OPS (session/notify) is fine
  
  **When collapsed form would win:** Post-v5.14.9, if all 5 domains become slow-path-only (drainer doesn't read oms_cfg_flags), then collapse to single uint64_t saves 16 bytes + clarifies "these are all cfg flags, not mixed domains." Currently, not a compelling win.

- **Suggested action:** Flag as a post-v5.14.9 design-space exploration (TECH_DEBT-0XX: "cfg flag bitmap collapse after drainer oms dependency expires"). For now, 5 fields is correct.

- **Effort estimate:** 0h (design decision already correct; defer future refactor)
- **Cross-references:**
  - CLAUDE.md item 20 (BITMAP_* trade-offs; per-domain vs single bitmap)
  - DESIGN_SPECS/bitmap-flag-api.md (false-sharing discussion)
- **Severity rationale:** MEDIUM because it's a design-space opportunity, not a bug. Current design is RIGHT for v5.14.9 due to hot-path locality needs.

## High-performance opportunities surfaced (NEW thinking per Caramel request)

### a. Cache-line layout of domain bitmaps + hot-path-read separation (HIGH.1 DETAILED)

**Opportunity:** ControllerConfig struct layout exposes a micro-architectural cache-line strategy decision.

**Current plan:** 5 bitmap fields (20 bytes) unplaced on the struct.

**Analysis:**
- Drainer thread reads `cfg.oms_cfg_flags` in hot inner loop (100-200ns target per execution cycle)
- Other 4 domains (GATE, RISK, ML, OPS) are read on slow-path entry (once per cycle, ~10-100µs cycle)
- If oms_cfg_flags shares a cache line with a slow-path-WRITTEN field (e.g., state counter), drainer's cacheline-read bounces when slow-path writes (false-sharing penalty 40-400ns)

**Recommended layout strategy:**
1. **Identify the "hot-read cluster"** on ControllerConfig (fields read by drainer every cycle)
   - Candidate: risk_pct, portfolio-sizing fields, cfg flags (oms at minimum)
2. **Place oms_cfg_flags ADJACENT to hot-read cluster** (same cache line if space, or immediately before/after)
3. **Place slow-only domains (RISK, OPS) on SEPARATE cache line** (add `alignas(64)` marker)
4. **ML domain:** Place adjacent to confidence threshold fields (which drainer reads during gate checks)
5. **GATE domain:** Currently slow-path-entry-cached; less critical; place adjacent to GATE threshold fields

**Expected win:** 2-5% drainer latency reduction (saves ~1-2 cache-line bounces per cycle when slow-path runs concurrently). Paper-test visible in p99 latency if 4+ cores running concurrently with slow-path contention.

**Implementation cost:** ~2h (audit, decision, bench)

**Recommended design:**
```cpp
// Per-entry emit_source column in FOREACH_ML_CFG_FLAG:
#define FOREACH_ML_CFG_FLAG(X) \
    X(CONFIDENCE_ENABLED,     STAMP_BOUND,    ...) \
    X(CONFIDENCE_COMPOSITE,   STAMP_BOUND,    ...) \
    X(BANDIT_ENABLED,         RUNTIME,        ...) \
    X(...)

// Dispatch in STAMP_CFG_AUTOPOPULATE:
#define X(name, domain, emit_src, doc) \
    STAMP_CFG_AUTOPOPULATE_EMIT_##emit_src(name, domain, doc)

#define STAMP_CFG_AUTOPOPULATE_EMIT_STAMP_BOUND(name, domain, doc) \
    // Read domain bitmap bit; emit as cfg key
    
#define STAMP_CFG_AUTOPOPULATE_EMIT_RUNTIME(name, domain, doc) \
    // Skip emit; runtime-only in execution context
    
FOREACH_ML_CFG_FLAG(X)
```

**Win:** Explicit dispatch prevents silent drift when new bitmap domains are added. Tests can verify all STAMP_BOUND entries are emitted in correct order.

**Implementation cost:** ~3h (design + implement + test; critical to do BEFORE .F.2 coding starts)

TEST(StampBoundMLCfgFlags, RoundTrip_EmitParseHMAC) {
