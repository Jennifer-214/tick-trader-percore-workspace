## Critical handoff-premise corrections (verify-before-act per `feedback_compaction_degrades_treat_handoffs_as_hints.md`)

The handoff doc + my orientation prompt contained 3 false premises that BOTH the DOD audit and merge-scan agents independently caught:

### Correction 1: "sp_* atomics read DIRECTLY by GUI thread" — FALSE

Verified via reading `DataStream/EngineTUI.hpp:1187-1196`: `sp_last_tick_us`, `sp_cycles_total`, `sp_yield_count`, `sp_state` are FIELDS on `PerCoreSnap`. `GUI/DashboardPanels.hpp:2327-2360` reads `pc->sp_*` where `pc = &snap->per_core[i]` — that's **snapshot-mediated**, symmetric with all other PerCoreSnap fields.

The cross-thread access happens at the **snapshot-publish boundary** (`EngineTUI.hpp:1839-1846`: snapshot publisher does `__atomic_load_n(..., RELAXED)` to capture sp_*-from-live-CoreContext into PerCoreSnap). Publisher runs at ~30Hz on the GUI thread. False-sharing concern is still real (publisher reads slow-path-written atomics + neighbor fields share cache line) — but the cadence is publish-rate not GUI-frame-rate.

**Impact:** alignas(64) isolation is still warranted for the sp_* cluster, but the cost-savings estimate is ~100-300 ns per snapshot publish × 16 cores at 30 Hz = ~50-150 µs/sec engine-wide. Modest but real.

### Correction 2: "embedded RollingStats × 4" — FALSE (mostly)

RollingStats × 4 lives inside `CoreSlowState<F>` (`ControllerEventLoop.hpp:102-136`), which is **POINTER-attached** via `CoreContext<F>::slow_state` (line 477; heap-allocated per-engine via `InitArena_Alloc`, line 704; ~3MB per engine × 16 engines = ~48MB total). Comment at line 472-476 explicitly documents the pointer-not-inline choice (would overflow 8MB stack on test allocations).

**Impact:** RollingStats × 4 audit is a different surface from EventLoopState's main cache-layout reorg. .B can include CoreSlowState in scope, but it's a separate cluster reorg (heap-attached struct, different access pattern) — needs to be called out distinctly in the plan, not conflated with EventLoopState reorg.

### Correction 3: sizeof(EventLoopState<64>) ≈ "272KB" — STALE BY ~15-20×

Per readiness audit rough tally: CoreContext<64> ≈ 700-1000B per core × 16 = ~12-16KB for cores[] array. Plus EventLoopState engine-wide fields (~200B). Plus CoreLatencyStats inheritance and other sub-structs. **Actual sizeof(EventLoopState<64>) ≈ 13-18 KB.** Not 272KB.

The "272KB" might have been from an earlier session conflating EventLoopState (struct) + the 16 × ~3MB CoreSlowState heap attachments, but that math doesn't work either (16 × 3MB = 48MB).

**Impact:** Step 0 of .B coding MUST run `pahole bin/engine` or hand-tally `sizeof(EventLoopState<64>)` + `sizeof(CoreContext<64>)` + `sizeof(CoreSlowState<64>)` against actual compiled output. This is the data-driven baseline for the reorg.

## Audit findings synthesis (ranked by ROI + structural impact)

### TIER 1: Clear structural wins — must-do for .B

**S1. Explicit `struct alignas(64) CoreContext<F>` declaration + sizeof static_assert.**
- Currently CoreContext's 64B alignment is TRANSITIVELY inherited via embedded CoreLatencyStats (which IS alignas(64) per `CoreLatencyStats.hpp:55`). Per C++ ABI rules, `alignof(CoreContext<F>) >= alignof(CoreLatencyStats) = 64`, so sizeof(CoreContext) IS rounded up to multiple of 64 → inter-slot false-sharing structurally prevented today.
- **Risk: brittle.** A future refactor removing CoreLatencyStats's alignas(64) silently breaks inter-slot guarantee.
- **Fix:** make alignment local to CoreContext declaration; ~5 LOC + static_assert.
- DOD Finding 10.

**S2. HOT/WARM/COLD field reorg of CoreContext per cache-layout-discipline Rule 4.**
- Current layout interleaves HOT (per-cycle decision fields), WARM (per-event accounting), COLD (display/lifetime/diag) — slow-path cycle touches ~17-22 cache lines from CoreContext per cycle.
- Target post-reorg: ~5-7 lines (HOT cluster only on per-cycle access).
- Concrete reorg shape proposed in DOD audit Finding 3.
- **Cost:** ~80 LOC reorder + ~3 alignas(64) cluster boundaries + cluster-padding fields.
- **Win:** ~500-800 ns/cycle warm-cache; up to 1.5 µs/cycle cold-cache. Locks pattern for .C/.D/.E sibling sweeps.

**S3. CoreContextDisplayMeta extraction (cache-layout-discipline Rule 1).**
- Extract 12 × `diag_*` FPN<F> fields (288B = ~4.5 cache lines) + `cfg_drift_tier1/2_count` + `cfg_drift_strict_refused` + `barrier_shadow_event_count` + `last_ml_critical_log_us` + `last_ml_threshold` + `last_ml_effective_threshold` + `core_ks_trips_total` + `idle_cycles` + `prev_gate_log_state` + `last_buy_dominant_horizon` + `last_barrier_mode_used` to a sibling `CoreContextDisplayMeta<F>` struct.
- These are written by slow-path body (rebuild diag capture) but READ ONLY by ShardedSnapshot publisher (`ShardedSnapshot.hpp:455-628`). Never read by per-cycle decision code.
- **Cost:** ~150 LOC (extraction + ~20-30 write-site rewrites in RebuildOneCore + ~15 read-site rewrites in ShardedSnapshot).
- **Win:** ~340-360 bytes/core × 16 = ~5.5KB memory; ~400-700 ns/cycle cold-cache savings; HOT cluster shrinks from ~8 lines mixed to ~3 lines clean.
- DOD Finding 1.

**S4. alignas(64) isolation of `sp_*` atomic cluster + WS telemetry cluster.**
- Group `sp_last_tick_us / sp_cycles_total / sp_yield_count / sp_state` (CoreContext lines 462-465; 25B) into `alignas(64) struct sp_telemetry { ... };`.
- Group `last_ws_tick_us + ws_ticks_per_5s + ws_bucket_last_sec[5] + ws_bucket_count[5]` (EventLoopState lines 557-567; 76B before padding) into `alignas(64) struct ws_telemetry { ... };`.
- **Cost:** ~20 LOC.
- **Win:** prevents cross-thread cache-line bouncing between slow-path writers and snapshot-publisher reads. ~100-300 ns/publish.
- DOD Finding 2.

**S5. Bit-pack 5 pure booleans → `uint8_t core_state_flags`.**
- Pure booleans on CoreContext: `dirty` (181), `model_load_failed` (249), `warmup_log_emitted` (267), `core_kill_tripped` (401), `cfg_drift_strict_refused` (255).
- 5 bits used, 3 free. New `FOREACH_CORE_STATE_FLAG(X)` registry per CLAUDE.md item 13 + item 20 (BITMAP_* API).
- Save 4 bytes/core × 16 = 64B + branchless multi-flag check enabled.
- **Cost:** ~30 LOC (registry + accessors) + ~12 write-site rewrites.
- **Win:** memory + branchless mask compute (e.g., `BITMAP_ANY(flags, MASK_KILL_TRIPPED | MASK_MODEL_LOAD_FAILED)` for early-exit predicates).
- DOD Finding 5 + reuse-pattern from `partner_pending_bitmap` (v5.14.9.G; engine-wide variant).

**S6. static_asserts for sizeof + offsetof per cluster boundary.**
- Currently ZERO static_asserts on EventLoopState/CoreContext/CoreSlowState. Precedent for sister surfaces: `ExecutionCore.hpp:176-184` (5 layout asserts), `RollingStats.hpp:127-133`.
- Add: `sizeof(CoreContext<64>) % 64 == 0`, `alignof(CoreContext<64>) == 64`, `offsetof` per cluster anchor (HOT-anchor, WARM-anchor, sp_telemetry, display_meta).
- **Cost:** ~15 LOC; zero runtime.
- **Win:** compile-time lock against accidental field-insert/reorder regression. Catches future drift.
- DOD Finding 9.

**S7. CoreSlowState lazy_rebuild fields hoisted to head.**
- `us_at_last_rebuild` + `price_at_last_rebuild` (lines 134-135) currently at struct TAIL after the 4 RollingStats (~170KB upstream).
- Per-cycle `EventLoop_RebuildOneCore` lazy-rebuild gate reads them FIRST (line ~2046). Currently cold-cache on every cycle.
- Hoist alongside `ema_price` at head. ~4 LOC.
- **Win:** ~3 ns/cycle warm; ~100 ns/cycle cold cache.
- DOD Finding 8.

### TIER 2: HIGH ROI but scope-extending — strong candidates for .B inclusion

**T1. CONSOLIDATE ShardedSnapshot's 4 per-core walks into 1 unified pass.**
- `ShardedSnapshot.hpp` walks `state->cores[i]` in FOUR separate loops: line 297 (bitmap_consistency), 347 (wins/losses/gross), 412 (per_core agg), 429 (per_core_extra).
- Each loop fetches `state->cores[i]` (sizeof ≈ 1KB) → 4 × 16 cores × ~1KB cold-cache pulls per snapshot publish.
- Consolidating to 1 loop that touches each cluster sequentially: ~46MB/s memory bandwidth savings at 60 Hz GUI publish (3 × 16 × ~1KB = 48KB redundant pulls per publish × 60 Hz).
- **Cost:** ~50-80 LOC refactor; boundary-stable (PerCoreSnap output is bytewise-identical).
- **Win:** 46MB/s memory bandwidth + cleaner snapshot publisher code + leverages .B's HOT/WARM/COLD layout for cache-warm sweeps.
- **Risk:** test regression — controller_test must verify snap field values byte-identical post-consolidation.
- Merge-scan Finding 7 (highest-ROI finding from the scan).

**T2. INIT_CORE_FIELDS X-macro registry for EventLoopState_Init.**
- `EventLoopState_Init` (line 594-707) writes ~30 fields into each CoreContext per core (96-line init loop). Reset-paths in `EngineSharded.hpp` (around :2237+) likely mirror many of these writes for engine-reset scenarios. → Class 18 mirror candidate per CLAUDE.md item 19.
- A `FOREACH_CORE_CTX_INIT_FIELD(X)` registry would centralize the init contract; adding a new CoreContext field becomes 1 row + auto-flow through all init/reset sites.
- **Cost:** ~100-150 LOC registry + ~3 caller-site rewrites; nontrivial but bounded.
- **Win:** structural elimination of mirror-drift class. Per Caramel's 2026-05-09 framing ("headache now > issues later"). 4 prior structural-fix wins in this session confirm the discipline pays back.
- **Risk:** scope creep on .B; could ship as .B.1 sub-tag bundled with the main reorg, or defer to a focused TECH_DEBT close in .B+1.
- Readiness Finding 11. Requires more verification of actual reset-site count before commitment.

### TIER 3: Defer or document only

**D1. `_pad[6] / _pad_kill[3] / _pad_strategy_state[7]` consolidation.**
- 16 bytes of padding across 3 sites. After bit-pack (S5) + cluster reorg (S2), these might naturally absorb new fields or get eliminated via reordering. Don't pre-engineer; let the reorg shape determine.
- Merge-scan Finding 3 + 8.

**D2. FOREACH_ROLLING_WINDOW(X) registry for the 4 RollingStats windows.**
- Marginal win (3 LOC savings at push site); template-barrier complications (different RollingStats<F, W> types).
- Defer to TECH_DEBT entry. Don't include in .B.
- Merge-scan Finding 9.

**D3. Hour-of-day session multiplier lookup table.**
- Branch in slow-path RebuildOneCore body; predictable; below noise.
- Out of .B scope; flag for /merge-scan revisit.
- DOD Finding 6.

**D4. Branchless mask compute rewrites in RebuildOneCore.**
- Most branches in RebuildOneCore are predictable OR gate expensive work — keeping them branchy is correct per Rule 8 explicit guidance.
- No structural rewrite warranted for .B.
- DOD Finding 6.

## Proposed scope shape — 3 OPTIONS for operator decision

### OPTION A: Minimal .B (TIER 1 only) — ~300-400 LOC

Just S1-S7 (must-do items). Defer T1 (snapshot consolidation) + T2 (INIT registry) to later sub-ships or TECH_DEBT.

**Pros:** Conservative; isolates failure modes; quick close (~3-4h coding + 1h verification).
**Cons:** Leaves the 46MB/s snapshot-publish bandwidth on the table; defers mirror-extinction structural opportunity to a future ship that may bury under different priorities.

### OPTION B: .B + snapshot consolidation (TIER 1 + T1) — ~400-500 LOC ← RECOMMENDED

S1-S7 + T1 (consolidate ShardedSnapshot's 4 per-core walks). Defer T2 to .B+1 (or bundle into v5.15.5.B.2 sub-tag if scope grows further).

**Pros:** Captures the highest-ROI merge-scan finding alongside the cache-layout sweep. Cluster boundaries enable cache-warm snapshot sweeps (synergy between S2 + T1). Boundary-stable refactor (PerCoreSnap output bytewise-identical).
**Cons:** Larger ship; ~5-6h coding + 1.5h verification. Snapshot consolidation needs careful test verification.

### OPTION C: Full structural + INIT registry (TIER 1 + T1 + T2) — ~600-700 LOC

All of B + T2 (INIT_CORE_FIELDS X-macro registry; structural Class 18 close).

**Pros:** Extinguishes the mirror-drift class for CoreContext init/reset; structural-fix-preferred per CLAUDE.md item 19 + Caramel's standing rule. Sets up the pattern for .C/.D/.E sibling reorgs to inherit. 2 NEW DESIGN_SPECS land (vs 1 in option B).
**Cons:** Significantly larger ship; ~8-10h coding + 2h verification. T2 requires more pre-coding verification (actual reset-site count audit) before commitment.

### My recommendation: OPTION B

Tier 1 must-dos lock the cache-layout discipline + the snapshot consolidation captures the highest-ROI parallel win. T2 (INIT registry) is genuinely a separate concern (mirror-pattern class) and warrants its OWN focused ship rather than being bundled. Mirror-function audit in .B can produce the EVIDENCE for T2 as a follow-up TECH_DEBT entry without forcing the structural close in .B itself.

Sister consideration: .C (OrderManagerState) likely has similar mirror-init class. If T2 ships in .B, .C inherits the pattern; if not, .C may surface fresh evidence + an even better registry shape. Defer-then-ship-properly fits the boundary-stable refactor preference.
