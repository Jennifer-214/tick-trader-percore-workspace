## 🔴 THE NEXT ACTION — one decision, then the work is mechanical

**The `STAMP_SET` refusal is DESIGNED and PROVEN, and deliberately NOT landed.** Armed, it rejected
exactly the emit-side sites with **zero other error classes** — including `StampHelper.hpp:250`, the
live `inference_cfg_bandit_blend_ratio` bit-without-value. That is the proof the approach works:
the defect stopped compiling.

It was **reverted the same session** because it was measurably too broad: a GROUP bit
(`xgb_hyperparams`) has no field of its own, so setting it without a value is legitimate, and the
assert refused those too. `STAMP_SET`'s in-code comment records all of this so the next session does
not rebuild the version already proven wrong.

**The correct rule is narrower: refuse `STAMP_SET` only when a same-named MEMBER exists.**

**The blocker is a toolchain call, and it is the operator's:**

- C++20 spells it inline — `requires { (s).name; }` — no generated traits, no name-universe question.
- **This build is C++17** (`CMakeLists.txt:4`), where it needs a `void_t` trait per name.
- Generating those traits needs a name-universe, and the FIRST one reached for is **unusable as-is**:
  `FOREACH_STAMP_BOUND_MODEL_CONST_GROUPS` is **drifted** from `enum StampHasFlagBit` (missing
  `environment_meta`; both premises re-verified TRUE at close). Generating from it leaves a hole
  exactly where a future caller lands — the same vacuity shape this arc has been closing all along.

> ⚠️ **CORRECTED AT CLOSE by the independent review — read this before picking a route.** The
> paragraph above is the reasoning the session deferred on, and its *inference* is wrong even though
> both its premises are true. The trait's question is **"does `s.name` exist as a MEMBER?"**, and that
> universe is the **member-bearing rows** — `FOREACH_STAMP_BOUND_MODEL_CONST` itself, which is already
> the generator for the struct bodies. Generate `has_member_<name>` from the main registry and default
> **ALLOW** for any name not in it, and you get exactly the stated correct rule (refuse only where a
> same-named member exists) with **no dependence on `_GROUPS` at all**. `_GROUPS` is simply the wrong
> universe for the question, so its drift is a real but SEPARATE defect — homed **TECH_DEBT-286**.
>
> **Consequence for the routes below: try the member-bearing-registry route FIRST.** Route B ("fix
> the drift, then generate from `_GROUPS`") is likely unnecessary work, and route A ("move to C++20")
> is a far larger blast radius than the problem warrants. They remain listed because they are still
> valid fallbacks, not because they are the leading candidates.
