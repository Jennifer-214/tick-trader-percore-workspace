Both files carry `__AVX512F__` (the ONLY files: `rg -ln "__AVX512F__"` = exactly these two). Each AVX-512
region has a paired scalar `#else` producing the documented byte-identical output (comments cite the
byte-determinism rules: `_mm512_div_pd` not mul-by-reciprocal; `_mm512_fmadd_pd` to match scalar FMA under
`-ffp-contract=fast`).

**ONE byte-identity nuance worth the A-class eye (not a blocker):** `BanditLearning.hpp` AVX-512 floor uses
`_mm512_max_pd(probs, 1e-10)` (`:227`) while the scalar `#else` uses `if (probs_out[i] < 1e-10) probs_out[i] = 1e-10;`
(`:241`). `max_pd` vs the scalar compare-assign are byte-equivalent **except possibly at NaN/signed-zero edges**
(`max_pd` has defined NaN/`-0.0` propagation; the scalar `<` differs on NaN). Inputs are bounded probabilities
(>0), so this is almost certainly vacuous — but it IS exactly the kind of edge the H10 byte-compare gate exists
to catch, so the gate is **non-vacuous and worth having**. Flag for the harness fixture design (use realistic
bounded inputs; the gate would legitimately RED if a future edit drifted these).

**`-mno-avx512f` selects the scalar path — VERIFIED (compiled probe):**
```
g++ -march=native              → __AVX512F__ defined   → AVX512F=ON
g++ -march=native -mno-avx512f → __AVX512F__ UNdefined  → AVX512F=OFF   ← scalar #else compiled
```
So the H10 byte-compare (`-march=native` vs `-march=native -mno-avx512f`, memcmp outputs) is **non-vacuous on this host.**

**⚠ PRECISION 1 (fold into Phase C) — the AVX-512 arm must be FORCED, not assumed-native:** this host happens
to have full AVX-512 (`/proc/cpuinfo`: `avx512f avx512bw avx512cd avx512dq avx512vl ...`), so `-march=native`
compiles the AVX-512 path HERE. But the body's Phase C says "`-march=native` (AVX-512 ON) vs `-march=native -mno-avx512f`
(scalar)" — on a **non-AVX-512 CI runner** `-march=native` would compile the SCALAR path on BOTH sides → the gate
compares scalar-vs-scalar = **vacuously GREEN, silently**. **FIX: pin the AVX-512 arm explicitly** —
`-march=skylake-avx512` (or `-mavx512f`) for the "ON" build, `-mno-avx512f` (or just generic) for the "OFF" build —
so the two arms are guaranteed-different REGARDLESS of the runner's host CPU. (Probe confirmed `-march=skylake-avx512`
forces `__AVX512F__` ON even where native wouldn't.) This is the H10 analogue of the FP gate's deliberate
`-DUSE_NATIVE_128` forcing.

(*"rdtsc bracketing has a ~25-30ns floor … subtract the floor"*). The body's Phase A.0 "floor-subtract per Run.hpp:329" matches (the note lives in the same DumpLatency function block).

**Slow-path number — IMPORTANT NUANCE:** the slow-path p99 is NOT in the DumpLatency table. It is emitted


**⚠ PRECISION 2 (fold into Phase D):** this is in **CYCLES (`cy`), not ns.** The H8 slow budget is ≤100μs.
The ratchet MUST convert cycles→ns via the same `tsc_ghz` the run calibrates (`Run.hpp:622`, printed
`[sharded] TSC calibrated at %.4f GHz`) before comparing to 100μs. (The drainer histogram, unlike the per-core
table, stores raw cycles.) Also note: the body says "Phase-7.B histogram (slow p99)" — this is the **DRAINER**
cycle, which is the closest standing slow-path latency signal; it is the drainer cadence, not the per-core
slow-rebuild cycle. If the ratchet's "slow ≤100μs" is meant to gate the **slow REBUILD** path specifically,
there is no standing per-core slow-rebuild histogram emit today — the drainer histogram is the available proxy.
**Recommend: ratchet the drainer-cycle p99 (the emitted signal) + the per-core hot p99; flag the slow-rebuild
gap if a tighter slow signal is wanted (homed, not blocking).**

**Reproducibility for a ratchet baseline:** the emit is deterministic in FORMAT; the VALUES are wall-clock
perf (rdtsc), inherently jittery. The DumpLatency note itself warns about kernel-preemption outliers
(*"try chrt -f 90 + isolcpus on a real production box for cleaner tails"*). **The body's Phase D mitigations
are the right ones and necessary**: explicit ~10% margin + median-of-N-runs + placement as a **MERGE-gate /
on-demand lane, NOT a per-commit hook** (perf builds too slow + too noisy for every commit). p99 specifically
is the noisiest percentile; recommend the ratchet gate on **median-of-N p99** with the margin, and treat the
H8 absolute (≤500ns / ≤100μs) as the hard ceiling + the baseline×(1+margin) as the soft ratchet. **Buildable,
but this is correctly the body's "MEDIUM complexity, the one non-trivial piece."**
