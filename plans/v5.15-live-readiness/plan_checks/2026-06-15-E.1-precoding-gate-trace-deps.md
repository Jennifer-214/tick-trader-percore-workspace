## 2. H21 IDENTIFIER-RETIREMENT — the persisted-key rename (TOP CONCERN — RED)

**This is the Knight-class finding.** H21: persistence/wire-visible identifiers (snapshot VERSIONs, persisted enum CODES, persisted bitmap bits, **cfg-field name KEYS**) are APPEND-ONLY + IMMUTABLE; retire by tombstone, never rename-in-place.

### 2a. `core_N_*` cfg keys ARE wire/persistence-visible identifiers

The cfg parser reads the literal `core_` prefix as a wire key:
```
ControllerConfig.hpp:2878:  if (strncmp(key, "core_", 5) == 0 && strstr(key, "_time_exit_ticks")) ...
ControllerConfig.hpp:2886/2897/2905/2918/2931/2941/2968:  ... "core_", 5 ... (_risk_pct / _max_drawdown_pct / _model_path / _symbol / _model_dir / _strategy / catch-all)
```
Renaming `core_N_strategy` → `node_N_strategy` (plan :899–901, :1760) **changes a persisted cfg key.** An existing `engine.cfg` / per-node cfg carrying `core_0_strategy=...` silently stops being parsed (falls through the renamed `strncmp(key,"node_",5)` branches) → the field reverts to default → **the wrong strategy/risk/TP runs.** That is the H21 failure mode on a capital path.

**How the plan handles it:** it does NOT, structurally. It lists the cfg rename as operator-migration ("engine.cfg rename… engine refuses pre-rename cfg", :1760; "manual rename; operator's responsibility; no backwards compat per D-9", :1772). There is **no `core_`→`node_` back-compat dispatch, no tombstone, no key-alias.** The codebase already HAS the right pattern for this exact problem — `FOREACH_LEGACY_PREFIXED_KEY` (MetaRegistry.hpp:67, "v1→v2 wire-key back-compat dispatch; 16 legacy→unprefixed pairs; parser+tests auto-flow") — and the plan does not extend it. Per `feedback_backwards_compat_not_default_concern`, a clean break is the DEFAULT, BUT cfg keys are explicitly a named load-bearing exception (persistence). At minimum the plan must (a) make the refuse LOUD + actionable (not a silent default-revert — verify the parser FAILS, not falls-through, on an unrecognized `core_*` key), OR (b) add a `core_`→`node_` row-set to `FOREACH_LEGACY_PREFIXED_KEY`.

### 2b. `SHARDED_SNAPSHOT_VERSION` bump is MANDATORY (and the plan's Decision-K forces it) — partially handled

- `SHARDED_SNAPSHOT_VERSION = 10u` (ShardedSnapshotPersist.hpp:94), with live H21 tombstone discipline in-code (v9 rejected; static_assert at :99) + ledgered (`identifier_ledger.txt`: `version|SHARDED_SNAPSHOT_VERSION|10`).
- The snapshot is **POSITIONAL** (`state->cores[i]` raw-fwrite, ShardedSnapshotPersist.hpp:173/501; per-core money block). So the `cores[i]`→`nodes[i]` *in-memory* rename does NOT by itself change the wire bytes. **BUT Decision-K (D-55, plan :1058) re-lays Portfolio/Position to SoA + re-types money to `Money`** → that changes the embedded byte layout → **`SHARDED_SNAPSHOT_VERSION` MUST bump 10→11 + tombstone 10 + ledger `--update`.** Plan Phase H covers stamp body (cluster_id/sub_account_id/variant_id/software_version) + "legacy stamps refused" (:1470) but **does NOT explicitly call the SHARDED_SNAPSHOT_VERSION bump** for the NodeState/SoA re-layout. The `.E.0.10` register's A20 fold (:1932) already maps the 4-edit snapshot-version-bump steps — wire those in. Also note the OMS event-log `OMSEL02` (OrderEventLog.hpp:107) + the D-214 fold (:1925) flag a possible `OMSEL02→OMSEL03` if `FillEvent`/`OrderEvent` gains persisted fields.
