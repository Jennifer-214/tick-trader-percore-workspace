### 3. Class 24 (Capability-cfg surface mismatch) codified

**NEW bug class entry in `DOCS/RECURRING_BUG_PATTERNS.md` Class 24:**

Recurring shape — capability exists in struct + parser + stamp but isn't operator-visible in Settings. Silent miscalibration risk because:
- Operator can't see the field
- Operator can't see if it's set correctly
- Operator can't see if it's being applied (Thompson_Update wire gap)

**NEW going-forward rule in `CLAUDE.local.md`:** every ML capability answers four columns at PR-review time:
1. cfg parse? (ControllerConfig field + parser path exist)
2. Settings render? (FOREACH_CFG_FIELD row exists; Settings panel shows it)
3. Stamp tag? (STAMP_BOUND metadata bit set if parity-relevant)
4. Per-core override? (PER_CORE_OK metadata bit set if per-core relevant)

Any "no" without documented exemption = feature not done. Fire `/ml-audit` at sub-ship close for any ship touching ML capability.

**Two canonical examples documented:**
- (a) `.F.4c` paper-test surfacing 17 invisible ML cfg fields
- (b) `.F.4c.2` Thompson_Update wire gap (mode selectable, doesn't work)

## Lessons learned (from commit body + ml-audit + skip-rationale)

### Paper-test discovery is the load-bearing post-commit verification step

The `.F.4c` paper-test surfaced TWO critical gaps in 60 seconds:
- ImGui "name is already taken" runtime regression (widget-ID collision)
- 17 ML cfg fields invisible in Settings panel (Class 24 first canonical)

Neither would have been caught by `./build.sh test` (compile-time + unit-test coverage doesn't exercise ImGui hash table OR Settings panel render path completeness). The operator paper-test gate is structurally necessary for GUI-affecting ships.

### Class 24 codification reinforces framework-discipline meta-principle

The cfg<->ML 4-column surface-alignment audit (NEW going-forward rule) is a process gate analog to the registry-discipline structural gates. Where the framework discipline says "if pattern can recur, encode it in a registry," the Class 24 rule says "if capability surface can drift, encode the alignment check in a 4-column audit." Both reduce recurrence by making the discipline mechanical/checkable rather than vigilance-dependent.

### Skip-rationale doc pattern for absorbed deliverables

The `.F.4c.1.1` skip per operator directive is captured in a dedicated rationale doc (`postmortems/2026-05-15-skipped-v5.15.5.F.4c.1.1-rationale.md`) — NOT buried in commit messages OR successor ship plan bodies. Pattern: when a planned ship is skipped because deliverables are absorbed elsewhere, write a stand-alone rationale doc explaining WHY + WHERE THE WORK LANDS INSTEAD. Aligns with auto-write discipline contract.

### Operator-invisible ML capability = silent miscalibration risk

The Class 24 canonical examples (`.F.4c` 17 invisible fields, `.F.4c.2` Thompson_Update wire gap) share a common pattern: capability EXISTS (struct field + parser + stamp emit) but operator can't observe it in Settings panel OR can't verify it's being applied in production paths. Both ship with the silent risk that operator believes capability is active but isn't (or has stale defaults that look correct but aren't tuned).

**Principle:** every ML capability needs end-to-end operator visibility from cfg load -> Settings render -> production wire -> stamp tag. The 4-column audit makes this mechanical.
