## What worked

1. **Cohort-audit upfront.** Verified trading_mode siblings (`reconcile_mode` + `model_verify_strict`) are all enum-valued, NOT BIT_FLAG-eligible → direct uint8 storage is correct cohort homogeneity. No migration needed. CLAUDE.local.md cohort-audit rule 2026-05-11 saved a wrong-design path.
2. **Step 0 stale-claim audit caught two real drift items.** (a) `cfg.core_strategies_explicit_set` already existed as uint16_t bitmap at line 917 from v5.9.0c — the plan was working from spec drift. Removed planned task A.3 (~30 min saved). (b) `LiveReadiness_Verify` lifecycle: PerCoreSnap.failure_flags isn't populated until snapshot publish at slow-path tail; boot gate runs BEFORE. Fixed by routing through `aggregate_zoo_drift(zoo)` from handle source-of-truth.
3. **Bitmap thinking.** Per Caramel's "bitmap is probably better right?" framing — once core_strategies_explicit_set was discovered as already-existing-bitmap, the branchless mask-compare check fell out naturally: `(set & ((1<<N)-1)) == ((1<<N)-1)`. Single AND + single compare; no per-core branch.
4. **X-macro registry for boot checks.** FOREACH_LIVE_READINESS_CHECK + inline X-macro walk in LiveReadiness_Verify means adding a future pre-flight check = 1 row + 1 template fn. Future v6.0 headless service can introspect the registry to publish "what does the boot gate check" via REST/JSON endpoint without runtime dispatch overhead.
5. **Existing infrastructure reuse.** TECH_DEBT-033 entry was pre-written by prior session in "CLOSED (planned)" form — just flipped status. /readiness skill structure was designed for additive checks; just appended Check 31. v5.14.9.F's FOREACH_LIFECYCLE_CFG_FLAG bitmap already had `breakeven_on_profit` allocated; just needed the read site. v5.14.1's FOREACH_STAMP_BOUND_CFG auto-flowed trading_mode through 6 consumer sites from one row.

## What surprised

1. **`cfg.core_strategies_explicit_set` already existed at line 917.** Discovered at Step 0 grep. The plan-check from earlier session (sprint plan-check HIGH-2) had said "core_strategy_explicit[] doesn't exist; needs adding" — that was wrong. The field has existed since v5.9.0c as `core_strategies_explicit_set` (plural-strategies + bitmap form). Spec drift in the plan. Net win: ~30 min of work saved + structural fit was already correct.
2. **EventLoopState's `state` is FUNCTION-local in EngineSharded_Run.** The cores array is `static ExecutionCore<F> cores[MAX_EXECUTION_CORES]` at function scope. LiveReadiness_Verify needs access to `state.cores[c].model_handle`. Resolved by passing the local `state` to the verify function — it's already accessible at the insertion point (line ~1472).
3. **Template parameter type mismatch (int F vs unsigned F).** Initially wrote `template <int F>` in LiveReadiness.hpp; compile failed with template-deduction errors because `CoreModelZoo<F>` + `ControllerConfig<F>` + `EventLoopState<F>` all use `template <unsigned F>`. One `sed -i 's/template <int F>/template <unsigned F>/g'` fixed all 11 occurrences.
4. **Check 26 was already a placeholder for a DIFFERENT future rule.** The /readiness SKILL.md had "Check 26 — DEFERRED-FOR-FUTURE-SHIP (placeholder)" reserved for v5.14.E.1's Class 18 symmetry test pattern. Couldn't overwrite. Added Check 31 instead. Plan needs a note about this.
5. **OrderManager_Init signature complexity.** Plan test setup used the simple init form; reality needs adapter + live_trading + starting_balance + fee_rate + event_log_mode + event_log_path. Existing tests use `EventLoopState_InitLegacy` for simple setup. Switched to that pattern.

## Decoupling-roadmap positioning

**POSITIONING: ⬆️⬆️ STRONGLY POSITIVE.**

- `trading_mode` is stamp-bound → mode introspectable via any model's stamp body without inspecting cfg.
- `FOREACH_LIVE_READINESS_CHECK` is compile-time table → future v6.0 headless service can publish "what does the boot gate check" via REST/JSON endpoint with zero dispatch overhead.
- `aggregate_zoo_drift` single chokepoint → drift state queryable from one helper; future external monitors (Rust / Python / Grafana) can call it without re-implementing.
- `breakeven_on_profit` reuses existing FOREACH_LIFECYCLE_CFG_FLAG bitmap → flag is mmap-friendly, single-AND query.
- All slow-path additions are publication-only (no in-process locking introduced; no callback registry with fn pointers crossing GUI/engine boundary).
