**Step 3:** MLStrategy exit-side prediction:
```cpp
// Inside ML_BuildParameters or MLStrategy_Adapt (slow-path).
// Gated on cfg.use_exit_model + exit_predictor_count > 0 +
// position currently open for this core's slot.
if (config->use_exit_model && ezoo->exit_predictor_count > 0
    && core_has_open_position(state, slot)) {
    int regime = state->cores[slot].regime_state.current;
    BanditState *bandit = &ezoo->exit_bandits[regime];  // NEW (.A.4)
    // Blend exit predictions across horizons via bandit weights:
    float blended_exit_prob = ensemble_blend(
        ezoo->exit_predictor, ezoo->exit_predictor_count,
        features, bandit);
    if (blended_exit_prob > config->exit_threshold) {
        // Force early exit. Slot's current position closes via
        // OMS_PushSubmit ORDER_MARKET_SELL. SHALT_EXIT_PREDICTED
        // surfaces in observability.
        FPN<F> qty = state->oms->portfolio.positions[slot].quantity;
        FPN<F> price_fpn = FPN_FromDouble<F>(current_price);
        OMS_PushSubmit(state->oms, (int16_t)slot, ORDER_MARKET_SELL,
                        qty, FPN_Zero<F>(), FPN_Zero<F>(),
                        STRATEGY_ML, price_fpn);
        // Mark for reward attribution (.A.4): exit_bandit gets credit
        state->cores[slot].last_exit_was_predicted = 1;
    }
}
```

**Cfg fields to add:**

FPN<F> exit_threshold;       // exit prob > this → fire early exit; default 0.6

**SHALT code:** `X(EXIT_PREDICTED, "exit-predicted", "ML exit

**Tests:**
- Default cfg → no exit prediction; existing behavior preserved
- cfg enabled + no exit models → graceful skip
- cfg enabled + exit models loaded → prediction runs; threshold

**Cost analysis (per /latency-track discipline):**
- Default cfg: ~5ns (one flag check + early return)
- cfg enabled + no exit models: ~10ns (flag + count check)
- cfg enabled + 3 exit models loaded: ~3-15μs slow-path cycle

  follow-up) drops to ~50ns.

**Hot path UNTOUCHED.** Slow-path budget impact: ~3-15μs added
when cfg enabled. Lazy rebuild (v5.12.2.B) skips ~30-50% of cycles
on stable regime → ~half the cost.

### v5.13.4 — Sell-side bandit (parallel to buy-side)

**Goal:** Each side gets its own per-regime BanditState. Buy-side
bandit tracks per-arm rewards from BUY decisions; exit-side tracks
per-arm rewards from EXIT decisions. Reward attribution splits per
event source.

**Why separate bandits:**
- Different objectives: buy = "right entry"; exit = "right exit"
- Different feature distributions at decision moment
- Different reward attribution semantics: buy reward = realized
  P&L per trade; exit reward = realized P&L vs counterfactual hold
- Bandits learn faster when action space is bounded — forcing one
  bandit to learn entry+exit doubles action space
- Independent regime conditioning per side

**Files touched:**
- `ML_Headers/CoreModelZoo.hpp` — `BanditState exit_bandits[REGIME_COUNT]`
  parallel to existing `bandits[REGIME_COUNT]`
- `ML_Headers/CoreModelZoo.hpp` — Init/Free + LoadFromCfg/AutoDetect
  populate exit_bandits when exit_predictor_count > 0
- `Strategies/MLStrategy.hpp` — pre-trade: read buy_bandit weights
  for ensemble blend; post-trade: increment buy_bandit pulls
- `Strategies/MLStrategy.hpp` — pre-exit: read exit_bandit weights;
  post-exit: increment exit_bandit pulls
- `CoreFrameworks/OrderManager.hpp` (drainer / fill handler):
  reward attribution post-fill — when exit fires:
  - If `last_exit_was_predicted == 1` (set by MLStrategy in .0
    when exit predictor fired): credit exit_bandit with realized
    P&L vs counterfactual ("would-have-held to TP" estimated as
    entry_price × tp_pct)
  - Else: credit buy_bandit only (existing flow)
- `CoreFrameworks/ShardedSnapshot.hpp` — persist exit_bandits
  alongside existing bandits. Bump SHARDED_SNAPSHOT_VERSION OR
  use Surface G `has_exit_bandits` flag for forward-compat
- `tests/controller_test.cpp` — exit_bandit init/persist/load;
  reward attribution math

**Counterfactual reward formula:**
```
At trade exit, given:
  entry_price, exit_price (actual), tp_pct, sl_pct,
  last_exit_was_predicted (1 if exit predictor fired, 0 otherwise)

If exit_predicted:
  hypothetical_tp_price = entry_price * (1 + tp_pct)
  hypothetical_sl_price = entry_price * (1 - sl_pct)
  // Estimate counterfactual: would price have hit TP or SL first?
  // For MVP: assume TP would have hit (best-case counterfactual).
  hypothetical_pnl = (hypothetical_tp_price - entry_price) * qty - fees
  actual_pnl = (exit_price - entry_price) * qty - fees
  exit_bandit_reward = actual_pnl - hypothetical_pnl
    // Negative reward if exit was premature (held would have been better)
    // Positive reward if exit avoided a loss (held would have lost)
  Bandit_Update(&exit_bandit[regime], chosen_arm, exit_bandit_reward_bps)

Else (TP/SL fired naturally):
  buy_bandit reward = realized_pnl_bps (existing flow)
```

**Risk:** counterfactual assumption ("TP would have hit") is
optimistic. Real counterfactual requires post-hoc inspection of
forward price path — possible in backtest, hard live. MVP uses
optimistic assumption; v5.13.X refines if paper-test data shows
the optimism creates systematic exit-bias.

**Cfg fields:**
```cpp
int exit_bandit_enabled;     // 0 (default) = no exit reward attribution; 1 = on
FPN<F> exit_bandit_lr;       // bandit learning rate; default 0.1 (matches buy-side)
```

**Tests:**
- exit_bandits init to uniform priors when exit_predictor_count > 0
- exit_bandits stays uninit when no exit models loaded
- counterfactual reward math: positive when exit avoided loss;
  negative when exit was premature
- Bandit_Update on exit_bandit doesn't affect buy_bandit
- Snapshot persist/load round-trips exit_bandits state

**Tag:** `v5.13.4` umbrella. Sub-tags: .A (struct + init), .B
(reward attribution), .C (snapshot persist), .D (tests).
