## Architecture deep-dive

### Sub-account topology + economic isolation

**What Binance sub-accounts give us:**

Binance Master account `M` can create N sub-accounts `S1, S2, ..., SN` via the Binance sub-account API. Each sub-account:

- Has its own API key + secret (created via Sub-Account API)
- Has its own balance (funded via internal transfer from master OR another sub-account; INSTANT and FEE-FREE)
- Has its own 1200/min rate-limit budget (NOT shared with siblings)
- Has its own user-data WebSocket listenKey
- Has its own positions list + trade history
- Has its own audit trail (Binance keeps separate records per sub-account)

**Internal transfer semantics:**

```
POST /sapi/v1/sub-account/futures/internalTransfer (HMAC signed by master key)
{
  "fromEmail": "master@example.com" OR "subaccount1@example.com",
  "toEmail": "subaccount2@example.com",
  "asset": "USDT",
  "amount": "1000.00",
  "futuresType": 2  // SPOT internal transfer
}

Response (~50ms):
{
  "tranId": 1234567890
}
```

Transfers are atomic + instant. Reconciliation post-transfer confirms balance updates on both source + destination.

**Per-node economic isolation:**

Each per-node binds to one sub-account. When per-node trades:
- Submits use sub-account's credentials + count against sub-account's rate budget
- Fills update sub-account's balance (engine-side mirror)
- Errors (rate-limit; ban) affect only that sub-account
- Total deployment capacity = N × 1200/min for N sub-accounts (vs 1200/min shared at master)

**This is structurally stronger than virtual partition mode:**
- Virtual partition: engine tracks per-node balance; shared real account
- Real sub-accounts: BINANCE enforces per-node balance + rate budget isolation
- Failure containment: one sub-account suspended → only that node affected; siblings continue

```cpp
    }

        FATAL("Sub-account %u has enableTrading=0; refusing to start", subaccount_id);
    }

        return -1;
    }

    return 0;
```

### Sub-account credential storage discipline

**Where credentials live:**

```
configs/clusters/binance/credentials/
├── master.cfg                    # MASTER account credentials (for sub-account ops only)
│   # Contents (gitignored):
│   # api_key = ${BINANCE_MASTER_API_KEY}
│   # api_secret = ${BINANCE_MASTER_API_SECRET}
│   # (env-var references; engine resolves at boot)
├── sub_0.cfg                     # Sub-account 0
│   # api_key = ${BINANCE_SUB0_API_KEY}
│   # api_secret = ${BINANCE_SUB0_API_SECRET}
│   # email = subaccount0@example.com   # for internal-transfer routing
│   # client_order_id_prefix = "C0_S0_"  # encoded in submits
│   # initial_capital_target_usdt = 2500  # for monitoring drift
├── sub_1.cfg
├── ...
└── sub_N.cfg
```

**Security boundaries:**

1. **File permissions:** `chmod 600 sub_*.cfg` (only engine user readable). Engine binary runs as `fox` user; cfg files owned by `fox`.

2. **Env-var resolution:** cfg files reference env vars (`${BINANCE_SUB0_API_KEY}`). Actual keys live in operator's secrets management (systemd `EnvironmentFile=`; HashiCorp Vault; etc.).

3. **No credentials in git:** `configs/clusters/*/credentials/` directory gitignored. Operator manages out-of-band.

4. **API key permissions:** Sub-account keys MUST have:
   - `enableTrading = true`
   - `enableSpotAndMarginTrading = true` (or futures-specific subset)
   - `enableWithdrawals = false` (CRITICAL)
   - IP-restricted (cfg-driven list; verified at boot)

**Boot-time permission audit (per D-31):**

```cpp
int VerifySubAccountPermissions(BinanceAdapter<F>& adapter, uint32_t subaccount_id,
                                 const SubAccountCredentials& creds) {
    // Query Binance for actual permissions (read-only operation)
    AccountInfo info;
    int result = BinanceQuery_AccountInfo(adapter, subaccount_id, &info);
    if (result != 0) {
        LOG_ERROR("Failed to query sub-account %u permissions: %d", subaccount_id, result);
        return result;
    }

    // CRITICAL: refuse start on enableWithdrawals
    if (info.canWithdraw) {
        LOG_FATAL("Sub-account %u has canWithdraw=true; refusing to start trading. "
                  "Disable withdrawal permissions at Binance API key management.",
                  subaccount_id);
        return -EPERM;
    }

    if (!info.canTrade) {
        LOG_FATAL("Sub-account %u has canTrade=false; cannot trade", subaccount_id);
        return -EPERM;
    }

    // Verify IP restriction matches cfg
    if (!IPRestrictionMatches(info.allowedIps, creds.allowed_ips)) {
        LOG_FATAL("Sub-account %u IP restriction mismatch", subaccount_id);
        return -EPERM;
    }

    LOG_INFO("Sub-account %u permissions verified: trade-only, IP-restricted", subaccount_id);
    return 0;
}
```

```cpp
struct SubAccountRateLimit {

    std::atomic<uint64_t> window_start_us;
    uint32_t max_per_minute;                  // 1200 default

    uint32_t subaccount_id = node.binding.subaccount_id;
    SubAccountRateLimit& rl = g_subaccount_rate_limits[cluster_id][subaccount_id];

    int32_t tokens = rl.tokens_available.fetch_sub(1, std::memory_order_acq_rel);
    if (tokens <= 0) {
        // Restore + deny
        rl.tokens_available.fetch_add(1, std::memory_order_release);
        return false;
    }
    return true;
}
```

### Rate-limit budget arithmetic + sliding window

**Per-sub-account budget:**

```cpp
struct SubAccountRateLimit {
    alignas(64) std::atomic<int32_t> tokens_available;   // current tokens (max=1200)
    alignas(64) std::atomic<uint64_t> window_start_us;   // sliding window start
    uint32_t max_per_minute;                              // 1200 for Binance retail
    uint32_t refill_per_second;                           // 20 (=1200/60)
};

// Refill at slow-path cadence (per-cluster manager thread; every 100ms)
void SubAccountRateLimit_Refill(SubAccountRateLimit* rl, uint64_t now_us) {
    uint64_t window_start = rl->window_start_us.load(std::memory_order_acquire);
    uint64_t elapsed_us = now_us - window_start;

    if (elapsed_us >= 60 * 1000 * 1000) {
        // Window expired; reset
        rl->tokens_available.store(rl->max_per_minute, std::memory_order_release);
        rl->window_start_us.store(now_us, std::memory_order_release);
    } else {
        // Refill proportionally: add tokens for elapsed time
        int32_t refill = (elapsed_us * rl->refill_per_second) / 1000000;
        int32_t current = rl->tokens_available.load(std::memory_order_acquire);
        int32_t new_count = std::min((int32_t)rl->max_per_minute, current + refill);
        rl->tokens_available.store(new_count, std::memory_order_release);
        rl->window_start_us.store(now_us, std::memory_order_release);
    }
}

// Per-node submit checks own sub-account rate budget
bool NodeSlowPath_CheckRateLimit(NodeState<F>& node) {
    uint32_t cluster_id = node.binding.cluster_id;
    uint32_t subaccount_id = node.binding.subaccount_id;
    SubAccountRateLimit& rl = g_subaccount_rate_limits[cluster_id][subaccount_id];

    // Try to decrement (atomic; lock-free)
    int32_t tokens = rl.tokens_available.fetch_sub(1, std::memory_order_acq_rel);
    if (tokens <= 0) {
        // Restore + deny
        rl.tokens_available.fetch_add(1, std::memory_order_release);
        return false;
    }
    return true;
}
```

**Why this works:**

- Per-sub-account budget tracked independently (no shared counter)
- Atomic fetch_sub is lock-free + cache-line-friendly
- Refill at slow-path cadence (every 100ms = 20 tokens per 100ms = 200ms to refill 40 tokens for typical burst)
- Worst case: cluster's per-node submits all hit at same instant; first 1200 succeed; rest get -EAGAIN; retry next cycle

Per-cluster panel shows per-sub-account rate budget:


### Capital allocation policy enforcement (with worked examples)

**Per-cluster cfg:**

```
configs/clusters/binance/cluster.cfg:
reserve_pct = 0.20             # 20% always in master account; never deployed
max_per_node_pct = 0.30        # No single node holds >30% of cluster's deployable
deployable_pct = 0.80          # Computed: 1 - reserve_pct
```

**Worked example 1 — Reserve enforcement:**

Cluster has $10,000 USDT total across master + sub-accounts:
- master: $2,500
- sub_0: $1,875
- sub_1: $1,875
- sub_2: $1,875
- sub_3: $1,875

Total cluster capital: $10,000
Reserve required: $10,000 × 0.20 = $2,000 (in master)
Deployable: $10,000 - $2,000 = $8,000

If sub_0 attempts to open $3,000 position:
- Current deployed: $7,500 (sum of sub_0..3 balances)
- Proposed deployed: $7,500 + $3,000 = $10,500
- Proposed reserve: $10,000 - $10,500 = -$500 (NEGATIVE)
- BREACH: refuse submit

Engine returns ERR_RESERVE_BREACH; operator alerted via webhook.

**Worked example 2 — max_per_node enforcement:**

Same cluster. sub_2 currently holds $1,875 position. sub_2 attempts to open additional $1,200 position:
- Current per-node deployed: $1,875
- Proposed per-node deployed: $1,875 + $1,200 = $3,075
- max_per_node: $10,000 × 0.30 = $3,000
- BREACH: $3,075 > $3,000; refuse submit

Engine returns ERR_PER_NODE_CAP_BREACH; node's slow-path skips submit.

```cpp
bool AggregatorEnforcement_CanSubmit(EngineState<F>& state, NodeState<F>& node,
                                      const SubmitCommand<F>& cmd) {
    uint32_t cluster_id = node.binding.cluster_id;
    ClusterState<...>& cluster = state.clusters[cluster_id];

    // Sum all cluster capital (master + N sub-accounts)
    FPN<F> total_cluster_capital = GetTotalClusterCapital(cluster);

    // Compute deployable budget (1 - reserve_pct)
    FPN<F> reserve_required = FPN_Mul(total_cluster_capital,
                                       FPN_FromDouble(cluster.cfg.reserve_pct));
    FPN<F> deployable_budget = FPN_Sub(total_cluster_capital, reserve_required);

    // Sum current deployed across cluster's nodes
    FPN<F> current_deployed = GetTotalDeployedInCluster(cluster);
    FPN<F> proposed_deployed = FPN_Add(current_deployed, cmd.notional);

    // Check reserve
    if (FPN_Greater(proposed_deployed, deployable_budget)) {
        LOG_WARN("Cluster %s: reserve breach refused. Deployable=%s, Proposed=%s",
                 cluster.exchange_name, FPN_ToString(deployable_budget),
                 FPN_ToString(proposed_deployed));
        return false;
    }

    // Check max_per_node
    FPN<F> max_per_node = FPN_Mul(total_cluster_capital,
                                   FPN_FromDouble(cluster.cfg.max_per_node_pct));
    FPN<F> proposed_node_deployed = FPN_Add(node.slow_account.open_notional, cmd.notional);
    if (FPN_Greater(proposed_node_deployed, max_per_node)) {
        LOG_WARN("Node %s/node_%u: per-node cap breach refused. Cap=%s, Proposed=%s",
                 cluster.exchange_name, node.binding.subaccount_id,
                 FPN_ToString(max_per_node), FPN_ToString(proposed_node_deployed));
        return false;
    }

    return true;
}
```

```cpp
// reserve_pct = 0.2
// max_per_node_pct = 0.30

bool AggregatorEnforcement_CanSubmit(EngineState<F>& state, NodeState<F>& node,
                                      const SubmitCommand<F>& cmd) {
    uint32_t cluster_id = node.binding.cluster_id;
    ClusterState<...>& cluster = state.clusters[cluster_id];

    // Sum master + sub-account balances
    FPN<F> total_cluster_capital = GetTotalClusterCapital(cluster);
    FPN<F> deployed = GetTotalDeployedInCluster(cluster);
    FPN<F> reserve_required = FPN_Mul(total_cluster_capital, FPN_FromDouble(cluster.cfg.reserve_pct));

    // Check reserve
    FPN<F> proposed_deployed = FPN_Add(deployed, cmd.notional);
    FPN<F> proposed_reserve = FPN_Sub(total_cluster_capital, proposed_deployed);
    if (FPN_Less(proposed_reserve, reserve_required)) {
        return false;  // would breach reserve
    }

    // Check max_per_node_pct
    FPN<F> max_per_node = FPN_Mul(total_cluster_capital, FPN_FromDouble(cluster.cfg.max_per_node_pct));
    FPN<F> proposed_node_deployed = FPN_Add(node.slow_account.open_notional, cmd.notional);
    if (FPN_Greater(proposed_node_deployed, max_per_node)) {
        return false;  // would exceed per-node cap
    }

    return true;
}
```

## Honest risks (with worked examples)

### R1 — Sub-account provisioning operational complexity

**Risk:** Setting up N sub-accounts (Binance UI + API key creation + IP restrictions + permission flags + env-var setup) is substantial one-time operator work.

**Worked example:** Operator wants to deploy 4 sub-accounts for Binance cluster:
1. Binance UI → Sub-Accounts → Create Sub-Account (4 times; ~5 min each = 20 min)
2. Verify each sub-account email + receive verification email + click link (~5 min)
3. Create API keys per sub-account (Binance UI → API Management; ~10 min × 4 = 40 min)
4. Set trade-only permissions on each key (~5 min × 4 = 20 min)
5. Add IP restrictions on each key (~5 min × 4 = 20 min)
6. Transfer initial capital from master to each sub-account (~5 min × 4 = 20 min)
7. Populate engine.cfg env vars (~10 min)
8. Boot engine; verify preflight passes (~5 min)

Total operator setup: ~2-3 hours one-time.

**Mitigation:**
- OPERATOR_MANUAL.md has step-by-step checklist
- Testnet first (zero capital risk)
- Engine boot-time check catches most misconfigurations
- Reusable scripts (provided in CONTRIBUTING/add-subaccount.md)

**Severity:** MED (one-time cost; well-mitigated by documentation)

### R2 — API permission misconfiguration (CRITICAL safety)

**Risk:** Operator may forget to disable withdrawal on sub-account API key. If engine ever runs with withdrawal-enabled key, theoretical attacker accessing engine state could drain funds.

**Worked example:** Operator creates sub_2 API key in Binance UI; forgets to uncheck "Enable Withdrawals". Engine boots; without preflight check, would happily trade. If engine server compromised (malware; supply chain attack; etc.), attacker exfiltrates API keys; uses withdrawal endpoint to drain sub_2.

WITH preflight check: engine refuses to start; explicit error: "Sub-account 2 has canWithdraw=true; refusing to start. Fix at Binance API key management."

**Mitigation:**
- MANDATORY boot-time check queries Binance for actual permissions (not trusting cfg-side claim)
- Refuses to start; operator must fix; explicit action required
- Logs the refusal with actionable message
- Per-key IP restriction (limits blast radius if key leaks)
- DOCS/INCIDENT_RUNBOOK.md documents key rotation procedure

**Severity:** HIGH (financial loss potential; well-mitigated by structural enforcement)

### R3 — Internal transfer rate limit + counts against budget

**Risk:** Binance internal transfers count against master account's rate budget. Frequent operator-triggered transfers could deplete budget for legitimate trading.

**Worked example:** Operator triggers 100 small transfers in 1 minute (e.g., automated rebalancing script bug). Master rate budget consumed. Sub-accounts can still submit (independent budgets) but master can't query account info, etc.

**Mitigation:**
- Manual operator-triggered (no automated rebalancing in `.E.5` scope)
- Rate-limited transfers (max 1 transfer per 5s; cfg-overridable)
- Visibility: rate-budget consumption visible in fox-tui
- Alert if budget < 50% remaining

**Severity:** LOW-MED (operationally manageable)

### R4 — Reconciliation drift

**Risk:** Engine-side balance mirror could drift from Binance truth (network issue mid-fill; missed WS event; etc.). Capital allocation enforcement could use stale balance, leading to over-deployment.

**Worked example:** sub_1 has actual balance $1,500 on Binance. Engine-side mirror shows $2,000 (didn't see last fill). Per-node cap calculation uses $2,000; allows position that actually breaches limit.

**Mitigation:**
- Hybrid reconciliation cadence (per-fill + every 5min) catches drift quickly
- On reconcile mismatch: log + alert + halt affected node trading
- Periodic full reconcile (every 30min; cfg-overridable)
- Operator-triggered reconcile via fox-cli

**Severity:** MED (financial implications; well-mitigated by cadence)

### R5 — Concurrent sub-account suspension

**Risk:** Binance suspends a sub-account (could be: API abuse, KYC issue, suspicious activity flag). Engine's submits to that sub-account start failing en masse.

**Worked example:** Binance suspends sub_2 due to perceived abnormal trading pattern. All sub_2 submits start failing with -2010 or similar. Engine's node_2 fills its retry SPSC; doesn't trade; sibling nodes continue.

**Mitigation:**
- Detect suspension via consecutive submit failures (cfg threshold; default 10 consecutive)
- Halt node trading on suspension; mirror to per-node kill flag
- Alert operator via webhook
- Operator workflow: contact Binance support; await resolution; manually un-halt via fox-cli

**Severity:** MED (operationally manageable; isolation via sub-account design)

### R6 — Capital pool inflexibility (real sub-accounts vs virtual partition tradeoff)

**Risk:** With real sub-accounts, capital can't move FREELY across nodes; requires explicit internal-transfer + reconcile cycle. If one node's strategy is losing while sibling is winning, you can't easily rebalance in real-time.

**Worked example:** sub_0's momentum strategy is losing $500; sub_2's ml strategy is winning $500. Operator would like sub_2's gains to support sub_0's continued operation. With virtual partition: trivial (just adjust cfg). With real sub-accounts: internal transfer + reconcile + ~minutes of latency.

**Mitigation:**
- Operator awareness: real sub-accounts are STRUCTURALLY isolated by design
- Internal-transfer plumbing makes rebalancing easy (fox-cli command)
- Trade-off documented in DESIGN_PHILOSOPHY (per-node economic isolation vs flexibility)
- Auto-rebalance scaffold (in cfg; not implemented at `.E.5`; future work)

**Severity:** LOW (intentional design tradeoff; operator awareness)

### R7 — Sub-account onboarding workflow (first-run operator experience)

**Risk:** First-time operator unfamiliar with Binance sub-account creation; setup mistakes lead to engine boot refusal.

**Worked example:** Operator forgets to add IP restriction to API key (sub-account works but key is more vulnerable). Engine preflight detects IP mismatch; refuses boot. Operator confused.

**Mitigation:**
- OPERATOR_MANUAL.md has detailed setup wizard
- Boot-time error messages are EXPLICIT + actionable
- DOCS/CONTRIBUTING/add-subaccount.md has step-by-step guide
- Testnet first deployment recommended (zero risk)

**Severity:** LOW-MED (first-time friction; well-documented)

### R8 — Forward-promise to `.E.6`/`.E.7`: virtual partition for non-sub-account exchanges

**Risk:** Alpaca doesn't support sub-accounts; IBKR uses FA structure. The architecture from `.E.5` is REAL-sub-account-centric; virtual partition mode for Alpaca needs adapter at `.E.6`.

**Mitigation:**
- NodeState.binding.subaccount_id field already supports both modes (real or virtual; just an index)
- Per-cluster cfg has `subaccount_mode = real | virtual` (default real for Binance; virtual for Alpaca)
- Aggregator enforcement works identically in both modes (just sums per-node state)
- Forward-promise documented in `.E.6`/`.E.7` plan bodies

**Severity:** LOW (substrate handles both modes)
