# v5.10.0 — Foundation: per-phase timers + sparse label buffer + parallel CSV + hardware-aware cfg

**Date:** drafted 2026-05-03 (post v5.9.5j-final merge)
**Branch:** `feat/v5.10-foundation` (current; from `experiment/per-core-sharding`)
**Predecessor:** v5.9 sprint merged @ `5ea002c`; tag `v5.9.5j-final`
**Effort estimate:** 1.5-2 days
**Hot path:** UNTOUCHED (slow-path / training-path / parse-path only)

## Theme

Bundle four design-notes ideas (Ideas #14, #15, #16, #18) into one
foundation ship. Order within the bundle is intentional:

1. **#18 timers FIRST** — instrumentation must precede any perf work
   so subsequent optimizations are measurable, not speculation.
2. **#15 sparse label buffer** — closes a real OOM (2026-05-03) on
   2-year datasets. Architectural fix, not patch.
3. **#16 parallel CSV ingest** — reduces 30-45 min of CSV parse to
   under 10 min on a multi-core box.
4. **#14 hardware-aware cfg** — exposes thread / RAM tunables so
   operator can adapt across hardware (Xeon upgrade etc.).

Foundation does NOT touch stamp body, ML feature math, or hot path.
Pure backtest-pipeline performance + RAM correctness.

## Items

### Item A — Per-phase backtest timers (Idea #18, ~30 min, SHIP FIRST)

Add `clock_gettime(CLOCK_MONOTONIC)` markers in
`BacktestSharded_Run` (and Train Model worker) at phase boundaries.
Print summary at backtest end + display in foxml_suite Training panel.

**Phases instrumented:**
- `parse` — CSV load
- `fan_out` — producer thread feeding SPSC rings
- `feature_collect` — per-core feature_matrix population
- `label_compute` — label assignment (post-#15: sparse phase)
- `hot_path` — engine_arch=per_core_slow tick loop
- `xgboost_train` — booster fit
- `wf_eval` — walk-forward fold evaluation
- `held_out_eval` — held-out gate evaluation
- `stamp_emit` — stamp_write_for_model (incl. HMAC sign)

**Output format:**
```
[backtest summary]
  parse:           42.1s (47%)
  fan_out:         12.3s (14%)
  feature_collect: 8.5s  (10%)
  label_compute:   1.2s  (1%)
  hot_path:        18.7s (21%)
  xgboost_train:   6.8s  (8%)
  total:           89.6s
```

**Files:**
- `Backtest/BacktestEngine.hpp` — phase timer struct + markers
- `Backtest/BacktestPanels.hpp` — Training panel timer display

**Tests:** smoke test that timers populate; relative percentages sum
to ≥99%.

**Why ship first:** every subsequent foundation item (sparse buffer,
parallel CSV, hardware cfg) needs measurable before/after to validate
the change is real.

### Item B — Sparse label buffer (Idea #15, ~4-6h, HIGH-priority OOM fix)

**Problem:** today `label_buffer[tick_count]` allocated per-tick at
~32 bytes/slot. With `poll_interval=100`, 99 of every 100 slots unused.

**Fix:** allocate `label_buffer[sample_count]`. Sample points are at
`poll_interval`-spaced indices; ~100x fewer slots.

**Memory math:**
| Dataset | Tick count | Old (dense) | New (sparse) |
|---|---|---|---|
| 1-year | 895M | 28.6 GB | ~286 MB |
| 2-year | 1.8B | 57 GB (OOM at 30.9 GiB) | ~572 MB |
| 5-year | 4.5B | 144 GB (infeasible) | ~1.4 GB |

5-year datasets become feasible on commodity hardware.

**Implementation:**

- `BacktestData_Load` allocation site:
  - Compute `sample_count = (tick_count + poll_interval - 1) / poll_interval`
  - Allocate `label_buffer = new label_t[sample_count]`
- Consumer-side index translation:
  - `Backtest_RunWalkForward` reads label by `sample_index`, not `tick_index`
  - `HeldOutSplit_TrainEval` same
  - `BacktestResults.sample_tick_indices[]` already maps sample → tick;
    use it for the inverse direction when needed
- Tests:
  - 1-year synthetic dataset: verify post-fix RAM ≤ 1 GB
  - 2-year synthetic dataset: verify completes (no OOM)
  - Bytewise equality: dense (old) vs sparse (new) labels for a 100k-tick
    fixture (proves no off-by-one in index translation)

**Files:**
- `Backtest/BacktestEngine.hpp` — allocation site + consumer rewrites
- `Backtest/HeldOutSplit.hpp` — sample-index propagation
- `Backtest/ValidationSplit.hpp` — sample-index propagation
- `tests/controller_test.cpp` — round-trip + bytewise equivalence tests

**Risk:** Medium-High. Off-by-one in consumer-side index translation is
the silent killer. Bytewise-equivalence test before and after is the
gate.

**Operator validation gate:** 2-year feature collect completes without
OOM on operator's 30.9 GiB box.

### Item C — Parallel CSV ingest (Idea #16, ~2-3h)

`BacktestData_Load` becomes a coordinator dispatching N worker threads.
Each worker reads its assigned files into thread-local buffers;
coordinator concatenates results in chronological order post-load.

**Implementation:**
- `csv_load_workers` cfg (default 4) gates parallelism
- Each worker pthread parses one CSV chunk into thread-local
  `vector<Tick>`
- Cross-file boundary check (v5.9.5j.2's `ts < 1.5e12` filter) preserved
  per-worker
- Post-join: coordinator concatenates worker buffers in file-date order
  (deterministic chronological output)
- Memory cap: ≤ N workers × per-file buffer; warn if projected memory
  > `feature_collect_max_gb` cfg

**Files:**
- `Backtest/BacktestEngine.hpp` — `BacktestData_Load` rewrite
- `tests/controller_test.cpp` — multi-worker load matches single-worker
  load (bytewise)

**Tests:**
- 100-CSV synthetic dataset: `csv_load_workers=1` vs `csv_load_workers=4`
  produces bytewise-identical tick array
- Worker-thread bogus-ts filter still fires (v5.9.5j.2 invariant)
- Cancel-mid-load: workers cleanly drop work (reuses existing
  cancel_flag plumbing)

**Risk:** Medium. Concurrency bugs are silent. Worker buffer
ordering must be deterministic; pthread coordination is the watch-point.

**Operator validation gate:** `csv_load_workers=8` on operator's box
shows linear-ish speedup vs `=1` for the same dataset.

### Item D — Hardware-aware cfg (Idea #14, ~1h)

Add cfg fields exposing currently-hardcoded parameters. These are
operator-tunable so the engine adapts when operator moves to Xeon /
more cores / more RAM:

| Cfg field | Default | Purpose |
|---|---|---|
| `xgb_train_nthread` | **1 (matches current hardcoded behavior)** | XGBoost train thread count. Currently hardcoded to `nthread=1` at `BacktestEngine.hpp:1352, 1638` for determinism. Operator opts in to >1 (with WARN: "breaks bytewise reproducibility"). |
| `xgb_eval_nthread` | 1 | WF/HeldOut eval thread count (matches current; WARN at boot if >1) |
| `csv_load_workers` | 1 (matches current serial load) | Parallel CSV worker threads (Item C). Default=1 preserves current bytewise-deterministic load order; operator opts in to parallel. |
| `feature_collect_max_gb` | 12 | Soft cap on feature_matrix RAM; advisory WARN if dataset projects to exceed (no hard gate) |
| `wf_split_max_gb` | 8 | Soft cap on WF split RAM (advisory WARN) |
| `held_out_max_gb` | 4 | Soft cap on held-out RAM (advisory WARN) |

**Defaults preserve current behavior. No silent behavior flips.**
Operator must explicitly opt in to multi-thread training / parallel CSV
load by setting cfg values >1. CHANGELOG entry will note this:
"v5.10.0 adds operator-tunable threading; defaults match v5.9.5j
behavior (single-threaded training + serial CSV) for bytewise
reproducibility. Set `xgb_train_nthread=N` or `csv_load_workers=N` to
opt in."

**Implementation:**
- Parser additions in `ControllerConfig.hpp`
- Defaults in `engine.cfg.example` (with comments explaining each)
- Read-from-cfg at the right call sites:
  - `xgb_train_nthread` → XGBHyperparams_Apply (already exists, just
    pass cfg value)
  - `xgb_eval_nthread` → WF + Held-Out eval booster init
  - `csv_load_workers` → Item C
  - `*_max_gb` → boot-time RAM projection logic
- Boot-time WARN:
  - Project `feature_matrix` RAM = `sample_count × feature_count × 8 bytes`
  - Project `label_buffer` RAM = `sample_count × 32 bytes` (post-Item B)
  - If projection > `*_max_gb`, emit operator-visible WARN with
    suggested mitigations ("reduce dataset_days" / "raise poll_interval")

**Files:**
- `CoreFrameworks/ControllerConfig.hpp` — 5 cfg fields + parser
- `engine.cfg.example` — 5 defaults documented
- `Backtest/BacktestEngine.hpp` — read cfg at call sites + boot WARN
- `tests/controller_test.cpp` — cfg parser tests + RAM-projection WARN

**Tests:**
- Default cfg parses cleanly
- `xgb_train_nthread=8` propagates to XGBoost
- `csv_load_workers=2` propagates to Item C
- `feature_collect_max_gb=1` triggers boot WARN on a 1-year dataset

### Item E — Internal regression tests (absorbed from former v5.10.0f, ~2h)

Two tests-only additions that catch silent integration regressions.
No new driver scripts; both ship as new TEST_CASE blocks in the
existing `controller_test.cpp` so `./build.sh test` IS the standalone
regression tool.

**E.1 — End-to-end ML pipeline test (~1-2h):**

Single TEST_CASE block exercising the full ML pipeline on a 10k-tick
synthetic fixture: feature collect → train → stamp → load → backtest →
run-history emit → stamp verify. Catches integration breakage that
unit tests miss (e.g., parser change three modules upstream silently
breaks stamp emit).

```
tests/fixtures/10k_ticks_e2e.csv      # NEW: deterministic 10k-tick fixture
tests/controller_test.cpp             # +1 TEST_CASE block (~50 LOC)
```

The fixture is checked-in synthetic data (predictable, no Binance
dependency, runs in <5s). TEST_CASE asserts: stamp_ok=1, run history
JSONL valid, predictions within sanity bounds.

**E.2 — Stamp roundtrip snapshot test (~1h):**

Catches silent canonical-body order regression. Today, if someone
reorders fields in stamp body emit code, HMAC verification fails at
runtime (not test time). Snapshot-based test gates this earlier.

```
tests/snapshots/stamp_canonical.expected     # NEW: golden body bytes
tests/controller_test.cpp                    # +1 TEST_CASE
```

Test feeds fixed `StampInferenceCfgInputs` to `stamp_emit_canonical_body`,
compares output to golden snapshot. Regen procedure documented as
test comment for legitimate stamp body extensions.

**Files (E):**
- `tests/fixtures/10k_ticks_e2e.csv` (NEW)
- `tests/snapshots/stamp_canonical.expected` (NEW)
- `tests/controller_test.cpp` — 2 new TEST_CASE blocks

## Item dependencies (within bundle)

```
A (timers) → ship FIRST; standalone, instruments everything below
B (sparse) → independent of A/C/D but should ship before D's RAM-projection logic
C (parallel CSV) → independent of A/B; depends on D's csv_load_workers cfg
D (hardware cfg) → wires C's csv_load_workers + B's RAM-projection
E (regression tests) → standalone; can ship anytime in bundle (recommend last to validate A-D didn't regress)
```

**Recommended in-bundle order:** A → B → D → C → E
(Timers first; sparse fix for OOM; cfg field additions; parallel CSV;
regression tests last to validate the whole bundle.)

## Risk register

| Risk | Mitigation |
|---|---|
| Item B off-by-one in index translation | Bytewise-equivalence test before/after gates the ship |
| Item C concurrency bug | Worker output ordering is deterministic by file-date; tests verify bytewise-identical output across worker counts |
| Item D cfg parser regression | New cfg fields do not change defaults silently — every default matches current behavior; behavior change only on explicit cfg set |
| OOM not actually fixed by Item B | Operator validation gate: 2-year dataset must complete without OOM before ship is tagged |
| Timer overhead skews results (Item A) | `clock_gettime(CLOCK_MONOTONIC)` is sub-µs; per-tick overhead negligible. Validate by comparing pre-vs-post-instrumentation runtime on small fixture |
