# E.1.0 — A3 ADVERSARIAL audit (necessity / false-confidence / guard-sprawl)

One independent lens, blind to the other agents, re-derived from LANDED code @ HEAD 572c978. Default = REFUTED.

## (1) FALSE-CONFIDENCE — can each gate pass GREEN while its invariant is VIOLATED?

The deepest risk. Per-gate, the concrete regression each would MISS:

### H14 (no C++ bitfield) grep — **SURVIVES (real protection).**
Mechanically decidable: `<type> <name> : <int>;` in a struct body is a closed lexical class with a small, *enumerable* false-positive surface (`?:` ternaries / `// file:982` comment refs / access-specifiers / ctor-init / `case`). 0 hits today (verified: no real bitfields), so it starts GREEN with no allowlist. Teeth-proof (inject `uint8_t x : 3;` → RED) is achievable and conclusive. **This is a genuine RED gate, not theater.** The ONLY false-confidence path is a sloppy regex that under-matches (e.g. misses multi-line decls or `unsigned:N` anonymous) — a coding-quality concern, closable by the teeth-proof + an explicit FP-surface exclusion list. Verdict: real.

### H10 (SIMD scalar-fallback byte-identical) gate — **SURVIVES, and this is the strongest leg of the whole ship.**
The C-class re-ground's SHAPE CORRECTION is CONFIRMED against code, and it sharpens necessity rather than weakening it:
- `check_fp_determinism.sh` ALREADY gates the **FP-native** axis (`±USE_NATIVE_128` ×{O3,O0}, wired pre-commit Check F via `check_determinism.sh:19`). That sub-axis is DONE — E.1.0 must NOT re-do it.
- The **H10 SIMD axis** (AVX-512 kernel == scalar `#else`) is **genuinely UNGATED**. Confirmed:
  - `RidgeBlender.hpp` has real `#if defined(__AVX512F__)` … `#else` … `#endif` blocks at :59/:493/:584/:621 — the scalar fallback EXISTS and is what H10 protects.
  - `controller_test.cpp:26763` SHA-256-locks AVX output **within-build only** and EXPLICITLY defers the cross-build compare: *"rebuild with -mno-avx512f and check actual matches this hash (future CI matrix task)."*
  - `DESIGN_SPECS/wire-format-patterns/avx512-byte-determinism-pattern.md:159` PRESCRIBES the `-mno-avx512f` vs `-mavx512f` compare — but nothing RUNS it. The pattern names the gate; E.1.0 builds it.
- **The false-confidence trap E.1.0 must avoid:** the EXISTING Bandit parity test (`controller_test.cpp:16713+`) compares AVX output to a hand-rolled `scalar_probs` LAMBDA — a *reimplemented oracle*, NOT the real `#else` branch in `BanditLearning.hpp`. That is exactly the Class-18 / `feedback_golden_master_over_reimplemented_oracle` weak form: it can pass GREEN while the actual fallback `#else` drifts. **E.1.0's Phase-C `-mno-avx512f` compile-2-ways gate is the CORRECT fix because it exercises the REAL fallback path** (the compiler selects `#else` under `-mno-avx512f`), not a parallel reimplementation. This is a textbook necessity-survival. Verdict: real protection filling a self-documented hole.
- *Caveat the A-lens must flag (the plan's own Open-Q #2):* the gate's OWN determinism — `-mno-avx512f` must actually force the `#else` for the chosen kernels AND the harness output must be run-to-run stable. If the AVX path is *always* taken on this CPU (it has `avx512f`), the scalar side is only ever reached under the `-mno` build — so the gate's value is entirely in the cross-BUILD compare, never an in-process A/B. That's fine, but it means the gate guards a path PRODUCTION never executes on an AVX-512 box. Its real consumer is a NON-AVX-512 deployment + E.1.2's NEW SoA kernels. Honest, but worth stating: on THIS machine the protected `#else` is dormant.

### H7 / H20 (hot/SP branchless dispatch) grep — **UNCERTAIN, leaning REFUTED-AS-DESIGNED (the #1 false-confidence hazard).**
This is the gate most at risk of being green-but-hollow:
- A precise data-dependent-hot-branch detector is **undecidable** (the plan concedes this). The grep is a heuristic over `if`/`switch`/`?:` in `SHARDED_FILES ∪ {ExecutionCore,GateParameters}`.
- **Allowlist sizing is LARGE, not small** (verified): `Strategies/StrategyParameters.hpp` = **118** `if/switch` lines; `ExecutionCore.hpp` = 17; `GateParameters.hpp` = 0. A heuristic that must allowlist ~130+ pre-existing hits to start GREEN is, on day one, mostly an allowlist — and an allowlist-dominated gate's real protection is ONLY "a NEW hit outside the allowlist." That CAN be a real (shrinking-only) RED gate **IF AND ONLY IF** the teeth-proof injects a NEW data-dependent branch on a *marked* dispatch path and shows RED. If the teeth-proof instead just flips an allowlisted line, the gate proves nothing.
- **The concrete regression it would MISS:** a careless rename (E.1.1) that turns an existing branchless `mask-select` into a data-dependent `if` *at a site that was already allowlisted* (or whose pre-rename form wasn't a bare `if`) sails through — the grep can't tell "this `if` is newly-branchy" from "this `if` was always here." So the gate does NOT actually catch the E.1.1 regression the OUTBOUND seam claims it catches, unless the rename happens to add a *textually new* `if` line outside the allowlist. **This is the gate whose advertised purpose (catch a careless-rename branch regression) is weakest against its mechanism.**
- Verdict: real-but-narrow. Keep it (cheap; catches the gross "added a switch on the hot path" case), but the plan MUST NOT claim it catches branchless→branchy *transformations* of existing sites — it catches NEW branch *lines* only. Demote the OUTBOUND-seam claim accordingly.

### H8 (latency ratchet) — **SURVIVES with the plan's own MEDIUM-complexity caveat.**
Substrate confirmed: `LATENCY_BENCH`/`LATENCY_PROFILING` @ `CMakeLists.txt:18-20`/:62-63; `EngineSharded_DumpLatency` emits real per-core `p99` (`Run.hpp:309`); Phase-7.B drainer histogram for slow-p99 (`Run.hpp:79/372/2433`); DumpLatency itself documents the ~25-30ns rdtsc floor to subtract. So the inputs are real. **False-confidence path:** p99 on a non-isolcpus laptop is jittery (DumpLatency's own note: "Max outliers are usually kernel preemption"). A ratchet with too-tight a margin false-FAILS (annoyance, not danger); too-loose a margin (or no median-of-N) lets a real regression hide under noise (the dangerous direction). The plan acknowledges this (margin + median-of-N) and correctly scopes it MERGE-lane not per-commit. Verdict: real IF the noise model is honest; the absolute H8 bound (≤500ns / ≤100μs) is a hard floor that's noise-immune regardless. Keep.

**FALSE-CONFIDENCE scorecard:** H14 real · H10 real (the prize) · H8 real (absolute-bound floor noise-immune) · **H7/H20 real-but-narrow — its seam claim is over-stated and must be demoted.**

## (2) NECESSITY — own ship, or fold into E.1.1?

**UNCERTAIN — the own-ship justification is REAL but rests on the WRONG successor in the plan's framing.**

- The plan + sub-master pin the load-bearing claim on **E.1.0→E.1.1** ("a names-only rename runs under the net"). But the A-lens objection lands: **a pure rename cannot change bytes or branch-structure or latency.** If E.1.1 is *genuinely* names-only (and the sub-master's seam says "byte-behavior-neutral"), then NONE of the 4 gates can fire on E.1.1's work except by a rename *typo* that adds a textual branch — which `controller_test` (3635/0) + `calls_graph_diff` would already catch. So **"guards before the rename" (D-82) is, for E.1.1 specifically, closer to a slogan than a load-bearing necessity.** The determinism net does little that the existing test suite + a per-PR `check_fp_determinism` run wouldn't.
- **BUT necessity SURVIVES on E.1.2** (the SoA relayout, which the plan even flags as "H10's first non-trivial consumer"). E.1.2 *does* change AVX-512 kernel memory layout → CAN change bytes (H10) and latency (H8). A relayout that silently breaks AVX==scalar byte-identity or regresses p99 is EXACTLY the silent-capital-determinism slip the net exists to RED-build. So the net IS load-bearing — for E.1.2, not E.1.1.
- **Could the working gates fold into E.1.1?** Mechanically yes (they're CI files; nothing stops landing them in the rename commit). The argument for a SEPARATE ship is *hygiene + bisectability*, not technical dependency: a pure-CI ship with ZERO engine delta is trivially bisectable and isolates "did the net itself break the build" from "did the rename break something." That's a real but SOFT justification (matches the plan's risk:LOW / "cleanest first cut"). It is NOT the strong dependency the D-82 framing implies.
- **What concretely breaks if E.1.1 carries its own byte-compare instead?** Almost nothing for E.1.1. The honest answer: the net's value is front-loading the H10 SIMD gate + H8 ratchet baseline *before E.1.2*, and E.1.0 is the natural place because it's the foundation leaf. Folding into E.1.1 would couple a 100-file rename diff with new CI infra in one commit — worse bisectability, no technical loss.

**Necessity verdict:** own-ship is JUSTIFIED on hygiene/bisectability + front-loading-for-E.1.2 grounds, NOT on the "rename runs under the net" framing the plan leads with. **Reshape the justification: lead with E.1.2 (the real consumer) and bisectability; demote the E.1.1 "names-only under the net" claim to a secondary, near-vacuous benefit.**

## (3) GUARD-SPRAWL — is 4 the right count?

**SURVIVES — no sprawl; arguably the count is correct, with one demotion.** Mapping to guard-matrix §1 ("highest reachable tier; max safety = right tier not max count"):
- H14 → Tier-2 grep is the HIGHEST reachable tier (can't be compile-time without a custom clang plugin; static_assert can't see syntax it rejects). Right tier. No sprawl.
- H10 → Tier-2 CI determinism gate is the highest reachable (byte-identity across two BUILDS is inherently a build-matrix CI concern, not compile-time). Right tier. EXTENDS `check_determinism.sh` (canonical-sister; verified it's the umbrella at :1-8) — NOT parallel infra. No sprawl.
- H8 → Tier-2 ratchet, MERGE-lane. Right tier (runtime perf can't be compile-time). No sprawl.
- H7/H20 → Tier-1 is the IDEAL ("hot path takes Tier-1 guards only" per §1), but H7/H20 branchlessness is NOT compile-time-representable without the undecidable-detector, so Tier-2 heuristic-grep is a DEGRADED fallback, not the right tier. **This is the one place the matrix's own rule bites:** a heuristic grep that can't be a *precise* RED gate is the lowest-value of the four. It is NOT sprawl (it's cheap, one file, shrinking allowlist), but it is the gate most vulnerable to the "low-value gate that costs maintenance forever" critique — every future legitimate hot-path `if constexpr` / binary-predicate addition needs an allowlist edit + a TECH_DEBT entry. **Recommendation: keep it, but explicitly scope its claim to "catches NEW textual branch lines on marked dispatch paths" and accept it as a Tier-2 SMOKE, not a precise invariant gate. Do not let it masquerade as Tier-1 hot-path protection.**

No gate duplicates another; none is a parallel mirror; all four sit at their highest *reachable* tier (H7/H20's reachable tier just happens to be weak). 4 is the right count.

## (4) SEAM — does E.1.0's OUTBOUND actually arm E.1.1's INBOUND?

**REFUTED AS WORDED for E.1.1; SURVIVES if re-pointed at E.1.2.** The sub-master's E.1.0→E.1.1 seam = "a STANDING green CI net the rename runs under." Traced:
- The net is STANDING (pre-commit Checks + merge-lane) — that part is real and arms automatically; no per-ship action needed. Good.
- But "the rename runs UNDER the net" as a GUARANTEE that the net CATCHES a careless-rename regression is **over-claimed** (see (1) H7/H20 + (2)): a names-only rename can only trip the net via a textual-branch typo or a literal byte/latency change — and a names-only rename produces neither by definition. The gates that WOULD catch a real regression (H10 bytes, H8 latency) only fire when bytes/latency *change*, which E.1.1 (byte-behavior-neutral) doesn't do. So for E.1.1, the seam is a near-vacuous "the net is on" — true but not the protective guarantee the wording implies.
- The seam is GENUINE for **E.1.2** (SoA relayout changes AVX bytes + latency → H10/H8 fire on a real regression). The plan even says so ("H10's first non-trivial consumer is E.1.2"). **The OUTBOUND seam should name E.1.2 as the consumer it actually arms, with E.1.1 as "runs under the standing net (no regression possible from a pure rename, so the net is a backstop not a tripwire here)."**

Seam verdict: "the rename runs under the net" is a SLOGAN for E.1.1, a real GUARANTEE for E.1.2. Re-point it.

## BOTTOM LINE

**RESHAPE-LIGHT — ship E.1.0 as its own pure-CI ship, but rebalance the framing + demote two over-claims.** It is NOT theater overall (H10 is a genuine, self-documented hole-closure; H14 is a clean RED gate; H8's absolute bound is noise-immune), and it is NOT guard-sprawl (4 gates, each at its highest reachable tier, no parallel infra). The own-ship decision is JUSTIFIED on bisectability + front-loading-for-E.1.2, not on the "rename runs under the net" story it leads with.

Three concrete reshapes before coding:
1. **Re-point necessity + the OUTBOUND seam at E.1.2** (the SoA relayout that actually changes bytes/latency), not E.1.1 (names-only → nothing for the net to catch). Demote the E.1.1 framing to "standing backstop."
2. **Demote the H7/H20 gate's claim** to "Tier-2 SMOKE catching NEW textual branch lines on marked dispatch paths" — it canNOT catch branchless→branchy *transformations* of existing/allowlisted sites (undecidable), so it does not deliver the careless-rename protection the seam advertises. Teeth-proof MUST inject a NEW branch outside the allowlist, not flip an allowlisted line. ~130+ pre-existing hits (118 in StrategyParameters alone) → the allowlist dominates day-one; size it from the I-class enumeration.
3. **Fix the H10 gate to exercise the REAL `#else`** (compile-2-ways `-mno-avx512f`), NOT a reimplemented scalar oracle like the existing Bandit lambda (Class-18 weak form). Flag the gate's own-determinism (Open-Q #2) + that on an AVX-512 box the protected `#else` is dormant (real consumer = non-AVX deploy + E.1.2's new kernels).
