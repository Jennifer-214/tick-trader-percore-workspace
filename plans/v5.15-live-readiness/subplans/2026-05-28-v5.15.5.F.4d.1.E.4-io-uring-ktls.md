## TL;DR

Replace BinanceAdapter worker thread's userspace-syscall-driven I/O with **per-node io_uring** (async kernel-side I/O) + **kTLS** (kernel-side TLS encryption). Each per-node owns its own io_uring submission + completion rings. Eliminates the last shared trading-flow thread per cluster (adapter worker DELETED).

**Latency improvement:** saves ~10-20μs per I/O operation on the critical path (kernel context switch elimination; userspace TLS encryption elimination).

**Five major changes:**

1. **Per-node io_uring rings.** Each node has its own submission ring (SQ) + completion ring (CQ); kernel processes submits asynchronously; node polls completions at slow-path cycle entry.

2. **kTLS for TLS encryption.** TLS 1.3 + AES-GCM session keys offloaded to kernel; userspace produces plaintext + kernel encrypts. Skips SSL_write userspace path entirely.

3. **BinanceAdapter worker thread DELETED.** Per-node owns its own submit path now; no shared worker thread per cluster (adapter shared resources collapse to just the WS connection state + protocol layer).

4. **WS connection per-node integration.** Each per-node owns own WS connection to /ws-api/v3 (radical change from .E.3's per-cluster shared connection; trades connection count for per-node isolation).

5. **NUMA-aware ring placement.** Per-node io_uring rings live on the same NUMA node as the per-node hot+slow CPU cores.

**Hot path latency:**
- Pre-`.E.4`: submit kernel context switch (~10μs) + userspace TLS encrypt (~10μs) + kernel TCP send (~5μs)
- Post-`.E.4`: io_uring submit (~1μs queue) + kTLS encrypt (~3μs kernel) + kernel TCP send (~5μs)
- Net: ~15μs saved per submit (in addition to .E.3's ~15-25ms WS handshake elimination)

## Architecture deep-dive

### Why io_uring + kTLS is the right next step

After `.E.3` lands persistent WS-API connections, each cluster has its WS connection going through kernel TCP/TLS stack:
```
Engine slow-path emits SubmitCommand
  ↓
Per-cluster adapter thread builds WS frame
  ↓
SSL_write(ssl_state, frame, len)         ← userspace TLS encrypt (~10μs CPU)
  ↓ (calls send() syscall internally)
sendmsg() syscall                         ← kernel context switch (~5μs)
  ↓
Kernel TCP stack processes               ← kernel TCP (~5μs)
  ↓
NIC TX queue → wire
  ↓
Total userspace+kernel CPU time: ~20-25μs per submit
```

After `.E.4`:
```
Engine slow-path emits SubmitCommand
  ↓
Per-node slow-path builds WS frame (plaintext)
  ↓
io_uring_prep_send (queue SQE)            ← ~200ns userspace queue write
  ↓
io_uring_submit() syscall                 ← BATCHED; amortized to ~1μs per submit
  ↓
Kernel kTLS encrypts                      ← ~3μs (kernel; AES-NI accelerated)
  ↓
Kernel TCP stack processes                ← ~5μs (unchanged)
  ↓
NIC TX queue → wire
  ↓
Total userspace+kernel CPU time: ~10μs per submit (~10-15μs saved vs .E.3)
```

**Per-node io_uring vs per-cluster:** per-node placement gives NUMA-awareness + per-node failure isolation (one node's ring overflow doesn't affect siblings). Per-cluster was viable but loses per-node optimization opportunities.

### io_uring fundamentals (for context)

io_uring is Linux's async I/O facility (kernel 5.1+; mature 5.6+). Key abstractions:

- **Submission Queue (SQ):** userspace writes Submission Queue Entries (SQEs); kernel reads
- **Completion Queue (CQ):** kernel writes Completion Queue Entries (CQEs); userspace reads
- **mmap'd shared memory:** SQ + CQ rings are mmap'd between userspace + kernel; no copies
- **Batched syscalls:** io_uring_submit() submits N SQEs in one syscall; reduces context switches
- **Async completions:** kernel processes SQEs in background; userspace polls or sleeps on CQ

For our submit path:
```cpp
// 1. Get SQE from ring
struct io_uring_sqe* sqe = io_uring_get_sqe(&ring);

// 2. Prepare send op
io_uring_prep_send(sqe, socket_fd, buf, len, MSG_NOSIGNAL);

// 3. Tag with user_data (for completion correlation)
io_uring_sqe_set_data(sqe, (void*)request_id);

// 4. Submit (batched; can call multiple times before submit)
io_uring_submit(&ring);

// 5. At slow-path entry: poll completions
struct io_uring_cqe* cqe;
while (io_uring_peek_cqe(&ring, &cqe) == 0) {
    uint64_t req_id = (uint64_t)io_uring_cqe_get_data(cqe);
    int32_t bytes_sent = cqe->res;
    // ... handle completion
    io_uring_cqe_seen(&ring, cqe);
}
```

### Per-node io_uring rings

```cpp
// CoreFrameworks/NodeIORings.hpp (NEW)

struct alignas(64) NodeIORings {
    // === io_uring instance per node ===
    struct io_uring ring;                     // liburing handle
    unsigned ring_depth;                      // typically 256-1024

    // === Submission queue helpers ===
    alignas(64) struct {
        uint64_t next_user_data;              // monotonic; for completion correlation
        SPSCRing<PendingIO, 256> pending;     // tracks in-flight ops by user_data
    } sq;

    // === Completion queue polling ===
    alignas(64) struct {
        std::atomic<uint64_t> completions_processed;
        std::atomic<uint64_t> completions_pending;
    } cq;

    // === Connection state (per-node WS to /ws-api/v3) ===
    PersistentWSConnection_Inlined ws_conn;   // moves here from cluster.adapter

    // === NUMA-awareness ===
    int numa_node;                            // pinned for ring allocation
};

// Submit via io_uring (replaces SSL_write + send syscall)
int IOUring_SubmitWSFrame(NodeIORings* rings, const char* frame, size_t frame_len) {
    struct io_uring_sqe* sqe = io_uring_get_sqe(&rings->ring);
    if (!sqe) {
        // SQ full; back-pressure
        return -EAGAIN;
    }

    uint64_t user_data = rings->sq.next_user_data++;
    PendingIO pending = {user_data, PENDING_KIND_SUBMIT, frame_len, NowUs()};
    SPSCRing_Push(&rings->sq.pending, pending);

    io_uring_prep_send(sqe, rings->ws_conn.socket_fd, frame, frame_len, 0);
    io_uring_sqe_set_data(sqe, (void*)user_data);

    io_uring_submit(&rings->ring);  // syscall; but batched (multiple SQEs per syscall)

    return 0;
}

// Poll completions at slow-path entry
void IOUring_PollCompletions(NodeState<F>& node, NodeIORings* rings) {
    struct io_uring_cqe* cqe;
    while (io_uring_peek_cqe(&rings->ring, &cqe) == 0) {
        uint64_t user_data = (uint64_t)io_uring_cqe_get_data(cqe);
        int32_t result = cqe->res;

        // Find pending op (via SPSCRing_Pop or by-id lookup)
        PendingIO pending;
        if (SPSCRing_PopBy(&rings->sq.pending, user_data, &pending)) {
            // Dispatch completion handler
            switch (pending.kind) {
                case PENDING_KIND_SUBMIT:
                    HandleSubmitCompletion(node, pending, result);
                    break;
                case PENDING_KIND_RECV:
                    HandleRecvCompletion(node, pending, result);
                    break;
            }
        }

        io_uring_cqe_seen(&rings->ring, cqe);
        rings->cq.completions_processed.fetch_add(1, std::memory_order_relaxed);
    }
}
```

### Completion polling vs sleep

Two strategies for harvesting completions:

**Strategy 1: Polling at slow-path entry (CHOSEN per Decision D)**
```cpp
void NodeSlowPath_Cycle(NodeState<F>& node) {
    IOUring_PollCompletions(&node.io_rings);   // ~1-5μs to drain ring
    // ... rest of slow-path
}
```

Pros: lowest latency for response handling; no extra thread; minimal context switching.
Cons: if no submits in flight, polling is wasted CPU (but very cheap; ~100ns).

**Strategy 2: Dedicated poller thread**
```cpp
// Separate thread calls io_uring_wait_cqe (blocking)
void IOUringPoller_Thread(NodeState<F>* node) {
    while (running) {
        io_uring_wait_cqe(&node->io_rings.ring, &cqe);  // blocks
        // ... handle completion
        io_uring_cqe_seen(...);
    }
}
```

Pros: blocking sleep; zero idle CPU.
Cons: extra thread per node (doubles thread count); thread wake-up latency (~5-10μs).

**Decision: Strategy 1 (polling).** Our slow-path cadence (5-50μs) is fine for polling cadence. Avoids thread proliferation; lower latency.

### Submit queue sizing + overflow handling

SQ depth = 256 entries (per Decision C). At 20 submits/sec max, 256 entries is ~12 seconds of pending submits. Realistically, SQ fills only during bursts:

- Normal flow: 0-2 entries in SQ; submitted immediately
- Burst (e.g., kill-switch close-all): N nodes × 1 submit each = N entries; submitted in single io_uring_submit batch
- Overflow scenario: producer faster than kernel can drain (very rare at 20/sec)

**Overflow handling:**
```cpp
int IOUring_SubmitWSFrame(NodeIORings* rings, const char* frame, size_t frame_len) {
    struct io_uring_sqe* sqe = io_uring_get_sqe(&rings->ring);
    if (!sqe) {
        // SQ full; back-pressure
        rings->cq.completions_pending.load(std::memory_order_acquire);
        if (...) {
            // Drain completions first to free SQ slots
            IOUring_PollCompletions(...);
            sqe = io_uring_get_sqe(&rings->ring);
            if (!sqe) return -EAGAIN;
        } else {
            return -EAGAIN;
        }
    }
    // ... normal submit path
}
```

If `-EAGAIN`: caller (slow-path) puts submit back into per-node retry SPSC + tries again next cycle.

### kTLS for kernel-side TLS

```cpp
// Setup kTLS on connected SSL socket (after TLS handshake)
int KTLS_Enable(int socket_fd, SSL* ssl_state) {
    // Get TLS cipher info from completed handshake
    const SSL_CIPHER* cipher = SSL_get_current_cipher(ssl_state);
    int cipher_nid = SSL_CIPHER_get_cipher_nid(cipher);

    // Verify supported cipher (TLS 1.3 + AES-GCM)
    if (cipher_nid != NID_aes_128_gcm && cipher_nid != NID_aes_256_gcm) {
        return -1;  // kTLS not supported for this cipher
    }

    // Extract session keys from OpenSSL
    unsigned char read_key[64], write_key[64];
    SSL_get_session_secret_for_kTLS(ssl_state, read_key, write_key);

    // Set TLS_RX (kernel decrypts incoming)
    struct tls12_crypto_info_aes_gcm_128 crypto_info_rx;
    PopulateCryptoInfo(&crypto_info_rx, read_key);
    setsockopt(socket_fd, SOL_TLS, TLS_RX, &crypto_info_rx, sizeof(crypto_info_rx));

    // Set TLS_TX (kernel encrypts outgoing)
    struct tls12_crypto_info_aes_gcm_128 crypto_info_tx;
    PopulateCryptoInfo(&crypto_info_tx, write_key);
    setsockopt(socket_fd, SOL_TLS, TLS_TX, &crypto_info_tx, sizeof(crypto_info_tx));

    // After kTLS enabled, send() on socket plaintext → kernel encrypts → wire
    // recv() on socket receives plaintext (kernel decrypts)
    return 0;
}
```

### kTLS handshake → encrypted-by-kernel flow

kTLS (RFC 8446 + Linux kernel kTLS implementation) works as follows:

1. **Userspace OpenSSL handshake:** Engine does normal TLS 1.3 handshake via OpenSSL on socket FD
2. **Extract session keys post-handshake:** Engine reads client_write_key + client_iv + server_read_key from OpenSSL state
3. **setsockopt(TLS_TX) + setsockopt(TLS_RX):** Engine passes keys to kernel
4. **From now on:** send() on socket = plaintext in; kernel encrypts; ciphertext on wire. recv() on socket = ciphertext on wire; kernel decrypts; plaintext out.

Kernel kTLS supports TLS 1.2 + TLS 1.3 with specific ciphers:
- TLS_AES_128_GCM_SHA256 ✅
- TLS_AES_256_GCM_SHA384 ✅
- TLS_CHACHA20_POLY1305_SHA256 ✅ (most modern kernels 5.10+)
- Other ciphers: NOT supported by kTLS; fallback to userspace TLS

Binance servers support TLS 1.3 + AES-GCM (verified via OpenSSL connect tests). Compatibility: HIGH.

**Code flow:**

```cpp
int KTLS_Enable(int socket_fd, SSL* ssl_state) {
    // Verify TLS 1.3
    if (SSL_version(ssl_state) != TLS1_3_VERSION) {
        LOG_WARN("Not TLS 1.3; kTLS skip");
        return -1;
    }

    // Verify supported cipher
    const SSL_CIPHER* cipher = SSL_get_current_cipher(ssl_state);
    int cipher_nid = SSL_CIPHER_get_cipher_nid(cipher);

    switch (cipher_nid) {
        case NID_aes_128_gcm:
        case NID_aes_256_gcm:
        case NID_chacha20_poly1305:
            break;  // supported
        default:
            LOG_WARN("Cipher %s not kTLS-supported; falling back to userspace", SSL_CIPHER_get_name(cipher));
            return -1;
    }

    // Enable TLS upper-layer (kernel-side decryption + encryption)
    int tls_version = TLS_1_3_VERSION;
    setsockopt(socket_fd, SOL_TCP, TCP_ULP, "tls", 4);

    // Set TX keys (encryption: plaintext → ciphertext)
    struct tls12_crypto_info_aes_gcm_128 crypto_info_tx;
    crypto_info_tx.info.version = TLS_1_3_VERSION;
    crypto_info_tx.info.cipher_type = TLS_CIPHER_AES_GCM_128;
    PopulateCryptoInfoFromSSL(&crypto_info_tx, ssl_state, /*is_tx=*/1);
    setsockopt(socket_fd, SOL_TLS, TLS_TX, &crypto_info_tx, sizeof(crypto_info_tx));

    // Set RX keys (decryption: ciphertext → plaintext)
    struct tls12_crypto_info_aes_gcm_128 crypto_info_rx;
    crypto_info_rx.info.version = TLS_1_3_VERSION;
    crypto_info_rx.info.cipher_type = TLS_CIPHER_AES_GCM_128;
    PopulateCryptoInfoFromSSL(&crypto_info_rx, ssl_state, /*is_tx=*/0);
    setsockopt(socket_fd, SOL_TLS, TLS_RX, &crypto_info_rx, sizeof(crypto_info_rx));

    // From now on: io_uring_send/recv on socket = plaintext; kernel encrypts/decrypts
    return 0;
}
```

**Performance benefit:** Userspace TLS encrypt = ~10μs CPU per TLS record (~16KB max). Kernel kTLS encrypt = ~3μs (kernel AES-NI). Per submit (~512B WS frame in TLS record): saves ~5-7μs.

### Per-cluster vs per-node WS connection migration

In `.E.3`, each cluster had 1 shared WS connection. In `.E.4`, each per-node owns its own WS connection:

**Before (.E.3):** 4 nodes per cluster → 1 WS connection per cluster → all 4 nodes' submits go through same connection.

**After (.E.4):** 4 nodes per cluster → 4 WS connections per cluster → each node has dedicated connection.

**Tradeoffs:**

| Axis | Per-cluster (.E.3) | Per-node (.E.4) |
|---|---|---|
| Connection count | 1 per cluster | N per cluster |
| TLS handshake cost | 1 at boot | N at boot (parallel) |
| Connection memory | ~80KB | N × ~80KB |
| Per-submit latency | shared queue (potential contention) | dedicated queue (zero contention) |
| Per-node fate | Cluster SPOF | Per-node fate |
| Migration complexity | (existing .E.3) | Requires per-node move |

**Migration:** at `.E.4`, the cluster's adapter struct fields move into per-node IORings struct. Boot establishes N parallel TLS handshakes per cluster (each node gets its own).

```cpp
// Engine boot at .E.4
void EngineInit_PerNodeConnections(EngineState<F>& state) {
    // For each cluster: spawn N parallel handshake threads
    for (uint32_t c = 0; c < state.cluster_count; ++c) {
        ClusterState<...>& cluster = state.clusters[c];

        // Parallel handshake (per-node thread)
        std::array<pthread_t, MAX_NODES> handshake_threads;
        for (uint32_t n = 0; n < cluster.node_count; ++n) {
            HandshakeArgs* args = &cluster.nodes[n]->handshake_args;
            args->ws_endpoint = cluster.adapter.ws_api_endpoint;
            args->api_key = cluster.subaccounts[cluster.nodes[n]->binding.subaccount_id].api_key;
            args->api_secret = ...;

            pthread_create(&handshake_threads[n], nullptr,
                           PerNodeHandshake_Thread, args);
        }

        // Wait for all handshakes (parallel; ~50ms wall time)
        for (uint32_t n = 0; n < cluster.node_count; ++n) {
            pthread_join(handshake_threads[n], nullptr);
        }

        // All nodes have established connections + cached TLS sessions
    }
}
```

### NUMA-aware ring placement

```cpp
// Boot-time: pin io_uring memory to local NUMA node
int IOUring_Init_NUMA(NodeIORings* rings, int numa_node) {
    // Set NUMA policy before io_uring_queue_init
    unsigned long nodemask = 1UL << numa_node;
    if (set_mempolicy(MPOL_BIND, &nodemask, sizeof(nodemask) * 8) != 0) {
        return -1;
    }

    // io_uring SQ + CQ memory allocated on this NUMA
    if (io_uring_queue_init(rings->ring_depth, &rings->ring, 0) != 0) {
        return -1;
    }

    // Reset policy
    set_mempolicy(MPOL_DEFAULT, nullptr, 0);

    rings->numa_node = numa_node;
    return 0;
}
```

## Design space + future-oriented choices

### Decision A: io_uring per-node vs per-cluster
**(a) per-node CHOSEN** — eliminates shared state; per-node isolation; NUMA-aware
(b) per-cluster — keeps shared worker thread shape; doesn't eliminate Class 26 surface fully

### Decision B: kTLS vs userspace TLS
**(a) kTLS CHOSEN** — kernel-side encryption; lower latency; modern Linux supports
(b) userspace TLS — fallback if kTLS cipher unavailable; cfg-driven fallback

### Decision C: SQ depth per node
**(a) 256 CHOSEN** — sufficient for ~20/sec submit rate with headroom for in-flight + recv
(b) 1024 — overkill; memory overhead
(c) 64 — tight; risk SQ-full back-pressure

### Decision D: Completion polling cadence
**(a) Slow-path entry CHOSEN** — polls at each per-node slow-path cycle (~5-50μs cadence); sufficient
(b) Dedicated poller thread — extra thread; not needed
(c) Hot path — too frequent; not for I/O

## Honest risks (with worked examples)

### R1 — io_uring kernel version + feature gating

**Risk:** io_uring features evolved across kernel versions; some operations only available on newer kernels (multishot recv at 5.13+; rings at 5.6+; etc.). Engine must select feature subset compatible with operator's kernel.

**Worked example:** Operator deploys on AWS instance with Linux 5.4 (Ubuntu 20.04 LTS default). Engine boot fails because io_uring_queue_init not supported pre-5.6. Operator must upgrade kernel OR use NETWORKING_KERNEL fallback (no DPDK/.E.8 either; pre-io_uring + userspace TLS).

**Mitigation:**
- Boot-time `uname -r` parse; refuse if <5.6
- Clear error message: "io_uring requires kernel 5.6+; detected X.Y; upgrade or disable via cfg networking.use_io_uring=false"
- cfg fallback to legacy syscall path (slower but works on any Linux)
- DEPLOYMENT_GUIDE.md documents kernel requirements

**Severity:** MED (operational; expected; mitigated by clear errors + fallback)

### R2 — kTLS cipher constraints

**Risk:** Linux kTLS supports specific ciphers (AES_GCM, CHACHA20_POLY1305). If Binance changes server config to require unsupported cipher (rare but possible), kTLS breaks.

**Worked example:** Binance updates TLS server to require TLS 1.4 (hypothetical; doesn't exist yet) or new cipher suite. Engine's kTLS handshake fails because kernel doesn't recognize cipher; SSL_connect proceeds with userspace TLS automatically. Performance degrades ~7μs per submit; observable but not catastrophic.

**Mitigation:**
- Cipher verification at boot (refuse kTLS if cipher unsupported)
- Userspace TLS fallback (automatic; no operator action)
- Per-cluster metric: `fox_tls_userspace_fallback_rate` (target: 0%)
- Alert if fallback rate non-zero

**Severity:** LOW-MED (graceful degradation; observability)

### R3 — N TLS handshakes at boot per cluster

**Risk:** With N=4-16 nodes per cluster, boot now does N parallel TLS handshakes (instead of 1 at `.E.3`). Increases boot time.

**Worked example:** 4-node cluster, each TLS handshake ~20-50ms. Parallel boot via N threads → ~50ms total (bounded by slowest). vs serial: ~80-200ms. Parallel is acceptable.

At N=16: parallel ~50ms (saturated); serial would be ~320-800ms. Parallel critical for sub-second boot.

**Mitigation:**
- Parallel TLS handshake per cluster (N threads; pthread-managed)
- Connection-pool pre-warming option (if operator wants instant ready: pre-handshake at engine start, before reconcile)
- TLS session ticket caching across reconnects (subsequent handshakes ~5ms via resumption)

**Severity:** LOW (handled by parallelism)

### R4 — io_uring completion handler safety

**Risk:** Completion handlers run in per-node slow-path thread context. If handler accidentally accesses cross-node state without proper synchronization, race conditions occur.

**Worked example:** Completion handler for node_0's submit response triggers Aggregator_OnFill, which writes to aggregator state. Aggregator state is atomic per D-54. But suppose handler also wants to update node_1's state for some reason — that would be a cross-node access; needs synchronization.

**Mitigation:**
- Completion handler discipline: ONLY modifies own per-node state + atomic writes to aggregator
- No cross-node access in handler
- Single-writer principle enforced by code review + audit-gate
- Aggregator_OnFill uses atomic ops (D-54 design)

**Severity:** MED (design discipline; verified by audit)

### R5 — Liburing dependency

**Risk:** NEW external dependency (liburing). License compatibility; version pinning; build reliability.

**Mitigation:**
- Liburing LGPL-licensed → AGPL-compatible (LGPL allows linking; we link statically)
- Pinned version in build.sh (e.g., liburing 2.5)
- AUR package available; system-wide install supported
- Fallback: if liburing missing, engine refuses to start with clear error

**Severity:** LOW (well-managed dependency)

### R6 — Per-node connection × N memory + handshake amplification

**Risk:** Per-node WS connection = N × cluster's previous resource cost.

**Worked example:** At `.E.3`, cluster had 1 WS connection (~80KB TLS state + 64KB recv buffer + 64KB send buffer ≈ 200KB). At `.E.4`, each node has own connection → N × 200KB. At N=16 in 2 clusters: 32 × 200KB = 6.4MB total. Modest.

Handshake: parallel; bounded by slowest. ~50ms boot.

**Mitigation:**
- Bounded by per-node memory budget (cfg-driven; default 256KB)
- Parallel handshake minimizes boot impact
- Operator scaling docs in DEPLOYMENT_GUIDE.md

**Severity:** LOW

### R7 — Kernel TLS RX path correctness

**Risk:** kTLS RX (kernel decrypts incoming) requires careful handling of partial records, sequence numbers, and re-key events. Bug in kernel kTLS RX has been observed historically (rare; usually fixed by kernel updates).

**Worked example:** TLS 1.3 session re-key happens after large data transfer; kernel must handle key rotation. If kernel kTLS RX bug exists, response data corrupts.

**Mitigation:**
- Use stable kernel version (6.0+ has substantial kTLS hardening)
- Byte-integrity verification in receive path (response JSON must parse cleanly)
- Fallback to userspace TLS if kernel kTLS errors detected
- Operator alert on TLS error rate above threshold

**Severity:** LOW-MED (kernel bug class; rare)

### R8 — Per-node thread count amplification

**Risk:** Per-node WS connection might need per-node WS keepalive thread. At N=16 nodes per cluster × 2 clusters = 32 additional keepalive threads (vs 2 at `.E.3`).

**Worked example:** 16-node cluster gains 16 keepalive threads. Each keepalive thread is mostly sleeping (30s ping interval); wakes briefly. CPU impact: negligible. Memory impact: each pthread ~8KB stack × 16 = 128KB. Acceptable.

**Mitigation:**
- Consolidate keepalive into per-cluster manager thread (1 thread per cluster; pings all node connections)
- vs per-node keepalive thread: design choice
- At `.E.4`: per-cluster manager preferred (1 thread per cluster polls all N connections; lower thread count)

**Severity:** LOW

### R9 — TLS session resumption + sub-account credential rotation

**Risk:** TLS session ticket is tied to (API key, server) pair. If operator rotates sub-account API key, cached ticket becomes invalid.

**Worked example:** Operator rotates sub_2 API key. Engine continues using cached ticket from old key; Binance rejects. Reconnect with new credentials does fresh handshake; new ticket cached.

**Mitigation:**
- Cached_session invalidated on credential change
- cfg reload via SIGUSR1 forces credential re-load + connection re-establishment
- Operator workflow: rotate key → SIGUSR1 → engine reconnects with new key

**Severity:** LOW (clear operator workflow)
