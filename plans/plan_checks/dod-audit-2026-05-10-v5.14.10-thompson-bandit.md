## Findings (severity-ordered)

### HIGH-1 — FOREACH_BANDIT_ALGORITHM registry retrofit candidate (curve-registry-pattern)

- **Surface:** Plan Step 3 (`Strategies/StrategyParameters.hpp` switch on `config->bandit_algorithm` at the planned dispatch insertion point near current `:880-1014`)
- **Pattern:** `DESIGN_SPECS/framework-patterns/curve-registry-pattern.md` "## The pattern (concrete shape)" + "## Trade-offs + when to apply"
- **Symptom:** Plan's Step 3 introduces a 3-case `switch (config->bandit_algorithm)` with `case 0/1/2` dispatching to:
  - case 0 (Exp3): `Bandit_GetProbabilities(&ezoo->bandits[regime_id], weights_buf)`
  - case 1 (Thompson): `Thompson_Sample(...)` + one-hot weight construction
  - case 2 (Both): both calls + telemetry
  This is exactly the **Option A naïve baseline** that `curve-registry-pattern.md` rejects. Decision criteria from the doc:
  - "Apply when ≥3 named compute modes exist" → 3 modes (Exp3, Thompson, Both). **Threshold met**.
  - "Skip when ≤2 modes (one if-else more readable)" → 3 ≥ 2; SKIP rule does not apply.
  - "Mode count is small + closed (≤2 modes)" → 3, BORDERLINE.
- **Trade-off (the "non-uniform contract" objection):** dispatch contract differs per algorithm:
  - Exp3 writes `weights_buf[N]` (probability distribution)
  - Thompson writes one-hot at `chosen_arm` index + caller derives weights
  - Both writes both AND emits telemetry
  This is exactly what `curve-registry-pattern.md` "## Lessons / gotchas — Don't bloat the dispatch contract" warns about. **However** — the contract CAN be unified to a single 4-arg signature without bloat:
  ```cpp
  // Uniform: every algo writes weights_buf[] (Thompson writes one-hot internally)
  // and *chosen_arm_out (Exp3 writes -1 sentinel meaning "no scalar choice").
  typedef void (*BanditAlgoFn)(EnsembleModelZoo<F>* ezoo,
                               int regime_id,
                               int n_arms,
                               double* weights_buf,
                               int* chosen_arm_out);
  ```
  Per-algorithm wrappers handle the internal differences:
  - `BanditAlgo_Exp3_Apply` calls Bandit_GetProbabilities; sets `*chosen_arm_out = -1`
  - `BanditAlgo_Thompson_Apply` calls Thompson_Sample; sets one-hot weights AND `*chosen_arm_out`
  - `BanditAlgo_Both_Apply` calls Exp3 first (fills weights), then Thompson (fills chosen_arm), telemetry hook reads both
- **Suggested fix:** Add `ML_Headers/BanditAlgorithmRegistry.hpp` (NEW file) with FOREACH_BANDIT_ALGORITHM:
  ```cpp
  #define FOREACH_BANDIT_ALGORITHM(X)                                                                  \
      X(EXP3,     0, BanditAlgo_Exp3_Apply,     "Exp3-IX exponential weights (default; deterministic)") \
      X(THOMPSON, 1, BanditAlgo_Thompson_Apply, "Bayesian Thompson sampling (Gaussian conjugate posterior)") \
      X(BOTH,     2, BanditAlgo_Both_Apply,     "run both; Exp3 chooses; Thompson logged for A/B")
  ```
  Auto-generates `BANDIT_ALGO_EXP3 / _THOMPSON / _BOTH` enum, `bandit_algorithm_fns[]` dispatch table, ToString/FromString helpers, COUNT bound. Step 3 dispatch becomes:
  ```cpp
  // Bounds-checked one-line dispatch — operator-tunable via cfg
  bandit_algorithm_fns[config->bandit_algorithm](ezoo, regime_id, ezoo->primary_count,
                                                  weights_buf, &chosen_arm);
  ```
- **Reasoning per CLAUDE.md item 19 + `feedback_overengineering_boundary_when_future_easier`:** 3 is borderline; future modes (UCB1, EXP4, Bayesian linear, Discounted Thompson, Sliding-Window UCB) are forecasted in the operator's own roadmap (FoxML/ML_Core has Bayesian-policy variants beyond Gaussian). Add 4th mode in 6 months under naïve switch = touches dispatch + cfg parser + GUI dropdown + tests + ToString helper. Add 4th mode under registry = 1 row + 1 free fn + 0 dispatch sites + 0 parser sites + auto-flow GUI + auto-flow tests. Future-work reduction multiplier ~5-8×; pattern overhead ~80 LOC one-time. **Strong recommend retrofit at .A sub-tag.**
- **Effort estimate:** +2-3h on top of the planned ~250 LOC Thompson math (registry header ~80 LOC + 3 wrapper fns ~20 LOC each + tests for dispatch table ~50 LOC). Aligns with the "v5.14.9.A FOREACH_DEGRADATION_CURVE" template — copy-pattern not invent-pattern.
- **Stamp-binding consideration:** if `bandit_algorithm` should be train/serve drift-detected (probably YES — switching algorithms invalidates the warmup), add to `FOREACH_STAMP_BOUND_CFG` per `curve-registry-pattern.md` "## Lessons / gotchas — Stamp binding for the curve choice". Independent decision; either way the registry helps.
- **Cross-references:**
  - First applied: `ML_Headers/ConfidenceScore.hpp:498-634` (FOREACH_DEGRADATION_CURVE — 4 curves; same shape)
  - Plan reference: `Strategies/StrategyParameters.hpp` :880 → :1014 (current Exp3+Ridge dispatch)
  - DESIGN_SPECS: `curve-registry-pattern.md` §"The pattern" + §"Reference implementations" + §"Adjacent patterns / future application candidates" (the doc EXPLICITLY lists "fee schedules", "decay schedules" as future application candidates — bandit algorithms fit the same shape).

### MEDIUM-1 — `bandit_algorithm` belongs in slow-path-gate cache (slow-path-gate-registry-pattern)

- **Surface:** Plan Step 3 dispatch reads `config->bandit_algorithm` per slow-path cycle per core
- **Pattern:** `DESIGN_SPECS/framework-patterns/slow-path-gate-registry-pattern.md` + CLAUDE.md item 18(c)/(d)
- **Symptom:** Plan's dispatch reads `config->bandit_algorithm` inline at the dispatch site — same pattern that `slow-path-gate-registry-pattern.md` extinguished for the other 7 cfg-toggleable gates (LADDER_ACTIVE, CONFIDENCE_ENABLED, COMPOSITE_ENABLED, RIDGE_WITHIN_ACTIVE, EXIT_BLENDER_ACTIVE, LAZY_REBUILD_ACTIVE, WS_FLATTEN_ACTIVE). Per item 18(d): "avoid sprinkling cfg-flag checks through deep functions; hoist to slow-path top + pass a small struct of resolved predicates."
- **Caveat (cfg-flag-eligibility-criteria.md):** `bandit_algorithm` is INT enum (3 values), NOT boolean. Per `cfg-flag-eligibility-criteria.md` 5-criteria: it FAILS the implicit "boolean" precondition for `FOREACH_<DOMAIN>_CFG_FLAG` migration (which packs into a uint8/16 bitmap). So `bandit_algorithm` does NOT belong in `FOREACH_ML_CFG_FLAG` directly.
- **HOWEVER** — `slow-path-gate-registry-pattern.md` is about CACHED PREDICATES, not bitmap packing. Two predicates derived from `bandit_algorithm` could fit:
  - `THOMPSON_ACTIVE` = `(cfg.bandit_algorithm == BANDIT_ALGO_THOMPSON || cfg.bandit_algorithm == BANDIT_ALGO_BOTH)` → 1 bit
  - `EXP3_ACTIVE`     = `(cfg.bandit_algorithm == BANDIT_ALGO_EXP3 || cfg.bandit_algorithm == BANDIT_ALGO_BOTH)` → 1 bit
  These are predicates fitting `FOREACH_SLOW_PATH_GATE` `PER_CORE` scope. Use sites then read via `BITMAP_IS_SET(gate_state->flags, MASK_THOMPSON_ACTIVE)` — same cache-friendly read as RIDGE_WITHIN_ACTIVE.
- **Suggested fix (alongside HIGH-1 fix):** Add 1-2 entries to `FOREACH_SLOW_PATH_GATE` in `CoreFrameworks/SlowPathGateRegistry.hpp`:
  ```cpp
  /* v5.14.10 — Thompson sampling alternative to Exp3 */                                              \
  X(PER_CORE,    THOMPSON_ACTIVE,                                                                      \
    ((_gate_cfg).bandit_algorithm == BANDIT_ALGO_THOMPSON) || ((_gate_cfg).bandit_algorithm == BANDIT_ALGO_BOTH), \
    "Thompson sampling enabled (algorithm=1 or =2)")                                                  \
  X(PER_CORE,    BANDIT_BOTH_ACTIVE,                                                                   \
    (_gate_cfg).bandit_algorithm == BANDIT_ALGO_BOTH,                                                  \
    "dual-mode A/B telemetry (algorithm=2)")
  ```
  Use sites in StrategyParameters.hpp pick the cached predicate; current SlowPathGateState `uint16_t flags` has 9 bits headroom → fits. (NOTE: GATE_COUNT < 16 must remain — confirmed via static_assert at SlowPathGateRegistry.hpp:152.)
- **Reasoning:** `bandit_algorithm` is read per slow-path cycle inside ML_BuildParameters body. Without caching, future audits via `/dod-audit` Check 27 would re-flag this as "missed slow-path-gate-registry application". Same shape as how RIDGE_WITHIN_ACTIVE was migrated in v5.14.9.B.0 from `if (config->ridge_within_horizon)` → `BITMAP_IS_SET(gate_state->flags, MASK_RIDGE_WITHIN_ACTIVE)`.
- **Effort estimate:** ~30min (2 registry rows; refactor 2-3 use sites; 2-3 test assertions). Tiny vs HIGH-1 effort.
- **Bonus win:** consolidates "is Thompson active" predicate at AUTOPOPULATE time — telemetry hook (`gate_state->flags & MASK_THOMPSON_ACTIVE`) becomes branchless query for "should we log Thompson choice?".
- **Cross-references:**
  - Pattern doc: `slow-path-gate-registry-pattern.md` §"Apply when:" first bullet
  - Existing precedent: SlowPathGateRegistry.hpp:69-99 (7 gates currently registered; pattern is field-tested)
  - CLAUDE.md item 18(d) — hoist cfg-flag checks to slow-path top

### MEDIUM-2 — Wire-format byte-preservation discipline for `thompson_state.json` (wire-format-byte-preservation-discipline)

- **Surface:** Plan Step 4 (NEW persistence file `<base_dir>/thompson_state.json`)
- **Pattern:** `DESIGN_SPECS/wire-format-patterns/wire-format-byte-preservation-discipline.md` Layer 2 (locale pinning at emit construction) + general format-version discipline
- **Symptom:** Plan Step 4 creates a NEW persistence file. Although there's no LEGACY HMAC chain to preserve (file doesn't exist pre-v5.14.10), the plan should not REPEAT Bandit_SaveJSON's gap. Audited Bandit_SaveJSON at `BanditLearning.hpp:369-435`:
  - Uses `fprintf(f, "%.17g", ...)` for doubles (correct precision)
  - Has `BANDIT_STATE_FORMAT_VERSION` field (correct version discipline)
  - Has `model_bundle_sha256` for binding (correct lineage)
  - **Does NOT call `uselocale(newlocale(LC_NUMERIC_MASK, "C", 0))`** — relies on global "C" locale being default.
- **Why this matters for Thompson:** ThompsonBanditState includes `rng_state` (uint64_t — written as `%lu` or `%016lx`; locale-immune integer) BUT also `mu_post[]`, `precision_post[]`, `mu_prior`, `precision_prior`, `precision_obs` (all DOUBLE — locale-sensitive when emitted via `%g` family). Per `wire-format-byte-preservation-discipline.md` §"Common drift causes" #3 ("Locale dependency — `%g` honors `LC_NUMERIC`. A stamp signed under `LC_NUMERIC=C` won't verify under `de_DE`"). Replay-determinism contract (Plan Pre-existing-work-audit "deterministic given seed") is strict — operator running engine under `LC_NUMERIC=de_DE` would write `0,55` instead of `0.55`, save→load round-trip would parse `0` (truncated at `,`).
- **Suggested fix:** Plan Step 4 adds (3 lines at emit construction; mirror v5.14.8.A.merged stamp_write_for_model pattern):
  ```cpp
  inline int Thompson_SaveJSON(const ThompsonBanditState* tbs, int n_regimes, const char* path, ...) {
      // ... open file ...
      locale_t pinned = newlocale(LC_NUMERIC_MASK, "C", (locale_t)0);
      locale_t prev = (locale_t)0;
      if (pinned) prev = uselocale(pinned);
      // ... fprintf body ...
      if (pinned) { uselocale(prev); freelocale(pinned); }
      // ... close + rename ...
  }
  ```
  ALSO: include `THOMPSON_STATE_FORMAT_VERSION` in JSON header (parallel to BANDIT_STATE_FORMAT_VERSION) so future migrations have a clean version bump path. Plan Step 1's struct should bump if any field is added (e.g., when `mu_prior` becomes per-arm in v5.14.X).
- **Reasoning:** The plan's "forward-compat-by-absence" language is the right shape, but the concrete discipline (locale pinning + format_version) needs to ship in the FIRST emit, not retrofitted later. Bandit_SaveJSON's missing `uselocale` is a TECH_DEBT-class gap (TECH_DEBT-027 candidate; flagged separately in this audit's deferral list).
- **Effort estimate:** +5 LOC at thompson save fn; +5 LOC at thompson load fn; +1 line `THOMPSON_STATE_FORMAT_VERSION 1` constant. Negligible.
- **Cross-references:**
  - Pattern doc: `wire-format-byte-preservation-discipline.md` Layer 2 (locale pinning)
  - Existing precedent: `ML_Headers/ModelInference.hpp` stamp_write_for_model (v5.14.8.A.merged) — shows the canonical 3-line pattern
  - GAP IN EXISTING CODE: `ML_Headers/BanditLearning.hpp:377-433` (Bandit_SaveJSON) has same gap — flag as TECH_DEBT-027 deferral
