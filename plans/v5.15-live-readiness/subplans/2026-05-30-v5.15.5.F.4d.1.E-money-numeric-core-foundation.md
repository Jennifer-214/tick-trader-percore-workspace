## Why this ship exists

The engine represents **all** numeric values — money (price/qty/fills/fees/P&L/balance) AND features/ML/stats — as one binary fixed-point type `FPN<F=64>` (value = magnitude/2⁶⁴). Binary fixed-point **cannot represent decimals exactly** (`2⁶⁴/10 ∉ ℤ`): `0.1` is stored as `0.0999…9997`. For features this is fine — they need *determinism* + magnitude-independent precision, not decimal-exactness (an EMA over prices generalizes over scales ~15 orders coarser than the `~1e-19` error). For **money** it is a latent correctness hazard: the value is correct-by-DISCIPLINE (round-at-reconcile) instead of correct-by-CONSTRUCTION, and it is **not source-exact** (the stored int is not what the exchange sent). That "correct by discipline, not construction" shape is the *same* fragility as the locale phantom-invariant the determinism net (`.E.0.1`) exists to kill (D-92).

D-97 reopened the question (operator pushback: "1e-19 ≫ tick" is a *magnitude* argument that never answered the *exactness / source-fidelity* argument). The correctness analysis is unambiguous: **decimal fixed-point wins for money.** And once decimal is committed, the implementation question ("a small `DecimalFPN` sibling?") resolved — over Session 4 — into a deeper, *better* answer: **one radix-parametrized `FixedPoint<RADIX,FRAC>` core**, because two parallel money types would be the Class-21/SSoT parallel-implementation trap (40+ ops are radix-agnostic). This is the money numeric core reaching its **final shape** — and it must do so **before** the `.E.1` ~5,000-site rename, or we rename the binary core and then re-architect it to decimal = touching the core twice (D-101).

**Cost of NOT doing it:** ship `.E.1`+ on a money core that is non-source-exact, has no rounding-mode control, no tick/lot quantization (a live-trading prerequisite that is entirely absent today), and a latent producer precision-loss seam (D-102) — then pay to re-do it after the rename. **Alternative ships considered + rejected:** minimal `DecimalFPN` sibling (rejected D-99 — parallel-type trap); from-scratch full rewrite (rejected D-99 — re-does the FP-determinism debugging `.E.0.1` just certified); defer decimal to post-`.E` (rejected D-101 — forces a double-touch of the core through the rename).

## The decision (settled — D-97 / D-99)

**DECIMAL fixed-point for the MONEY domain; binary fixed-point STAYS for features/ML/stats — both as instantiations of ONE unified `FixedPoint<RADIX, FRAC>` template.**

- **Money** → `FixedPoint<10, 8>` (decimal, scale 10⁸). Exact-by-construction; source-exact; rounds at a decimal place (= how money is accounted).
- **Features/ML/stats** → `FixedPoint<2, 64>` (binary, the current `FPN<64>` behavior). They need determinism (bit-identical cross-run/binary for train-serve M5 + H10) + `Exp`/`Sqrt`/`Log` + magnitude-independent precision — NOT decimal-exactness.
- **The native-128 `FixedPoint64.hpp`** type is ABSORBED into `FixedPoint<2,64>` with a native-storage policy (kills the parallel type + its F-058 aliasing-pun home).

This is **"aggressive structural rewrite that REUSES determinism-certified bodies"** (D-99): rewrite the FRAME (unify into one template) + absorb FP64 + write the DECIMAL specifics fresh against the anti-pattern catalog; **reuse** the `.E.0.1`-certified binary op bodies (post-`.E.0.1` there are no known bugs left in them — F-056/57/58/78 ARE those bugs, fixed and locked). Captures 100% of a rewrite's upside (one coherent core, all known classes designed out) because the only bug-bearing code is what's written fresh anyway.

**This is NOT premature abstraction** (D-99): two CONCRETE instantiations exist today ({2,10}), not hypotheticals. The discipline boundary (§1.5): get the {2,10} core 100% right; do NOT add `ROUNDING`/`OVERFLOW`-policy template params no instantiation uses (THAT would be the over-parametrize anti-pattern). "Get it 100% right now" = correctness of the core, not generality for imagined variants.

## The architecture — `FixedPoint<RADIX, FRAC>`

```
FixedPoint<RADIX, FRAC>  — one template; value = stored_integer / (RADIX^FRAC)
  RADIX = 2,  FRAC = 64   → binary   (== today's FPN<64>; features/ML/stats; native-128 storage policy absorbs FP64)
  RADIX = 10, FRAC = 8    → decimal  (money; scale 10^8; exact for every Binance price+qty)
```

- **`FRAC` meaning forks by radix** (O-3 RESOLVED D-110): binary → frac *bits*; decimal → frac *digits*. Primary constant `static constexpr SCALE = RADIX^FRAC`; `FRAC` = "fractional places in the given radix." Documented in the template header so `FixedPoint<10,8>` is unambiguous.
- **Radix-agnostic ops (40+, REUSE the certified bodies):** Add/Sub/AddSat/SubSat, all comparisons, Floor/Ceil/Round, Min/Max/Abs/Negate/Sign, BlendOnMask, ToString/FromString (word-loops; base-parameterized). These are the bodies `.E.0.1` certifies — reuse, do not rewrite.
- **Radix-specific ops (`if constexpr (RADIX==2)` vs `==10`):** `Mul` (scale-reduction: `>>FRAC` binary vs `/10^FRAC` decimal — the latter compiles to a branchless reciprocal-multiply, fixed-cost) and `Div` (`(n<<FRAC)/d` vs `(n·10^FRAC)/d`). Notional `price×qty` uses a double-width intermediate (**`int128` for the `<10,8>` money instantiation** per D-97's honest caveat) — already how both `FPN_Mul` and `FP64_Mul` work (`__uint128_t`/2N-word product), so we inherit the pattern; only the reduce differs.
- **Feature-only math stays binary-only** (`Exp` 2^k, `Sqrt` bit-scan seed, `Sin/Cos/Log/InvSqrt/Pow`) — these are the genuinely binary-specific ops, and they live in the feature domain, so the decimal instantiation simply never needs them. This is *why* the unification is low-risk: the hard-to-port ops are exactly the ones decimal doesn't use.

## The golden-EPOCH invariant (settled — D-100)

The determinism invariant is **scoped to a core EPOCH**:
- **Within an epoch:** byte-reproducibility (cross-run / cross-binary / cross-locale) is ABSOLUTE — the determinism gate enforces it continuously.
- **The epoch transition** (binary→decimal money core) is a **DELIBERATE, RECORDED event**: bump version, regenerate the characterization golden, retrain + re-stamp models. **before ≠ after is the boundary, NOT a regression**; *after ≠ match-going-forward* would be the regression. That scoping is the invariant.
- **CRITICAL — determinism ≠ correctness:** a wrong-but-deterministic decimal impl reproduces byte-for-byte forever (the determinism gate would bless a consistent wrong answer). So the regeneration boundary gets a **ONE-TIME correctness gate** the determinism gate cannot provide:
  - decimal-exactness differential (`0.1 + 0.2 == 0.3` exactly);
  - fees/PnL to the penny vs a hand-computed reference (and vs an EXTERNAL decimal reference — Python `decimal`/bignum — a one-shot validation frozen to golden, NOT a standing reimplemented oracle: the golden-master nuance);
  - round-trip `parse → emit → parse` stability.
  - Validate ONCE at regen → freeze → determinism guards it thereafter.
- **Permitted now because nothing live depends on the old values** (same precondition as the accepted HMAC/old-model retrain). This flips once running capital on prior models — the doc records that boundary.
