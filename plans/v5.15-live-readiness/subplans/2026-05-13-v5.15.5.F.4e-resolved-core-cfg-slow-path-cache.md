## Key changes

1. **Create `CoreFrameworks/ResolvedCoreCfg.hpp`:**
   - `template <unsigned F> struct alignas(64) ResolvedCoreCfg` with HOT/WARM/COLD cache-line tiers
   - `static_assert(sizeof(ResolvedCoreCfg<F>) == 192, "3 cache lines exact for AVX-512 future-work")`
   - Per-cache-line padding to fixed multiples
2. **AUTOPOPULATE the resolved struct fields** via `FOREACH_CFG_FIELD` walk:
   - Only fields without HIDDEN_BY_DEFAULT or operational-monitoring flags enter the cache (skip boot-only + monitoring fields)
   - Skip per-core-NON-overridable fields if their resolution is trivial (just `cfg->X` direct)
3. **Implement `ResolveCoreCfg(cfg, core_idx, resolved)`:**
   - Branchy override resolution per CLAUDE.md item 28 (predictable branch wins)
   - FP conversion at resolve time (FPN_FromDouble called once, not per-read)
   - Bitmap flag resolution: apply per-core overrides via existing `Cfg_GetEffective_<domain>_cfg_flags` accessors
4. **Modify `EventLoop_RebuildOneCore`:**
   - Add `ResolvedCoreCfg<F> resolved;` at slow-path entry
   - Call `ResolveCoreCfg(cfg, core_idx, &resolved);`
   - Replace ~60 `cfg->X` reads with `resolved.X` reads in slow-path body
   - Downstream functions (regime detector, mean reversion, etc.) accept `const ResolvedCoreCfg<F>&` as a parameter instead of `const Cfg*`
5. **Verify backtest determinism:**
   ```bash
   ./bin/foxml_suite --batch ... # post-migration
   cmp paper_runs/backtest_run.bin baseline_resolved_cfg_pre.bin  # must be byte-identical
   ```
6. **Measure slow-path p99 delta:**
   - Pre-migration baseline (captured at Step 0)
   - Post-migration measurement
   - Compute delta; verify <100 μs p99 maintained
7. **HOT_PATH_CHANGELOG entry MANDATORY** per CLAUDE.md item 17. Cost analysis:
   - Adds ~60 cycles per slow-path entry per core (resolution overhead)
   - Saves 600-1800 cycles of scattered reads
   - Net win: 10-30x

## Key concerns / pitfalls

- **Backtest determinism is the most critical gate.** ANY divergence between pre/post backtest output = bug. Common sources of divergence:
  - FP conversion order differs (`FPN_FromDouble(cfg.X)` called at different points → different rounding paths). **Mitigation:** convert at resolve time + pin conversion order to registry order.
  - Per-core override semantics differ (e.g., resolved struct uses `core_X[i]` if `override_set` but old code did `core_X[i] > 0 ? ... : cfg.X`). **Mitigation:** audit each per-core override resolution carefully against the OLD resolution logic.
  - Bitmap flag override resolution differs. **Mitigation:** reuse `Cfg_GetEffective_<domain>_cfg_flags` directly; don't re-implement.
- **Downstream consumers (RegimeDetector, MeanReversion, ExitPredictor, etc.) need API updates.** Currently they take `const Cfg*` or read globals. Migrate them to `const ResolvedCoreCfg<F>&`. Touches ~10-15 files.
- **Hot path MUST NOT TOUCH.** ResolvedCoreCfg is for SLOW PATH ONLY. Hot path reads from `ExecutionCore::params` (already cached + published via seqlock). Verify no hot-path call inadvertently references ResolvedCoreCfg.
- **Cache-line layout discipline:** populate HOT-first ordering by sampling actual slow-path read frequency. Use `perf record` to identify which fields are hottest; place those in cache line 0.
- **Pre-coding audit suggested:** per CLAUDE.local.md "suggest mid-sprint audits when work impacts downstream plans" rule — this is HIGH-RISK + new pattern field-tested for the first time. Recommend `/test-strength-audit + /dod-audit` pre-coding to catch determinism gaps and `/parity-check` post-coding to verify no regressions in train-serve parity (FP conversion paths potentially affect feature pack determinism).
