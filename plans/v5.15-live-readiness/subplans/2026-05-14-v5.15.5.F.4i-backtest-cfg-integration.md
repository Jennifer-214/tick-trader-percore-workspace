## Why this sub-ship exists

Operator UX problem identified 2026-05-14 (Caramel): "the Settings tab shows the same settings as live; backtest.cfg can only be edited by hand-editing the file." This is a symptom of cfg-surface fragmentation:

- `engine.cfg` → `ControllerConfig<F>` struct → SettingsPanel (90 of 213 fields surface)
- `backtest.cfg` → separate struct → **NO GUI surface; manual text edit only**
- `controller.cfg` → separate struct → manual edit (deferred to v5.15.6)
- `secrets.cfg` → separate struct → manual edit (deferred to v5.15.6)
- Training params → in foxml_suite → Training panel (partial)

Five separate parsers + five separate edit surfaces + GUI shows only the engine one. Categorical-tag pattern + `lives_in_struct` discriminator unify the surface (per `categorical-tag-applicability-pattern.md` "Cross-file cfg unification" section).

`.F.4i` is the first non-engine.cfg integration; v5.15.6 ships extend to remaining cfg files using the locked design.

## Step 2 — Identify the backtest cfg STORAGE strategy (~30 min)

**Two possible storage models:**

**Option A: Separate BacktestCfg struct.** Engine cfg + backtest cfg live in separate structs:
```cpp
template <unsigned F>
struct ControllerConfig {
    // engine fields ...
};

struct BacktestCfg {
    char data_csv_path[256];
    int  walk_forward_window_size;
    double walk_forward_holdout_pct;
    // ... ~30-50 backtest-only fields ...
};
```

Parser dispatches via `lives_in_struct`: STRUCT_CFG writes to ControllerConfig; STRUCT_BACKTEST_CFG writes to BacktestCfg. Two separate cfg structs.

**Option B: Nested BacktestCfg in ControllerConfig.**
```cpp
template <unsigned F>
struct ControllerConfig {
    // engine fields ...
    
    struct BacktestSection {
        char data_csv_path[256];
        int  walk_forward_window_size;
        // ...
    } backtest;
};
```

One struct; backtest fields nested. Parser writes to `cfg.backtest.<field>`.

**Decision criteria (decide at Step 2 based on Explore agent's audit):**
- If backtest cfg already lives in a separate `BacktestCfg` struct in the codebase: **Option A** (don't migrate struct shape; just add to registry with appropriate `lives_in_struct` discriminator).
- If backtest cfg fields are currently scattered (some in ControllerConfig with `backtest_` prefix, some elsewhere): **Option B** (consolidate as nested section). Simpler dispatch.

Default lean: **Option A** (preserve existing separation; less migration risk).

## Step 4 — Parser dispatch routing (~30 min)

Update `tt::cfg_parse_field<KIND_X>` dispatch in `CoreFrameworks/CfgFieldDispatch.hpp` to route writes by `lives_in_struct`:

```cpp
namespace tt {
    template <CfgFieldDescriptor::Kind K>
    inline void cfg_parse_field(void* cfg_root, const CfgFieldDescriptor& desc, const char* val);

    // KIND_DOUBLE specialization:
    template <> inline void cfg_parse_field<CfgFieldDescriptor::KIND_DOUBLE>(
            void* cfg_root, const CfgFieldDescriptor& desc, const char* val) {
        // Route to correct struct via lives_in_struct discriminator:
        char* target_base = cfg_dispatch_target<CfgFieldDescriptor::KIND_DOUBLE>(cfg_root, desc.lives_in_struct);
        double v = parse_double_fast(val);
        v = std::clamp(v, desc.payload.as_double.clamp_min, desc.payload.as_double.clamp_max);
        *reinterpret_cast<double*>(target_base + cfg_field_offset(desc, desc.lives_in_struct)) = v;
    }
}

// Dispatcher: which struct base pointer to use based on lives_in_struct
template <CfgFieldDescriptor::Kind K>
inline char* cfg_dispatch_target(void* cfg_root, CfgFieldDescriptor::LivesInStruct lis) {
    switch (lis) {
        case CfgFieldDescriptor::STRUCT_CFG:
            return reinterpret_cast<char*>(&static_cast<ControllerConfig<64>*>(cfg_root)->engine);
        case CfgFieldDescriptor::STRUCT_BACKTEST_CFG:
            return reinterpret_cast<char*>(&static_cast<ControllerConfig<64>*>(cfg_root)->backtest);
        // future: STRUCT_CONTROLLER_CFG, STRUCT_SECRETS_CFG, STRUCT_TRAINING_CFG
        default:
            return reinterpret_cast<char*>(cfg_root);  // fallback to root
    }
}
```

**Note:** assumes a unified `Cfg` "root" struct that contains pointers/sub-structs for each `lives_in_struct` value. If using Option A (separate structs not nested), the dispatcher signature changes — passes 4 base pointers (one per lives_in_struct) instead of one root + sub-resolution. Choose at Step 2.

## Step 5 — Save dispatch + per-`lives_in_struct` cfg.example auto-gen (~30 min)

Cfg_Save (per `.F.4d` registry-driven save) extends to emit ONE FILE PER `lives_in_struct` value:

```cpp
void Cfg_SaveAll(const Cfg* cfg, const char* base_dir) {
    // Save engine.cfg:
    FILE* engine_fp = fopen("engine.cfg", "w");
    Cfg_Save_Filtered(cfg, engine_fp, CfgFieldDescriptor::STRUCT_CFG);
    fclose(engine_fp);

    // Save backtest.cfg:
    FILE* backtest_fp = fopen("backtest.cfg", "w");
    Cfg_Save_Filtered(cfg, backtest_fp, CfgFieldDescriptor::STRUCT_BACKTEST_CFG);
    fclose(backtest_fp);
}

void Cfg_Save_Filtered(const Cfg* cfg, FILE* fp, CfgFieldDescriptor::LivesInStruct filter) {
    #define EMIT_CFG_SAVE_LINE(kind, name, label, section, meta, payload, tooltip, \
                               strat, op_mode, regime, risk, requires_cfg, lives_in) \
        if ((lives_in) == (filter)) { \
            tt::cfg_save_field<CfgFieldDescriptor::KIND_##kind>(fp, cfg, g_cfg_field_descriptors[FIELD_IDX_##name]); \
        }
    FOREACH_CFG_FIELD(EMIT_CFG_SAVE_LINE)
    #undef EMIT_CFG_SAVE_LINE
}
```

cfg.example auto-gen (per `.F.4d`) extends similarly: one `<X>.cfg.example` per `lives_in_struct` value, with category-grouped sections within each.

uint16_t current_op_mode_mask = 0;

else if (cfg.is_paper)   current_op_mode_mask |= OP_MODE_CAT_PAPER;

    active_strategy_cats |= strategy_categories_lut[cfg.core[core].strategy];

        if (current_section == #section) { \
            tt::cfg_render_field<CfgFieldDescriptor::KIND_##kind>(...); \

## Anti-patterns to avoid

- **Don't fold engine.cfg + backtest.cfg into one file in this ship.** Phase 2 cfg struct merger is deferred to v5.16+. Keep files separate; just unify the GUI surface via filtering.
- **Don't break backtest determinism.** The registry-driven parser MUST reproduce the manual parser's behavior byte-identically for backtest_*.cfg fields. Test via output diff.
- **Don't tie op-mode filtering to parser/persist.** Categorical filtering is GUI-only; parser writes backtest fields regardless of whether op-mode is currently BACKTEST. (Otherwise switching modes mid-session would lose data.)
- **Don't hardcode lives_in_struct dispatch in cfg field consumers.** Consumers read `cfg.backtest.<field>` directly (after struct routing); they don't care about the discriminator. Discriminator is parser/save concern only.
- **Don't add new backtest fields during this migration.** Migration first; new features after. Adding + migrating same time = harder bisect.
- **Don't surface secrets in the unified Settings tab without IS_SECRET masking.** secrets.cfg is deferred to v5.15.6 anyway; if a secret field accidentally lands in `.F.4i` scope, it MUST have IS_SECRET metadata bit + password masking.

## If something goes wrong

- **Backtest determinism breaks (output bytes differ):** registry-driven parser parses backtest field with different precision/order than manual parser. Bisect by reverting individual KIND specializations; verify each KIND's tt:: dispatch reproduces manual parse behavior.
- **Settings tab shows backtest fields in LIVE mode:** op-mode mask computation is wrong. Verify `current_op_mode_mask` is set correctly at GUI render entry.
- **backtest.cfg save produces different bytes than operator's existing file:** field ordering in `Cfg_Save_Filtered` walk differs from operator's expectations. Either order by FIELD_IDX (matches registry order) or by alphabetical name; document the choice in `.F.4i` ship notes.
- **Cross-struct parser dispatch fails (writes to wrong struct):** the `cfg_dispatch_target` function returns wrong base pointer for `STRUCT_BACKTEST_CFG`. Verify cfg root struct layout + dispatcher's struct-resolution logic.
- **Rollback:** `git reset --hard pre-v5.15.5.F.4i` (anchor at Step 0).
