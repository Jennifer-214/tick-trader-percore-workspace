## 2. The locked typing (D-380 — restate)

1. **single-doc plain JSON** (not NDJSON, not YAML — machine bus, byte-deterministic, zero new dep).
2. **uniform record-set TABLE** `{schema, rows}` (schema = the field-layout; name-as-column; sorted).
3. **schema-as-DATA registry** — one emit helper reads each kind's schema+version from a **language-neutral** data file (both C++ + Python read it); never a per-language hardcode.
4. **comments-only-never-code** — `codegen` live-only/off-bus; tooling never writes engine logic.

## 3. Concrete shapes (the build)

### 3a. The envelope — `foxtag grammar --json` (the 1st canonical)
```json
{ "envelope_version":"1.0", "kind":"grammar", "schema_version":"v1.0",
  "payload_schema_version":"grammar/1",
  "producer":{"tool":"foxtag","version":"0.1.0","command":"grammar","args":["--json"]},
  "status":{"ok":true,"code":0,"findings":[]},
  "target":{"paths":[],"git_head":"4c076ed"},
  "payload":{
    "categories":  {"schema":["name"],              "rows":[["HOT_PATH"],["SLOW_PATH"]]},
    "unit_types":  {"schema":["name"],              "rows":[["STRUCT"],["FUNCTION"]]},
    "derived_axes":{"schema":["unit_type","axis"],  "rows":[["STRUCT","SIZE"],["STRUCT","ALIGN"]]},
    "ladder":      {"schema":["section"],           "rows":[["OVERVIEW"],["CODE"]]}
  } }
```

### 3b. The schema registry — LANGUAGE-NEUTRAL (a JSON data file both sides read)
```json
// tools/lib/toolio_schemas.json  — the SSoT the ONE emit helper reads (C++ AND Python)
{ "grammar/1": {"tables": {"categories":["name"],"unit_types":["name"],
                           "derived_axes":["unit_type","axis"],"ladder":["section"]}},
  "units/1":   {"table": ["file","type","name","open_line","close_line","tags"]},
  "verdict/1": {"table": ["file","line","severity","message","kind"]} }
```
Add/evolve a kind = add/edit a row. Every emitter + reader tracks it. Zero emitter-code edits. (Format TBD by the audit — JSON vs a fenced block in the schema doc; must be C++-parseable without a new heavy dep.)

### 3c. The emit helper (write-SSoT) + the reader
```python
# tools/lib/toolio.py (Python side; a C++ twin in foxtag.hpp for the core)
def emit(kind, payload, *, producer, git_head, findings=()):
    schema = SCHEMAS[payload_schema_version_for(kind)]   # reads toolio_schemas.json
    validate(payload, schema)                            # rows conform to declared columns → else FAIL LOUD
    return { "envelope_version":"1.0", "kind":kind, "schema_version":SCHEMA_VER,
             "payload_schema_version":..., "producer":producer,
             "status":{"ok":not findings,"code":0 if not findings else 1,"findings":list(findings)},
             "target":{"git_head":git_head}, "payload":payload }
def read(env):                                           # ONE reader walks {schema, rows} for ANY kind
    return env["payload"]                                # consumers index by column-name via schema
```

### 3d. `cmd_grammar` (C++) — counts → SETS-in-envelope

## 5. Adoption / parity (D-349 — nothing cuts over unguarded)
The plugin reads `.toolbus/grammar.json` → derives its `UNIT` set + `[DERIVED]` axes → **kills the hardcoded Lua mirror** (`tag_grammar_adapter.lua:27` + `tagcontext.lua:9-10`) — this feeds `0.3`. Every other producer (units/layout/fields) + the check_* gates adopt the envelope **behind `parity_check`**, per-consumer + soak. **PASS ≠ cutover done** — it means cutover is ALLOWED.

## 6. Tests (selftests — non-vacuity per Class-51)
- `toolio.py --selftest`: emit→read roundtrip; a row that violates its declared schema **FAILS LOUD** (planted-bad); a known-good passes.
- `toolio_schemas.json`: a malformed kind row REDs.
- `grammar --json` parity: SETS match the counts (`|categories|==78` …) + the Python authority (byte-identical section in `parity_check.sh`).
- `foxtag_client.grammar()` returns the four tables.

## 7. Verification gate
foxtag builds; `grammar --json` validates against `toolio_schemas.json`; every new `--selftest` GREEN; `parity_check.sh` GREEN; `check_session_docs.sh` GREEN; `check_import_from_core.py` GREEN (no new roll-your-own root). Engine hot path UNTOUCHED (`calls_graph_diff` — foxtag never links into the engine).

## 8. Open design tensions — the I→A cascade's targets
These are surfaced deliberately (grounding made them concrete); the cascade investigates + refutes each.

- **Q1 — write-SSoT location (C++ vs Python).** "ONE write path" (D-378) — but the envelope must be emittable from BOTH the C++ core (`grammar`) AND Python (`verdict`/`layout`). Is the emit helper duplicated C++/Python (a mirror risk), or does C++ emit raw record-sets + `foxtag_client` wraps the envelope (one true emitter, Python-side)? The latter keeps ONE envelope-emitter but means the C++ CLI's raw `--json` isn't a full envelope. Which?
- **Q2 — schema registry format (the mirror trap).** The registry MUST be language-neutral (§3b) — but can foxtag's C++ read a JSON data file at startup without a heavy dep (it already parses its own grammar fences)? Or does the registry live as a fenced block in the schema doc (foxtag already reads those)? Verify feasibility; a C++-hardcode + Python-copy is the Class-18 mirror we must not build.
- **Q3 — is a full schema-registry justified NOW for 1 kind (grammar)?** `generalize-on-cohort` says build for grammar, generalize at the 2nd kind. Counter: the registry IS the D-379 mechanism + prevents the mirror. Right-size it: minimal registry (2 rows) + the discipline, not a schema DSL.
- **Q4 — `.toolbus/` location + gitignore scope** (`tools/.toolbus/` vs repo-root); does the plugin (separate repo) read it via a path or a copy?
- **Q5 — `content_hash` in v1 or defer?** (D-378 optional). Likely defer until a consumer needs dedup.
- **Q6 — reuse audit.** Does `foxroots` / `foxtag_client` / the existing `parity-dump` already give us a seam so the emit helper isn't net-new infra? (canonical-sister discipline.)
