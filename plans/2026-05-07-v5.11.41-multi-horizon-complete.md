## Trigger

Operator-flagged 2026-05-07 (post-v5.11.40 ship): the Train Multi-Horizon button trains N XGBoost models per horizon but does NOT run Walk-Forward, held-out validation, or auto-stamp per horizon. The function `train_multi_horizon_worker_fn` at `Backtest/BacktestPanels.hpp:3032` ends after `XGBoosterSaveModel` and writes a minimal `summary.txt`. Comment at line 3255-3256 explicitly states: *"Per-horizon summary.txt (minimal — full Save Run would require running WF; G.1 trains-and-saves only)"*.

Operator's exact phrasing:
- "does this train 3 models at once as well, and run WF and stuff and full validation for N experiments run?"
- "yeah lets add per horizon for this too for the WF and held out validation and stamps and stuff. that sounds critical"
- "would it be possible to distribute across N core?"
- "it wont introduce parity drift will it?"

The functional gap is real. Operator running 3 horizons today gets 3 trained models with no WF metrics, no held-out validation, no stamp — must manually re-run those for each model from the GUI. Defeats the purpose of the bulk Multi-Horizon button.

This ship bundles the functional fix (per-horizon WF + held-out + stamp) with the perf optimization (N-core parallel) into one ship per operator request: *"lets bundle all this together because it hits the same plumbing anyways, and we arnt writing single core code and then immediately overwriting it later"*.

```cpp
int max_parallel = run_control->run_config.multi_horizon_max_threads;
if (max_parallel <= 0) max_parallel = std::min(8, /*ncores*/get_nprocs() / 2);

if (actual_parallel >= 2) {

    // Serial path (existing v5.11.41.A logic)
    for (int h = 0; h < horizon_count; ++h) { ... }
}
```

**Step 1:** add cfg field `multi_horizon_max_threads` (default 0 = auto, computed as min(8, ncores/2) at runtime). In `ControllerConfig.hpp:754` block, add field; in `ControllerConfig.hpp:1092` block, set default=0; in `ControllerConfig.hpp:1538` block, add CFG_PARSE_INT.

**Step 2 — labels array isolation.** Critical: each parallel thread mutates a different label set. Cannot share `results->labels` (it's in-place written by `Backtest_ComputeLabelsFromSamples`). Solution:

```cpp
// Pre-thread setup: allocate per-horizon labels array (deep-copy)
struct PerHorizonWorkerArgs {
    TrainingPanelState *state;
    RunControlState *run_control;
    BacktestResults isolated_results;   // shallow copy + own labels[] pointer
    int horizon_idx;
    int horizon_ticks;
    float tp_pct;
    float sl_pct;
    int label_type;
    char model_path_template[256];
    char auto_stamp_secret[128];
    int auto_stamp_enabled;
    int n_splits, buffer_ticks, min_train;
    float gap_threshold;
};

// In spawn loop:
for (int h = 0; h < horizon_count; ++h) {
    auto *args = (PerHorizonWorkerArgs*)malloc(sizeof(PerHorizonWorkerArgs));
    memcpy(&args->isolated_results, results, sizeof(BacktestResults));
    // Allocate own labels[] heap region; original results->labels stays untouched
    args->isolated_results.labels = (float*)malloc(results->sample_count * sizeof(float));
    args->horizon_ticks = horizons[h];
    args->tp_pct        = tp_pcts[h];
    args->sl_pct        = sl_pcts[h];
    // ... populate rest of args
    pthread_create(&tids[h], NULL, &per_horizon_worker, args);
}
```

**Per-horizon worker function:**

```cpp
static void* per_horizon_worker(void *arg) {
    auto *args = (PerHorizonWorkerArgs*)arg;
    int h = args->horizon_idx;

    // Override per-horizon config (LOCAL copy, not shared)
    BacktestRunConfig local_cfg = args->run_control->run_config;
    local_cfg.label_forward_ticks = args->horizon_ticks;
    local_cfg.label_tp_pct        = (double)args->tp_pct;
    local_cfg.label_sl_pct        = (double)args->sl_pct;
    local_cfg.xgb_train_nthread   = 1;  // PARITY CONTRACT: pin to 1 for parallel mode

    Backtest_ComputeLabelsFromSamples(&args->isolated_results, &local_cfg);

    // Build per-horizon held-out split (uses sample_count from local copy)
    HeldOutSplit split = HeldOutSplit_Make(args->isolated_results.sample_count,
                                            (double)args->state->fv_held_out_fraction);
    char unlock_token[33];
    memcpy(unlock_token, split.lock_token, sizeof(unlock_token));
    HeldOutSplit_Unlock(&split, unlock_token);

    // Build per-horizon stamp request
    FullValidationResults *fv = &args->state->mh_horizon_fv[h];
    memset(fv, 0, sizeof(*fv));
    // ... populate auto_stamp_path/_secret etc. from args
    Backtest_RunFullValidation(fv, &args->isolated_results, &split,
                                args->n_splits, args->horizon_ticks,
                                args->buffer_ticks, args->min_train,
                                &args->state->mh_horizon_progress[h],
                                &args->state->mh_cancel,
                                args->label_type, args->gap_threshold);

    args->state->mh_horizon_complete[h] = 1;
    free(args->isolated_results.labels);
    free(args);
    return NULL;
}
```

## Parity contract (the answer to operator's question "it wont introduce parity drift will it?")

**Per-horizon STAMP BODY** (post-Phase A.0 schema closure):
- `feature_registry_hash` — same across all horizons (good: scaler covers all features)
- `label_registry_hash` — same across all horizons (good: same label_kind)
- `engine_version` — same across all horizons
- `scaler_sha256` — same across all horizons (scaler computed once over full feature matrix)
- `label_lookahead_ticks` — DIFFERENT per horizon, recorded in stamp body via Phase A.0 (correct: that's the horizon)
- `label_tp_pct` / `label_sl_pct` — DIFFERENT per horizon, recorded in stamp body via Phase A.0 (correct: per-horizon barriers)
- `xgb_train_nthread` — recorded for forensic post-hoc detection of mode divergence (Phase A.0)

**Per-horizon MODEL BINARY**:
- Different (each horizon trained on different labels). Bytewise identical given identical inputs.

**Cross-mode (serial vs parallel) parity**:
- IF `xgb_train_nthread=1` is pinned in parallel mode: serial-mode stamp identical to parallel-mode stamp (per horizon)
- IF parallel mode runs at default `xgb_train_nthread`: stamps will differ between modes (XGBoost's `hist` method aggregation order is nthread-dependent)
- **Decision: pin `xgb_train_nthread=1` in parallel mode**. Operator's serial-mode setting (typically 4) is preserved when running serial; only auto-overridden when parallel mode is active.

**Stamp body extension** (closed in Phase A.0): `xgb_train_nthread` field added with `has_xgb_train_nthread` Surface G forward-compat flag. Verifier records value in `ModelStampResult.xgb_train_nthread`; load-time refusal NOT triggered (engine has no expected nthread cfg-side). Recorded for forensic post-hoc detection (operator can grep stamps to confirm which mode produced each model).
