- **Surface:** `Backtest/BacktestSharded.hpp:197-201`
- **Pattern:** `structural-fix-preferred-decision-framework.md` (CLAUDE.md item 19) + `bitmap-flag-api.md`

### MEDIUM-2 — Cache cost trade-off undocumented (event_log_mode HOT→COLD relocation)

- **Surface:** `CoreFrameworks/OrderManager.hpp:1244,1260,1291` (drainer fill-path reads); `OrderManager.hpp:188-189` (HOT cluster comment stale).
- **Pattern:** `latency-vs-cache-decision-framework.md` (CLAUDE.md item 28) + `cache-layout-discipline-for-hot-side-structs.md`
- **Symptom:** Pre-.C.3, `event_log_mode` was an `int` in the HOT cluster (line 235 prior commit; co-located with `event_log` reads). Post-Finding-A', `event_log_mode` is now a 2-bit slot in `oms_state_flags` which lives in the COLD cluster (line 409 — adjacent to `adapter` at offset 0..47 within the COLD cache line).
  
  Drainer fill-process `ProcessFillCommand` reads `oms->oms_state_flags` at line 1244 (mode 1 fill handler dispatch) + 1260 (rejection event log dispatch). This is a NEW cache line touch from the COLD cluster on every fill.

  In LIVE mode: the COLD line is already in cache from `adapter` reads on `OrderManager_Submit`, so no extra penalty.
  
  In PAPER/BACKTEST mode (the dominant test+training surface): `adapter` is the empty default struct — the drainer never reads it, so the COLD line is NOT in cache. Each fill now pays a cold-line load to read `oms_state_flags`. Per CLAUDE.md item 28 framework: ~13ns (L3 hit) to ~100ns (DRAM miss) per fill.

  Compensating: the prior HOT cluster `int event_log_mode` between `submit_queues` and `event_log` was likely consuming 4 bytes of HOT-line space (or absorbed by alignment), so the change frees up to 4 bytes of HOT cluster space. Tighter `event_log` packing might net cache-positive on the drainer cycle, but the trade hasn't been measured.

  This trade-off is REAL but UNDOCUMENTED. The commit message claims "Saves 4 bytes per OMS in COLD cluster" (which is itself wrong — `event_log_mode` was HOT pre-.C.3 per line 234 comment); the actual saving moves the read from HOT to COLD. Net cache impact is workload-dependent.

  Also: the HOT cluster comment at line 188-189 still says "(orders, rings, event_log_mode, event_log)" — `event_log_mode` is no longer a HOT field. Doc-debt.
- **Suggested fix:**
  1. Update the HOT cluster comment at `OrderManager.hpp:188-189` to drop "event_log_mode" from the field list.
  2. Add a HOT_PATH_CHANGELOG.md entry per CLAUDE.md item 17 noting the cache-locality trade (one additional COLD-line touch per fill in paper mode; offset by ~4 bytes of HOT-cluster headroom).
  3. Optional optimization for paper mode: read `oms_state_flags` once at the start of `ProcessFillCommand` into a local; downstream uses the local. Compiler likely already does this; verify with `-S` if performance-critical.
  4. Future migration: if multiple HOT-path predicates end up packed into `oms_state_flags`, consider a HOT-cluster MIRROR uint8_t cache of bits that the drainer needs per fill (mirror updated at slow-path cadence — `event_log_mode` is boot-set so the mirror is trivial).
- **Effort estimate:** 30 min (comment fix + changelog entry). Measurement deferred to /latency-track skill when paper-test cadence tightens.
- **Cross-references:** CLAUDE.md item 28, item 17, item 18; `latency-vs-cache-decision-framework.md`; `cache-layout-discipline-for-hot-side-structs.md`.

### LOW-2 — OMS_PROJECT_INIT_BIT / RESET_BIT use `if/else` instead of branchless mask-write

- **Surface:** `MemHeaders/OmsFieldRegistry.hpp:371-375` + `410-414`
- **Pattern:** CLAUDE.md item 18(a) (branchless mask compute) + `latency-vs-cache-decision-framework.md` Rule 2
- **Symptom:** The BIT-kind init and reset macros use a branch on the init/reset value:

  ```cpp
  #define OMS_PROJECT_INIT_BIT(name, type, init, smask)                                 \
      do {                                                                              \
          if ((int)(init)) _oms->oms_state_flags |=  (uint8_t)(tt::smask);              \
          else             _oms->oms_state_flags &= (uint8_t)(~(uint8_t)(tt::smask));   \
      } while (0);
  ```

  Boot-only path (and paper-reset path for `kill_switch_tripped`), so the branch cost is irrelevant in practice (~3-5ns × few-times-per-boot = nothing measurable). But the macro form leaks a per-init branch into compiled output where a branchless variant compiles to fewer instructions:

  ```cpp
  uint8_t mask = (uint8_t)(tt::smask);
  uint8_t val_mask = (uint8_t)(-(int)(!!(int)(init))) & mask;  // 0x00 or full mask
  _oms->oms_state_flags = (uint8_t)((_oms->oms_state_flags & ~mask) | val_mask);
  ```

  Compiler likely cmovs the original form (predictable boot-time path), so semantically zero cost. Recommendation is style/consistency with the rest of the codebase's branchless mask discipline rather than a perf issue.
- **Suggested fix:** rewrite as branchless mask-select. Style consistency only; no measurable perf impact. Defer until next AUTOPOPULATE pattern application surfaces a similar boot path.
- **Effort estimate:** 5 min (2-line macro rewrite each × 2 macros = 8 LOC).
- **Cross-references:** CLAUDE.md item 18(a), item 28, `latency-vs-cache-decision-framework.md` Rule 2 "Prefer branchless over data-dependent branches".

## STORAGE_KIND dispatch correctness (operator brief item 4)

**Verified GREEN.**

The MULTI_BIT dispatch macros derive shift via `__builtin_ctz(smask)`:

```cpp
#define OMS_PROJECT_INIT_MULTI_BIT(name, type, init, smask)                           \
    MBS_SET_U8(_oms->oms_state_flags, (uint8_t)(tt::smask),                           \
               (int)__builtin_ctz((unsigned)(tt::smask)), (init));
```

For `MASK_OMS_STATE_EVENT_LOG_MODE = 0x18` (bits 3-4 = 0001 1000):
- `__builtin_ctz(0x18)` = 3 (trailing zeros before the lowest set bit)
- `MBS_SET_U8(field, 0x18, 3, init)` → `field = (field & ~0x18) | (((init) << 3) & 0x18)` — correct slot write.

The slot's `width` is implicit in the mask layout (popcount of contiguous bits). The mask must be a CONTIGUOUS bit-range for `__builtin_ctz` shift-derivation to work correctly. This is currently the case for all MULTI_BIT registry entries (only EVENT_LOG_MODE today). Future registry additions adding a non-contiguous multi-bit mask would silently corrupt the slot write — but no such case exists today.

**Defensive recommendation (not a finding):** add a `static_assert` in the registry that each MULTI_BIT row's mask is a contiguous bit range. Implementation: `static_assert((mask >> __builtin_ctz(mask)) == ((1u << __builtin_popcount(mask)) - 1))` for each row. Catches future contributors who try to use a non-contiguous mask.
