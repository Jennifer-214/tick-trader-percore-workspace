## Realistic `.F.4c` scope (revised post-.F.4b)

The plan claims ~400 LOC + 3 new tt:: specializations. Realistic post-.F.4b:

- **tt:: dispatch:** likely NO new specializations needed. `tt::cfg_parse_field<T>` already has `std::is_integral_v<T>` (signed atoi + clamp) + `std::is_unsigned_v<T>` (strtoull + clamp) + `std::is_array_v<T>` (strncpy) branches. KIND_INT = signed/unsigned integral; KIND_BOOL = stored as uint8_t (handled by `std::is_unsigned_v<T>`); KIND_INT_ENUM = int with extra validation (clamp to `[0, count)` if invalid → use default).
  - **Possible refinement:** add a `desc.kind == KIND_INT_ENUM` branch inside the existing integral handling that clamps to `[0, count)` on invalid + uses `desc.payload.as_int_enum.default_val` on out-of-range. ~5 LOC.
- **Registry rows:** ~80 new rows (~30 INT + ~15 INT_ENUM + ~30 BOOL). Bulk of the LOC.
- **INT_ENUM labels:** ~15 named `static const char* const ARRAY_NAME[]` declarations at namespace scope in CfgFieldRegistry.hpp (per amendment notice; compound literals inside X-macro are C99 + may not work in C++20).
- **Parser:** the existing `EMIT_CFG_PARSER_CASE` walk already runs for all FOREACH_CFG_FIELD entries. Adding INT/BOOL rows = automatic parser coverage. Remove ~80 manual `CFG_PARSE_INT(...)` / `CFG_PARSE_U32(...)` invocations.
- **field_defs[]:** new entries auto-extend per `EMIT_CFG_FIELD_DEF_FROM_REGISTRY` macro at SettingsPanel.hpp line ~280. Some preexisting manual CFG_INT entries may overlap → remove them (tooltip preservation discipline; same as .F.4b).
- **STAMP_BOUND derived filter:** new infrastructure — `FOREACH_STAMP_BOUND_CFG_DERIVED(X)` walk over `FOREACH_CFG_FIELD` with `STAMP_BOUND` metadata filter. Layer 5b canonical body hash test. This IS new code (~80 LOC); see wire-format-byte-preservation-discipline.md § Layer 5b for the spec.
- **Tests:** mirror `test_v5_15_5_F4b_cfg_field_dispatch()` shape — add KIND_INT roundtrip, KIND_INT_ENUM range-clamp, KIND_BOOL normalization (any non-zero → 1) tests. Plus Layer 5b hash lock test if STAMP_BOUND filter lands.

**Net estimate:** ~250-300 LOC. Mostly additive registry rows + maybe 5 LOC tt:: refinement for INT_ENUM + ~80 LOC STAMP_BOUND derived filter. The "Storage-size handling: Option A vs Option B" discussion in the plan body is MOOT — T is deduced; storage width comes from the field's declaration; no Option A/B needed.

## Design philosophy reminders (load-bearing for `.F.4c`)

Per `DOCS/DESIGN_PHILOSOPHY.md`:

- **§ 3 H13 — type-erased `reinterpret_cast` is FORBIDDEN.** If you find yourself writing `*reinterpret_cast<T*>((char*)cfg + offset) = v` style anywhere in tt:: dispatch, that's the Class 23 anti-shape. Use the X-macro extractor with field-by-reference; T deduced.
- **§ 7 Structural-fix family — tt:: dispatch is templated on TYPE, not Kind enum.** The `template <Kind K>` shape in the plan body is STALE. Use `template <typename T>` with T deduced from `cfg->X` field reference.
- **§ 5 Determinism — Layer 5b hash lock for STAMP_BOUND derived filter.** This is the wire-format byte-preservation discipline applied to a derived view. Synthetic populate every STAMP_BOUND-flagged field with deterministic values; SHA-256 the canonical body output; lock the hash at ship time. Future row reorders fire the hash test.
- **§ 11 Process discipline — consult Caramel before coding after audits fire.** Even if audit findings look clearly addressable, present them inline + iterate before starting code work. `feedback_consult_on_audit_findings` memory.
- **§ 10 Operator UX — tooltip byte-identity for migrated fields.** Hand-tuned operator prose (multi-line tooltips with examples) MUST be preserved when migrating from field_defs[] to registry. Use R"(...)" raw strings or `\n` escapes to match byte-for-byte.
- **§ 4 Latency — STAMP_BOUND derived filter is boot/training-time only.** No hot/slow-path impact. HOT_PATH_CHANGELOG entry = NONE.
