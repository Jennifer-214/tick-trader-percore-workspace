### #5 — Feature mask cfg per-core (3-4h)

Disable specific features per core (e.g., core 0 trains without
flow_ewma signals; core 1 includes them). Cfg field
`feature_mask_<core_id>` (uint64_t bitmap; 1 = enabled).

`Features_PackAll` checks mask before calling each FEATURE_N
compute fn; masked-off → 0 or sentinel.

Stamp body field: `feature_mask` per-stamp (separate from
`feature_registry_hash` since mask is operator config, not registry
structure).

Load-time: stamp's mask must match runtime mask (refuse strict /
warn-only).

**Design question:** is mask baked into `feature_registry_hash` or
separate field? Recommendation: **separate**. Hash is structural,
mask is configuration. Different ownership.

### #7 — Scaler comparison tool (2h)

CLI utility: `tools/compare_scalers.sh <a.scaler> <b.scaler>`.
Loads both via FeatureStandardizer_Load, computes per-feature
mean/stddev diff, reports % delta. Flags > 50% change as potential
regime shift.

Output:
```
Feature                | mean_a    | mean_b    | Δ%      | stddev_a | stddev_b | Δ%
short_slope            | 0.000018  | 0.000020  | +11%    | 0.0014   | 0.0015   | +7%
short_r2               | 0.4521    | 0.4498    | -0.5%   | 0.2814   | 0.2792   | -0.8%
flow_10s               | 0.18      | 0.42      | +133%   | 0.92     | 1.84     | +100%   ⚠ regime shift?
...
```

### #18 — RFV scaler binding (after design decision)

`Backtest_RunFullValidation` doesn't currently persist a scaler.
Design question: should RFV (a) reuse Train Model's existing scaler,
(b) compute its own from trainval split, or (c) skip scaler entirely
for evaluation?

**Recommendation:** Option B. Scaler is part of the held-out
validation artifact, not borrowed from training. Mirrors v5.9.5e
hermeticity principle.

After decision, implementation:
- RFV computes scaler from `[0, trainval_end_idx)` portion
- Persists as `<model>.scaler` next to held-out model
- Auto-stamp includes scaler_sha256 (already wired post-v5.9.5h)
