## Theme

Slow-path stalls (GC pause, OS scheduler hiccup, blocking I/O on
health log) leave hot path executing on stale GateParameters. The
`ConfidenceScorer.confidence_freshness_tau=300s` at
`ML_Headers/ConfidenceScore.hpp:217` damps confidence over time but
doesn't HARD-GATE. A high-confidence prediction made minutes ago can
still fire trades on stale params.

Fix: stamp every parameter publish with `publish_tick`, hot-path
checks gap, fires `SHALT_PARAM_STALE` when stale. Opt-in via cfg
(`param_staleness_gate_enabled`); default off.

## Phase A — `publish_tick` field + accessors (`v5.12.1.B.1`)

**Goal:** Add monotonic `publish_tick` field to `ParameterSlot<T>`
seqlock-paired with the payload. New write/read accessors that take/
return `publish_tick` alongside the payload, preserving existing
accessor signatures (boundary-stable).

**Step 0:** `CoreFrameworks/ParameterSlot.hpp` already has the seqlock
infra (`:143` Init, `:180` Write, `:225` Read, `:248` Sequence). Add
`publish_tick` field to the slot's payload-holder struct (next to the
double-buffered T values; both buffers carry their own publish_tick
copy so seqlock pairing works).

```cpp
// CoreFrameworks/ParameterSlot.hpp adjacent to existing payload field
// v5.12.1.B: each buffer carries its own publish_tick alongside the
// payload, so seqlock pair-read returns (T, publish_tick) atomically.
struct PayloadWithTick {
    T payload;
    uint64_t publish_tick;
};
PayloadWithTick buffers[2];
```

**New accessor signatures** (adjacent to existing
`ParameterSlot_Read` at `:225`):

```cpp
// v5.12.1.B: writer takes publish_tick alongside payload
template <typename T>
inline void ParameterSlot_Write_AndPublishTick(
    ParameterSlot<T>* slot, const T& new_params, uint64_t publish_tick);

// v5.12.1.B: reader returns publish_tick alongside payload
template <typename T>
static inline void ParameterSlot_Read_AndPublishTick(
    const ParameterSlot<T>* slot, T* out, uint64_t* publish_tick_out);
```

**Backward compat:** existing `ParameterSlot_Write` at `:180` and
`ParameterSlot_Read` at `:225` are PRESERVED (they internally call
the new variants with `publish_tick = 0`, marking "no staleness
tracking"). All pre-v5.12 call sites keep working unchanged.

**Tests** (+3):
1. seqlock pair-read: writer sets (payload=X, tick=T); reader sees
   either (old_payload, old_tick) OR (X, T) — never torn.
2. monotonic publish_tick: successive writes fail-loud if tick
   decreases (assert in writer).
3. legacy accessor parity: `ParameterSlot_Read` returns same payload
   as `ParameterSlot_Read_AndPublishTick` (publish_tick discarded).

**Sub-ship gate:** ParameterSlot tests pass; tag `v5.12.1.B.1`.

## Phase B — Slow-path writes publish_tick (`v5.12.1.B.2`)

**Goal:** `EventLoop_RebuildOneCore` (`CoreFrameworks/ControllerEventLoop.hpp:1768`)
calls `ParameterSlot_Write_AndPublishTick` with `now_tick`. All
publish sites updated.

**Step 0:** grep for `ParameterSlot_Write` callers:
```bash
grep -rn 'ParameterSlot_Write\b' CoreFrameworks/ Strategies/
```

Replace each call with `ParameterSlot_Write_AndPublishTick(&slot,
new_params, now_tick)` where `now_tick` is the current tick counter
(threaded through from the slow-path entry).

**Lazy-rebuild compatibility note (forward dep on v5.12.2.B):**
when v5.12.2.B's lazy rebuild SKIPS a rebuild cycle, it MUST still
update `publish_tick` to `now_tick` (republish with same payload + new
tick). Otherwise the staleness gate false-fires during legitimate
quiet periods. v5.12.2.B's sub-plan captures this dependency.

**Tests** (+2):
1. Slow-path rebuild → publish_tick increments to current tick
2. Multiple cores write independent publish_tick values (no
   contention; per-core slot)

**Sub-ship gate:** tag `v5.12.1.B.2`.

## Phase C — Hot-path staleness check + SHALT_PARAM_STALE (`v5.12.1.B.3`)

**Goal:** Hot path reads `publish_tick` alongside payload, computes
`current_tick - publish_tick`, branchless-gates the entry on
`< cfg.param_max_age_ticks`. Fires `SHALT_PARAM_STALE` when stale.

**Step 0:** Add SHALT code via X-macro at
`Strategies/StrategyInterface.hpp` adjacent to existing
`X(LOW_CONFIDENCE, ...)` at `:255`:

```cpp
X(PARAM_STALE,      "param-stale",      "slow-path params older than max_age_ticks")
```

**Cfg fields** (in `CoreFrameworks/ControllerConfig.hpp`):
- `uint64_t param_max_age_ticks;` (default 1000 = 10x poll_interval=100)
- `int param_staleness_gate_enabled;` (default 0)

**Hot-path edit site:** `BG_Evaluate` body (in `CoreFrameworks/OrderGates.hpp`).
Add ONE branchless mask check:

```cpp
// v5.12.1.B: branchless staleness gate (only active if cfg flag = 1)
// gate_pass = (gate_pass) AND ((gap < max_age) OR (!enabled))
uint64_t gap = now_tick - params_publish_tick;
uint64_t stale_mask = -(uint64_t)((int)(gap >= cfg.param_max_age_ticks)
                                  & cfg.param_staleness_gate_enabled);
gate_pass &= ~stale_mask;
strategy_halt_reason = (stale_mask & SHALT_PARAM_STALE) |
                       (~stale_mask & strategy_halt_reason);
```

**Hot path branch budget:** the above is FOUR scalar ops + one mask
op. No new branches. Bench gate (10M-tick replay) must show p99
unchanged vs `pre-v5.12.1.B` baseline.

**Tests** (+4):
1. publish_tick atomicity (slow-path writes monotonically; reader
   sees seqlock-paired value)
2. fresh path (gap < max_age → entry permitted, halt_reason = OK)
3. stale path (gap > max_age → entry blocked, halt_reason =
   SHALT_PARAM_STALE)
4. enabled=0 disables entirely (stale path → entry permitted; no
   hot-path cost beyond the mask compute)

**Sub-ship gate:** bench gate p99 ≤ `pre-v5.12.1.B` baseline;
tag `v5.12.1.B`.

## Accounting for prior ships

**v5.12.1.A (predecessor):** added `last_ws_tick_us` for WS-level
freshness. Orthogonal to this ship — `publish_tick` is parameter-
level freshness, different layer. No interaction; both can fire
independently for different stall classes:
- `last_ws_tick_us` stale → producer thread stalled (network/exchange)
- `publish_tick` stale → slow-path stalled (OS scheduler / CPU steal)

## Accounting for next ships

**v5.12.1.C:** uses Phase 1.A's WS field, not this ship's
`publish_tick`. No dependency.

**v5.12.1.D:** confidence-sizing infrastructure plumbing — orthogonal.

**v5.12.2.B (lazy slow-path rebuild):** MUST update `publish_tick` on
lazy-skip path (republish with current tick + same payload), else this
gate false-fires during legitimate quiet periods. Captured forward
dep — v5.12.2.B sub-plan reiterates.
