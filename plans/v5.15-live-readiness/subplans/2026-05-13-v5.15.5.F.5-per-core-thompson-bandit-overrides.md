## Key concerns / pitfalls

- **Stamp-bound fields:** `bandit_algorithm` and `thompson_rng_seed` are STAMP_BOUND (per cohort audit) — verify per-core overrides DON'T cause stamp drift refusal. The stamp body should contain the GLOBAL value; per-core overrides are operator-side runtime customization. **Decision:** per-core stamp-bound overrides require explicit operator acknowledgment via `acknowledge_per_core_stamp_drift=1` cfg flag? OR they're orthogonal to stamp drift? **Audit at `.F.5` start.**
- **Thompson per-core implications:** if core 0 uses Thompson but core 1 uses Exp3-IX, do their reward signals interact? Per CLAUDE.md item 24 (per-arm reward observability invariant) — bandits are independent per-core; per-arm rewards are observable regardless of which arm was selected → dual-mode A/B is mathematically valid. **Document in FEATURE_LOOKUP.md at ship.**
- **Momentum filter per-core:** verify each momentum filter's downstream caller reads from the per-core resolved value, not global. May require code touch in `Strategies/Momentum.hpp` (or wherever momentum-min checks live).
- **Default value semantics:** for fields where `0` is a valid value (e.g., `confidence_hard_block_threshold=0` means "disabled"), the override_set sentinel approach works. For fields where `0` is INVALID (e.g., `lazy_rebuild_force_period_us=0` would be nonsensical), parsing logic must clamp + verify.
