## Sub-ship breakdown

Per future doc 3-ship split (.E.1/.E.2/.E.3); each gets full plan body at planning-time per `feedback_plan_right_not_fast`.

### `.E.1` Foundation — MPSC primitive + new thread infrastructure (PARALLEL with existing drainer)

**Risk:** MED (additive; doesn't break existing). New infrastructure runs alongside current drainer as safety fallback.

**Scope:**
- MPSC queue primitive in FoxLIB (Vyukov bounded; well-known pattern; tests for contention + ordering + bounded-overflow)
- NEW API client thread skeleton (consumes from MPSC; serializes Binance REST calls; returns submit-ack via per-core SPSC)
- NEW fill router thread skeleton (reads Binance user-data WS; routes fills to per-core SPSC by order_id → core mapping)
- order_id → core mapping struct (small per-order; lifetime = submit-to-fill window)
- Both new threads run PARALLEL with existing drainer (validated against current drainer's behavior; safety fallback active)
- Tests verify MPSC primitive under contention scenarios

**Effort:** ~1-2 days focused.

**Acceptance:** MPSC primitive lands in FoxLIB with tests; new thread infrastructure spawned + idle (no production traffic yet); existing drainer untouched + still primary.

### `.E.2` Migration — per-core slow-path absorbs drainer responsibilities incrementally

**Risk:** HIGH (changes hot+slow-path execution flow; first behavioral change of architecture).

**Scope (per future doc; absorb one event class at a time):**
1. Manual close events first (lowest-risk; GUI-initiated; well-understood)
2. Fill consumption second (medium-risk; touches OrderManager state)
3. Post-fill bookkeeping last (highest-risk; touches P&L + trade log + position update)

Each absorption step:
- Wire per-core slow-path to consume the relevant event class from per-core SPSC (populated by .E.1's fill router thread)
- Remove the corresponding code path from central drainer body
- Build verify + test verify per absorption step (incremental safety)
- HOT_PATH_CHANGELOG entry per absorption (cost analysis)

**Effort:** ~2-3 days focused.

**Acceptance:** All 3 event classes absorbed by per-core slow-path; central drainer now does ONLY OMS_DrainSubmit (which migrates to API client thread at .E.3); tests GREEN at each absorption step.

### `.E.3` Cleanup — drainer thread deletion + coordination + concurrency-model amendment

**Risk:** MED (cleanup; mostly deletion of now-unused code + concurrency-model-summary spec rewrite).

**Scope:**
- Migrate OMS_DrainSubmit from central drainer → API client thread (final responsibility transfer)
- Delete central drainer thread spawn + thread body
- Cross-core "close all" / "halt all" coordination via shared atomic flag (simple; small overhead; per-core polls at slow-path cadence)
- Rate-limit awareness: per-core enqueue backpressure (don't let one core's high-frequency submits starve others' MPSC slot allocation)
- Concurrency-model-summary.md REWRITE (threading model fundamentally changed; drainer removed; API client + fill router added)
- DESIGN_SPECS NEW: mpsc-queue-pattern.md + per-core-drainer-architecture.md (Stage 3 first canonical at this ship)
- Final 5-binary test pass + parity-check + dod-audit + bug-check sweep (Class 26 + Class 27 surface elimination verification)

**Effort:** ~1-2 days focused (close to 2 if concurrency-model-summary amendment is extensive).

**Acceptance:** Central drainer thread DELETED; concurrency-model-summary.md amended; all tests GREEN; Class 26 + Class 27 detection at drainer surface returns CLEAN (surfaces eliminated structurally).

## Honest risks

Per future doc + 2026-05-27 PM realism check:

### R1 — Paper-test throughput data doesn't exist yet (the BIGGEST risk)

Future doc warning: "premature architectural optimization without throughput data could deliver an elegant refactor with zero observable production benefit."

**Mitigation options:**
- (a) Run paper-test session BEFORE .E starts (insert between .D and .E); use data to validate decision
- (b) Run .E.1 Foundation as standalone ship (low-risk; MPSC + thread infra); pause for paper-test before .E.2 Migration commits architectural change
- (c) Accept the risk per operator decision ("benefits just seem to far outweigh"); proceed without empirical validation
- **Recommendation:** (b) Foundation-then-pause-for-paper-test gives architectural prep + data validation; minimizes wasted effort if paper-test shows current drainer isn't bottleneck

### R2 — Exchange API rate-limit handling becomes per-core distributed

Currently trivial (1 thread = 1 rate-limit budget). Post-rework: N producers via MPSC need backpressure + rate-aware enqueue. If one core's submission rate spikes, others' submits could starve.

**Mitigation:** Rate-limit-aware MPSC enqueue (token-bucket per-core + global cap); designed at .E.1 Foundation; tested under contention; validated at .E.2 Migration.

### R3 — Test coupling depth unknown (test rework scope variable)

Future doc: "~3215 tests; many drainer-aware". Test rework could be shallow (~1 day) or deep (~3 days) — biggest variable in effort estimate.

**Mitigation:** Audit test coupling depth as Phase A.1 of .E.1; informs sub-ship plan body scope estimates.

### R4 — Replay determinism under N-way parallel submission

Per-core drainer changes order submission timing. Replay logic must still produce byte-identical output across runs.

**Mitigation:** /parity-check at each .E sub-ship close; replay determinism test ADDED as new acceptance criterion; if replay breaks → halt sub-ship + investigate before proceeding.

### R5 — Cross-core "close all" coordination corner cases

Currently single drainer naturally serializes "close all" — global flag set; drainer processes serially.
Post-rework: per-core polls flag; race conditions possible (e.g., new position opened on core A after close-all set + before core A polls).

**Mitigation:** Designed at .E.3 Cleanup; spec covers the race scenarios; tests for each.

### R6 — Drainer-as-source-of-truth assumptions in adjacent code

Some adjacent subsystems may assume "drainer iterates all cores per cycle" — e.g., kill switch evaluation. Need to enumerate + migrate or relocate to per-core or to coordinator thread.

**Mitigation:** Phase A.2 enumeration of drainer-touched state at .E.1; complete inventory before .E.2 Migration.
