# v5.9 — ML Hardening: train-serve parity, observability, prevention

**Date:** 2026-05-01
**Theme:** close the silent-failure gaps in the ML pipeline that the
v5.8 paper-testing pass surfaced, and add process guardrails so the
same bug-classes can't recur.
**Pre-req:** v5.8.10 shipped (last tag on `feat/v5.8-easy-additions`).
**Branch:** `feat/v5.9-ml-hardening` from `feat/v5.8-easy-additions`
(or `main` after that branch merges).

This is a quality sprint, not a feature sprint. Most ships add no
operator-visible new behavior — they make existing behavior
observable, validated, and harder to break.

---

## Why now

v5.8 paper testing surfaced a recurring pattern: **the ML pipeline
has multiple "wired but unobserved" code paths.** Things compile,
tests pass, but in operator workflows the wiring either doesn't
fire (auto-stamp UI gap, registry-hash check dormant) or fires but
silently degrades to a fallback (model load failure → SimpleDip).

Plus the audit pass exposed a meta-issue: an automated audit can
produce a false CRITICAL when the codebase has forward-compat dead
code (the unused FeatureComputeCtx auxiliary fields). Removing that
ambiguity helps both human and tool readers.

Three classes of issue this plan targets:

1. **Silent failures** — code paths that fail without operator-
   visible signal (model load, NaN feature, warmup gate, default-
   to-DIP cfg).
2. **Train-serve parity** — places where train and serve paths
   could diverge silently. v5.8.6 added structural protection via
   `feature_registry_hash`, but the regression test only covers
   one input shape.
3. **Prevention layer** — process changes (invariants doc, end-to-end
   recipes, regression-test fixtures) that catch *future* issues at
   plan-time or PR-time rather than paper-test time.

## Phase 1 — Visibility + immediate guards (v5.9.0, ~11-13h)

The four original HIGH-severity audit findings, the four post-paper-
test findings (cfg visibility, default-vs-deliberate, prediction NaN,
Train Model worker), and the unused-field cleanup. Closes the
"silent failures" class by making them visible.

### Items addressed

**1. NaN/Inf guards FOLDED INTO `Features_PackAll` (audit #4)**

**Resolution (post-readiness 2026-05-01):** Validation lives INSIDE
`Features_PackAll` itself, NOT at 5 caller sites. Single source of
truth. The packer returns -1 on validation failure (instead of the
feature count), and callers branch on the sentinel.

```cpp
// In ML_Headers/FeatureRegistry.hpp:
template <unsigned F>
inline int Features_PackAll(const FeatureComputeCtx<F>* ctx, float* out) {
    int n = 0;
#define X(id, name, version, enabled, fn, note) \
    if ((enabled)) { \
        out[FEATURE_##id] = (float)FPN_ToDouble(fn(ctx)); \
        if (isnan(out[FEATURE_##id]) || isinf(out[FEATURE_##id])) { \
            return -1;  /* sentinel: validation failure */ \
        } \
        ++n; \
    }
    FOREACH_FEATURE(X)
#undef X
    return n;
}
```

Each of the 5 callers gets a one-line branch:
```cpp
int n = Features_PackAll(&ctx, buf);
if (n < 0) {
    // NaN/Inf detected — zero buffer, emit one rate-limited health log,
    // bump per-core nan_feature_events_total. Skip this rebuild cycle.
    memset(buf, 0, MODEL_MAX_FEATURES * sizeof(float));
    HealthLog_Critical_RateLimited(...);
    state->cores[slot].nan_feature_events_total++;
    return /* skip prediction */;
}
```

**Why this design:** Mirrors the v5.8 single-source-of-truth principle.
Adding new validation is one site. The 5 callers each add a 4-line
branch but no validation logic. Per-core counter on EventLoopState
surfaces in TUISnapshot for ML Status panel display.

`CoreModelZoo_TryLoadRole` already logs to stderr, but the live

**3. ML entry health logs missing prediction + threshold (audit #17)**

Currently `cat="entry" strat=ml` events log `price`, `qty`, `slot`
but not the model-side decision context. Extend:

- `prediction=` (the value returned by `Model_Predict` /
  `Model_PredictMulti` — for barrier, log all 3 class probs)
- `threshold=` (the `ml_buy_threshold` at decision time, or the
  3-class threshold for barrier)
- `confidence=` (when `confidence_enabled=1`, the scorer's value)
- `effective_threshold=` (post-confidence damping)
- `feature_registry_hash=` (current build's hash, for log-time
  attribution if logs are reviewed across builds)

Plumb through `MLBuildContext.out_prediction` + `out_confidence` into
the entry event emit at fill time.

**4. Cfg-source visibility + suite-vs-engine cfg divergence (HIGH, surfaced 2026-05-01)**

The today-bug: foxml_suite reads `backtest.cfg`, live engine reads
`engine.cfg`. Operator sets `core_N_strategy=mr` in engine.cfg but
the suite ignores that file → all cores default to SIMPLE_DIP per
`ControllerConfig_Default` line 847 → no ML inference fires in the
backtest. Silent.

Three sub-fixes:

(a) **Engine header panel displays loaded cfg path.** Both
    engine_gui and foxml_suite show the cfg path they parsed at boot.
    Operator sees at-a-glance: "engine: 5.9.0 | cfg: backtest.cfg |
    registry: fc91...4a40". Mirrors the v5.8.6b engine header pattern.

(b) **Suite warns on legacy cfg.** When foxml_suite parses a cfg
    file that has zero `core_N_strategy=` lines AND `engine_arch=`
    is missing, emit a stderr WARN at boot:
    `[cfg] WARN: backtest.cfg lacks per-core strategy fields. All 4
    cores will default to SIMPLE_DIP. Add core_N_strategy= entries
    to enable other strategies. (Was the cfg meant to be a copy of
    engine.cfg?)`

(c) **Cfg-source comparison panel.** New panel in foxml_suite that
    diffs `backtest.cfg` vs `engine.cfg` (when both exist) and
    surfaces divergent fields. Operator catches "I edited engine.cfg
    but the suite reads backtest.cfg" before training.

**Effort:** ~1h.

**5. Default-vs-deliberate cfg field tracking (HIGH, surfaced 2026-05-01)**

Today: `ControllerConfig_Default` sets `core_strategies[i] = 2`
(SIMPLE_DIP) for all 16 slots. If cfg file is missing
`core_N_strategy=`, defaults silently apply. The "0!"/"1!"/"2!"/"3!"
warning markers in Per-Core P&L panel fire on every non-AUTO core,
including ones that fell to default — operator can't distinguish
"I deliberately set this to DIP" from "cfg was missing this field."

Fix:

(a) **Track explicit-set bitmap in cfg parser.** Each ControllerConfig
    field that has a default gets a parallel `_was_explicit` bit
    (only relevant fields, not all). Set on parse, unset on default.

(b) **Distinguish in TUI.** "0!" indicator becomes "0!" (deliberate)
    vs "0?" (defaulted) vs "0" (auto-regime). Three-state.

(c) **Boot warning on all-default critical fields.** If
    `core_strategies[]` is ALL defaulted (no explicit cfg lines),
    emit a stderr WARN at boot in BOTH suite and live engine.

**Effort:** ~1.5h.

**6. Prediction NaN guard (HIGH, sibling of feature NaN)**

`Features_PackAll` validates feature input (per #1 above), but
`Model_Predict` / `Model_PredictMulti` return raw float — XGBoost
can return NaN on poorly-trained models or pathological inputs.
Currently: if `prediction = NaN`, the gate decision `prediction >
threshold` evaluates false (NaN compares unequal to everything) →
no entry. Silent miss.

Fix: same fold idiom as feature NaN. After `Model_Predict`:

```cpp
double pred = Model_Predict(&zoo->buy_signal, features, n);
if (isnan(pred) || isinf(pred)) {
    state->cores[slot].nan_prediction_events_total++;
    HealthLog_Critical_RateLimited("[ML] core %d: prediction NaN/Inf — skipping", core);
    return;  // no entry; same fall-through as model-not-loaded
}
```

For `Model_PredictMulti` (3-class), check all class probs.

**Effort:** ~30min.

**8. WF purge gap not validated post-generation (audit #10)**

for (int i = 0; i < split->n_folds; ++i) {

### Items addressed

**1. Warmup progress observable (audit #9)**

**2. Label function NaN guards (audit #12)**

`Backtest/LabelFunctions.hpp` label generators (especially
`Label_ForwardPnl`) can produce NaN on degenerate inputs. Wrap each
with **per-type neutral-default handling**:

| Label kind (`label_kind` field) | NaN behavior |
|---|---|
| 0 = binary classification | 0.5 (neutral, neither class) |
| 1 = regression | 0.0 (zero return) |
| ≥2 = multiclass softmax | **skip the sample** (don't include in training; bump nan_labels_dropped) |

```cpp
float lbl = compute_label(...);
if (isnan(lbl) || isinf(lbl)) {
    HealthLog_Warn_RateLimited("[label] idx %d produced NaN/Inf", idx);
    if (LabelType_IsRegression(label_type))     return 0.0f;
    else if (LabelType_IsMulticlass(label_type)) return NAN;  // sentinel: skip
    else /* binary */                            return 0.5f;
}
```

Caller checks: `if (isnan(lbl)) { stats->nan_labels_dropped++; continue; }`
for multiclass; otherwise consume the neutral default + bump the
counter.

Add a one-line counter in BacktestResults: `nan_labels_dropped`.
Display in Past Runs.

**3. ConfidenceScore tau=0 silent default (audit #13)**

In `ConfidenceScorer_Init`, log a WARN when `tau <= 0` and the
default is being used. Better: reject at config parse time.

**4. ML class-weight handling docs (audit #3)**

Class imbalance is a training-script concern (XGBoost in Python),
not C++ code. But it's worth documenting:

- `DOCS/ML_TRAINING.md` (NEW): explains how to build a properly-
  weighted XGBoost model when class distribution is uneven
- Specifically calls out the user's 4.2/48.3/47.5 distribution and
  recommends `sample_weight` with inverse-frequency weights

**5. ConfidenceScore hard-floor (audit #21, was deferred)**

Audit #21 flagged that confidence scoring DAMPS the threshold but
doesn't BLOCK at very-low confidence. With low IC (noisy
predictions), the dampened threshold can become pathological —
trades fire on essentially-random predictions.

Fix: hard floor in StrategyParameters:

```cpp
constexpr double CONFIDENCE_HARD_BLOCK = 0.05;
double conf = ConfidenceScorer_Compute(...);
if (conf < CONFIDENCE_HARD_BLOCK) {
    Gate_Zero(out);
    out->strategy_halt_reason = SHALT_LOW_CONFIDENCE;
    return;
}
// existing damping below floor unchanged
```

Cfg-driven floor (`confidence_hard_block_threshold`, default 0.05).

## Phase 3 — Train-serve parity regression test (v5.9.2, ~4-5h)

**Spike resolved (2026-05-01, pre-coding):** existing scaffolding
fully reusable. No contingency needed.

- `tests/parity_harness.cpp` (240 lines, Track E.6) provides
  `DiffStats`, `compute_diff_stats()`, per-feature error breakdown,
  first-differing-row dump.
- `controller_test.cpp` already has ~10 EventLoopState construction
  sites (lines 3903, 3997, 4115, etc.) — `EventLoopState_InitLegacy`
  + `EventLoopState_RegisterCore` + `EventLoop_RebuildAllParameters`
  are callable directly in test context.
- Phase 3 INTEGRATES existing pieces, doesn't build from scratch:
  backtest path via `Backtest_RunFullValidation(collect_features=1)`
  → feature_matrix; live path via manual `EventLoopState` tick
  replay → `Features_PackAll` per cycle; diff via reused
  `compute_diff_stats()`.

**Effort:** 4-5h holds. No spike sub-phase needed.

The deferred prevention layer. v5.8.6 added structural protection
via `feature_registry_hash`, but only one input shape (synthetic
RegimeSignals) is bytewise-tested. This phase adds a **comprehensive
parity regression** that runs both the live engine path and the
backtest path on the same synthetic tick stream + asserts feature
output matches at every sample boundary.

### Why this matters

The class of bug we want to prevent: **a future change to
`Regime_ComputeSignals` or `MLBuildContext` populator could cause
the live and backtest paths to compute slightly different feature
values for the same input.** This passes the existing equivalence
test (which uses synthetic signals directly, bypassing
`Regime_ComputeSignals`). A regression test that drives both paths
through real tick data + asserts equivalence would catch it.

### Test design

```cpp
// tests/parity_train_serve.cpp (or new EXTENSIBILITY block)
//
// 1. Build synthetic tick stream: 10k ticks with known timing,
//    price, volume distributions
// 2. Construct two equivalent state contexts:
//    a. Live engine path: EventLoopState with one core,
//       MLBuildContext fully populated
//    b. Backtest path: ShardedBacktestDriver with same data
// 3. At each slow-path cycle, both paths compute features
// 4. Assert: feature_matrix[live][i][j] == feature_matrix[backtest][i][j]
//    for all i ∈ samples, j ∈ 0..NUM_REGISTERED_FEATURES
// 5. Tolerance: bit-exact (FP equality after FPN_ToDouble round-trip)
```

This is a heavy test (~10k slow-path cycles × 2 paths) but only
runs in `./build.sh test`, not in fast iterations. Catches drift
the existing tests miss.

### Items addressed

- Audit cross-cutting #1 (the false-CRITICAL one): closes the gap
  by structural assertion rather than just verification
- Future changes to `Regime_ComputeSignals` plumbing: instantly
  flagged if either path falls out of step
- Documents what train-serve parity actually means in code (the
  test is the executable spec)

## Phase 4 — Feature standardization (v5.9.3, ~6-8h)

The deferred v5.9 feature from the original v5.8 plan. Implement
mean-centering + unit-variance scaling for ML features.

### Items addressed

- Audit #11 (feature scaling absent)
- Original v5.9 plan goal (was: "indexes by FeatureId" since v5.8
  registry exists)

### Design

`ML_Headers/FeatureStandardizer.hpp` (NEW):

- `FeatureStandardizer<F>` struct holds per-feature mean + stddev
  arrays sized `NUM_REGISTERED_FEATURES`
- `FeatureStandardizer_Compute(...)` runs over the training-side
  feature_matrix at training time, computes mean + stddev per
  column, persists to a sidecar file `<model>.scaler` (or extends
  the stamp body)
- `FeatureStandardizer_Apply(...)` applies standardization at
  serve time: `out[i] = (in[i] - mean[i]) / stddev[i]`
- Stamp body extended: `feature_scaler_present=1` + `scaler_sha256=<hex>`
- Verifier checks scaler file exists alongside model when stamp says
  present
- Backward-compat: stamps without `feature_scaler_present` work in
  warn-mode; strict mode requires it for v5.9.3+ models

### Resolved design (post-readiness 2026-05-01)

1. **Sidecar file format:** binary (not text). Avoids locale-pinning
   concern + smaller file. Layout: `[u32 magic][u32 num_features]
   [double mean[N]][double stddev[N]][u8 sha256[32] of body]`.
   Sidecar SHA-256 stored in stamp body field `scaler_sha256`.

2. **Sidecar path convention:** `{model_dir}/{model_name}.scaler`.
   Same shape as `.stamp` (sidecar to the `.json`/`.bin` model file).
   Save Run copies it alongside the model + stamp.

3. **MODEL_FORMAT_VERSION bump:** 5 → 6. v5.8.x stamps lack
   `feature_scaler_present` field. Verifier WARN-loads (parses as
   absent) and skips standardization. Strict mode requires the field.

4. **Stamp body new fields** (when format_version >= 6):
   - `feature_scaler_present=0|1` (boolean — present and applied)
   - `scaler_sha256=<hex>` (SHA-256 of sidecar; verifier checks)

5. **engine.cfg.example entry:** `feature_scaler_present=0` (default
   off until models are retrained). Documented alongside other
   stamp-related settings from v5.8.10.

6. **Standardizer compute timing:** post-ALL-folds (computed once
   on the full trainval set after WF cross-validation completes),
   NOT per-fold. Matches the "single scaler per model" contract +
   the stamp's wf_mean_val + held_out_metric (which are also
   post-all-folds). Persist sidecar + stamp simultaneously.

#### Recipe: model rollback procedure (if model goes bad in live)

1. Open engine_gui Stats panel, observe symptom (e.g., losing trades
   pile up).
2. Identify rollback target: previous saved run with green stamp +
   passing paper test.
3. Stop engine: `pkill engine_gui` (or quit via GUI).
4. Edit engine.cfg: change `core_N_model_dir=` to the rollback
   model dir. **Do NOT delete the bad model file** — keep for
   forensics.
5. Restart engine. Boot log should show the rollback model loading
   + match line.
6. Verify model is the expected one via Engine header panel
   registry hash.
7. Document in `logging/health.jsonl` what happened (manual
   `health_log` line via CLI tool, or just append to a paper log).
8. Post-rollback: run a paper backtest of the bad model on the
   period where it failed. If you can't reproduce the failure mode
   in paper, escalate (data issue or hidden state bug, not just
   model drift).

seqlock-protected ModelHandle.

#### Recipe: retraining cadence

- Held-out gap drifts > `gap_acceptable_threshold` on recent

- Win rate drops > 10% over a 7-day rolling window vs the

- Regime classifier shifts category (e.g., used-to-be-trending
  market becomes ranging) — model trained on prior regime won't
  generalize
- After every quarter (calendar trigger — defensive)
- After any v5.x ship that bumps `MODEL_FORMAT_VERSION` or
  `FEATURE_REGISTRY_HASH`

### Output D — Cross-binary version handshake

Today: engine_gui (live) and foxml_suite (training) are separate
binaries. Operator could upgrade one but not the other. Models
stamped by foxml_suite at v5.9.0 + loaded by engine_gui at v5.8.10
would `MODEL_FORMAT_VERSION` mismatch (engine refuses) — but
ENGINE_VERSION_STRING mismatch (e.g. 5.9.0 trained, 5.9.1 deployed)
is currently silent.

Fix: live engine warns at boot if any loaded model's
`engine_version` (from stamp body) differs from current
`ENGINE_VERSION_STRING` by major.minor. Patch differences are fine
(e.g. 5.9.0a vs 5.9.0b). Major.minor differences emit a stderr WARN
and require operator acknowledgment via cfg
`acknowledge_cross_binary_version_drift=1`.

**Effort:** ~1h.
