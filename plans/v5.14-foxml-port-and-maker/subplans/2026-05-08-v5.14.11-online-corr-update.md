## Why this exists

Current v5.14.0 `RidgeBlender_BuildCorr` recomputes the N×N
correlation matrix from scratch every Ridge cycle (~1µs at N=8,
K=64). On most cycles, the prediction history barely changes — only
the newest record is novel; all others are stale-from-last-cycle.

Incremental online updates use Welford-style running stats:
- `mean_new = mean_old + (x_new - mean_old) / n`
- `M2_new = M2_old + (x_new - mean_old) × (x_new - mean_new)` ← variance numerator
- `outer_xy_new = outer_xy_old + (x_i - mean_i) × (x_j - mean_j)` ← covariance numerator

Then `corr[i][j] = outer_xy[i][j] / sqrt(M2[i] × M2[j])` on demand.

Benefits:
- Per-record update: O(N²) vs O(N²K) full recompute → ~40x speedup
  on each tick where a new prediction lands
- Per-cycle finalize: O(N²) → cheaper than full recompute too
- Sliding-window variant (drop oldest record): adds O(N²) for the
  drop step; still much cheaper than full recompute

Tradeoff:
- Slightly more complex state management
- Numerical drift over very long runs (Welford-style is stable but
  not perfect for Σx²); periodic full-recompute reset (~every 1000
  cycles) keeps drift bounded

## Implementation plan

### Step 1 — RidgeOnlineState struct + Update fn

File: `ML_Headers/RidgeBlender.hpp` (extend)

```cpp
template <unsigned F>
struct RidgeOnlineState {
    double mean[MAX_RIDGE_MODELS];
    double M2[MAX_RIDGE_MODELS];                              // Welford variance numerator
    double outer_xy[MAX_RIDGE_MODELS][MAX_RIDGE_MODELS];      // covariance numerator
    uint64_t n;                                                // sample count
    uint64_t cycles_since_recompute;                           // numerical-drift reset gate
};

// Push one new prediction record (N values across N arms).
// Cost: O(N²) per call (outer-product update inner loop).
template <unsigned F>
inline void RidgeBlender_UpdateOnline(RidgeOnlineState<F>* state,
                                        const float* predictions,
                                        int n_models);

// Finalize: convert running accumulators into correlation matrix.
// Cost: O(N²) once per Ridge cycle.
template <unsigned F>
inline void RidgeBlender_FinalizeCorr(double corr_out[MAX_RIDGE_MODELS][MAX_RIDGE_MODELS],
                                       const RidgeOnlineState<F>* state,
                                       int n_models);
```

### Step 2 — AVX-512 outer-product vectorization (cfg-gated; -O3 path)

For the inner loop:
```cpp
for (int i = 0; i < N; ++i) {
    for (int j = 0; j < N; ++j) {
        outer_xy[i][j] += (predictions[i] - mean_i) × (predictions[j] - mean_j);
    }
}
```

At N=8, the inner loop fits perfectly in AVX-512 vector width.
Vectorize via `_mm512_fmadd_pd`:
- Load 8 doubles for predictions
- Subtract mean (broadcast)
- Outer product = 8 broadcasts × 8 fmadd into 8 result vectors

Cost: O(N²) → roughly N inner-loop fmadd_pd operations + N
broadcasts. ~30ns at N=8 (vs ~200ns scalar).

Same data-deterministic guarantee as v5.11.7 Bandit_GetProbabilities
AVX-512 vectorization: use `_mm512_div_pd` (not mul-by-reciprocal),
`_mm512_fmadd_pd` matches gcc's scalar fusion order, sum reductions
stay scalar to preserve left-to-right ordering.

### Step 3 — Engine wiring

File: `Strategies/StrategyParameters.hpp` (replace BuildCorr call)

```cpp
if (config->ridge_online_corr) {
    // Push the latest prediction record from reward_ring head
    int latest_idx = (ezoo->reward_ring_head - 1 + REWARD_RING_SIZE) % REWARD_RING_SIZE;
    RidgeBlender_UpdateOnline<F>(&ezoo->ridge_online_state,
                                   ezoo->reward_ring[latest_idx].predictions,
                                   ezoo->primary_count);
    // Periodic full-recompute reset (numerical drift bound)
    if (++ezoo->ridge_online_state.cycles_since_recompute > 1000) {
        // Recompute from scratch via existing BuildCorr; reset cycles
        RidgeBlender_BuildCorr<F>(ezoo->ridge_state.corr_matrix,

        ezoo->ridge_online_state.cycles_since_recompute = 0;
    } else {
        RidgeBlender_FinalizeCorr<F>(ezoo->ridge_state.corr_matrix,
                                       &ezoo->ridge_online_state,
                                       ezoo->primary_count);
    }
} else {
    // Existing full BuildCorr path (default; unchanged)
    RidgeBlender_BuildCorr<F>(...);
}
```

## Latency analysis

**Slow-path (Ridge cycle):**
- Default (ridge_online_corr=0): ~5ns flag check + ~1µs full BuildCorr
- Online + scalar: ~5ns + ~200ns Update + ~50ns Finalize = ~250ns
- Online + AVX-512: ~5ns + ~30ns Update + ~30ns Finalize = ~70ns
- Hot path UNTOUCHED.

Per-cycle savings (when Ridge enabled): ~700-900ns. Modest in
absolute terms; meaningful as a fraction of Ridge's total ~3µs cost
(~25-30% reduction).
