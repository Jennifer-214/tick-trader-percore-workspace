## Theme

Cross-build determinism. v5.10 design Idea #11. Within-build,
v5.9.2's replay-determinism test verifies bytewise identity. But
across builds (different compiler / -O level / FMA support), IEEE-754
double additions can reorder, producing different RegimeSignals
values → silently different predictions.

`RollingStats`, `RegimeSignals`, `RORRegressor`, `FlowFeatures` use
`double` today. ~500 LOC of double math to convert to FPN<F>. After
conversion: bytewise identical across any compiler/flags.

### B.2.5 — FPN_Exp + FPN_Sqrt primitives + FlowFeatures conversion (~2 days)

**Source:** /plan-check 2026-05-06 surfaced this. Original B.2 claim
"FlowFeatures: ~100 LOC convert" understated the work — actual
FlowFeatures.hpp uses `exp()` (3× per push for EWMA decay) and
`sqrt()` (2 sites in z-score computes). Cross-build determinism
requires FPN-native versions of both primitives.

**Items:**

1. **NEW `ML_Headers/FPN_Exp.hpp`** — FPN-native exponential.
   Implementation: range reduction to a fundamental interval (e.g.
   `[-ln(2)/2, ln(2)/2]` via `exp(x) = 2^k * exp(r)`) + Taylor or
   minimax polynomial in the reduced range. Mirrors the FPN_Trig
   approach (locked design gate from operator decision 2026-05-02).
   Epsilon bound vs. IEEE-754 `exp`: ≤ 1e-6 over the EWMA decay
   range `[-30, 0]` (covers `decay = exp(-dt/half_life)` where dt
   in seconds, half_life in {10, 60, 300}).

2. **NEW `ML_Headers/FPN_Sqrt.hpp`** — FPN-native square root via
   Newton-Raphson on integer pipeline. Initial seed via bit-scan
   reverse on the integer FPN representation; ~5-7 NR iterations
   for FPN<64> precision. Fully deterministic; no FPU.

3. **FlowFeatures.hpp conversion (~100 LOC):**
   - `FlowState.ewma_10s/1m/5m` field types: double → `FPN<F>`
   - `FlowState_Push` decay calls: `exp(-dt / N)` → `FPN_Exp(FPN_Neg(FPN_Div(dt_fpn, N_fpn)))`
   - `LargeTradeState_ZScore` return type: double → `FPN<F>`;
     `sqrt(var)` → `FPN_Sqrt(var_fpn)`
   - `SpreadState_ZScore` same pattern
   - `RegimeSignals` consumers picked up by B.2 (they were waiting
     on this)

**Coding rules adherence (per DOCS/STRATEGY_AND_CODING_RULES.md):**
- Pure integer math; no `double` in hot/slow path after this phase
- Determinism: same input bytes → same output bytes (NR iterations
  are integer-deterministic)
- AVX-512 not required for these primitives (low-frequency math
  on slow path); scalar fallback is the canonical implementation.
  Vectorization can fold into v5.11.x if profiling shows wins.

**Files touched:**
- `ML_Headers/FPN_Exp.hpp` — NEW (~80-120 LOC + 30 LOC tests)
- `ML_Headers/FPN_Sqrt.hpp` — NEW (~60-100 LOC + 30 LOC tests)
- `ML_Headers/FlowFeatures.hpp` — type changes + call-site rewrites (~100 LOC delta)

**Tag:** `v5.10.0b.2.5`

### B.3 — FPN library performance hardening (Part 11, ~1-2 days)

**Source:** Gemini audit `DOCS/LATENCY_OPTIMIZATION_AUDIT.md` Part 11.
Folded in here because B.4's retrain absorbs any byte-level shifts
from the divide change; shipping Part 11 separately would force a
second retrain cycle. The FPN library is touched as a contained
sub-phase before retrain.

**Items (4):**

1. **AVX-512 compression of `FPN_Min` / `FPN_Max`**
   (`FixedPoint/FixedPointN.hpp`). Current scalar `#pragma GCC unroll
   65534` chains over `FPN<F>::N` words generate long sequences that
   clobber GP registers for `FPN<256>` / `FPN<512>`. Replace with
   `__m512i` registers + `_mm512_min_epi64` / `_mm512_max_epi64` /
   `_mm512_mask_blend_epi64`. Single-instruction min/max on packed
   8×64-bit words. **Bytewise-equal to scalar** — pure perf.

2. **Lemire / libdivide fast division by constants** in `FPN_ToString`
   / `FPN_FromString`. Current `O(N * digits)` divmod-by-10 chain
   inside the conversion loop. Use precomputed reciprocal
   multiplication (Lemire's method) for branchless inner divmod.
   Bytewise-equal output; bottleneck shift on REST parse + data
   ingestion.

3. **`adc` / `sbb` / `cmov` inline asm** for `FP64_AddSat` and the
   `FixedPoint64.hpp` saturated-arithmetic helpers. Current heavy
   logical ops to detect carry/borrow across the `__uint128_t`
   boundary compile to many micro-ops; explicit ASM gives 1-2 ops
   per saturation step. Gated behind `__x86_64__`. Bytewise-equal.

4. **True 128-bit integer divide via Newton-Raphson reciprocal
   multiplication** (`FixedPoint64.hpp::FP64_DivNoAssert`). Current
   path converts `__uint128_t` magnitudes to `long double`, divides
   in FPU, converts back — induces FPU/ALU pipeline-switch stalls
   AND sacrifices precise integer semantics. Replace with pure
   integer Newton-Raphson reciprocal multiplication. **Note: this
   IS a byte-level change** vs. the float-divide path; B.4's retrain
   absorbs it, but be aware that this is the only Part 11 item that
   changes output bits. Test bound: divide error ≤ 1 ULP across
   exhaustive small-magnitude inputs.

**Files touched:**
- `FixedPoint/FixedPointN.hpp` — AVX-512 min/max + Lemire divmod
- `FixedPoint/FixedPoint64.hpp` — asm AddSat + Newton-Raphson divide
- `tests/controller_test.cpp` — +6-8 tests (AVX-512 vs scalar
  bytewise equality, Newton-Raphson 1-ULP bound, asm AddSat
  saturation correctness, Lemire output equality with scalar divmod)

**Coding rules adherence (per DOCS/STRATEGY_AND_CODING_RULES.md):**
- AVX-512 paths gated behind `__AVX512F__` build-flag check; scalar
  fallback preserved for non-AVX-512 builds
- No allocations; no `virtual`; no `std::*` containers — pure value
  types and fixed-size arrays
- Determinism: same inputs → same bytes within a build (Newton-
  Raphson is integer-deterministic)

**Tag:** `v5.10.0b.3`

## Risk register

- High-risk refactor: ~500 LOC double → FPN; potential precision
  bugs that pass tests but fail in real backtests
- All existing models invalidated (must retrain) — operator coordination
- FPN sin/cos for hour-of-day signals: not first-class.
  **DESIGN GATE LOCKED 2026-05-02 (operator decision):**
  - **CHOSEN: FPN-native polynomial approximation.** ~3-4h impl;
    100-150 LOC; reusable for any future FPN trig needs (additional
    use cases pay back the investment). Bytewise deterministic at
    runtime by definition (FPN integer math, no IEEE-754).
  - **Implementation:**
    - Range reduction: `x mod 2π` via branchless FPN_Sub iterations
      (`while (x > π) x -= 2π`)
    - Taylor series for `sin(x)` in `[-π, π]`: 5-7 terms
      `sin(x) ≈ x - x³/6 + x⁵/120 - x⁷/5040 + x⁹/362880`
    - `FPN_Cos(x) = FPN_Sin(x + π/2)` — single helper
    - Compile-time FPN constants for divisors (6, 120, 5040, ...)
  - **Epsilon-bound test (B.1 gate):** FPN_Sin must agree with IEEE-754
    `sin` within 1e-6 over `[0, 2π]` for representative inputs
    (timestamps in milliseconds-since-midnight).
  - **Fallback:** if polynomial fails epsilon bound for some input
    range, ship lookup table (1440-entry precomputed FPN array;
    23KB; ~30 min). Polynomial preferred but lookup is a known-good
    backup if precision issues surface.
  - **v5.11 NOT NEEDED** for FPN trig — primitives ship in v5.10.0b.
  - File: NEW `ML_Headers/FPN_Trig.hpp` (~150 LOC + 30 LOC tests)
