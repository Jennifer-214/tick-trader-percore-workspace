# v5.14.1.E — Heterogeneous winsor exit models + Ridge for exit side

**Date drafted:** 2026-05-09
**Branch:** `feat/v5.14-foxml-port-and-maker`
**Predecessor:** v5.14.1.D (winsor + per-core override) close
**Rollback anchor:** `pre-v5.14.1.E` = v5.14.1.D close

**Closes:**
- Operator workflow gap: how to deploy heterogeneous winsor exit models
  using existing multi-handle infrastructure
- Mathematical correctness gap: bandit double-counts correlated exit models;
  Ridge is the correct tool for blending correlated alpha sources
- Architectural symmetry gap: v5.14.0 added Ridge for buy side; exit side
  was left on bandit-only

## Architectural finding (drives the small scope)

The exit-side multi-handle architecture **already exists** as of v5.13.4:

```cpp
// EnsembleModelZoo (CoreModelZoo.hpp:785+)
ModelHandle<F> exit_predictor[ENSEMBLE_HORIZON_MAX];  // already an array
int exit_predictor_count;                              // already counted
BanditState exit_bandits[NUM_REGIMES];                 // per-regime selector
```

Each `exit_predictor[i]` has its own `ModelHandle.scaler` (FeatureStandardizer).
v5.14.1.D extends FeatureStandardizer with winsor — so EVERY `exit_predictor[i]`
benefits automatically per the per-handle scaler infrastructure.

`EnsembleModelZoo_LoadFromCfg` already discovers `models/<base>_horizon_<H>/`
subdirs and loads each into `exit_predictor[i]` with its own scaler/stamp.

**Heterogeneous winsor exit models work TODAY** via this infrastructure
once v5.14.1.D ships. v5.14.1.E doesn't add the architecture — it adds:
1. End-to-end test fixture proving the heterogeneous setup works
2. Operator-facing documentation (workflow playbook)
3. Ridge blending mode for exit side (mathematically better blender for
   correlated models than bandit)
