## The empirical pivot (verification pass — compiled, not reasoned)

|---|---|
| FromDouble, ToDouble, Mul, DivNoAssert, AddSat, SubSat, Sub, all comparisons, Negate, Abs, Min, Max, IsZero | **0/27 (byte-identical)** |

- Cross-binary: native_O3 ≡ native_O0 (deterministic). ✓
- Post-F-056 sim (generic NR-sqrt body w/ native inner Mul/Div): native-NR-sqrt ≡ generic-NR-sqrt, **0 differing** → **determinism gate flips cleanly GREEN.**
- **WHY R1 is wrong at F=64:** FRAC_WORDS=1, so generic FromDouble writes only `frac_hi=floor(frac×2⁶⁴)` to w[0] — identical to native's single-word cast. R1's `frac_lo` divergence only exists at F≥128.

**Consequence:** R1's elaborate "FromDouble/ToDouble legitimately differ, resolved by F-057" disposition is a PHANTOM at F=64. The gate can be **simpler + stricter**: "all native FPN<64> ops byte-identical to generic EXCEPT sqrt (the bug F-056 fixes)" — a blanket gate passes today except for sqrt. And the plan's "3239/0 GREEN, broken-replaced: none" is **CONFIRMED CORRECT** (quorum-C's predicted FPN-trace test breakage was based on the same false R1 premise — refuted empirically; accounting-audit was right).

## CRITICAL / HIGH findings (must resolve before/in coding)

### H1 — F-076 fingerprint zero-init: FOLD into .E.0.1 (was "fold IF" / R4 LOW) — CONFIRMED 5×
`Backtest/Fingerprint.hpp:180` SHA-256s **raw** `ControllerConfig` bytes (comment claims canonical serialization — it doesn't); `ControllerConfig_Default` is default-init not zero-init; struct is mixed-alignment, no `_padding=0` (H12). Consumer is concrete: → `BacktestPanels.hpp:3157` (`config_used`) → `XGBoosterSetAttr("foxml_fingerprint")` → read at `ModelInference.hpp:509` = **trained-model lineage**. Empirical: two identical-value configs in differently-dirtied buffers → 16,961/68,224 differing bytes; **copy-assign still leaves 9** → a `_Default` memset ALONE is insufficient. Fix must zero the actual hashed buffer at the `config_used` populate site OR hash field-wise. Non-deterministic lineage (H9/H12); gates Net-1's fingerprint characterization (D-73). **Upgrade R4 LOW→HIGH; fold; correct the fix-site.**

### H2 — Recorder EMIT side locale-unpinned: ship's determinism premise is HALF-MET (NET-GATING) — completeness-critic
Plan fixes the PARSE side (F-054/55). But the CSVs being replayed are WRITTEN by recorders that emit locale-tainted floats: `TickRecorder.hpp:186` + `DepthRecorder.hpp:249` use bare `fprintf("%.8f,...")`, and there is **no process `setlocale(LC_NUMERIC,"C")`** (0 hits in source; existing pins are per-emit `uselocale` in stamp/JSON emits only). The F-059 golden-master must be GENERATED by these recorders, and the replay-locale gate as specced tests PARSE symmetry only → a recorder writing locale-variant bytes **passes the gate while corrupting the golden**. Replay determinism = write ∧ read immunity; the plan closes only read. **This is the finding that would falsify the ship's own premise if left uncovered.**

### H3 — cfg-parser atof cluster + no boot locale pin: SSoT claim false as written — CONFIRMED 3× (quorum) + verification
35 `atof` sites parse FPN cfg fields (`ControllerConfig.hpp:~2147-2357`); no `setlocale(LC_NUMERIC,"C")` in any `main()`. Parser is MIXED — registry-migrated fields use locale-immune `parse_double_fast`; unmigrated MANUAL_PARSER fields use `atof`. So the plan's "single-source-of-truth ONE parser / backtest↔live asymmetry closed" is ASPIRATIONAL. The candidate Class-37 grep-CI must be CATEGORICAL (`atof`/`strtod`/`strtof` on any parse path), not the 2 named files.

> **★ Highest-leverage amendment — ONE fix closes H2 + H3 + makes the gate meaningful:** a process-wide **`setlocale(LC_NUMERIC,"C")` at every entrypoint boot**. `LC_NUMERIC` governs BOTH `fprintf("%f")` emit AND `atof` parse → a single boot pin makes recorders emit C-locale (H2) AND the residual cfg `atof` parse C-locale (H3), and the replay-locale CI gate becomes a real guarantee instead of testing a property the engine doesn't hold. Consistent with the H9 locale-pinning-at-emit discipline (the engine already wants C numeric locale; it's an HFT engine with no i18n need). Recommend this over per-site `uselocale` wraps.
