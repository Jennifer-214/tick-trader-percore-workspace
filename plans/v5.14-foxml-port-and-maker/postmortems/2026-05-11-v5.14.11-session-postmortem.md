## Design pivots (each one surfaced something worth remembering)

### Pivot 1: FPN padding bug — structural fix vs patch

**Trigger:** Initial v5.14.11.B AVX-512 attempt to RidgeBlender introduced ~600 bytes to RidgeWeights struct, shifting stack layout downstream. The shift exposed FPN<F=64>'s LATENT uninit-padding bug: implicit struct padding bytes between `int32_t sign` and the next field were uninitialized; under the new stack alignment, `memcmp`-comparing FracDiff output became non-deterministic.

**Caramel's pushback:** "for the FPN, what is your recommended solution? what fits with the design philosophy i have? like we deviated and now we introduced issues" — explicit "we" framing (joint ownership), pointing to design-philosophy alignment as the deciding criterion (not LOC, not time).

**Decision:** Option A — `int32_t _padding = 0;` default-init field on FPN<F>. One-line structural fix; C++ default-member-init guarantees padding consistency across all constructions + copies; eliminates the bug CLASS, not just this instance. Established `DESIGN_SPECS/wire-format-patterns/struct-padding-determinism-pattern.md` as the reusable methodology; canonical first-reference: v5.14.11.B.2 FPN<F>; preventive application: ThompsonBanditState (4-byte gap after `int n_arms`).

**Going-forward rule candidate:** when a bug surfaces in a struct used for byte-equivalence comparisons (`memcmp` / SHA-256 / wire format / HMAC input), check WHOLE-STRUCT padding patterns BEFORE adding ad-hoc init code. The structural fix (explicit `_padding = 0` field via default member init) is bytewise-equivalent to the symptom fix in this case but ALSO eliminates the recurrence class for future stack-layout shifts. Codified as CLAUDE.md item 27 + DESIGN_SPECS doc.

### Pivot 2: Branchless Cholesky — "variable latency is bad"

**Trigger:** Initial v5.14.11.B.1 Cholesky AVX-512 implementation added `if (j > 0)` / `if (i > 0)` guards inside the inner reduction loop to skip zero iterations.

**Caramel's pushback:** "is this on the slow path? shouldn't we have all calculations like this be branchless? variable latency is bad" — three-claim challenge: (1) slow-path code paths still benefit from branchless math per CLAUDE.md item 18, (2) latency variance under load is a separate concern from average latency, (3) branchless math kernels are the design default.

**Decision:** Rewrite Cholesky_Solve as fully branchless constant-8 scalar (no AVX-512 explicit; compiler auto-vectorizes) + pre-zero L_out/y_out/w_out invariants so unused-row iterations are bytewise no-ops via IEEE-754 (`x*0=0`, `x-0=x` exact). Established `DESIGN_SPECS/refactor-patterns/branchless-math-kernel-pattern.md` as the reusable methodology; canonical first-reference: v5.14.11.B.1 Cholesky_Solve; subsequent applications: v5.14.11.B.3 RidgeBlender_UpdateOnline + BuildCorr (constant-iter inner reductions, vectorized via AVX-512 per item 25).

**Going-forward rule candidate:** math kernels on slow/hot path are constant-iter + branchless by DEFAULT. NO `if` guards inside reduction loops. Zero-contribution iterations are bytewise no-ops via IEEE-754 invariants. Algorithmic state pre-zero (per-row, per-solve, per-cycle) establishes the zero-invariant. Codified as CLAUDE.md item 26 + DESIGN_SPECS doc; enforced via `/dod-audit` skill checks (v5.14.11.B.5).

### Pivot 3: Pattern-codification-lifecycle as a META-DESIGN_SPEC

**Trigger:** Mid-sprint Caramel observation: "in the umbrella if there are any design specs we can save and reuse and generalize we should create those as well" — recognition that the DESIGN_SPECS authoring CADENCE itself was a reusable pattern (when to promote inline rule → docs entry → CLAUDE.md item → tooling enforcement).

**Decision:** Wrote `DESIGN_SPECS/meta-disciplines/pattern-codification-lifecycle.md` as a 7-stage lifecycle (inline observation → DESIGN_SPECS draft → CLAUDE.md item → cross-link → tooling enforcement → wider audit → catalog stabilization). This is the FIRST meta-pattern doc — it doesn't describe a code/data pattern; it describes the AUTHORING DISCIPLINE itself.

**Going-forward rule candidate:** when a session develops a reusable architectural pattern (e.g., bit-packed flags, AUTOPOPULATE companion, branchless math kernels), promote to CLAUDE.md once 2+ applications exist OR documented as DESIGN_SPECS. Meta-patterns get their own DESIGN_SPECS doc when the AUTHORING discipline itself becomes a reusable methodology. Added to CLAUDE.local.md as the "codify design principles in CLAUDE.md as patterns mature" rule (2026-05-09); reinforced via v5.14.11 closure with the meta-DESIGN_SPEC itself.

### Pivot 4: Cohort-audit when new cfg field has siblings

**Trigger:** During v5.14.11 plan-synthesis, the new `ridge_online_corr` boolean cfg field had 3 siblings (`ridge_within_horizon`, `ridge_across_horizons`, `exit_blender_mode`) that were STILL direct int fields despite v5.14.9.F sweep migrating other ML flags. Intra-family inconsistency would itself be a tech-debt class.

**Caramel's framing:** "id rather not add tech debt" — captured at plan-synthesis after seeing that (1) intra-family inconsistency would itself be a tech-debt class and (2) the framework verdict + codebase precedent diverged.

**Decision:** Run the 5-criteria `DESIGN_SPECS/refactor-patterns/cfg-flag-eligibility-criteria.md` framework on the COHORT, not just the new field. All 4 passed eligibility → cohort migration in same ship (v5.14.11.C). Pattern documented in cfg-flag-eligibility-criteria.md's new "Cohort audit when new field has siblings" section.

**Going-forward rule candidate:** at plan-synthesis time, when a new boolean cfg field appears in proposed scope, grep for sibling fields in the same domain (e.g., `*_enabled` / `*_mode` / `ridge_*` in ML domain). If 2+ siblings exist, cohort-audit is part of plan-readiness check (per CLAUDE.md item 13 reuse-audit + item 16). Lives alongside `/readiness` Check 24 + Check 25. Codified in CLAUDE.local.md "Going-forward rule: cohort-audit when new cfg field has siblings" (2026-05-11).

### Pivot 5: Branchless multi-flag mask dispatch — "Ridge ON AND Thompson OFF" → 1 mask AND+compare

**Trigger:** Ridge buy-side dispatch site had a 2-branch scalar form: `if (_ridge_gate && config->bandit_algorithm == 0 && ezoo->primary_count >= 2)`. With gate_state cached predicates (MASK_RIDGE_WITHIN_ACTIVE + MASK_THOMPSON_ACTIVE), the predicate could collapse to a single mask AND+compare.

**Decision (A from pre-coding audit):** `constexpr uint16_t ridge_only_mask = MASK_RIDGE_WITHIN_ACTIVE | MASK_THOMPSON_ACTIVE; if ((gate_state->flags & ridge_only_mask) == MASK_RIDGE_WITHIN_ACTIVE && ezoo->primary_count >= 2)` — collapses 2 scalar branches to 1 mask AND + 1 compare; ~2-3ns saved per cycle when gate_state wired; scalar form retained for backtest fallback (gate_state == nullptr).

**Going-forward rule candidate:** when a slow-path predicate has 2+ scalar branches that are ALL backed by cached gate_state bits, refactor to single mask AND+compare. The pattern: `(gate_state->flags & MASK_REQUIRED_BITS) == MASK_EXPECTED_VALUE`. Saves branch density (CLAUDE.md item 18); especially valuable when the slow-path is in a tight loop. Branchless multi-flag check is the default for gate-cached predicates going forward.

### Pivot 6: Effort-deferral vs design-deferral — Caramel's reaffirmation

**Trigger:** Multiple times in this sprint, I would suggest deferring an item to TECH_DEBT. Caramel's pushback consistently: do it now if architecturally bounded; defer only if separate concern.

**Caramel's framing:** "i'd rather not add tech debt" + "do it right now" instinct validated 4/4 times this session (FPN padding fix vs defer; Cholesky branchless rewrite vs ship with branches + defer; cohort migration vs defer to v5.X; pattern-codification-lifecycle meta-DESIGN_SPEC vs skip).

**Going-forward rule:** defer is last-ditch. "Effort-avoidance" deferrals have been wrong 3/3 times this session (continuing the trend from v5.14.10). Captured in `feedback_no_defer_for_effort.md` memory. Design-deferral (waiting for context to make the right design choice) remains valid; effort-deferral is anti-pattern.

## Architectural surprises (caught at audit time, not at ship time)

### Surprise 1: Tool call validation errors — embedded Edit inside Write fails

**Caught by:** Two distinct tool failures during this sprint.

**Specifics:** First failure during v5.14.11.B.0 audit findings write — `InputValidationError: An unexpected parameter \`Edit\` was provided` because Edit syntax was embedded inside a Write tool call. Second failure during v5.14.11.B.6 wider audit commit — tags ended up pointing to the wrong commit because the bad tag had to be deleted and re-created.

**Resolution:** Always separate Write and Edit tool calls. Two tool calls in one message is fine; nesting them is not.

**Lesson:** tool call ergonomics matter. When a Write tool creates a file that needs subsequent edits, those Edits are SEPARATE tool calls. Could be added to /handoff Step 7 as a "tool invocation hygiene" note.

### Surprise 2: Engine vs workspace commit splits

**Caught by:** `git add .claude/skills/...` failed with "pathspec is beyond a symbolic link" during v5.14.11.B.5 commit.

**Specifics:** Engine repo has many gitignored/symlinked paths into the workspace (DOCS/HOT_PATH_CHANGELOG.md, DOCS/TECH_DEBT.md, plans/, .claude/skills/). When a sub-ship touches symlinked files, the commits must split between engine (Version.hpp + source code) and workspace (the symlink targets).

**Resolution:** Engine repo gets only Version.hpp + non-symlinked source; workspace repo gets the actual symlinked-doc changes (committed via workspace path). Two commits per ship when both are touched.

**Lesson:** check `readlink -f path` before staging if there's any chance the file is symlinked. The engine `DOCS/` migration (v5.11.43) means many architectural docs live in workspace and are symlinked into engine. Going-forward rule already in v5.14.10 postmortem Surprise 7 — reinforced here.

### Surprise 3: TECH_DEBT-017 didn't exist in ledger despite being referenced in audits

**Caught by:** /readiness audit + /dod-audit had both referenced "TECH_DEBT-017 inventory" / "close TECH_DEBT-017" but `grep -n` in the ledger returned nothing.

**Specifics:** Audit reports cited TECH_DEBT-017 as the inventory entry tracking the Ridge cohort cfg-flag migration candidates. The entry was a planning ASPIRATION that was never actually written to the ledger.

**Resolution:** Wrote TECH_DEBT-017 retrospectively as CLOSED v5.14.11.C with full migration context. Auto-write contract honored.

**Lesson:** when an audit references a TECH_DEBT entry that hasn't been written yet, the agent should CREATE the entry (open) at audit time AND close it at ship time, not skip the creation. /readiness Check 25 (TECH_DEBT scan) caught the SYMPTOM (missing entry); the auto-write contract (CLAUDE.local.md 2026-05-09) is the FIX. Could be a /readiness improvement: detect "TECH_DEBT-NNN cited but not in ledger" cases and auto-open the entry.

### Surprise 4: Direct-field fallback patterns must migrate when fields are removed

**Caught by:** Compilation errors after removing 3 direct int cfg fields (`ridge_within_horizon`, `ridge_across_horizons`, `exit_blender_mode`).

**Specifics:** StrategyParameters.hpp had fallback patterns like `gate_state ? BITMAP_IS_SET(gate_state->flags, MASK_RIDGE_WITHIN_ACTIVE) : (config->ridge_within_horizon != 0)`. The `config->ridge_within_horizon` read no longer compiled after the migration. SlowPathGateRegistry.hpp predicates already used `BITMAP_IS_SET((_gate_cfg).ml_cfg_flags, MASK_ML_CFG_RIDGE_WITHIN_HORIZON)` so were unaffected; only the dispatch-site fallback ternary needed updating.

**Resolution:** Migrated fallback to `BITMAP_IS_SET(config->ml_cfg_flags, MASK_ML_CFG_RIDGE_WITHIN_HORIZON)`. Also refactored buy-side dispatch to branchless multi-flag mask check per Decision A (combines this surface with the optimization).

**Lesson:** when migrating a cfg field from direct-int to bitmap, grep for the field name across all source files BEFORE removing the field. Fallback patterns (`gate_state ? ... : config->field`) are a recurring trap. Could be a /readiness improvement: pre-flight grep for direct-field references when a cohort migration is in scope.

### Surprise 5: Tests had to migrate too

**Caught by:** Test compilation failures after cfg field removal.

**Specifics:** 12 test sites in tests/controller_test.cpp referenced removed direct fields — both reads (default checks, parser checks) and writes (cfg.ridge_within_horizon = 1; for gate-state tests).

**Resolution:** Migrated reads to `BITMAP_IS_SET(cfg.ml_cfg_flags, MASK_ML_CFG_*)`; migrated writes to `BITMAP_SET(cfg.ml_cfg_flags, MASK_ML_CFG_*)` + `BITMAP_CLR` for resets. Stamp body field reads (inf.* and sr.*) DID NOT migrate — those names are auto-generated by FOREACH_STAMP_BOUND_CFG NAME column and persist.

**Lesson:** when migrating cfg fields, distinguish (a) cfg field references (which migrate) from (b) auto-generated struct field names (which persist via the registry's NAME column). The two share names because the legacy_field column was the migration source. Could be added to migration plan checklists.

## Lessons synthesis

**1. Structural fixes pay off in the same sprint.** v5.14.11.B.2 FPN padding fix (Pivot 1) extinguished a recurring bug class with a one-line change. By Pivot 2 (Cholesky branchless), the same discipline was applied preventively: constant-iter + branchless + IEEE-754 zero invariants. By Pivot 5 (cohort migration), the rule was load-bearing: defer would have left intra-family inconsistency as future tech debt.

**2. Caramel's "design philosophy alignment" framing is more reliable than "fits the time budget".** When picking between options, the question that consistently produced sound decisions was "does this align with the design philosophy?" not "does this fit in this sprint?" Time-budget framing led to scope cuts; philosophy-alignment framing led to structural fixes that compounded.

**3. Meta-patterns deserve their own DESIGN_SPECS docs.** Pattern-codification-lifecycle.md is the first; it describes the authoring DISCIPLINE itself (when to inline → DESIGN_SPECS → CLAUDE.md → tooling). Future candidates: audit-cadence patterns, multi-agent dispatch patterns, sprint-sequencing patterns. The catalog can support a "patterns-about-patterns" section.

**4. /dod-audit enforcement closes the loop.** v5.14.11.B.5 wired the new patterns (items 26+27) into /dod-audit + /readiness checks. Future ships that introduce new math kernels will get audited automatically. The DESIGN_SPECS docs are normative; the skills enforce them.

**5. Wider-engine audits validate that patterns are sound.** v5.14.11.B.6 audited all ML_Headers/ math kernels for branchless-math + struct-padding compliance. Returned GREEN with 0 violations — meaning the patterns are SELF-CONSISTENT in current code and don't require retroactive migration. Sister to /merge-scan: where /merge-scan finds reuse opportunities, wider audits find compliance gaps.

**6. Engine vs workspace commit splits are a recurring friction.** Per Surprise 2, multiple commits per ship when symlinked docs are touched. The DOCS/ migration (v5.11.43) is the root; the friction is operational. No structural fix candidate today (engine-private vs workspace-private split is intentional) but worth tracking — if the friction grows, consider a `/sync-workspace` extension that automates the engine-side propagation commits.

**7. v5.14.11 was the smallest mega-bundle so far** (3 ship phases: A + B umbrella w/ 8 sub-tags + C). vs v5.14.10 (7 sub-tags) or v5.14.9 (17 sub-tags). The B umbrella with 8 sub-tags shows that "small mega-bundle" is still a viable shape — one architectural theme (online correlation + branchless math) split into pattern-establishment (.B.0) + applications (.B.1/.B.2/.B.3/.B.7) + propagation (.B.4/.B.5/.B.6).
