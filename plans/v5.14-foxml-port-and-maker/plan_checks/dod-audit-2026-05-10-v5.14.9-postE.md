**v5.14.9.F scope decision: NARROW (2 fields only)**

**Reasoning:**

1. **Field heterogeneity (latency-critical):** The 16 candidates serve DIFFERENT purposes:
   - **Hot-path gates** (gate_ema_enabled, danger_enabled, param_staleness_gate_enabled): hot-path reads; caching strategy differs (use atomic on ParameterSlot, not engine-wide cfg struct)
   - **Slow-path gates** (kill_switch_enabled, use_exit_model, etc.): slow-path reads; ALREADY migrated to FOREACH_SLOW_PATH_GATE (v5.14.9.B.0) for 7 of them
   - **Config/boot gates** (use_real_money, depth_enabled): single-time read at boot; bit-packing provides NO win (read once, never again)
   - **Event dispatch gates** (notify_enabled): single-time read at event-time; bit-packing not beneficial
   - **Feature flags** (foxml_vol_scaling_enabled, bandit_enabled, vol_sizing_enabled): slow-path feature toggles; consistency + observability matter more than memory (already handled by observability snapshots)

2. **Bit-packing win vs scatter (cost-benefit):**
   - Grouped into ONE uint16_t cfg_flags bitmap: **saves 30 bytes per ControllerConfig** (16 × 1 byte → 2 bytes + 1 stored)
   - Per-core override handling: each PER_CORE_OVERRIDE_FIELDS includes partial_exit_enabled ONLY (explicit choice); adding 16 new per-core boolean overrides = **16 new lines in PER_CORE_OVERRIDE_FIELDS macro** + per-core resolver logic
   - Observability regression: cfg display in SettingsPanel currently lists each field separately. Bit-packed fields need special display code (decode + check each bit). +30 LOC in panel code.
   - **v5.14.9.F scope pressure: already at 3 concurrent subsystems (ladder, gate registry, feature bitmap). Adding BROAD cfg flag refactor = scope creep.**

3. **Strict trigger-based approach (recommended):**
   - **v5.14.9.F ships NARROW: partial_exit_enabled + lat_enabled (2 fields)**. Both are observability-critical (displayed constantly in Account header + Strategy Status). Bit-packing saves **2 bytes per instance + allows multi-flag checks** (e.g., "any exit gate active?").
   - **TECH_DEBT-xxx**: "FOREACH_ENGINE_CFG_FLAG registry for 16 remaining booleans" — trigger is "when ControllerConfig reaches 50+ boolean fields (currently ~28 booleans + 80 numeric = 108 fields; 28 booleans = 28 bytes = 25% bloat; at 50 booleans = 50 bytes = 35% bloat, time to compress)." OR "when per-core override count > 10 (currently 3; would require registry pattern for consistency)."

4. **Alternative justification for BROAD (rejected):**
   - "All 16 should be bit-packed uniformly for consistency" — COUNTER: consistency achieved via pattern application at trigger time (TECH_DEBT entry), not pre-emptively. Premature abstraction violates CLAUDE.md item 19 (structural fix only at recurrence threshold). Count = 1 (current v5.14.9.F proposal = 2 fields). NOT at recurrence threshold.
   - "Operator may hot-swap all 16 cfg booleans frequently" — COUNTER: rg audit shows only 8–10 sites actively use each boolean. Most are set-and-forget (use_real_money, depth_enabled, bandit_enabled). Caching wins limited.
