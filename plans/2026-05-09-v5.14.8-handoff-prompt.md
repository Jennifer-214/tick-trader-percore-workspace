## CRITICAL: The asymmetric has_* naming issue (NEW finding)

**Discovered mid-coding 2026-05-09 (not in any of the 6 audits).**

ModelStampResult (parser-side) and StampInferenceCfgInputs (emitter-side)
use DIFFERENT `has_*` names for the same logical fields:

| Logical field | ModelStampResult (parser) | StampInferenceCfgInputs (emitter) |
|---|---|---|
| Bandit blend ratio | `has_inference_cfg_bandit` | `has_bandit` |
| Fees | `has_inference_cfg_fees` | `has_fees` |
| Scaler | `has_scaler_fields` | `has_scaler` |
| Num outputs | `has_model_num_outputs` | `has_num_outputs` |

**Operator decision needed:**

| Option | Approach | Risk |
|---|---|---|
| 1. Unify has_* names (pick one convention for both) | Touches 38+ callers + parser + emitter | **HIGH** |
| 2. Per-struct prefix in registry (auto-generates different names per struct) | X-macro complexity grows; preserves callers | **MEDIUM** |
| 3. Keep asymmetric (registry for emitter only; parser stays manual) | Doesn't close TECH_DEBT-006 fully | **LOW** |

**Operator preference (2026-05-09):** Option 2 — per-struct prefix in
registry. Resolves asymmetry while preserving callers. Estimated
~+1-2h vs original .A scope.

**Implementation hint:** the X-macro can be expanded with a callback
that prepends a struct-specific prefix to has_* generation. Caller
passes prefix as a separate macro parameter:

```cpp
// For ModelStampResult (parser-side; "has_inference_cfg_*" prefix):
#define X(name, group, type, fmt, def, get, when, doc) \
    type name;
FOREACH_STAMP_BOUND_MODEL_CONST(X)
#undef X
// + group has_* with "inference_cfg_" prefix where group=="inference_cfg":
#define GROUP_HAS_DECL(g, doc) uint8_t has_inference_cfg_##g;  // OR has_##g
FOREACH_STAMP_BOUND_MODEL_CONST_GROUPS(GROUP_HAS_DECL)
#undef GROUP_HAS_DECL

// For StampInferenceCfgInputs (emitter-side; "has_*" prefix):
// same expansion but GROUP_HAS_DECL just generates has_##g (no prefix)
```

The PARSER-side prefix discipline depends on EXISTING field names that
must be preserved for caller compat. Audit the actual prefix used per
group:
- ModelStampResult: `has_inference_cfg_bandit` (NOT `has_bandit`)
- ModelStampResult: `has_inference_cfg_fees` (NOT `has_fees`)
- ModelStampResult: `has_scaler_fields` (NOT `has_scaler`)
- ModelStampResult: `has_model_num_outputs` (NOT `has_num_outputs`)

**Alternative:** rather than per-struct registry expansion, define
caller-side aliases (e.g., `#define has_inference_cfg_bandit has_bandit`)
to UNIFY at the source. Less elegant but mechanical. Worth considering
for the 4 asymmetric flags only (other 7+ have consistent naming).

## Wire-format risk areas (be careful)

These are the surfaces where mistakes are HARDEST to diagnose:

1. **HMAC byte-for-byte preservation** — registry-driven emit MUST produce
   identical canonical body bytes to current manual emit. Format strings,
   field order, even whitespace must match. Test by comparing
   pre-migration v5.14.7 stamp's signature against re-emit-then-sign of
   same fields.

2. **`%g` vs `%.6g` vs `%.17g`** — different fields use different printf
   formats. Registry preserves these per-entry. Verify each entry's `fmt`
   field matches existing snprintf format string in stamp_write_for_model.

3. **xgb_tree_method is `char[16]`** — string-typed; can't use the same
   STAMP_MODEL_CONST_AUTOPOPULATE_ONE that handles numeric types. Need
   STAMP_MODEL_CONST_AUTOPOPULATE_STR_ONE variant OR per-entry conditional
   handling. The registry data file has a comment placeholder for this
   ("char[16] handled separately at struct-gen time").

4. **String fields generally** — scaler_sha256 (char[65]), expected_role
   (char[16]), overlay_hash (char[65]), effective_hash (char[65]). Need
   strncpy-based parsing + emit. Same pattern across all string entries;
   could be a separate STAMP_MODEL_CONST_STRING_ONE macro.

5. **emit_when expressions** — registry entries reference
   `inf->has_inference_cfg`, `inf->has_bandit`, etc. These need to
   resolve correctly at the migrated emit site. Per-struct prefix for
   asymmetric naming addresses this — emit-side uses `inf->has_bandit`
   (current emitter has_*); parser-side uses
   `result->has_inference_cfg_bandit` (current parser has_*).

## What CAN go wrong + how to recover

**HMAC mismatch on legacy stamp load:**
- Symptom: existing v5.14.7 stamps fail signature verification
- Cause: registry-driven emit produces different bytes than manual emit
- Recovery: rollback to `pre-v5.14.8.A.2` tag; re-examine emit order vs
  registry entry order; compare canonical body byte-for-byte

**Caller compile error after STAMP_HAS migration:**
- Symptom: `m->has_X` access in caller fails to compile
- Cause: bit-packing removed direct has_* fields; caller didn't use accessor
- Recovery: grep for missed `has_` accesses; replace with STAMP_HAS macro

**Asymmetric naming refactor breaks parser:**
- Symptom: parser crashes or returns wrong field values
- Cause: per-struct prefix logic in registry didn't preserve parser-side names
- Recovery: rollback to .A.1; re-examine prefix dispatch in struct generation

**Tests pass but real-world model load fails:**
- Symptom: production model load shows new failures
- Cause: round-trip test didn't cover specific field combination
- Recovery: extend round-trip test with operator's real model; add
  per-field assertion
