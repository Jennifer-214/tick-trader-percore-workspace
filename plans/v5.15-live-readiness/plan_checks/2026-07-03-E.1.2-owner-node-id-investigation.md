# E.1.2 `owner_node_id` — store-vs-derive investigation (synthesis)

## Arc
The 128B re-scope (D-292/D-293) proposed carving a 6-bit `owner_node_id` into `Position._pad_pos` for D-209 boot-reconcile attribution. Operator questioning ("why 16-bit / combine + mask / does this impact the hot path / are these the best fixes") drove a 3-I + 3-A investigation. **Verdict: don't store it — derive it. Stored field is the 3rd over-reach this session** (defer-to-E.1.3, born-generation, stored-`owner_node_id`), each caught by adversarial pass in favour of the leaner existing-mechanism answer.

## Verdict: DERIVE, don't store (unanimous, code-grounded)
- **A-1 (REFUTED):** no real-code path where a position's slot ≠ its node's geometry (`slot = node*2+leg`). Every open writes `positions[slot]` at the geometric slot; snapshot reload is a `memcpy` keyed by slot (node recovers via geometry); orphans are SOLD not adopted; live boot is flat; even the deferred venue-net fix iterates own nodes → geometric slots. The **slot IS the SSoT** (the servicing thread iterates `positions[slot]`, `SlowPath.hpp:134`); a stored field can only be a lie-capable Class-27 mirror. And it stamps from the same node-0 fallback (`Reconcile.hpp:243-245`), so it doesn't even fix the D-209 collapse.
- **A-2 (converges):** deriving `owner = partial_on ? (slot>>1) : slot` buys zero wire / no H12 hole / no `SHARDED` bump / no `CONTROLLER` bump / no write-sites / no drift-then-misread. It confirmed the version bump is unavoidable *if* you carve (reconcile refuses/opens-new, never rewrites loaded positions), which is another reason deriving wins.
- **A-3 (converges structurally):** its own fix for the `:856` bug is the *same* shared accessor.
- **Spec read (`per-node-position-ownership-model.md:41-70`, AR-11 tiebreak):** the spec DOES advocate the field ("make ownership a field, not an index implication") — but as the foundation for the **per-node sub-pool** future (K>1 slots/node, where slot stops encoding node), explicitly deferred ("build WHEN scaling earns it"), and justified by riding "the D-55/D-206 192B bump" — the free ride D-292 killed. Read post-D-292, the spec AGREES: derive now, reserve for the sub-pool.

## The resolution (D-294)
- **`Sharded_SlotNode(slot, partial_on)`** — add the missing INVERSE of the existing `Sharded_LegSlot`/`Sharded_NodeSlotMask` family (`ControllerEventLoop.hpp:1099/1117`), route the 6 open-coded `slot>>partial_on` sites through it. Canonical-sister; single-sources the derivation; closes the `:856` drift class.
- **Reserve** the `_pad_pos` bits (byte-neutral, UNPOPULATED) as the cheap door to the sub-pool future; add the actual field when that ships (+ its slot-assignment policy). Flip condition: a global free-slot pool / sub-pool that breaks `slot==node` — D-209 defers it, D-293 excludes distributed.
- **Position stays 128B** (D-292 reinforced) — no field, no carve, no version bump.

## Two real bugs found (independent of the accessor; close-out-now, E.1.2)
1. **`ControllerEventLoop.hpp:856` — ungated `slot>>1`** (Class-18 mirror-drift recurrence per A-3). In single-position mode (default) `slot==node`, so `slot>>1` = node/2 → per-node stats misattributed to node/2 on event-log-replay warm-restart. Severity **LOW today** (all consumers display/persist, none gate capital; aggregates sum unchanged), latent-MED if Phase-2.2 risk gates read per-node. Comment `:853-855` ("shifts harmlessly") is FALSE. **Fix:** route through `Sharded_SlotNode` (closes the class).
2. **`Portfolio.hpp:70` `_pad_pos[7]` — H12 hole.** No default-initializer; `Position_Reset` (`:221-231`) subset-zeroes (skips it) despite its comment claiming "full-struct SSoT" (A28/TD-182); the pad reaches the wire (`ShardedSnapshotPersist.hpp:169` `fwrite` of all 128B) → non-deterministic bytes in a byte-equivalence context. **Fix:** `_pad_pos[7] = {0}` DMI (matches the registry `= init` pattern) + registry-drive `Position_Reset` off the `FOREACH_POSITION_FIELD` `init` column (AM-3 — closes the subset-zeroing class) + `memset` the pad.

## Guard gap (→ task #13 codification)
`check_struct_alignment.py (c)` verifies a byte-serialized struct has a size-pin, NOT that its pad is zero-init — it did not catch bug 2, and a tree grep found NO explicit-pad-zero convention (other serialized structs may carry the same latent H12 hole). Strengthen the guard.
