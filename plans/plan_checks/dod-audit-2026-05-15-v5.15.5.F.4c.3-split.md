## Findings (severity-ordered)

### HIGH — F1: `PerCoreCfg<F>` cache-line alignment is asserted but per-element padding-or-alignment unspecified in plan body

**Surface:** plan Step 2 + B (ControllerConfig<F> restructure); architectural gate row "`sizeof(PerCoreCfg<F>) % 64 == 0`".

**Symptom:** Plan stipulates `sizeof(PerCoreCfg<F>) % 64 == 0` static_assert (good — closes anti-pattern of fragmented sizing). But does NOT explicitly stipulate `alignof(PerCoreCfg<F>) == 64` or `alignas(64)` on the type. This matters when `cores[16]` is laid out: sizeof%64==0 alone is not sufficient to guarantee `cores[c]` starts on a fresh cache line — the FIRST element's address is governed by the array's containing struct's layout AND the type's alignof. If alignof is 8 (most fields are FPN<F=64> with 8-byte alignof), the array could begin at an 8-byte boundary; elements would still be 64B-multiples in size so adjacent slots remain non-overlapping cache-line-wise BUT the FIRST slot could cross a cache-line boundary depending on enclosing struct layout.

The cross-thread-snapshot-publish-cluster-isolation.md Step 5 explicitly mandates BOTH: `static_assert(alignof(SlowPathTelemetry) == 64)` AND `static_assert(sizeof(SlowPathTelemetry) % 64 == 0)`. Per-core cluster (PerCoreCfg<F>) is the same shape (one slot per core, accessed from per-core slow-path thread + GUI reader thread) — both asserts apply.

**Suggested fix:** Plan body's Step 2 + architectural-gate row should explicitly require:
```cpp
struct alignas(64) PerCoreCfg { /* X-macro generated fields */ };
static_assert(alignof(PerCoreCfg<64>) == 64, "PerCoreCfg<F> must be cache-line aligned for cores[c] cross-thread access isolation");
static_assert(sizeof(PerCoreCfg<64>) % 64 == 0, "PerCoreCfg<F> sizeof must be 64-multiple so cores[c] elements occupy distinct cache lines");
```
Add both asserts to plan body Step 2 and to verification gate. The `per-instance-registry-pattern.md` DRAFT mentions sizeof%64 in its concrete shape — extend it to also mandate alignof==64 at Stage 3 promotion.

**Effort estimate:** 2-line plan edit + 1-row DESIGN_SPEC clarification.

**Cross-references:** `cache-layout-discipline-for-hot-side-structs.md` Rule 3 + `cross-thread-snapshot-publish-cluster-isolation.md` Step 5 + `per-instance-registry-pattern.md` § "Cache discipline".

### HIGH — F2: A2 bitmap-bool migration — runtime bitmap rebuild walker needs registry-bitmap-set-discipline verification

**Surface:** plan § A — "A2 hybrid bitmap-bool migration"; plan § B "Deletions" reference `ml_cfg_flags`; plan § H ML-side read sites; current code path `ControllerConfig.hpp:2236` `FOREACH_ML_CFG_FLAG`.

**Symptom:** Plan migrates 12 `ml_cfg_flags` bits to flat `KIND_BOOL` rows in per-core registry; runtime bitmap is "rebuilt from rows at slow-path rebuild." This is THE critical path that preserves hot-path branchless mask dispatch. The plan correctly identifies this in audit-gate item 8 ("bitmap-resident bool migration LOCKED to A2..."), but the plan body does NOT specify:

1. **Bit-position determinism.** The rebuilt `ml_cfg_flags` bitmap's per-bit positions MUST come from a compile-time constant per row (X-macro metadata column or enum value), not from the row's iteration order in the per-core registry. If iteration order changes (row reorder for clarity), bit positions shift silently → MASK_ML_*-keyed consumers across the codebase read wrong bit. Per `registry-bitmap-set-discipline.md` Shape A (missing SET) + Shape B (bypassed chokepoint), this is exactly the recurring class — except here it's "wrong bit position" instead of "missing SET."

2. **Bitmap overflow static_assert per registry.** The 12 bits sit in `uint16_t ml_cfg_flags` today (per current code). The rebuilt bitmap MUST keep that storage class OR be explicitly upgraded — and the new per-core registry needs a co-located `static_assert(MASK_ML_*_HIGHEST_BIT < 16)` overflow guard per `bitmap-overflow-protection-discipline.md`. Plan doesn't state where the assert lives.

3. **SET-discipline at the rebuild walker.** Rebuild walker iterates per-core registry rows; for each KIND_BOOL row that maps to a former `ml_cfg_flags` bit, the rebuild must OR-set the corresponding MASK_* bit. The bit-to-row mapping needs explicit anchoring (e.g., a new metadata column `runtime_bitmap_bit_pos` per KIND_BOOL row, or a parallel `FOREACH_MLCFG_BITMAP_BIT(X)` that pairs row-name to bit-position with a static_assert that the row exists in the per-core registry).

**Suggested fix:** Plan body § A2 should:
- Specify HOW per-bit position is anchored at compile time (mention `bitmap-overflow-protection-discipline.md` integration)
- Mandate a static_assert pairing the migrated bool-row count to `sizeof(uint16_t) * 8`
- Mention the SET-site discipline at the rebuild walker (single chokepoint; no bypass)
- Reference `registry-bitmap-set-discipline.md` Shape A/B as the prevention discipline

**Effort estimate:** plan body addition ~10 lines; the implementation is mechanical at coding time but the discipline must be stated explicitly to survive cold-pickup.

**Cross-references:** `registry-bitmap-set-discipline.md` + `bitmap-overflow-protection-discipline.md` + `multi-bit-state-encoding-pattern.md` (sister; rejected for K=2 bool flags but worth citing the alternative). The plan correctly chose A2 hybrid over multi-bit per CLAUDE.md item 30 / cfg-scope-discipline § "A2 bitmap-bool migration."

### MEDIUM — F5: Cross-thread access pattern of `cores[c]` reads from GUI tab needs cluster-isolation note OR rationale for skipping

**Surface:** plan § F (Settings panel updates); plan § B (PerCoreCfg<F> layout).

**Symptom:** Per-core tabs in Settings panel render `cores[c].<field>` for the active tab. GUI thread READS `cores[c]`; slow-path thread for core c WRITES to `cores[c]` (post-parse / post-cfg-reload). This is a cross-thread access surface — exactly what `cross-thread-snapshot-publish-cluster-isolation.md` covers.

BUT: the cfg surface is largely STATIC at runtime (cfg is loaded at boot or reloaded from file on signal). The plan's § F + the universal-registry-bitmap-dispatcher-pattern.md § "GUI ↔ engine thread isolation" load-bearing rule states: "GUI thread owns a `ControllerConfig<F> gui_engine_cfg` instance (its mirror of `engine.cfg`); Engine HP/SP threads own a separate `ControllerConfig<F> engine_cfg` instance." If this rule is in force, the GUI's `cores[c]` reads are FROM THE GUI'S OWN MIRROR, not the engine's running state — no cross-thread access actually happens at the running-engine cores[c] address.

The plan does NOT state which model it follows. If the GUI shares the engine's `ControllerConfig<F>` instance (single struct, both threads access), then F1's alignof+sizeof asserts plus per-element isolation are LOAD-BEARING for false-sharing prevention. If the GUI has its own mirror per the load-bearing rule, the false-sharing concern dissolves but the cache-line alignment is still hygienic for sizeof determinism + array layout.

**Suggested fix:** Plan body Step 2 (or § F) should explicitly state which model is in force:
- **Option α (recommended per the universal-dispatcher rule):** GUI has its own `ControllerConfig<F> gui_engine_cfg`; reload-signal channel propagates engine.cfg changes. False sharing not a concern; cache-line discipline is hygiene.
- **Option β:** GUI reads engine's running cfg directly (shared instance). Cache-line discipline is LOAD-BEARING; F1's asserts close it.

Either choice is fine but must be stated. Reviewers can then trace the implications.

**Effort estimate:** 5-line plan body addition.

**Cross-references:** `cross-thread-snapshot-publish-cluster-isolation.md` Step 1 + `universal-registry-bitmap-dispatcher-pattern.md` § "GUI ↔ engine thread isolation."
