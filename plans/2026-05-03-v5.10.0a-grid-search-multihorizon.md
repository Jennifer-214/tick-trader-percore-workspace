**Date:** drafted 2026-05-02; ships post-merge of v5.9 → experiment/per-core-sharding
**Branch:** `feat/v5.10.0a-grid-search` (new, from `experiment/per-core-sharding`)

**Effort estimate:** 1-2 days
**Hot path:** UNTOUCHED (training-only)

## Theme

Operator's "parallel hyperparameter search" idea (v5.10 design Idea #1)
made real: 4 cores train models with different sweep parameter
combinations in parallel. Builds on v5.9.5h's hyperparam cfg fields
and v5.9.5j's auto-stamp.

Also includes Idea #4 (multi-horizon prediction) since it's a
specialization of grid search (sweep `label_forward_ticks` instead
of `xgb_subsample`).

## Items

### #1 — Parallel grid search wired to hyperparams (~1-2 days)

**Phase a (30 min):** Wire OptimizerPanel to sweep XGBoost hyperparams.
After v5.9.5h, hyperparams are cfg fields (`xgb_subsample`, etc.).
`OptimizerRange` already supports any `cfg_path`-keyed sweep via
`ConfigField_Set` (BacktestEngine.hpp:1809). Just expose hyperparams
in OptimizerPanel UI's parameter selector (combo populated from
cfg-field-list).

**Phase b (1-2 days):** Cross-core parallel training.

- Per-core feature_matrix slicing — already exists in BacktestSharded
  (driver fans ticks across SPSC rings; per-core engines compute
  parallel)
- Per-core training: each core gets a different sweep parameter
  combination, trains its own XGBoost model
- Per-core model save with sweep-index suffix (e.g.,
  `models/sweep_001_subsample_0.5/`)
- Aggregation: pick best by metric (`OPT_METRIC_*`) across all cores
- Triple-split discipline: separate train/val/test where test is
  locked, only used for final selection (mitigates overfit-by-tuning)

**Files:**
- `Backtest/BacktestEngine.hpp` — `Backtest_RunSweep` already
  serial; add `parallel_cores` cfg + per-core dispatch (~100 LOC)
- `Backtest/BacktestPanels.hpp` — OptimizerPanel UI: hyperparam
  selector combo, "parallel cores" toggle (~50 LOC)
- `tests/controller_test.cpp` — sweep over `xgb_subsample`, verify
  best run identified

### #4 — Multi-horizon prediction (~5-7h, after #1)

Cfg field `horizon_list=100,500,1000,5000,20000` (CSV). Training loop
iterates horizons, trains N models in parallel via #1's machinery.
Inference path loads all N models, returns highest-confidence
prediction.

Stamp body: `grid_member_count` field + per-member SHA list (similar
to ensemble design in design-notes line 73-81).

**Files:**
- `CoreFrameworks/ControllerConfig.hpp` — `horizon_list` cfg field
  + parser (CSV → int array)
- `Backtest/BacktestEngine.hpp` — multi-horizon training loop
- `ML_Headers/ModelInference.hpp` — multi-model inference + selection
- `ML_Headers/CoreModelZoo.hpp` — load N models per core role
- `tests/controller_test.cpp` — multi-horizon round-trip

## Test plan

- 6+ tests for grid search (cross-core parity, best-selection,
  triple-split honored)
- 4+ tests for multi-horizon (load N, predict, selection logic)

## Risk register

- Cross-core XGBoost thread-safety: XGBoost was set to `nthread=1`
  for determinism; verify per-core parallelism doesn't break
  reproducibility
- Triple-split data leakage: easy to accidentally include test set
  in selection; add explicit guard

## Verification

- Sweep `xgb_subsample` from 0.5 to 1.0 in 0.1 steps → 6 models
  trained, best identified by val accuracy
- Multi-horizon: train 5 models on `[100, 500, 1000, 5000, 20000]`,
  inference picks highest-confidence per-tick
- Replay-determinism test still passes (within-build, same data →
  same models)
