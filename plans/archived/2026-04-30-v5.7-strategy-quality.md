# v5.7 — Strategy Quality: Why MOM Enters Losing Trades

**Created:** 2026-04-30
**Trigger:** Live paper run on 2026-04-30 showed MOM Core 0 entered
at $76695 (small upward push) in `regime: RANGING` → trade sat at
-0.20% net for 64m, time-exit pending, fees only. Repeated pattern.
**Depends on:** v5.6 (visibility) shipped first — without v5.6
diagnostic readouts you cannot tell wrong-signal from
right-signal-bad-luck.

## Problem statement

Two failure modes observed in live paper:

1. **MOM enters in non-trending regimes.** Core 0 is hardcoded
   `core_0_strategy=momentum` — it fires on every breakout signal
   regardless of regime. In RANGING regimes, breakouts revert.
2. **AUTO resolves to MOM in RANGING regimes.** Live screenshot
   showed `regime: RANGING (0m)` AND `Core 2 AUTO(MOM)` — AUTO is
   supposed to gate MOM behind TRENDING but apparently allowed it.
   Either the regime classifier is wrong, hysteresis is too loose,
   or the regime→strategy map is mis-tuned.

Net effect: **MOM eats fees on small flat trades.** With $1.50 fees
per round-trip on $750 positions = 0.20% drag. MOM's TP is typically
0.7-1.0%, SL 0.5%. In ranging markets where moves are 0.1-0.3%,
trades neither hit TP nor SL — they time-exit at near-zero gross,
leaving fees-only loss.

## Goals

1. Stop MOM from entering when the move can't reasonably make 2×
   round-trip fees plus TP margin
2. Make AUTO's regime → strategy resolution auditable + correct
3. Make Core 0 (and any hardcoded-MOM core) regime-respecting OR
   give the operator a clear cfg path to reroute through AUTO
4. Add per-strategy entry-quality metrics so we can detect this
   regressing again post-fix

## Non-goals

- Change MOM's mathematical contract (still buy-above breakout, still
  stddev-based TP/SL geometry). Tightening filters is in scope;
  rewriting the strategy is not.
- Change other strategies (DIP, EMA, MR, ML). They aren't the
  observed problem.
- Build a backtest grid search over MOM parameters (that's a separate
  optimization workstream — v5.7 is bug-fixing, not optimization).

## Cross-cutting invariants

1. **Regime classifier audit before code changes.** Fix the symptom
   only after confirming the root cause (classifier wrong vs config
   wrong vs MOM filters too loose). Don't tune blindly.
2. **No new entry path** — every MOM-tightening additional check
   integrates into existing `Momentum_BuySignal` / `Momentum_BuildParameters`
   flow, gates via existing `Gate_Zero` / `BUY_BLOCKED` mechanism.
   Visibility (v5.6) renders these naturally.
3. **Per-strategy quality metric must distinguish CAUSE.** "MOM entered
   and lost" must be classifiable into: bad-signal (regime wrong),
   bad-execution (slippage/fees), bad-luck (signal correct, market
   reversed). Without this distinction, v5.7 can't measure success.
4. **Defaults preserve behavior.** Every new cfg field added in this
   plan defaults to a value that reproduces current behavior exactly.
   Operator opts in to v5.7 features by editing cfg, after observing
   v5.7 panel data. No silent behavior flip on upgrade. The CHANGELOG
   notes which defaults SHOULD be flipped after measurement, but ships
   defaults at no-change.
5. **Strategy lifecycle spot-check before Phase 5.** Verify Momentum's
   5-stage lifecycle (`Init`, `Adapt`, `BuildParameters`, `ExitAdjust`,
   `RegimeAdjust`) is fully wired per `STRATEGY_INTERFACE.md` before
   adding filters in `Momentum_BuildParameters`. v5.4.0 restored these
   but spot-check that Momentum specifically isn't a half-wired one.
6. **Production = `use_real_money` OR live-paper engine.** Boot warnings
   referenced as "production mode" mean: `use_real_money == 1` (live)
   OR live-paper `EngineSharded_Run` (`engine_mode == ENGINE_MODE_SHARDED`
   AND not invoked through `BacktestSharded_Run`). Backtest runs through
   the suite never trigger production warnings.

## Phase 0 — Regime classifier audit (no code)

**Goal:** answer "did the regime classifier correctly call the
2026-04-30 paper run as RANGING the whole time, or did it briefly
flip to TRENDING during MOM entries?"

### Method

1. **Replay the health log** — already capturing `cat="regime"` per
   slow-path cycle. Grep for regime transitions during the paper run
   window. Cross-reference timestamps with order_history CSV to find
   what regime was active at each MOM entry moment.
2. **Per-core regime trace** — `RegimeSignals` dump at the moment
   each entry fired. Specifically: `trending_score`, `volatile_score`,
   hysteresis state, and the resolved strategy.
3. **Configured thresholds** — read engine.cfg's regime cutoffs
   (`regime_trending_min_score`, `regime_volatile_min_score`,
   hysteresis-related cfgs) and validate they're sane for the
   current market.

### Output

`DOCS/changelogs/2026-04-30-regime-classifier-audit.md` — one of:

- **PASS** — classifier correctly called RANGING; MOM still entered
  because Core 0 is hardcoded MOM. Fix is config-side: route Core 0
  through AUTO.
- **HYSTERESIS-BUG** — classifier correctly called RANGING but flipped
  to TRENDING briefly during the breakout, MOM entered during the flip,
  classifier returned to RANGING after. Fix: tighten hysteresis or
  add cooldown after flips.
- **CLASSIFIER-BUG** — classifier wrongly called TRENDING when market
  was actually ranging. Fix: revisit `Regime_Classify` thresholds /
  feature inputs.
- **MAP-BUG** — classifier correct, but `REGIME_STRATEGY_TABLE` resolved
  RANGING → MOM erroneously. Fix: cfg / map.

Phases 1-N below depend on which audit outcome lands.

## Phase 1 — v5.7.1 — Per-strategy entry-quality logging (always run)

**Independent of audit outcome — needed for measurement.**

### Pre-req: expose regime scores

`trending_score` and `volatile_score` are currently locals in
`Regime_Classify` (RegimeDetector.hpp:508, 561). Add fields to
`RegimeState`:

```c
int last_trending_score;   // last classification cycle's score
int last_volatile_score;
```

Set inside `Regime_Classify` before return; read by entry-log capture
when a fill happens. Single-source rule preserved (no recomputation).

Persistence: NOT added to ShardedSnapshot (regime state already
re-derives on warmup; scores would be stale if loaded from snapshot).
Initialize to 0 in `Regime_Init`.

Add to health log: `cat="entry"` line emitted on every fill, capturing:

```
{
  ts, core, strategy, resolved_strategy,
  entry_price, tp, sl, qty,
  regime, trending_score, volatile_score, regime_age_sec,
  stddev_pct, ema_sma_spread, short_r2, ror_slope,
  fee_pct, tp_pct, tp_margin_over_floor,
  bg_volume_threshold, current_volume,
  reason: "fired" | "would_have_blocked_X"
}
```

Add to health log: `cat="exit"` line emitted on every exit, capturing:

```
{
  ts, core, strategy, exit_kind: "tp"|"sl"|"time"|"shutdown"|"ratchet",
  hold_ticks, hold_seconds,
  entry_price, exit_price, gross_bps, net_bps,
  realized_usd, fees_usd
}
```

After ~1 hour of paper trading: a single `jq` pipeline classifies
every trade by (strategy, regime_at_entry, exit_kind, net_bps). This
is the data foundation for everything else in v5.7.

### Single-source rule (carried from v5.6)

Each numeric field reads the SAME variable used in the strategy /
controller / regime path. Don't recompute fee_pct or tp_pct here.

### Tests

`tests/controller_test.cpp` — new section `// === ENTRY_QUALITY ===`:

1. `entry_log_emits_on_fill` — synthesize fill, verify log line
2. `exit_log_emits_on_each_kind` — TP, SL, time-exit, shutdown each
3. `entry_log_captures_regime_at_entry` — verify regime field is the

   be set explicitly in cfg to bypass.

4. Do not auto-overwrite `engine.cfg`. The warning prompts the user.

## Phase 3 — v5.7.3 — Fix-by-audit-outcome (HYSTERESIS-BUG)

**Only run if Phase 0 verdict was HYSTERESIS-BUG.**

Existing infrastructure: `RegimeState.hysteresis_count` /
`hysteresis_threshold` (RegimeDetector.hpp:457-458). The current
hysteresis is "consecutive cycles with same proposed regime."

Phase 0 audit decides whether existing hysteresis just needs tighter
defaults, OR whether a wall-clock dwell gate is also needed:

**Option A (preferred — simpler):** raise `hysteresis_threshold`
default from current value to 8-16 cycles. No new cfg, no new code —
just a default change. Defaults preserve = no behavior flip on
upgrade; user opts in by editing.

**Option B (only if A insufficient):** add wall-clock dwell:

1. Add `regime_min_dwell_ticks` cfg (default 0 = preserve current
   behavior). Once a regime is classified, hold it for at least N
   ticks before allowing classification to flip — orthogonal to
   hysteresis_count which counts consecutive proposals.
2. Add `regime_post_flip_cooldown_ticks` cfg (default 0 = preserve
   current behavior). After a flip from RANGING → TRENDING, no new
   entries from the trending strategy for cooldown_ticks. Confirms
   the flip is sustained before committing capital.

Implementation in `Strategies/RegimeDetector.hpp`. Both gates default
ON (defaults match the values that would have prevented the
2026-04-30 paper run problem).

### Tests

- Synthetic regime-flip burst (TRENDING for 100 ticks → RANGING for
  1000 → TRENDING for 100 → RANGING) — verify only sustained flips
  drive strategy switches, brief flips don't
- min_dwell_ticks=0 (cfg disable) recovers pre-v5.7 behavior

**Commit:** `regime(detector): hysteresis dwell + cooldown (v5.7.3)`
**Tag:** `v5.7.3`

## Phase 4 — v5.7.4 — Fix-by-audit-outcome (CLASSIFIER-BUG / MAP-BUG)

**Only run if Phase 0 verdict was CLASSIFIER or MAP bug.**

Currently the trending/volatile thresholds are HARDCODED in
`Regime_Classify`:
- Line 578: `if (trending_score >= 2 && ...)` — TRENDING gate
- Line 587: `else if (volatile_score >= 2 && ...)` — VOLATILE gate

To enable safe tuning, expose as cfg fields with defaults preserving
current behavior:

```c
int regime_trending_min_score;  // default 2 (= current hardcoded)
int regime_volatile_min_score;  // default 2 (= current hardcoded)
```

Then audit-driven tuning is a cfg edit, not a code change. Preserves
v5.7 invariant #4 (defaults preserve behavior).

Other possible audit-driven scope:

- Add new `RegimeSignals` term to discriminate (e.g. require
  short_r2 > threshold AND ror_slope > threshold for TRENDING, not
  just one).  **Train-serve drift risk** — `RegimeSignals` is consumed
  by ML pack; verify no drift before changing the struct.
- Update `REGIME_STRATEGY_TABLE` defaults (the regime → strategy
  table at `StrategyInterface.hpp:101`).

Effort 2-6h depending on bug. Tests: synthetic regime cases that
matched the bug, verify post-fix classification.

## Phase 5 — v5.7.5 — MOM-tightening (regardless of audit outcome)

**Defensive depth.** Even if the regime side is fixed, MOM should
self-gate against marginal entries.

### Filters to add

All implemented inside `Momentum_BuySignal` / `Momentum_BuildParameters`,
all gated via `BUY_BLOCKED` flag (so v5.6 visibility surfaces them).
**All defaults preserve current behavior (filter off / threshold of 0)**
so upgrade is silent. Operator opts in after observing v5.7 panel
data.

1. **Min profit margin filter (NEW SHALT_*)**
   - Require `tp_pct >= cfg.momentum_min_tp_margin_pct`
   - Default: **0.0** (filter off — preserves current behavior)
   - Recommended-after-measurement: 0.40% (CHANGELOG note only)
   - Below that → BUY_BLOCKED with `strategy_halt_reason = SHALT_MOM_TP_TOO_TIGHT`
   - Rationale: MOM trades that don't have at least 0.4% headroom
     can't survive fees + slippage in flat markets

2. **Recent reversion filter**
   - Require last_n_ticks volume_delta > 0 (trade flow agrees with
     direction). Reject if recent flow is opposing the breakout.
   - cfg: `momentum_min_buy_delta_recent`
   - Default: **0.0** (filter off)
   - Recommended-after-measurement: 0.05
   - SHALT code: `SHALT_MOM_NO_FLOW`

3. **R² minimum**
   - Require short-window R² above `cfg.momentum_min_r2`
   - Default: **0.0** (filter off)
   - Recommended-after-measurement: 0.30
   - Below → BUY_BLOCKED, SHALT code: `SHALT_MOM_LOW_R2`
   - Rationale: low R² = noisy data = breakout is probably noise

4. **Spacing-aware**
   - MOM already respects controller-side spacing, but tighten for
     MOM specifically: require last_entry was a TP (winner), not SL
     or time-exit. Avoids re-entering after the strategy just
     demonstrated it can't read the regime.
   - cfg: `momentum_require_last_win`
   - Default: **0** (filter off)
   - Recommended-after-measurement: 0 (off — too aggressive in
     general, only enable in operator-known specific scenarios)
   - SHALT code: `SHALT_MOM_LAST_LOST`

All four filters individually cfg-toggleable. All four emit a
SHALT_MOM_* code visible in the v5.6 GUI. Defaults preserve current
behavior; CHANGELOG includes a "tuning recipe" doc with recommended
values per market regime, but ships defaults at no-change.

### Tests

`tests/controller_test.cpp` — new section `// === MOM_QUALITY ===`:

- One test per filter: synthesize the failing condition, verify
  BUY_BLOCKED + correct SHALT code
- Composite: synthesize a low-quality breakout that fails all four
  filters, verify all four codes (or document which one wins —
  decide upfront)

**Commit:** `strategies(momentum): quality filters + SHALT codes (v5.7.5)`
**Tag:** `v5.7.5`

## Phase 6 — v5.7.6 — Per-strategy quality dashboard panel

**Read approach: JSONL with explicit per-line newline+fsync.** The
shmem aggregator alternative is deferred to v5.8 if/when JSONL parse
load becomes measurable. JSONL is more debuggable (operator can grep
the raw file) and reuses the existing health log pipeline. The tradeoff
is parse cost on each refresh; mitigated by:
- Background thread (not render thread)
- Append-only read (track last byte offset, only re-parse new tail)
- 5s refresh cadence (not per-frame)
- Resource cleanup: thread joined on shutdown via existing
  `cancel_flag`; file handle closed in destructor

**Read-only panel.** New "Strategy Quality" panel in GUI showing
per-strategy aggregates from health.jsonl entry/exit records:
