# E.1.2.D — the training + model-artifact surface

**Origin (2026-08-21, Caramel):** *"changing that drop down mid training changes how the model gets
labeled"* · *"we have major issues with how the models get saved"* · *"is this a anti pattern we have
or should update with"*. Three i-class scans fired at her direction; ~30 findings; full digest in
`reports_dir`.

## Why this is a ship and not a punch-list

Every other surface in this codebase — registry, wire-format, cfg-flow, snapshot — carries a
RECURRING_BUG_PATTERNS class, a DESIGN_SPEC, and a CI guard. **The model-artifact surface carries
none of the three, and H21 covers no path form and no role filename.** That is the mechanism behind
every finding below: nothing was watching, so defects accumulated silently for months. Fixing the
instances without closing the gap guarantees a fourth scan next quarter.

### Leaf 4b — the ENTRY-POINT miss (2026-08-22, found by the Stage-6.5.4 adversarial review)

Leaf 4 enumerated the four **consumers** of the hyperparameters and unified them. It never
enumerated the **entry points** into that unified path, and there were three:

| entry point | state after `f99e102` | after 4b |
|---|---|---|
| `mh_run_one_horizon_fv` (multi-horizon **Train**) | ✅ wired | ✅ |
| `fullvalidation_worker_fn` (**Run Full Validation** button) | ❌ **unwired — still measured 6/0.1/200 AND overwrote the target's signed stamp with them** | ✅ wired |
| `walkforward_worker_fn` (standalone **Walk-Forward** button) | ❌ unwired, and read six fields LIVE off `state->` (it had NO snap block at all — S1-F6) | ✅ wired + snap block added |

The `= nullptr` default that makes `hp_override` safe for un-updated callers is exactly what made
the omission silent: no compile error, no warning. **The generalizable proxy, now recorded as the
close-ritual candidate:** for any parameter threaded through a call chain, grep the callee across
all roots and assert EVERY production caller passes the new argument. This is `AR-20` turned inward
on a fix's own reach, stacked on `AR-19` (a sweep scoped by the previous edit rather than by tracing
the subject) — and it is the third consecutive close at which a quantifier in a handoff outran its
measured set.

### Leaf 4 in detail — what it was, and what the fix actually is

**The four configurations, measured:**

| Consumer | Trained/recorded at | Source |
|---|---|---|
| the SHIPPED model | the operator's panel values (`2 / 0.050 / 350`) | 8 LIVE `state->` reads from a worker thread |
| the walk-forward folds | `6 / 0.1 / 200` + 4 cfg overrides | `XGBHyperparams_Defaults()` + `eff_cfg` |
| the held-out model | pure `6 / 0.1 / 200 / 0.8 / 0.8 / 5 / 42` | `XGBHyperparams_Defaults()`, **no overrides at all** |
| the STAMP | `6 / 0.1 / 200` | the same hardcoded defaults |

So the operator's tuning loop was **open**: hyperparameter changes could not appear in the numbers
used to judge them, and — the reason it survived — **no artifact on disk could contradict the stamp,
because the stamp came from the same defaults the validation used.** The held-out figure, which is
the one gating deployment, described a model nobody trained and nobody shipped.

**Fix shape (deliberately NOT the first one attempted):** the obvious route — add the three missing
hyperparams to `ControllerConfig` so `config_used` carries them — was BUILT and REVERTED. A guard
caught it: `ControllerConfig` is RAW-fingerprinted into the model stamp (H9/H12, D-254), so growing
it shifts every cfg fingerprint. Perturbing a fingerprinted struct for a training-time convenience
is the wrong trade. The landed shape instead threads one `const tt::XGBHyperparams *hp_override`
(default `nullptr` = previous behaviour bytewise) through `Backtest_RunFullValidation` →
`Backtest_RunWalkForward` + `HeldOutSplit_TrainEval`, and the worker builds it ONCE from the
click-time snaps.

**It also closes S1-F1 for free**, because the same snapshot replaces the eight live `state->` reads:
those snaps had been populated in `MultiHorizonWorkerArgs` since v5.11.41 and read by NOTHING — the
Class-13 sub-shape *"snap block complete, consumer bypasses it"*. The parallel path needed the
snapshot on `MultiHorizonParallelJob` too, since its worker cannot reach the outer scope.
`summary.txt`'s hyperparam lines were a SECOND live read minutes after the first, so an edit in
between made the summary disagree with the model beside it; they now report the snapshot.

**Acceptance oracle — PARTIAL, stated not implied.** `C.3k` pins the shared fallback
(`XGBHyperparams_Defaults()` = 6/0.1/200/0.8/0.8/5/42) so a silent change to it moves all three
fallback sites at once. The plumbing that carries the operator's snapshot into those sites needs
XGBoost + real data to exercise and is **dogfood-verified, not pinned**: train one horizon, then
grep the emitted `.stamp` for the operator's values instead of `6 / 0.1 / 200`. Suite 3879 → 3888
(+9 = C.3k exactly), both TUs build, cache-layout strict-new rc=0 / 0 NEW, H21 GREEN at 92,
calls-graph CLEAN.

**CORRECTED 2026-08-22 (scan-1 NEW-1):** "four configurations collapse to one" was true for 7 of 8 axes — WF + held-out hardcoded `n_rounds = 200` and ignored the snapped `n_estimators`, so the gating metrics still measured 200-tree models while ship+stamp used the operator's count; bytewise invisible at defaults (Defaults().n_estimators == 200). Both sites now consume `hp.n_estimators` (fixed same day).

**Operator consequence:** every metric on every existing model describes a 6/0.1/200 architecture.
After this lands, re-run Run Full Validation on `twins` to get honest numbers for the deployed
2/0.050/350 model — no retraining needed, RFV does not save a model.
