When fanning out multiple agents for an audit / decision / pre-coding arming, label them by ROLE with Caramel's shorthand: **A-class = ADVERSARIAL** (prompted to FIND / REFUTE / prove-wrong, default-refuted — the [[feedback_adversarial_framing_default_for_checks]] framing) and **I-class = INVESTIGATIVE** (map the surface: the complete write-set, the options, the seams, the blast-radius — the `/finding-analyzer` framing). Use these labels in each agent's `label`/`description` and in the synthesis (I-1, I-2, A-1, A-2, …) so a fan-out is terse to specify and the report reads at a glance.

**Why:** operator-stated preference (2026-06-14) — *"refer to adversarial as A-class and investigative as I-class for easier fan-outs."* The two roles are the two halves of the canonical investigate→refute gate; naming the ROLE (not the underlying skill) is what matters — an I-class agent might run `/accounting-audit` or `/hft-audit`; an A-class agent might run `/bug-check` or a 3-lens refute. Borne out the F-059 arming (2026-06-14): I-class mapped the write-set + exit-trigger; A-class REFUTED and caught that the planned seams were wrong-path and that the test would largely duplicate existing coverage — a confirmatory pass would have missed both.

**How to apply:** (1) An I-class agent MAPS (no grading) — armed per M8 ([[feedback_define_done_and_arm_scout_subagents]]: refs + toolchain + nav-infra + domain skill + a **dependency/blast-radius trace of its surface** — `/dependency-chain-trace`+`/trace-deps`: what it touches DOWNSTREAM + where data flows IN; STANDARD for BOTH I- and A-class per the methodology § The pattern step 3, operator-directed 2026-06-14), then scouts the surface. (2) An A-class agent REFUTES — same arming, prompted to break the I-class conclusion / the proposal, default-refuted, never grading its own work ([[feedback_independence_for_judgment_not_mechanical]]). (3) Run ≥1 of each for a capital/determinism keystone; their DISAGREEMENT is signal → the orchestrator resolves by code-read (AR-11), never by fiat. **Existing skills that ARE this pattern:** `/decision-check` (one I → one A, a single DECISION; the lightweight gate) and `/precoding-audit-gate` (parallel multi-skill fan-out against a PLAN; the heavyweight gate). An I+A fan-out to ARM a coding keystone (e.g. F-059) is `/precoding-audit-gate`-shaped but task/keystone-scoped. Canonical methodology body: `adversarial-multi-agent-audit-methodology.md`.

**Two meanings of "cascade" — disambiguate when specifying a fan-out:** (a) a STAGED I→A pipeline — I-class designs/maps on the corrected shape → A-class refutes that design (the sharper successor to a parallel discovery pass; what the F-059 fan-out was). (b) a dependency / blast-radius **cascade audit** — trace how a change impacts UP- and DOWN-stream: the `/dependency-chain-trace` (flow-trace: read/write sites + lifecycle + cohort siblings + blast radius) / `/trace-deps` / `/finding-analyzer` family. Different tools for different questions — *how do I verify+design this change?* (a) vs *what does this change touch?* (b). Name which you mean. Re-running (a) when the supplied shape proves wrong → [[feedback_recascade_audit_on_corrected_shape]].
