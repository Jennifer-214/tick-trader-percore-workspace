## How I resolved the 2 reconciliations

**(1) Cluster/node hierarchy — EARLY (foundational) or LATE (framework)? → SPLIT IT (the answer is BOTH, cleanly separated).**
D-15/D-28 say the hierarchy IS foundational data layout (the container nodes live in); the v0.1 plan + working-draft-8 lumped it with the FOREACH_EXCHANGE framework into one late E.1.6. The §4-caveat-5 explicitly flags this: *distinguish FOUNDATIONAL layout that only LOOKS like framework.* My resolution: **the structural CONTAINER (`ClusterState` + the Deployment→Cluster→Node layout + NodeState.binding) is E.1.6, sequenced EARLY-among-the-data-layers** (right after the capital gate, before the additive framework); **the FOREACH_EXCHANGE adapter-FRAMEWORK is E.1.7, last.** The discriminator is data-layout (container, foundational, early) vs additive-registry (framework, deferrable, late) — exactly cut-line-principles 3 vs 5. This is why N=9 not 8: the split is correctness-load-bearing because E.1.4's aggregator already indexes `binding.cluster_id`, so the container must exist as real layout before/around the gate, while the adapter dispatch genuinely can follow.

**(2) E.1.1-rename ↔ E.1.2-relayout ordering (avoid touching the struct twice).**
D-101 says numeric-core-final-before-rename — already satisfied (Ship-A/B made Position Money-typed; the currency floor confirms it). So the remaining "touch twice" risk is: rename touches the struct's NAME (`CoreContext`→`NodeState`); relayout touches its BYTES (AoS→SoA + `owner_node_id` + VERSION bump). My resolution: **rename FIRST (E.1.1, name-only, layout frozen), relayout SECOND (E.1.2, bytes-only, name frozen)** — the two touches are ORTHOGONAL (identifiers vs byte-offsets) and ORDERED under SEPARATE anchors, so neither is "the same edit done twice." Doing layout first would force the rename to chase a moving struct; doing them together is the un-bisectable v0.1 monolith. The struct-cascade-impact tool (TD-175) is built in E.1.1 to drive the rename enumeration, then RE-USED in E.1.2 to drive the byte-cascade (composition + byte-context) — one tool, two ordered applications, no double-touch. Sequencing rationale = cut-line-principle-3 (data-layout before consumers) applied at the struct's own internal granularity: name-binding is a "consumer" of the type, byte-layout is the "data" — but since the rename must precede consumers AND the layout, the clean order is rename→relayout→consumers(E.1.3+).

## Weakest cut (self-adversarial) + where by-layer is SUBOPTIMAL vs by-spine

**Weakest cut: the E.1.4 / E.1.6 boundary (capital-gate vs container-layout ordering).** I placed the GLOBAL aggregator (E.1.4) BEFORE the ClusterState container (E.1.6), but the aggregator's per-cluster running-aggregate + per-cluster kill flags INDEX `binding.cluster_id` and a `per_cluster[NUM_EXCHANGES]` array — which is exactly ClusterState territory. An A-class agent will rightly ask: *how does E.1.4 aggregate per-cluster before the cluster container exists?* My defense is that E.1.4 needs only the cluster_id as an INDEX (a `uint32_t` on NodeState.binding) + a flat `per_cluster[]` aggregate array — NOT the full ClusterState (producer/adapter/WS threads), which is genuinely later. But this is a real coupling: the minimal `binding.cluster_id` + the `per_cluster[]` slot arguably belong in E.1.2's layout (with NodeState) or a thin pre-E.1.4 container stub, making E.1.6 purely the per-cluster THREADS. **If the A-class pushes, the fix is to move `binding.cluster_id` + the flat per-cluster aggregate slots into E.1.2 (data-layout) and reduce E.1.6 to the cluster-shared-THREADS only** — which actually strengthens the by-layer purity. I flag this as the most likely amendment.

**Where by-layer is SUBOPTIMAL vs by-spine (the D-214 three spines: fill-completeness / cross-thread-coherence / per-node-purity).** The by-layer cut SCATTERS the three capital-correctness spines across E.1.3 (per-node-purity, via absorption) + E.1.4 (cross-thread-coherence, via the aggregator/torn-read) + E.1.5 (fill-completeness, via the real handler). A by-spine cut would instead make each SPINE one ship — keeping each correctness-proof self-contained and letting the operator verify "the fill spine is complete" as a single reviewable unit, rather than tracking a spine's delivery across three layer-ships' outbound seams. By-spine is SUPERIOR for **verification locality of the capital-correctness argument** (the thing that gates real money): the three spines are the actual safety case, and by-layer fragments that case across thread/aggregator/fill boundaries. The by-layer counter-argument is **rollback granularity + dependency-honesty**: the spines have a hard delivery ORDER (per-node-purity must precede coherence must precede fill-completeness — a node must own its state before its cross-thread reads can be made coherent before its fills can be reassembled), and by-layer makes that order the ship order with one bisectable anchor each, whereas a by-spine ship would internally re-introduce the layer-mixing (a "fill spine" ship still touches topology + aggregator + handler together → the un-bisectable monolith returns at spine granularity). **Net: by-layer wins for bisectability + rollback + honest dependency-ordering; by-spine wins for the verification locality of the safety case. The synthesis the orchestrator should weigh: keep by-layer's ORDER but add a per-spine ACCEPTANCE-CRITERION thread that the rolling-window seam (D-72) verifies converges at E.1.5 close — get both.**
