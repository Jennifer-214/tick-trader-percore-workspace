## CRITICAL findings (RED gate, blocking)

### CRITICAL-1: Symbol axis migration is on the wrong struct (parity + trace-deps convergent)

**The error:** Plan says `cfg.symbol` migrates to `cfg.cores[c].symbol`. But `symbol` does NOT live on `ControllerConfig<F>` — it's on `BinanceConfig` at `DataStream/BinanceCrypto.hpp:64` (live engine) and on `BacktestCfg` (backtest path).

Plus: `KIND_STRING` infrastructure doesn't ship until `.F.4e` per `CoreFrameworks/CfgFieldRegistry.hpp:22`. The per-core registry can't hold string-typed rows at `.F.4c.3`.

**Resolution:** **DEFER symbol axis to `.F.4e`** when `KIND_STRING` + `KIND_FILE_PATH` infra lands. Remove from `.F.4c.3` scope. Document the defer in cfg-scope-discipline.md and the plan body.

### CRITICAL-2: A2 bitmap-bool migration underspecified (parity + dod convergent)

**Three gaps:**
- (a) **Bit count off-by-one** — plan says 12 bits; audit found **13** in `ML_Headers/MlCfgFlagRegistry.hpp:52-64` (CONFIDENCE_ENABLED + LAZY_REBUILD_ENABLED + USE_EXIT_MODEL + RIDGE_WITHIN_HORIZON + RIDGE_ACROSS_HORIZONS + FOXML_VOL_SCALING_ENABLED + BANDIT_ENABLED + EXIT_BANDIT_ENABLED + CONFIDENCE_COMPOSITE_ENABLED + EXIT_BLENDER_MODE + PER_HORIZON_BARRIER_BLEND + RIDGE_ONLINE_CORR + ... = 13)
- (b) **Row order lock** — A2 rebuild walker must reconstruct the bitmap with bit positions anchored to `FOREACH_ML_CFG_FLAG` enum ordinals (compile-time constants from each row's metadata), NOT iteration order. Without explicit lock, wire bytes silently swap if row declaration order shifts.
- (c) **4 stamp-emit-via-BITMAP_BIT rows** at `ML_Headers/StampBoundCfgRegistry.hpp:106-146` use `HANDLE_STAMP_EMIT_BITMAP_BIT` with ternary normalization. Migration timing decision: (i) handle at `.F.4c.3` (extend A2 to cover stamp-emit path) OR (ii) defer to `.F.4d` (let the wire-format framework handle the bitmap-bit emit pattern).

**Resolution:** Plan body needs explicit specification of A2 mechanism — bit count, row-order anchor, stamp-emit-via-BITMAP_BIT migration timing. Operator decision required.

## HIGH findings (resolve before coding; ~30 min plan edit each)

### HIGH-1: `_BuildParameters` strategy fn signatures (trace-deps)

4 strategy fns (`SimpleDip_BuildParameters`, `MR_BuildParameters`, `EmaCross_BuildParameters`, ML branches) take `const ControllerConfig<F>* config` and read `config->take_profit_pct` etc. at 11 critical sites in `Strategies/StrategyParameters.hpp:326-1794`. Post-split those fields disappear from `ControllerConfig<F>`.

Plan section H is silent on whether sigs change. Three options:
- **Option A (recommended per boundary-stable rule):** sig changes to `const PerCoreCfg<F>* core_cfg` — call sites pass `&cfg.cores[c]`
- **Option B:** sig keeps `const ControllerConfig<F>* config` + adds `int core_idx` param — call sites pass `(cfg, c)`; body does `cfg->cores[core_idx].field`
- **Option C:** the 4 strategy fns get a wrapping helper `BuildStrategyParameters(cfg, core_idx)` that resolves the per-core slice + delegates

Option A is cleanest + matches the per-core slice reference convention from `/merge-scan` F2.

### HIGH-2: Existing per-core arrays in `ControllerConfig<F>` not classified (trace-deps + merge-scan)

`ControllerConfig<F>` ALREADY has `core_strategies[16]` (line 971), `core_strategies_explicit_set` (line 972, partner-bitmap), `core_risk_pct[16]` (line 989), plus 5 string arrays at lines 1008-1029 (`core_model_path`, `core_model_dir`, `core_horizon_list`, `core_ensemble_blend_mode`, `core_disabled_horizons`).

Plan Section B handles strings explicitly (defer to `.F.4e`) but is silent on FPN/uint8 arrays. Per /merge-scan F3 cohort completeness rule: these are siblings of fields the plan migrates — must classify as in-cohort OR explicitly preserve.

**Resolution:** Collapse `core_strategies[16]` → `cores[c].strategy` (KIND_INT_ENUM row in per-core registry). Collapse `core_risk_pct[16]` → `cores[c].risk_pct` (already in scope per plan section A; verify deduplication). Strings stay manual at `.F.4c.3`; migrate at `.F.4e` with the string-cfg cohort.

### HIGH-3: Test fixture migration count undercount 4-5× (parity)

Plan says ~50-100 sites. Actual: **414 `cfg.<field>=` writes in `controller_test.cpp`** + 32 production read sites in ML_Headers + Strategies + CoreFrameworks.

Realistic effort: 8-12 hr migration + 4-6 hr audit. This is NOT blocking but plan needs honest revision.

**Resolution:** Update plan Section I + Step 7 LOC estimate from "~200 LOC" to "~400-500 LOC across ~414 sites + ~32 production sites." Add note: "Mechanical via grep + sed; centralized test-setup helper at `controller_test_init_cfg_for_core_zero(cfg)` proposed per /merge-scan F8 to concentrate future test-cfg-init in one place."

### HIGH-4: `STAMP_CFG_AUTOPOPULATE` + `INFERENCE_CFG_AUTOPOPULATE` macro adapter (parity)

These macros at `ML_Headers/StampBoundCfgRegistry.hpp:223` + `MemHeaders/CfgDerivedInferenceCfgRegistry.hpp:141` require caller variables named exactly `inf` and `cfg`. Per-core dispatch needs aliasing.

**Resolution:** Plan adds adapter snippet: each per-core stamp emit creates a local alias `const auto& cfg = global_cfg.cores[core_idx];` before invoking the macro. Or extend macros to parameterize the cfg-source. Decision at audit gate.
