### [HIGH] `oms-ts-2` — No test cross-checks sum(core_realized)==oms->realized_pnl or sum(core_fees)==oms->total_fees — two independent net-P&L derivations on the money path are never reconciled
*verified* · section `oms-money` · fix: .E.5 (sub-accounts) — the reconciliation invariant is foundational for per-account ledgers; add the cross-check test as part of .E.5 scope. Also valuable standalone before paper-test.
- **Where:** Two independent derivations: (1) handle_sell_fill OrderManager.hpp:1186-1194 -> oms->realized_pnl/oms->balance/total_fees via OrderManager_AccountMakerTakerFee; (2) EventLoop_DrainPostFillOneCore ControllerEventLoop.hpp:1522-1538 -> ctx.core_realized/ctx.core_fees (re-derives gross=exit_notional-entry_notional, exit_total_fees=pos.entry_fee+last_exit_fee[slot]). Grep for any test relating core_realized to realized_pnl / core_fees to total_fees returns ZERO matches.
- **What:** The production money path computes each closed trade's net P&L and fees TWICE from partially-overlapping state: handle_sell_fill computes net from snapshotted entry_fee+exit_fee and updates the OMS-global oms->realized_pnl/oms->total_fees; DrainPostFillOneCore independently recomputes exit_net_pnl from Position.entry_fee + oms->last_exit_fee[slot] and updates per-core ctx.core_realized/ctx.core_fees. No test asserts these two views agree (sum over cores of core_realized == oms->realized_pnl; sum of core_fees == oms->total_fees). The mode-1 test checks ctx fields only; the round-trip test checks oms fields only; nothing bridges them.
- **Why:** If the two derivations drift — e.g., last_exit_fee[slot] is stale/overwritten by a same-slot reopen, or Position.entry_fee differs from the entry_fee handle_buy_fill actually charged, or a saturating-add (FPN_AddSat in core_fees vs FPN_Add in oms math) diverges at scale — the per-core dashboard P&L and the account balance silently disagree. This is precisely the reconciliation invariant .E.5 sub-accounts will depend on (per-account PnL MUST sum to global). A divergence here is undetectable today.
- **⚠ Don't carry forward (.E.1 rewrite):** During the .E.1 core->node rewrite, keep the two derivations structurally distinct ONLY if a test pins their equality. Do not let the rename silently change which fee/notional field either side reads without the reconciliation test in place.
- **Test to add:** After any multi-core round-trip drive (e.g., extend the mode-1 test at 7656), add: assert fabs(sum_c FPN_ToDouble(state.cores[c].core_realized) - FPN_ToDouble(oms->realized_pnl)) < 1e-6 and fabs(sum_c core_fees - oms->total_fees) < 1e-6. Run with both partials on and off, and with at least one losing leg.
- **Anti-pattern:** Same money quantity derived independently in two code paths (global accumulator vs per-shard accumulator) with no test asserting the two agree.

### [MEDIUM] `live-12` — Rate-limit weight (X-MBX-USED-WEIGHT-1m) parsed and stored but never used to proactively throttle — only reactive 429/418 handling
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `live-binance` · fix: .E.5 (per-cluster rate budget — E-MASTER explicitly lists 'per-cluster rate budget' under the multi-exchange substrate; the proactive throttle belongs there).
- **Where:** DataStream/BinanceOrderAPI.hpp: rate_limit_weight field (~line 101); populated from header in binance_rest_request (api->rate_limit_weight = atoi(weight_hdr+22), ~line 380); read ONLY for logging in binance_retry_request 429/418 branch (~line 471) and BinanceAdapter.hpp error_message (~line 224). No site compares it against a budget threshold to pre-emptively pause/slow submissions.
- **What:** The engine reads Binance's used-weight header on every response and stores it, but never acts on it. The only rate-limit handling is reactive: after a 429/418 is returned, binance_retry_request waits delays[attempt]+5s and retries. There is no proactive throttle that slows or defers order/reconcile/balance REST calls as the used-weight approaches the 1-minute cap. Under burst conditions (force-close flattening many slots, reconcile fetching account+openOrders+myTrades, periodic ReconciliationLoop polling, plus order submits) the weight can climb into a 418 IP-ban, which on production Binance escalates to multi-minute/hour bans — during which the engine cannot place exits.
- **Why:** For an HFT engine that can burst REST traffic (flatten-all, boot reconcile, periodic poll), reactive-only rate limiting risks a 418 ban precisely when the engine most needs to act (e.g., flattening on a kill-switch). The data to prevent this is already collected (rate_limit_weight) but unused. Severity = MEDIUM: not a guaranteed failure, but a latent live-availability hazard with the fix-enabling signal already in hand.
- **⚠ Don't carry forward (.E.1 rewrite):** When .E.5 adds a per-cluster rate budget, wire the already-parsed used-weight into a pre-submit gate (defer/slow when weight > soft cap) rather than leaving it logging-only. Do NOT carry forward a parsed-but-ignored rate signal.
- **Test to add:** Add a test that simulates rising used-weight responses and asserts the submit path begins deferring/pacing before the cap; none exists.
- **Anti-pattern:** Telemetry value parsed and stored on every response but never consumed by any control decision (collected signal with no feedback loop).

### [MEDIUM] `oms-bc-3` — Order_BindPreResolved fixes pre_resolved.fee_rate at SUBMIT using is_maker=0, but real is_maker is set at FILL with no re-bind -> maker fills booked at TAKER rate while counted in the maker bucket (latent; bites future maker path)
*verified* · section `oms-money` · fix: .E.5 (sub-accounts) or whenever the maker path (TECH_DEBT-008) activates — store BOTH maker_rate and taker_rate in OrderPreResolved (or re-resolve fee_rate after Order_SetIsMaker, before HandleFill), so fee uses the rate matching the realized is_maker
- **Where:** CoreFrameworks/Order.hpp:356-364 Order_BindPreResolved reads is_maker (Order_GetIsMaker) which is 0 at submit (Order_Init sets is_maker=0; CoreFrameworks/OrderManager.hpp:980 calls Order_BindPreResolved during Submit before any fill). Real flag set later at CoreFrameworks/OrderManager.hpp:1354 Order_SetIsMaker(o, cmd.result.is_maker) in OrderManager_ProcessFillCommand — AFTER pre_resolved is bound, with NO subsequent Order_BindPreResolved/re-resolve. Consumed in handle_buy_fill (OrderManager.hpp:1143-1145) and handle_sell_fill (OrderManager.hpp:1188-1190): fee = notional * o->pre_resolved.fee_rate (taker rate), then OrderManager_AccountMakerTakerFee(oms, Order_GetIsMaker(o), fee) buckets by the post-fill flag.
- **What:** pre_resolved.fee_rate is decision-time-bound at submit to `is_maker ? maker_rate : taker_rate`, but is_maker is necessarily false at submit (MARKET orders, and LIMIT maker-ness isn't known until the exchange reports it). When a fill later reports is_maker=true, the fee is still computed from the taker-bound pre_resolved.fee_rate, yet AccountMakerTakerFee routes that amount into total_maker_fees / maker_fills_count. So a maker fill is charged the taker rate AND categorized as maker.
- **Why:** Latent on the current engine (MARKET-only, is_maker always 0 -> taker rate, taker bucket -> correct), but it is a real correctness inversion the moment any maker fill occurs (the deferred LIMIT/POST_ONLY path per TECH_DEBT-008, or any executionReport with maker=true). It silently corrupts both the fee AMOUNT (taker > maker typically) and the maker/taker breakdown, defeating the `total_fees == total_maker_fees + total_taker_fees` invariant's usefulness for reconciliation. Distinct from Class 29: Class 29 ensures pre_resolved is BOUND; here it is bound but to the WRONG rate because the maker/taker discriminant is unknown at bind time.
- **⚠ Don't carry forward (.E.1 rewrite):** At .E.1/.E.5, do not assume pre_resolved.fee_rate is correct for maker fills. The decision-time-binding pattern must carry maker_rate AND taker_rate (or re-resolve on the executionReport), since is_maker is a FILL-time fact, not a submit-time one. Add a static comment / assert that pre_resolved.fee_rate is taker-only until the maker path lands.
- **CI check:** Static check: flag any pre_resolved/decision-time bind that branches on a field (is_maker) which is mutated by a known LATER-stage setter (Order_SetIsMaker) on the same object, without a re-resolve between the setter and the consumer.
- **Test to add:** Add a test that constructs an Order, binds pre_resolved with distinct maker_rate != taker_rate, sets is_maker=true post-bind (simulating a maker executionReport), runs HandleFill, and asserts the booked fee equals notional*maker_rate and lands in total_maker_fees. Today it would book notional*taker_rate into the maker bucket.
- **Anti-pattern:** Decision-time pre-binding of a value whose selector is not actually known at decision time (binding fee_rate by is_maker at submit when maker-ness is only determined at fill) — the pre-resolved cache is bound to a placeholder discriminant.

### [MEDIUM] `oms-money-blindspot-2` — Per-core ezoo_refs[]/core_cfg_refs[] telemetry indexed by Order::core_id, but under partials core_id carries the portfolio slot (2*core+leg) — wrong-core / null telemetry
*verified* · section `oms-money` · fix: standalone (same focused ship as oms-money-blindspot-1, since both are .F.4d Step 7 calib telemetry); the index-domain fix should land before .E.5 sub-accounts adds more per-core/per-account telemetry surfaces

- **What:** ezoo_refs[] and core_cfg_refs[] (MAX_EXECUTION_CORES=16) are wired at boot by CORE INDEX i. The calib emit indexes them by oms->ezoo_refs[(int)o->core_id]. - **CI check:** Extend check_per_core_registry_integrity.py: flag any read of an array sized [MAX_EXECUTION_CORES] indexed by an Order/Position field that is set from a Sharded_LegSlot()/portfolio-slot expression at any construction site (slot-vs-core index-domain mismatch detector).
- **Test to add:** Add a partials-enabled (partial_exit_enabled=1, >=2 cores) end-to-end calib test that exits a position on core c>=1 leg A and asserts the calib row's thompson telemetry came from core c (not slot 2c).
