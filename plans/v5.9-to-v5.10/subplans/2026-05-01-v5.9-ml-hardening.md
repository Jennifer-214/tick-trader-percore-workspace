# v5.9 — ML Hardening: train-serve parity, observability, prevention

**Date:** 2026-05-01
**Theme:** close the silent-failure gaps in the ML pipeline that the
v5.8 paper-testing pass surfaced, and add process guardrails so the
same bug-classes can't recur.
**Pre-req:** v5.8.10 shipped (last tag on `feat/v5.8-easy-additions`).
**Branch:** `feat/v5.9-ml-hardening` from `feat/v5.8-easy-additions`
(or `main` after that branch merges).

This is a quality sprint, not a feature sprint. Most ships add no
operator-visible new behavior — they make existing behavior
observable, validated, and harder to break.

---

## Why now

v5.8 paper testing surfaced a recurring pattern: **the ML pipeline
has multiple "wired but unobserved" code paths.** Things compile,
tests pass, but in operator workflows the wiring either doesn't
fire (auto-stamp UI gap, registry-hash check dormant) or fires but
silently degrades to a fallback (model load failure → SimpleDip).

Plus the audit pass exposed a meta-issue: an automated audit can
produce a false CRITICAL when the codebase has forward-compat dead
code (the unused FeatureComputeCtx auxiliary fields). Removing that
ambiguity helps both human and tool readers.

Three classes of issue this plan targets:

1. **Silent failures** — code paths that fail without operator-
   visible signal (model load, NaN feature, warmup gate, default-
   to-DIP cfg).
2. **Train-serve parity** — places where train and serve paths
   could diverge silently. v5.8.6 added structural protection via
   `feature_registry_hash`, but the regression test only covers
   one input shape.
3. **Prevention layer** — process changes (invariants doc, end-to-end
   recipes, regression-test fixtures) that catch *future* issues at
   plan-time or PR-time rather than paper-test time.

## Phase 1 — Visibility + immediate guards (v5.9.0, ~11-13h)

The four original HIGH-severity audit findings, the four post-paper-

### Items addressed

**1. NaN/Inf guards FOLDED INTO `Features_PackAll` (audit #4)**

**Resolution (post-readiness 2026-05-01):** Validation lives INSIDE
`Features_PackAll` itself, NOT at 5 caller sites. Single source of
truth. The packer returns -1 on validation failure (instead of the
feature count), and callers branch on the sentinel.

```cpp
// In ML_Headers/FeatureRegistry.hpp:
template <unsigned F>
inline int Features_PackAll(const FeatureComputeCtx<F>* ctx, float* out) {
    int n = 0;
#define X(id, name, version, enabled, fn, note) \
    if ((enabled)) { \
        out[FEATURE_##id] = (float)FPN_ToDouble(fn(ctx)); \
        if (isnan(out[FEATURE_##id]) || isinf(out[FEATURE_##id])) { \
            return -1;  /* sentinel: validation failure */ \
        } \
        ++n; \
    }
    FOREACH_FEATURE(X)
#undef X
    return n;
}
```

Each of the 5 callers gets a one-line branch:
```cpp
int n = Features_PackAll(&ctx, buf);
if (n < 0) {
    // NaN/Inf detected — zero buffer, emit one rate-limited health log,
    // bump per-core nan_feature_events_total. Skip this rebuild cycle.
    memset(buf, 0, MODEL_MAX_FEATURES * sizeof(float));
    HealthLog_Critical_RateLimited(...);
    state->cores[slot].nan_feature_events_total++;
    return /* skip prediction */;
}
```

**Why this design:** Mirrors the v5.8 single-source-of-truth principle.
Adding new validation is one site. The 5 callers each add a 4-line
branch but no validation logic. Per-core counter on EventLoopState
surfaces in TUISnapshot for ML Status panel display.

**2. Silent model-load failure visibility (audit #5)**

`CoreModelZoo_TryLoadRole` already logs to stderr, but the live
engine has no GUI surface. Add:

- Per-core `model_load_failed` flag in CoreContext / EventLoopState

**3. ML entry health logs missing prediction + threshold (audit #17)**

Currently `cat="entry" strat=ml` events log `price`, `qty`, `slot`
but not the model-side decision context. Extend:

- `prediction=` (the value returned by `Model_Predict` /
  `Model_PredictMulti` — for barrier, log all 3 class probs)
- `threshold=` (the `ml_buy_threshold` at decision time, or the

- `confidence=` (when `confidence_enabled=1`, the scorer's value)
- `effective_threshold=` (post-confidence damping)
- `feature_registry_hash=` (current build's hash, for log-time
  attribution if logs are reviewed across builds)

Plumb through `MLBuildContext.out_prediction` + `out_confidence` into
the entry event emit at fill time.

**4. Cfg-source visibility + suite-vs-engine cfg divergence (HIGH, surfaced 2026-05-01)**

The today-bug: foxml_suite reads `backtest.cfg`, live engine reads
`engine.cfg`. Operator sets `core_N_strategy=mr` in engine.cfg but
the suite ignores that file → all cores default to SIMPLE_DIP per
`ControllerConfig_Default` line 847 → no ML inference fires in the
backtest. Silent.

Three sub-fixes:

(a) **Engine header panel displays loaded cfg path.** Both
    engine_gui and foxml_suite show the cfg path they parsed at boot.
    Operator sees at-a-glance: "engine: 5.9.0 | cfg: backtest.cfg |
    registry: fc91...4a40". Mirrors the v5.8.6b engine header pattern.

(b) **Suite warns on legacy cfg.** When foxml_suite parses a cfg
    file that has zero `core_N_strategy=` lines AND `engine_arch=`
    is missing, emit a stderr WARN at boot:
    `[cfg] WARN: backtest.cfg lacks per-core strategy fields. All 4
    cores will default to SIMPLE_DIP. Add core_N_strategy= entries
    to enable other strategies. (Was the cfg meant to be a copy of
    engine.cfg?)`

(c) **Cfg-source comparison panel.** New panel in foxml_suite that
    diffs `backtest.cfg` vs `engine.cfg` (when both exist) and
    surfaces divergent fields. Operator catches "I edited engine.cfg
    but the suite reads backtest.cfg" before training.

**Effort:** ~1h.

**5. Default-vs-deliberate cfg field tracking (HIGH, surfaced 2026-05-01)**

Today: `ControllerConfig_Default` sets `core_strategies[i] = 2`
(SIMPLE_DIP) for all 16 slots. If cfg file is missing
`core_N_strategy=`, defaults silently apply. The "0!"/"1!"/"2!"/"3!"
warning markers in Per-Core P&L panel fire on every non-AUTO core,
including ones that fell to default — operator can't distinguish
"I deliberately set this to DIP" from "cfg was missing this field."

Fix:

(a) **Track explicit-set bitmap in cfg parser.** Each ControllerConfig
    field that has a default gets a parallel `_was_explicit` bit
    (only relevant fields, not all). Set on parse, unset on default.

(b) **Distinguish in TUI.** "0!" indicator becomes "0!" (deliberate)
    vs "0?" (defaulted) vs "0" (auto-regime). Three-state.

(c) **Boot warning on all-default critical fields.** If
    `core_strategies[]` is ALL defaulted (no explicit cfg lines),
    emit a stderr WARN at boot in BOTH suite and live engine.

**Effort:** ~1.5h.

**6. Prediction NaN guard (HIGH, sibling of feature NaN)**

`Features_PackAll` validates feature input (per #1 above), but
`Model_Predict` / `Model_PredictMulti` return raw float — XGBoost
can return NaN on poorly-trained models or pathological inputs.
Currently: if `prediction = NaN`, the gate decision `prediction >
threshold` evaluates false (NaN compares unequal to everything) →
no entry. Silent miss.

Fix: same fold idiom as feature NaN. After `Model_Predict`:

```cpp
double pred = Model_Predict(&zoo->buy_signal, features, n);
if (isnan(pred) || isinf(pred)) {
    state->cores[slot].nan_prediction_events_total++;
    HealthLog_Critical_RateLimited("[ML] core %d: prediction NaN/Inf — skipping", core);
    return;  // no entry; same fall-through as model-not-loaded
}
```

For `Model_PredictMulti` (3-class), check all class probs.

**Effort:** ~30min.

**8. WF purge gap not validated post-generation (audit #10)**

```cpp
for (int i = 0; i < split->n_folds; ++i) {
```

**9. Remove unused `FeatureComputeCtx` aux fields (audit cross-cutting)**

**2. Label function NaN guards (audit #12)**

`Backtest/LabelFunctions.hpp` label generators (especially
`Label_ForwardPnl`) can produce NaN on degenerate inputs. Wrap each
with **per-type neutral-default handling**:

| Label kind (`label_kind` field) | NaN behavior |
|---|---|
| 0 = binary classification | 0.5 (neutral, neither class) |
| 1 = regression | 0.0 (zero return) |
| ≥2 = multiclass softmax | **skip the sample** (don't include in training; bump nan_labels_dropped) |

```cpp
float lbl = compute_label(...);
if (isnan(lbl) || isinf(lbl)) {
    HealthLog_Warn_RateLimited("[label] idx %d produced NaN/Inf", idx);
    if (LabelType_IsRegression(label_type))     return 0.0f;
    else if (LabelType_IsMulticlass(label_type)) return NAN;  // sentinel: skip
    else /* binary */                            return 0.5f;
}
```

Caller checks: `if (isnan(lbl)) { stats->nan_labels_dropped++; continue; }`
for multiclass; otherwise consume the neutral default + bump the
counter.

Add a one-line counter in BacktestResults: `nan_labels_dropped`.
Display in Past Runs.

**3. ConfidenceScore tau=0 silent default (audit #13)**

**4. ML class-weight handling docs (audit #3)**

**5. ConfidenceScore hard-floor (audit #21, was deferred)**

Audit #21 flagged that confidence scoring DAMPS the threshold but
doesn't BLOCK at very-low confidence. With low IC (noisy
predictions), the dampened threshold can become pathological —
trades fire on essentially-random predictions.

Fix: hard floor in StrategyParameters:

```cpp
constexpr double CONFIDENCE_HARD_BLOCK = 0.05;
double conf = ConfidenceScorer_Compute(...);
if (conf < CONFIDENCE_HARD_BLOCK) {
    Gate_Zero(out);
    out->strategy_halt_reason = SHALT_LOW_CONFIDENCE;
    return;
}
// existing damping below floor unchanged
```

Cfg-driven floor (`confidence_hard_block_threshold`, default 0.05).

## Phase 3 — Train-serve parity regression test (v5.9.2, ~4-5h)

**Spike resolved (2026-05-01, pre-coding):** existing scaffolding
fully reusable. No contingency needed.

- `tests/parity_harness.cpp` (240 lines, Track E.6) provides
  `DiffStats`, `compute_diff_stats()`, per-feature error breakdown,
  first-differing-row dump.
- `controller_test.cpp` already has ~10 EventLoopState construction
  sites (lines 3903, 3997, 4115, etc.) — `EventLoopState_InitLegacy`
  + `EventLoopState_RegisterCore` + `EventLoop_RebuildAllParameters`
  are callable directly in test context.
- Phase 3 INTEGRATES existing pieces, doesn't build from scratch:
  backtest path via `Backtest_RunFullValidation(collect_features=1)`
  → feature_matrix; live path via manual `EventLoopState` tick
  replay → `Features_PackAll` per cycle; diff via reused
  `compute_diff_stats()`.

**Effort:** 4-5h holds. No spike sub-phase needed.

The deferred prevention layer. v5.8.6 added structural protection
via `feature_registry_hash`, but only one input shape (synthetic
RegimeSignals) is bytewise-tested. This phase adds a **comprehensive
parity regression** that runs both the live engine path and the
backtest path on the same synthetic tick stream + asserts feature
output matches at every sample boundary.

### Why this matters

The class of bug we want to prevent: **a future change to
`Regime_ComputeSignals` or `MLBuildContext` populator could cause
the live and backtest paths to compute slightly different feature
values for the same input.** This passes the existing equivalence
test (which uses synthetic signals directly, bypassing
`Regime_ComputeSignals`). A regression test that drives both paths
through real tick data + asserts equivalence would catch it.

### Test design

```cpp
// tests/parity_train_serve.cpp (or new EXTENSIBILITY block)
//
// 1. Build synthetic tick stream: 10k ticks with known timing,
//    price, volume distributions
// 2. Construct two equivalent state contexts:
//    a. Live engine path: EventLoopState with one core,
//       MLBuildContext fully populated
//    b. Backtest path: ShardedBacktestDriver with same data
// 3. At each slow-path cycle, both paths compute features
// 4. Assert: feature_matrix[live][i][j] == feature_matrix[backtest][i][j]
//    for all i ∈ samples, j ∈ 0..NUM_REGISTERED_FEATURES
// 5. Tolerance: bit-exact (FP equality after FPN_ToDouble round-trip)
```

This is a heavy test (~10k slow-path cycles × 2 paths) but only
runs in `./build.sh test`, not in fast iterations. Catches drift
the existing tests miss.

### Items addressed

- Audit cross-cutting #1 (the false-CRITICAL one): closes the gap
  by structural assertion rather than just verification
- Future changes to `Regime_ComputeSignals` plumbing: instantly
  flagged if either path falls out of step
- Documents what train-serve parity actually means in code (the
  test is the executable spec)

## Subship order (v5.9.2 tail, CRITICAL-first per 2026-05-02)

Audit-derived order: ship CRITICAL items first, snapshots second (which
catches anything that drifted during 2c), cfg-binding third. Each
subship has a paper-test gate before the next subship starts.

```
v5.9.2c (CRITICAL: IC buffer + CSV sort)
   ↓ paper test ≥ 4h
v5.9.2a (snapshot tests + invariant docs + verification checklist doc)
   ↓ paper test ≥ 4h
v5.9.2b (cfg-binding + engine_version + cadence)
   ↓ paper test ≥ 12h
v5.9.3a (scaler infrastructure, disabled by default)
   ↓ paper test ≥ 12h (must verify scaler is no-op for existing models)
v5.9.3b (scaler enabled at apply sites + training compute)
   ↓ paper test ≥ 24h (MANDATORY — scaler is the highest-risk surface)
v5.9.3c (end-to-end parity validation + retrain ritual)
   ↓ paper test ≥ 12h
v5.9.4 / v5.9.5 (recipes + postmortem)
```

## Phase 3.6 — Stamp-bound inference cfg + engine_version verification (v5.9.2b, ~2-3h)

**Why this exists:** the inventory walk surfaced 4 more parity gaps
that snapshot tests don't cover. These are CFG-LEVEL drift surfaces
(operator can change a cfg field between train and serve, no hash
flips, model behavior silently differs at inference). Closing them
hardens v5.9 against the broadest "I changed a cfg and now things
are different" class.

### Sub-area 1: Stamp-bound inference-affecting cfg

Currently the stamp body records `feature_registry_hash` (catches
structural feature changes) and `engine_version` (informational only;
not yet verified at load). It does NOT record cfg fields that
materially affect inference behavior. Operator can:

- Train with `confidence_threshold_scale=2.0` → serve with `=3.0`
  → effective threshold formula differs → live decision drift
- Train with `barrier_gate_enabled=1` → serve with `=0` → model
  trained against barrier-modulated trades, served via binary
  threshold
- Train with `confidence_hard_block_threshold=0.05` (Phase 2) →
  serve with `=0.0` → low-conf entries fire that wouldn't have
  been part of training distribution
- Phase 4 will add `feature_scaler_present` — same shape

**MODEL_FORMAT_VERSION decision (resolved post-readiness 2026-05-02):**
v5.9.2b STAYS AT format_version=5. New inference_cfg_* fields are
forward-compat additions, guarded by "if cfg field is non-default,
emit". v5.9.3 owns the 5→6 bump for scaler. Same pattern as v5.8.6
when `feature_registry_hash` was added without bumping
MODEL_FORMAT_VERSION (forward-compat parser tolerates unknown keys,
v5.8.x stamps lack the field, v5.8.1a+ verifier handles missing as
"skip check"). Cross-references PARITY_LIFECYCLE.md row "Stamp body
field add" — backward-compat default = field absent.

Add to stamp body when respective cfg field is non-default OR enabled:
```
inference_cfg_confidence_threshold_scale=<double>
inference_cfg_barrier_gate_enabled=<0|1>
inference_cfg_confidence_hard_block_threshold=<double>

inference_cfg_bandit_blend_ratio=<double>     # when bandit_enabled=1 (sub-area 5)
inference_cfg_fee_rate_maker=<double>         # when cost_gate_enabled=1 (sub-area 5)
inference_cfg_fee_rate_taker=<double>         # when cost_gate_enabled=1 (sub-area 5)
training_poll_interval=<uint32>               # for cadence parity check (sub-area 7)
```

Verifier behavior:
- Field present in stamp + matches cfg → OK
- Field present + differs → strict refuse / non-strict warn (3-tier behavior)
- Field absent → skip check (forward-compat for v5.9.0/.1/.2 stamps)

+ `tools/stamp_model.sh` `--training-poll-interval`. Caller (foxml suite

stamp READ buffer at line 661). 9 new fields × ~50 bytes each = ~450

change.

`inference_cfg_drift_count` counts mismatches with current cfg.

### Sub-area 1: IC buffer reset on model load — **VERIFIED ALREADY PROTECTED** (DEFERRED)

**Status post-readiness 2026-05-02:** the comprehensive parity audit
flagged this as CRITICAL but pre-coding verification found
`ConfidenceScorer_Init` is already called at all 3 boot-time sites
that initialize per-core ML state:

- `ControllerEventLoop.hpp:509` (EventLoopState_Init, defaults for
  every core regardless of strategy)
- `EngineSharded.hpp:834` (per-core cfg values for STRATEGY_ML cores
  AFTER `CoreModelZoo_LoadFromDir`)
- `BacktestSharded.hpp:267` (mirror of EngineSharded for backtest)

The audit's concern was about MID-SESSION model reload. Per
`CLAUDE_ML_INVARIANTS.md` rule 5 ("Models load once at boot —
hot-swap unsupported"), mid-session reload is not a feature today.
If/when it becomes a feature, the ConfidenceScorer reset must fire
on every model swap — but that's a deferred concern tied to the
hot-swap feature itself.

**Same false-CRITICAL pattern as v5.9.0a's MLBuildContext finding**
(speculation about train-serve drift that turned out to already be

aux fields. Doing the analogous cleanup here:

- No code change in v5.9.2c
- v5.9.2a's PARITY_LIFECYCLE.md should reference this verification
  as evidence the boot-time pattern is sufficient

**Drift class (if hot-swap ever lands):** runtime, predicts on stale state.

`ConfidenceScorer` maintains rolling IC + RMSE buffers. When a new
model is loaded mid-session (currently doesn't happen in production
since "Models load once at boot — hot-swap unsupported" per
CLAUDE_ML_INVARIANTS rule 5, BUT v5.9.3+ retraining workflow may
introduce model swaps for paper testing) OR at engine boot when
loading a model whose stamp differs from the previous boot's model,
buffers carry IC/RMSE values computed from the OLD model's
predictions. Threshold damping on the first ~32 predictions of the
new model is systematically biased.

loads in v5.9.3a), call `ConfidenceScorer_Init` on the core's
confidence struct to flush stale buffers. Adjacent comment pointing
to CLAUDE_ML_INVARIANTS rule 5 ("models load once at boot") so
future authors know this only fires at boot today but is the right
defensive pattern.

**Tests:**
- "ConfidenceScorer flushed on Model_Load — IC=0, RMSE=0 post-load"
- "scorer state preserved across slow-path cycles when model NOT reloaded"

### Sub-area 2: CSV tick-sort validation (CRITICAL)

**Drift class:** training-time, garbage features silently.

`BacktestData_Load` (BacktestEngine.hpp:59) reads CSV ticks in file
order. If the CSV is unsorted (timestamps out of order — happens with
concatenated daily exports, or mistyped tick replay logs), rolling
stats / ROR / tick rate features compute on out-of-order data with NO
warning. Result: training run completes successfully with garbage
features, model trains on noise, paper deploys, operator wonders why
predictions are nonsense.

**Fix:** after each CSV is loaded, validate that
`ticks[i].timestamp_us >= ticks[i-1].timestamp_us` for all i. New
cfg field as **int enum** (matches existing codebase pattern;

```cpp
// Add to ControllerConfig (CoreFrameworks/ControllerConfig.hpp):
#define CSV_SORT_WARN   0   // default — log violations, proceed
#define CSV_SORT_STRICT 1   // refuse load on any violation
#define CSV_SORT_AUTO   2   // sort in-place + INFO log
int csv_sort_check_mode;     // default 0 (CSV_SORT_WARN)
```

cfg parser entry: standard int parse, default 0.

`engine.cfg.example` entry:
```
# CSV tick-sort validation mode (v5.9.2c)
#   0 = warn  (default — log violations, proceed with potentially-garbage data)
#   1 = strict (refuse load on any violation)
#   2 = auto  (sort in-place + log INFO)
csv_sort_check_mode=0
```

For multi-file loads, validate the CONCATENATED array (covers Tier 4

after all files are concatenated into the `label_ticks` array
(BacktestEngine.hpp ~line 487-498).

**Tests:**

- "deliberately unsorted CSV → WARN logged, count matches"
- "strict mode + unsorted → refused"
- "auto mode + unsorted → sorted, INFO logged, downstream features OK"

### Sub-area 3: Held-out lock token reproducibility (MEDIUM)

**Drift class:** operator workflow friction, not silent drift, but
worth fixing while we're here.

`HeldOutSplit_GenToken` (HeldOutSplit.hpp:62) uses
`(uint64_t)(uintptr_t)&s` (stack address) as entropy at line 105.
Token differs across runs even with identical inputs. If operator
saves token from run 1 and re-runs with same cfg, token mismatches.
Result: re-evaluation friction, operator confusion.

**Fix — concrete signature change** (resolved post-readiness):

```cpp
// CURRENT (HeldOutSplit.hpp:62):
static inline void HeldOutSplit_GenToken(
    char out[33], int total, int trainval_end, uint64_t entropy);

// NEW (v5.9.2c):
static inline void HeldOutSplit_GenToken(
    char out[33], int total, int trainval_end,
    const char* cfg_path,           // stable across runs with same cfg
    uint64_t training_data_hash);   // hash of input data file path(s) + sizes

// Implementation: compute entropy internally from stable inputs:
//   uint64_t e = FNV1a64(cfg_path) ^ FNV1a64_u64(training_data_hash)
//                ^ ((uint64_t)trainval_end << 32);
// Then identical body to current.
```

`training_data_hash` source: FNV1a64 over the concatenated data file
paths + sizes (NOT contents — too expensive). Cheap to compute, stable
when cfg's data_paths and the underlying CSV files are unchanged.

**Caller refactoring required (the audit's real finding):**

Two call sites need updating:
- `HeldOutSplit_Make` (HeldOutSplit.hpp:106) — currently passes
  `(uint64_t)(uintptr_t)&s` as entropy. Update to compute
  `training_data_hash` from the run_cfg's data_paths and pass

**Fix — explicit allowlist test design (resolved post-readiness):**

```cpp
// Helper: given a synthesized populated snap, walk fields and
// assert each is either populated (non-zero) OR in the explicit
// expected-zero allowlist.
struct ExpectedZeroFields {
    const char* field_name;
    const char* reason;

static const ExpectedZeroFields k_expected_zero[] = {
    {"samples",      "hot-path latency histograms not in sharded snapshot"},
    {"min_ns",       "hot-path latency"},
    {"p50_ns",       "hot-path latency"},

    {"core_open_positions", "legitimately 0 when no position"},
    {"sl_cooldown_remaining", "legitimately 0 when not in cooldown"},
    // etc.

// positions, default cfg), assert: for each field in PerCoreSnap,
// either the field is non-zero OR it's in k_expected_zero.
// New fields added without populator updates fail this test
// because they're not in the allowlist.
```

(a) add the populator line so the field is populated (preferred), OR

Either path is a deliberate choice; silent forget = test failure.

## Phase 4 — Feature standardization (v5.9.3, ~6-8h)

The deferred v5.9 feature from the original v5.8 plan. Implement
mean-centering + unit-variance scaling for ML features.

### Items addressed

- Audit #11 (feature scaling absent)
- Original v5.9 plan goal (was: "indexes by FeatureId" since v5.8
  registry exists)

### Design

`ML_Headers/FeatureStandardizer.hpp` (NEW):

- `FeatureStandardizer<F>` struct holds per-feature mean + stddev
  arrays sized `NUM_REGISTERED_FEATURES`
- `FeatureStandardizer_Compute(...)` runs over the training-side
  feature_matrix at training time, computes mean + stddev per
  column, persists to a sidecar file `<model>.scaler` (or extends
  the stamp body)
- `FeatureStandardizer_Apply(...)` applies standardization at
  serve time: `out[i] = (in[i] - mean[i]) / stddev[i]`
- Stamp body extended: `feature_scaler_present=1` + `scaler_sha256=<hex>`
- Verifier checks scaler file exists alongside model when stamp says
  present
- Backward-compat: stamps without `feature_scaler_present` work in
  warn-mode; strict mode requires it for v5.9.3+ models

### Resolved design (post-readiness 2026-05-01 + v5.9.2 deep audit 2026-05-02)

1. **Sidecar file format:** binary (not text). Avoids locale-pinning
   concern + smaller file. Layout (revised post-deep-audit):
   ```
   [u32 magic = 0xFE5C1AE2]
   [u32 num_features]                      // must equal NUM_REGISTERED_FEATURES at load
   [u64 feature_registry_hash]             // NEW: must equal FEATURE_REGISTRY_HASH() at load
   [u32 stddev_floor_q]                    // NEW: stddev_floor encoded as Q32 fixed-point (1e-9 default)
   [double mean[N]]
   [double stddev[N]]
   [u8 sha256[32] of body up to here]
   ```
   Sidecar SHA-256 stored in stamp body field `scaler_sha256`.

   **Why `feature_registry_hash` in the sidecar:** the audit's #1
   critical finding. Without this, retraining the registry between
   v5.9.3 ships could silently mis-index scaler entries to wrong
   features — the scaler stays valid by file integrity (sha256) but
   maps to a different feature set than the loaded model expects.
   Refusing on registry mismatch makes drift impossible to ship
   accidentally. Two-layer protection: stamp's `feature_registry_hash`
   AND scaler's `feature_registry_hash` both must match the engine.

   **Why `stddev_floor_q` in the sidecar:** Compute and Apply must
   use IDENTICAL floor. Embedding it in the sidecar means a future
   change to the constexpr default doesn't silently change behavior
   for existing models — the persisted floor wins. v5.9.3 default
   is `SCALER_STDDEV_FLOOR = 1e-9`.

2. **Sidecar path convention:** `{model_dir}/{model_name}.scaler`.
   Same shape as `.stamp` (sidecar to the `.json`/`.bin` model file).
   Save Run copies it alongside the model + stamp.

3. **MODEL_FORMAT_VERSION bump:** 5 → 6. v5.8.x stamps lack
   `feature_scaler_present` field. Verifier WARN-loads (parses as
   absent) and skips standardization. Strict mode requires the field.

   **3 backward-compat cases enumerated:**
   - format_version=5 stamp → engine assumes `feature_scaler_present=0`,
     applies identity (no-op standardize). Pre-v5.9.3 models work unchanged.
   - format_version=6 stamp + `feature_scaler_present=0` → no scaler
     loaded, identity applied. Operator opted out post-retrain.
   - format_version=6 stamp + `feature_scaler_present=1` → engine MUST
     load `.scaler` sidecar AND verify SHA + registry hash. If sidecar
     missing OR hashes mismatch: REFUSE model load (strict mode), WARN
     in non-strict (and apply identity). **Silent fallback is forbidden.**

4. **Stamp body new fields** (when format_version >= 6):
   - `feature_scaler_present=0|1` (boolean — present and applied)
   - `scaler_sha256=<hex>` (SHA-256 of sidecar; verifier checks)

   `ModelStampResult` struct gains: `int feature_scaler_present` +
   `char scaler_sha256[65]` — both nullable (zeroed for v5.x stamps).

5. **engine.cfg.example entry:** `feature_scaler_present=0` (default
   off until models are retrained). Documented alongside other
   stamp-related settings from v5.8.10.

6. **Standardizer compute timing:** post-ALL-folds (computed once
   on the full trainval set after WF cross-validation completes),
   **POST-COMPACTION** (after multiclass NaN-label filter applied —
   see v5.9.1 wrapping). The scaler's stats must be computed over
   THE EXACT SAME SAMPLE SET the model trains on. Otherwise: scaler
   sees data the model never sees, producing miscalibrated stats.
   Persist sidecar + stamp simultaneously.

7. **Scaler SHA computation timing:** at `FeatureStandardizer_Persist`
   write time. Compute SHA over body bytes EXCLUDING the trailing
   sha256[32] field (i.e. SHA covers the magic + num_features +
   registry_hash + stddev_floor_q + mean + stddev). Embed in the file's
   trailing sha256[32]. Then immediately after rename(), invoke
   `sha256_file_hex_inproc` to get the hex of the FULL file
   (including the embedded sha256), and pass that hex as
   `scaler_sha256` to `stamp_write_for_model`. Stamp's `scaler_sha256`
   = hash of full file, NOT hash of body — matches the v5.3.0 stamp
   pattern where `model_sha256` is hash of full `.bin` file.

8. **Float ↔ double precision contract:** Compute reads
   `feature_matrix[sample][feat]` as float, casts to double in the
   accumulator (Welford-style). Apply casts input float to double,
   subtracts `mean[i]` (double), divides by `max(stddev[i],
   stddev_floor)` (double), casts result back to float. Both paths
   use identical ordering. Verified by v5.9.3c parity test on
   synthetic input.

9. **Scaler load timing:** at `Model_Load` time inside
   `CoreModelZoo_TryLoadRole`. Sidecar lifecycle = model lifecycle.
   New field `FeatureStandardizer<F>* scaler` on the model handle
   struct (NULL when not loaded — matches "feature_scaler_present=0"
   semantics). Free in `Model_Free`.

10. **Apply sites (5, not 3 as plan originally claimed):** The deep
    audit found 5 `Model_Predict` callers, all with Features_PackAll
    immediately preceding. All 5 must invoke
    `FeatureStandardizer_Apply` between PackAll and Predict:
    - `Strategies/MLStrategy.hpp:129` (legacy buy_model)
    - `Strategies/StrategyParameters.hpp:723` (zoo->barrier multi)
    - `Strategies/StrategyParameters.hpp:751` (zoo->buy_signal)
    - `CoreFrameworks/PortfolioController.hpp:1639` (regime model)
    - `CoreFrameworks/PortfolioController.hpp:1806` (barrier peak/valley)

### Live↔training parity addendum (2026-05-02 deep-dive)

These three gaps were surfaced by walking the v5.9.0b / v5.9.1
observability patterns against the Phase 4 design. All three are
"works in strict mode" but silently degrade in non-strict mode.

**Gap G — Trainer-side persist failure must be atomic with stamp emit.**

If `FeatureStandardizer_Persist(...)` fails (disk full, permission
denied, IO interrupt), the trainer must NOT proceed to write a stamp
claiming `feature_scaler_present=1` + `scaler_sha256=<garbage>`. A
half-baked artifact pair (stamp says scaler present, sidecar missing)
is exactly the silent-drift class v5.9 is designed to prevent.

Required ordering in `Backtest_TrainModel` (or wherever the v5.9.3b
training integration lands):

```
1. compute scaler in-memory (FeatureStandardizer_Compute)
2. persist sidecar atomically (FeatureStandardizer_Persist)
   — IF FAIL: ABORT entire training run, no stamp written
3. compute scaler_sha256 from on-disk file via sha256_file_hex_inproc
   (verifies it landed, doesn't trust the in-memory copy)
4. write stamp atomically with scaler_sha256
   — IF FAIL: rm <model>.scaler so no orphan, return error
5. only after both succeed: emit run-history JSONL
```

If any step fails, error propagates; no half-state on disk.

Tests:
- "Backtest_TrainModel: simulated persist failure (read-only model_dir)
  produces NO stamp + NO sidecar"
- "Backtest_TrainModel: persist succeeds + stamp emit fails → cleans up
  sidecar"

**Gap H — Live scaler load failure must surface to the operator distinctly
from model load failure.**

In strict mode (`held_out_gate_strict=1`), scaler refusal sets
`model_load_failed=1` and the existing v5.9.0b ML Status panel + entry
log surfaces handle it. ✓

In non-strict mode (`held_out_gate_strict=0`), the engine continues
with identity scaler applied. Operator sees "model: loaded" in the ML
Status panel and has NO INDICATION inference is silently using identity.
This is the silent-drift class.

Required additions:

```cpp
// CoreContext extension (ControllerEventLoop.hpp)
uint8_t  scaler_load_failed;          // 1 = scaler missing/corrupt, identity applied
uint8_t  scaler_format_version_seen;  // 5 (no scaler) or 6+ (scaler-aware)
uint64_t last_scaler_warn_log_us;     // rate-limit gate for warn-mode log

// PerCoreSnap extension (DataStream/EngineTUI.hpp)
uint8_t  ml_scaler_load_failed;        // 1 = warn-mode load with identity fallback
uint8_t  ml_scaler_format_version;     // for ML Status panel render
```

ML Status panel branches:
```
scaler: applied (registry_hash=abc12345)   ← clean v5.9.3 case (green)
scaler: NONE (legacy v5 model)             ← format_version=5 explicit (sand)
scaler: WARN — sidecar missing             ← non-strict + missing (red)
scaler: WARN — sidecar SHA mismatch        ← non-strict + corrupt (red)
```

CRITICAL log emitted on engine boot when warn-mode picks up identity
fallback (rate-limited at 5min like v5.9.0b's ML→SimpleDip log):

```
[CRITICAL] core %d: scaler load failed (reason=%s) but engine
continuing with identity (held_out_gate_strict=0). Predictions WILL
drift from training distribution. Set strict=1 in cfg to refuse.
```

Tests:

### Numerical contract (load-bearing, applies across compute and apply)

Both `FeatureStandardizer_Compute` and `FeatureStandardizer_Apply` MUST
use IDENTICAL math. Drift here is silent and bytewise-permanent.

**Why double, not FPN<F>:** training-side reference is Python/numpy/
XGBoost which compute mean/stddev in IEEE-754 double. FPN math
produces subtly different bits than IEEE double for the same inputs
(FPN_DivNoAssert vs IEEE `/`). Using FPN at apply time vs double at
compute time = guaranteed bytewise mismatch. Standardizer is on the
slow path (between PackAll and Predict, ~once per slow-path cycle),
so the FPN/branchless rule that protects the hot path doesn't apply.

**Specified math sequence (BOTH compute and apply MUST do this):**

```cpp
// Apply (per feature, per slow-path cycle)
double in    = (double)features[i];           // float → double
double sd    = std::fmax(stddev[i], floor);   // BRANCHLESS on x86 (maxsd)
double diff  = in - mean[i];                  // IEEE double subtract
double out   = diff / sd;                     // IEEE double divide
features[i]  = (float)out;                    // double → float

// Compute (training-time, mean accumulator)
// Reads feature_matrix[sample][feat] (float type), casts to double
// in the accumulator (Welford-style). One-pass, identical math
// sequence.
```

`std::fmax` on x86 emits `maxsd` (single instruction, branchless).
On ARM/other, may emit a branch — acceptable here since standardizer
is slow-path.

**Stddev floor:** `SCALER_STDDEV_FLOOR = 1e-9` (constexpr default,
embedded in sidecar as Q32 fixed-point so persisted floor pins per-model).
At apply, both `stddev[i]` and the floor are doubles; `fmax` selects
the larger. For constant features (stddev=0): result is `(in-mean)/floor`
which is finite (clamped to floor instead of dividing by 0).

**Two-layer NaN guard:**

- Pre-apply (existing v5.9.0): `Features_PackAll` returns -1 sentinel
  if any FPN feature is non-finite OR float-cast produces NaN/Inf.
  Caller (ML_BuildParameters) skips the cycle.
- Post-apply (NEW in v5.9.3b): after FeatureStandardizer_Apply, walk
  features array and check `std::isfinite(features[i])`. If any
  feature is non-finite (e.g. mean[i] was NaN due to scaler corruption
  that bypassed sha check, or stddev was below floor and feature was
  at FPN saturation limit), bump `nan_feature_events_total` and
  return -1 sentinel to caller. Same downstream path as pre-apply NaN.

**Both layers required.** Pre-apply doesn't catch issues introduced
by the scaler math itself; post-apply doesn't catch garbage features
that should have been gated upstream.

### Output D — Cross-binary version handshake

Today: engine_gui (live) and foxml_suite (training) are separate
