# v5.6 — Execution / Display Divergence Audit + Diagnostic Visibility

**Created:** 2026-04-30
**Trigger:** Live paper run on 2026-04-30 showed DIP core continuously
in "READY" status while making zero trades, including missing a clearly
profitable dip-and-recover (chart screenshot in conversation log). Root
cause: hot-path `BG_Evaluate` enforces 5 conditions; GUI top table
checks 1. Display layer's truth model is a strict subset of execution
layer's truth model — recurring bug Class 1 (display↔execution).

## Problem statement

Hot path (`ExecutionCore.hpp:280-298`):

```
bg_fires  = price_ok & volume_check & ~blocked_mask
can_enter = ~any_active & permission & bg_fires
```

GUI Buy Gate top table (`DashboardPanels.hpp:506-520`) only checks
`price_ok` (price crossed threshold). It treats everything else as
implicitly-true. So:

- **`BUY_BLOCKED` set** → GUI says READY, hot path refuses → silent miss
- **`VOLUME_REQUIRED` + low volume** → same
- **`permission==0` (kill switch / startup gate)** → same
- **`any_active` from hot-path bitmap diverges from snapshot positions
  array** → same

This is systemic. Three independent BUY_BLOCKED paths fire today
(fee-floor `StrategyParameters.hpp:884`, cost-gate `:919`,
book-imbalance `ControllerEventLoop.hpp:1846`), all silent.

Plus halt_reason 10 (book-imbalance) is **fully invisible** — `halt_names[]`
in `DashboardPanels.hpp:529` only has indices 0-9 with bound `< 10`.

## Goals

1. Make every hot-path "no-fire" reason visible somewhere on the GUI
2. Document the divergence model so future hot-path additions don't
   regress (mandatory GUI surface for new predicate)
3. Capture gate-state transitions in the health log so post-hoc
   diagnosis of missed trades is `grep`-easy

## Non-goals

- Changing strategy logic. Strategies are doing the right thing.
- Changing hot-path logic. The 5-condition predicate is correct.
- New strategies, new ML models, new regime types.
- **Strategy quality / "why is MOM entering when it'll lose?"** — that's
  v5.7 (separate plan). v5.6 surfaces *why entries were blocked*; it
  does not surface *why entries should have been blocked but weren't*.

## Cross-cutting invariants (apply to all phases)

These constraints must hold for every code change in this plan:

1. **Single-source rule** — every "actual vs threshold" pair displayed
   must read the SAME variable the controller's gate check reads.
   Display code may NOT recompute a threshold. If a threshold isn't
   currently exposed as a slow-path output, plumb the existing
   variable through; do not duplicate the formula. (Anti-DRIFT bar.)

2. **Test-file naming upfront** — all new tests in this plan land in
   `tests/controller_test.cpp` under a new `// === EXECUTION_DISPLAY ===`
   section (matches existing section banner convention). Phase 1 adds
   the section header; subsequent phases append. No new test file.

3. **TUISnapshot vs ShardedSnapshot distinction** — TUISnapshot is
   RAM-only, frame-cadence, double-buffered (`snapshots[2]` at
   `EngineTUI.hpp:1003`); never persisted, no version bump needed.
   ShardedSnapshot is the persisted on-disk state, version-bumped
   (currently v6). All v5.6 PerCoreSnap additions are RAM-only —
   never bump SHARDED_SNAPSHOT_VERSION.

4. **Byte budget** — TUISnapshot is double-buffered, so per-field cost
   is ×2. Phase 4's claimed +160B/core × 16 cores actually costs
   **5KB total**. Still trivial vs current snapshot size; flag if any
   single phase pushes over 16KB additional.

5. **AUTO core SHALT propagation** — AUTO resolves to a concrete
   strategy and invokes its `_BuildParameters`. The `out` struct
   (including new `strategy_halt_reason`) is copied by-value from the
   resolved strategy's output to the AUTO core's pending_params; no
   special handling needed. Verify in test once.

## Phase 3 — v5.6.2 — Strategy-internal halt reason

**Cover the "off, no halt_reason" case.** Strategies internally call
`Gate_Zero` for their own reasons (uptrend not confirmed, no
mean-reversion signal, ML threshold not crossed). Today these zero
`bg_price_threshold` without setting any halt code → GUI shows "off"
with no explanation.

### Code changes

1. **`CoreFrameworks/ControllerEventLoop.hpp`** — add to CoreContext:
   ```
   uint8_t strategy_halt_reason;  // 0=ok, 1+=strategy-specific
   ```

2. **`StrategyInterface.hpp`** — define codes:
   ```
   constexpr uint8_t SHALT_OK             = 0;
   constexpr uint8_t SHALT_NO_UPTREND     = 1;  // EmaCross, MeanReversion long-trend
   constexpr uint8_t SHALT_NO_MEAN_REV    = 2;  // MeanReversion vwap_ok/long_ok/delta_ok
   constexpr uint8_t SHALT_FEE_FLOOR      = 3;  // dispatcher fee-floor BUY_BLOCKED
   constexpr uint8_t SHALT_COST_GATE      = 4;  // dispatcher cost-gate BUY_BLOCKED
   constexpr uint8_t SHALT_STDDEV_ZERO    = 5;  // any strategy on dead market
   constexpr uint8_t SHALT_NO_BREAKOUT    = 6;  // Momentum
   constexpr uint8_t SHALT_ML_NO_PRED     = 7;  // ML zoo unloaded / no inference
   constexpr uint8_t SHALT_ML_BELOW_THR   = 8;  // ML prediction < threshold
   constexpr uint8_t SHALT_LOW_CONFIDENCE = 9;  // ConfidenceScorer veto
   ```

3. **Each strategy's `_BuildParameters` (in `StrategyParameters.hpp`)**:
   set `out->strategy_halt_reason = SHALT_*` BEFORE the Gate_Zero call.
   Reset to `SHALT_OK` at top of each rebuild.

4. **PerCoreSnap**: add `uint8_t strategy_halt_reason`.

5. **Display**: in priority chain (Phase 1), add between `halt_reason`
   and `no signal` cases:
   ```
   elif strategy_halt_reason > 0  → "off: <shalt_name>"
   ```
   Add `shalt_names[]` array.

### Tests

Per-strategy test: synth low-stddev market, run BuildParameters,
assert `out->strategy_halt_reason == SHALT_STDDEV_ZERO`.

**Commit:** `strategies(*): emit strategy_halt_reason for GUI visibility (v5.6.2)`
**Tag:** `v5.6.2`

### Single-source rule (CRITICAL)

Every numeric pair shown is read directly from the variable the
controller's gate check reads. Display code MUST NOT recompute. Where
the controller's check runs as a temp local (e.g.
`Strategy_SpacingOk` returns bool, doesn't expose the spacing margin),
refactor the check to expose the comparand into a slow-path output
field, then read that field for both the gate decision and the
display. New helper convention: `Gate_<Name>Diagnostic` returns a
`{passed, actual, threshold}` triple; controller uses `passed`,
display reads `actual` + `threshold`.

### Source data plumbing

copy into snapshot):

- `tp_pct_actual` — from `out->tp_pct`
- `tp_pct_floor`  — `3 × fee_rate_taker`
- `last_entry_price`, `spacing_floor` — from spacing check
- `vwap_threshold`, `vwap` — from VWAP check
- `long_rel_slope`, `min_long_slope` — from long-slope check
- `volume_delta`, `min_buy_delta` — from delta check
- `stddev_pct`, `min_stddev_pct` — from stddev check
- `book_imbalance`, `imbalance_threshold` — from Track E.3 check

Pack as a `GateDiagnostics` sub-struct on PerCoreSnap to keep field

## Phase 5 — v5.6.4 — Snapshot truthfulness sweep

**Audit-FIRST, fix-only-if-needed.** The phase is split into two
parts:

### 5a — Audit (always run)

Verify the current state of synchronization between slow-path
`cached_params` writes and `TUI_CopySnapshotSharded` reads. Existing
infrastructure to investigate:

- `ParameterSlot_Read` / `ParameterSlot_Write` (seqlock primitive)
  used in `ExecutionCore.hpp:252` and `ShardedSnapshot.hpp:166,380`
- `TUISnapshot::snapshots[2]` double-buffer at `EngineTUI.hpp:1003`
- `TUI_CopySnapshotSharded` field-by-field copy

Specifically check:
1. Does `TUI_CopySnapshotSharded` use `ParameterSlot_Read` to grab
   `cached_params` atomically, or does it read fields individually?
2. Are individual scalar fields (uint8/uint16/uint32) copied via
   plain assignment (torn-read possible in theory, fine for x86)
   or via `__atomic_load_n` (explicit memory order)?
3. Does any slow-path write happen WITHOUT going through the seqlock
   protocol — i.e. fields written directly to a published struct?

### 5b — Fix only if audit found gaps

If audit clean: phase collapses to a docs-only commit recording the
verified guarantees in `EXECUTION_DISPLAY_INVARIANTS.md`. Save ~5h
estimated effort.

If audit finds torn-read risks: add per-field `__atomic_load_n` /
`store_n` OR wrap the copy block in a per-core seqlock matching the
existing `ParameterSlot_*` pattern. Do NOT invent a new sync
primitive — extend or reuse the existing one.

The snapshot is built once per GUI frame (`TUI_CopySnapshotSharded`).
Slow path may have updated `cached_params` mid-snapshot-copy.

### Audit method

For each PerCoreSnap field:

1. Where is the source written? (slow path / hot path / drain)
2. What synchronization is in place? (atomic / seqlock / racy-but-ok)
3. Can the GUI ever observe a torn read?
4. Does the field interpretation match the predicate it implies?

Cross-check by running a long TSan stress (≥10 minutes paper) with
GUI live. Any data race in TUI_CopySnapshotSharded → fix.

### Expected fixes

- Any field copied in non-atomic fragments under a slow-path write →
  add per-core snapshot seqlock OR use `__atomic_load_n` per field
- Fields with stale source (slow-path computed once per poll_interval
  but GUI shows current price) → add "as-of" timestamp display so
  user knows freshness

**Commit:** `gui(snapshot): per-core seqlock + freshness annotations (v5.6.4)`
**Tag:** `v5.6.4`

## Phase 7 — v5.6.6 — Health log gate-state transitions

**Capture every gate state change in `health.jsonl` so post-hoc
diagnosis of missed trades is grep-easy.**

Today health log has 3 categories: `drain`, `engine`, `regime`. Add:

- `cat="gate"` — emitted on transitions of:
  - `BUY_BLOCKED` flag on/off (per core)
  - `halt_reason` change (per core)
  - `strategy_halt_reason` change (per core)
  - `permission` 0↔1 (per core)
- Log payload: timestamp, core, old/new state, current gate price,
  current market price, slow-path cycle counter
- Same `health_log_level` controls (0=info, 1=warn, 2=error)

### Edge-triggered ONLY (CRITICAL — rate limit)

The slow path runs every `poll_interval` ticks (typically 10-100).
Logging gate state every cycle would emit ~MB/min during volatile
periods and overflow disk during all-day runs. **Only emit on edge
transitions:** the slow path keeps a per-core `prev_gate_state` byte
(packed: BUY_BLOCKED | halt_reason << 4 | permission); compare against
current; emit only on diff.

State packing:
```c
struct GateLogState {
    uint8_t halt_reason          : 4;  // 0..15
    uint8_t strategy_halt_reason : 4;  // 0..15
    uint8_t buy_blocked          : 1;
    uint8_t permission           : 1;
    uint8_t reserved             : 6;
};
```
2 bytes per core, packed in CoreContext. On change → emit log line +
update prev_state. No timer-based polling.

Locale: emit numerics through `LC_NUMERIC=C` per existing `RunHistory`
pattern; verify `health_log_writer` follows the same pinning before
shipping.

### Test query

After live paper run with v5.6.6:
```
grep '"cat":"gate"' health.jsonl | jq 'select(.core==3)'
```
should show every DIP gate state change with full context.

**Commit:** `logging(health): gate-state transitions (v5.6.6)`

## Risk + rollback

Each phase is independently shippable + revertable. PerCoreSnap is
RAM-only (no migration). Strategy halt code additions default to
SHALT_OK so unset behavior is identical to current.

Phases 1-3 are pure additive (new fields + new render branches), low
risk. Phase 4 adds significant snapshot bytes (verify GUI frame budget
holds). Phase 5 is the highest-risk one because it touches snapshot
synchronization — gate behind extended TSan run before tagging.
