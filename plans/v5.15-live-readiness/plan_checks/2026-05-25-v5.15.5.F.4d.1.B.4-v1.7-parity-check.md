### HIGH

#### H-1 — D1-B Step B.3 body inline citation reads from WRONG gate-state struct (silent PARITY-032 closure break if coded verbatim)

**Source:** v1.7 plan body Step B.3 inline citation (line 640) vs Step B.3a row declaration (line 651)

**The contradiction:**

Step B.3a declares the new gate row with `ENGINE_WIDE` scope:
```cpp
X(ENGINE_WIDE, BREAKEVEN_ON_PROFIT,                                      \
  BITMAP_IS_SET((_gate_cfg).lifecycle_cfg_flags, MASK_LIFECYCLE_CFG_BREAKEVEN_ON_PROFIT), \
  "breakeven-on-profit lifecycle event ...")                              \
```

Per `CoreFrameworks/SlowPathGateRegistry.hpp:189-207`, ENGINE_WIDE-scoped bits live on `EventLoopState.global_gate_state.flags` (struct `GlobalGateState`). PER_CORE-scoped bits live on `CoreContext<F>.gate_state.flags` (struct `SlowPathGateState`). The two cache surfaces are STRUCTURALLY DISTINCT — they're separate `uint16_t flags` fields on different parent structs.

But Step B.3 body inline citation (line 640) reads from the PER_CORE struct path:
```cpp
if (BITMAP_IS_SET(state.cores[c].gate_state.flags, MASK_BREAKEVEN_ON_PROFIT)) {
    EventLoop_BreakevenOnProfitOneCore(state, cfg, current_price, c);
}
```

The `MASK_BREAKEVEN_ON_PROFIT` bit will be OR-set into `state.global_gate_state.flags` by `SLOW_PATH_GATE_AUTOPOPULATE_ENGINE_WIDE` (the ENGINE_WIDE walker — see SlowPathGateRegistry.hpp:236-243); it will NEVER be set in `state.cores[c].gate_state.flags` (the PER_CORE walker dispatches `SKIP` for ENGINE_WIDE rows per :147). Reading from the wrong struct path means BITMAP_IS_SET returns 0 always → BreakevenOnProfit never fires from SlowPathCycleOneCore → **PARITY-032 closure is silently broken**.

**Sister-canonical verification:** existing ENGINE_WIDE gates `LAZY_REBUILD_ACTIVE` + `WS_FLATTEN_ACTIVE` are read via `state->global_gate_state.flags` per ControllerEventLoop.hpp:2344 + :3558 (canonical use sites). NEW BREAKEVEN_ON_PROFIT bit should follow the same pattern.

**Severity rationale:** HIGH not CRITICAL because: (1) Step B.3 body has not been coded yet (Phase B Step B.3 is downstream of Phase A Step A.6.5 header trial + Phase B Step B.2 BootPerCore body unlock); (2) the Step B.3a row declaration is correctly ENGINE_WIDE; (3) if the implementer follows the canonical sister-pattern (look at LAZY_REBUILD_ACTIVE reader code), they'll naturally use the right path. But the inconsistency is in the plan body text — a coding-time reader of the plan body would write the wrong code.

**Fix path:** Amend Step B.3 inline citation to read from the correct struct:

```cpp
// CORRECTED (ENGINE_WIDE scope reads from global_gate_state):
if (BITMAP_IS_SET(state.global_gate_state.flags, MASK_BREAKEVEN_ON_PROFIT)) {
    EventLoop_BreakevenOnProfitOneCore(&state, cfg, current_price, c);
}
```

Also amend Pre-coding concern #12 (line 938) wording: drop "state.cores[c].gate_state.flags" reference; replace with "state.global_gate_state.flags".

**Secondary concern raised by this fix:** When does `SLOW_PATH_GATE_AUTOPOPULATE_ENGINE_WIDE` get called BEFORE SlowPathCycleOneCore reads the cached bit? Per canonical sister sites:
- `EventLoop_RebuildOneCore` (called inside SlowPathCycleOneCore body) re-populates via `SLOW_PATH_GATE_AUTOPOPULATE_ENGINE_WIDE(state->global_gate_state, *config)` at ControllerEventLoop.hpp:2335 (defensive re-populate at entry)
- `EventLoop_CheckWsStaleness` re-populates at :3555 (same defensive pattern)

So if BreakevenOnProfit gating reads `state.global_gate_state.flags` AFTER RebuildOneCore call inside SlowPathCycleOneCore body, the cache is populated and read-time-correct. **Recommend coding ordering:** call RebuildOneCore first → THEN read BREAKEVEN_ON_PROFIT gate bit → THEN call BreakevenOnProfitOneCore. This matches the current EngineSharded centralized arch ordering at :1932-1940 (RebuildOneCore precedes TimeExit/TrailingSL/BreakevenOnProfit). Plan body Step B.3 body-content order should explicitly note this.

**Effort:** ~3 minutes (Edit plan body Step B.3 inline citation + concern #12).

**Cross-ref:** GAP — not protected by existing structural enforcement (FOREACH_SLOW_PATH_GATE AUTOPOPULATE walker correctly dispatches by scope, but the consumer site's struct-path choice is hand-written; no compile-time enforcement that the reader path matches the row's scope). Worth tracking as a future TECH_DEBT entry: `gate-state-reader-scope-mismatch-class` (Class 24-shape: capability declared one way; consumer reads another way; silent failure). Defer entry unless second instance surfaces.
