## Latency opportunities surfaced (from cross-spec audit)

Per `slow-path-cfg-resolution-cache-pattern.md` Implementation checklist:

1. **Hot-path cfg drift check audit** (cross-spec verify): confirm no slow-path entry calls drift-check (should be boot+hot-swap only). Investigate during .F.4e.
2. **`__builtin_prefetch` at slow-path entry**: prefetch `per_core_overrides[core_idx]` to L1 before resolution body executes. Hides L2→L1 latency (~10ns/cycle/core). Future-work flag.
3. **AVX-512 batch-load of ResolvedCoreCfg** (item 25): 3 × 64-byte cache lines → 3 uops. Future-work; only worth it if cycle measurement shows resolution is bottleneck.
4. **Delta-cache resolved struct**: if cfg.epoch unchanged + override bits unchanged since last cycle, reuse last cycle's resolved struct entirely. Cost: 1 cycle epoch compare. Future-work.
5. **K-state cohort multi-bit state** (item 30 cohort): 6 fields → uint16_t (2 bytes) vs 24 bytes. ~22 bytes/core × 16 = 352 bytes saved.

Each is logged in TECH_DEBT.md after .F.4e baseline measurements; addressed in subsequent sprints if budget tightens.

Closes the reverse direction of the drift class (Cfg struct → Registry direction). May become redundant safety belt if `.F.4b` stretch goal (X-macro generates Cfg struct fields) lands.
