## GATE 1 — H7/H20 grep-CI (hot/SP branchless) → **REFUTED (ship as advisory, not a teeth-gate)**

### False-NEGATIVES (real violations the regex MISSES) — the disqualifier

1. **Function-pointer dispatch tables are invisible to an if/switch/`?:` regex.** The single most dangerous form of a *missed* branchless conversion — a runtime-enum dispatch — when done RIGHT is a fn-pointer table (Pattern 1), and when done WRONG (the Class-28 hand-wave) is `switch(algo){…}`. A regex that flags `switch` cannot distinguish "compliant table" from "missed branch", and a NEW violation introduced as `handlers[algo](…)` vs `if(algo==X)…` is **indistinguishable to the grep** — both are "a call". Landed proof the compliant form exists and is grep-opaque: `ML_Headers/bandit_dispatch_table.hpp:206/226` (`g_buy_reward_dispatch[algo]`), referenced from the SP dispatch `Strategies/StrategyParameters.hpp:1240`. The gate cannot catch the regression it most exists to catch.
2. **Macro-hidden data-dependent select.** `Run.hpp:2010 #define SH_PNL(v) ((v)>=0.0 ? SH_GREEN : SH_RED)` — a ternary hidden behind a macro name. A grep over the *use* site sees `SH_PNL(x)`, not the `?:`. Any future hot/SP macro of this shape is a branch the source-grep never sees. (This one is display-only, but it proves the class is live in the scoped files.)
3. **Inlined callee in a non-scope file.** ExecutionCore inlines BG/SG (`ExecutionCore.hpp:350/398` "Inlined BG_Evaluate / SG_Evaluate"). A data-dependent branch added to a helper that lives OUTSIDE `SHARDED_FILES ∪ {ExecutionCore,GateParameters}` but is `inline`-pulled INTO the hot path is not in the grep's file set → missed. The grep scopes by *file*, but the hot path is defined by *inlining*, not by file membership. (Plan open-question #5 acknowledges this but offers no fix.)

### False-POSITIVES (compliant code the regex WRONGLY flags)

4. **30 raw `if`/`switch` tokens in `ExecutionCore.hpp` ALONE** (`grep -cE '\bif\b|\bswitch\b'` = 30). The compliant hot path legitimately contains: `if constexpr`, `__builtin_expect`-rare (kill-switch / gate-change), boot-init, asserts, genuine binary predicates (`if(ptr==nullptr)`). The exception matrix (`branchless-dispatch-discipline.md` §"Decision matrix") lists 6 legitimate branch classes. A regex cannot evaluate "is this `__builtin_expect`-tagged + truly rare?" or "is the predicate a genuine binary with no alternative computation?" — those are **semantic, undecidable** judgments (the plan B.2 itself says "a perfect hot-path-branch detector is undecidable").

### Allowlist sizing — the killer

The plan defers allowlist sizing to "the I-class pass" but B.2's own design forces a **large** seed: 30 if/switch in one file × the full `SHARDED_FILES` set ⟹ the "shrinking-only allowlist" starts with dozens of entries, **each requiring a TECH_DEBT row + categorical trigger** (plan B.2). At that hit-density the allowlist IS the codebase's hot path, and a "shrinking-only" ratchet over dozens of human-classified exceptions is high-friction with near-zero marginal signal. **This is security-theater risk**: a GREEN H7 grep (everything either matched-exception or allowlisted) *lulls* — it asserts nothing about a NEW fn-pointer-table or macro-hidden branch (#1/#2), which is precisely the regression class. **Verdict: REFUTED as a teeth-gate.** Salvage path: ship it as an ADVISORY surfacer (the existing `/hft-audit` "Branchless dispatch opportunity scan" already does this per the spec §"Audit + prevention") — NOT a RED-build pre-commit gate. A regex pre-commit gate on an undecidable property either false-fails compliant code or false-passes the dangerous form; here it does BOTH.

## GATE 2 — H10 SIMD-fallback determinism (`-march=native` vs `-march=native -mno-avx512f`, memcmp) → **SURVIVES (non-vacuous) — with one caveat**

### Does `-mno-avx512f` change emitted code for the chosen kernels? YES.

The `#if defined(__AVX512F__)` blocks gate on the macro; `-mno-avx512f` un-defines `__AVX512F__` ⟹ the compiler takes the scalar `#else`. Confirmed distinct bodies:
- `RidgeBlender.hpp:493` (BuildCorr) AVX-512 `_mm512_fmadd_pd` loop vs `:517 #else` triple-nested scalar.
- `RidgeBlender.hpp:584/621` (UpdateOnline) AVX-512 vs scalar `#else`.
- `BanditLearning.hpp:204` (GetProbabilities) AVX-512 `_mm512_div_pd/_mm512_fmadd_pd/_mm512_max_pd` vs `:236 #else` scalar.

So the two lanes emit **genuinely different machine code**. The byte-compare is NOT trivially-green-by-identical-emission.

### Will the memcmp be GREEN? YES, BY DESIGN — and that is correct, not vacuous.

The kernels were deliberately engineered bytewise-identical to scalar: `_mm512_div_pd` NOT reciprocal-mul ("1-ULP could differ", `BanditLearning.hpp:213/250`); `_mm512_fmadd_pd` to match `-ffp-contract=fast` scalar FMA (`:214-218`); and critically the **sum reductions are kept SCALAR** specifically because `_mm512_reduce_add_pd` does tree-reduction with different rounding (`BanditLearning.hpp:186-191`, `RidgeBlender.hpp` mirror). This is exactly what H10 demands. A GREEN result is the *correct* steady state — H10 is a **regression catcher** (catches a future kernel edit that breaks the parity, e.g. someone "optimizing" to reciprocal-mul or `_mm512_reduce_add_pd`), NOT a find-a-bug-now gate. The plan correctly frames it as "ARMS here, E.1.2 is first non-trivial consumer". **Not vacuous.**

### Harness run-to-run determinism? STABLE.

The kernel fns (`Bandit_GetProbabilities`, `RidgeBlender_BuildCorr/UpdateOnline`) take explicit array inputs, no rand/time/uninit reads in the math path (grep clean). `BanditLearning.hpp:472 clock_gettime` exists but is OUTSIDE the kernel (a diagnostic timestamp, not in `GetProbabilities`); a harness driving the kernels with fixed fixtures is deterministic. The existing `check_fp_determinism.sh` 2-way-compile shape is the right sister to extend (plan Phase C is genuinely an EXTEND, not parallel infra — open-question #4 confirmed).

### Caveat (downgrades to "SURVIVES-with-condition"):
- **The gate only has teeth on an AVX-512 machine.** On a non-AVX-512 CI runner, BOTH lanes compile the scalar `#else` (the `-mno-avx512f` flag is a no-op when the macro was never set) ⟹ identical bytes trivially ⟹ green-but-meaningless. The gate's validity is *machine-conditional*. The plan must (a) assert `__AVX512F__` is actually set in lane 1 (e.g. compile-probe + hard-fail if absent), else the gate silently self-disables on the wrong host. Currently unaddressed. **Teeth-proof in Phase C (perturb scalar fallback → RED) is sound IF run on the AVX-512 dev box** — but the selftest must guard the host capability or it green-lulls on a non-AVX-512 runner.

**Verdict: SURVIVES** (the chosen kernels DO differ; memcmp is meaningful on this host; harness deterministic) **conditioned on** an explicit `__AVX512F__`-present assertion in lane 1.

## GATE 3 — H8 latency ratchet → **REFUTED (the p99 source is non-reproducible AND the plan's stderr-parse target is wrong)**

### (A) The parsed p99 is a 256-sample SLIDING-RING p99 — not reproducible.

`EngineSharded_DumpLatency` (`Run.hpp:325`) prints `s.p99_ns`, which `CoreLatencyStats_Snapshot` computes from `recent[RING_SIZE=256]` — "the most recent 256 samples … sliding window … reflect RECENT behavior" (`CoreLatencyStats.hpp:29-36`, computed `:219-233`: copy ring → `std::sort` → `local[n*99/100]`). The header itself: "samples are p-stats from 256 most recent ticks" (`Run.hpp:313`). ⟹ the p99 the ratchet would parse is the p99 of *whichever 256 ticks happened to be in flight at shutdown* — thermal/scheduler/turbo/preemption-dependent, run-to-run variable. The header even warns "Max outliers are usually kernel preemption" (`Run.hpp:330`). A tight ratchet (plan Phase D: `≤ baseline × (1+margin)`, margin ~10%) against a 256-sample tail near a 500ns budget will **false-FAIL on noise**. The `lifetime_p99_ns` (`:240-256`) is more stable BUT is a **power-of-2 log-bucket UPPER BOUND** — "reported values within ~2x of true percentile" (`:239`). A 2× quantization is useless for a 10%-margin ratchet (one bucket step = 100% jump). **Neither available p99 is fit for a tight ratchet.** Median-of-N-runs (plan Phase D) reduces but does not eliminate ring-content variance, and cannot un-quantize the lifetime bucket.

### (B) Floor-subtraction (`Run.hpp:329`) is a COMMENT, not code.

Plan Phase A.0 + D: "Floor-subtract the rdtscp overhead (`Run.hpp:329`)". Line 329 is `fprintf(stderr, "Subtract the floor from min/p50 for actual hot-path work cost.\n")` — a **human-facing print instruction**, NOT a subtraction. There is NO floor-subtraction code anywhere in `DumpLatency` (grep for floor/subtract in Run.hpp returns only this print + unrelated `tp_floor`). The "floor" is hand-waved as "~25-30ns on this CPU" (`:328`) with no canonical constant the ratchet can import. The ratchet would have to *invent* its own floor value and subtraction. "Well-defined floor-subtraction (Run.hpp:329)" as the A1 prompt phrases it: **it is not defined in code at all.**

### (C) The plan's stated parse target (`LATENCY_BENCH` stderr) does not exist for the sharded engine.

- `build.sh latency` (`build.sh:209`) builds `build_lat` with `-DLATENCY_PROFILING=ON` — **NOT `-DLATENCY_BENCH=ON`** (CMakeLists:62 only defines LATENCY_BENCH under its own option). Plan Scope §"Design-shape" says "The ratchet parses `LATENCY_BENCH` stderr" — but the documented build doesn't set it.
- The `LATENCY_BENCH` stderr block (`main.cpp:1222`) is under `#ifndef MULTICORE_TUI` — the **single-core TUI path**. The `engine` binary defines `MULTICORE_TUI` (CMakeLists:12), and live/sharded refuses non-sharded (`main.cpp:306`). ⟹ that BENCH block is **dead for the sharded engine**, AND it emits only avg/min/max — **no p99 at all** (`main.cpp:1226-1230`).
- The ONLY p99 emitter for the sharded path is `DumpLatency` at `Run.hpp:2345`, fired **once at run shutdown** (after all threads join). So the ratchet must run the sharded engine to completion and scrape the shutdown table — i.e. the 256-ring p99 of (A), under PROFILING not BENCH.

**Verdict: REFUTED.** The ratchet as specified parses a stderr stream that the sharded engine doesn't produce; the only real p99 is a non-reproducible 256-sample sliding-ring value (or a 2×-quantized lifetime bucket); and the floor-subtraction it relies on is a comment, not code. Salvage requires: (i) add a stable fixed-workload p99 emitter (e.g. a dedicated lifetime-percentile dump with linear buckets, or a fixed-N replay that drains a deterministic tick count), (ii) define the floor as an importable constant, (iii) keep it a MERGE-lane advisory with a WIDE margin — never a per-commit hard fail. As written it false-fails or no-ops.

A naive single-line `\b[a-z_]+ : [0-9]` regex flags `count : 0` as a bitfield. Plan B.1 lists the FP surface (`?:` ternaries, `// file:982` comment refs, access-specifiers, case labels, ctor init-lists) — but the multi-line-ternary case (the actual landed one) means line-by-line regex is insufficient; needs either same-line `?` lookback over a joined logical line, or struct-body scoping. With that, teeth-proof (inject `uint8_t x:3;` → RED) is sound.
- **Verdict: SURVIVES**, conditioned on the regex handling multi-line ternaries (the real FP at ShardedSnapshot.hpp:433 proves the naive version false-fires). This is the one gate genuinely worth shipping as a hard pre-commit gate — bitfield syntax is *syntactically* decidable (unlike H7/H20's semantic undecidability), so a careful regex has real teeth.
