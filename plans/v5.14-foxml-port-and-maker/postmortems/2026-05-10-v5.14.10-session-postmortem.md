## Design pivots (each one surfaced something worth remembering)

### Pivot 1: cfg=2 dual-mode validity — per-arm reward observability is load-bearing

**Trigger:** During pre-coding consult, my synthesis labeled cfg=2 "Both" mode as "shadow telemetry with limited insight" (applying generic bandit-framework critique that assumes per-choice reward observation; would invalidate parallel-training because Thompson would never get to act + its rewards would be counterfactual).

**Caramel's pushback:** "is running both at the same time good?" + "does this allow training the thompson model while the bandit actually works? so we can get and track output for both at once? that doesnt seem like a terrible idea"

**Actual reality** (verified at `CoreModelZoo.hpp:881-882`): this codebase grades each ensemble arm's prediction independently against actual price movement (per-arm reward observability). Thompson never needs to ACT to observe its rewards — the reward is the prediction's correctness, observable for every arm every cycle regardless of which one was selected.

**Decision:** KEEP cfg=2 dual-mode. Both bandits learn from the SAME per-arm signal stream; their CHOICES diverge over time; offline analysis answers "which algo would have driven better aggregate PnL." Mathematically valid in this codebase even though it would NOT be in a typical bandit setup.

**Going-forward rule candidate:** when applying generic ML/bandit framework critiques, FIRST check the codebase's specific reward attribution model. The general "shadow rewards are counterfactual" argument is true in pull-based bandits but false in prediction-graded bandits. This codebase's per-arm reward observability is a load-bearing assumption that affects which dual-mode designs are valid. Could be documented as CLAUDE.md item 24+ ("per-arm reward observability invariant") or a new DESIGN_SPECS doc.

### Pivot 2: Cache layout strategy convergence — D+E unified cluster

**Trigger:** Initial spec for FULL Bayesian dashboard added 5 PerCoreSnap fields (~196 bytes; 3.125 cache lines spanned badly). Caramel asked sharp follow-ups: "is there a better alignment strategy we can use here?", "we basically have 6 bytes doing nothing which is kind of bad", "are those additional cache lines no matter what, or only if both the bandit and the thompson are running?", "is there no way to avoid this without looking at everything else running on the slow path and optimizing the cache alignment there?"

**Iteration:**
- v1: original 200B (3.125 cache lines; bad span)
- v2: optimized to 104B (uint32 vs uint64 pulls; float vs double display) — 24B trailing pad
- v3 (Caramel): "what about the 6 bytes between u8s and arrays?" → arrays-first reorder
- v4 (D+E): unified bandit cluster (Exp3 + Thompson under one alignas(64); 162B used in 192B allocated = 3 cache lines exact)

**Architectural insight:** the right framing was "cluster ALL bandit telemetry" (Exp3 + Thompson together), not "add Thompson cluster separately." This emerged through Caramel's broader pushback about looking at the whole PerCoreSnap layout, not just Thompson's slice.

**Decision:** Path B + Option 1 — pre-Thompson PerCoreSnap layout audit (.0 sub-ship) BEFORE adding Thompson fields. Establishes per-snapshot-cluster-layout-pattern.md as reusable methodology + first reference application (bandit telemetry cluster).

**Going-forward rule candidate:** when adding fields to a snapshot struct, check WHOLE-STRUCT layout BEFORE adding (not just where the new fields would go). Cache-locality decisions made at "where do I put these 5 fields" scope are local-optimal but globally-suboptimal compared to "what's the right cluster organization for the entire snapshot." TECH_DEBT-011 substantial close codifies this; per-snapshot-cluster-layout-pattern.md is the methodology.

### Pivot 3: PRNG + Box-Muller choice — own splitmix64, not std::mt19937_64

**Trigger:** Plan originally specified `std::mt19937_64` + `std::normal_distribution`. Pre-coding /parity-check caught PARITY-014: `std::normal_distribution` is libstdc++-implementation-defined (NOT C++ standardized at the algorithm level); same seed + same reward sequence on different libstdc++ versions → DIFFERENT Thompson sample sequences. Replay determinism BROKEN.

**Initial fix consideration:** use raw `mt19937_64::operator()` (which IS C++ standardized) + own Box-Muller. But mt19937_64 has 312-word internal state — awkward to serialize for thompson_state.json (would need 2.5KB per state × NUM_REGIMES × N_cores = ~12-50KB JSON).

**Better fix:** own splitmix64 PRNG (algorithm fully specified; single uint64 state; deterministic across all platforms; trivially serializable). Box-Muller via own implementation using raw splitmix64 output.

**Trade-off accepted:** splitmix64 has lower statistical quality than mt19937_64 (passes TestU01 SmallCrush + Crush; not Crypto-secure). Acceptable for bandit posterior sampling.

**Going-forward rule candidate:** when picking a PRNG for replay-determinism use, prefer a SIMPLE algorithm with small state over a high-quality algorithm with large state. Persistence is the load-bearing concern; quality is secondary for non-cryptographic uses. splitmix64 / xorshift64* / PCG are all good fits for this niche.

### Pivot 4: Pattern Variant A/B emergence for log column registries

**Trigger:** v5.14.10.D shipped FOREACH_CALIB_LOG_COL using fprintf-direct emit (single writer; small log; calib log style). v5.14.10.F applied the pattern to ShardedTradeLog — but the trade log uses snprintf-to-buffer + fwrite (P8.3 truncation guard pattern; multi-writer). Same registry idea, different emit style.

**Recognition:** the log column registry pattern has TWO valid implementation variants:
- **Variant A (fprintf direct):** single writer; direct fprintf per column; minimal stack usage. Calib log uses this.
- **Variant B (snprintf to buffer + fwrite):** multi-writer with single row shape OR atomic-row requirement OR truncation guard. Trade log uses this.

**Documented in:** `DESIGN_SPECS/framework-patterns/calibration-log-column-registry.md` "Pattern variants" section (added v5.14.10.F). Future log refactors choose variant based on writer characteristics.

**MetricsLog deferral:** has 2 writers with DIFFERENT row shapes (SlowPath: 26 cols populated + blank details; Event: 13 cols populated + 12 blank middle + populated details). Neither Variant A nor B cleanly fits; needs Variant C OR per-writer registries OR design pass. Captured as TECH_DEBT-031.

**Going-forward rule candidate:** patterns can have multiple valid variants depending on caller-side characteristics. Document variants explicitly in the DESIGN_SPECS doc; let future contributors pick the variant matching their use case rather than forcing one design.

### Pivot 5: Source file length musing → TECH_DEBT-029

**Trigger:** Mid-sprint Caramel observation: "we should probably add a tech debt item to reduce file length in some cases i think, just a musing keep coding"

**Decision:** added TECH_DEBT-029 capturing the source-side analog of CLAUDE.md's "Test file size discipline" (test files > 5k lines must split before adding more). Inventory: ControllerConfig.hpp 2727L, CoreModelZoo.hpp 2239L, StrategyParameters.hpp 1693L, DataStream/EngineTUI.hpp 1382L. Splits are HIGH-RISK refactors (every consumer's #include shifts); each warrants a focused ship.

**Going-forward rule candidate:** operator musings during a sprint should be captured as TECH_DEBT entries even if not actionable in the current ship. Per CLAUDE.local.md auto-write contract (deferred items must be queryable, not buried in chat memory). The triage decision (address now vs defer) happens in the entry itself — but the entry MUST exist.

### Pivot 6: MetricsLog scope cap — pragmatic deferral

**Trigger:** v5.14.10.F's plan said "generalize FOREACH_LOG_COL to MetricsLog + ShardedTradeLog (closes /merge-scan N2 finding)." During execution, MetricsLog's writer-shape divergence (2 writers with different row shapes) made the Variant A/B fit awkward.

**Initial instinct:** ship full refactor anyway (per `feedback_no_defer_for_effort`). LOC estimate ballooned from 150-250 → 300-450; design discussion needed for handling per-writer-shape differences.

**Better decision:** scope-cap .F to ShardedTradeLog only (clean Variant B fit). Defer MetricsLog refactor to a focused future ship via TECH_DEBT-031. The design decision (Option 1 vs 2 vs 3 for handling row-shape divergence) benefits from operator input + can be made when next MetricsLog column addition forces the question.

**Why this isn't effort-avoidance:** the deferral is for VALIDATION ("wait until next column addition forces the design choice") not for AVOIDING WORK. Per `feedback_no_defer_for_effort`, defer is last-ditch — but design-decision-deferral is a valid form when the right answer depends on context not yet available.

**Going-forward rule candidate:** scope-cap decisions should distinguish "deferring effort" (anti-pattern) from "deferring design" (sometimes valid). Effort-deferral tries to ship LESS; design-deferral tries to ship the RIGHT design when context isn't yet available. Both look the same in commit messages; the distinction matters for evaluating whether a defer was sound.

## Architectural surprises (caught at audit time, not at ship time)

### Surprise 1: Stale plan heading + predecessor refs

**Caught by:** Step 1 verification (re-reading plan against MASTER + git log).

**Specifics:** Plan title said "v5.14.11" but renumbered to v5.14.10 in MASTER on 2026-05-10. Predecessor refs cited "v5.14.7" (the maker MVP that was DEFERRED-INDEFINITE) instead of "v5.14.9" (the actual predecessor). **Resolution:** Caught at Step 1; batched 13 mechanical fixes + amendment + re-audit. Mechanical drift is the MOST COMMON audit finding type.

**Lesson:** when MASTER renumbers a sub-ship slot, the plan body needs synchronized updates. Going-forward rule (CLAUDE.local.md): rename plans when ship order/numbering diverges. But the BODY also needs grep + fix for old references. Could be a `/readiness` Check addition (Check 26+: cross-reference plan body against MASTER's current sub-ship numbering).

### Surprise 2: Filename ≠ type name confusion

**Caught by:** First grep for `EnsembleModelZoo` returned "no such file" because the file is named `ML_Headers/CoreModelZoo.hpp` but DEFINES BOTH the `CoreModelZoo<F>` AND `EnsembleModelZoo<F>` structs. Plan claimed "EnsembleModelZoo.hpp" 8+ times.

**Resolution:** corrected plan + handoff doc to cite `ML_Headers/CoreModelZoo.hpp` (filename) for `EnsembleModelZoo<F>` struct (type name). Documented in synthesis doc.

**Lesson:** filename ≠ type name is a recurring trap when types coexist in one file. /trace-deps audits should specifically grep file paths AND type names against actual code, not assume file path = type name.

### Surprise 3: ML_BuildParameters dispatch line-ref drift

**Caught by:** /trace-deps verification.

**Specifics:** Plan said dispatch at "Strategies/StrategyParameters.hpp:~835". Actual location post-v5.14.9 was lines 887-1009 (~80-line shift). Caused by intervening v5.14.9.F.2 ML_CFG_FLAG bitmap migration + v5.14.0/v5.14.1.E Ridge override insertion.

**Resolution:** corrected line refs in plan; documented "post-v5.14.9.F.2 dispatch shifted ~80 lines" in handoff for future sessions.

**Lesson:** when a plan is older than ~1 sprint cycle, line refs are likely stale. /trace-deps should re-grep all file:line claims and emit a "stale line refs" report as standard output, not a special finding.

### Surprise 4: TUISnapshot scope confusion in tests

**Caught by:** Build verify after writing first batch of v5.14.10.B tests.

**Specifics:** Tests used `EngineTUI::TUISnapshot::PerCoreSnap::MASK_*` qualified name; compiler reported "EngineTUI::TUISnapshot has not been declared." Reading the file revealed TUISnapshot is at TOP-LEVEL namespace (not nested in EngineTUI struct). Two scopes had to be fixed: B.7 test scope + D.1 test scope.

**Resolution:** changed all `EngineTUI::TUISnapshot::...` → `TUISnapshot::...`. Used Edit replace_all (safe — no other "EngineTUI::TUISnapshot" tokens elsewhere).

**Lesson:** when adding tests for nested constants in a struct, verify the namespace structure with `rg "^struct" file.hpp` BEFORE writing the qualified name. Saves a build cycle.

### Surprise 5: Test bug — comparison loop checked all 8 arms but only n_arms=4 are persisted

**Caught by:** persistence round-trip test failed 3/4 (mu_post + precision_post + total_pulls) but rng_state passed.

**Specifics:** Save/Load only persist the FIRST n_arms entries (arms 4-7 stay at their pre-load value). Test's comparison loop checked all 8 arms but pre-zeroed all 8 to sentinel 999.0. Arms 4-7 stayed at 999 post-load while pre-save had been 0 → comparison failed.

**Resolution:** updated comparison loop to only check `tb->n_arms` entries (active arms). Renamed test labels to clarify "active arms" scope. All 4 round-trip tests then passed.

**Lesson:** test bugs are easy when the test's data setup doesn't match the system's persistence semantics. Save/Load only round-trips ACTIVE arms; tests should mirror that scope. When debug binaries reproduce the persistence flow, they often catch test bugs vs implementation bugs.

### Surprise 6: IsReadyForInference contract change broke v5.14.2.E.1 contract test

**Caught by:** Build verify after extending FOREACH_ENSEMBLE_POST_LOAD with Thompson init.

**Specifics:** `EnsembleModelZoo_IsReadyForInference` predicate gained a new check (Thompson init flag required when primary_count >= 2). This BROKE the v5.14.2.E.1 contract test which only set `initialized_bandits=1` + `initialized_exit_bandits=1` but not `initialized_thompson_bandits=1`. Test now returned 0 (NOT ready) instead of 1 (ready).

**Resolution:** updated v5.14.2.E.1 contract test to also set `initialized_thompson_bandits=1` to mirror the new contract. Renamed test label to reflect the extended contract.

**Lesson:** when a predicate's CONTRACT changes (not just its body), all callers' contract tests need synchronized updates. Could be a `/readiness` Check addition (Check 28+: predicate-contract-changed audit — grep callers of changed predicates).

### Surprise 7: HOT_PATH_CHANGELOG.md is a workspace symlink (Edit refuses)

**Caught by:** First Edit attempt to write the v5.14.10 entry returned "Refusing to write through symlink."

**Specifics:** `DOCS/HOT_PATH_CHANGELOG.md` is a per-file symlink to `/home/caramel/code/tick-trader-percore-workspace/DOCS/HOT_PATH_CHANGELOG.md` per the v5.11.43 DOCS migration. Same applies to PARITY_ISSUES.md and TECH_DEBT.md.

## Going-forward rule candidates (extract to CLAUDE.local.md if validated)

1. **Per-arm reward observability is a load-bearing assumption** — when applying generic ML/bandit critiques to this codebase, first check `CoreModelZoo.hpp:881-882` reward attribution model. The "shadow rewards are counterfactual" argument is true in pull-based bandits but FALSE in prediction-graded bandits. Could codify as CLAUDE.md item 24+ or a new DESIGN_SPECS doc.

2. **Pattern variants are valid; document them explicitly** — log column registry has Variant A (fprintf direct) + Variant B (snprintf to buffer). Force-fitting MetricsLog to one variant would be premature. Variant taxonomy in DESIGN_SPECS docs lets future contributors pick the right shape rather than wedging into the wrong one.

3. **Effort-deferral vs design-deferral** — `feedback_no_defer_for_effort` says defer is last-ditch. But DESIGN-deferral (waiting for context to make the right design choice) is a valid form. Distinction matters for evaluating defer decisions in retrospect. Could be added to CLAUDE.local.md as a clarification on the existing rule.

4. **Mechanical citation drift is the most common audit finding** — pre-coding audits should run a "stale-claim audit" (re-grep all file:line refs against HEAD) as a first sub-step. Currently it's implicit in /trace-deps; could be promoted to a standalone Check or Step.

5. **Filename ≠ type name confusion (recurring trap)** — when a file defines multiple types or when type names diverge from filenames, /trace-deps should specifically check both AS SEPARATE QUERIES. CoreModelZoo.hpp + EnsembleModelZoo<F> + ThompsonBandit.hpp + BanditAlgorithmRegistry.hpp all coexist in this codebase; future audits should expect this.

6. **Predicate-contract-changes need callers' tests updated** — when extending predicates like IsReadyForInference, /readiness should grep callers for contract-test patterns (`check(... predicate(...) == 1)` or similar). Synchronized updates prevent the "1 test fails after extension" cycle.

7. **DOCS/ symlinks must be edited via workspace path** — the v5.11.43 migration means `DOCS/HOT_PATH_CHANGELOG.md` + `DOCS/PARITY_ISSUES.md` + `DOCS/TECH_DEBT.md` + others are workspace symlinks. Direct Edit refuses; must edit via `tick-trader-percore-workspace/DOCS/<name>`. Could be added to /handoff Step 7 + skill docs.

8. **Audit-driven discipline is working at scale** — v5.14.10's 5-audit pre-coding gate + amendment re-audit caught 3 PARITY issues + 8 mechanical drift items + 1 over-conservative defer recommendation. Worth continuing the discipline; possibly tightening (Check additions per #4-#7 above).

## Lessons synthesis

**1. Audit-driven discipline scales.** v5.14.10's 5-audit pre-coding gate + amendment re-audit caught everything that mattered before code touched. 3 PARITY issues that would have shipped silently. 8 mechanical drift items that would have tripped Step 0 immediately. 1 defer recommendation reversed (cfg=2) via Caramel pushback. Net: zero rollbacks across 7 sub-ships.

**2. Cache-layout strategies converge through iteration, not first-pass design.** The 4-question conversation with Caramel about Thompson display fields took the design from 200B raw → 104B optimized → unified bandit cluster. Each pass exposed a layer the previous design missed. This is normal for cache-layout work; budget for iteration in future cache-sensitive ships.

**3. Wire-format byte preservation discipline is generalizable across surfaces.** Applied 3× in v5.14.10:
- thompson_state.json (NEW format; full Layer 1-6 discipline applied)
- Bandit_SaveJSON (TECH_DEBT-027; opportunistic locale pin close)
- calib log refactor (byte-identical output preserved by D.3+D.4 tests)

The discipline doc now has 3 reference applications. Future serialization work should reference it.

**4. Pattern Variant A vs B emergence — log column registry has 2 valid implementation styles.** Calib log uses Variant A (fprintf direct; single writer); trade log uses Variant B (snprintf to buffer + fwrite; multi-writer with truncation guard). MetricsLog DOESN'T fit either cleanly (multi-writer with different row shapes); deferred to TECH_DEBT-031 with 3 design options enumerated. The pattern's flexibility (multiple variants) is a feature, not a bug.

**5. Class 18 mirror prevention via PostLoadSetup registry pattern (v5.14.2.E.1) applied 3× now.** init_bandits + init_exit_bandits (v5.13.4) + init_thompson_bandits (v5.14.10.C). Each new init/load pair adds 1 row to FOREACH_ENSEMBLE_POST_LOAD; auto-flows to all 3 callers (boot, backtest, hot-swap). The registry IS the structural fix; without it, each new ensemble surface would risk a missed init call site.

**6. Caramel's "harder upfront for easier future" rule validated AGAIN.** Multiple times in v5.14.10:
- Decision A (RETROFIT FOREACH_BANDIT_ALGORITHM vs DEFER): retrofit chosen; future bandit algos = 1 row each
- Decision B (ABSORB FOREACH_CALIB_LOG_COL vs DEFER): absorb chosen; future log columns = 1 row each
- Decision E (PerCoreSnap layout audit ADD vs DEFER): add chosen; future ML telemetry inherits cluster pattern
- N2 absorption (FOREACH_TRADE_LOG_COL .F): absorb chosen; closes /merge-scan finding immediately

Each "harder upfront" choice paid off in the same sprint via the registry-driven additions in subsequent sub-tags. The rule is reliable.

**7. v5.14.10 postmortem authoring discipline.** Postmortems for v5.14.5 / .6 / .8 / .9 exist; v5.14.7 was DEFERRED-INDEFINITE so no postmortem. v5.14.0/.1/.2/.3/.4 may not have postmortems (predates the discipline). v5.14.10 postmortem (this doc) authored 2026-05-11 post-ship — establishes the cadence: every major sub-ship gets a postmortem within ~1 day of close while context is fresh.
