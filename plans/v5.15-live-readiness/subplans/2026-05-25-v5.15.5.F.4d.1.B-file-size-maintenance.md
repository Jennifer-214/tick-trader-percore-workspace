## Design space + future-oriented choices

### Decision A — Subfolder vs flat-sibling split form

| Option | Description | Verdict |
|---|---|---|
| **(a) Subfolder named after original; top-level shim** | `CoreFrameworks/EngineSharded.hpp` (shim re-exports) + `CoreFrameworks/EngineSharded/{Run,Async,SlowPath,Boot}.hpp` | **CHOSEN** |
| (b) Flat sibling files with prefix | `CoreFrameworks/EngineShardedRun.hpp`, `EngineShardedAsync.hpp`, etc. | rejected — prefix repetition pollutes top-level dir; harder to spot multi-file units |
| (c) Subfolder; no top-level shim | All callers update include path | rejected — breaks include-line stability; invasive |

**Rationale for (a):**
- **Explicit grouping** — `EngineSharded/` directory tells you "multi-file unit" at a glance
- **Clean sub-names** — `EngineSharded/Async.hpp` vs `EngineShardedAsync.hpp` (no prefix repeat)
- **Include stability** — external callers continue `#include "CoreFrameworks/EngineSharded.hpp"` unchanged (shim re-exports)
- **Scales** — adding sub-files later doesn't pollute parent directory
- **Sister precedent** — `workspace/DOCS/tech-debt/{open,closed,in-flight}.md` (TECH_DEBT-116 ship) already uses subfolder pattern for docs; extending to source code is natural sister application
- **Mirrors common C++ patterns** — LLVM / Boost / many large libraries organize this way

**Trade-off:** One extra layer of indirection (top-level shim). Acceptable for organizational clarity.

**Codification implications:** `file-size-split-discipline.md` v1.0 currently codifies FLAT-sibling pattern only (examples cited). Subfolder pattern is a NEW addition codified as Stage 2 DRAFT amendment at `.B.5` planning → Stage 3 first canonical at `.B.6` ship close (`EngineSharded/` reorg = first canonical).
