# v5.15.5 — Per-Horizon TP/SL on Serving Side

**Goal.** Close the train-serve barrier-parity gap. Each
multi-horizon model is trained against label-specific TP/SL (via
v5.13.5 `Label Kind CSV` + TP/SL CSV inputs), but the live engine
currently reads single `cfg.ml_tp_pct` / `cfg.ml_sl_pct` and applies
them to all positions regardless of which horizon dominated.
Model trained on 0.03% barrier labels can fire a trade at 0.05%
TP — train-serve drift class. Required prerequisite for credible
multi-horizon ensemble support in production (Caramel 2026-05-12:
"required for multi-horizon/multi-model support").

**Critical-function classification.** Touches load-bearing parity
surface: stamp body → ezoo state → slow-path blend → ParameterSlot
seqlock → hot path consumer. Cfg-drift Tier 1 promotion can refuse
loadable models in strict mode. Plan-first audit per
CLAUDE.local.md "Going-forward rule for new plans". `/readiness`,
`/trace-deps`, `/parity-check` all run before coding starts.

## Design — Option D (mode-dispatch with shadow): FOREACH_BARRIER_BLEND_MODE registry covering LEGACY / BLEND / DOMINANT / BOTH-variants

**Operator framing (Caramel 2026-05-12 iteration):**

The A-vs-B engineering merit is a genuine coin-flip — depends on the
trained ensembles' regime stability + barrier-CSV diversity, which is
empirical. Instead of committing to one, ship BOTH modes + a shadow
path (mirror of v5.14.10.B Thompson dual-mode). Operator picks the
driving mode + can run BOTH for paper-test comparison. Tech debt
reductions (X-macro registries, AUTOPOPULATE, dropdown-from-FOREACH
pattern just shipped on Label Kind CSV) make adding 5 modes cheap.

**FOREACH_BARRIER_BLEND_MODE registry** (new
`ML_Headers/BarrierBlendModeRegistry.hpp`):

```cpp
#define FOREACH_BARRIER_BLEND_MODE(X) \
    X(LEGACY,                "legacy",                "cfg-direct (pre-v5.15.5 behavior)") \
    X(BLEND,                 "blend",                 "Σ wᵢ · barrierᵢ — bandit-weighted blend") \
    X(DOMINANT,              "dominant",              "argmax(weights) picks one arm's barriers") \
    X(BOTH_BLEND_DRIVES,     "both_blend_drives",     "Blend drives trade; dominant logged for compare") \
    X(BOTH_DOMINANT_DRIVES,  "both_dominant_drives",  "Dominant drives trade; blend logged for compare")

// Auto-generated MODE_BARRIER_BLEND_* constants + MODE_BARRIER_BLEND_COUNT
enum {
#define X(id, name, desc) MODE_BARRIER_BLEND_##id,
    FOREACH_BARRIER_BLEND_MODE(X)
#undef X
    MODE_BARRIER_BLEND_COUNT
};
```

**Per-mode semantics:**
- `LEGACY` (default v5.15.5; safe fallback): cfg.ml_tp_pct /
  cfg.ml_sl_pct direct, bytewise identical to pre-v5.15.5 behavior.
  Per-arm barriers loaded but unused. Operator opts in to new modes.
- `BLEND`: `tp = Σ wᵢ · per_arm_buy_tp_pctᵢ` using `weights_buf[]`
  (post-bandit / post-Ridge). Smooth, consistent with prediction
  blend.
- `DOMINANT`: `tp = per_arm_buy_tp_pct[argmax(weights_buf)]`. Exact
  per-trade train-serve match for the firing arm. Can flicker
  between arms in ambiguous regimes.
- `BOTH_BLEND_DRIVES`: blend value drives `params->tp_pct`; dominant
  value computed + recorded in shadow ring for offline compare. Pair
  with paper-test mode to compare hypothetical fills.
- `BOTH_DOMINANT_DRIVES`: dominant value drives; blend computed +
  recorded in shadow ring.

**Shadow telemetry (modes 3-4 only):**
- Per-cycle: push `(actual_tp, shadow_tp, actual_sl, shadow_sl,
  weights_buf, dominant_idx)` into a ring buffer at
  `EnsembleModelZoo<F>` (size 256, similar to existing
  `exit_reward_ring`).
- Per-trade-fire: log line emitted with both barriers visible.
- Aggregate JSON: `<core_model_dir>/barrier_mode_shadow_stats.json`
  with cumulative counts + barrier deltas (mirror
  `bandit_state.json` pattern, `CoreModelZoo.hpp:2040`).

**Bandit invariant.** Per-arm direction-graded reward holds
(CLAUDE.md item 24). Shadow mode is mathematically valid because
rewards aren't gated by which mode fired — direction-grading
each arm against actuals works in either mode.

**Latency profile per mode (slow-path only):**
- `LEGACY`: 0 ns added (cfg direct as before)
- `BLEND`: +20-30 ns (8-iter Σ wᵢ · barrierᵢ + 2 FPN conversions)
- `DOMINANT`: +10-15 ns (8-iter compare-and-select argmax + 2 FPN
  conversions)
- `BOTH_*`: +35-50 ns (both paths computed + ring push)
- **Hot path: 0 ns regardless of mode.** All work slow-path.

**Tech-debt-leveraged ease.** Per Caramel's "the tech debt reductions
we did make this easy to add right" — yes:
- X-macro registry pattern (CLAUDE.md item 13) → mode dispatch
  auto-generated; adding a 6th mode = 1 row
- STAMP_BOUND_CFG_AUTOPOPULATE (item 21) → cfg field auto-wired
  into stamp body + cfg-drift check
- Dropdown-from-FOREACH pattern (v5.13.5; just-shipped Label Kind
  CSV tooltip iteration) → GUI dropdown auto-derives mode list
- Bitmap flag cohort audit (item 18 set 2026-05-11) → catches
  cohort drift if mode-related siblings emerge
- AUTOPOPULATE companion (item 21) → no manual per-callsite
  population, no recurrence of v5.9.5b production-caller class

## Structural-fix additions (operator decision 2026-05-12 post-audit)

Three structural-fix opportunities surfaced during the post-audit
design discussion. All bundled into v5.15.5.A:

### #1 — MODE_FLAGS[] bit-packed lookup table (Rule 8 Pattern 8b)

Extend FOREACH_BARRIER_BLEND_MODE tuple with a 3rd column for
bit-packed mode semantics. Auto-generates a lookup table:

```cpp
// ML_Headers/BarrierBlendModeRegistry.hpp
constexpr uint8_t MODE_F_BLEND_DRIVES    = 1 << 0;
constexpr uint8_t MODE_F_DOMINANT_DRIVES = 1 << 1;
constexpr uint8_t MODE_F_SHADOW_ACTIVE   = 1 << 2;
constexpr uint8_t MODE_F_LEGACY          = 1 << 3;

#define FOREACH_BARRIER_BLEND_MODE(X) \
    X(LEGACY,                MODE_F_LEGACY,                                  "...") \
    X(BLEND,                 MODE_F_BLEND_DRIVES,                            "...") \
    X(DOMINANT,              MODE_F_DOMINANT_DRIVES,                         "...") \
    X(BOTH_BLEND_DRIVES,     MODE_F_BLEND_DRIVES | MODE_F_SHADOW_ACTIVE,     "...") \
    X(BOTH_DOMINANT_DRIVES,  MODE_F_DOMINANT_DRIVES | MODE_F_SHADOW_ACTIVE,  "...")

constexpr uint8_t MODE_FLAGS[MODE_BARRIER_BLEND_COUNT] = {
#define X(id, flags, doc) [MODE_BARRIER_BLEND_##id] = (flags),
    FOREACH_BARRIER_BLEND_MODE(X)
#undef X
};

// Slow-path dispatch — fully branchless via mask compute:
uint8_t flags = MODE_FLAGS[mode];
bool blend_drives    = flags & MODE_F_BLEND_DRIVES;     // cmov
bool dominant_drives = flags & MODE_F_DOMINANT_DRIVES;  // cmov
bool shadow_active   = flags & MODE_F_SHADOW_ACTIVE;    // cmov
// Single branchless ternary chain — no nested if/else:
FPN<F> tp_pct = blend_drives    ? tp_blend
              : dominant_drives ? FPN_FromDouble<F>(per_arm_barriers[dominant_h].tp)
              : config->ml_tp_pct;
```

Adding 6th mode = 1 row + 1 flags expression. ~30 LOC.

### #3 — Layout C: AoS `struct{tp,sl}[8]` for per_arm_barriers

Confirmed best for our access patterns post-arithmetic check:
- Cache miss cost (~100ns cold) is 75× the AVX cycle delta (~1.3ns)
- C buys 1 cache line for BOTH DOMINANT and BLEND access patterns
- AVX-friendly with ~12 cycles (negligible vs the cache savings)
- Smallest storage (64B per ensemble; 1 cache line)
- See Phase A Step 1 design rationale block above

Cumulative .A scope expansion: +110 LOC (#1: 30, #2b: 50, #3: replaces existing per_arm_* design).
Updated v5.15.5.A total: ~990 LOC.

## Phase A — Per-arm barrier load (no behavior change)

**Goal.** EnsembleModelZoo carries per-loaded-model barriers.
Behavior unchanged (blend not wired yet).

**Step 0.** Verify FOREACH_STAMP_BOUND_MODEL_CONST_PRE_CFG
registry includes `label_tp_pct` + `label_sl_pct` rows in
`ML_Headers/StampBoundModelConstRegistry.hpp`. If absent: add per

**Step 1.** Extend `EnsembleModelZoo<F>` (CoreModelZoo.hpp) with
**Option C (AoS struct{tp,sl}[8])** for optimal cache locality:

```cpp
// v5.15.5 — per-arm trained barriers (loaded from stamp body).
// AoS struct{tp,sl}[8] = 64B = exactly 1 cache line, alignas(64).
// DOMINANT mode read: 1 line (both tp+sl colocated for the arm).
// BLEND scalar read: 1 line (single iteration over all 8 structs).
// BLEND AVX-512 (v5.15.6 deferred): _mm512_load_ps loads all 16
// interleaved floats; permute to dup weights + masked reductions
// extract tp_sum / sl_sum. ~12 cycles total (~4 ns at 3 GHz);
// negligible vs the ~100 ns saved on a cold-cache miss.
//
// Why Option C (AoS) over SoA: 1 cache line guaranteed for BOTH
// DOMINANT and BLEND access patterns. SoA float[8]+float[8] adjacent
// achieves the same 1-line footprint, but AoS is structurally
// clearer ("per_arm_barriers[h].tp" vs parallel-array idiom) and
// trivially handles future per-arm-field additions without
// re-clustering. SoA double[8] separate would be AVX-natural but
// costs 2 cache lines per DOMINANT lookup — net worse given the
// 75× cost ratio of cache miss (~100ns) vs AVX cycle delta (~1.3ns).
//
// NOT EXIT-SIDE — exit predictor is signal-based, not barrier-based
// (see "NOT in scope" below).
struct alignas(64) PerArmBarriers {
    float tp;
    float sl;
};
PerArmBarriers per_arm_barriers[ENSEMBLE_HORIZON_MAX];  // 64B = 1 line
```

**Cache line consideration.** New arrays are
`ENSEMBLE_HORIZON_MAX * sizeof(float) = 8 * 4 = 32 bytes` each.
Group together at end of struct OR in a cache-aligned cluster
with other per-arm metadata. Phase A includes a sizeof + offset
audit per latency-path-discipline.md Rule 1 (field-span analysis).
Since these are slow-path read (once per cycle), cache-line
crossing is acceptable but should be documented.
