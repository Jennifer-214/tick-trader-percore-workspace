# v5.4.1 — Per-core stats reset bug + snapshot version migration

**Filed:** 2026-04-30 (immediately post-v5.4.0 ship)
**Status:** investigating
**Root cause:** unknown, two candidate bugs being separated by user fresh-test

## Symptom (as observed)

Screenshot capture (Apr 30, post-v5.4.0 paper run) shows:

```
Account:
  realized: $-3.32  unrealized: $+5.00
  gross:    $+1.68  net: $+1.68  fees: $0.00     ← gross != realized
                                                  ← fees=0 inconsistent with trade history

Per-Core P&L:
  Core 0 MOM   $+0.00  $0.0000  0/0   0%   ← all four cores blank
  Core 1 EMA   $+0.00  $0.0000  0/0   0%
  Core 2 AUTO  $+0.00  $0.0000  0/0   0%
  Core 3 DIP   $+0.00  $0.0000  0/0   0%

Trade History (4 trades):
  C0 B MOM TP $+0.61 fee $1.50
  C0 A MOM TP $+0.61 fee $1.50
  C1 B EMA SL $-2.27 fee $1.50
  C1 A EMA SL $-2.27 fee $1.50
  → sum P&L = $-3.32 (matches Account.realized)
  → sum fees = $6.00 (NOT matching Account.fees=$0.00)

Stats panel: buys 0 exits 0 W:0 L:0  (all blank)
```

User report: "when you start and close and reopne, the trade log tracks
stuff but every other stat resets which is bad, and will lead to per
core bleed."

## Two candidate bugs, separable

### Bug A — snapshot version migration too strict

`SHARDED_SNAPSHOT_VERSION` was bumped 3 → 4 in v5.4.0 Phase 1
(`ShardedSnapshotPersist.hpp:66`). The loader is strict:

```cpp
// ShardedSnapshotPersist.hpp:288
if (fread(&version, 4, 1, f) != 1 || version != SHARDED_SNAPSHOT_VERSION) {
    fprintf(stderr, "[snapshot] %s version %u != current %u — refusing load\n", ...);
    fclose(f); return 0;
}
```

Any snapshot from a pre-v5.4.0 build is rejected silently (well, with
a stderr log). Engine inits all state to zero. Trade log JSONL is a
separate file and survives.

**Fix candidate (a):** load-with-grace — if version is older but
still recognizable, read the fields that exist in both versions, skip
the v5.4.0-only fields (just `strategy_state_kind` per core). Old
snapshots get a soft-import: balance, realized_pnl, per-core counters
all restored; strategy_state_kind defaults to 0xFF (Phase 1 sentinel).

**Fix candidate (b):** version-bump policy — pin per-version readers
in the load function, dispatched by version number. Cleaner long-term
but bigger code change.

(a) is cheaper for v5.4.1; (b) is the right shape for v6+.

### Bug B — per-core counters don't bump even within one session

Even with a clean v4 snapshot (or no snapshot, fresh start), the
screenshot's evidence suggests per-core counters are zero while the
4 trades' aggregate realized P&L did make it to OMS-level
`realized_pnl`. Specifically:

- `Account.realized = $-3.32` matches sum of 4 trade P&Ls — so
  `oms->realized_pnl` IS being bumped on each exit.
- `state->cores[c].core_realized` for ALL c is zero — increment at
  `ControllerEventLoop.hpp:959` (`ctx.core_realized = FPN_Add(...)`)
  is never running for these trades.

`EventLoop_DrainPostFillOneCore` is the function with that increment.
Wrapper `EventLoop_DrainPostFill` iterates registered cores and calls
OneCore for each. Wrapper is called from the drainer thread's loop.

**Threading topology check (per_core_slow default, the production
arch):** drainer thread is sole caller of `OrderManager_Tick` +
`drain_post_fill`. Each per-core slow-path thread does its own
RebuildOneCore but does NOT call DrainPostFill (drainer owns OMS
state). This is correct by design.

**Hypotheses for why DrainPostFill loses the counter increments:**

1. **`my_mask` mismatch under partials.** Line 918:
   `my_mask = (1 << (core_id*2)) | (1 << (core_id*2 + 1))` for partial_on=1.
   For core_id=0: bits 0+1. For core_id=1: bits 2+3. Trade history shows
   C1 A and C1 B trades — slots 2 and 3. If `last_closed_mask` had bit
   2 + 3 set, core_id=1's iteration should pick them up. Verify by
   logging `last_closed_mask` and `my_mask` per-iteration on entry to
   `DrainPostFillOneCore`.

2. **`last_closed_mask` cleared before the loop runs.** Line 944
   `oms->last_opened_mask &= ~my_mask` — only clears MY bits. But
   what if some upstream code clears the whole mask before
   `DrainPostFillOneCore` sees it?

3. **Drainer thread not calling DrainPostFill in per_core_slow arch.**
   Verify by reading `EngineSharded.hpp` around line 1422
   (`drain_with_submit`) — specifically that `drain_post_fill` is in
   the loop for both centralized AND per_core_slow arches.

4. **CoreContext pointer aliasing.** If `state->cores[c]` array is
   somehow not aligned correctly per core, the increment hits the
   wrong core's struct. Verify by comparing
   `&state->cores[0].core_realized` vs `&state->cores[1].core_realized`
   addresses; they should differ by exactly `sizeof(CoreContext<F>)`.

5. **Sharded snapshot save zeros counters in the wrong place.** If
   between trade close and snapshot save, something resets per-core
   counters. The save itself just reads — but if snapshot save is
   triggered and then the engine crashes/restarts mid-save, the file
   could have partial / mismatched data. (Unlikely given sane atomic
   write semantics.)

**Repro plan:**

1. Stop engine.
2. Move aside the snapshot file (default path in `engine.cfg` ->
   `snapshot_path`).
3. Restart; let the engine close at least 2 trades.
4. Inspect:
   - Account header `realized` vs Trade History sum — should match.
   - Per-Core P&L — should be non-zero on cores that traded.
   - Stats panel `buys/exits/W/L` — should be non-zero.
5. If per-core stays zero, it's Bug B — instrument
   `DrainPostFillOneCore` with `Health_Log` and re-run.
6. If per-core bumps correctly, it's Bug A — old snapshot was the
   single source of the visible mismatch.

## Fix design (after repro narrows)

### If Bug A only

Add a graceful pre-v5.4.0 load path. Keep version 4 reader as the
canonical path; when we see version 3, read the v3-shaped fields,
default `strategy_state_kind` to 0xFF, log "migrated v3 → v4
snapshot — strategy state will reinit on next cadence."

Test: synthesize a v3 snapshot blob, load with v4 binary, verify
`oms->realized_pnl` and `core_realized[]` restored, no crash.

### If Bug B only

Instrument first to confirm WHICH of the 5 hypotheses. Most likely
Hypothesis 1 (mask mismatch) or Hypothesis 3 (drainer doesn't call
DrainPostFill in per_core_slow). Once narrowed, fix is:
- (1) verify the partials mask formula matches OMS_HandleFill's
  slot-write geometry exactly. Add an assert at boot.
- (3) wire `drain_post_fill` into the drainer loop unconditionally
  (it's slow path — cost is negligible — and structural parity
  prevents this class of bug).

### If both

Ship Bug A fix first (smaller, isolated). Then Bug B fix in a
follow-up commit on the same v5.4.1 branch.
