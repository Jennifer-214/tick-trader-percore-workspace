## Candidate 1 — DELTA_DIVERGENCE / volume-divergence feature

**Hypothesis:** Current 34-feature pack has 7 pure-volume features
(VOLUME_SLOPE, VOLUME_DELTA, VOLUME_AVG, CUMDELTA, FLOW_10S/1M/5M,
LARGE_TRADE_Z) + 1 explicit price↔volume interaction (VWAP_DEV).
XGBoost CAN learn cross-features ("high volume + up-slope = real")
implicitly via tree splits — but only at the cost of tree depth +
amplifying noise. An EXPLICIT engineered "is this price move backed
by volume?" feature would reduce tree depth + sharpen signal.

**Proposed feature:**
```
DELTA_DIVERGENCE = sign(CUMDELTA) - sign(price_slope)
- Price up + buyer volume up   = real (returns 0)
- Price up + seller volume up  = MANIPULATED / spoof / wash (returns ±2)
- Price down + buyer volume up = capitulation? (returns ±2)
```
Or stronger: `MOVE_VOLUME_CONFIRMATION =
(abs(price_slope) / price_stddev) × (volume_ratio_short_vs_long)`.
High when price moves on heavier-than-baseline volume.

**Engineering shape:** new row in `FOREACH_FEATURE`
(`ML_Headers/FeatureRegistry.hpp:294`) + new `ML_Compute_DeltaDivergence`
function (~20 LOC; uses existing CUMDELTA + short_slope from
RollingStats — no new state). FEATURE_REGISTRY_HASH flips
automatically; old stamps invalidate cleanly. ~half-day code +
forced retrain of all existing models.

**Re-trigger condition** (from v5.12 Phase 4.A finding):
- Paper-test reveals high false-positive rate on 3-class barrier in
  low-volume conditions
- Operator observes specific manipulation events (spoof / wash) where
  price signal fired but volume didn't confirm
- A/B test (current 34-feature model vs 35-feature with divergence)
  shows the divergence model has materially better precision on
  manipulation-sensitive periods

**Cost when re-triggered:** ~half-day code + ~hours of retrain time
(operator-side, scaled to dataset size). Parity preserved by
construction (CLAUDE.md item 14-15).

**v5.12 capture:** drafted as separate stub
`plans/2026-05-08-v5.13-CANDIDATE-volume-divergence-feature.md`
(if drafted) OR consolidated into this file as Candidate 1.

## Candidate 2 — Buy-side / sell-side specialized models

**Hypothesis:** Current ML pipeline has ONE buy-decision model.
Exits are rule-based (TP/SL/trailing-SL/time-exit). Adding a
sell-side ML model (`exit_signal` slot in EnsembleModelZoo, slot
already exists per FUTURE_ML "Multi-role zoo", unexercised today)
lets the model decide when to exit BEFORE TP based on signal.

**Safety shape (recommended):**
- TP stays HARD (cfg `tp_pct`). Cap on the upside, fires
  unconditionally as today.
- Exit model can ONLY EXIT EARLIER than TP. Never override TP upward.
- Trailing-SL stays as today (acts as floor).
- Three-layer exit logic: (1) ML says exit → exit early; (2) ML
  silent + price hits TP → TP fires; (3) ML silent + price hits
  trailing-SL → trailing-SL fires.

**Worst case:** model misfires → premature exit, revenue lost
(NOT loss amplified). Best case: exit at peak before TP, capture
more upside than fixed TP would.

**Why this is strictly better than current:** trailing-SL is already
"model-controlled exit" (just a dumb rule-based model). ML exit is
the smart version. As long as TP stays hard, expected value ≥
current.

**Engineering shape:**
- Train an `exit_signal` model (separate label kind: target =
  "should exit in next N ticks"; binary OR 3-class
  PEAK_NOW/HOLD/EXIT_NOW)
- Loader populates `exit_signal_handles` slot in EnsembleModelZoo
- New strategy predicate in EVENT_LOOP_TIME_EXIT or new EXIT_GATE
  layer adjacent to TimeExitOneCore
  (`CoreFrameworks/ControllerEventLoop.hpp:2641`)
- Hot path remains untouched (exit decisions are slow-path cadence;
  TP/SL still on hot path)

**Effort:** ~1 week including label generation infrastructure +
per-handle training pipeline + safety gates.

**Re-trigger condition** (from v5.12 Phase 4 finding):
- Paper-test P&L attribution shows current trailing-SL + TP is
  leaving meaningful upside on the table (positions exit at TP
  before peak when peak is identifiable)
- Specific symptom: drawdown-from-peak > X% on a meaningful fraction
  of TP-fired exits

## Candidate 3 — Multi-model bandit per side

**Hypothesis (operator intuition 2026-05-08):** Each SIDE (buy / sell)
benefits from multiple model TYPES (regression for trend strength,
3-class barrier for regime-conditional direction, binary for fast
mean-reversion). Bandit per side picks per-regime which TYPE wins.

**Architecture (mirror per side):**
- Buy side bandit: arms = {regression_h50000, binary_h1000,
  barrier_h7500}; reward = realized P&L of trades initiated under
  that arm
- Sell side bandit: arms = {regression_exit, binary_exit, barrier_exit};
  reward = realized P&L of exits attributed to that arm (counterfactual
  vs alternative timings)

**Why per side:**
- Different objectives: buy = "right entry"; sell = "right exit"
- Different feature distributions: at-entry features vs at-position
  features (exit needs unrealized P&L, time held, drawdown depth, NOT
  just spot regime signals)
- Different reward attribution: entry reward = clean per-trade;
  exit reward = counterfactual (= realized exit price vs alternative
  exit timings within same trade)
- Bandits learn fastest when action space is bounded — forcing one
  bandit to learn entry+exit doubles action space

**Bandit infrastructure already exists:**
- `ML_Headers/BanditLearning.hpp:51` — `Bandit_GetProbabilities` AVX-512
- `ML_Headers/BanditLearning.hpp:222` — `Bandit_Update`
- v5.10.0a.G shipped per-regime bandit weights infrastructure
- Adding a SECOND bandit instance (one per side) reuses same code

**Engineering shape:** ~1-2 weeks
- Buy-side bandit: existing infrastructure
- Sell-side bandit: new instance; reuses ML_Headers/BanditLearning.hpp
- Reward attribution: per-trade callback → buy-bandit on trade open;
  per-exit callback → sell-bandit on trade close
- Strategy code: `MLStrategy.hpp` reads from primary handles (post
  v5.12.3.E cleanup); add an `ExitMLStrategy` parallel for sell-side
- v5.11.62 invariant preserved: all role semantics live at loader +
  Model_Predict layer; strategy code is role-agnostic

**Re-trigger condition:**
- Buy/sell side specialized models (Candidate 2) shows alpha
- Phase 4.A mixed-output paper-test reveals model TYPE matters
  per-regime (= multi-arm bandit on the buy side has
  distinguishable per-regime preferences)

**Effort if Candidate 2 ships first:** ~1 week (add sell-side bandit
+ reward attribution; reuse infrastructure)

## Candidate 4 — Multi-strategy bandit

**Hypothesis:** Current AUTO mode picks strategy via cfg + regime
hint. Replace with a bandit that LEARNS per-regime which STRATEGY
wins (DIP vs MOMENTUM vs EMA_CROSS vs ML).

**Different from Candidate 3:** Candidate 3's bandit is WITHIN-ML
(model TYPE selection). This Candidate is ACROSS-strategy
(strategy-class selection).

**Engineering shape:** ~1 week
- AUTO mode currently lives in `Strategies/StrategyParameters.hpp`
  dispatcher. Replace cfg-pick with bandit-pick at strategy
  selection time.
- Bandit reward: realized P&L of trades attributed to the
  strategy-arm
- Per-regime: separate bandits per regime (or one bandit with regime
  as a context feature)

**Re-trigger condition:**
- Phase 4 finding shows specific strategies (e.g. DIP) win in
  RANGING regimes consistently while ML wins in TRENDING — i.e.
  AUTO's current cfg-based regime pick is leaving alpha on the table

**Risk:** AUTO mode complexity. Currently AUTO is a pass-through;
bandit-AUTO becomes a state machine. Mitigation: opt-in cfg
`auto_strategy_via_bandit=0` (default); operator flips on after
validation.

## Candidate 5 — Online learning on booster

**Source:** `plans/FUTURE_ML.md` #3.

**Hypothesis:** Markets drift. Bandit weights already learn online
(per-arm). Going further: online-update the underlying booster via
XGBoost's `XGBoosterUpdateOneIter` on a recent-trades buffer.

**Engineering shape:** moderate. New state on ModelHandle:
`online_updates_since_train` counter; `online_buffer[1024]` ring of
recent (features, outcome) pairs. Periodic update every N trades or
N hours. Stamp body extension records the counter for forensics.

**Risk:** online updates can make model worse if early outcomes are
unrepresentative. Mitigation: shadow comparison — keep frozen
baseline; auto-revert if online-updated model underperforms baseline
by margin.

**Effort:** ~1.5-2 weeks including auto-revert infrastructure.

**Re-trigger condition:**
- Bandit weights stay near-uniform forever (= bandit can't
  discriminate), suggesting the booster needs adaptation
- Paper-test shows model degrades over time on out-of-distribution
  data (model-drift watchdog from v5.10.0e fires repeatedly)

## Candidate 6.5 — Multi-model exit blend strategies

**Source:** Operator question 2026-05-08 ("how would we blend
detecting a valley, and then not selling on the correlated peak,
but using a regression model to determine how long to hold").

**Hypothesis:** Smart exit decisions blend multiple model TYPES
into a composite exit signal. v5.12 Phase 3.A (composite-signal
extractor) + Phase 3.B (mixed-output normalizer) provide the
infrastructure. This Candidate is the STRATEGY shape that uses
the infrastructure.

**4 blend patterns worth paper-testing** (each with worst-case
fallback to current trailing-SL/TP rule):

### 6.5.A — Composite exit conviction
```
exit_score = +1.0 × barrier.P(peak)
             - 0.5 × regression.continuation_normalized
exit IF exit_score > threshold
```
Smart version of trailing-SL. Two model types blended; bandit
weights the trade-off per regime.

### 6.5.B — Time-decay exit
Exit conviction ramps up if held > regression's predicted hold-time:
```
overhold_factor = max(0, ticks_held - regression.predicted_hold) / regression.predicted_hold
exit_conviction = barrier.P(peak) × (1 + overhold_factor)
```
Forces graceful exit on stale holds.

### 6.5.C — Volume-confirmed reversal
Pairs with DELTA_DIVERGENCE feature (v5.13 candidate):
```
exit IF (barrier.P(peak) > threshold) AND (DELTA_DIVERGENCE ≈ 0 AND VOLUME_AVG > baseline)
```
Gate exits behind volume-confirmed reversal — low-volume reversals
are noise.

### 6.5.D — Ensemble agreement
Exit only when ≥ 2 model types agree:
```
votes = (barrier.P(peak) > t) + (regression.weak > t) + (binary.down > t)
exit IF votes >= 2
```
Cuts false-positive exits when models disagree.

**Engineering shape:** lives entirely in `Model_Predict` composite-
signal layer (Phase 3.A) + per-handle normalizer (Phase 3.B). NO
strategy code changes. Each pattern is a different
`target_classes[]` / `class_weights[]` configuration on the exit-
side ModelHandle.

**Re-trigger condition:** Phase 4.A paper-test reveals that current
trailing-TP/SL leaves identifiable upside on the table (positions
exit at TP before peak; OR positions hold past peak into reversals).
Then pick which of 6.5.A/B/C/D matches the observed failure mode.

**Effort when re-triggered:** ~1 day per pattern (just stamp body
configurations + test); paper-test each in parallel paper-traders;
keep the winner.

## Candidate 6 — Multi-objective models

**Source:** `plans/FUTURE_ML.md` #4.

**Hypothesis:** Single direction probability throws away usable
information. A multi-output model could predict direction +
volatility + timing + holding period.

**Engineering shape:** XGBoost `multi_strategy=multi_output_tree` (recent
versions). Stamp body gains per-output semantic labels. Strategy
reads each output via named getter. Composite-signal extraction
(Candidate 1; v5.12 Phase 3.A) covers the extraction layer.

**Effort:** big. ~2-3 weeks of training-side work because each output
needs labeled training data (direction is easy; volatility needs
post-hoc realized-vol; timing needs finer walk-forward).

**Re-trigger condition:**
- Phase 4.A mixed-output study suggests per-horizon model TYPES help
  (= regime-conditional model preference real). Multi-output is the
  next-tier extension.

## Candidate 7 — Bandit algorithm variants

**Source:** Operator question 2026-05-08 ("are there other types of
bandits or blending we should use? is this just one variant or is it
the latest?").

**Hypothesis:** Current Bandit-Exp3 is the ADVERSARIAL workhorse —
right base for trading because markets shift and prior outcomes
don't predict cleanly. Other variants worth knowing about + when
each becomes interesting.

| Variant | When it wins | Status |
|---|---|---|
| **Exp3** (current) | Adversarial; markets shift; standard | ✅ shipped v5.10.0a.G + v5.11.7 |
| **Exp3.S** | Non-stationary rewards; tracks regime shifts faster than Exp3 base | v5.13+ if Exp3 weights drift too slowly to follow market regime |
| **UCB1** | Stochastic stationary rewards | Worse fit for trading (assumes stationary; markets aren't) |
| **Thompson sampling** | Bayesian posterior over arm rewards; samples from posterior to choose | Empirically strong; v5.13 swap candidate if Exp3 underperforms |
| **Contextual bandits (LinUCB)** | Takes context vector (regime + market state) → chooses arm | More powerful than per-regime bandits; v5.14+ if v5.13 reveals context-conditioning would help |
| **Mixture-of-experts** | Gating network jointly trained with experts | Most powerful; complex to train; not technically a bandit |

### Bandit-variant decision tree (from Phase 4.A paper-test)

- **Bandit weights stay near-uniform forever** → bandit can't
  discriminate. Likely cause: rewards too noisy (Exp3 doesn't
  separate signals fast enough). Try Thompson (Bayesian posterior
  smooths noise).
- **Bandit weights drift slowly between regimes** → Exp3.S adds
  drift parameter; tracks regime shifts faster.
- **Bandit weights are stable per regime BUT a richer context
  signal might help** → contextual bandit (LinUCB / contextual
  Thompson). Pass regime + spread_bps + cumdelta as context;
  bandit blends per-context.
- **Bandit weights are right but discrete-arm constraint is
  limiting** → mixture-of-experts; gating network outputs
  continuous weight vector.

### Should we formulate a PRIVATE algorithm?

**Recommendation: NO, not now.** Reasons:
1. Battle-tested algorithms have known guarantees + bug fixes; novel
   algorithms = research work + high bug risk
2. Domain-specific structure (regime transitions, microstructure
   events) is captured in the FEATURE engineering layer + the
   per-handle composition (v5.12 Phase 3.A/B), NOT in the bandit
   layer
3. Opportunity cost: time spent on novel bandit research is time
   NOT spent on paper-test data collection that drives every other
   v5.13 decision

When private algorithm becomes interesting:
- v5.14+ if multiple paper-test cycles reveal a SPECIFIC failure
  mode that public algorithms address poorly
- Most likely shape: extend Thompson sampling with a
  domain-specific prior (e.g. "model trained on more recent data
  has higher prior") rather than fully novel algorithm

### Effort if re-triggered

| Variant swap | Effort |
|---|---|
| Exp3 → Exp3.S | ~half-day (drift parameter; same interface) |
| Exp3 → Thompson | ~1 day (posterior tracking + sampling; tested replay-determinism) |
| Exp3 → Contextual (LinUCB) | ~1 week (context vector plumbing; per-context regression) |
| Exp3 → Mixture-of-experts | ~2 weeks (gating network training + inference path) |

All variants reuse existing bandit interface (`Bandit_GetProbabilities`,
`Bandit_Update`); the SWAP is internal. Strategy code unchanged.
