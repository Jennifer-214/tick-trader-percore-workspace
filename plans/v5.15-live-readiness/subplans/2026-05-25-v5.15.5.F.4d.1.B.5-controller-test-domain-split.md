## Design space + future-oriented choices

### Decision A — Split criteria

| Option | Description | Verdict |
|---|---|---|
| **(a) Domain-aligned sub-files** (5 sub-files by concern) | engine / features / stamps / ML / misc — matches CLAUDE.md rule | **CHOSEN** |
| (b) Per-section sub-files (3,208 files) | One file per `TEST_SECTION("name")` block | rejected — absurd cross-ref burden |
| (c) Date-ordered chunks (~5k lines each) | Split by line range, ignore semantic boundaries | rejected — splits semantically-related tests across files |
| (d) Severity-tier (regression / smoke / parity / structural) | Split by test type | rejected — overlaps with domain split + harder to reason about |

**Rationale for (a):** Domain alignment matches how tests get added (when working on ML features, you add to ML domain tests; when working on stamps, you add to stamp tests). Future test authorship has natural slot. CLAUDE.md test file size discipline already calls out this exact split shape ("Categories should be domain-aligned: `controller_test_engine.cpp` / `_features.cpp` / `_stamps.cpp` / `_ml.cpp` / `_misc.cpp`").

### Decision B — Helper extraction shape

Per `feedback_audit_canonical_sister_before_new_infra` — check existing helper pattern.

Current `controller_test.cpp` opens with ~200 LOC of helpers (test counter / TEST_SECTION macro / check macros / fixtures). These extract to `tests/test_common.hpp` (single header; included by all 5 sub-files).

**Verdict:** Single `test_common.hpp` shared across all 5 sub-files. NO per-domain helper file (avoids fragmentation; helpers are universal).

### Decision C — Build system shape (H2 amended 2026-05-25)

**The "umbrella links object files" framing in v1.0 was load-bearing-underspecified.** Each TU can only have ONE `int main()` — so 5 sub-domain .cpp files can't each have main() AND be linked into the umbrella binary together (linker conflict).

Decision tree for the actual shape:

| Option | Mechanism | Verdict |
|---|---|---|
| **(a) Function-exposed sub-files + thin main wrappers** | Each sub-file has `void RunTests_<domain>()` (NO main); 5 thin `*_main.cpp` wrappers (each ~5 LOC: `#include + int main() { RunTests_X(); return tests_failed; }`); umbrella `controller_test_main.cpp` calls all 5 RunTests_X functions | **CHOSEN** |
| (b) Renamed-main sub-files | Each sub-file has `int controller_test_<domain>_main()` (renamed); 5 sub-binaries built from per-sub thin wrappers calling the renamed main; umbrella wraps all 5 | rejected — uglier naming, same complexity |
| (c) Test registration framework | Each sub-file calls `RegisterTest("name", fn)` into global runner; all binaries link a runner | rejected — requires test framework rewrite; current `TEST_SECTION` macro doesn't have registration semantics |
| (d) Header-only sub-files | Sub-files are `.hpp` containing test sections inline; each sub-binary `.cpp` `#include`s + has main | rejected — breaks "tests live in .cpp" convention; preprocessor expansion at compile time |

**Rationale for (a):** Preserves `./build/controller_test` invocation (back-compat); enables per-domain parallel test runs; aligns with multi-binary precedent (`depth_recorder_test`, `parity_harness`). Sub-files have clean function-name interface (`void RunTests_engine()` etc.); main wrappers are 5-LOC each (~25 LOC total in `tests/wrappers/`).

**File structure:**
```
tests/
  test_common.hpp                         ← shared helpers (TEST_SECTION macro, check macros, fixtures)
  controller_test_engine.cpp              ← contains void RunTests_engine() with all engine-domain TEST_SECTION blocks
  controller_test_features.cpp            ← void RunTests_features()
  controller_test_stamps.cpp              ← void RunTests_stamps()
  controller_test_ml.cpp                  ← void RunTests_ml()
  controller_test_misc.cpp                ← void RunTests_misc()
  wrappers/
    controller_test_engine_main.cpp       ← #include + int main() { RunTests_engine(); return tests_failed; }
    controller_test_features_main.cpp     ← ...
    controller_test_stamps_main.cpp       ← ...
    controller_test_ml_main.cpp           ← ...
    controller_test_misc_main.cpp         ← ...
    controller_test_main.cpp              ← umbrella main; calls all 5 RunTests_X(); reports total
  test_common_decls.hpp                   ← forward-declares void RunTests_engine() etc. for umbrella wrapper
```

**CMakeLists.txt update:** 6 new test targets (5 sub-binaries + 1 umbrella). Each sub-binary links exactly its own sub-file `.cpp` + wrapper `.cpp` + `test_common.hpp` deps. Umbrella links all 5 sub-files + umbrella wrapper.

**Tests-failed counter discipline (M-3 amendment 2026-05-25):** `test_common.hpp` declares **`inline int tests_failed = 0;`** (C++17 inline-variable; linker dedupes across TUs into single storage). Each `RunTests_X()` increments this single counter. Sub-binaries return its value as exit code. Umbrella sums automatically (single shared counter across all linked TUs).

**Why NOT TU-local static:** `static int tests_failed = 0;` in a header gives EACH TU its own counter (each .cpp #including the header has its own private storage). Sub-binary `main()` would see only its own RunTests_X's count + lose visibility into shared state across sub-files. WRONG mechanism for this requirement.

**Why NOT non-inline global with `extern` in header + definition in one .cpp:** Functionally correct but requires a dedicated `.cpp` file just for the definition (uglier; one more TU). C++17 `inline int` is the cleaner mechanism that achieves the same single-definition-across-TUs semantic with no extra file.

**Why NOT thread-local:** Tests run single-threaded in our framework; thread-local adds overhead + breaks the counter semantic (each thread would have own count).

`inline int tests_failed = 0;` is the correct + minimal mechanism.

### Decision D — Original file removal timing

| Option | Description | Verdict |
|---|---|---|
| **(a) Remove at ship close, after ALL sub-files verified passing independently** | Keep `controller_test.cpp` as fallback during transition | **CHOSEN** per risk mitigation |

### Decision E — Section assignment when domain is ambiguous

Some tests cross domains (e.g., ML feature tests that exercise the engine boot path). Tiebreaker rule:

1. **Primary surface** — what the test PRIMARILY validates (not what it incidentally touches)
2. **`misc.cpp` is the catch-all** — tests that genuinely span >2 domains go here
3. **Operator review** — if assignment is non-obvious at coding time, surface for Caramel triage rather than auto-pick

Estimated misc.cpp size: ~10-20% of tests (~3-6k LOC; under 5k threshold).

### Decision F — Scope-escalation policy (M7 amended 2026-05-25)

What if post-extract any sub-domain remains > 5,000 line threshold? Escalation policy:

| Trigger | Escalation |
|---|---|
| Any sub-domain > 5,000 lines post-extract | Split that sub-domain into 2 sub-sub-files within this same ship (e.g., `controller_test_engine_boot.cpp` + `controller_test_engine_oms.cpp`); update CMakeLists.txt for sub-sub-binaries |
| Any sub-domain > 100 sections post-extract | Split per same rule (line count + section count are independent thresholds per CLAUDE.md test discipline) |
| Misc.cpp grows > 5,000 lines | Re-evaluate cohort assignment; some "misc" tests may actually belong to a 6th domain (e.g., regime / strategies) — extract to NEW sub-domain `controller_test_regime.cpp` etc. |
| Test count regression (sum of sub-binaries < 3,208) | HALT extract; investigate. Most likely cause: test section accidentally orphaned during extract (missing `TEST_SECTION` macro in destination file). Recover via grep on pre-`pre-v5.15.5.F.4d.1.B.5` git history |

**Hard rule:** No sub-file ships over threshold. If escalation reveals 6+ sub-domains needed, accept the scope growth; per `feedback_no_defer_for_effort` close-it-now-properly beats defer-to-next-ship.
