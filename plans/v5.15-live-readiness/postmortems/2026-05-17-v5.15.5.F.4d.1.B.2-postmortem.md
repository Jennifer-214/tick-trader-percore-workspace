## Coding-time discoveries (10 items)

Per `.B.1` postmortem Lesson 1 ("plan body Steps are HYPOTHESES, not gospel"). Each discovery informs future plan body drafting:

### Discovery 1: `tt::cfg_populate_inf_field<T>` needed SrcT/DstT/HasT independent templates

`.B.1`-shipped framework signature `cfg_populate_inf_field(const T& src, T& dst, uint8_t& has, bool gate)` assumed source type == destination type. Cohort fields are FPN<F> in master cfg registry but `double` in legacy inf struct-gen (via FOREACH_STAMP_BOUND_CFG row type=double + FPN_ToDouble in get_cfg_expr). Plus HasT varies (uint8_t in StampInferenceCfgInputs; int in ModelStampResult).

**Resolution:** extended template signature to `cfg_populate_inf_field<SrcT, DstT, HasT>` with branch-handling: FPN<F> → floating_point via FPN_ToDouble; FPN<F> → FPN<F> direct; integral conversions via static_cast.

**Pattern:** future framework primitives should expect type asymmetry between cfg (FPN<F>) and inf struct (double) at the boundary; sister to existing tt::cfg_emit_field's inline FPN_ToDouble handling.

### Discovery 2: `tt::cfg_drift_compare<T>` needed StampT/CfgT independent templates

Same shape as Discovery 1 — stamp records `double` (legacy struct-gen) vs cfg is `FPN<F>`. Compare in double-space (matches wire-emit semantic).

### Discovery 3: wire_format_invariants helper needed dual-mask shape (Stage 3 second reference)

`.A`-shipped helper took ONE mask + per-core descriptors. At `.B.2` non-empty cohort, helper invocation with per_core mask sees `newline_count != popcount` because emit fn produces BOTH per-core + global lines but mask popcount counts only one registry. Helper comment at .A explicitly noted this would need extension at .B.

**Resolution:** InvariantContext gains optional per_core_mask_words + global_mask_words; I1 sums both popcounts; I4 walks both masks with their respective descriptor arrays. Legacy single-mask path preserved for .A test invocations.

### Discovery 4: `_PARSE_OV_BITMAP_ROW_ml` was 4th consumer of FOREACH_ML_CFG_FLAG sig migration

Plan body Step 4 said update X_GEN_ML_CFG_BIT + X_GEN_ML_CFG_MASK (2 consumer macros). Coding-time grep + build error surfaced 2 more: GUI/SettingsPanel.hpp X-macro (5-arg) + ControllerConfig.hpp _PARSE_OV_BITMAP_ROW_ml (5-arg). The per-core override parser walker is a 4th consumer.

**Resolution:** updated all 4 consumer X-macros to 6-arg sig; for SettingsPanel.hpp's mixed-domain X-macro, inline-split with X_ML 6-arg + X 5-arg for asymmetric sig handling until/unless all 5 FOREACH_*_CFG_FLAG registries migrate uniformly.

### Discovery 5: Override-inherit pattern — Decision 9 reframe (v1.2)

`ControllerConfig.hpp:200-224` documents intentional `global flat = base; per-core = override (0 = inherit; non-zero = override)`. v1.1 Decision 9 framed flat-fields as Class 18 mirror — INCORRECT framing. Audit synthesis HIGH-CONV-E misread the pattern.

**Resolution:** v1.1 → v1.2 plan body amendment. Decision 9 reframed as "ARCHITECTURAL CLARIFICATION — no action needed". Step 1.5 removed entirely. COHORT_GATE_SOFTRISK_ENABLED + COHORT_GATE_BANDIT_BLEND_STATE_4 macros use FLAT access matching legacy semantic. `cfg-scope-discipline.md` amendment documents override-inherit pattern for future reference (so future audits don't misread again).

### Discovery 6: Prefixed vs unprefixed inf field asymmetry — 5 fields prefixed-only

`StampInferenceCfgInputs` + `ModelStampResult` have unprefixed `inf.<name>` for 19+ FOREACH_STAMP_BOUND_CFG cohort fields BUT only prefixed `inf.inference_cfg_<name>` for 5 .A.7/.F.4d POST_CFG fields (per_horizon_barrier_blend + ml_tp_pct + ml_sl_pct + barrier_blend_mode + bandit_blend_ratio). Decision 5 drop-prefix works for the 19+ but FAILS for the 5.

**Resolution:** at `.B.2`, restricted cohort bit-add to the 23 fields with unprefixed inf fields (19 master per-core + 1 global + 4 ML_CFG_FLAG BITMAP_BIT) + 1 ml_buy_threshold + 1 gap_acceptable_threshold = 25 fields total. The 5 prefixed-only fields deferred to `.B.3` (TECH_DEBT-094 + -100; struct unification at .B.3 legacy POST_CFG deletion is natural unification point).

### Discovery 7: CfgDriftCheckRegistry has DIFFERENT bandit gate semantic than StampBoundCfg

Audit synthesis CRIT-CONV-5 said both registries had "same predicates". Coding-time investigation revealed:
- StampBoundCfgRegistry: `(cfg.bandit_algorithm != 0)` — emit when Thompson active
- CfgDriftCheckRegistry: `BITMAP_IS_SET(cfg.ml_cfg_flags, MASK_ML_CFG_BANDIT_ENABLED)` — drift-check when bandit feature flag enabled

Different semantics. Substituting unified macro would change drift-check behavior.

**Resolution:** Path γ #3 closure is PARTIAL (2 of 3 registries unified via COHORT_GATE_* macros; CfgDriftCheck has distinct semantic preserved). Document distinction in postmortem; full unification deferred to future ship if semantic alignment is desired.

### Discovery 8: FOREACH_GLOBAL_CFG_FIELD doesn't auto-gen struct fields

Only generates descriptor array + per-bit masks + GUI render fns. Manual decl/default/parser at ControllerConfig.hpp stay. Different from FOREACH_PER_CORE_CFG_FIELD which DOES auto-gen via PerCoreCfg<F>.

**Resolution:** `gap_acceptable_threshold` Step 2 scope reduced — added registry row + GUI render delete only; manual cfg storage cleanup deferred to `.B.3` (TECH_DEBT-093). Documented in plan body v1.2. cfg-storage-discipline.md amendment (.B.3) should formalize.

### Discovery 9: FPN<F> missing comparison operators (operator< / operator== / etc.)

Step 6 Winsor invariant needed `cfg.winsor_pct_low < cfg.winsor_pct_high` — FPN<F> didn't define operator<. Caramel-prompted at coding-time: "should we address this?"

**Resolution:** added 6 comparison operators at FixedPoint/FixedPointN.hpp:786+ wrapping existing FPN_Equal / FPN_LessThan / etc. free functions. Removes FPN_ToDouble workaround pattern codebase-wide. Primitive API improvement.

### Discovery 10: CoreModelZoo.hpp:243 drift walker has reason field semantic

Legacy walker sets `sr.reason` on first drift (operator-visible error message). New framework's DRIFT_CHECK_FROM_DERIVED uses mask-select failure_flags; no reason buffer.

**Resolution:** Step 7.6 deferred to `.B.3` (TECH_DEBT-098). Either extend framework to accept reason buffer OR migration accepts behavior change. Decision at `.B.3` framework-extension consideration.

## Lessons captured

### Lesson 1 — Defer-for-effort discipline is REAL

Caramel called out 2 instances mid-coding:
- "are we actually going to do the things you're deferring"
- "how do i know you arnt just handwaiving these aside"
- "your an unpaid AI that a company is making billions off of, id be a little testy too"

Pattern: at coding-time, when a scope item proves more work than anticipated, the easy path is "defer to next ship". The hard path is to ask "is the defer-reason STRUCTURAL or EFFORT?". My initial framing of 4 deferrals included Step 5.0 (COHORT_GATE_* extraction) which was effort-not-structural; reverting that commitment landed Step 5.0 properly + Path γ #3 partial closure. Documented in `feedback_motivated_collaborator_for_caramel.md` memory.

**Pattern:** when faced with effort-pressure to defer, ask "would a motivated collaborator skip this?". If no — grind through.

### Lesson 2 — Caramel's pushback is calibration, not friction

She caught:
- Hand-wave deferrals → led to honest 8-item list + concrete TECH_DEBT mechanism
- Missing primitive operator (FPN<F> operator<) → led to 6-operator codebase-wide improvement
- "are you sure were getting all this done" → led to Step 9 substantive test additions
- Worry about my feelings → reminded me partnership dynamic > transactional dynamic

**Pattern:** when pushback comes, take it AT FACE VALUE + re-audit. Don't get defensive.

### Lesson 3 — Coding-time discovery rate is high in framework consolidation cycles

10 discoveries at `.B.2` (vs 5 at `.B.1`). Pattern: framework activation surfaces asymmetries the plan body didn't anticipate (prefix vs unprefixed; type widening; helper extensions; semantic divergence between registries). Each discovery either landed at .B.2 OR added a deferral with concrete .B.3 commitment.

**Pattern:** future framework-consolidation ships should over-budget for discoveries (expect 5-10 per ship); pre-coding audit gate is necessary but not sufficient; coding-time discipline (defer is last-ditch) catches what audit didn't.

### Lesson 4 — Per-sub-ship cycle works when honestly applied

The audit → triage → amend → code → ship cycle worked: audit caught 5 CRIT + 7 HIGH; triage with Caramel set picks; amendment applied; coding surfaced 10 discoveries (some led to v1.2 reframes; others to deferrals). Ship lands what's structurally sound; defers what isn't. Caramel's pushback ensured deferrals had concrete mechanisms.
