## Theme

`ExecutionCore_Tick` (lines 235-511) is already heavily optimized — branchless predicate logic, cached parameter slot, CMOV-based active/inactive blends, predicted-not-taken event-push branch. This ship pushes the remaining 4 micro-optimizations from audit Part 1 plus closes a layout gap I caught during pre-coding review (Finding A — `live_sl` spans cache lines 0→1).

**Expected wins** (annotated AUDIT vs PLAN-derived per readiness audit):
- 1.1 template-bool elision: ~1-3ns (AUDIT: ~1ns load+branch; ~2ns total for entry+exit pair)
- 1.5 cache layout + permission isolation: ~30-80ns (AUDIT: 30-50ns from permission ping-pong + ~10-30ns PLAN-derived from Finding A `live_sl` single-line load)
- 1.2 AVX-512 leg compares: ~40ns (AUDIT: leg-B compute cost cited)
- 1.3 SIMD mask blend: ~5-10ns (PLAN-derived; audit gives no number)
- 1.4 branchless ring buffer commit: ~5ns (PLAN-derived; "worth 5ns at best")

**Total expected p50 improvement: ~75-135ns realistic, with 100ns-class as the typical case.** Pre-ship p50 from `experiments/per_core_sharding/bench_batch_floor.cpp` baseline ≈ 35-50ns; post-ship target ~15-30ns. p99 should compress proportionally; p99.9 should drop visibly because tail variance from branch mispredicts + cache-line bounce is the dominant tail source.

## Phase 1.1 — Template-bool elision of `lat_enabled` (`v5.11.1.1`)

**Audit:** Part 1.1 — current `lat_enabled` check is a relaxed atomic load + `__builtin_expect(... , 0)` branch every tick. Even predicted-not-taken, the load + branch occupy execution ports.

**Step 0:** Convert `ExecutionCore_Tick` from `static inline void ExecutionCore_Tick<F>(...)` to `static inline void ExecutionCore_Tick<F, bool LAT_ENABLED>(...)`.

**File:line targets (verified against HEAD `d1fb214` post-v5.11.0.1):**
- `CoreFrameworks/ExecutionCore.hpp:247` — function signature (was 236 pre-v5.11.0.1; +11)
- `CoreFrameworks/ExecutionCore.hpp:251, 253, 515` — `lat_enabled` check sites (wrap in `if constexpr (LAT_ENABLED)`; was 240, 242, 505 pre-v5.11.0.1; +11 each)

**Caller sites** — every place that calls `ExecutionCore_Tick<F>(...)`. Adding non-deducible `bool LAT_ENABLED` template arg forces ALL callers to specify explicitly. Verified call sites by grep:
- `CoreFrameworks/EngineSharded.hpp:2000` — production hot path loop
- `CoreFrameworks/ShardedBacktestDriver.hpp:197` — backtest per-core driver
- `tests/controller_test.cpp:5818, 5841, 5880, 5886, 5914, 5919` — 6 test sites
- ~~`Backtest/BacktestSharded.hpp`~~ — file exists but has no `ExecutionCore_Tick` call (verified empty grep)
- ~~`CoreFrameworks/LegacyReferenceDriver.hpp`~~ — file exists but has no `ExecutionCore_Tick` call

**Total: 8 call sites** (2 production + 6 test). Tests will fail to compile until updated. Effort estimate revised: ~40 LOC source + ~30 LOC test plumbing = ~70 LOC for Phase 1.1 (was ~50 in pre-readiness draft).

**Code shape:**
```cpp
template <unsigned F, bool LAT_ENABLED>
__attribute__((always_inline))
static inline void ExecutionCore_Tick(ExecutionCore<F>* core, const Tick<F>& tick) {
    uint64_t lat_t0 = 0;
    if constexpr (LAT_ENABLED) {
        uint32_t hi, lo;
        asm volatile("mfence\n\tlfence\n\trdtsc\n\t" : "=a"(lo), "=d"(hi));
        lat_t0 = ((uint64_t)hi << 32) | lo;
    }
    // ... rest of function ...
    if constexpr (LAT_ENABLED) {
        uint32_t hi, lo;
        asm volatile("rdtscp\n\tlfence\n\t" : "=a"(lo), "=d"(hi) : : "rcx");
        uint64_t lat_t1 = ((uint64_t)hi << 32) | lo;
        CoreLatencyStats_Sample(&core->latency_stats, lat_t1 - lat_t0, lat_t1);
    }
}
```

The `latency_stats.enabled` field stays (still needed for runtime ON/OFF switching of LAT_ENABLED=true builds). But when LAT_ENABLED=false, the entire sampling block compiles out — `latency_stats.enabled` is never loaded.

**Caller-site dispatch:**
```cpp
// Build flag determines which instantiation runs:
#ifdef LATENCY_PROFILING
    ExecutionCore_Tick<FP, /*LAT_ENABLED=*/true>(core, tick);
#else
    ExecutionCore_Tick<FP, /*LAT_ENABLED=*/false>(core, tick);
#endif
```

The `LATENCY_PROFILING` macro is defined per `CMakeLists.txt:18` build option. Production builds (no `-DLATENCY_PROFILING=ON`) get the LAT_ENABLED=false instantiation; the lat profiling helper compiles to NOTHING. Latency builds (`./build.sh latency` or `./build.sh gui` which has it on) get LAT_ENABLED=true.

**Verification per discipline doc:**
- New test: `test_execution_core_tick_lat_disabled_no_load` — compile-time check that LAT_ENABLED=false instantiation has zero references to `latency_stats.enabled`. Use `static_assert` or assembly inspection.
- `-S` inspection of `ExecutionCore_Tick<64, false>` body: should not contain any `mov` to/from `latency_stats.enabled` offset, no `rdtsc` / `rdtscp`.
- Replay-determinism test still passes (no semantic change).

**Asymmetric RDTSC pattern note (Finding D from review):** entry uses `mfence; lfence; rdtsc`; exit uses `rdtscp; lfence`. Pick one canonical pattern. **Recommend `rdtscp; lfence` both sides** since rdtscp is serializing (no need for mfence+lfence pre-amble) and gives consistent measurement bracket. Cosmetic but clean.

**Risk:** Low. Template instantiation is a compile-time mechanic; runtime behavior identical to current code for both LAT_ENABLED values.

**Sub-ship gate:** `./build.sh test` 1642/0 + `./build.sh latency` builds + `tools/calls_graph_diff.sh` clean (no new orphans). Tag `v5.11.1.1`.

## Phase 1.5 — Cache layout reorder + `permission` isolation (`v5.11.1.5`)

**Audit:** Part 1.5 — `permission` shares cache line 0 with active/entry_price/live_tp/live_sl. Controller atomic-stores from a different CPU; line 0 ping-pongs. ~30-50ns stall on next tick.

**Plus Finding A from pre-coding review:** `live_sl` (24-byte FPN<64>) lands at offset 56-80 in current layout, **spanning cache lines 0→1**. Steady-state CMOV reads `live_sl` every tick → loads 2 cache lines instead of 1.

**Step 0:** Reorder `ExecutionCore<F>` struct fields per the analysis in `plans/2026-05-06-latency-path-discipline.md` Rule 1.

**File:line target:** `CoreFrameworks/ExecutionCore.hpp:62-153` (struct definition; was 62-143 pre-v5.11.0.1; closing brace shifted +10 by `ring_push_failures` field addition at struct tail).

**Snapshot recovery write site (P2 concern from readiness):** `CoreFrameworks/ShardedSnapshotPersist.hpp:619` writes `core_ptr->entry_price = entry;` during snapshot recovery. The new layout puts `entry_price` on cache line 1 (intentional — not in steady-state path). Field name stays the same so by-name access compiles unchanged; recovery path is one-time, not steady-state. Verify post-1.5 that snapshot recovery still works via the existing `ShardedSnapshotPersist` round-trip tests.

**New layout (canonical per discipline doc):**
```cpp
template <unsigned F>
struct alignas(64) ExecutionCore {
    // ── CACHE LINE 0 (64B): steady-state HOT READS only ──
    // active flags + 2 FPN reads = 56B + 8B pad = 64B exactly.
    uint8_t  active;            // hot: read every tick
    uint8_t  active_b;          // hot: read every tick
    uint8_t  _pad_hot[6];
    FPN<F>   live_tp;           // 24B at offset 8 — fits in line 0
    FPN<F>   live_sl;           // 24B at offset 32 — fits in line 0  (Finding A fix)
    uint8_t  _pad_line0[8];     // pad to 64

    // ── CACHE LINE 1 (cold in steady state) ──
    // entry_price is WRITE-only on entry events (not read in steady CMOV).
    // Leg-B fields gated by `if (active_b)` — line never touched when leg
    // B is inactive (the common case).
    FPN<F>   entry_price;       // 24B; offset 64
    FPN<F>   entry_price_b;     // 24B; offset 88
    FPN<F>   live_tp_b;         // 24B; offset 112  (spans into line 2)
    FPN<F>   live_sl_b;         // 24B; offset 136

    // ── permission isolated to its OWN cache line (audit Part 1.5) ──
    // Controller atomic-stores from a different CPU; this prevents the
    // store from invalidating the hot-fields cache line.
    alignas(64) uint8_t permission;
    uint8_t  _pad_perm[63];

    // ── Parameter slot + cache (existing layout, unchanged) ──
    ParameterSlot<GateParameters<F>> param_slot;
    uint64_t cached_seq;
    GateParameters<F> cached_params;

    // ── Identity + rings + lat (existing layout, unchanged) ──
    uint16_t core_id;
    uint8_t  _pad_id[6];
    SPSCRing<TradeEvent<F>, EXECUTION_CORE_EVENT_RING_SIZE> event_ring;
    SPSCRing<Tick<F>, EXECUTION_CORE_TICK_RING_SIZE>* tick_ring;
    CoreLatencyStats latency_stats;

    // ── v5.11.0.1 failure counter (struct tail, cold) ──
    uint64_t ring_push_failures;
};
```

**Step 1:** Update `ExecutionCore_Init` (line 168-200ish) to initialize fields in the new order. Same field set; just reordered.

**Step 2:** Verify all readers/writers still work:
- `core->permission`: still accessed via `__atomic_store_n / __atomic_load_n` — works regardless of position. Field is now on its own line, so write doesn't invalidate hot fields.
- `core->active / active_b`: still bytes at offsets 0-1 — code referencing them by name compiles same.
- `core->live_tp / live_sl / entry_price`: same field names, code unchanged.
- `core->latency_stats`: name lookup unchanged.

**Step 3:** Add static_asserts to catch future layout regressions:
```cpp
static_assert(offsetof(ExecutionCore<64>, live_sl) + sizeof(FPN<64>) <= 64,
              "live_sl must fit in cache line 0 — see latency-path-discipline.md Rule 1");
static_assert((offsetof(ExecutionCore<64>, permission) % 64) == 0,
              "permission must be cache-line-aligned — see audit Part 1.5");
```

**Verification per discipline doc:**
- `-S` inspection: `ExecutionCore_Tick` body should issue 1 cache line load for `live_sl`+`live_tp` (was 2).
- Compile-time: static_asserts pass.
- Replay-determinism test: bytewise-equal output (no semantic change).
- New test: `test_execution_core_layout_invariants` — runtime check of `offsetof` for the critical fields.

**Risk:** Medium. Struct layout change touches ABI for serializers. Greps to run pre-coding:
- `grep -rn "offsetof(ExecutionCore"` — find any code that pinned offsets. Update if so.
- `grep -rn "memcpy.*ExecutionCore"` — find any direct-memory copies. Verify they don't depend on field order.
- `grep -rn "ExecutionCoreState\|ExecutionCore<F>"` — sanity check.

**Sub-ship gate:** `./build.sh test` 1642/0 + new layout test passes + `-S` inspection confirms `live_sl` single-line load + `tools/calls_graph_diff.sh` clean + ShardedSnapshotPersist round-trip test passes (validates by-name access still works post-reorder). Tag `v5.11.1.5`.

## Phase 1.2 — AVX-512 leg A+B compares (`v5.11.1.2`)

**Audit:** Part 1.2 — the leg B SG_Evaluate is currently branch-gated (`if (__builtin_expect(active_b, 0))`) because FPN<64> compares don't pipeline cleanly on i5-1035G4. Audit's fix: pack both legs' compares into a single AVX-512 vectorized op (`_mm512_cmpge_epu64_mask`).

**Step 0:** Replace the scalar leg A+B compare logic (currently at `CoreFrameworks/ExecutionCore.hpp:351-364` post-v5.11.0.1; will shift after v5.11.1.5's reorder) with vectorized intrinsics.

**Pre-conditions:**
- Phase 1.5 must have shipped (live_tp + live_sl + leg-B fields layout known).
- Build must have `-mavx512f` (already enabled via `-march=native` if the host CPU has AVX-512).

**Code shape (canonical):**
```cpp
// Pack 4 ratchet'd thresholds into a __m512i (4× FPN<64>'s magnitude word):
//   [tp_a_mag, sl_a_mag, tp_b_mag, sl_b_mag]
// Pack tick price 4 times in another __m512i:
//   [tick_price_mag, tick_price_mag, tick_price_mag, tick_price_mag]
// Single _mm512_cmpge_epu64_mask call → 4-bit mask.
// Bit 0 = tp_a_hit, bit 1 = sl_a_hit_inv, bit 2 = tp_b_hit, bit 3 = sl_b_hit_inv.

// (Detailed intrinsic sequence + scalar fallback for non-AVX-512 builds
// to be written at coding time. See LATENCY_OPTIMIZATION_AUDIT.md Part 1.2
// + STRATEGY_AND_CODING_RULES.md §5 for the canonical pattern.)
```

**Crucial — bytewise determinism with scalar reference:**
The AVX-512 path MUST produce mask bits identical to the scalar `FPN_GreaterThanOrEqual` / `FPN_LessThanOrEqual` reference. This is a v5.10.0b-style "boundary-stable refactor": same outputs, faster path. Test by:
- Run scalar reference + AVX-512 path on synthetic inputs (random FPN values across the comparison space).
- Assert bit-for-bit equal masks.

**Scalar fallback for non-AVX-512 builds:**
Wrap the AVX-512 path in `#ifdef __AVX512F__` (compile-time check via `<immintrin.h>`). Else fall back to current scalar branch-gated leg-B compute. Tested by building with `-mno-avx512f` (verify CI box has the option).

**Compile-time elision of leg B branch:**
With AVX-512, both legs are evaluated unconditionally. The `if (active_b)` branch goes away. Net: same branchless gate as leg A, just with a 4-bit mask instead of 2 scalar bools.

**Verification:**
- New test: `test_execution_core_avx512_leg_compares_match_scalar` — 1000 synthetic input vectors; bytewise-equal mask outputs.
- New test: `test_execution_core_no_active_b_branch` — assembly inspection or template specialization confirming `__builtin_expect(active_b, 0)` is gone.
- Replay-determinism test still bytewise-equal.
- Bench gate (operator-side): p99 should compress; p50 dropping ~40ns visible.

**Risk:** High. AVX-512 vectorization changes hot-path code generation substantially. Compiler may spill zmm registers if `ExecutionCore_Tick` body grows too large (~500 LOC currently). Per discipline doc Rule 4 (and v5.11.1's master plan risk section): "**Inspect assembly output (`-S`) to ensure no stack traffic is introduced in `ExecutionCore_Tick`. Use `register` hints or refactor scope if spills occur.**"

**Concrete spill-detection mechanism (per readiness audit P2):**
```bash
# Capture pre-v5.11.1.2 baseline:
g++ -S -O3 -march=native -DUSE_NATIVE_128 \
    -I. -o /tmp/exec_core_baseline.s \
    -include CoreFrameworks/ExecutionCore.hpp -x c++ /dev/null
grep -cE '\(%rsp\)|-[0-9]+\(%rbp\)' /tmp/exec_core_baseline.s
# Note the count N. Post-1.2 the count must be ≤ N + small epsilon
# (function preamble accounts for ~2-4 stack slots).
# Stack spills inside ExecutionCore_Tick body proper would push count > N.
```
Run this same grep post-v5.11.1.2 commit and compare. Sub-ship gate fails if count grows by > 4.

**Sub-ship gate:** `./build.sh test` (incl. new mask-equality + no-branch tests) + `-S` inspection confirms zero stack spills (per the grep above) + `tools/calls_graph_diff.sh` clean + replay-determinism bytewise-equal. Tag `v5.11.1.2`.

## Phase 1.4 — Branchless ring buffer commit (`v5.11.1.4`)

**Audit:** Part 1.4 — current code at `CoreFrameworks/ExecutionCore.hpp:406` (was 395 pre-v5.11.0.1; +11):
```cpp
if (__builtin_expect(can_enter | can_exit_a | can_exit_b, 0)) {
    // event push
}
```
This is the last control-flow branch in the hot-path steady state. Audit wants:
```cpp
// Unconditional event write to current ring slot:
core->event_ring.slot[head] = event_to_push;
// Conditional head advance:
head += (can_enter | can_exit_a | can_exit_b);
```

**Pre-conditions:** Phase 1.2/1.3 have shipped (mask result in vector form).

**Step 0:** Refactor the rare-branch event push to use unconditional write + conditional head advance.

**Crucial — semantic preservation:**
Current code has rich logic inside the branch:
- Per-leg event construction (PARTIAL_LEG_A vs PARTIAL_LEG_B)
- Per-leg push success tracking (`exit_a_pushed`, etc.)
- Failed-push state preservation (active flag NOT flipped if push failed)
- v5.11.0.1 counter increment on failure

Branchless commit needs to preserve ALL of this. Approach:
- Unconditionally write 3 candidate events to a per-core scratch buffer (in cache, not the ring).
- Use 3 separate head-advance increments (one per event), each gated by its own can_* mask.
- Push success tracking still happens; on failure, head doesn't advance.

This is more delicate than the audit's one-line sketch suggests. **Detailed design to be worked out at coding time** — likely requires iteration with `-S` inspection to confirm the compiler generates the expected branchless layout.

**Alternative (simpler):** keep the branch but ensure it's predicted-perfectly. Current code's `__builtin_expect(can_enter | can_exit_a | can_exit_b, 0)` already does this. The audit's "remove the branch" is the maximal optimization; the steady-state cost is currently ~1 branch predict that's correct ~99% of the time = ~0ns. **Worth ~5ns at best.** May not be worth the complexity.

**Recommendation:** Implement Phase 1.4 only if Phase 1.2's `-S` inspection reveals the branch is causing pipeline stalls under the new vectorized leg compute. Otherwise the rare-branch is acceptable.

**Verification:**
- Replay-determinism test bytewise-equal (event ring contents identical across runs).
- v4.7.3 push-failure semantics preserved (failed push leaves active flag unchanged; counter increments).
- `-S` inspection confirms expected branchless layout.

**Risk:** Medium-high. Most subtle of the 4 phases. Worth deferring to a follow-up if the gain is marginal.

**Sub-ship gate:** All replay-determinism + push-failure tests pass; `-S` inspection clean (no stack spills); `tools/calls_graph_diff.sh` clean. Tag `v5.11.1.4`. **OR defer to v5.11.1.X follow-up if gain is < 5ns.**

## Open questions / explicit deferrals

1. **AVX-512 hardware availability.** Build host (i7-11850H) has AVX-512. Operator's deployment box: assume same. CI / dev boxes: may not. 2. **Phase 1.4 conditional ship.** Audit claims branchless ring buffer commit saves ~5ns. After Phase 1.2/1.3 land, run `-S` inspection on the new `ExecutionCore_Tick` body. If the rare-branch is causing visible pipeline stalls (mispredicts > 0.1%), proceed with 1.4. Otherwise mark as **DEFERRED** to v5.11.1.X follow-up — the simpler current code is preferable.

3. **Bench harness.** Plan calls for "p99 ≤ baseline p99 across 10M-tick replay." Operator runs this; engine doesn't have an in-process bench harness. Pre-tag, operator captures baseline (`./bin/engine` from `pre-v5.11.1` tag); post-tag, runs the same replay and compares p99 in the TUI's latency panel. **Operator-side, but engineering-validated via -S inspection + replay determinism.**

4. **Asymmetric RDTSC pattern (Finding D from review).** Phase 1.1 standardizes both samples on `rdtscp; lfence`. Cosmetic.

5. **Cross-build determinism (scoped per readiness audit P2).** v5.11.0.D (PGO) introduced a new build-flag axis. Phase 1.2/1.3's AVX-512 vs scalar fallback is another. **In-scope for v5.11.1 final: AVX-512 on/off only (2 build variants).** PGO axis is deferred to v5.11.0.D's separate validation run since:
   - PGO determinism is a property of v5.11.0.D, not v5.11.1
   - Combining axes makes failure triage ambiguous (was it AVX-512 or PGO that broke determinism?)
   - Operator can run the 4-axis matrix later as a v5.12+ validation gate

   **Triage flow if AVX-512 on/off hashes diverge at v5.11.1 final:**
   1. Re-run replay against `pre-v5.11.1` baseline → confirm baseline hash is stable
   2. Bisect: `v5.11.1.5 → v5.11.1.2 → v5.11.1.3 → v5.11.1.4` to find which phase introduced the divergence
   3. Likely culprit: AVX-512 path produces bit-different mask vs scalar fallback. Test the new `test_execution_core_avx512_leg_compares_match_scalar` test.
   4. If mask test passes but full replay still diverges, the issue is downstream in event ring ordering or timing — investigate further.

Audit + plan reference `i7-11850H` (Tiger Lake-H, has AVX-512) as deployment. **The AVX-512 code path only runs on the i7-11850H.** Bench validation at v5.11.1 final must run on the i7-11850H (deployment box), not the i5-1035G4 (older dev box).
