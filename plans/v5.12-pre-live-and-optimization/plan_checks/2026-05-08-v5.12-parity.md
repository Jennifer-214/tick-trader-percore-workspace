### MEDIUM

#### 1. Phase 3.A + 3.B stamp body fields deferred without explicit guard barriers
- **Surfaces affected**: Surface G (stamp body schema), Section L (production-caller field population)
- **Finding**: Phase 3.A (composite-signal) + Phase 3.B (normalizer) both define ModelHandle struct fields but DEFER stamp body extensions (`has_normalizer`, `has_composite_signal`) to follow-up ships. This is architecturally sound (Surface G pattern explicitly allows deferred fields). However:
  1. The loader code path in CoreModelZoo_TryLoadRole (lines 225-324) does NOT have parsing for these fields, and there are NO has_* initialization guards in the verifier's ModelStampResult to receive them
  2. If an operator manually trains a model with Phase 3.B or 3.A config BEFORE the follow-up loader ships, the stamp will contain fields the verifier doesn't parse, and they'll be silently lost
  3. No explicit refusal guard ("if stamp has normalizer field but engine predates loader-side integration, refuse with WARN")
- **File:line citations**:
  - ModelInference.hpp:1174-1280 (ModelStampResult struct — NO has_normalizer, has_normalizer_param, has_num_classes_active, has_composite_signal)
  - ModelInference.hpp:1472-1593 (verify_model_stamp parsing loop — NO branches for normalizer/composite fields)
  - ModelHandle struct (lines 348-368) defines normalizer/normalizer_param/num_classes_active/target_classes/class_weights, but loader never populates from stamp
  - CoreModelZoo.hpp line 225-324 (stamp-field population after verify) — NO normalizer/composite handling
- **Current symptom**: Forward-incompatible behavior if operator trains mixed-output or composite models before follow-up lands. Stamps will have fields but engine will use defaults, silently drifting predictions.
- **Recommended fix**:
  - **Option A (safest for this ship)**: Add has_* placeholders to ModelStampResult NOW + parse stubs that ignore/warn but don't die. This gives the follow-up something to hook into without silent drift.
    - Add to ModelStampResult: `uint8_t has_normalizer; uint8_t normalizer_kind; float normalizer_param; uint8_t has_composite_signal; uint8_t num_classes_active; int target_classes[8]; float class_weights[8];`
    - Add parse branches in verify_model_stamp: `else if (strcmp(key, "normalizer_kind") == 0) { ... r.has_normalizer = 1; }` etc.
    - Add WARN at Model_TryLoadRole boot if stamp has normalizer but engine hasn't wired the loader yet
    - DO NOT set ModelHandle fields (leave defaults) — deferred-loader will do the assignment
  - **Option B (current deferred-ship pattern, document risk)**: Keep deferred as-is but add a comment + CLAUDE.md checkpoint linking to when the follow-up MUST land (v5.12.3.C+E integration or earlier) with a hard date/blocking condition
- **Cross-ref**: ALREADY-PROTECTED (deferred pattern is documented in each commit message as deliberate)
- **Effort estimate**: Option A ~30 min (struct + parse + warn); Option B ~5 min (doc only)
- **Severity rationale**: MEDIUM (not CRITICAL because deferred pattern is intentional and documented; operator can't train these models yet without follow-up landing). Becomes CRITICAL if operator trains a model with Phase 3.B label_kind before follow-up loads — prediction drift without operator awareness.

#### 3. v5.12.3.C per-core time-exit override configuration not stamp-bound
- **Surface affected**: Section F (cfg parity), ControllerConfig fields
- **Finding**: v5.12.3.C adds `core_time_exit_ticks[16]` cfg array (per-core overrides of max_hold_ticks). This is a CFG field that affects inference (exit timing logic). Currently NOT stamp-bound — no `inference_cfg_*` or `has_*` flag in stamp body.
  - Engine can hot-reload cfg, changing per-core exit timing without retraining stamps
  - Operator can swap engines with different default cfg values; exit timing will drift
  - Not part of the v5.9.2b inference_cfg binding set
- **File:line citations**:
  - ControllerConfig.hpp: new field `core_time_exit_ticks[16]` at line ~1255 (in v5.12.3.C diff)
  - No corresponding stamp body field in ModelStampResult or parsing logic
- **Current symptom**: Operator can hot-swap cfg.core_time_exit_ticks without stamp refusal/WARN. Behavior change is silent.
- **Recommended fix**:
  - Leave as-is (LOW priority): cfg is reloadable by design; operator responsibility to understand which cfg values affect inference
  - OR: add to stamp body at next inference_cfg extension (v5.12.3.E or v5.13); documented as "will bind in follow-up"
- **Cross-ref**: DESIGN CHOICE (not a gap — per-core overrides are intentionally cfg-driven, not model-bound)
- **Effort estimate**: If binding v5.12.4+: ~1h (new cfg field set + parsing + boot WARN)
- **Severity rationale**: LOW because this is intentional hot-reload design. Operator workflow assumes cfg changes are allowed.
