### [HIGH] `lbs-5` — User-data WS frame buffer is 4KB; large outboundAccountPosition events overflow ud_ws_read_frame and trigger a reconnect loop, dropping fills
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `live-binance` · fix: .E.3 (persistent WS connection management) / .E.4 (io_uring+kTLS rewrite of the WS read path)
- **Where:** DataStream/BinanceUserData.hpp:431 (char frame_buf[4096]) + ud_ws_read_frame BinanceUserData.hpp:201 (if ((int)pay_len > buf_size-1) return -1) → read loop :458-460 treats -1 as 'frame read error, reconnecting' and breaks.
- **What:** The user-data stream delivers executionReport, balanceUpdate, AND outboundAccountPosition events. Every frame must be fully READ before the parser decides whether to ignore it. ud_ws_read_frame returns -1 when the payload exceeds frame_buf size (4096-1). For an account holding many assets, outboundAccountPosition (the full balances snapshot sent after each trade) can exceed 4KB. That oversized frame returns -1, which the read loop treats identically to a connection error: it breaks and reconnects (2s sleep). Because outboundAccountPosition fires right after each fill, this can produce a reconnect loop precisely when fills are happening — and fills that arrive during the reconnect gap are lost in-session (compounds the known live-3).
- **Why:** An availability/correctness defect on the live fill path: a benign-but-large informational frame is misclassified as a fatal read error, causing fill-time disconnects. The blind spot is that the frame reader's size limit was sized for tiny executionReports without accounting for the other event types on the same stream.
- **⚠ Don't carry forward (.E.1 rewrite):** Size the user-data frame buffer for the largest event on the stream (outboundAccountPosition for a max-asset account), and distinguish 'frame too large' from 'connection error' — an oversized known-ignorable frame should be drained/skipped, not treated as a disconnect.
- **Test to add:** Add a ud_ws_read_frame test feeding a >4096-byte payload (126/127 extended length path) and assert it is skipped/handled, not reported as a disconnect; and an integration test that a large outboundAccountPosition between two fills does not drop the second fill.
- **Anti-pattern:** A multiplexed stream's frame reader sized for the smallest expected message, conflating 'payload exceeds buffer' with 'connection lost' so large benign frames cause reconnects.

### [MEDIUM] `conc-bc-2` — BinanceAdapter submission_queue (SPMC) + OMS result_queue (MPSC) silently break SPSC contract at worker_count>1; no guard pins it to 1
*verified* · section `concurrency` · fix: .E.3 (WS-API + persistent connections) / .E.4 (I/O threads) — per-worker queues land with the multi-connection work
- **Where:** CoreFrameworks/BinanceAdapter.hpp: submission_queue SPSCRing @~92, N workers each SPSCRing_TryPop(&state->submission_queue) in BinanceAdapter_WorkerLoop @166, worker spawn loop @290-292, worker_count clamp [1,MAX_BINANCE_WORKERS=4] @270-272. Result push: WorkerLoop calls p.cb(...) @232 -> OrderManager_FillResultCallback (CoreFrameworks/OrderManager.hpp @782) -> SPSCRing_TryPush(&oms->result_queue) @790. Call site hardcodes worker_count=1 at CoreFrameworks/EngineSharded/Run.hpp:591.
- **What:** The single submission_queue (drainer->worker SPSC) is popped by EVERY worker thread, and OMS result_queue is pushed by EVERY worker's fill callback. With the shipped worker_count==1 both rings are correctly SPSC. But BinanceAdapterState reserves MAX_BINANCE_WORKERS=4 worker slots/threads and the comments at Run.hpp:587 ('Scale up to 2-4'), BinanceAdapter.hpp:33/38 explicitly anticipate scaling. At worker_count>1: submission_queue becomes single-producer/MULTI-consumer (SPMC) and result_queue becomes MULTI-producer/single-consumer (MPSC). tt::SPSCRing's own header states 'no MPMC support, no MPSC, no SPMC' — concurrent TryPop on one ring (two consumers racing tail) and concurrent TryPush (two producers racing head + clobbering the same slot) corrupt the ring (lost/duplicated commands, torn slot writes). Nothing mechanically enforces worker_count==1 — there is no static_assert and no runtime assertion; only a hardcoded literal at one call site and 4 comment reminders.
- **Why:** Latent (not live: worker_count is hardcoded 1, not cfg-reachable) but a sharp foot-gun precisely at the scaling point the code is architected for. Severity MEDIUM not HIGH because unreachable today; it is a real correctness landmine for live order submission (the highest-stakes path) the moment the literal is bumped, with silent data corruption and no guard. Directly on the .E.3/.E.4 I/O-thread surface (per the .E plan's BinanceAdapter-as-canonical-sister work).
- **⚠ Don't carry forward (.E.1 rewrite):** When .E.3/.E.4 scale the adapter to N workers/connections, do NOT keep the single shared submission_queue + single shared result_queue. Use per-worker submission_queue[i] (drainer/node fans by worker) and per-worker result_queue[i] (each worker pushes its own; consumer drains all N) so each ring stays strictly SPSC. This is the 'replace with per-worker queues when scaling' note the code already anticipates.
- **CI check:** Static check: for every SPSCRing field, assert it has at most one distinct producing thread and one consuming thread; flag rings whose producer/consumer is inside a thread-pool loop (workers[i]) unless a static_assert(pool_size==1) or per-instance-ring pattern is present. Cheap interim: add static_assert(worker_count constant==1) or a runtime assert at BinanceAdapter_Init while the rings are shared.
- **Test to add:** No test runs the adapter with worker_count>1 under TSan. Add a guarded test that, if worker_count>1 is ever allowed, drives concurrent submits + result callbacks under TSan and asserts no ring corruption — or a compile-time assert that worker_count is 1 while the shared-ring design stands.
- **Anti-pattern:** An SPSC ring shared across a thread pool whose single-producer/single-consumer invariant is held only by a config/literal value, with no static_assert or runtime guard enforcing the pool size that keeps it SPSC

### [MEDIUM] `lbs-6` — TOCTOU race on the non-thread-safe shared rest_api between user-data WS-reconnect thread and keepalive thread (the 'serialized' guarantee is a racy flag check, not a real mutex)
*suspected · **NEEDS-RUNTIME-CONFIRM*** · section `live-binance` · fix: .E.3 (persistent WS connection management) — give the WS thread and keepalive thread separate BinanceOrderAPI instances (the adapter already mandates per-thread instances), or a real handoff primitive.
- **Where:** DataStream/BinanceUserData.hpp:80 (single BinanceOrderAPI rest_api shared by both threads) ; keepalive uses it at :282/:538 after a ws_connected check at :527 ; WS thread uses it via ud_obtain_listen_key/binance_rest_request at :256 during reconnect. Thread-safety contract: BinanceAdapter.hpp:14-29 (BinanceOrderAPI is NOT thread-safe; concurrent use races sockfd/ssl → documented heap-corruption history).
- **What:** Both ud_keepalive_thread and ud_ws_thread call REST on the SAME s->rest_api instance. The header (BinanceUserData.hpp:609-611) claims they are serialized because keepalive only fires REST when ws_connected==1 and the WS thread only does REST during reconnect (ws_connected==0). But this is a time-of-check/time-of-use race: the keepalive thread reads ws_connected==1 at :527, then proceeds into binance_rest_request; concurrently the WS read loop can hit a frame error, call ud_ws_close (sets ws_connected=0), and re-enter ud_obtain_listen_key (REST on the same rest_api). The mutable sockfd/ssl/connected fields are then touched by two threads at once on a struct that is explicitly not thread-safe — the same class as the documented back-to-back heap-corruption bug. The 2s reconnect sleep makes the overlap window narrow but does not eliminate it (keepalive REST can be in flight when the WS thread reaches its REST call).
- **Why:** Concurrent use of a non-thread-safe SSL/socket struct is undefined behavior (sockfd reuse, SSL object double-free, corrupted reads) on the live credential/listen-key path. The guard chosen (a racy atomic flag read) does not actually serialize; it only reduces probability.
- **⚠ Don't carry forward (.E.1 rewrite):** Do not share one BinanceOrderAPI across the WS-reconnect and keepalive threads guarded only by a flag check. Per the adapter's own rule (per-thread instances, never share), give each thread its own instance, or serialize with an explicit ownership handoff.
- **Test to add:** TSan stress test: drive ud_ws_thread reconnects and ud_keepalive_thread refreshes concurrently against a mock REST endpoint; assert no data race on rest_api (sockfd/ssl).
- **Anti-pattern:** Two threads sharing a documented non-thread-safe resource, 'serialized' only by reading an atomic state flag (TOCTOU) rather than by exclusive ownership or a lock-free handoff.

### [MEDIUM] `lbs-7` — ws_active=1 is latched at WS init regardless of whether the user-data WS ever connects; if WS handshake keeps failing, REST fills are suppressed to ACK-only and no fills are ever booked
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `live-binance` · fix: .E.3 (persistent WS connection management — drive adapter ws_active from the live ws_connected signal with a fallback-to-REST timeout)
- **Where:** CoreFrameworks/EngineSharded/Run.hpp:768 (g_sharded_binance_adapter.ws_active.store(1) immediately after BinanceUserData_Start, which only spawns threads and cannot have connected yet) ; consumed at CoreFrameworks/BinanceAdapter.hpp:212 (ws_active → ACK-only fill result) → OrderManager.hpp:1343 (ORDER_ACKNOWLEDGED, slot kept open awaiting a WS fill that never arrives).
- **What:** ws_active is set to 1 right after BinanceUserData_Start (which merely launches the WS + keepalive threads). It is never gated on actual WS connectivity, and is never reset to 0 if the WS fails to connect or reconnect-loops (the WS thread's s->ws_connected atomic exists but is not wired back to adapter.ws_active). With ws_active=1, the REST worker returns ACK-only (no fill price/qty) and ProcessFillCommand transitions orders to ORDER_ACKNOWLEDGED and keeps the slot open, expecting the WS to deliver the real fill. If the WS is broken (e.g., the cluster-mismatch in lbs-2, or the 4KB-frame reconnect loop in lbs-5), the real fill never arrives via WS and was deliberately discarded via REST — so the order sits ACKNOWLEDGED indefinitely, never booked, and the slot is never freed.
- **Why:** Couples two independent failure modes into a silent total fill-loss: REST fills are suppressed on the ASSUMPTION the WS is live, but that assumption is latched at startup and never revalidated. The blind spot is a producer/consumer liveness mismatch — adapter.ws_active (consumer gate) is not derived from the WS thread's actual ws_connected (producer truth).
- **⚠ Don't carry forward (.E.1 rewrite):** adapter.ws_active must be derived from the user-data thread's actual ws_connected state (with hysteresis/timeout), not latched at init. When WS is down, REST fills must be booked fully, not suppressed to ACK-only.
- **Test to add:** Integration test: start live path with the user-data WS forced to fail handshake; submit an order; assert the fill is booked via REST (full fill data) rather than left ORDER_ACKNOWLEDGED with the slot stuck open.
- **Anti-pattern:** A consumer-side capability gate latched true at startup on the assumption a background producer will become live, with no path to revert it if the producer never connects — turning a degraded-mode fallback into a hard outage.

### [LOW] `conc-dod-2` — Depth book double-buffer (snapshots[2] + active_idx) is a 2-buffer publish with no version/seqlock guard; a long-lived reader reference held across a slow-path cycle can be overwritten by a 2-frame writer burst (the exact failure ParameterSlot's seqlock was chosen to avoid)
*suspected · **NEEDS-RUNTIME-CONFIRM*** · section `concurrency` · fix: .E.3/.E.4 (I/O threads) — when the depth/WS I/O threads are reworked, either (a) convert the book handoff to tt::ParameterSlot<BookSnapshot<F>> (seqlock; the codebase's sanctioned cross-thread snapshot primitive), or (b) have readers MEMCPY the snapshot under an acquire-load + re-check active_idx (cheap retry) instead of holding a long-lived reference. Standalone-fixable earlier if depth gating is enabled in a live deployment before .E.3.
- **Where:** DataStream/BinanceDepth.hpp struct DepthSharedState<F> (snapshots[2] + int active_idx, ~lines 80-90); writer publish at depth_thread_fn (~lines 307-317: back=1-active_idx; copy active->back; parse into back; __atomic_store_n(active_idx, back, RELEASE)). Long-lived reader reference: CoreFrameworks/EngineSharded/Run.hpp:1935-1941 `int dactive = __atomic_load_n(&g_depth_shared.active_idx, ACQUIRE); const BookSnapshot<F>& depth = g_depth_shared.snapshots[dactive];` then passed by const-ref into EngineCommon_SlowPathCycleOneCore which reads its fields throughout a ~100-300us cycle. Shorter-lived read: CoreFrameworks/EngineSharded/Async.hpp:407-411.
- **What:** The depth thread publishes book snapshots via a classic 2-buffer flip (single writer). A reader acquire-loads active_idx=X and reads snapshots[X]. The writer's next frame writes 1-X (safe), but the frame AFTER that computes back=1-(1-X)=X and overwrites snapshots[X] — the very buffer a still-running reader may hold. The slow-path holds a const-reference to snapshots[dactive] and reads its FPN fields (bids/asks/spread/mid/imbalance, ~200B of multi-word FPN) across the entire slow-path cycle. There is NO version counter / seqlock / retry: nothing detects that the underlying buffer was recycled mid-read. Result would be a torn book snapshot (some fields from frame N, some from frame N+2) feeding Regime_ComputeSignals -> regime classification / book_imbalance gate.
- **Why:** DESIGN_SPECS/concurrency-patterns/cross-thread-snapshot-publish-cluster-isolation.md Option A and the ParameterSlot.hpp header BOTH explicitly reject N-buffer schemes for cross-thread snapshot handoff in favor of a seqlock, on the grounds that a fast-enough producer wraps the rotor back onto the buffer a reader is mid-copy (the documented phase-05 '8000 torn reads / 1M' result). The depth path uses a 2-buffer flip — strictly weaker than the rejected triple-buffer — for a snapshot that a reader holds by reference across a multi-microsecond cycle. Severity LOW because: (1) depth cadence is 100ms while the slow-path cycle is ~100-300us, so a 2-frame burst inside one read requires the slow path to stall >100ms (rare); (2) the pattern is documented as a CANONICAL PRECEDENT in TECH_DEBT (open.md ~600-630, cited as the template for future mmap double-buffers), i.e. the codebase has accepted it. Flagged because it is materially inconsistent with the project's own seqlock-over-N-buffer ruling and the held-by-reference read amplifies the window vs a snapshot-copy reader.
- **⚠ Don't carry forward (.E.1 rewrite):** If the decoupled runtime/viewer mmap double-buffer (TECH_DEBT future) is built from this BinanceDepth precedent, do NOT propagate the bare 2-buffer + active_idx pattern for snapshots that readers hold by reference or copy non-atomically — use the seqlock (ParameterSlot) the project already standardized on, or a >=3-buffer with reader-claim, per the project's own N-buffer rejection rationale.
- **Test to add:** Add a stress test mirroring the phase-05 ParameterSlot torn-read test but for the depth double-buffer: producer thread flips snapshots at a rate approaching the reader's read duration; reader validates each consumed BookSnapshot is internally self-consistent (e.g. spread == asks[0].price - bids[0].price, mid == (bid0+ask0)/2). Currently no MT test exercises depth concurrent publish/consume.
- **Anti-pattern:** Cross-thread snapshot published via a fixed N-buffer flip with no version/seqlock guard, then consumed by a reader that holds a long-lived reference across a multi-microsecond compute window (the held reference, not a copy, is what makes the recycle hazard real).

### [LOW] `conc-bc-3` — Depth double-buffer (single active_idx flip) has no torn-read protection; asymmetric with param/TUI seqlock discipline
*verified* · section `concurrency` · fix: .E.3 (WS-API / depth thread topology) — promote depth buffer to the seqlock pattern when the depth thread is reworked
- **Where:** DataStream/BinanceDepth.hpp: DepthSharedState { BookSnapshot<F> snapshots[2]; int active_idx; } @80-90; producer publish in depth_thread_fn: back=1-active_idx @307, snapshots[back]=snapshots[active_idx] @308, parse @309, __atomic_store_n(&active_idx, back, RELEASE) @317. Consumer (per-core slow thread): dactive=__atomic_load_n(&active_idx, ACQUIRE) (CoreFrameworks/EngineSharded/Run.hpp:1935), const BookSnapshot<F>& depth = g_depth_shared.snapshots[dactive] @1936; fields copied at EngineCommon.hpp:524-526 (depth.imbalance/spread/mid_price) with NO post-read re-check of active_idx.
- **What:** The depth order book is published via a 2-slot rotating buffer with a single atomic active_idx flip and NO version counter / seqlock. The consumer acquire-loads active_idx once, then reads three multi-field FPN values off a bare reference into snapshots[dactive] without re-validating active_idx afterward. With only 2 buffers, TWO producer flips (next frame published to the other slot, then a subsequent frame wrapping back) overwrite snapshots[dactive] while the consumer is mid-read, yielding an internally-inconsistent (imbalance,spread,mid) tuple. The producer's copy-current-into-back step (@308) means a torn read mixes two adjacent snapshots rather than reading garbage, but it is still inconsistent. This is the same producer/consumer job the codebase elsewhere protects with a proper seqlock (ParameterSlot, and EngineTUI.hpp:1302 TUI snapshot) — the depth buffer is the odd one out.
- **Why:** Latent torn-read; safe TODAY only because depth5 frames arrive ~100ms apart while the consumer's field-copy window is ~tens of ns (two flips in that window is practically impossible). Slow-path-only input to regime/strategy (not an accounting/wire path), so LOW. The substantive concern is discipline asymmetry + zero structural protection: nothing prevents a future faster depth feed, a wider BookSnapshot, or the consumer holding the reference longer from turning this into corruption. Distinct from any prior finding (depth not covered) and from seam-comp-2 (DepthReplay stale-day, REFUTED) — this is the live double-buffer protocol.
- **⚠ Don't carry forward (.E.1 rewrite):** In the .E topology rewrite, do NOT keep the bare 2-slot active_idx flip for shared market state. Use the same seqlock/version-bracketed read the param slot uses (or >=3 buffers with version), so the consumer detects an overwrite-during-read and retries — matching concurrency-model-summary.md's single discipline rather than a special-case unprotected buffer.
- **CI check:** Grep/AST check: flag any read of snapshots[atomic_load(active_idx)] taken as a reference/pointer (not a single atomic snapshot copy) and used across >1 field access without an enclosing seqlock retry loop
- **Test to add:** No test stresses the depth double-buffer with a fast producer + concurrent consumer to detect torn reads. Add a TSan/stress test that publishes depth frames faster than the consumer reads and asserts each consumed (imbalance,spread,mid) tuple is internally consistent (came from one frame).
- **Anti-pattern:** Publishing a multi-field shared struct via a single atomic index flip into a 2-slot buffer and reading it through a long-lived reference with no version/seqlock re-validation (torn-read safety resting on producer cadence)
