## .F.1 — Hold-time persistence across program restart

**Problem (operator-reported 2026-05-13):** Positions display Hold = "5m T" uniformly after engine restart days later. Positions were genuinely held longer than 5 minutes — `entry_timestamp_us` is being reset on load.

**Investigation findings (audit-confirmed):**

- `Position.entry_timestamp_us` IS persisted in PORTFOLIO_SNAPSHOT_VERSION=5+ wire format (Portfolio.hpp:127 offset lock).
- However, on this session the SHARDED snapshot was REFUSED (file v7 vs current v8 — `[snapshot] data/sharded_snapshot.dat version 7 != current 8 — refusing load`).
- Positions were instead restored via `OrderEventLog replay` (8 events loaded from `logging/order_events.bin`).
- **Hypothesis:** the OrderEventLog replay path calls `Portfolio_OpenSlot` which sets `entry_timestamp_us = clock_gettime(CLOCK_REALTIME)` — i.e., NOW — losing the original wall-clock entry time.

**Where to look:**

- `CoreFrameworks/Portfolio.hpp:322` — `entry_timestamp_us = clock_gettime(...)` write site
- OrderEventLog replay code (need to grep; likely in `CoreFrameworks/OrderEventLog.hpp` or similar)
- The original entry event in the log presumably has the original timestamp — replay should restore it, not overwrite with NOW.

**Fix approach:**

1. Find OrderEventLog replay → identify where it calls Portfolio_OpenSlot.
2. Modify replay to pass the LOGGED entry timestamp (not NOW) into Portfolio_OpenSlot.
3. Either:
   - Add an overload `Portfolio_OpenSlot_FromReplay(..., uint64_t logged_entry_ts_us)` that uses the logged timestamp.
   - OR add a separate field on Position that distinguishes "live entry" vs "replayed entry" semantics.

**Risk:** LOW. Replay-path-only change; live entry path untouched.

**Test:** Open paper-test session → wait 10m → close → wait 1m → re-open → verify Hold column shows ~11m (not 5m or 1m).

## .F.3 — STRUCTURAL: FOREACH_MODEL_HEALTH_FLAG registry

**Problem (operator-reported 2026-05-13):** ML Status panel says "Model Health: clean (no drift across cores)" + "Stamp + scaler + cfg + HMAC + age all aligned with runtime" when in fact engine boot logged 4 `[held-out gate] WARN: feature-registry-hash mismatch (retrain required)` for the multi-horizon ensemble.

The boot-time stamp-verification result is NOT propagated to runtime observability — engine log says one thing, GUI says the opposite.

**Structural answer (per CLAUDE.md item 19 + DESIGN_SPECS/meta-disciplines/structural-fix-preferred-decision-framework.md):**

Define `FOREACH_MODEL_HEALTH_FLAG` X-macro registry. Single source of truth for:
- Per-handle bitmap field (`uint8_t health_flags` on ModelHandle or equivalent)
- Per-core aggregated bitmap (OR of all this core's handles' flags)
- Snapshot field for GUI publish
- ML Status panel display (registry-driven; render per-set-bit with doc string)
- Engine log refactored to USE the registry's doc strings (closes Class-18 mirror between log + GUI text)
- `/readiness` Check 26+ scans flags before live mode enters

**Registry entries** (initial; expandable):

```cpp
#define FOREACH_MODEL_HEALTH_FLAG(X)                                                          \
    X(FEATURE_HASH_MISMATCH,    "feature_registry_hash mismatch (retrain required)")           \
    X(SCALER_HASH_MISMATCH,     "scaler feature_registry_hash mismatch")                       \
    X(STAMP_HMAC_INVALID,       "HMAC not verified (held_out_stamp_secret empty or check failed)") \
    X(MODEL_AGE_EXCEEDED,       "model age exceeds model_max_age_hours")                       \
    X(GRID_MEMBER_COUNT_MISSING,"pre-v5.10.0a.G.2 ensemble metadata (consistency check skipped)") \
    X(MODEL_FORMAT_LEGACY,      "model_format_version older than current")                     \
    X(CFG_DRIFT_TIER_1,         "Tier-1 cfg drift detected (live REFUSE)")                     \
    X(CFG_DRIFT_TIER_2,         "Tier-2 cfg drift detected (live WARN)")
// 8 flags fits uint8_t bitmap. Future expansion → uint16_t.
```

**Storage:**
- `uint8_t model_health_flags` field on ModelHandle (per-handle granularity)
- `uint8_t core_model_health_flags` aggregated to CoreContext (per-core OR) — placed in WARM cluster or via existing FOREACH_DISPLAY_META_FIELD registry extension (cleaner: DisplayMeta sibling)

- Etc.

**GUI:**

- Color: yellow/orange for issues; green for clean.
- Per-core breakdown if multiple flags differ across cores.

**Per /readiness:** add Check 26 or 27 that scans for any per-core model_health_flags non-zero → flags YELLOW unless acknowledged via cfg flag (e.g., `acknowledge_model_health_warnings=1`).

### Why this ship exists

Caramel paper-tested `.F.4c` engine `82a9004` and surfaced a runtime regression: **Dear ImGui's widget-ID system reports "name is already taken" at runtime when two visible controls share the same display label**. ImGui hashes the visible label string into the widget ID; identical labels collide → only one of the colliding controls retains interaction state, so the other appears non-functional. Operator-observed downstream symptom: "some of them just don't work."

Root cause is at the `.F.4c`-shipped `tt::cfg_render_field<T>` dispatch layer (`GUI/SettingsPanel.hpp:60-128`). Every ImGui call inside the dispatch passes `desc.label` DIRECTLY as both the display text AND the widget ID:

| File:line | Site | Current call shape |
|---|---|---|
| `GUI/SettingsPanel.hpp:78` | KIND_DOUBLE FPN<F> | `ImGui::SliderFloat(desc.label, &vf, lo, hi, fmt)` |
| `GUI/SettingsPanel.hpp:90` | KIND_DOUBLE float | `ImGui::SliderFloat(desc.label, &vf, lo, hi, fmt)` |
| `GUI/SettingsPanel.hpp:97` | KIND_STRING char[N] | `ImGui::InputText(desc.label, field, std::extent_v<T>)` |
| `GUI/SettingsPanel.hpp:103` | KIND_INT_ENUM | `ImGui::Combo(desc.label, &v, labels, count)` |
| `GUI/SettingsPanel.hpp:109` | KIND_BOOL | `ImGui::Checkbox(desc.label, &b)` |
| `GUI/SettingsPanel.hpp:119` | KIND_INT generic | `ImGui::SliderInt(desc.label, &v, lo, hi)` |
| `GUI/SettingsPanel.hpp:985` | residual `field_defs[]` path | `ImGui::Checkbox(fd->label, &bv)` |

Two collision shapes can fire today:
1. **Inter-descriptor collision** — two `FOREACH_CFG_FIELD` rows whose display labels happen to match (e.g., a "TP %%" appearing in both Trading + per-strategy sections, or future-row addition that duplicates an existing label without operator noticing).
2. **Cross-tab residue collision** — a `cfg_render_field<T>` row whose label coincides with a hand-rolled ImGui control elsewhere on the same parent context (the per-core block at `:1653` wraps in `PushID(c + 1000)` so global-vs-percore is isolated; risks remain inside the global tab and inside each per-core tab respectively).

### Structural fix — decouple display label from ImGui widget ID

Per CLAUDE.md item 19 (structural fix preferred when bug class can recur) + DESIGN_PHILOSOPHY § 1.5 (framework discipline meta-principle): the structural answer is to make the widget ID independent of the display label, with uniqueness sourced from the descriptor's `cfg_field_name` (already guaranteed unique by `FOREACH_CFG_FIELD` row uniqueness — same property used by `FIELD_IDX_*` enum + bitmap dispatcher framework).

**Mechanism:** wrap every ImGui call inside `tt::cfg_render_field<T>` with `ImGui::PushID(desc.cfg_field_name); … ImGui::PopID();`. ImGui's PushID stack composes hash inputs across nested scopes, so the full uniqueness tuple becomes `(parent_scope, cfg_field_name, label)`. The per-core block's existing `PushID(c + 1000)` nests cleanly outside — `(core_id, cfg_field_name, label)` for per-core overrides.

```cpp
// GUI/SettingsPanel.hpp ~line 70 — within tt::cfg_render_field<T>
namespace tt {
    template <typename T>
    inline bool cfg_render_field(T& field, const CfgFieldDescriptor& desc) {
        // ... static_assert ...
        ImGui::PushID(desc.cfg_field_name);  // ID stack: parent → cfg_field_name → label hash
        bool changed = false;
        if constexpr (is_FPN_v<T>) { /* ImGui::SliderFloat(desc.label, ...) */ }
        // ... existing branches unchanged; desc.label stays the display text ...
        if (desc.tooltip && ImGui::IsItemHovered()) { ImGui::SetTooltip("%s", desc.tooltip); }
        ImGui::PopID();
        return changed;
    }
}
```

**Why PushID over `"label##cfg_field_name"` suffix string format:**
- ImGui-native idiom (precedent at `SettingsPanel.hpp:1169-1171/1227-1235/1245-1301/etc.`)
- Zero per-frame allocation (no `snprintf` into a thread-local buffer)
- Composes with nested `PushID(core_id)` for per-core overrides without string surgery
- Descriptor row shape unchanged (no new `id_label` field added to `CfgFieldDescriptor`)
- Display label stays operator-facing without forced uniqueness ergonomics (operator can have e.g. "TP %%" appear in Trading + per-strategy sections without renaming)

### Residual `field_defs[]` site (`GUI/SettingsPanel.hpp:985`)

The bool path at `:985` (`ImGui::Checkbox(fd->label, &bv)`) operates on the legacy `field_defs[]` table (not yet migrated to `FOREACH_CFG_FIELD`; tracked at TECH_DEBT-063 for `.F.4e`). Same structural fix applies: wrap with `ImGui::PushID(fd->key); … ImGui::PopID();` since `fd->key` is the equivalent uniqueness anchor on the legacy descriptor.

### Boot-time uniqueness assertion (defense-in-depth)

Compile-time guarantee:

```cpp
// CoreFrameworks/CfgFieldRegistry.hpp — defense-in-depth at registry expansion
// Already implicit via FIELD_IDX_<name> enum (duplicate cfg_field_name = duplicate enumerator = compile error).
// Add explicit static_assert documenting the contract:
template <size_t N>
constexpr bool cfg_field_names_unique(const CfgFieldDescriptor (&a)[N]) {
    for (size_t i = 0; i < N; ++i)
        for (size_t j = i + 1; j < N; ++j)
            if (__builtin_strcmp(a[i].cfg_field_name, a[j].cfg_field_name) == 0) return false;
    return true;
}
static_assert(cfg_field_names_unique(g_cfg_field_descriptors),
              "FOREACH_CFG_FIELD row has duplicate cfg_field_name — "
              "violates universal-registry-bitmap-dispatcher-pattern.md "
              "row-uniqueness contract + .F.4c.1 ImGui-ID uniqueness reliance");
```

Runtime guarantee (covers hand-rolled controls + `field_defs[]` residue):

```cpp
// One-time at GuiThread_Init (or Settings_Init): walks all CfgFieldDescriptors +
// field_defs[]; asserts no (scope, key) duplicate. Catches future regressions at
// startup rather than at runtime "name is already taken" popup.
void Settings_VerifyImGuiIdUniqueness();
```
