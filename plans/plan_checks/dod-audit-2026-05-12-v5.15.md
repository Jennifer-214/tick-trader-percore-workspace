## HIGH findings (must-address before sub-ship coding)

### HIGH-1 — HotSwapSnapshot struct violates `struct-padding-determinism-pattern.md` + `per-snapshot-cluster-layout-pattern.md` (CLAUDE.md item 27)

**Surface:** `plans/v5.15-live-readiness/subplans/2026-05-12-v5.15.4-live-mode-strict-defaults.md` lines 227-238 (HotSwapSnapshot struct sketch)

**Pattern:** `struct-padding-determinism-pattern.md` + `per-snapshot-cluster-layout-pattern.md` (CLAUDE.md items 21, 27)

**Symptom:** struct sketched as:
```cpp
template <int F>
struct alignas(64) HotSwapSnapshot {
    EnsembleModelZoo<F>* prev_ezoo;        // 8 B
    CoreModelZoo<F>*     prev_single_zoo;  // 8 B
    int                  prev_n_models;    // 4 B  ← implicit 4B padding to align uint64_t below
    uint64_t             prev_handle_count;// 8 B
    uint64_t             snapshot_seq;     // 8 B
    uint8_t              snapshot_taken;   // 1 B  ← implicit 7B padding to round to 8B (alignas(64) demands struct size multiple of 8)
};
// Implicit total: 48 B used + ~7B internal + ~16 B trailing padding to reach 64 B = 64 B
```

**Two gaps:**
1. Implicit padding (4 bytes after `prev_n_models` + 7 bytes after `snapshot_taken`) — UB unless initialized. Even though the struct isn't explicitly compared via `memcmp` in the current plan, snapshot/revert + atomic publish + cross-thread reads make it byte-equivalence-adjacent. CLAUDE.md item 27 demands explicit padding for any cross-thread snapshot.
2. No `static_assert(sizeof(HotSwapSnapshot<F>) % 64 == 0, "...")` — required per `per-snapshot-cluster-layout-pattern.md` Step 5.
3. snapshot_seq is global (`__atomic_fetch_add(&g_swap_seq, ...)`) but not declared anywhere in the plan — referenced as bare identifier.

**Suggested fix (amendment to v5.15.4.B Step 1):**

```cpp
template <int F>
struct alignas(64) HotSwapSnapshot {
    EnsembleModelZoo<F>* prev_ezoo;        // 8 B
    CoreModelZoo<F>*     prev_single_zoo;  // 8 B
    int                  prev_n_models;    // 4 B
    int32_t              _padding0 = 0;    // 4 B explicit zero-init padding
    uint64_t             prev_handle_count;// 8 B
    uint64_t             snapshot_seq;     // 8 B
    uint8_t              snapshot_taken;   // 1 B
    uint8_t              _padding1[7] = {};// 7 B explicit zero-init padding
    // = 48 B used; padding accounts for alignment gaps; trailing space fills to 64 B
};
static_assert(sizeof(HotSwapSnapshot<64>) == 64,
    "HotSwapSnapshot must be cache-line sized");
static_assert(alignof(HotSwapSnapshot<64>) == 64,
    "HotSwapSnapshot must be cache-line aligned");

// Global swap-seq generator. Lives at file scope; reset is monotonic
// across engine lifetime + survives hot-swap retries.
static std::atomic<uint64_t> g_swap_seq{0};
```

**Effort:** ~10 LOC amendment; ~5 min revision time.

**Why HIGH:** the v5.14.11.B FPN<F> latent-bug postmortem documented that uninit padding leaks through stack-layout shifts. The HotSwapSnapshot is exactly the struct shape that surfaces this class: cross-thread observable, returned/captured by value, mixed-alignment fields. Catching this at plan-time costs minutes; catching post-coding costs hours + a hot-swap regression.

### HIGH-2 — Plan-vs-code naming inconsistency for ModelHandle MASK constants

**Surface:** `plans/v5.15-live-readiness/subplans/2026-05-12-v5.15.0-modelhandle-migration.md` lines 122-138 (declares `MASK_HANDLE_HAS_*`) BUT line 197 declares `HANDLE_HAS(h, name)` macro that pastes to `MASK_HANDLE_HAS_##name`; AND `MASTER.md` line 504 (DOD analysis) refers to "STAMP_HAS_<NAME>" as the established pattern.

**Pattern:** `x-macro-registry-with-presence-dispatch.md` + `autopopulate-pattern-for-production-caller-class.md`

**Symptom:** the established pattern at `MemHeaders/BitmapMacros.hpp:78-90` uses `STAMP_HAS / STAMP_SET / STAMP_CLR` for ModelStampResult bit-packed flags. Plan introduces parallel `HANDLE_HAS / HANDLE_SET / HANDLE_CLR` for ModelHandle. Two adjacent patterns differ by prefix:
- `STAMP_HAS(s, NAME)` → `BITMAP_IS_SET(s.has_flags, MASK_STAMP_HAS_NAME)`
- `HANDLE_HAS(h, NAME)` → `BITMAP_IS_SET(h.has_flags, MASK_HANDLE_HAS_NAME)`

Defensible (different struct families), but the verify_model_stamp parser (.B) reads stamp bytes into BOTH `ModelStampResult` AND `ModelHandle` post-load — same parser sets bits in BOTH structs' has_flags. Two parallel mask families increase cognitive load when reading the parser.

**Suggested fix (amendment to v5.15.0.A Step 1 & 3):**

Option A (recommended): unify under `STAMP_HAS / SET / CLR` everywhere; ModelHandle bits live in `MASK_HANDLE_HAS_*` namespace OR `MASK_STAMP_HAS_*` with shared bit positions for fields that appear in BOTH structs. Explicit alignment: bits that appear in both `ModelStampResult.has_flags` AND `ModelHandle.has_flags` MUST be at the same position (so parser can set both via same mask).

Option B (less ideal): keep two namespaces (`MASK_STAMP_*` + `MASK_HANDLE_*`); accept parser duplication; document the rationale.

**Pick Option A.** Plan should be amended with a 1-paragraph "naming + bit-position alignment" sub-section at v5.15.0 Step 1. Cost: zero LOC (just naming decision). Catches drift before .A starts.

**Effort:** ~15 min plan amendment.

**Why HIGH:** the verify_model_stamp parser refactor (.B) walks a single dispatch table that produces both `ModelStampResult` (parse-side) and `ModelHandle` (post-verify copy via TryLoadRole). If bit positions diverge between the two structs, the parser table entry needs TWO masks per row — registry-tuple gains a column it doesn't need. Catch at plan-time.
