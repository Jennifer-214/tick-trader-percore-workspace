## Re-scope: critical design correction

### Discovery 1 (already addressed)
`BacktestSharded_Run` has 19+ file-static globals. Parallel invocation
requires major refactor → deferred to v5.10.0a.1 or v5.10.0b.

### Discovery 2 (THIS revision addresses)
The original plan's Phase a + Phase b assumed `Backtest_RunSweep` (the
existing OptimizerPanel sweep) trained ML models. **It does not.** It
sweeps engine-side cfg (TP/SL, fee_rate, risk_pct etc) and runs full
backtests with whatever model is already deployed.

**The actual operator workflow for hyperparam search:**
1. Click "Collect Features" once (collects feature_matrix + labels).
2. Then sweep over hyperparams: for each (xgb_subsample, ...) combination,
   train an XGBooster with those params, run WF, record metrics.
3. Pick best by val_accuracy.

This is a **NEW function** — `Backtest_RunHyperparamTrainSweep` —
parallel to `Backtest_RunSweep` but training-side. Operator already has
the building blocks: feature_matrix in `BacktestResults`, WF function
`Backtest_RunWalkForward`, hyperparam-aware booster setup
`XGBHyperparams_Apply`. Just needs orchestration.

### Why correct now (not v5.10.0a.x)
Phase a UI exposure already lists xgb_* in the Combo. Operators clicking
those will get 0 effect (UX trap) unless we ship the consumer in the
same release. The honest call is fix Phase a properly = ship D + E
before tagging v5.10.0a.

## Sub-ships (each its own tag)

### v5.10.0a.D — Backtest_RunHyperparamTrainSweep function (~3-4h)

NEW function in `Backtest/BacktestEngine.hpp`. Mirrors `Backtest_RunSweep`
shape but trains models per cell instead of running backtests.

**Signature:**
```cpp
// Configures + trains an XGBooster per sweep cell, runs WF, records
// per-cell val accuracy. Caller provides pre-collected feature_matrix
// + labels (via prior Train Model "Collect Features" run) and ranges
// over xgb_* cfg fields.
//
// Different from Backtest_RunSweep:
//   - No Backtest_Run per cell (no engine sweep)
//   - Per cell: configure XGBooster from cfg, train on shared
//     feature_matrix + labels, run WF, record val_accuracy
//   - Output: OptimizerResults (same struct; metric is val_accuracy
//     not P&L)
//
// Single-thread baseline; parallelism via v5.10.0a.F.
static inline void Backtest_RunHyperparamTrainSweep(
    OptimizerResults *opt,
    const BacktestResults *feature_data,  // pre-collected
    const OptimizerRange *ranges, int num_params,
    int label_type, int wf_n_splits, int wf_horizon, int wf_buffer,
    int wf_min_train,
    volatile int *current_run, volatile int *total_runs,
    volatile int *cancel_flag);
```

**Implementation (~80-120 LOC):**
1. Set opt->dims[], opt->total_runs from ranges
2. Per cell (i0, i1):
   - Build per-cell XGBHyperparams from base + range overrides
   - Construct DMatrix from feature_data->feature_matrix +
     feature_data->labels
   - Create Booster, apply hyperparams (XGBHyperparams_Apply with
     nthread=1 for determinism per booster)
   - Train (XGBoosterUpdateOneIter loop; n_rounds = 200 default)
   - Run WF: `Backtest_RunWalkForward(&wf_results, feature_data, ...)`
     using a per-cell label override mechanism — actually simpler:
     since XGBHyperparams flow through training but feature_data is
     constant, the WF folds use the trained booster directly. Need
     to invoke WF logic without re-training... let me think:
     
     **Cleaner design:** WF already trains its own boosters per-fold.
     For hyperparam sweep, OVERRIDE the booster setup inside WF to
     use cell-specific hyperparams. Two options:
     - A. Add a `hyperparam_override` param to Backtest_RunWalkForward
     - B. Set cfg.xgb_* fields on `feature_data->config_used` per cell,
       since WF reads from there
     
     Option B is the cleanest — feature_data->config_used is a copy
     ControllerConfig (set by BacktestSharded_Run line 111). Mutate
     it per cell, call WF, restore. **However:** mutating const
     `feature_data` is a contract violation. Solution: take a
     non-const `BacktestResults*` OR clone the config once and
     pass to WF via a NEW WF overload.
     
     **Selected:** Option C (new approach) — extend Backtest_RunWalkForward
     with optional `XGBHyperparams* override` param (default nullptr =
     use feature_data->config_used). This is a 1-line change to the
     function signature + a 3-line change inside (use override-or-cfg).
3. Record opt->stats[idx] / opt->metric[idx] per cell
4. Compare best metric → update opt->best_idx

**Files touched:**
- `Backtest/BacktestEngine.hpp` — new function (~100 LOC) + WF
  signature extension (~5 LOC)
- `tests/controller_test.cpp` — sweep test (1-2 tests)

**Tests (4 explicit; addresses /readiness 2026-05-03 must-fix #3):**
- D.1: Sweep over xgb_subsample 0.5/0.7/0.9, verify 3 cells trained,
  best by val acc identified
- D.2: Cancel mid-sweep cleanly aborts
- D.3: N_params=2 covers cross-product
- D.4: WF with override=nullptr produces identical metric to pre-v5.10.0a.D
  call (compat regression guard — defends against silent default-path
  divergence)

**Risks:**
- WF override design adds 1 param to existing function — compat-breaking
  for callers? It's a default-NULL extension, so existing callers
  unaffected. D.4 test explicitly guards this contract.

### v5.10.0a.F — Parallel pthread training (~2-3h)

Extend Backtest_RunHyperparamTrainSweep with optional parallelism. When
`cfg.xgb_train_nthread > 1` (already a cfg field per v5.10.0D), spawn
N pthread workers, each trains its own Booster on the shared
feature_matrix.

**XGBoost 3.3.0 thread-safety verified** (build log: "Found XGBoost
(found version 3.3.0)"). XGBoost 2.0+ documents:
- DMatrix construction is thread-safe (read-only on input arrays)
- Independent Booster instances (separate `XGBoosterCreate` calls)
  are thread-safe across pthreads as long as no Booster is shared
  between threads
- nthread=1 per booster keeps per-booster work single-threaded;
  parallelism is across boosters

Sources: XGBoost C API docs + GitHub #5957 #6996. 3.3.0 is well past
2.0 so the contract is stable.

**Implementation (~100 LOC):**
- Parallel path inside Backtest_RunHyperparamTrainSweep (gated by
  `xgb_train_nthread > 1` cfg flag)
- Coordinator pthread_create + pthread_join with bounded parallelism
  (worker pool size = xgb_train_nthread, capped at total_runs)
- Per-cell `WorkerArgs` carries: cell index, parameter values,
  feature_data ptr (read-only), output metric ptr, cancel flag ptr
- Workers write directly to `opt->stats[idx]` / `opt->metric[idx]`
  (each writes its own cell index; no contention)
- Cancellation: workers check cancel_flag between iterations
- Determinism: nthread=1 per booster; bytewise reproducible given
  same seed + data; parallel == serial output

**Files touched:**
- `Backtest/BacktestEngine.hpp` — parallel path (~100 LOC)
- `tests/controller_test.cpp` — parallel == serial bytewise test
  (3-4 tests)

**Tests:**
- Serial vs parallel sweep identical OptimizerResults (key claim)
- Cancel mid-parallel cleanly drops in-flight cells
- xgb_train_nthread=1 path stays serial (no pthread overhead)

**Risks:**
- Race on shared feature_data (must verify all reads are read-only)
- pthread cleanup on cancel (use detached threads + join)

**Tag:** `v5.10.0a.F` after build clean + bytewise test passes.

#### G.3 — CoreModelZoo multi-horizon load (~3-4h, was 2h)

**Re-scoped per /readiness 2026-05-03 must-fix #1:** Current
`CoreModelZoo<F>` has 1 ModelHandle per role (not N). Multi-load
requires struct mutation. Effort revised from 2h → 3-4h.

**Selected design — Sidecar EnsembleModelZoo (low blast radius):**
Keep `CoreModelZoo<F>` UNCHANGED. Existing 1-handle-per-role callers
stay valid. Add a SIDECAR struct populated only for multi-horizon
ops:

```cpp
// EXISTING — unchanged:
template <int F>
struct CoreModelZoo {
    ModelHandle<F> barrier;        // single horizon (legacy)
    ModelHandle<F> regime;
    ModelHandle<F> exit_predictor;
    ModelHandle<F> buy_signal;
};

// NEW — v5.10.0a.G.3:
template <int F>
struct EnsembleModelZoo {
    ModelHandle<F> barrier[HORIZON_LIST_MAX];      // [0..N-1] populated
    ModelHandle<F> regime[HORIZON_LIST_MAX];
    ModelHandle<F> exit_predictor[HORIZON_LIST_MAX];
    ModelHandle<F> buy_signal[HORIZON_LIST_MAX];
    int barrier_count;        // 0 = ensemble inactive for this role
    int regime_count;
    int exit_predictor_count;
    int buy_signal_count;
    int active;               // 0 = use single_zoo; 1 = use ensemble
};

// Engine state holds BOTH:
//   CoreModelZoo<F>     single_zoo;     // existing single-horizon path
//   EnsembleModelZoo<F> ensemble_zoo;   // populated when cfg.horizon_count > 0
//
// At boot:
//   if (cfg.horizon_count > 0) populate ensemble_zoo + set active=1
//   else continue using single_zoo as before (active=0 → ensemble_zoo unused)
//
// At inference:
//   if (zoo->active) iterate ensemble; else use single_zoo (existing path)
```

**Why sidecar vs struct mutation:**
- Existing 30-50 single-zoo dispatch sites stay UNTOUCHED — zero
  blast radius for non-multi-horizon operators
- New multi-horizon path adds ONE explicit branch (`if active`) at
  G.4 inference site
- Operators not using horizon_list see zero behavior change
- v5.10.0a.G.3 is now scoped to CoreModelZoo.hpp + 1-2 inference
  sites (G.4's responsibility), not 30-50 sites

**Memory: same as plan original — up to ~1.6GB per core when active.**
Default empty = no extra memory.

**Files touched:**
- `ML_Headers/CoreModelZoo.hpp` — new EnsembleModelZoo struct +
  EnsembleModelZoo_LoadFromCfg helper (~120 LOC)
- `ML_Headers/CoreModelZoo.hpp` — ensemble_zoo lifecycle (Init/Free)
