### HIGH-2 — structural-fix-preferred-decision-framework — 1k-cycle reset is a band-aid

**Surface:** plan lines 70-72 + 140-144 (numerical drift mitigation)
**Pattern:** `structural-fix-preferred-decision-framework.md`
**Symptom:** plan admits Welford-style `M2` accumulator is "stable but not perfect for Σx²; periodic full-recompute reset (~every 1000 cycles) keeps drift bounded." This is direct-patch shape — fix this instance via periodic recompute. **Per the framework, bug class "incremental algorithm drifts" recurs** → structural fix preferred even at higher upfront cost.

**Available structural alternatives:**

A. **Sliding-window Welford (true sliding-window O(1) variance):** drop oldest as new arrives; drift bounded by window size (REWARD_RING_SIZE=256 records). No periodic reset; deterministic. Higher complexity (need ring drop logic on `outer_xy`).

B. **Kahan / compensated summation in Welford updates:** numerically stable accumulation; ~3-4 extra fmadd_pd ops per update. Bounds error to O(ε) instead of O(N·ε). Doesn't address "drift over very long runs" claim (compensated summation bounds error per-update, not per-accumulator-age) so periodic recompute may still be needed BUT at much longer cadence (10k-100k cycles instead of 1k).

C. **Both A+B combined:** highest precision; full sliding-window with compensated summation. Cost: ~2x scalar update cost; AVX-512 path absorbs it.

D. **Direct patch (plan's current proposal):** periodic recompute at 1k cycles. Cheap; simple; semantically "good enough."

**Recurrence count analysis per the framework:**
- Welford-style drift is a textbook recurring class in incremental statistics (40+ years of literature)
- Codebase precedent: `RollingStats_Push` (ML_Headers/RollingStats.hpp:194+) uses running-sums (NOT Welford); operates on FPN<F> (exact integer math) — drift is N/A there per the plan's own observation (line 75-76 of RollingStats.hpp)
- THIS ship uses `double` (not FPN); drift IS real here
- Recurrence count in the ENGINE: 1 (this is first incremental float accumulator in the engine). Framework says 2-3 occurrences = "potential class"; 4+ = "mandatory structural fix"

**Verdict:** at recurrence count 1, framework permits direct patch + flag. However, framework Step 3 (upfront-cost-vs-future-multiplier) says "lean toward structural fix when future-work simplification is large AND upfront cost bounded." Here:
- Future simplification: SMALL (no planned 2nd incremental-float accumulator in the engine roadmap)
- Upfront cost: BOUNDED (Welford sliding-window is well-documented)
- Risk: LOW (option C is additive; falls back to recompute on edge cases)

**Recommendation:** DEFER decision to operator consult. Three reasonable paths:
1. **Ship Plan D (1k reset)** — direct patch; flag for sliding-window when next incremental float accumulator emerges (~ "recurrence count 2" trigger)
2. **Ship Plan B (Kahan in updates)** — minimal structural fix; bounds per-update error; reset cadence relaxes to 10k-100k cycles or eliminates
3. **Ship Plan C (sliding-window Welford + Kahan)** — full structural fix; closes the class for any future incremental float accumulator

Operator decision criterion: how confident are we no 2nd incremental float accumulator emerges in v5.15+? If "very confident: low priority feature space" → D is fine. If "may emerge in maker order routing v6.0" → B or C is the durable choice.

**Effort estimate:**
- Plan D: 0 (already in plan)
- Plan B: ~1h additional (Kahan helper + 4 update sites; cf. compensated-summation literature)
- Plan C: ~2-3h additional (Welford sliding-window helper + drop-oldest logic + ring traversal)

**Cross-ref:** DESIGN_SPECS/meta-disciplines/structural-fix-preferred-decision-framework.md; CLAUDE.md item 19; CLAUDE.local.md "structural fix preferred" rule.

**Surface:** plan Step 4 (cfg field declaration)
**Pattern:** `cfg-flag-eligibility-criteria.md`

- `cfg.ridge_across_horizons` (ControllerConfig.hpp:666) — same
- `cfg.exit_blender_mode` (ControllerConfig.hpp:1105) — same

**Why precedent says STAY DIRECT (root-cause audit of the v5.14.9.F sweep history):**

Re-reading the v5.14.9.F.4 closure (TECH_DEBT-009 PARTIAL CLOSED comment in DOCS/TECH_DEBT.md:236): the sweep migrated **booleans presented as 0/1 flags**. Inspection of the actual ridge fields:

- `ridge_across_horizons` declared as `int` with comment `// 0=bandit (default), 1=Ridge across horizons`
- `exit_blender_mode` declared as `int` with comment `// 0=bandit (default), 1=Ridge`

These ARE binary flags semantically; comment naming pattern even confirms (`!= 0` predicate in SlowPathGateRegistry.hpp:85, :89). **Framework-wise, they SHOULD be in FOREACH_ML_CFG_FLAG.** The 5-criteria audit applied to them returns MIGRATE same as `ridge_online_corr`.

**Three hypotheses for why the v5.14.9.F sweep skipped them:**

**Hypothesis A (oversight):** the sweep audit listed booleans-as-`int` fields by grep pattern (e.g., `int .*_enabled` / `int .*_active`) which would miss `ridge_within_horizon` (no `_enabled` / `_active` / boolean-suggestive suffix). Plausible.

**Hypothesis B (deliberate — stamp-binding coupling):** these 3 fields are ALL in `FOREACH_STAMP_BOUND_CFG` via DIRECT_FIELD presence dispatch (StampBoundCfgRegistry.hpp:102-138). Migrating to FOREACH_ML_CFG_FLAG would require the stamp-binding registry to ALSO understand bitmap-flag fields (different reader/parser path). Possible deferral rationale: keep bitmap-flag migration orthogonal to stamp-binding for now.

**Hypothesis C (deliberate — semantic asymmetry):** `ridge_within_horizon=1 + ridge_across_horizons=1` is a valid combined state (Ridge across BOTH dimensions); these are NOT 2 independent feature toggles — they compose hierarchically. Same applies to `exit_blender_mode`. Force-bitmap-packing them would still work (each bit is independent) but the X-macro tuple metadata would lose the "compose-with-sister-flag" relationship.

**Recommendation: DEFER decision to operator consult.**

Three reasonable paths for `cfg.ridge_online_corr`:
1. **MIGRATE to FOREACH_ML_CFG_FLAG** (per framework) — and also catalog 3 existing ridge fields as TECH_DEBT for future migration in a unified sweep
2. **STAY DIRECT** (per precedent) — match the 3 existing ridge fields' shape for consistency within the ridge-blender domain
3. **DEFER decision until /parity-check + /trace-deps complete** — stamp-binding implications need verification (does `ridge_online_corr` need stamp-binding? plan says no; verify in /trace-deps)

Operator decision criterion: is there architectural value in keeping the ridge-blender cfg fields visually clustered as direct fields, OR is there value in unified bitmap-flag treatment for all ML booleans?

**Effort estimate:**
- Path 1: ~30 min (add to FOREACH_ML_CFG_FLAG; update parser+GUI auto-flow); plus TECH_DEBT entry for migrating the 3 existing fields
- Path 2: 0 (plan's current proposal)
- Path 3: ~5 min to add deferral comment to plan + open TECH_DEBT entry

### MEDIUM-2 — mirror-pattern (CLAUDE.md item 19) — extract helper for dual call sites

**Surface:** plan Step 3 (engine wiring) — TWO call sites mirror same shape: buy-side at StrategyParameters.hpp:996 + exit-side at :1195
**Pattern:** `structural-fix-preferred-decision-framework.md` Class 18 mirror prevention; `postloadsetup-registry-pattern.md` helper-extraction precedent
**Symptom:** plan adds `if (config->ridge_online_corr)` block at BOTH sites. Each block does: (a) get latest record from reward_ring, (b) call UpdateOnline, (c) periodic 1k-reset gate, (d) FinalizeCorr OR fall back to full BuildCorr. Same 4-step sequence at TWO sites against different ezoo structs (`ezoo->ridge_state` + `ezoo->exit_ridge_state`).

**Class 18 mirror risk:** if a future ship adds a 5th step (e.g., "validation check before finalize" or "log on reset") it would need to land at BOTH sites. Same shape as PARITY-009/010/011/012 (PostLoadSetup precedent at v5.14.2.E.1) where init/load step additions at one site silently broke the other path.

**Recommendation:** extract a helper at the v5.14.11 ship time (not deferred). Mirror the PostLoadSetup discipline: extract once when the second call site emerges, not when the third emerges.

```cpp
// RidgeBlender.hpp — extract per-side update+finalize as one helper.
template <unsigned F>
inline void RidgeBlender_OnlineCycleStep(RidgeWeights<F>& ridge_state,
                                          const EnsembleModelZoo<F>::PredictionRecord* reward_ring,
                                          int ring_head,
                                          int ring_count,
                                          int n_models,
                                          uint64_t reset_cadence_cycles) {
    // Step 0: get latest record
    int latest_idx = (ring_head - 1 + REWARD_RING_SIZE) % REWARD_RING_SIZE;
    // Step 1: UpdateOnline
    RidgeBlender_UpdateOnline<F>(&ridge_state.online_state,
                                  reward_ring[latest_idx].predictions, n_models);
    // Step 2: periodic reset gate
    if (++ridge_state.online_state.cycles_since_recompute > reset_cadence_cycles) {
        // Full recompute from flat history
        RidgeBlender_BuildCorr<F>(ridge_state.corr_matrix, /* flat ring */, ring_count, n_models);
        ridge_state.online_state.cycles_since_recompute = 0;
    } else {
        // Step 3: Finalize incremental
        RidgeBlender_FinalizeCorr<F>(ridge_state.corr_matrix, &ridge_state.online_state, n_models);
    }
}
```

Both call sites become 1 line:
```cpp
// buy-side (StrategyParameters.hpp:996 area)
RidgeBlender_OnlineCycleStep<F>(ezoo->ridge_state, ezoo->reward_ring, ezoo->reward_ring_head,
                                  /* count */, ezoo->primary_count, 1000);
// exit-side (StrategyParameters.hpp:1195 area)
RidgeBlender_OnlineCycleStep<F>(ezoo->exit_ridge_state, ezoo->exit_reward_ring,
                                  ezoo->exit_reward_ring_head, /* count */,
                                  ezoo->exit_predictor_count, 1000);
```

**Effort:** ~30 min (helper extraction; both call sites collapse to 1 line); plus mirror-symmetry test (assert helper produces same state regardless of which ring/struct fed in).
