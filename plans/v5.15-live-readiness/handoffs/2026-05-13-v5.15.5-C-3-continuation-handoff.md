## Step 4 — Session-specific design context (read before resuming Phase 3b)

This session worked through several DESIGN DECISIONS that the plan file alone doesn't capture in full nuance. Read these before resuming:

### 4a. Option A canonical vs Option B (.B.7-style separate registries)

**Decision:** Option A — single canonical FOREACH_OMS_FIELD with 7-attribute tuple (rather than 3 separate registries that .B.7 used). **Caramel chose Option A** after asking "how is A overengineering?" and pushing back on my initial "B is right-sized" recommendation.

**Rationale:**
- OMS RESET fields = PERSIST fields exactly (10 fields; 1:1 overlap)
- .B.7's case had RESET as a SUBSET of INIT (different field semantics)
- For OMS, the 3 derived views project from ONE canonical source — drift impossible
- Adding new OMS field = 1 row; cannot drift across views

**Tuple shape:** `X(name, type, init_value, reset_value, reset_kind, persist_kind, persist_mask)` where `reset_kind` ∈ {DO_RESET, SKIP_RESET}, `persist_kind` ∈ {DIRECT, BIT, SKIP_PERSIST}.

**Reference design specs (in compose-with order):** registry-tuple-as-single-source-of-truth, heterogeneous-registry-pattern, autopopulate-pattern-for-production-caller-class, pre-post-cfg-registry-split-for-emit-order-preservation, x-macro-registry-with-presence-dispatch, bitmap-flag-api.

### 4b. SHARDED_SNAPSHOT_VERSION 7 → 8 bump + refuse-not-migrate

**Decision:** Bump cleanly + refuse v7 files. **Caramel's framing 2026-05-13:** "if backward compat isnt an issue, is this a real problem?" + "once i hit a certain point ill start thinking about backwards compta, but thats a later issue, not a now issue."

**Reasoning:**
- v7 snapshots are paper-mode-only (live mode reconciles from exchange, never persists via this path)
- Paper P&L history is recoverable by running paper again — no financial impact
- Codebase precedent: v6→v7 bump also refused old; no backward-compat layer was added

**Implication for Phase 3b:** the canonical registry adds `paper_session_start_us` as a 10th row — wire format changed at v8. Loaders for v7 files refuse cleanly via existing version-mismatch path in `ShardedSnapshotPersist.hpp:324`.

### 4c. AUTOPOPULATE Layer ordering (Phase 3b critical)

The OMS_INIT_AUTOPOPULATE macro body has **8 layers** with strict ordering:

```
L1: FOREACH_OMS_FIELD value-init walk (24 scalar fields)
L2: special-case scalars (adapter struct copy, oms_state_flags conditional
     LIVE_TRADING bit, event_log_mode arg copy)
L3: alignas(64) cluster atomic stores (flatten_pending, recovery_until_us,
     total_submitted/filled/rejected)
L4: Portfolio_Init helper-init
L5a: Order_Init per-slot across MAX_INFLIGHT_ORDERS (different scope from
      MAX_PORTFOLIO_POSITIONS)
L5b: FOREACH_OMS_PER_SLOT_FIELD + OMS_META_CLEAR across MAX_PORTFOLIO_POSITIONS
L6: SPSC ring inits (result/ws_result/reconcile + 16 submit queues)
L7: OrderEventLog conditional init + LoadFromDisk + replay
     MUST RUN BEFORE L8 (StartAsyncWriter depends on Init'd log)
L8: OrderEventLog_StartAsyncWriter (MUST RUN LAST)
```

**Layer ordering invariants** (already annotated via MUST FOLLOW comments at the existing OrderManager_Init call sites in Phase 1):
- L7 before L8 (`StartAsyncWriter` depends on log being `_Init`-only or `_InitWithFile`'d)
- L7's replay block (Portfolio_FromEventLog) depends on `OrderEventLog_Init` running first inside L7

**Phase 3b migration:** replace OrderManager_Init body (~120 LOC) with a single `OMS_INIT_AUTOPOPULATE(oms, adapter, live_trading, starting_balance, fee_rate, event_log_mode, event_log_path);` call. The macro's body produces the 8 layers in order.

### 4d. Per-core trade log + regime — operator semantic refinements

Caramel asked for two refinements 2026-05-13 (captured in the bundled-plan):

1. **Regime per trade** — schema change adds `regime` + `regime_name` columns to trade log CSV. Captured at trade-emit time from `state.cores[core_id].regime_state.current_regime`. Reuses FOREACH_REGIME or REGIME_NAME[] lookup.

2. **Per-core CSV split** — `ShardedTradeLog::file` (single FILE*) → `files[MAX_EXECUTION_CORES]` array. 16 per-core CSVs instead of one aggregate. Reader/TradeHistoryPanel reads merged sort-by-timestamp from per-core files.

**Composition:** new `FOREACH_TRADE_LOG_COL` registry (analog of `FOREACH_CALIB_LOG_COL`) drives column-by-column row emit. Adding next column = 1 row.

### 4e. summary.json structure — global + per_core + per_strategy + per_regime

Operator-visible JSON structure for paper-reset archive's summary file (Phase 6 deliverable). Full schema in bundled-plan Phase 4 section. Sections:

- `session`: start_us / end_us / iso strings / duration
- `global`: balance_start/end, realized_pnl, fees, counters, kill_switch state
- `per_core` (16 entries): strategy_id + name, wins/losses/win_rate, core_realized, peak_balance, dd_pct
- `per_strategy`: aggregated by strategy_id (sum over cores running that strategy)
- `per_regime`: aggregated by regime (sum over trades placed during that regime)

The `per_regime` section REQUIRES regime data in trade log (Phase 5 dependency). Phase 4's registry-driven JSON writer composes with Phase 5's per-core regime-captured CSVs.

### 4f. Bench gate composition opportunities (7 patterns)

The bench gate design spec was extended this session with a **"Extreme-optimization composition"** section listing 7 compose-with patterns. Phase 7 implementation can opt into:

1. AUTOPOPULATE companion (FOREACH_OMS_BENCH_SITE) — N bench sites = N registry rows
2. Multi-bit mode encoding — pack bench mode (OFF/COARSE/FINE/FULL) as 2 bits
3. **Per-core bench enable** — extreme optimization; instrument just core N, leave 15 cores at production-zero-cost via `partner-core-bitmap-pattern`
4. Cache-layout discipline (HOT bucket array + COLD observability sub-cluster)
5. Branchless bucket-index calc (BMI2 PEXT for non-power-of-2 buckets)
6. Cluster isolation (ND1; each histogram alignas(64))
7. Heterogeneous registry (mixed measurement types per site)

**Recommended first application** (Phase 7 minimum): pattern 1 (AUTOPOPULATE) + pattern 6 (cluster isolation) + pattern 5 (branchless math). Patterns 2-4 are opt-in for extreme cases.
