### MED — M4: O4 caller-responsibility enumeration omits "what if alloc fails" continue semantic

Plan body Step C.1 LIVE responsibility list at line 605-621 says:
```cpp
if (!zoo_ptr) {
    fprintf(stderr, ...);
    CORE_STATE_FLAG_SET(state.cores[c], MODEL_LOAD_FAILED);
    continue;
}
```

`continue` skips the rest of the per-core loop iteration. But Step C.1 step 4 (post-helper LIVE-only wires) shows `oms.ezoo_refs[c]` + `CoreLatencyStats_Enable` AFTER the helper call — these are inside the `for (int c = 0; ...)` loop body. The `continue` correctly skips them when alloc fails.

**Subtle issue:** at HEAD LIVE :947 the actual continue ALSO skips ExecutionCore_Init + EventLoopState_RegisterCore + EventLoopState_SetCoreStrategy (because at HEAD those happen AFTER the alloc inside the for body). But under v1.6 caller restructure, ExecutionCore_Init etc. are INSIDE the helper body — which is called BEFORE alloc-check completes? No, alloc-check is at lines 606-621 of Step C.1, BEFORE helper call at line 623. Order is:

1. Compute core_balance
2. ML alloc attempt (with continue on fail)
3. Helper call (passes zoo_ptr/ezoo_ptr — nullable if alloc skipped via STRATEGY != ML check; nullable also if alloc failed and continue skipped 3+4)
4. Post-helper wires (skipped by continue when alloc failed)

So order is right — but the question is whether SPSCRing_Init + ExecutionCore_Init + EventLoopState_RegisterCore (which happen INSIDE the helper) get called when alloc FAILS. Per v1.6 the answer is: alloc-fail continues BEFORE helper is called, so SPSCRing_Init et al. are SKIPPED for that c. **But at HEAD LIVE :909-914 (pre-extract) the SPSCRing_Init et al. happen BEFORE the alloc-check :941-948.** So this changes ordering semantics: post-extract LIVE skips per-core SPSCRing_Init when alloc fails; pre-extract LIVE inits SPSCRing then fails alloc then continues.

**Is this a behavioral regression?** Probably NOT — at boot when alloc fails the core is dead anyway (MODEL_LOAD_FAILED set; no permission grant; no tick consumption). The SPSCRing being uninitialized is benign (no producer pushes ticks to it because... wait, actually producer DOES push ticks to it via fan_out at LIVE :2400+ regardless of MODEL_LOAD_FAILED state).

**Recommended amendment:** Plan body Step C.1 should explicitly choose:
(a) Alloc-check BEFORE helper call (current v1.6 spec; small ordering regression — SPSCRing not initialized on alloc-fail cores); OR
(b) Alloc-check moved INSIDE helper as initial work, with nullable zoo_ptr/ezoo_ptr meaning "alloc may have failed; helper sets MODEL_LOAD_FAILED + returns early" (no caller continue needed); OR
(c) Helper signature takes a separate `out_alloc_failed` bool pointer + caller continues on that.

(a) is current spec but has the ordering subtlety. (b) is cleanest contract-wise but pushes more logic into helper. (c) is awkward. Per v1.6 O4 caller-responsibility framing, (a) is consistent — but operator should be aware of the ordering subtlety. Worth a one-liner at Step C.1 note: "SPSCRing_Init + ExecutionCore_Init + EventLoopState_RegisterCore are SKIPPED for alloc-fail cores (ordering reversal vs pre-extract; benign — fail-cores have no permission anyway, ring being empty is safe)".

### MED — M5: Branchless gate sketch in plan body Step B.3 is hand-wave-shaped

Plan body Step B.3 sketch at line 557:
```cpp
uint64_t bo_mask = -(uint64_t)(!FPN_IsZero(cfg.cores[c].breakeven_on_profit_threshold) ? 1 : 0);

```

The `if (bo_mask)` is STILL a branch — just one whose mispredict-rate is low because operators with feature-off cfg consistently hit the `bo_mask == 0` path. This is the "predictable branch" pattern, NOT the "branchless dispatch" pattern. Per H20 + `branchless-dispatch-discipline.md` § "The hand-wave anti-pattern":
> "branch is fine because predictor handles it" → STOP; re-examine through determinism + p99 lens.

Two acceptable patterns:
(a) **Truly branchless:** call `EventLoop_BreakevenOnProfitOneCore` UNCONDITIONALLY; the OneCore body's first line is `if (FPN_IsZero(cfg.cores[c].breakeven_on_profit_threshold)) return;` (early-out at function entry). Caller pays function-call overhead (~5ns ret/ret stack push) but no branch in caller.
(b) **`if constexpr`-friendly compile-time:** N/A here (runtime cfg value).
(c) **Function pointer table:** overkill for 2-state dispatch.

**Recommended amendment:** Step B.3 sketch should be replaced with the cleaner pattern (a):
```cpp
// In SlowPathCycleOneCore body:
EventLoop_BreakevenOnProfitOneCore(&state, &cfg, current_price, c);
// (Inside helper: if (FPN_IsZero(cfg.cores[c].breakeven_on_profit_threshold)) return early; ~5ns ret-on-zero, ~50-200ns full call)
```

Sister to existing pattern at LIVE :3242-3243 where `EventLoop_TimeExitOneCore` is called UNCONDITIONALLY then short-circuits internally on `cfg.cores[c].max_hold_ticks > 0`. SAME shape, SAME discipline.

This is also cheaper than the v1.6 O3 sketch because:
- v1.6 O3 sketch: FPN_IsZero (5ns) + cmov mask (1ns) + branch on bo_mask (5ns predicted, 30-100ns mispredicted) + maybe full call
- Pattern (a): unconditional call (5ns ret-stack) + FPN_IsZero (5ns) + early-return (~1ns ret) OR full call

For threshold=0 cohort: pattern (a) is ~10ns vs v1.6 O3's ~10ns (when predicted) — same. For threshold>0 cohort: pattern (a) is ~50-200ns vs v1.6 O3's ~50-200ns + extra mask compute. Equal or better. Plus pattern (a) is consistent with existing TimeExitOneCore/TrailingSLRatchetOneCore discipline.
