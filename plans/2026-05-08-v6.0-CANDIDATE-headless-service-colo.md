# v6.0 Candidate — Headless Service + Colo Architecture (PRIVATE)

**Date drafted:** 2026-05-08
**Status:** CANDIDATE STUB. v6.0 is a major architectural shift —
not a sprint plan, but a design map for "where the engine goes after
the v5.x optimization cycle closes."

**Why private:** captures unshipped architectural direction +
operator-specific deployment intent. Per CLAUDE.local.md
"Going-forward rule for new docs: default to private if... names
operator-specific deployment details (NUMA topology, NIC brand,
isolcpus core IDs, etc.)".

**Predecessor:** v5.x final state. v6.0 opens after operator commits
to colo deployment. No specific commitment yet.

**Source thread:** operator question 2026-05-08 about decoupling
runtime from GUI, running as headless service, attaching via SSH for
TUI/GUI output.

---

## Theme

v6.0 is the **headless-service + colo architecture** shift. Splits
the current monolith engine + GUI binary into:
- **Engine binary** — pure trading core, runs as systemd service,
  publishes TUISnapshot over wire (flatbuffer / capnproto). No GUI
  code linked.
- **Remote management binary** — connects to engine over secure
  channel (TLS/mTLS over TCP, OR Unix domain socket when local).
  Renders snapshot via TUI (ANSI) or GUI (ImGui-over-network).
  Stateless: engine is source of truth.

**Not v5.12 / v5.13:** architecturally invasive (~3-4 weeks min).
Wait for the v5.x optimization cycle to close + operator commitment
to colo deployment before opening v6.0.

## Sub-shifts (5 candidate ships)

### v6.0.1 — Snapshot wire serialization

**Goal:** TUISnapshot struct serialized over network. Choice:
flatbuffer (fast deser, schema-versioned), capnproto (also good),
custom binary (max speed, custom maintenance). Recommendation:
flatbuffer (good ecosystem, schema evolution).

**Shape:** new file `CoreFrameworks/SnapshotWire.fbs` (flatbuffer
schema mirroring TUISnapshot). Add codegen step in `build.sh` to
generate `snapshot_wire_generated.h`. Engine has new function
`TUISnapshot_Publish_Wire(snap)` that serializes to a wire buffer
ready for transport.

**Effort:** ~3-4 days.

---

### v6.0.2 — Engine "publish to network" mode

**Goal:** Engine listens on a configurable port (cfg
`management_port=9999`), accepts authenticated client connections,
publishes snapshot stream. Multi-client (multiple GUI/TUI viewers
attached simultaneously).

**Shape:**
- New thread (or async io_uring loop) in engine: accept-loop
- Authentication: pre-shared key (cfg
  `management_secret=<hex>`) for v6.0; future TLS in v6.1
- Stream: snapshot every `snapshot_publish_period_ms` (default 100ms)
- Lock-free fan-out: snapshot_wire buffer mmap'd, all clients read
  from same buffer (one writer = engine, N readers = clients)

**Effort:** ~1 week including security review + lock-free fan-out.

---

### v6.0.3 — Remote management binary (TUI client)

**Goal:** New binary `bin/engine_tui_remote`. Connects to engine,
streams snapshot, renders ANSI dashboard. Operator-friendly: launch
with `engine_tui_remote --host trading.colo.local --port 9999
--secret $SECRET`.

**Shape:** thin wrapper around existing TUIAnsi rendering code; reads
TUISnapshot from network instead of in-process. ~500 LOC.

**Effort:** ~3 days.

---

### v6.0.4 — Remote management binary (GUI client)

**Goal:** New binary `bin/engine_gui_remote`. Connects to engine,
streams snapshot, renders ImGui dashboard. Same UX as current
`bin/engine_gui` but engine runs elsewhere.

**Shape:** thin wrapper around existing GUI rendering. ~1k LOC.

**Effort:** ~1 week including authentication UI + reconnection
handling.

### v6.0.4.5 — Multi-symbol shared-portfolio architecture

**Why on this list:** today each engine instance owns a single symbol's
OMS + portfolio. Adding BTC + ETH on the SAME portfolio (cross-symbol
risk allocation, shared OMS, multiplexed tick fan_out) is a major
architectural shift. Operator question 2026-05-08: "if i wanna add
like BTC + ETH strats, on the same portfolio, it would be good to do
that?" — answered: shared-portfolio is v6.0+ work; multi-instance
approach is the v5.x paper-test path.

**Today's working pattern (zero code change):**
- Run N engine instances on same hardware (one per symbol)
- Each has own portfolio + OMS + cfg + ML model
- Cross-symbol analysis via post-processing (combine paper_runs/ CSVs)

**v6.0 shared-portfolio architectural shift:**

1. **Multi-symbol fan_out** — one process reads N WS streams,
   multiplexes ticks across N per-core slow-paths or N symbols-as-
   cores in a single slow-path. Producer thread becomes the
   multiplexer; per-symbol per-core data plane stays the same shape.

2. **Shared OMS / portfolio** — `OrderManagerState` becomes per-symbol
   sub-states + a top-level allocator. `Portfolio.active_bitmap`
   extends from uint16_t (16 slots) to per-symbol bitmaps. Risk
   allocation: `cfg.symbol_<X>_balance_share` distributes capital
   across symbols. Cross-symbol rebalancing on slot exit.

3. **Per-symbol cfg + ML loading** — `cfg.symbol_<X>_strategy`,
   `cfg.symbol_<X>_model_path`. Bandit ensemble per symbol or shared
   bandit across symbols (regime classifier output gates per-symbol
   strategy selection).

4. **Per-symbol RollingStats / RegimeDetector / FlowFeatures** —
   each symbol's slow_state independent. Memory footprint scales
   linearly with N symbols. AVX-512 across symbols becomes
   load-bearing here (Phase 2.A's deferred AVX-512 FPN_Min/Max
   array-form would vectorize across symbol lanes — this is the
   re-trigger condition for that ship).

5. **Snapshot persist with multi-symbol state** — `SHARDED_SNAPSHOT_VERSION`
   bump + per-symbol section. Forward-compat handling for legacy
   single-symbol snapshots.

6. **Risk allocation policy** — first-come-first-served (current
   per-core pattern extended to per-symbol-per-core), or weighted
   by per-symbol vol/sharpe, or correlation-aware (avoid
   simultaneous BTC + ETH long when correlation is high).

**Effort estimate:** 2-4 weeks solo-developer minimum for the full
shift. Phase 4 paper-test data should drive whether to commit; if
cross-symbol provides orthogonal alpha to BTC alone → ship; if
not → defer indefinitely.

**Re-trigger conditions:**
1. Phase 4.A paper-test reveals cross-symbol strategies have alpha
   (ETH contributes orthogonal P&L vs BTC alone)
2. Operator commits to colo deployment (multi-symbol density matters
   more at colo where rack space + power are constrained)
3. Operational pain from running multiple engine instances surfaces
   (port conflicts, reconcile coordination, snapshot
   per-instance vs per-account confusion)

**v6.0 + multi-symbol could ship together OR separately.** They
share the "operator goes operational" trigger but the architectural
shifts are independent. Multi-symbol could ship first under v5.13+
if paper-test surfaces alpha early.

### v6.0.5 — Persistent service infrastructure

**Goal:** systemd unit file for auto-restart, log rotation,
SCHED_FIFO promotion of hot-path threads, NUMA pinning, etc.
Operator runbook in `DOCS/OPERATOR_DEPLOYMENT.md` becomes a
service-deployment guide.

**Shape:**
- `tools/engine.service` — systemd unit
- Log rotation via systemd journal OR logrotate
- Restart policy: on-failure with backoff
- Health check endpoint (HTTP `/health` returning JSON with engine
  state + uptime + recent error counts)

**Effort:** ~1-2 days.

## Re-trigger conditions for v6.0 itself

1. Operator commits to colo deployment (signs the colo provider
   contract, or stages a colo trial)
2. Multi-client management need (operator + monitoring + ops
   dashboard all connected)
3. Engine restart-induced downtime becomes a problem (= operational
   maturity demands true service architecture)
4. Multi-symbol expansion makes the in-process GUI fall behind on
   render cadence (= GUI thread struggles to keep up)

If none of these fire within 6 months of v5.12 close, v6.0 stays a
candidate.

## Open architectural questions (for when v6.0 opens)

- **Wire format:** flatbuffer vs capnproto vs custom? Recommendation
  above is flatbuffer; revisit at v6.0.1 design time.
- **Multi-client coherence:** all clients see the same snapshot
  generation, or each client has its own pacing? Recommendation:
  same snapshot (single-writer engine fans out to all).
- **Snapshot back-pressure:** if a client is slow, does engine block
  or drop snapshots? Recommendation: drop (latest-wins; engine never
  blocks on management-channel writes).
- **Authentication:** pre-shared key (v6.0) → mTLS (v6.1) → SSO
  integration (v6.2)?
- **Multi-engine deployment:** one client connects to N engines
  (multi-symbol)? Useful but adds UX complexity. Defer to v6.1.
