## Why this ship exists

`v5.15.5.F.4c.1` paper-test surfaced two compounding cfg-surface issues:

1. **Visual:** Global tab has many duplicate empty section headers (pre-existing `.F.4c` bug worsened by `.F.4c.1` adding 19 cohort rows). Operator can't usefully scan the Settings panel.
2. **Architectural:** Trading parameters live at global scope with optional per-core override. Each core nominally has its own ridge_lambda / confidence_* / thompson_* / bandit_algorithm, but the cfg surface presents them as "set a global, optionally override per-core." Operator can't reason cleanly about "what config is this core actually running."

Caramel's stated architectural intent (2026-05-15):
> *"global settings honestly shouldnt have any settings that control actual trading strats, it should mostly be the gui settings right? like all actual trading settings should be only per core right? for finer control, no global overrides, splits into a single global registry, and then a reuseable per engine core registry"*

The structural answer: **split `FOREACH_CFG_FIELD` into TWO registries** with clear scope discipline. System/GUI/operational/recording knobs stay global (operator sets once); trading/ML/risk/regime knobs become per-core authoritative (each core has its own row instance — NO global default, NO override mechanism). The "set globally + override per-core" pattern that's been the source of Class 24 recurrence dies structurally.

This is the foundation `.F.4d`'s wire-format framework + `.F.4e`'s GUI metadata derived filters + `.F.4d.1`'s bandit ghost-training expansion all consume. Built on the wrong registry shape = retrofit pain at every subsequent ship. Locking the architecture NOW is correct sequencing.

### A. Two-registry framework infrastructure

| Component | LOC | Notes |
|---|---|---|

| `g_global_cfg_field_descriptors[]` + `g_per_core_cfg_field_descriptors[]` | (auto-gen from each registry) | Same `CfgFieldDescriptor` struct from `.F.4b/.F.4c`; two arrays |
| Per-registry bitmap masks + composed views | (auto-gen via `FOREACH_METADATA_BIT` applied twice) | Each registry gets its own mask set: `g_global_cfg_render_mask` / `g_global_cfg_save_mask` / etc. + `g_per_core_cfg_render_mask` / ... |
| `cfg_field_names_unique` static_assert | (extended) | Per-registry uniqueness check (each registry's rows internally unique); cross-registry-name-collision is ALLOWED only if intentional (a global `xgb_seed` and per-core `xgb_seed` — but the discipline doc discourages this; one or the other) |
| `GlobalRenderTable<F>` + `PerCoreRenderTable<F>` | (function-pointer tables auto-gen) | Mirrors `CfgRenderTable<F>` from `.F.4c`; two instances |

`tt::cfg_parse_field<T>` / `cfg_save_field<T>` / `cfg_assign_field<T>` / `cfg_diff_field<T>` / `cfg_render_field<T>` are **UNCHANGED** — they're type-trait dispatch operating on `T&`, not registry-aware. Same primitives consume either registry.

### B. ControllerConfig<F> restructure

```cpp
// NEW shape — one PerCoreCfg<F> instance per execution core
template <unsigned F>
struct PerCoreCfg {
    // ~50 trading fields, X-macro-generated from FOREACH_PER_CORE_CFG_FIELD
    FOREACH_PER_CORE_CFG_FIELD(EMIT_CFG_STRUCT_FIELD)
};

template <unsigned F>
struct ControllerConfig {
    // ~15 global fields — X-macro-generated from FOREACH_GLOBAL_CFG_FIELD
    FOREACH_GLOBAL_CFG_FIELD(EMIT_CFG_STRUCT_FIELD)
    
    // Per-core trading config — N authoritative instances
    PerCoreCfg<F> cores[MAX_EXECUTION_CORES];  // 16
    
    // Non-cfg manual fields (per .F.4d MANUAL_FIELDS_INVENTORY discipline):
    //   - Runtime state, derived/computed, internal helpers
    //   - String-typed per-core fields not yet in X-macro framework
    //     (core_model_path[], core_model_dir[], core_horizon_list[],
    //      core_ensemble_blend_mode[], core_disabled_horizons[]) — migrate
    //     to FOREACH_PER_CORE_STRING_CFG_FIELD at .F.4e
};
```

Deletions from current `ControllerConfig<F>`:
- All scalar trading fields move to `PerCoreCfg<F>`
- `PerCoreOverrides<F>` struct DELETED (the override mechanism is no longer needed; per-core IS authoritative)
- `core_overrides[16]` field DELETED (replaced by `cores[16]`)
- `ControllerConfig_ResolveForCore` becomes trivial direct-read (or DELETED entirely if no callers remain that need a "resolved view")
- `PER_CORE_OVERRIDE_BITMAP_DOMAINS` macro DELETED (override-bitmap mechanism eliminated; bitmap-resident bools in `ml_cfg_flags` migrate to per-core registry directly as KIND_BOOL rows OR stay in ml_cfg_flags as per-core-instance bitmap field; decide at audit)

### C. Parser updates — `[core N]` section syntax + hard-break legacy

```
# engine.cfg new format
# Global section (no header — defaults at top of file)
num_execution_cores=4
engine_mode=sharded
require_mlockall=1
record_ticks=0
held_out_stamp_secret=path/to/secret
trading_mode=paper
kill_switch_daily_loss_pct=3.0

# Per-core sections
[core 0]
strategy=ml
model_dir=models/classification/multi_2year_01
risk_pct=15.0
take_profit_pct=3.0
stop_loss_pct=1.5
ridge_lambda=0.15
bandit_algorithm=1

[core 1]
strategy=ml
model_dir=models/classification/short_horizon
risk_pct=10.0
take_profit_pct=2.5
stop_loss_pct=1.0
ridge_lambda=0.20
bandit_algorithm=2

# ... [core 2], [core 3] sections similarly
```

Parser logic:
1. Lines before the first `[...]` header → parsed against `FOREACH_GLOBAL_CFG_FIELD` registry (writes to `ControllerConfig<F>` flat fields)
2. After `[core N]` header → parsed against `FOREACH_PER_CORE_CFG_FIELD` registry (writes to `cfg.cores[N].<field>`)
3. Unknown global key → ERROR with migration hint: `"key '<name>' moved to per-core scope at v5.15.5.F.4c.3. Place under a [core N] section. See migration guide."`
4. Unknown per-core key → ERROR with migration hint
5. `[core N]` where N >= num_execution_cores → WARN + ignore (operator might be staging future-core cfg)

**Hard-break per Caramel's directive 2026-05-15:** legacy `take_profit_pct=3.0` at global scope = ERROR. No backward-compat shim. Operator runs migration tool once.

### E. Per-core stamp body emit + drift check

Each core's HMAC stamp covers ITS per-core cfg fields (filtered by STAMP_BOUND metadata):

```cpp
// At stamp emit time (per-core boot or model load):
void EmitCoreStamp(const PerCoreCfg<F>& core_cfg, int core_id, ...) {
    char body[4096];
    int n = build_canonical_body(body, sizeof(body), &core_cfg, core_id);  // walks STAMP_BOUND per-core rows
    // HMAC-SHA256 over body + secret
}

// At boot drift check:
for (int c = 0; c < num_execution_cores; ++c) {
    auto& core_cfg = cfg.cores[c];
    // Compare core_cfg fields against core's stamp; fire drift bits per Class 23/24 discipline
}
```

The wire format CHANGES at this ship: per-core stamps are emitted per core (4 stamps for 4 cores vs 1 unified stamp). Layer 5b hash recomputation required. Per-core stamp fixtures replace the v5.14 unified fixture.

**Open question for audit gate:** what's the byte layout of per-core stamps? Options:
- (a) Each core gets its own stamp file: `models/core_0.stamp` + `models/core_1.stamp` + ... — distinct files
- (b) One unified stamp file with per-core sections inside: `models/cores.stamp` containing 4 inline bodies
- (c) Hybrid — stamps in per-core model directories: `models/<core_N_model_dir>/cfg.stamp`

Likely (c) — fits the existing per-core model_dir convention; each core's stamp lives with its model.

## If something goes wrong

- **Layer 5b per-core hash mismatch:** synthetic populate missed a field OR per-core row order changed accidentally. Investigate before re-locking the constants. Don't blindly update.
- **Cfg parser state machine error:** `[core N]` header parsed mid-line OR multiple sections detected. Add unit test for the failing input + fix state machine.
- **Test fixture compile error:** likely a `cfg.<name>` access that should now be `cfg.cores[0].<name>`. Mechanical grep+fix.
- **Migration tool emits malformed output:** round-trip test failure. Diff legacy parse against migrated parse; fix the tool.
- **Hot path regression:** calls_graph_diff catches it. Investigate which slow→hot call boundary changed; usually a missed seqlock read.
- **Backtest non-determinism:** backtest path reads from `cores[backtest_core_idx]`; verify the resolved field matches what backtest_core_idx core would see in production.
