## Phase A — TUI strat_stats array sizing fix (`v5.10.3.A`)

**Audit:** Finding #8 (HIGH per Section K rule — UB in build warning + display↔execution invariant breach).

**Bug recap:** `EngineTUI.hpp:906` has `StrategyStatsSnap strat_stats[5]` (size 5). `TUIAnsi.hpp:824, 828` iterates with `NUM_STRATEGIES=6` (`NUM_STRATEGIES_REAL + 1`; +1 for AUTO sentinel). Index 5 reads past array bounds → garbage in TUI display.

**Step 0 (Option 1 — single source of truth):** Resize the array to use `NUM_STRATEGIES` directly. This satisfies CLAUDE.md Decision 13 (X-macro registry pattern for multi-site additions) — `NUM_STRATEGIES` already drives the strategy count everywhere; the snapshot array deviating from it is the bug.

**File:line targets:**

### A.1 — Resize array
`DataStream/EngineTUI.hpp:906`:
```cpp
// before:
StrategyStatsSnap strat_stats[5];
// after:
StrategyStatsSnap strat_stats[NUM_STRATEGIES];
```

(Verify `NUM_STRATEGIES` is in scope at EngineTUI.hpp:906 before write — `Strategies/StrategyInterface.hpp:131` defines it; check the include chain.)

### A.2 — Population loop fix
`DataStream/EngineTUI.hpp:1405` — population loop:
```cpp
// before:
for (int i = 0; i < 5; i++) { /* populate strat_stats[i] */ }
// after:
for (int i = 0; i < NUM_STRATEGIES; i++) { /* populate strat_stats[i] */ }
```

**Decision:** the AUTO sentinel slot (i=5 = NUM_STRATEGIES_REAL) needs population semantics. Options:
- Zero-init it (no per-strategy stats, just a slot for "unspecified"): simplest.
- Aggregate stats across all real strategies: more useful, slightly more code.

**Recommend zero-init for v5.10.3.A** (smallest fix). Aggregate logic could be a v5.11.X polish item.

### A.3 — TUIAnsi.hpp loops verified safe
`DataStream/TUIAnsi.hpp:824, 828` loops with `< NUM_STRATEGIES` are now correct (no longer reading past array bounds). No code change here, but the warning should disappear.

### A.4 — Build clean
After A.1+A.2, rebuild and confirm `-Waggressive-loop-optimizations` warning at TUIAnsi.hpp:824, 828 is gone:
```bash
./build.sh test 2>&1 | grep -E "warning:|aggressive-loop"
```

**Verification:**
- New test: `test_strat_stats_array_sizing` — assert `sizeof(strat_stats) / sizeof(strat_stats[0]) == NUM_STRATEGIES` via `static_assert` in EngineTUI.hpp.
- Manual: build with `-O3` and `-Og`, screenshot TUI, compare AUTO bin display values. Pre-fix: garbage differs across builds. Post-fix: zero-init AUTO bin shows consistent zero counts.

**Risk:** Low. Array-size change is additive (+1 slot of `StrategyStatsSnap` = ~32 bytes per snapshot). No callers should break since they all already use `NUM_STRATEGIES` as the iteration bound.

**Sub-ship gate:** `./build.sh test gui suite` 2>&1 grep "aggressive-loop" returns empty. Tag `v5.10.3.A`.

## Phase C — is_buyer_maker comment + KNOWN_ISSUES entry (`v5.10.3.C`)

**Audit:** Findings #5 (HIGH compound bug, predates v5.10) + #15 (LOW comment-only).

**Decision:** Ship comment + doc only for v5.10.3. Full plumb-through (`SharedBacktest_FromHistorical` patch + slow-path scalar bus extension + RollingStats_Push call updates) is ~4h architectural surgery — too big for the close-out window AND risks introducing a new bug class the audit hasn't seen. Document the gap; close in v5.10.X or v5.11+ when there's dedicated budget.

**Reasoning:** Train-serve parity is *preserved* (both paths broken with `is_buyer_maker=0`); the audit explicitly says "FEAT_VOLUME_DELTA is locked at +1.0 in both paths" — so models trained on this data don't learn anything from the feature, but they also don't see the train-side data differently from the serve-side data. The bug degrades feature richness, not parity. Acceptable to defer per the audit's "Severity rationale" (closes Finding #5).
