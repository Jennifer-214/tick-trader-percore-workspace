### [HIGH] `dsgui-1` — GUI chart trade markers + equity curve silently broken in sharded mode: TradeReader parses legacy CSV schema while engine writes format-v3 to the same file
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `datastream-gui` · fix: standalone (GUI fix; also folds into .E.2 headless/GUI-removal — if the in-process chart is retained post-.E.2 it must parse v3; if removed, finding is mooted)
- **Where:** GUI/TradeReader.hpp TradeData_Refresh (~lines 76-170) consuming logging/SYMBOL_order_history.csv; writer is CoreFrameworks/ShardedTradeLog.hpp ShardedTradeLog_Init (~line 158-162, filename comment 'matches the path the GUI's TradeReader expects') + TradeLogColRegistry.hpp FOREACH_TRADE_LOG_COL (v3 13-col schema). Consumed by GUI/ChartPanel.hpp GUI_PriceChart markers + GUI_EquityChart (~line 1344-1400). Sibling consumer GUI/TradeHistoryPanel.hpp (~lines 51-135) parses the SAME file CORRECTLY in v3.
- **What:** The sharded engine (production default) writes the aggregate trade log in format v3: a leading '# v3 sharded engine...' comment line, then column header 'timestamp_us,core_id,strategy_id,event_type,price,entry_price,exit_price,pnl,fees,balance_after,trade_size,regime,regime_name', then data rows where event_type is 'E'/'X'. - **Why:** Canonical Class 2 (display<->execution divergence): two GUI consumers of the same execution output, one updated to the new format and one left reading the dead legacy schema. The operator looking at the live chart sees no trade markers / flat equity and cannot distinguish 'engine took no trades' from 'display parser is broken' — exactly the misleading-state failure Class 2 documents. Production-default path is sharded, so this is the default GUI experience, not an edge case.
- **⚠ Don't carry forward (.E.1 rewrite):** Do NOT carry the legacy BUY/SELL/field-14 column offsets into any post-.E.1 viewer. ### [HIGH] `dsgui-1` — CandleAccumulator takes a pthread_mutex on the producer per-tick fan_out path (H3 violation + producer p99 budget breach, GUI build)
*verified* · section `datastream-gui` · fix: .E.2 (headless/GUI-removal) eliminates the GUI build path entirely; standalone fix before paper-test = replace CandleAccumulator's pthread_mutex with the seqlock + double-buffer pattern already used by TUISnapshot (TUISnapshot_Publish_Begin/End + ReadInto), or have the producer push into an SPSC ring the GUI drains.
- **Where:** GUI/CandleAccumulator.hpp — CandleAccumulator_Push (lines 41-82, pthread_mutex_lock at 46) + CandleAccumulator_Snapshot (lines 132-154, holds lock while copying up to CANDLE_MAX+1 = 4097 Candle structs). Producer call site: CoreFrameworks/EngineSharded/Async.hpp:287 (CandleAccumulator_Push inside EngineSharded_Async_FanOut, per tick, under #ifdef USE_IMGUI_GUI). Legacy producer call site: main.cpp:645. GUI reader: GUI/GuiThread.hpp:410 (CandleAccumulator_Snapshot at 60Hz). CANDLE_HISTORY_MAX=4096 (Limits.hpp:6).
- **What:** On every tick the producer/fan_out thread calls CandleAccumulator_Push, which does pthread_mutex_lock/unlock. The 60Hz GUI render thread calls CandleAccumulator_Snapshot which holds the SAME mutex while it memcpys the entire candle ring (up to 4097 * 64B ~= 256KB) plus the in-progress candle into a CandleSnapshot. When a GUI snapshot overlaps a tick, the producer thread blocks on the lock until the ~256KB copy completes — directly stalling tick fan-out into the SPSC rings.
- **Why:** H3 forbids std::mutex/condition_variable/sleep_for/pthread_rwlock 'anywhere'; CLAUDE.md concurrency model states 'No mutex per H3' and prescribes lock-free/seqlock cross-thread handoff (the TUISnapshot publish path already does exactly this). The producer fan_out budget is <100ns p50 / <=200ns p99 (CLAUDE.md latency table); a contended pthread_mutex_lock that waits on a 256KB copy is orders of magnitude over budget and adds unbounded p99 variance on the production GUI binary — the worst outcome for a determinism-prioritizing system. Unlike Notify (intentional off-trading-path async primitive, documented exempt), this mutex sits squarely on the latency-budgeted producer path.
- **⚠ Don't carry forward (.E.1 rewrite):** Do NOT reintroduce CandleAccumulator (or any GUI-fed accumulator) with a pthread_mutex on the producer path when the headless/viewer-decoupled architecture lands; the candle feed should be a file-mediated or SPSC-ring publish, never a lock shared with the hot producer.
- **CI check:** grep CI check: pthread_mutex_lock / std::mutex reachable from any fan_out / producer / hot-path / drainer translation unit (extend the H3 banned-token scan to flag mutex use in EngineSharded/Async.hpp + CandleAccumulator.hpp, not just the literal std::mutex token).
- **Test to add:** No test asserts the producer path is lock-free under the GUI build; add a TSAN/contention test that runs CandleAccumulator_Push in a tight loop on one thread while CandleAccumulator_Snapshot runs on another and measures producer-side block time (or, post-fix, asserts the publish path is wait-free for the writer).
- **Anti-pattern:** A cross-thread buffer fed from a latency-budgeted producer path guarded by a mutex whose critical section on the reader side is a large bulk copy — couples render-thread copy duration into producer-path latency.

### [HIGH] `persist-dod-1` — Periodic snapshot save reads full live OMS+per-core state un-synchronized on the producer thread; torn state persisted as the warm-restart seed
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `persistence` · fix: .E.2 (mmap publish + crash-recovery) — couple the periodic save to a quiescent/seqlock-published snapshot of OMS+per-core state, OR move the save to the drainer thread and publish per-core state via the existing seqlock/double-buffer mechanism so the writer is the reader
- **Where:** CoreFrameworks/EngineSharded/Async.hpp — EngineSharded_Async_FanOut, periodic-save block ~lines 419-431 (static save_counter; every 1024 slow-path cadence calls ShardedSnapshot_Save<F>(&state, "data/sharded_snapshot.dat", ...)). Save body: CoreFrameworks/ShardedSnapshotPersist.hpp ShardedSnapshot_Save — bulk `fwrite(state->oms->portfolio.positions, sizeof(Position<F>), 16)` (~line 162) + field-by-field multi-word FPN per-core counters (core_realized/core_peak_balance/pnl_feeder/balance ~lines 154,180-253). Thread topology: producer runs FanOut; drainer writes portfolio.positions + balance (OrderManager HandleFill via OMS_Tick); per-core slow threads write CoreContext P&L/regime/confidence.
- **What:** The periodic snapshot save fires on the PRODUCER thread at slow-path cadence (~every 1024 cycles ≈ 13 min at typical paper rates). It serializes the entire live engine state — portfolio.positions[16] as one bulk fwrite plus per-core 24-byte FPN counters and the OMS balance/realized_pnl block — with no seqlock, no atomic snapshot, and no quiescence. Concurrently the drainer thread writes Position fields (entry_price/quantity, each a 24-byte multi-word FPN) and oms->balance on every fill, and per-core slow threads write core_realized / core_peak_balance / pnl_feeder / ConfidenceScorer. A multi-word FPN or a Position can be read half-old/half-new, and cross-field invariants (balance vs realized_pnl, position bitmap vs position contents) can be captured inconsistently. The atomic-rename makes the FILE write atomic, but the in-memory READ that produced the bytes is not — so a logically-corrupt-but-complete snapshot is durably written and becomes the seed for the next warm-restart (paper mode loads this file at boot).
- **Why:** Determinism/recovery hazard ranked just below wire-byte. The tracked races are narrower: persist-3 is the SHUTDOWN save only (Run.hpp:2198, fires once, just before joins), and conc-1/oms-5 cover only the kill-switch read of oms->balance. This is the FULL-STATE periodic persist path and runs continuously during normal paper operation, so a torn save silently poisons warm-restart: restored positions could have inconsistent entry_price (mis-priced TP/SL re-derivation), balance could not reconcile with realized_pnl, or pnl_feeder/regime hysteresis could be self-inconsistent — all presented as a clean resume. Low per-event probability (~1 fill/sec vs the rare save) but high consequence and it accumulates across many sessions.
- **⚠ Don't carry forward (.E.1 rewrite):** In the .E.1 core->node state-layout rewrite, do NOT keep a producer-thread save that bulk-reads drainer/slow-owned mutable state directly. The new per-node layout should expose a publish-on-write snapshot (double-buffer / seqlock) that the persister reads, so save and the owning writer never alias live multi-word fields.
- **CI check:** TSan run with the periodic-save cadence forced low (save_counter threshold=1) under a multi-threaded paper soak — flags the data race between ShardedSnapshot_Save reads and drainer/slow-path writes
- **Test to add:** Add a multi-threaded test (or TSan harness) that runs producer+drainer+slow threads with active fills while ShardedSnapshot_Save fires repeatedly, asserting (a) no TSan race and (b) every persisted snapshot satisfies balance/realized_pnl + bitmap/position cross-invariants on reload
- **Anti-pattern:** A background/periodic serializer reading live cross-thread mutable multi-word state directly (no seqlock / no quiescence) and durably persisting it as a recovery seed

### [HIGH] `wfa-1` — Warm-restart restores positions EXIT-DISARMED: cached_params.flags=0 (TP/SL_ENABLED unset) until first slow-path rebuild → restored position cannot honor its own stop-loss during the boot window
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `persistence` · fix: .E.2 (mmap publish + crash-recovery — the warm-restart state-restore surface). Standalone-fixable sooner: in ShardedSnapshot_Load re-activation loop, publish a param_slot with GATE_FLAG_TP_ENABLED|GATE_FLAG_SL_ENABLED and the restored live_tp/live_sl (or call a boot-time RebuildOneCore for cores with restored positions) so exits are armed before the hot thread starts.
- **Where:** CoreFrameworks/ShardedSnapshotPersist.hpp ShardedSnapshot_Load re-activation loop (~lines 611-676: sets core_ptr->active=1, live_tp, live_sl, but NOT param_slot flags); comment ~lines 584-600 falsely claims '...hot-path SG/TP/SL gates armed'. Gate dependency: CoreFrameworks/ExecutionCore.hpp ExecutionCore_Tick_Impl — tp_enabled/sl_enabled read from flags=core->cached_params.flags (~line 348, 413-414); sg_fires_a = (tp_enabled & tp_hit_a)|(sl_enabled & sl_hit_a) (~line 431). Default: ExecutionCore_Init (~line 214-220) seeds param_slot+cached_params from GateParameters_Init → flags=0 (GateParameters.hpp:218). TP/SL_ENABLED set only inside strategy _BuildParameters (StrategyParameters.hpp:360/436/550/642/1562), published via ExecutionCore_SetParameters from the slow-path rebuild (ControllerEventLoop.hpp:3161).
- **What:** ShardedSnapshot_Load walks the restored active_bitmap and re-activates each ExecutionCore: it sets active=1 and recomputes live_tp/live_sl from entry × (1±pct). But the hot-path exit gate gates TP/SL firing on GATE_FLAG_TP_ENABLED / GATE_FLAG_SL_ENABLED, which live in cached_params.flags — published ONLY by the slow-path rebuild (ExecutionCore_SetParameters), never by the load path. At boot, cached_params.flags=0 (GateParameters_Init default). There is no boot-time pre-thread-start param publish. So from snapshot load until the FIRST slow-path rebuild publishes params for that core, sg_fires_a = (0 & tp_hit)|(0 & sl_hit) = 0: a restored open position cannot exit on TP or SL even if price blows straight through stop_loss_price. The window closes at the first rebuild (needs ticks to flow + slow_path_interval cadence), and on restart rolling stats reset to 0 so the rebuild also has to re-warm before producing meaningful params, widening the window. The load comment explicitly (and incorrectly) advertises the gates as armed.
- **Why:** A warm-restart that resumes an open paper position leaves that position unprotected against its own stop-loss for the boot→first-rebuild window. Determinism/safety: the persisted exit intent (stop_loss_price) is silently inert until the slow path catches up. This is the same zombie-position failure mode the 2026-04-27 re-activation fix was written to prevent, reintroduced one level down (prices restored, enable-flags not). Distinct from seam-2 (kill-switch re-block on restart) and from persist-4/5 (test gaps) — those are about entry permission / coverage; this is about EXIT capability of an already-open restored position. Severity HIGH because a stop-loss is the operator's primary risk control and it is defeated precisely in the recovery scenario warm-restart exists to serve.
- **⚠ Don't carry forward (.E.1 rewrite):** When .E.1 rewrites core->node and re-homes the restore path: do NOT carry forward the assumption that setting active+live_tp/live_sl is sufficient to arm exits. The exit gate's enable flags live in the published param slot, not on the node's hot mirrors — any restore must publish flags (or trigger a rebuild) before the hot loop can fire. Treat 'restore = active + prices + ENABLE flags + permission policy' as the atomic unit.
- **CI check:** Grep/AST check: any function that sets core->active=1 (or node active) outside the normal entry path must, in the same scope, also publish a GateParameters with GATE_FLAG_TP_ENABLED|GATE_FLAG_SL_ENABLED (or invoke a rebuild) — flag re-activation sites that set active without an adjacent param publish.
- **Test to add:** Extend the re-activation test (tests/controller_test.cpp ~5954-5997, which only asserts active==1 + live_tp/live_sl values): after ShardedSnapshot_Load, drive a tick through ExecutionCore_Tick with price <= restored stop_loss_price (no intervening RebuildOneCore) and assert the exit event fires / position closes. Today that tick would NOT fire the exit, exposing the disarmed-flags window.
- **Anti-pattern:** Restore/re-activation path sets the value mirrors of a feature but not the enable bit that gates the consumer, so the restored state is silently inert until an unrelated periodic recompute publishes the missing bit.
