## Item 1 — Engine Topology advanced features (~1-2h)

The v5.0.2 panel shows pin info + cadence. Plan called for more.

**Add to TUISnapshot::PerCoreSnap**:
- `uint64_t sp_last_tick_us` — wall-clock timestamp (us) of last slow-path
  cycle. Producer reads via `__atomic_store` from the slow-path thread.
- `uint64_t sp_cycles_total` — monotonic count of slow-path cycles.
- `uint64_t sp_yield_count` — how often the slow-path yielded due to
  reset-in-progress or cadence-not-elapsed (cheap counter).
- `uint16_t sp_submit_queue_depth` — live depth of OMS submit queue
  (computed as `head - tail` from atomic loads).
- `uint8_t sp_state` — coarse thread state: 0=running, 1=parked (reset
  in progress), 2=cadence-yield. Updated atomically by the slow-path
  itself before yielding.

**Add to TUISnapshot top-level**:
- `int paused_engines_mask` — uint16 bitmap. UI Pause/Resume toggle sets
  bit `c`; slow-path checks bit `c` and yields if set.

**Slow-path thread changes**:
- After each cycle: store current wall-us into `state.cores[c].sp_last_tick_us`,
  increment `sp_cycles_total`.
- Before yielding: set `sp_state` and increment `sp_yield_count`.
- At top of loop: check `paused_engines_mask & (1 << c)` and yield if set.

**Topology panel UI additions** (under existing per-engine table):
- New columns: **State**, **Last cycle**, **Cycles**, **Q depth**.
  - State: text + color (running=green, parked=yellow, paused=red).
  - Last cycle: `Δus` since last sp_last_tick_us — drift indicator.
  - Cycles: total count.
  - Q depth: current submit queue depth (warns if > 16, queue cap = 32).
- Per-engine action column: **Pause** / **Resume** button per row.
  - PushID(c), label changes based on bit state.
  - Click toggles bit in shared `paused_engines_mask`.

**Skip** (per plan, defer):
- Restart per-engine — would need thread teardown/respawn. Not worth
  the complexity; full engine restart covers it.

**Exit criteria**:
- New columns render; values change in real time.
- Pause button parks the slow-path thread; Resume unparks; logs to stderr.
- Hot-path remains unaffected (no new branches added there).

## Item 2 — Parity regression tests (~1-2h)

Adds to `tests/controller_test.cpp`. No threading in tests (those are
covered by sanitizer runs in item 3). Focus on **state mutation
identity**: OneCore helpers produce identical state to wrapper loops
that call them N times.

**Test 1 — OneCore identity (~40 assertions)**:
- For each helper (Rebuild, TimeExit, TrailingSLRatchet, DrainPostFill):
  - Set up 4 cores in known state
  - Call wrapper, snapshot state
  - Reset, call OneCore for c=0..3 manually, snapshot state
  - Assert byte-identical (memcmp on `state->cores`)
- Edge: empty state (no positions) — both paths must agree.
- Edge: STRATEGY_NONE skip — wrapper skips, OneCore caller skips.

**Test 2 — Single-core update isolation (~16 assertions)**:
- For each OneCore helper:
  - Set up 4 cores, identical state
  - Call OneCore for c=0 only
  - Assert state.cores[0] mutated as expected
  - Assert state.cores[1..3] BYTE-IDENTICAL to pre-call snapshot
- Catches accidental cross-core writes (the latent partials bugs we
  fixed in v4.7.38 were exactly this class).

**Test 3 — Reset Paper invariant (~10 assertions)**:
- Set up 4 cores with open positions, P&L history, etc.
- Run reset (synchronous, no threads)
- Verify all per-core counters cleared, balance restored to start,
  positions emptied
- Verify partner_pending_pnl, core_gross_wins/losses cleared
  (the v4.7.26 fix territory)

**Test 4 — Submit queue full handling (~6 assertions)**:
- Push commands until queue full (32 cap)
- Assert further pushes rejected (returns 0)
- Drain — assert order_bitmap reflects 32 reservations
- Push again — assert succeeds after drain

**Test 5 — Topology field stability (~4 assertions)**:
- Populate TUISnapshot via TUI_PopulateTopology
- Assert engine_arch / nproc / pin_offset round-trip correctly
- Re-populate with different values, assert update visible

**Total: ~76 new assertions, target 780 pass**

**Exit criteria**:
- All new tests pass
- Total test count ≥ 780
- No existing tests regressed

- `./build.sh asan` — `-fsanitize=address -O1 -g`

  Look for data race warnings.

with synthetic ticks for ~30 seconds, ctrl-c, verify clean.

- TSan: 0 race warnings on `engine` synthetic-tick run.

## Item 5 — Slow-path work breakdown profiling (~1-2h)

The current `slow_path_latency` measures the entire per-cycle work
(Rebuild + TimeExit + TrailingSL + permission grant + ExecutionCore
push). To debug slow strategies, break it down by section.

**New struct on CoreContext**:
```cpp
struct SlowPathBreakdown {
    CoreLatencyStats rebuild;    // RebuildOneCore call
    CoreLatencyStats time_exit;  // TimeExitOneCore call
    CoreLatencyStats trail_sl;   // TrailingSLRatchetOneCore call
    CoreLatencyStats push_params;// ExecutionCore_SetParameters
    CoreLatencyStats other;      // permission, swap pickup, etc.
};
```

**Bracket sites in per_core_slow loop body**:
- Wrap each section with `__rdtsc()` deltas, `CoreLatencyStats_Sample`.
- ~10 ns of overhead per section × 5 sections = ~50ns per cycle. Slow-path
  is microsecond-scale, so the overhead is < 1%.

**Centralized path**: same brackets in producer's slow-path body's
per-core sections, sampling into `state.cores[c].slow_path_breakdown`.

**Backtest path**: same brackets in `ShardedBacktestDriver`.

**TUISnapshot extensions**:
- Per-core: 5 × (samples, p50, p99) for each section. Keep light —
  the existing single sp_* fields stay (rolling 256 + lifetime).

**Topology panel addition** (or new dedicated panel):
- Per-engine row: hover/expand reveals section breakdown table.
- Or: third sub-table in Per-Core Latency panel with per-section p50/p99.

**Exit criteria**:
- Backend captures all 5 sections per arch.
- UI displays section breakdown.
- Existing slow-path latency stat still populated (sum of sections ≈ total).

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Item 4 introduces races | Sub-plan specifies single-writer rules; item 3 sanitizer runs catch leaks/races |
| Item 5 perf overhead | Bracket sites are slow-path only; ~50ns/cycle is < 1% |
| Item 1 lifecycle button state diverges from thread reality | Atomic updates from slow-path itself (single writer) |
| Test additions slow CI | Tests are deterministic, ~few ms each; total runtime stays under 2s |

## Order of attack

Sequential: items 1 → 2 → 3 → 4 → 5. Each independently shippable.

**Why this order**:
- Items 1+2 finalize observability + tests for the v5.0 architecture.
  Item 2's "topology field stability" tests need item 1's fields, so
  1 → 2 strict.
- Item 3 (TSan/ASan) is **strictly before item 4**: if TSan flags
  pre-existing producer→shared-RollingStats reads as races, we
  document them as known + fixed in item 4 (clean attribution).
- Item 4 is the biggest refactor; rollback story is cleaner with
  1+2+3 already green.
- Item 5 brackets are technically independent of item 4 (could swap),
  but landing 4 first means the breakdown stats live on a per-core
  CoreContext that's already restructured.

Final tag: `v5.1.1` after item 5 lands clean.
