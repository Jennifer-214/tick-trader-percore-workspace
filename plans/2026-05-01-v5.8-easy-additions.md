# v5.8 — Easy Additions sweep

**Date:** 2026-05-01
**Theme:** every category in the codebase where "add one thing"
requires touching N sites becomes a one-line X-macro append.
**Pre-req:** v5.6/v5.7 paper-validated + merged.
**Branch:** `feat/v5.8-easy-additions` from main.

This is a refactor sprint, not a feature sprint. No new operator-
visible behavior. Every change is "the same thing, with fewer
places to forget to update."

The ML hardening work (feature standardization, leakage sentinels,
WF stability) becomes v5.9, built on top of v5.8's feature registry
indexed by stable FeatureId.

---

## Why now

Two forcing functions converged:
1. **Strategy plug-and-play idea was parked** in
   `DOCS/STRATEGY_REFACTOR_IDEAS.md` waiting for the "next strategy
   add" trigger.
2. **Feature registry needed** for v5.9 ML hardening (standardization
   + leakage + stability all index by FeatureId).

Both want the same X-macro idiom. Doing them together = one refactor
sprint, two registries with the same shape, and the codebase gets a
consistent extensibility pattern.

`STRATEGY_REFACTOR_IDEAS.md` trigger conditions are met: rather than
wait for a 6th strategy, we batch-fix multiple categories at once.
Better leverage.

---

### Output B — canonical signature specs + plug-and-play recipes

These docs go in `DOCS/` and are the ENFORCEMENT mechanism for the
"adding one thing = drop a header + 1 X-macro line + recompile"
contract. Without them, the X-macros work but adding new things
still requires reading existing strategies/features to figure out
the right shape.

**`DOCS/STRATEGY_INTERFACE.md` (update existing):**

Section 1 — canonical signatures:

```cpp
// Per-core state. Fields strategy-specific; struct itself is
// owner-managed by Strategy_InitPerCore / Strategy_FreePerCore.
template <unsigned F>
struct <Name>State {
    // ... strategy-specific fields ...
};

// Init: called once per core at registration. Allocates state,
// sets up rolling-stat seeding, etc. Caller-allocated state ptr.
template <unsigned F>
inline void <Name>_Init(
    <Name>State<F>* state,
    const RollingStats<F>* rolling,
    BuySideGateConditions<F>* buy_conds);

// Adapt: called per slow-path cycle. Updates state from rolling
// stats + portfolio feedback. Drives any adaptive behavior
// (regression-driven offset shift, idle squeeze, etc).
template <unsigned F>
inline void <Name>_Adapt(
    <Name>State<F>* state,
    FPN<F> current_price,
    FPN<F> portfolio_delta,
    uint16_t active_bitmap,
    const BuySideGateConditions<F>* buy_conds,
    const ControllerConfig<F>* cfg);

// BuildParameters: called per slow-path cycle. Emits gate parameter
// pack consumed by the hot path via seqlock. THIS IS THE CONTRACT
// WITH THE HOT PATH.
template <unsigned F, unsigned W = 128>
inline void <Name>_BuildParameters(
    const RollingStats<F, W>* rolling,
    const ControllerConfig<F>* config,
    FPN<F> allocated_balance,
    GateParameters<F>* out,
    <Name>State<F>* state = nullptr);

// ExitAdjustSharded: called per slow-path cycle for active positions
// owned by this core. Writes ratchet_sl / ratchet_tp via the
// Strategy_WriteRatchetSL / Strategy_WriteRatchetTP helpers (which
// apply the v5.1.7 fee-floor cap automatically).
template <unsigned F, unsigned W>
inline void <Name>_ExitAdjustSharded(
    EventLoopState<F>* state,
    int slot,
    <Name>State<F>* strat_state,
    FPN<F> current_price,
    const RollingStats<F, W>* rolling,
    const ControllerConfig<F>* cfg);
```

Section 2 — recipe (the plug-n-play part):

```
TO ADD A NEW PUBLIC STRATEGY "Foo":

1. Create file: Strategies/Foo.hpp
   Copy template from DOCS/STRATEGY_TEMPLATE.hpp
   Replace <Name> with Foo, fill in strategy-specific logic.

2. Add one line to FOREACH_STRATEGY(X) in StrategyInterface.hpp:
   X(FOO, "FOO", "Foo", FooState, \
      Foo_Init, Foo_BuildParameters, Foo_Adapt, Foo_ExitAdjustSharded)

3. Add color: append one ImVec4 to strat_colors[NUM_STRATEGIES] in
   GUI/DashboardPanels.hpp (only manual touch site remaining)

4. Run: ./build.sh test
   Pass = compiled + dispatched correctly.

5. Optional: add cfg.example entry: # core_0_strategy=foo

DONE. ~3 sites total (was 8+).

TO ADD A PRIVATE STRATEGY:
Same recipe but file goes in Strategies/private/Foo.hpp and the
X-macro line wraps in #if __has_include("private/Foo.hpp").
```

spread, large trade). Each compute fn takes ctx, reads what it needs,
returns FPN<F>.

**Migration scope clarification (2026-05-01 readiness audit):** the
X-macro shape above shows 7 features as illustration. **The actual
codebase has 34 features defined as `FEAT_*` constants** at
`ML_Headers/ModelInference.hpp:37-78`. Phase 2 must migrate ALL 34,
not just the 7 shown. ID order must be preserved exactly (FEAT_*
indices 0-33) so existing trained models can still find their
features at the same positions during the transition cycle.

**ModelFeatures_Pack callers (2026-05-01 audit) — all need updating
to `Features_PackAll(ctx, out)`:**
- `Strategies/MLStrategy.hpp:115`
- `Strategies/StrategyParameters.hpp:658` (ML dispatch path)
- `Backtest/BacktestSharded.hpp:438`
- `CoreFrameworks/PortfolioController.hpp:1622, 1775` (legacy single-
  core; gate behind `__has_include` or accept that legacy path drops
  in this phase)
The legacy callers are the most surgical — confirm before-the-edit
whether legacy controller still needs ML at all, or whether dropping
legacy ML support in v5.8.1 is acceptable.

**MLBuildContext field mapping:** the existing `MLBuildContext` in
`StrategyParameters.hpp` already bundles the same inputs we need
(rolling_medium, rolling_baseline, cumdelta_state, tick_rate_state,
book_imb_history, flow_state, large_trade_state, spread_state, ...).
`FeatureComputeCtx<F>` should mirror these field-by-field. The
migration is essentially renaming + relocating MLBuildContext fields
into FeatureComputeCtx, then having ML_BuildParameters construct a
FeatureComputeCtx from its existing inputs.

**Auto-generated:**
- `enum FeatureId` with stable IDs
- `FEATURE_NAMES[]` for stamps + GUI
- `FEATURE_REGISTRY[NUM_FEATURES]` with metadata
- `FEATURE_REGISTRY_HASH` (fnv-1a over name+version, contributes to
  fingerprint)
- `Features_PackAll(ctx, out_array)` — replaces `ModelFeatures_Pack`

**Adding a feature:**
1. Implement `ML_Compute_FooFeature(ctx) -> FPN<F>`
2. Append one line to `FOREACH_FEATURE(X)`
3. Compile. Old models force-invalidate via fingerprint mismatch.

**Drift detection test (load-bearing):**

Four tests in `// === EXTENSIBILITY ===` section:

1. `FEATURE_REGISTRY_HASH != 0` — sanity
2. Stamp built from current registry → loads successfully — round-trip
3. Stamp with mutated hash → load rejected — drift detection
4. `FEATURE_REGISTRY_HASH == EXPECTED_SNAPSHOT_HASH` — pinned snapshot test
   - Any change to `FOREACH_FEATURE(X)` flips the hash and fails this test
   - Developer must update the snapshot value, acknowledging "yes I'm
     changing the model contract" — forces retrain decision
   - This is the test that *enforces* the train-serve contract

**Pre-requisites added to plan:**
- **Bump `MODEL_FORMAT_VERSION` 4 → 5** (otherwise load check at
  `ModelInference.hpp:277` won't fire on old models)
- **Add `feature_registry_hash` field to stamp body** alongside
  existing fields. Sign via HMAC like the rest of the body.
- **Persist a `EXPECTED_REGISTRY_HASH_SNAPSHOT` constant** in
  `tests/controller_test.cpp` for the drift snapshot test.

**Effort (revised 2026-05-01 post-audit):** 34 features × ~30min each
= ~17h migration + ~3h tests + ~1h stamp body extension + ~1h
MODEL_FORMAT_VERSION bump + ~1h FeatureComputeCtx skeleton + ~1h
ModelFeatures_Pack caller updates = **~24h** (was ~13h estimated
before counting features). The ~30min per feature includes:
read-the-current-pack-line + write `ML_Compute_<Name>(ctx)` +
add X-macro row + verify field availability in ctx.

If 34 features feels too large for a single ship, split into:
- v5.8.1a: FeatureComputeCtx + FOREACH_FEATURE skeleton + first
  ~10 features migrated (~10h)
- v5.8.1b: remaining ~24 features + drift hash + tests (~14h)

**Commit + tag:** `v5.8.1` (single ship) or `v5.8.1a`/`v5.8.1b` (split)

## Phase 5b — Stateful GUI panel registry (v5.8.4b)

**Scope clarification (2026-05-01 audit):** of the 14 currently
shipped GUI panels, **only 4 are stateful**: `TradeHistory`,
`LogViewer`, `Settings`, `StrategyQuality`. The other 10 are
stateless `GUI_Panel_X(snap)` 1-liner calls that don't benefit
from a registry.

This phase scopes ONLY to the stateful panels. Stateless panels
keep their direct render-loop calls (already minimal).

**Trigger to revisit (deferred work):** if a future ship adds 5+
stateless panels OR a stateless panel becomes stateful, revisit
this scope. Current cost-benefit favors leaving stateless alone.

**Pre-existing arch debt — DEFERRED out of v5.8 scope (2026-05-01
readiness audit):** `LogViewer_Refresh` (`LogViewerPanel.hpp:28-44`)
and `TradeHistory_Refresh` (`TradeHistoryPanel.hpp:40-48`) currently
perform synchronous `stat()` + `fopen()` + `fread()` on the GUI
render thread. Per readiness skill HARDENING checks, this is a
real blocking-I/O violation that can stall ImGui's ~60Hz render
cadence. The X-macro refactor in this phase **does not fix this**
— it merely registers the existing init/render functions in a
table. Migration to cache+refresh-button pattern is a separate
~2h ship; file as v5.8.x maintenance follow-up after v5.8 lands.

**Lifecycle asymmetry (deep readiness audit 2026-05-01):**
- `TradeHistory_Init(state, path)` — explicit init, takes path
- `LogViewer_Init(state, path)` — explicit init, takes path
- `Settings_Init` — exists but no path parameter
- `StrategyQualityState` — **NO explicit `_Init` function**; state
  is loaded on-demand at Refresh button (state struct is initialized
  via in-place struct{} = zero-init at first use)

The 4-panel registry must accommodate this asymmetry. Three options
(decide before coding):

- **Option A:** Add no-op `StrategyQuality_Init(state)` stub for
  signature uniformity. Cleanest registry, minimal cost.
- **Option B:** Registry entry has nullable `_Init` pointer; dispatcher
  skips if null. Marginally more code in dispatcher but no stub fns.
- **Option C:** Auto-zero state via memset/calloc in panel dispatcher
  before first render. Hides the lifecycle question entirely.

**Recommendation:** Option A — match the v5.8.0 strategy registry
shape where `SimpleDip_Adapt = NULL` is just a null function pointer
in the X-macro row. Same idiom: registry entries can have nullable
function pointers, dispatcher checks before call. (Option A and
Option B converge here; effectively pick the X-macro
"NULL-allowed-pointers" pattern.)

**X-macro shape:**

```cpp
// GUI/GuiThread.hpp
#define FOREACH_PANEL(X) \
    X(BUY_GATE,         /* state type — none */, GUI_Panel_BuyGate,         /* no init */) \
```

## Phase 5c — Backtest metric X-macro registry (v5.8.4c)

**Why included:** adding a metric (sharpe variant, sortino, etc.)
touches `BacktestStats` struct + `_Compute` formula + GUI render.
Frequency: moderate; likely to grow during v5.9 ML hardening as
new metrics surface.

**X-macro shape:**

```cpp
// Backtest/BacktestEngine.hpp
#define FOREACH_BACKTEST_METRIC(X) \
    X(SHARPE,        "sharpe",        Compute_Sharpe,        "%.3f") \
    X(SORTINO,       "sortino",       Compute_Sortino,       "%.3f") \
    X(MAX_DRAWDOWN,  "max_drawdown",  Compute_MaxDrawdown,   "%.2f%%") \
    X(PROFIT_FACTOR, "profit_factor", Compute_ProfitFactor,  "%.2f") \
    X(WIN_RATE,      "win_rate",      Compute_WinRate,       "%.1f%%") \
    X(EXPECTANCY,    "expectancy",    Compute_Expectancy,    "$%+.2f") \
    X(AVG_HOLD,      "avg_hold",      Compute_AvgHold,       "%.0fm")
```

Auto-generates the `BacktestStats` field array (or computes on
demand from a single stats source). Display via `FoxmlMetric` panel
loops the registry.

Adding a metric = 1 compute fn + 1 X-macro line. Down from 3 sites.

**Pre-step (Phase 5c.0 — first sub-step, 2026-05-01 readiness audit):**
the `Compute_Sharpe`, `Compute_Sortino`, etc. functions referenced
above **don't exist as separate functions today** — the metric math
is inline inside `BacktestStats_Compute` (`Backtest/BacktestEngine.hpp:354`)
and `BacktestStats_ComputeFromEquity` (`Backtest/BacktestEngine.hpp:402`).

Phase 5c must first extract per-metric compute helpers:
- `Compute_Sharpe(stats, equity_curve, n)` — pull the Sharpe formula
  out of `BacktestStats_ComputeFromEquity`
- `Compute_MaxDrawdown(stats, equity_curve, n)` — same
- `Compute_ProfitFactor(stats, trades, n)` / `_WinRate` /
  `_Expectancy` / `_AvgHold` — pull from `BacktestStats_Compute`

Once each is a standalone `static inline` function, the X-macro can
reference them via function pointer. The original `_Compute` /
`_ComputeFromEquity` callers become loops over the registry.

**Drift findings (deep readiness audit 2026-05-01) — extraction
must reconcile pre-existing inconsistencies, not paper over them:**

1. **profit_factor zero-guards diverge across 4 sites:**
   - `BacktestEngine.hpp:378` → `(gl > 0.0001) ? gw/gl : 0.0`
   - `BacktestSharded.hpp:703` → `cumulative_wins / cumulative_losses`
     (no guard — divides by zero if losses=0)
   - `EngineTUI.hpp:461` → `(g_losses > 0.001) ? g_wins/g_losses : 0.0`
     (different epsilon from BacktestEngine: 0.001 vs 0.0001)
   - `ShardedSnapshot.hpp:335` → `g_wins_d / g_losses_d` (unsafe)

2. **expectancy uses `fabs()` inconsistently:**
   - `BacktestEngine.hpp:383` → `(wr*avg_win) - (lr*fabs(avg_loss))`
   - `EngineTUI.hpp:1356` → `(wr*avg_win) - (lr*avg_loss)` (no fabs)
   - `ShardedSnapshot.hpp:345` → same as TUI (no fabs)
   - Likely harmless because `avg_loss` is signed-negative, so the
     fabs is redundant in correct invariants — but the discrepancy
     means a code reader can't tell which version is canonical.

3. **max_drawdown computed in two independent paths:**
   - `BacktestEngine.hpp:405-416` (BacktestStats_ComputeFromEquity)
   - `BacktestSharded.hpp:508-707` (incremental during run)
   - Verify formula equivalence on historical data before extraction.

**Reconciliation strategy:**
- Pick canonical formula (recommend BacktestEngine.hpp's safer-guard
  version with epsilon=0.0001 + fabs).
- Replace the 4 callsites with single `Compute_ProfitFactor(...)` /
  `Compute_Expectancy(...)` calls.
- Add bytewise regression test: run full backtest, capture pre-refactor
  stats, run again post-refactor, assert identical values for known
  data set. Catches transcription errors during extraction.

**Effort:** ~2h X-macro registry + ~1h metric extraction + ~1.5h
drift reconciliation + bytewise regression test
= **~5.5h** (was ~3h estimated before noting drift; +1.5h for
finding & fixing the 3 multi-site formula divergences).

**Commit + tag:** `v5.8.4c`

## Cross-cutting invariants

0. **No silent orphan regressions** (v5.4.0 lesson). Naming
   divergences between X-macro lines and actual function names
   compile-fail loudly (good). But function-pointer table can
   silently dispatch to the WRONG variant of a function if multiple
   variants exist (legacy stub vs state-aware sharded version).
   Prevention measures embedded in each phase below; cross-cutting
   discipline:

   - Each X-macro line's function references are **copied exactly
     from the existing dispatcher's switch statements**, not deduced
     from function naming patterns
   - `tools/calls_graph_diff.sh` runs BEFORE and AFTER each phase
     ships; any orphan flagged blocks the tag
   - Phase 0 audit produces a "canonical signatures" doc; any
     strategy whose lifecycle functions don't match canonical gets
     refactored in Phase 0.5 BEFORE X-macro can be written
   - Tests in `// === EXTENSIBILITY ===` walk every `FOREACH_*(X)`
     entry and assert each function pointer is non-null + dispatches
     correctly. Loop test prevents "added strategy to code but
     forgot to add to X-macro" silent failures.
   - Variant function naming: if multiple versions of a function
     exist (e.g. `_BuildParameters` + `_BuySignal` legacy stub),
     resolve which one is canonical for the X-macro **before**
     writing the macro, not during. Document choice in
     `STRATEGY_INTERFACE.md`.

1. **Existing 5 strategies continue to dispatch correctly.** No
   behavior change — refactor only.
2. **Existing models continue to load** OR force-invalidate via
   fingerprint mismatch. Both are valid; whichever you pick, the
   stamp body must reflect it (FEATURE_REGISTRY_HASH change forces
   retrain).
3. **Public/private split preserved.** `Strategies/private/EmaCross`
   conditional include via `__has_include` continues to work. Public
   release snapshot drops the line, dispatcher auto-omits the case.
4. **Hot path UNTOUCHED.** Registries are dispatch tables consulted
   on slow path; no per-tick cost.
5. **Each phase tagged + pushed before starting next.** Per-phase
   discipline (filesystem-crash incident lesson).
6. **Test count preserved or improved.** No tests deleted; existing
   behavior tests must still pass post-refactor.

## Risk assessment

**LOW risk overall — pure refactor with conservative migration:**

- No new operator-visible behavior
- Tests preserved, run before each commit
- Each phase independently revertable
- Hot path untouched (no per-tick changes)
- Models continue working OR force-invalidate cleanly via
  fingerprint hash bump
- Public/private split preserved via conditional includes

**Specific risk: macro debug noise.** Compiler errors in X-macro-
expanded code can be cryptic. Mitigation: keep each X line on its
own row, use clear naming, write tests that exercise the full
dispatch path so errors surface during testing not in production.

**Specific risk: existing strategies' function signatures don't
match conventional shape.** Mitigation: identify in Phase 0 audit;
either widen the X-macro spec to handle variants, or refactor
non-conforming strategies first (small change, ~1h each).

## Trigger conditions to pause / reorder

- **A strategy or feature needs to land before v5.8 finishes** → add

- **`/readiness` finds the macro pattern doesn't fit a category** →
  defer that category to v5.8.x bug-fix phase or skip it entirely.

## Phase 1 verification gate (post-strategy-registry)

After Phase 1 (strategy registry) ships, validate against 5 concrete
criteria. **Treat these as fix-targets, not abort triggers** —
v5.4.0's bug class showed the right move when something fails is
audit + targeted fix, not abandoning the sprint.

| # | Criterion | Verification |
|---|---|---|
| 1 | All 5 strategies dispatch correctly | Paper run + observe each strategy gets parameters built each cycle |
| 2 | Test count preserved + 5+ new EXTENSIBILITY tests added | `./build.sh test` shows 925+ pass |
| 3 | Zero new function-call orphans | `tools/calls_graph_diff.sh` before/after diff is empty |
| 4 | Latency p99 unchanged | `LATENCY_PROFILING=ON` build before/after, p99 within 5% |
| 5 | Build time within 20% of baseline | sanity check (X-macro nesting can blow this if abused) |

**Failure protocol:**
- Criterion fails → diagnose root cause first
- ≤ 5h to fix → patch in same phase, re-verify, continue
- > 5h to fix → pause, evaluate if X-macro pattern fits for this
  category. If not, keep hand-written dispatch for THIS category,
  continue with subsequent phases. The pattern is opt-in per
  category, not all-or-nothing.

This applies to every subsequent phase (2-5c) with criteria adapted
to the category (e.g. Phase 2 substitutes "FEATURE_REGISTRY_HASH
matches snapshot" for criterion 1).
