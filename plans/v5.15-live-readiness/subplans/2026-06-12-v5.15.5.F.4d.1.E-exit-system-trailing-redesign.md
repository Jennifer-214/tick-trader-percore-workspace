# Exit-system trailing-profit redesign — STUB / charter

> **This is a captured-and-parked STUB, not a ready plan.** It preserves the design + the code-grounded
> analysis from the `.E.0.10` A25 dialogue (2026-06-12) so nothing is lost. A full plan body (Phase breakdown,
> Tests-changed section, canonical-sister inspection, acceptance criteria) gets authored when the operator
> SEQUENCES this into the `.E.N` pipeline. Do NOT start coding from this stub — it is a design capture.

## End goal (the vision)

Replace the fixed-take-profit exit with a **trailing profit-lock + give-back-from-peak reversal exit**:
when price reaches the TP target, do NOT hard-exit — instead **ratchet the stop-loss up to the old TP level
and let the position ride**; keep trailing the SL upward as price climbs; **exit at the next peak when a
downward reversal is detected** (give-back-from-peak). This protects a previous high better than a fixed TP
and does not cap upside at the configured target.

**Long-horizon (operator vision, D-206):** the ratchet itself becomes **LEARNED** — a generalized function
where the model / online-learning strategy + the bandit + the ratchet-TP design co-function, with a
**dual-bandit** setup fine-tuning the ratchet parameterization at runtime. The ratchet config (trail
multiplier, give-back threshold, peak-arming gain) becomes a set of bandit ARMS.

## What this is NOT (the A25 boundary)

A25 (D-204/D-205) = **correctness of the reference prices** (`original_tp`/`original_sl` priced off the
actual fill, not the expected entry). THIS redesign = **what the exit DOES with those prices**. A25 is a
**prerequisite**: this redesign ratchets the SL *to* `original_tp`, so `original_tp` must be fill-priced
FIRST (do A25 before this).

## Current behavior (code-grounded gap analysis — exit-behavior agent, 2026-06-12)

Today's exit = **three fixed-level triggers**, all `Money_Ge`/`Money_Le` against a stored level:
1. **Hot SG gate** (`ExecutionCore.hpp:413-431`) — `tp_hit = price ≥ effective_tp`, `sl_hit = price ≤ effective_sl`; TP-hit is an **unconditional HARD exit**. `effective_tp = Money_Max(live_tp, ratchet_tp)`.
2. **Slow-path time-exit** (`ControllerEventLoop.hpp:3300-3362`).
3. **Kill-switch** (`:2849-2900`) — halts ENTRIES on equity drawdown; does not close positions.

Two slow-path ratchet writers move the SL level between ticks but never change the hard-exit semantics:
- `EventLoop_TrailingSLRatchetOneCore` (`ControllerEventLoop.hpp:3601-3660`) — trails `ratchet_sl` to `current_price − stddev×sl_trail_mult`, fee-floor-capped, gated on `gain > tp_hold_score`, max-only.
- **[D-253 fold 2026-06-22] — the mult-knob loss-floor is a RUNTIME guard THIS redesign OWES; ③ does NOT (and cannot) cap it.** ③/D-253 validates the PERCENT-form exit knobs (`give_back_pct`, `peak_arming_gain` → the `CAPITAL_BOUND` bits at the walker, by construction). But the trailing knobs that govern REALIZED loss are stddev MULTIPLIERS (`sl_trail_mult`): `ratchet_sl = current_price − stddev×sl_trail_mult`, so a cfg-bounded multiplier (`MULT[0,10]`) does NOT cap the resulting loss at 100% — a large-enough stddev produces an SL implying >100% loss (= margin = the no-margin violation [[project_no_margin_trading]]). The cfg-bound is a BOOT value-check; the loss-cap on a derived trailed level is a RUNTIME invariant the walker can't see. **D-206 OWES a slow-path runtime guard** at the ratchet decision (refuse/clamp `ratchet_sl < entry × (1 − BARRIER_SANE_MAX_SL)` — never let the trailed stop imply >100% loss; the SAME `BarrierValidation.hpp` SSoT, applied in `EventLoop_TrailingSLRatchetOneCore`). Do NOT over-claim "③ validates the ratchet by construction" — it validates the percent knobs only. Canonical: D-253.
- the per-strategy `Strategy_ExitAdjustPerCore` (`StrategyLifecycle.hpp:336`, dispatched at `ControllerEventLoop.hpp:2716`) → `*_ExitAdjustSharded` — these READ `original_tp` as the trail-arming gate (the A25 surface).
- `ratchet_tp` (`Strategy_WriteRatchetTP`) only RAISES the hard-exit TP target; it never converts TP→stop.

**Gap vs the desired behavior (3 load-bearing pieces ABSENT):**

| Desired piece | Status | Detail |
|---|---|---|
| On TP-hit, don't hard-exit | **NOT PRESENT** | `tp_hit → sg_fires → EXIT` is unconditional in the branchless hot gate |
| Ratchet SL up to the old TP on TP-hit | **NOT PRESENT** | `ratchet_sl` trails below current price, never set to `original_tp` |
| Ride past TP / keep trailing | **PARTIAL** | `ratchet_sl` rising-floor machinery exists + is consumed (`Money_Max(sl,ratchet_sl)`), but only operates BELOW TP (position hard-exits at TP) |
| Peak / give-back-from-peak reversal exit | **NOT PRESENT** | NO per-position price-peak / MFE / drawdown-from-peak tracking exists (only `core_peak_balance`, an equity kill-switch) |

~30% reusable scaffolding: the `ratchet_sl` rising-floor primitive + the slow-path per-position cadence walk + `original_tp` as the natural "old TP" anchor + the `Money_Max` peak-ratchet shape (already used for `core_peak_balance`).

## Cheapest struct plan (cascade agent, `-fdump-record-layouts`-verified)

**Keep peak-tracking on the SLOW path; route give-back through the EXISTING `ratchet_tp`/`ratchet_sl` channel.**
→ ZERO hot-gate change, ZERO `GateParameters`/`ExecutionCore` growth (the give-back resolves to a level the
existing `Money_Max(tp,ratchet_tp)` already consumes; **and `GateParameters` is embedded 3× inside `ExecutionCore` (`param_slot.buffers[2]` + `cached_params`), so a naive hot-gate `give_back_price` field would TRIPLE the per-core hot-struct cost — the slow-path-only + reuse-the-ratchet-channel choice is what AVOIDS that, not incidental**). Only struct cost = **ONE forced `Position` 128→192B**
(a persisted `Money` PEAK + a riding-mode flag in the existing 7B `_pad_pos`). **Coordinate with D-55**
(Position AoS→SoA at `.E.1`) — do this as a SoA-column add, not an AoS field add, if D-55 lands first.

- cfg knobs (give-back-pct, peak-arming gain, per-arm ratchet configs) = **1-row-each in `FOREACH_CFG_FIELD`**, fully auto-flowing (parser + GUI + tooltip + `core_N_*` override) — zero manual cascade.

## Cascade RISKS (the silent ones — must be in the eventual plan body)

1. **#1: the warm-restart re-arm** (`ShardedSnapshotPersist.hpp:591-687`) must thread the new PEAK + riding-state, or a restored position silently loses its peak + re-arms at the original TP — the **A1 bug class** (warm-restart read the wrong basis). Compiles clean; fails silently.
2. **2–3 divergent `Position` persist geometries** — `Portfolio_Save` prefix vs `ShardedSnapshotPersist` full-struct vs the legacy `PortfolioController` path, under different version constants (`PORTFOLIO_SNAPSHOT_VERSION` vs `SHARDED_SNAPSHOT_VERSION`). Coincident at 128B today; DIVERGE the moment a PERSIST field meets a SKIP_PERSIST sibling. Bump BOTH versions (H21).
3. **`is_trailing` is a DERIVED GUI signal** at 2 sites (`EngineTUI.hpp:273`, `:1556`: `take_profit_price != original_tp`) — a riding-mode flag breaks the derivation; switch both to read the explicit flag.
4. **`PositionEntryArgs` Class-18-mirror** (`Portfolio.hpp:332`) — if PEAK must survive replay, add it there + both `Portfolio_OpenSlot` populate sites, or replay/backtest positions start with a zero peak (train/serve parity gap).

## Invariants + audit tier

- **HIGH-RISK** (touches the H7/H8 branchless hot SG gate). The "suppress TP exit in riding mode" must stay BRANCHLESS (mask-select, not a data-dependent branch). Full `/precoding-audit-gate` HIGH-RISK + `/blindspot-scan` + `/hft-audit` before coding.
- **Determinism (H9 + the determinism gate):** a runtime-LEARNED ratchet introduces runtime-varying exit behavior → must stay deterministic/seeded + reproducible across runs/replay; the bandit state must persist + warm-restart correctly (like `exit_bandits`).
- **Keep the LEARNING slow-path-only; the hot gate consumes the resolved levels branchlessly** (the ratchet DECISION is slow-path; the gate never learns).
- **H22 per-node purity:** the peak/ratchet state is per-position, per-node-local — no cross-node coupling.

## Framework-fit (the learned ratchet EXTENDS, does not add infra)

The dual-bandit ratchet learning extends the EXISTING bandit substrate: `exit_bandits` + `EnsembleModelZoo`
+ Thompson; `Order::flags_packed` already carries `bandit_chosen_arm` (Order.hpp). New arms = ratchet
parameterizations = **1-row-in-registry** per the X-macro pattern — NOT a new bandit framework. (Canonical-sister

## Open questions (for the full plan body at sequencing time)

- Peak granularity: per-tick (hot) vs per-cadence (slow)? (cascade agent strongly recommends slow — keeps cache-line-0 intact.)
- Give-back rule: fixed pct of peak, ATR-scaled, or bandit-learned from the start?
- Interaction with partial-exit legs A+B (leg B "rides" to a fixed TP2 today — does it become the trailing leg?).
- Does `original_sl` need the symmetric peak treatment, or is the trailing SL sufficient?
- Sequencing: before or after the D-55 Position SoA transition? (coordinate to avoid a double Position rework.)
- **ExitRecord/ExitBuffer peak field** — once positions ride-past-TP + track a peak/MFE, the exit/trade record (`Portfolio.hpp:166-183` `ExitRecord`/`ExitBuffer`, snapshotted at `PositionExitGate`) likely needs a `peak`/MFE field, both for post-hoc analysis AND as the learned-ratchet's reward signal (give-back accepted vs the peak). Decide whether the peak is recorded at exit.
- **Learned-ratchet determinism — make it an ACCEPTANCE CRITERION, not just "seeded":** the ratchet DECISION must be a PURE FUNCTION of seeded + persisted bandit state, byte-replayable across runs/replay (the determinism gate must pass with the learned ratchet ON). A mid-learning deploy changes the trajectory DETERMINISTICALLY, not randomly. (Sharpens the Invariants § determinism line.)
