### [CRITICAL] `conc-5` — Multi-producer race on per-core submit_queues SPSC ring: drainer thread AND per-core slow thread both push the same ring on the LIVE order-submit path
*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `concurrency` · fix: .E.1 (per-node thread topology rebuild — E-MASTER-REFERENCE.md §4 'concurrency-model-summary.md: drainer removed; per-node owns trading flow'; eliminating the central drainer makes each node the sole producer for its own order flow, restoring SPSC). Interim standalone option if .E.1 slips: partition producers per TECH_DEBT-129 Option B (drainer keeps market-driven events; per-core handles policy-driven exits) OR replace submit_queues with a true MPSC ring (header line 42 already names this).
- **Where:** CoreFrameworks/OrderManager.hpp — submit_queues[MAX_EXECUTION_CORES] (decl ~line 269), OMS_PushSubmit (~line 1056: SPSCRing_TryPush(&oms->submit_queues[cmd.core_id], cmd)). Producer #1 = DRAINER thread via EngineSharded_Async_DrainWithSubmit @ CoreFrameworks/EngineSharded/Async.hpp:872 (OMS_PushSubmit for hot-path entries/exits drained from event_ring; cmd.core_id = portfolio_slot). Producer #2 = PER-CORE SLOW thread c via EngineCommon_SlowPathCycleOneCore @ CoreFrameworks/EngineCommon.hpp:694 (exit-model) + EventLoop_TimeExitOneCore @ CoreFrameworks/ControllerEventLoop.hpp:3361 + EventLoop_TrailingSLRatchetOneCore @ ~3431, all via OMS_PushExitForSlot → OMS_PushSubmit. Thread spawn: drainer @ Run.hpp:1455; per-core slow threads @ Run.hpp:1604-1616 calling SlowPathCycleOneCore @ Run.hpp:1939.
- **What:** tt::SPSCRing is strictly single-producer single-consumer (header line 10-12: 'no MPSC'). SPSCRing_TryPush does head.load(relaxed) → next_head=head+1 → slots[head&MASK]=item → head.store(release) with NO CAS / no producer serialization. In the current sharded topology, for a given core c's submit_queues[c], TWO distinct OS threads push concurrently with no lock between them: the drainer thread (running DrainWithSubmit for hot-path entry/exit events whose portfolio_slot maps to core c) and slow-path-thread-c (running time-exit / trailing-SL ratchet / exit-model force-sells for the slots owned by core c). When both push in the same window: both read identical head, both write the SAME slot index, both store head+1 → one SubmitCommand is silently overwritten (lost order) AND head advances by 1 instead of 2 (ring depth desync; a subsequent slot is consumed as garbage or skipped). On a live exchange this means a real BUY or force-SELL can be silently dropped, or a stale slot re-submitted. OMS_PushSubmit's own comment (OrderManager.hpp:1046-1049) asserts 'Today's caller (producer slow-path) is the sole producer for ALL queues — still SPSC per ring. When Phase C spawns per-core slow-paths, each thread is the sole producer for its own ring' — but Phase C HAS shipped (per-core slow threads exist at Run.hpp:1604) and they are NOT the sole producer for their ring: the drainer races them. SubmitCommand-doc at OrderManager.hpp:108-113 likewise frames per-core-slow-thread producers as 'future'.
- **Why:** Latency>determinism>maintainability gradient: this is a correctness/determinism failure on the LIVE money path (lost or duplicated exchange orders → position-state divergence vs exchange). It is non-deterministic (window-dependent), will not reproduce in single-threaded tests, and the in-code documentation actively asserts the opposite (a reviewer trusts 'SPSC contract holds in both modes'). Severity CRITICAL because it can drop a force-SELL exit (risk-control bypass) or a BUY, on real capital, with no error surfaced (TryPush returns true on the surviving push).
- **⚠ Don't carry forward (.E.1 rewrite):** Do NOT carry forward the OMS_PushSubmit / SubmitCommand comments claiming 'sole producer for ALL queues' / 'future: per-core slow-path threads' — in the .E.1 per-node rewrite, the node's order-submit ring must have exactly ONE producer (the node's own thread) by construction, and the comment must state that as an enforced invariant, not an aspiration. Do not reintroduce a shared central drainer that pushes the same ring a node thread also pushes.
- **CI check:** Static call-graph check: for each SPSCRing_TryPush(&X) site, collect the set of thread-entry functions (pthread_create / std::thread lambda roots) that can reach it; fail if any ring X has >1 distinct producer thread root (and symmetrically >1 consumer root for TryPop).
- **Test to add:** Add a multi-threaded stress test that spawns a drainer-role thread and a slow-path-role thread both calling OMS_PushSubmit on the same submit_queues[c] under contention, with a single draining consumer, and asserts total_pushed == total_drained (no lost/duplicated commands) over 1M iterations. (Sister to conc-2: there is currently NO multi-threaded SPSC test at all.)
- **Anti-pattern:** An SPSC ring whose producer-side push is reachable from two or more threads after a topology change, while the in-code comment still asserts single-producer — the safety doc lags the thread model.

### [HIGH] `fpmem-1` — Production accounting path runs strict-aliasing UB type-punning (_to_fp64/_from_fp64) under -O3 -flto
*verified · **NEEDS-RUNTIME-CONFIRM*** · section `fixedpoint-mem` · fix: standalone (foundational) — fix before .E.1 core->node rewrite touches FPN call sites
- **Where:** FixedPoint/FixedPointN.hpp _to_fp64 (~line 1221: `r.magnitude = *((__uint128_t*)v.w)`) + _from_fp64 (~line 1224: `*((__uint128_t*)r.w) = v.magnitude`), under #ifdef USE_NATIVE_128; reached by every FPN<64> op specialization (FPN_AddSat/SubSat/Mul/DivNoAssert/Equal/LessThan/Min/Max/FromDouble/ToDouble/Sqrt, lines ~1229-1254). Build wiring: CMakeLists.txt:21 option(USE_NATIVE_128 ... ON) + :67/:153/:198 target_compile_definitions(engine/engine_gui/foxml_suite PRIVATE USE_NATIVE_128); :11 target_compile_options(... -O3 -march=native -funroll-loops -flto).
- **What:** With USE_NATIVE_128 ON (the default for every production + test target), FPN<64> arithmetic forwards to FP64 via two helpers that read a uint64_t w[2] array through a __uint128_t* lvalue and write a __uint128_t through the same cast. This is a strict-aliasing violation (uint64_t and __uint128_t are not similar types; accessing one object through an lvalue of the other is UB under C++ [basic.lval]). The build uses -O3 -flto with no -fno-strict-aliasing, so the optimizer is licensed to assume the uint64_t writes and __uint128_t reads do not alias and may reorder/elide them. Additionally FPN.w is only alignof(uint64_t)=8-byte aligned, but the cast dereferences it as __uint128_t (alignof 16) — a misaligned access that is separately UB and can fault or be miscompiled on stricter targets.
- **Why:** This is the FPN<F=64> accounting hot/slow path (H4): balance, PnL, price, qty, fees all flow through FPN_Add/Sub/Mul/Div which specialize to these helpers in production. UB on the accounting path means the latency/determinism guarantees (H8/H9) rest on the optimizer happening to do the obvious thing today; an LTO inlining decision or compiler upgrade can silently corrupt money math or break cross-build byte-equivalence. Severity HIGH because it is the production accounting path under the most aggressive optimization settings, not a cold corner.
- **⚠ Don't carry forward (.E.1 rewrite):** Do NOT reintroduce raw pointer-cast punning when renaming. Use memcpy (compiles to zero instructions at -O2+, no aliasing/alignment UB) or a __may_alias__ typedef, or make FPN<64>::w a union member with the __uint128_t. The 'zero-cost conversions (identical memory layout)' comment is the trap — layout-equal does not make the cast legal.
- **CI check:** grep CI: flag `*((__uint128_t*)` / `*(__uint128_t*)` / reinterpret_cast<__uint128_t*> over a uintN_t array member; also add -fno-strict-aliasing OR -Wstrict-aliasing=2 to a dedicated CI build of the FixedPoint unit tests
- **Test to add:** No UBSan build exercises FPN<64> arithmetic with -fsanitize=alignment,undefined; add a UBSan (alignment+aliasing) run over the FixedPoint test block
- **Anti-pattern:** type-punning a fixed-width integer array through a wider-integer pointer cast on the strict-aliased optimized build, justified by a 'same memory layout' comment

*grep-verified · **NEEDS-RUNTIME-CONFIRM*** · section `fixedpoint-mem` · fix: .E.1 Foundation (foundational FixedPoint layer)
