## Decision A — FOREACH_BANDIT_ALGORITHM registry retrofit?

### The split

- **dod-audit + readiness:** FOLD into v5.14.10.A. Curve-registry-pattern MATCHES (same shape as FOREACH_DEGRADATION_CURVE v5.14.9.A). Future modes (UCB1, EXP4, Bayesian linear) foreseeable → 5-8× future-work multiplier. Per `feedback_no_mvp_for_plumbing` + `feedback_overengineering_boundary_when_future_easier`: plumbing gets full design.
- **trace-deps:** DEFER with explicit TECH_DEBT trigger ("Next bandit algo = 4th instance triggers refactor"). Rationale: dispatch contract is non-uniform (Exp3 writes weights[]; Thompson writes one-hot + chosen_arm; Both does both). Ship grows from ~610 LOC → ~900-1100 LOC.

### Resolution path: uniform 4-arg dispatch contract makes signature mismatch a non-issue

```cpp
typedef void (*BanditAlgoFn)(EnsembleModelZoo<F>* ezoo,
                             int regime_id,
                             int n_arms,
                             double* weights_out,
                             int* chosen_arm_out);

// FOREACH_BANDIT_ALGORITHM registry (3 entries today; future = 1 row each)
#define FOREACH_BANDIT_ALGORITHM(X)                                                                  \
    X(EXP3,     0, BanditAlgo_Exp3_Apply,     "Exp3-IX (default; bytewise-identical to pre-v5.14.10)")\
    X(THOMPSON, 1, BanditAlgo_Thompson_Apply, "Bayesian Thompson sampling; non-stationary-friendly") \
    X(BOTH,     2, BanditAlgo_Both_Apply,     "Run both for A/B telemetry (cfg=2 dual-mode)")
```

Each compute fn writes BOTH outputs (weights[] AND chosen_arm); callers read whichever they need. Exp3's chosen_arm = argmax(weights); Thompson's weights[] = one-hot at chosen_arm. Uniform contract, zero ambiguity.

### Recommendation: **RETROFIT NOW**

Per Caramel's overengineering-boundary rule: pick harder-now-easy-later when future work is FORESEEABLE. UCB1 + EXP4 + Bayesian linear are all in the bandit literature; 4th algorithm WILL land. ~+2-3h on the ship vs ~5× future-work multiplier per algorithm.

Per `feedback_no_mvp_for_plumbing_only_for_unknown_unknowns`: this is plumbing (3-mode dispatch is well-understood); ship the full design.

Trade-off you're absorbing: ~250 LOC plan → ~400-500 LOC; .A ship grows by ~1 day. Defer kept available if you'd rather minimize ship size.

## Decision C — Slow-path-gate cached predicates THOMPSON_ACTIVE / BANDIT_BOTH_ACTIVE?

`cfg.bandit_algorithm` is INT (3 values), so the FIELD itself isn't bitmap-eligible. But 2 derived booleans CAN cache:
- `THOMPSON_ACTIVE = (bandit_algorithm == 1 || bandit_algorithm == 2)`
- `BANDIT_BOTH_ACTIVE = (bandit_algorithm == 2)`

Add 2 entries to FOREACH_SLOW_PATH_GATE alongside MASK_RIDGE_WITHIN_ACTIVE / MASK_EXIT_BLENDER_ACTIVE. Per-cycle cfg load → bitmap mask AND. Saves ~3-5ns/cycle per ML cycle.

**Recommendation:** **ADD**. Pattern-aligned; gate_state has 9 bits headroom; v5.14.9.B.0 SLOW_PATH_GATE precedent. Marginal ns win but follows CLAUDE.md item 18 (slow-path latency reduction priority). Effort: ~10 min.
