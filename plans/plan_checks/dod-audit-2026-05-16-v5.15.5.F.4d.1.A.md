## Findings (severity-ordered)

### CRITICAL — F-1: Meta-registry tuple shape mismatch (sub-ship will not build as drafted)

- **Surface:** Plan body § "FOREACH_DERIVED_FILTER Level-1 meta-registry at `.A`" (lines 249-260); sidecar § Step 4 "Edit at `CoreFrameworks/MetaRegistry.hpp` — `FOREACH_REGISTRY` row addition" (lines 450-458)
- **Pattern:** `meta-registry-pattern-for-codebase-registry-discipline.md` (Stage 3 ACTIVE)
- **Symptom:** Plan/sidecar specify an 8-column row insertion:
  ```cpp
  X(DERIVED_FILTER,
    "CoreFrameworks/DerivedFilterRoster.hpp", 1, ROOT,
    "metadata-bit-driven-derived-filter-framework.md", Class_21, MIXED,
    "Manages 7 cfg-derived filters; Stage 3 ACTIVE first canonical at .F.4d.1.A")
  ```
  **But** the existing `CoreFrameworks/MetaRegistry.hpp:35` defines `FOREACH_REGISTRY(X)` with a **4-column tuple**: `X(registry_name, LEVEL, PARENT_NAME, description)`. All 49 currently-enrolled rows (`MetaRegistry.hpp:37-105`) use the 4-col shape, and `tools/check_meta_registry.py` parses against that shape. The 8-col row will not compile; the parser will not recognize it.
  
  Additionally, the row uses `PARENT=ROOT` but existing rows use `PARENT_NAME=ROOT_NONE` (defined `MetaRegistry.hpp:33` as `0`) for Level-0 rows, and a concrete `FOREACH_REGISTRY` parent token for Level-1+. A Level-1 cohort meta-registry should have `PARENT_NAME=FOREACH_REGISTRY` per existing convention.
- **Suggested fix (compile-success path):** Use the 4-col existing shape. The DESIGN_SPEC's 8-col shape is the **target** for the broader TECH_DEBT-057 / TECH_DEBT-058 meta-registry refactor; `.A` should **add a row in the current 4-col shape**, with the design_spec / bug_class / wire_format_kind metadata deferred to TECH_DEBT-057.
  ```cpp
  X(FOREACH_DERIVED_FILTER, 1, FOREACH_REGISTRY,
    "Derived-filter cohort meta-registry (.F.4d.1.A first canonical: STAMP_BOUND_CFG).")
  X(FOREACH_STAMP_BOUND_CFG_DERIVED, 2, FOREACH_DERIVED_FILTER,
    "Stamp-bound derived filter (DERIVED_FILTER cohort row; built via framework at .F.4d.1.A).")
  ```
  Note: existing rows at Level 1 use `FOREACH_REGISTRY` as PARENT_NAME (top-level meta), not `ROOT_NONE`. Level 2 cohort children use their Level-1 meta as PARENT. The plan's "Level=1, PARENT=ROOT" terminology in the DESIGN_SPEC is consistent with this — but the macro tokens used must be `FOREACH_REGISTRY` and `FOREACH_DERIVED_FILTER`, not `ROOT`/`ROOT_NONE` reinterpretation.
- **Effort estimate:** ~5 min plan body amendment + ~5 min sidecar amendment. **MUST FIX before coding starts** — Step 4 will fail build otherwise.
- **Cross-references:** F-2 (sidecar `Step 4` field also wrong); H15 + H19 codification; TECH_DEBT-057 (full schema migration deferred).

### MEDIUM — F-4: Cache-layout numeric in plan body (~64 bytes per descriptor) is wrong — descriptor is up to 128B

- **Surface:** Plan body § "DOD analysis" (line 487-489): "Descriptor struct size: ~64 bytes (cache-line); 1 descriptor per cache line; 213 fields × 64 bytes = ~14KB total; fits in L1 cache"
- **Pattern:** `cache-layout-discipline-for-hot-side-structs.md` (referenced in `framework-composition-overview.md`)
- **Symptom:** `CfgFieldRegistry.hpp:204` declares `static_assert(sizeof(CfgFieldDescriptor) <= 128, "...");` (TWO cache lines, not one). Counting members: 8 (header) + 32 (4 string pointers) + 10 (categorical masks) + 8 (requires_cfg) + 32 (payload union) = 90 bytes minimum; aligned to 128 per the static_assert. Walker cost numbers are off by 2× but still negligible (~213 × 2-4ns = ~800ns boot; not a budget concern).
- **Suggested fix:** Plan body amendment to say "Descriptor struct size: ≤128 bytes (2 cache lines per `CfgFieldRegistry.hpp:204` static_assert); 213 fields × 128 bytes = ~27KB total; fits in L1 cache." This is hygiene; no impact on `.A` correctness.
- **Effort estimate:** ~2 min plan body edit. Non-blocking.

### LOW — F-6: Sidecar `ControllerConfig<64>&` reference in macro Variant 3 needs an include

- **Surface:** Sidecar § Step 3 macro definition (line 294: `const ControllerConfig<64>& cfg`)
- **Pattern:** Header dependency hygiene
- **Symptom:** `DERIVED_FILTER_DECLARE_WIRE_FORMAT_TWO_SOURCE` (sidecar Step 3) macro takes a `ControllerConfig<64>&` parameter, but `DerivedFilterFramework.hpp` at sidecar Step 1 only includes `CfgFieldRegistry.hpp`. `ControllerConfig<F>` is declared at `CoreFrameworks/ControllerConfig.hpp:373` — distinct file. Macro expansion at the consumer site (`StampBoundDerivedFilter.hpp`) doesn't necessarily have `ControllerConfig` in scope unless the consumer adds the include.
  
  At sidecar Step 4 (`StampBoundDerivedFilter.hpp` definition, lines 374-389) the includes are:
  ```cpp
  #include "DerivedFilterFramework.hpp"
  #include "../ML_Headers/MlCfgFlagRegistry.hpp"
  ```
  Neither pulls `ControllerConfig.hpp` transitively (CfgFieldRegistry is the schema; ControllerConfig depends on CfgFieldRegistry but not vice versa). The bitmap walker function `STAMP_BOUND_CFG_walk_bitmap_rows` will fail to compile because `ControllerConfig<64>` is incomplete.
- **Suggested fix:** Add `#include "ControllerConfig.hpp"` to `StampBoundDerivedFilter.hpp` (sidecar Step 4). Alternatively: forward-declare `template<unsigned F> struct ControllerConfig;` at top of `DerivedFilterFramework.hpp` to make the macro definition compile in isolation, then require the include at the consumer site (cleaner separation; matches Variant 1 style). Forward-decl form is preferred because it keeps `DerivedFilterFramework.hpp` schema-only.
- **Effort estimate:** ~2 min (single include line OR single forward decl). Should be fixed before Step 3 build verify; otherwise that step fails.
