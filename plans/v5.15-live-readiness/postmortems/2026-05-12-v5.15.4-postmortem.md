### v5.15.4.C — `HotSwap_ShadowLoad_Ensemble<F>` in new `CoreFrameworks/HotSwap.hpp`

- New file with 2 template helpers per `shadow-load-state-transition-pattern.md`.
- Ensemble helper:
  1. Reads horizon list from pre-swap ezoo (operator's boot-time horizon set inherited)
  2. `aligned_alloc(64, sizeof(EnsembleModelZoo<F>))` → new heap allocation
  3. `EnsembleModelZoo_Init` on new

- Returns -1 (OOM) / -2 (load failed) / -3 (strict validate failed) / 0 (success).
- Legacy `EnsembleHotSwap.hpp::EngineSharded_HotSwapEnsemble` retained (still

### Boot-path heap migration (implicit; scope discovered during .C/.D)

Plan didn't enumerate this but shadow-load requires it: `free(old_ezoo)` on
the first swap is UB unless the pre-swap pointer is heap-allocated. Pre-v5.15.4
boot used function-static arrays (`static CoreModelZoo<F> ml_zoos[MAX_EXECUTION_CORES]`).
Migrated to per-core `aligned_alloc(64)` heap allocations at the
`if (cfg.core_strategies[i] == STRATEGY_ML)` block. ~30 LOC of `ml_zoos[i]` →
`zoo_ptr` substitution. Process-exit leak acceptable (same property as
pre-v5.15.4: no shutdown cleanup of internal allocations either).

## What surprised me

### 1. Plan amendment (PARITY-023) saved time, not added it

Original v5.15.4 plan had broken capture-pointer-and-revert design.
Pre-coding `/parity-check` audit caught it; plan amended to shadow-load.
Shadow-load is conceptually MORE work than capture-pointer (~330 vs ~200
LOC estimate) but the implementation went smoother because:
- No revert path needed (failure → Free new; pre-swap untouched)
- No HotSwapSnapshot struct invented (local variables suffice)
- Atomic_exchange_n is 1 instruction; the lock-free reader-side
  preservation is structural, not engineered

### 2. Boot-path static→heap migration was unplanned but necessary

Plan implicitly assumed heap-allocated zoos for `free(old)` validity. The
existing `static CoreModelZoo<F> ml_zoos[]` arrays needed migration to
`aligned_alloc(64)` heap. ~30 LOC; not in the plan's scope estimate but
inseparable from the shadow-load design. Per `feedback_no_defer_for_effort`,
implemented properly inline rather than splitting to a sub-ship.

### 3. C++ template syntax in template-fn-internal lambda

`tt::HotSwap_ShadowLoad_SingleZoo<F>(args)` failed to compile in the lambda
inside `EngineSharded_Run`. GCC parsed `<F>(` ambiguously. Fix was structural
(forward-declare `EventLoopState<F>` via include of `ControllerEventLoop.hpp`
in HotSwap.hpp), not syntactic (the actual root cause was HotSwap.hpp not
seeing the type definition; the `<F>(` parse error was misleading).

### 4. PARITY-023 wasn't real (in production) — it was a plan-stage error

PARITY-023 was caught at PRE-CODING audit. The capture-pointer-and-revert
design never shipped to production code (only to plan draft). So technically
no production bug was fixed — the audit prevented a planned production bug.
That's the audit-driven pre-coding gate working as designed (per
DESIGN_SPECS/audit-driven-pre-coding-gate.md).

## Decoupling-roadmap positioning

⬆️⬆️ strongly positive. Shadow-load discipline is the canonical state-transition
primitive future v6.0+ headless services will use. Pattern positions for:

- **Atomic config deploys** — operator pushes new cfg via REST endpoint;
  service shadow-loads + validates + atomically commits.
- **Signing key rotation** — same primitive applied to HMAC secrets.
- **Multi-tenant model deploys** — shadow-load isolates per-tenant zoos.

`aligned_alloc(64)` + container `alignas(64)` discipline preserves mmap-readiness
for future memory-mapped state exposure to off-process viewers.
