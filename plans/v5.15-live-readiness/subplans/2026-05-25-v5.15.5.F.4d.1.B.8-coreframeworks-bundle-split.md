## Why this ship exists

Per umbrella plan body Decision D bundling: `.B.8` bundles 2 CoreFrameworks headers because (a) both are CoreFrameworks/ category, (b) both are slow-path adjacent (similar Phase A audit needs), (c) split work is mechanical pattern application post-`.B.6` codification. Bundling reduces per-ship overhead.

Per `feedback_no_defer_for_effort`: full close, not partial.

**Why these 2 headers specifically together (not paired differently):**
- `ControllerEventLoop` + `ControllerConfig` are TIGHTLY coupled — ControllerEventLoop's `EventLoop_RebuildOneCore` reads cfg fields from `ControllerConfig<F>`; both touch the seqlock cfg→hot handoff surface. Splitting one but not the other creates incomplete picture for downstream consumers.
- `ControllerEventLoop` + `EngineSharded` (already split at `.B.6`) had natural separation point; not bundle candidates.
- `ControllerConfig` + `PortfolioController` (PortfolioController is at `.B.10`) — PortfolioController has legacy/sharded duality that warrants separate ship.

**Order of header splits within this ship:** ControllerEventLoop FIRST (less X-macro-laden; easier first pass to validate `.B.6` pattern at 2nd application); ControllerConfig SECOND (heavier X-macro discipline; benefits from ControllerEventLoop verification first).

## Design space + future-oriented choices

### Decision A — ControllerEventLoop sub-file boundaries

| Sub-file | Owns | Estimated LOC | Dependencies |
|---|---|---|---|
| `SlowPath.hpp` | `EventLoop_UpdateRollingStateOneCore`, `EventLoop_RebuildOneCore`, `EventLoop_TimeExitOneCore`, `EventLoop_TrailingSLRatchetOneCore` — the per-core lifecycle functions | ~1,500-2,000 | EventLoopState struct (in Struct.hpp? or stays in shim header? — see below) |
| `Drainer.hpp` | `OMS_DrainSubmit`, `DrainPostFill`, `OrderManager_Tick` — drainer-thread orchestration | ~800-1,200 | EventLoopState; references SlowPath helpers via shim |
| `KillSwitch.hpp` | kill_switch evaluation logic + `EventLoopState_ConfigureKillSwitch` (PARITY-026 + .B.4 EngineCommon caller) | ~300-500 | EventLoopState |
| `Freshness.hpp` | `ConfidenceScorer_UpdateAndMark`, drift tracking (PARITY-002 fix lives here) | ~300-500 | EventLoopState; ConfidenceScorer cross-call |

**Decision: where does `EventLoopState` struct definition live?**

Options:
- (a) Top of shim (before sub-file includes) — every sub-file sees it without explicit include
- (b) Dedicated `Types.hpp` sub-file included first
- (c) Inline in `SlowPath.hpp` (since SlowPath is biggest consumer)

**CHOSEN: (b) `ControllerEventLoop/Types.hpp` — dedicated types sub-file.** Cleanest dependency: `Types.hpp` first; SlowPath / Drainer / KillSwitch / Freshness include it via shim. Avoids ordering surprises.

Updated sub-file list: `Types.hpp` + `SlowPath.hpp` + `Drainer.hpp` + `KillSwitch.hpp` + `Freshness.hpp` (5 sub-files; `Types.hpp` likely small ~100-200 LOC of struct definitions).

### Decision B — ControllerConfig sub-file boundaries

| Sub-file | Owns | Estimated LOC | Dependencies |
|---|---|---|---|
| `Struct.hpp` | `ControllerConfig<F>` template struct + ALL X-macro registries (`FOREACH_CFG_FIELD`, `FOREACH_PER_CORE_CFG_FIELD`, `FOREACH_GLOBAL_CFG_FIELD`, `FOREACH_*_CFG_FLAG`, `FOREACH_DRIFT_OVERRIDE`, `FOREACH_DERIVED_FILTER`, etc.) + cohort macros (`COHORT_GATE_*`, `MASK_*`, `BITMAP_BIT_*`) | ~1,500-2,000 | No internal deps |
| `Parser.hpp` | `ControllerConfig_Load<F>` template function + per-Kind parser dispatches via `tt::cfg_parse_field<T>` | ~800-1,200 | Struct.hpp (uses all macros for parser walk) |
| `Defaults.hpp` | Default initializer values (the 16 KEEP-MANUAL exemptions from `.B.3` Step 8.6 with inline rationale; plus any non-registry-driven defaults) | ~300-500 | Struct.hpp |
| `Validate.hpp` | Parse-time invariant validation (Winsor bounds + cross-field checks) | ~200-400 | Struct.hpp + Parser.hpp (called from parser) |

**Critical: X-macro definition→consumption order discipline (M2 per .B.6 codification)**

`Struct.hpp` MUST be included first in shim — defines all X-macro registries. `Parser.hpp` + `Defaults.hpp` + `Validate.hpp` consume the macros. Shim include order: `Struct.hpp` → `Defaults.hpp` → `Validate.hpp` → `Parser.hpp` (parser depends on defaults + validators).

If Struct.hpp exceeds 1,500 lines (X-macro registries alone may be substantial), split further into `Struct.hpp` (struct definition + most-used macros) + `Macros.hpp` (less-used X-macro registries). Decided at Phase B after measurement.

### Decision D — ControllerConfig<F> struct layout preservation (H6 cross-thread; CRITICAL)

`ControllerConfig<F>` is in cross-thread context (slow→hot seqlock cfg handoff). H6 invariant requires `alignas(64)` cluster discipline + struct field ordering preserved exactly. Splitting Struct.hpp from the rest MUST NOT change struct layout.

**Discipline:**
- `Struct.hpp` contains the ENTIRE struct definition (no field reordering, no field hoisting to other sub-files)
- `static_assert(sizeof(ControllerConfig<int64_t>) == EXPECTED_SIZE);` added at Struct.hpp bottom (if not already present)
- `static_assert(offsetof(ControllerConfig<int64_t>, FIELD) == EXPECTED_OFFSET);` for cross-thread critical fields (verified at Phase A audit)
- `/dod-audit` Phase A + Phase C verifies cluster alignment

### Decision E — Friend declaration audit (M1 per .B.6 codification)

`ControllerConfig<F>` may have friend declarations (e.g., parser accessor friends). Similarly `EventLoopState` may friend EngineSharded types.

**Phase A audit task:** grep for `friend` in current ControllerEventLoop.hpp + ControllerConfig.hpp. For each:
- Identify both sides; determine sub-file landing per Decisions A/B
- If split across sub-files: refactor (move both sides to same sub-file OR add forward decl pattern)

**Expected outcome:** Low friend usage in template-heavy + macro-heavy codebase like this; most operations are public methods or template functions. Phase A audit verifies.

### Decision F — Macro definition order across both headers

ControllerConfig.hpp Struct.hpp defines macros consumed in:
- Same header's Parser.hpp / Defaults.hpp / Validate.hpp (handled per Decision B shim include order)
- OTHER headers' downstream consumers (e.g., StampHelper, ModelInference, CfgGateRegistry)

**Discipline:** Other headers continue to `#include "CoreFrameworks/ControllerConfig.hpp"` (the shim) — they get full macro set in correct order via shim. No downstream caller change needed.

### Decision G — Decoupling positioning (informational)

`ControllerEventLoop/SlowPath.hpp` becomes natural runtime-binary boundary at v6.0 decoupling (per `plans/_future/2026-05-12-decoupling-endgoal-roadmap.md`). `ControllerConfig/Struct.hpp` becomes the cfg ABI surface that viewer attaches to via mmap.

**Positioning:** ⬆️ POSITIVE for v6.0 viewer split.

## Pre-coding concerns

1. **ControllerConfig<F> struct layout regression** — H6 cross-thread invariant. Mitigation: Struct.hpp contains ENTIRE struct (no hoisting); sizeof + offsetof static_asserts.
2. **X-macro consumer registration** — Downstream consumers (StampHelper, ModelInference, CfgGateRegistry, drift checkers) walk macros via include of ControllerConfig.hpp shim. Verify Phase B B.13 shim re-exports complete macro set.
3. **ControllerEventLoop SlowPath body templates** — `EventLoop_RebuildOneCore<F>` is templated; instantiated for `F=int64_t` (FPN<64>). Template definition splits across sub-files only if helpers also split; per Decision A SlowPath.hpp keeps full body.
4. **Parser body has ~50 strcmp branches + X-macro-generated parser blocks** — preprocessor expansion order matters. Parser.hpp includes Struct.hpp (via shim) to access macros; expansion happens at compile time per shim include order.
5. **Seqlock cfg→hot handoff** — ControllerConfig<F>* pointer passed across threads via seqlock cached params. Pointer arithmetic unchanged by split; struct fields accessed by name (not offset) at hot-path; split doesn't affect.
6. **Test fixtures** — controller_test.cpp (now split per `.B.5`) has ControllerConfig fixtures; verify still accessible post-split.
