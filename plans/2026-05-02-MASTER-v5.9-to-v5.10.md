   `xgb_train_nthread` (default `auto` = nproc), `csv_load_workers`

   not feasible in foundation).

### Cross-plan conflict check (run before each ship)

When opening a plan to start coding, run this checklist:

- [ ] Files this plan touches — does any concurrent plan touch
      same file? If yes, sequence them or merge their scopes.
- [ ] Cfg fields this plan adds — do any conflict with existing
      cfg names (engine.cfg.example) or earlier-plan claims?
- [ ] Stamp body fields this plan adds — does the canonical-order
      position in the matrix above match the actual ship order?
- [ ] Test count claim — does it sum cleanly with existing total?
- [ ] Architectural invariants — has any prior ship landed work
      that invalidates this plan's assumptions?
- [ ] Branch state — is this plan still building on the right
      predecessor (e.g., v5.10.0a presumes v5.10.0 foundation has
      shipped to `feat/v5.10-foundation`)?

If any check flags YES, **update the master plan first** before
coding. The master is the source of truth.

### Master plan update protocol

When ANY sub-plan changes scope or shipping order:
1. Edit the affected sub-plan file.
2. Update this master's Integration Matrix to reflect the change.
3. Re-verify the cross-plan conflict checklist.
4. If a downstream plan is affected, edit it too (cascade).
5. Commit master + all touched sub-plans together.

**Smell test:** if a sub-plan's effort estimate doubles, or its
files-touched list grows by > 50%, the plan needs a re-readiness pass
before coding begins.

### Sub-plan review SLA

Per the v5.4 architectural-sprint discipline (CLAUDE_REVIEW.md
Check 11), every sub-plan must pass:

- `/readiness <plan-path>` — clean GREEN before coding
- `/parity-check` — narrow scope to the plan's surfaces (e.g.,
  `/parity-check stamp` for v5.10.0d, `/parity-check features` for
  v5.10.0b)
- Operator validation gate — explicit test steps after coding,
  before tag

Skip any of these and the master plan is silently lying about
deliverable readiness.
