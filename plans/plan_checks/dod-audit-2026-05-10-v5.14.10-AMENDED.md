- **Pattern:** `bitmap-flag-api.md` (BITMAP_BIT_U8 / MASK_* convention)
- **Symptom:** Plan's bit-packing layout is correct (1 + 3 + 4 = 8 bits exactly fit uint8_t). However:
  - `chosen_arm` is 3 bits (0-7) — matches `BANDIT_MAX_ARMS = 8` ✓
  - 4 bits reserved — generous headroom for future bandit-state-flags (e.g., "thompson_warmup_done", "exploration_phase_active", "rng_reseeded_this_cycle")
  - Plan does NOT define MASK_THOMPSON_ACTIVE / MASK_THOMPSON_CHOSEN_ARM constants explicitly in the snippet; plan §D Step 1 should specify the 3-mask layout following `bitmap-flag-api.md` MASK_* convention:
    ```cpp
    static constexpr uint8_t MASK_THOMPSON_ACTIVE      = BITMAP_BIT_U8(0);
    static constexpr uint8_t MASK_THOMPSON_CHOSEN_ARM  = (uint8_t)(0b00001110);  // bits 1-3 (3-bit field)
    static constexpr uint8_t SHIFT_THOMPSON_CHOSEN_ARM = 1;
    // Reserved bits 4-7 for future flags
    ```
  - Encoding: `state = (active ? MASK_THOMPSON_ACTIVE : 0) | ((chosen_arm & 0x7) << SHIFT_THOMPSON_CHOSEN_ARM)`
  - Decoding: `active = BITMAP_IS_SET(state, MASK_THOMPSON_ACTIVE)`; `chosen_arm = (state & MASK_THOMPSON_CHOSEN_ARM) >> SHIFT_THOMPSON_CHOSEN_ARM`
- **Suggested fix:** plan §D Step 1 add the explicit MASK_/SHIFT_ constants block + encode/decode pattern. Important because chosen_arm is a 3-BIT FIELD (not single bool) — operators of `BITMAP_*` may not realize the helper macros support multi-bit fields. The `(state & MASK_FIELD) >> SHIFT_FIELD` decode is standard but should be canonical in the plan to avoid future drift.
- **Effort:** ~5 min code snippet + explanatory comment in plan
- **Cross-references:** `bitmap-flag-api.md` §"Width-typed bit builders" (canonical multi-bit field idiom); `MemHeaders/PerCoreStateFlagsRegistry.hpp` (existing precedent for state-bitmap conventions)

### NEW-1 — `per-snapshot-cluster-layout-pattern.md` (ships with v5.14.10.0)

**Goal:** capture the methodology for grouping PerCoreSnap fields by concern (bandit / ridge / confidence / ladder / regime / latency / etc.) into cache-line-aligned clusters with arrays-first layout.

**Recommended sections (follows DESIGN_SPECS template):**

1. **Problem statement** — recurring pain points:
   - PerCoreSnap is grew organically (~70+ fields today); fields added by ship-by-ship without cluster discipline
   - False-sharing risk when display thread reads cross-thread-published fields scattered across cache lines
   - Hot/cold field placement: cold fields placed in middle of hot cluster forces cache-line load for cold data
   - GUI display reader cadence (60Hz) competes with slow-path writer cadence (~10-100Hz/core); each cache miss costs ~50-200 cycles
   - Adding a NEW telemetry surface (next ML feature, next bandit telemetry, next regime metric) without layout audit recurs the problem

2. **Design space explored** — at least 3 options:
   - **Option A: monolithic ad-hoc layout** (current; reject)
   - **Option B: one cluster per concern** (chosen; methodology below)
   - **Option C: full FOREACH_PER_CORE_SNAP_FIELD registry** (TECH_DEBT-011 referenced; deferred — needs design pass; fits SCOPE COLUMN heterogeneous-registry pattern; future ship)

3. **The pattern (concrete shape) — methodology + decision tree:**
   - **Identify clusters by CONCERN:** group fields written by the SAME slow-path code section (e.g., bandit telemetry written together; ladder factor written together). Cross-thread reads from GUI naturally align with concern.
   - **Arrays-first reorder per cluster:** put `T arr[N]` fields BEFORE scalar fields within each cluster — eliminates middle padding when N×sizeof(T) is cache-line-aligned (e.g., float[8] = 32B, double[5] = 40B).
   - **alignas(64) per cluster:** each cluster gets `alignas(64)` boundary mark. Between-cluster cache lines stay independent.
   - **Cache-line-count budgeting:** target ≤2-3 cache lines per cluster. Wide clusters (>3 lines) trigger sub-clustering (e.g., split bandit telemetry into "decision state" + "posterior values" sub-clusters).
   - **Hot/cold split awareness:** within a cluster, place fields by WRITER cadence: hot-write fields first; cold-write fields last. Reader cache pressure is proportional to write frequency.
   - **Cross-thread coherency analysis per cluster:** explicitly note (a) which threads write, (b) which threads read, (c) cache invalidation pattern. Document write-cadence (per-cycle / per-fill / boot-only).

4. **Trade-offs + when to apply / skip:**
   - Apply when: ≥3 fields cluster by concern; cross-thread access expected; cache-aligned write/read pattern
   - Skip when: 1-2 fields (cluster overhead unjustified); single-thread access only; boot-only fields
   - Cost: ~2-5h per PerCoreSnap layout pass; padding may grow slightly (alignment cost) vs sequential layout

5. **Reference implementations:**
   - First applied: v5.14.10.0 (this ship) — bandit telemetry cluster
   - Future application candidates: ridge cluster (post-v5.14.10), confidence cluster, ladder cluster, regime cluster, latency cluster

6. **Cross-references to existing patterns:**
   - `bitmap-flag-api.md` §"Cache-line awareness for shared bitmaps"
   - `partner-core-bitmap-pattern.md` (different concern: per-core 1-bit; this pattern: cluster of fields)
   - `heterogeneous-registry-pattern.md` §"Cache-layout discipline for DOMAIN SPLIT bitmap fields" (sister discipline at registry layer)
   - CLAUDE.md item 4 (per-core data plane)
   - CLAUDE.md item 12 (display↔execution invariant)
   - CLAUDE.md item 18 (slow-path latency reduction priority)
   - TECH_DEBT-011 (sister-registry: full FOREACH_PER_CORE_SNAP_FIELD registry; this pattern is the methodology layer; registry would be the structural-fix layer)

7. **Lessons / gotchas:**
   - Adding a field to existing cluster ≠ free; verify it doesn't push cluster past cache-line boundary
   - GUI side reads PerCoreSnap via `TUISnapshot_ReadInto` (full memcpy under seqlock) — cluster layout doesn't help GUI snapshot read latency, but DOES help slow-path WRITE coherency
   - alignas(64) cost: ~28-58 bytes padding per cluster; cumulative effect across 5+ clusters is ~150-300 bytes per PerCoreSnap × 16 cores = 2.4-4.8 KB total — acceptable vs cache-miss savings
   - Static_assert offset stability per cluster (e.g., `static_assert(offsetof(PerCoreSnap, thompson_mu_post) == EXPECTED_OFFSET)`) prevents accidental mid-cluster reorders during future ship

8. **Audit detection** (per `/dod-audit` Step 3):
   - Symptom: PerCoreSnap field added without alignas-aware placement; ad-hoc append-at-end
   - Symptom: clustered telemetry fields fragmented across non-contiguous offsets (split clusters)
   - Symptom: cache-line span analysis missing on cross-thread struct member layout

**Doc length target:** 250-350 lines (follows DESIGN_SPECS norm).

### NEW-2 — `calibration-log-column-registry.md` (ships with v5.14.10.D)

**Goal:** establish FOREACH_CALIB_LOG_COL registry-tuple shape; CSV format invariants; backward-compat strategy for legacy readers (column-append-only); auto-extension at writer/reader.

**Recommended sections:**

1. **Problem statement** — recurring pain points:
   - Calibration log CSV columns added manually 3-site updates: header constant + writer column + reader/parser column
   - TECH_DEBT-010 catalogs this for ≥3 years; now hits trigger (cfg=2 telemetry adds 4-5 columns)
   - Legacy CSV readers (post-process tooling, pandas scripts, paper-test analysis notebooks) MUST tolerate new columns appearing at end (column-append-only forward-compat)
   - Adding a calib log column without registry → drift between writer + parser → silent column misalignment; pandas reads wrong column → silent regression in calibration plots

2. **Design space explored:**
   - **Option A: manual 3-site updates** (current state — reject; TECH_DEBT-010)
   - **Option B: parallel column-name array + getter-fn array** (rejected — same drift class)
   - **Option C: FOREACH_CALIB_LOG_COL X-macro registry tuple** (chosen)

3. **The pattern (concrete shape):**
   - **Tuple shape (4-col):** `X(col_name, type, getter_expr, doc)`
     - `col_name`: snake_case column header string
     - `type`: int / double / string / uint64_t etc.
     - `getter_expr`: expression yielding the value at write time (caller-provided context)
     - `doc`: operator-facing description for tooling tooltips + audit
   - **Auto-generated artifacts:**
     - CSV header line: walk registry, emit `col_name,` for each → trailing comma stripped
     - CSV row writer: walk registry, emit `printf(<fmt-for-type>, <getter_expr>)` per col
     - CSV reader/parser column index map: walk registry, build `enum CalibLogCol { ... COL_COUNT }` + `static const char* col_names[] = { ... }`
     - Audit/tooling doc generator: walk registry, emit `# col_name: doc` block
   - **Format invariants:**
     - LC_NUMERIC=C pinned at writer construction (per `wire-format-byte-preservation-discipline.md` Layer 2)
     - Double precision: `%.17g` (lossless round-trip)
     - Integer: `%d` / `%u` / `%lu` per type
     - String: quoted or escaped per CSV RFC 4180 (recommend simple `"%s"` with no embedded commas/quotes; reject at write time if embedded chars present)
     - Newline: `\n` (Unix; not `\r\n`); end-of-file no trailing newline
   - **Backward compat:** column-append-only; new columns ALWAYS appended; existing columns NEVER reordered/removed; legacy parsers tolerate extra columns at end

4. **Trade-offs + when to apply:**
   - Apply when: ≥3 columns + multi-site write/read drift risk + future column additions expected
   - Skip when: 1-2 columns + stable scope; standalone debug log
   - Cost: ~2-3h to set up registry + ~20 min per added column

5. **Reference implementations:**
   - First applied: v5.14.10.D (this ship) — auto-extends 4-5 cfg=2 telemetry columns + retroactively migrates existing ~20 columns
   - Future applications: any new CSV log added to engine (paper-trade decision log, regime-classification trace log, OMS event-stream digest)

6. **Cross-references:**
   - `registry-tuple-as-single-source-of-truth.md` (parent meta-pattern)
   - `wire-format-byte-preservation-discipline.md` (CSV format Layer 2 pinning)
   - `x-macro-registry-with-presence-dispatch.md` (base X-macro shape)
   - CLAUDE.md item 13 (X-macro for multi-site additions)
   - TECH_DEBT-010 (pre-amendment sister entry)

7. **Lessons / gotchas:**
   - Column-append-only discipline: REORDERING existing columns breaks legacy parsers silently. NEVER reorder. NEVER delete (use _DEPRECATED suffix + retain emit for ≥2 ships before final removal).
   - `getter_expr` refers to caller-provided context (e.g., `oms->total_realized` at the writer site); registry tuple references symbols that must be in scope at use site
   - Type coercion: tuple's `type` column doesn't auto-cast; getter_expr must yield correct type (or use explicit cast in expr)
   - Operator-facing CSV header: `col_name` should be snake_case + no spaces (pandas `df['col_name']` access pattern); `doc` is the human description (not header)

8. **Audit detection:**
   - Symptom: CSV writer adds `printf(...)` column without registry entry
   - Symptom: CSV reader/parser hardcodes column index without registry walk
   - Symptom: 3+ columns added in single ship without registry consideration

9. **Variants — future considerations:**
   - **5-col extension:** add `display_label` column when GUI calib panel ships (post-v5.14.10) — operator-facing column header in panel UI vs CSV-internal `col_name`
   - **6-col with `severity`:** for failure-mode-style columns where rendering color depends on threshold
