## NEW DOD concerns

### Concern 1: BootGlobal non-const ControllerConfig<F>& signature (MINOR)

**Severity:** LOW. **Source:** API surface review.

BootGlobal mutates `cfg.cores[c].fee_rate_*` in-place for BNB discount (per C1). This requires signature `ControllerConfig<F>& cfg` (not const). All OTHER helpers take `const ControllerConfig<F>& cfg`.

**Risk:** Future contributor sees BootGlobal's mutable cfg signature, copies pattern to a new helper, inadvertently allows cfg mutation in a helper that shouldn't mutate. Slippery slope away from const-cfg discipline.

**Mitigation:** Plan body Decision A v1.2 § Split 1 should add explicit signature documentation:
- "BootGlobal takes mutable `ControllerConfig<F>&` because BNB discount is applied in-place at boot. This is the ONE EXCEPTION to const-cfg discipline. All other helpers (BootPerCore + SlowPathCycleOneCore + SlowPathCycleAllCores) take `const ControllerConfig<F>&`."

Alternatively: extract BNB discount to its own helper `EngineCommon_ApplyBnbDiscount(ControllerConfig<F>& cfg)` per blindspot B14.2 v1.0 recommendation. Then BootGlobal can take const cfg + caller invokes ApplyBnbDiscount separately before BootGlobal. Tradeoff: more helpers (now 5) vs cleaner const-discipline. Plan body operator decision — both are GREEN-DOD; operator preference.

**My recommendation:** Document the exception at Decision A signature comment block (cheaper than 5th helper). Sister-pattern strengthens by exception-with-rationale rather than proliferation.

### Concern 2: SlowPathCycleOneCore body size

**Severity:** LOW. **Source:** Helper API surface review + plan body line 361 (~200-350 LOC estimate).

200-350 LOC slow-path-only helper body × 2 template instantiations (live F=64 + backtest BACKTEST_FP) × 4-6 call sites + inlining = ~2000-5000 LOC of generated code per binary (per blindspot B5 estimate). Slow-path body OK at this size, but verify L1i cache pressure at /post-ship-audit (CodeMetrics_StaticFnSize hint).

**Mitigation:** None required PRE-coding. Verify at /post-ship-audit post-`.B.4` ship. If L1i pressure measured, consider sub-helper extraction. Already noted in plan body Pre-coding concerns (deferrable).

### Concern 3: AllCores wrapper for-loop = future code-motion opportunity

**Severity:** LOW. **Source:** Forward-looking.

AllCores wrapper is ~10-15 LOC. If future ML latency tightening surfaces, the for-loop could be vectorized (SIMD-style multi-core processing). Per-snapshot-cluster-layout-pattern's "cache-warm reader access" property would benefit. Note for `.F.5.C` or v6.0 viewer split when AllCores becomes the canonical fan-out boundary.

**Mitigation:** None required at .B.4. Document at FEATURE_LOOKUP "Related" section for future ship handover.
