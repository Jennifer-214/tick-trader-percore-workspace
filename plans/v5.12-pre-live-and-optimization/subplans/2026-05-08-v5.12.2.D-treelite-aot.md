## Theme

Treelite (or in-house transpiler) emits `inference.h` per model.
Engine load path prefers compiled `.h` symbol if present, falls back
to XGBoost C API. Brings single-row inference from ~1-5μs to <100ns.

**Per-handle composition layer** (Phase 3.A composite-signal extractor
+ Phase 3.B mixed-output normalizer) sits ABOVE this — they call
`Model_Predict`; this ship just changes what `Model_Predict` calls
internally. Clean ordering: ship Phase 2.D first if AOT compiled,
THEN Phase 3 layers compose above; OR ship Phase 3 first against C
API, THEN Phase 2.D swaps the backend transparently. Either works.

**Re-trigger justification:** v5.12 includes the composite-signal
extractor (Phase 3.A) and mixed-output normalizer (Phase 3.B). Both
extend `Model_Predict` (`ML_Headers/ModelInference.hpp:507`); AOT
compile is a natural co-traveler since the per-handle composition
layer is cleaner above a trait-bounded predictor than an external
library call.

## Phase C — `Model_Predict` backend dispatch (`v5.12.2.D.3`)

**Goal:** `Model_Predict` at `:507` checks `m->backend` and dispatches.
Default = C API; BACKEND_AOT routes to `Model_Predict_AOT`.

**Step 0:** Modify `Model_Predict`:
```cpp
template <unsigned F>
inline float Model_Predict(ModelHandle<F>* m,
                           const float* features, int num_features) {
    if (m->backend == BACKEND_AOT) {
        return Model_Predict_AOT(m, features, num_features);
    }
    // existing C API path unchanged below
    // ...
}
```

This is the SINGLE site where backend selection happens. Phase 3.A
(composite-signal) and Phase 3.B (normalizer) call `Model_Predict`
above this dispatch — they don't see the backend distinction.

**Tests** (+2): predict path with BACKEND_AOT routes to AOT (verify
via mock that Model_Predict_AOT is called); predict path with
BACKEND_XGBOOST_C_API uses existing path bytewise unchanged.

**Tag:** `v5.12.2.D.3`.

## Phase D — `aot_compile_model.sh` operator tool (`v5.12.2.D.4`)

**Goal:** Operator-side script. Takes `models/<name>.json` (XGBoost
JSON), invokes treelite to compile to `models/<name>.aot.so`,
computes SHA-256, prints stamp-body fields the operator can paste
into the stamp:

```bash

# Emits <model>.aot.so + prints stamp body extension fields.
# v5.12.2.D
```

**Tests** (+1): tool roundtrips a known XGBoost model → AOT compiled
→ predicts within tolerance.

**Tag:** `v5.12.2.D.4`.

## Final tag — `v5.12.2.D`

**Train-serve parity gate (1000-feature):** AOT compiled prediction =
XGBoost C API prediction within `1e-6` ABSOLUTE epsilon, across 1000
random feature vectors. Test in `tests/parity_harness.cpp`. If
divergence > epsilon: REFUSE to load (reject at boot, error message
points to operator-recompile workflow).

**Operator-validation:**
- Train a model (existing workflow)
- Run `aot_compile_model.sh` to produce `.aot.so` + stamp fields
- Re-stamp the model with AOT fields included
- Set `cfg.use_aot_inference=1`
- Run engine; verify boot log shows `BACKEND_AOT` selected
- Run a paper-test session; final predictions match a parallel C
  API run within tolerance (some sessions for confidence)

## Accounting for next ships

**Phase 3.A (composite-signal):** orthogonal layer ABOVE
`Model_Predict`. The composite extraction reads `out_result[i]` —
both BACKEND_AOT and BACKEND_XGBOOST_C_API populate `out_result`
the same way. No interaction.

**Phase 3.B (mixed-output normalizer):** ditto — calls
`Model_Predict` (which is backend-dispatched). Normalizer sees the
prediction value, not which backend produced it.

**Phase 3.C (per-core time-exit):** orthogonal.

**Phase 3.D (feature_mask):** orthogonal — feature_mask runs at
PACK time (`Features_PackAll`), the masked feature vector is then
passed to Model_Predict (whichever backend). No interaction.

**Phase 4 (PRIVATE):** depends on Phase 3.A/B; AOT compile is a perf
win underneath but doesn't affect strategy hypotheses.
