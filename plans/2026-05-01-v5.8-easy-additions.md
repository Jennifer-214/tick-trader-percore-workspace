# v5.8 — Easy Additions sweep

**Date:** 2026-05-01
**Theme:** every category in the codebase where "add one thing"
requires touching N sites becomes a one-line X-macro append.
**Pre-req:** v5.6/v5.7 paper-validated + merged.
**Branch:** `feat/v5.8-easy-additions` from main.

This is a refactor sprint, not a feature sprint. No new operator-
visible behavior. Every change is "the same thing, with fewer
places to forget to update."

The ML hardening work (feature standardization, leakage sentinels,
WF stability) becomes v5.9, built on top of v5.8's feature registry
indexed by stable FeatureId.

---

## Why now

Two forcing functions converged:
1. **Strategy plug-and-play idea was parked** in
   `DOCS/STRATEGY_REFACTOR_IDEAS.md` waiting for the "next strategy
   add" trigger.
2. **Feature registry needed** for v5.9 ML hardening (standardization
   + leakage + stability all index by FeatureId).

Both want the same X-macro idiom. Doing them together = one refactor
sprint, two registries with the same shape, and the codebase gets a
consistent extensibility pattern.

`STRATEGY_REFACTOR_IDEAS.md` trigger conditions are met: rather than
wait for a 6th strategy, we batch-fix multiple categories at once.
Better leverage.

## Phase 0 — Audit + standardization specs (~5h)

Two outputs from this phase, not just one:

### Output A — extensibility audit

Catalog every category in the codebase where adding a "thing"
requires touching multiple sites. For each: count current touch
points, score frequency × touch-points = pain rank.

Expected categories from initial scan:

| Category | Touch points today | Frequency | Pain rank |
|---|---|---|---|
| Strategy | 8 | every 6 months | HIGH |
| ML feature | 5-7 | every v5.x ML ship | HIGH |
| SHALT_* code | 4 | every strategy filter ship | HIGH |
| Controller halt_reason | 3 | every controller gate ship | MEDIUM |
| Regime | 5 | rare | MEDIUM |
| Cfg field | 4-5 (parse + default + struct + example.cfg) | very frequent | MEDIUM (already CFG_PARSE_* macros) |
| GUI panel | 4 | rare | LOW |
| Health log category | 2-3 | rare | LOW |
| Backtest metric kind | 3 | rare | LOW |
| Snapshot field | 3 | every visibility ship | LOW (each is genuinely different) |

**Output:** `DOCS/EASY_ADDITIONS_INVARIANTS.md` listing each category,
its current touch-point count, the proposed X-macro shape, and the
post-refactor count. Bias toward batching the HIGH+MEDIUM categories
in this sprint.

### Output B — canonical signature specs + plug-and-play recipes

These docs go in `DOCS/` and are the ENFORCEMENT mechanism for the
"adding one thing = drop a header + 1 X-macro line + recompile"
contract. Without them, the X-macros work but adding new things
still requires reading existing strategies/features to figure out
the right shape.

**`DOCS/STRATEGY_INTERFACE.md` (update existing):**

Section 1 — canonical signatures:

```cpp
// Per-core state. Fields strategy-specific; struct itself is
// owner-managed by Strategy_InitPerCore / Strategy_FreePerCore.
template <unsigned F>
struct <Name>State {
    // ... strategy-specific fields ...
};

// Init: called once per core at registration. Allocates state,
// sets up rolling-stat seeding, etc. Caller-allocated state ptr.
template <unsigned F>
inline void <Name>_Init(
    <Name>State<F>* state,
    const RollingStats<F>* rolling,
    BuySideGateConditions<F>* buy_conds);

// Adapt: called per slow-path cycle. Updates state from rolling
// stats + portfolio feedback. Drives any adaptive behavior
// (regression-driven offset shift, idle squeeze, etc).
template <unsigned F>
inline void <Name>_Adapt(
    <Name>State<F>* state,
    FPN<F> current_price,
    FPN<F> portfolio_delta,
    uint16_t active_bitmap,
    const BuySideGateConditions<F>* buy_conds,
    const ControllerConfig<F>* cfg);

// BuildParameters: called per slow-path cycle. Emits gate parameter
// pack consumed by the hot path via seqlock. THIS IS THE CONTRACT
// WITH THE HOT PATH.
template <unsigned F, unsigned W = 128>
inline void <Name>_BuildParameters(
    const RollingStats<F, W>* rolling,
    const ControllerConfig<F>* config,
    FPN<F> allocated_balance,
    GateParameters<F>* out,
    <Name>State<F>* state = nullptr);

// ExitAdjustSharded: called per slow-path cycle for active positions
// owned by this core. Writes ratchet_sl / ratchet_tp via the
// Strategy_WriteRatchetSL / Strategy_WriteRatchetTP helpers (which
// apply the v5.1.7 fee-floor cap automatically).
template <unsigned F, unsigned W>
inline void <Name>_ExitAdjustSharded(
    EventLoopState<F>* state,
    int slot,
    <Name>State<F>* strat_state,
    FPN<F> current_price,
    const RollingStats<F, W>* rolling,
    const ControllerConfig<F>* cfg);
```

Section 2 — recipe (the plug-n-play part):

```
TO ADD A NEW PUBLIC STRATEGY "Foo":

1. Create file: Strategies/Foo.hpp
   Copy template from DOCS/STRATEGY_TEMPLATE.hpp
   Replace <Name> with Foo, fill in strategy-specific logic.

2. Add one line to FOREACH_STRATEGY(X) in StrategyInterface.hpp:
   X(FOO, "FOO", "Foo", FooState, \
      Foo_Init, Foo_BuildParameters, Foo_Adapt, Foo_ExitAdjustSharded)

3. Add color: append one ImVec4 to strat_colors[NUM_STRATEGIES] in
   GUI/DashboardPanels.hpp (only manual touch site remaining)

4. Run: ./build.sh test
   Pass = compiled + dispatched correctly.

5. Optional: add cfg.example entry: # core_0_strategy=foo

DONE. ~3 sites total (was 8+).

TO ADD A PRIVATE STRATEGY:
Same recipe but file goes in Strategies/private/Foo.hpp and the
X-macro line wraps in #if __has_include("private/Foo.hpp").
```

**Auto-generated from this:**

- `STRATEGY_*` constants
- `NUM_STRATEGIES` (compile-time count via macro recursion or

- `STRATEGY_SHORT_NAMES[]` array
- `STRATEGY_FULL_NAMES[]` array
- `Strategy_BuildParameters` dispatcher (switch generated from X-macro)
- `Strategy_InitPerCore` dispatcher
- `Strategy_AdaptPerCore` dispatcher

- Compile-time hash for fingerprint contribution

**Adding a strategy becomes:**
1. Implement strategy file with conventional function names
2. Append one line to `FOREACH_STRATEGY(X)`
3. Compile

**Tests:**
- All 5 existing strategies still pass their tests after migration
- Adding a synthetic 6th strategy via X-macro line + stub functions

- Conditional include of `private/EmaCross` works in both modes

**Effort:** ~8h migration of 5 existing + ~2h tests = 10h.

- Macro errors are noisy. Mitigate by keeping each X-macro entry

## Phase 2 — Feature X-macro registry (v5.8.1)

Already discussed — same X-macro idiom for ML features.

**X-macro shape:**

```cpp
// ML_Headers/FeatureRegistry.hpp
#define FOREACH_FEATURE(X) \
    X(EMA_SMA_SPREAD,  "ema_sma_spread",   1, ML_Compute_EmaSmaSpread,  "EMA - SMA / stddev") \
    X(SHORT_R2,        "short_r2",         1, ML_Compute_ShortR2,       "R² short-window") \
    X(ROR_SLOPE,       "ror_slope",        1, ML_Compute_RorSlope,      "regression-on-regression") \
    X(BOOK_IMBALANCE,  "book_imbalance",   1, ML_Compute_BookImbalance, "(bid - ask) / total") \
    X(FLOW_EWMA_10S,   "flow_ewma_10s",    1, ML_Compute_FlowEwma10s,   "signed flow 10s") \
    X(LARGE_TRADE_Z,   "large_trade_z",    1, ML_Compute_LargeTradeZ,   "z trade size") \
    X(SPREAD_Z,        "spread_z",         1, ML_Compute_SpreadZ,       "z spread bps")
```

**Pre-req:** define `FeatureComputeCtx<F>` bundling all inference
inputs (rolling stats, EMA, ROR, flow, depth, spread, large trade).
Each compute fn takes ctx, reads what it needs, returns FPN<F>.

**Auto-generated:**
- `enum FeatureId` with stable IDs
- `FEATURE_NAMES[]` for stamps + GUI
- `FEATURE_REGISTRY[NUM_FEATURES]` with metadata
- `FEATURE_REGISTRY_HASH` (fnv-1a over name+version, contributes to
  fingerprint)
- `Features_PackAll(ctx, out_array)` — replaces `ModelFeatures_Pack`

**Adding a feature:**
1. Implement `ML_Compute_FooFeature(ctx) -> FPN<F>`
2. Append one line to `FOREACH_FEATURE(X)`
3. Compile. Old models force-invalidate via fingerprint mismatch.

**Drift detection test (load-bearing):**

Four tests in `// === EXTENSIBILITY ===` section:

1. `FEATURE_REGISTRY_HASH != 0` — sanity
2. Stamp built from current registry → loads successfully — round-trip
3. Stamp with mutated hash → load rejected — drift detection
4. `FEATURE_REGISTRY_HASH == EXPECTED_SNAPSHOT_HASH` — pinned snapshot test
   - Any change to `FOREACH_FEATURE(X)` flips the hash and fails this test
   - Developer must update the snapshot value, acknowledging "yes I'm
     changing the model contract" — forces retrain decision
   - This is the test that *enforces* the train-serve contract

**Pre-requisites added to plan:**
- **Bump `MODEL_FORMAT_VERSION` 4 → 5** (otherwise load check at
  `ModelInference.hpp:277` won't fire on old models)
- **Add `feature_registry_hash` field to stamp body** alongside
  existing fields. Sign via HMAC like the rest of the body.
- **Persist a `EXPECTED_REGISTRY_HASH_SNAPSHOT` constant** in
  `tests/controller_test.cpp` for the drift snapshot test.

**Effort:** ~8h migration of existing implicit features + ~3h tests
+ ~1h stamp body extension + ~1h MODEL_FORMAT_VERSION bump =
**~13h** (revised from 10h).

**Commit + tag:** `v5.8.1`

## Cross-cutting invariants

0. **No silent orphan regressions** (v5.4.0 lesson). Naming
   divergences between X-macro lines and actual function names
   compile-fail loudly (good). But function-pointer table can
   silently dispatch to the WRONG variant of a function if multiple
   variants exist (legacy stub vs state-aware sharded version).
   Prevention measures embedded in each phase below; cross-cutting
   discipline:

   - Each X-macro line's function references are **copied exactly
     from the existing dispatcher's switch statements**, not deduced
     from function naming patterns
   - `tools/calls_graph_diff.sh` runs BEFORE and AFTER each phase
     ships; any orphan flagged blocks the tag
   - Phase 0 audit produces a "canonical signatures" doc; any
     strategy whose lifecycle functions don't match canonical gets
     refactored in Phase 0.5 BEFORE X-macro can be written
   - Tests in `// === EXTENSIBILITY ===` walk every `FOREACH_*(X)`
     entry and assert each function pointer is non-null + dispatches
     correctly. Loop test prevents "added strategy to code but
     forgot to add to X-macro" silent failures.
   - Variant function naming: if multiple versions of a function
     exist (e.g. `_BuildParameters` + `_BuySignal` legacy stub),
     resolve which one is canonical for the X-macro **before**
     writing the macro, not during. Document choice in
     `STRATEGY_INTERFACE.md`.

1. **Existing 5 strategies continue to dispatch correctly.** No
   behavior change — refactor only.
2. **Existing models continue to load** OR force-invalidate via
   fingerprint mismatch. Both are valid; whichever you pick, the
   stamp body must reflect it (FEATURE_REGISTRY_HASH change forces
   retrain).
3. **Public/private split preserved.** `Strategies/private/EmaCross`
   conditional include via `__has_include` continues to work. Public
   release snapshot drops the line, dispatcher auto-omits the case.
4. **Hot path UNTOUCHED.** Registries are dispatch tables consulted
   on slow path; no per-tick cost.
5. **Each phase tagged + pushed before starting next.** Per-phase
   discipline (filesystem-crash incident lesson).
6. **Test count preserved or improved.** No tests deleted; existing
   behavior tests must still pass post-refactor.

## Risk assessment

**LOW risk overall — pure refactor with conservative migration:**

- No new operator-visible behavior
- Tests preserved, run before each commit
- Each phase independently revertable
- Hot path untouched (no per-tick changes)
- Models continue working OR force-invalidate cleanly via
  fingerprint hash bump
- Public/private split preserved via conditional includes

**Specific risk: macro debug noise.** Compiler errors in X-macro-
expanded code can be cryptic. Mitigation: keep each X line on its
own row, use clear naming, write tests that exercise the full
dispatch path so errors surface during testing not in production.

**Specific risk: existing strategies' function signatures don't
match conventional shape.** Mitigation: identify in Phase 0 audit;
either widen the X-macro spec to handle variants, or refactor
non-conforming strategies first (small change, ~1h each).

## Trigger conditions to pause / reorder

- **A real bug shows up in v5.6/v5.7 paper testing** → fix it before
  starting v5.8. Refactor sprint should not interleave with bugfix
  sprints.
- **A strategy or feature needs to land before v5.8 finishes** → add
  it via the OLD pattern, then refactor it into the registry during
  the relevant phase.
- **`/readiness` finds the macro pattern doesn't fit a category** →
  defer that category to v5.8.x bug-fix phase or skip it entirely.

## What this enables

After v5.8 ships:

- Adding a new strategy = 1 X-macro line + 1 file (down from 8 sites)
- Adding an ML feature = 1 X-macro line + 1 compute function (down
  from 5-7 sites)
- Adding a SHALT code = 1 X-macro line (down from 4 sites)
- Adding a halt reason = 1 X-macro line (down from 3 sites)
- Adding a regime = 1 X-macro line + classifier logic (down from 5
  sites)

The codebase becomes plug-and-play across the categories that
matter. Future you spends less time grumbling at "I forgot to
update the GUI mirror." Past-you's idiom (the per-core override
X-macro from v5.0.x) becomes the codebase's standard.
