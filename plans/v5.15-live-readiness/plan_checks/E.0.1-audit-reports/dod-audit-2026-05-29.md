## Q1 — H10: is excluding FromDouble/ToDouble from the determinism gate DEFENSIBLE? (PRIORITY)

**Verdict: GREEN — the exclusion is DEFENSIBLE and correctly reasoned. It is NOT an H10 violation being waved through.**

The crux is understanding what H10 actually asserts and what the gate actually guards.

**H10 reads:** "AVX-512 SIMD kernels MUST have a scalar fallback producing BYTEWISE IDENTICAL output." Generalized: *two implementations of THE SAME mathematical function selected by a build flag must agree byte-for-byte.* The invariant is **same-function ⇒ same-bytes**, so that the build-time choice (native vs generic; SIMD vs scalar) is observationally invisible. That is exactly what F-056 fixes for sqrt: native sqrt and generic sqrt purport to compute the same function (√x to FPN<64> precision) but disagree → real H10 violation → correctly removed (native specialization deleted; both paths collapse to the one deterministic NR).

**Why FromDouble/ToDouble are different in kind, not merely tolerated.** `FPN_FromDouble` and `FPN_ToDouble` are **not two implementations of one function** — they are *lossy boundary conversions* between an IEEE-754 double (≈52-bit mantissa) and a 4096-bit fixed-point value. Once tests build the shipped flags (F-057), there is only ONE FromDouble in the binary — the native one. Generic FromDouble is **never linked into any shipped target** (verified: every production target sets `USE_NATIVE_128`). So there is no "two paths must agree" obligation to satisfy: the generic version is dead code in production. H10's same-function-same-bytes premise requires *two live paths of the same function*; post-F-057 there is one. The plan's R1 names this precisely: native FromDouble "inherently touches `double` in BOTH paths (nothing to delete down to a double-free version, unlike sqrt → deterministic NR)."

**The actual H10 obligation for FromDouble/ToDouble is cross-run/cross-binary determinism of the SINGLE shipped path — and the plan demands exactly that.** Acceptance criterion (b) — "shipped native path cross-run/cross-binary byte-deterministic (run 2×/2 opt-levels)" — IS the H10/H9 guard for FromDouble/ToDouble. Native `FP64_FromDouble` (`FixedPoint64.hpp:33-45`) is `floor` + integer-cast + `frac×2⁶⁴`-truncate: pure IEEE-754 deterministic ops, no `sqrt`/transcendental/locale dependence → deterministic across runs and `-O` levels on the x86 target. The gate covers it; it just isn't a *native-vs-generic equality* assertion, because that comparison is meaningless once generic is unlinked.

**Why a blanket "all-ops native==generic" gate would be the WRONG design (and the plan is right to reject it).** A naïve all-ops ±`USE_NATIVE_128` equality harness would RED on FromDouble/ToDouble for a *legitimate* algorithm difference, conflating "two dead-code-divergent conversions" with "a live non-determinism." That false-RED would either block the ship or pressure someone to force the two conversions into bytewise agreement — pointless work on a path where only one version ships. The plan's scoping — *sqrt-scoped* ±native diagnostic (the RED→GREEN signal that proves F-056) PLUS *single-path* cross-run/cross-binary determinism for everything shipped — is the correctly-decomposed H10 enforcement. This is **proportionate-response** discipline (`feedback_proportionate_response_to_audit_findings`): the gate matches the actual invariant per op-class rather than over-asserting a uniform rule.

**One residual the plan should make a hard pre-condition (not a blocker, a sharpening).** The defensibility of excluding FromDouble/ToDouble from the equality leg rests entirely on the claim "no shipped target builds generic `FPN<64>`." The plan asserts this (R1: "consistently used post-F-057 (no target builds generic)"). I verified it for the four C++ executables in `CMakeLists.txt`. **Recommend** the determinism CI gate include a one-line grep/assert that NO target compiles `FPN<64>` paths without `USE_NATIVE_128` (i.e., the F-057 enrollment is total, including any future test target) — this converts the exclusion's load-bearing premise into a *standing mechanical guarantee* rather than a point-in-time manual check. This is the candidate Class "Tested-path ≠ shipped-path" guard the plan already proposes (grep-CI asserting test targets carry prod FP flags) — I'm noting it must also forbid *new* generic-FPN<64> targets, not just enroll today's two. **Severity: LOW (sharpening; the plan's structural guard already 90% covers it).**

**Net:** the H10 gate is designed as a proper H10 guard. Excluding FromDouble/ToDouble from the *equality* leg is correct because post-F-057 they are single-path; the *determinism* leg (cross-run/cross-binary) is the H10/H9 obligation that applies to them and the plan demands it. **No BLOCKING gap.**

## Q2 — H13: is `memcpy` the correct H13-aligned fix for the F-058 pointer-pun?

**Verdict: GREEN — `memcpy` is correct. H13 / the type-trait-dispatch spec does NOT prescribe `tt::` dispatch here; that would be a category error.**

H13 forbids `*reinterpret_cast<T*>((char*)cfg + offset) = v` — **type-erased, registry-driven, typed-FIELD dispatch** where a Kind/offset token is used to write into a field of unknown-at-the-cast-site type. The canonical antidote (`type-trait-dispatch-via-tt-namespace.md`) is about exactly that surface: X-macro registry dispatchers (parse/save/render/drift-check) over heterogeneous typed fields, where `tt::<verb>_field<T>` deduces T from a field reference so the Kind enum can't drift from storage. The doc's whole apparatus — 3 barriers, `is_FPN_v`, static_assert type-family guard — is meaningful *only* when there is a registry + a Kind token + many field types.

F-058 is **none of that**. `_to_fp64`/`_from_fp64` reinterpret a fixed `FPN<64>` (`uint64_t w[2]` region) as a fixed `__uint128_t` — a single, known, compile-time-fixed type pair, no registry, no Kind, no field-address arithmetic. The hazard is **strict-aliasing + alignment UB on a raw byte-reinterpretation**, not type-erased dispatch. The standard-blessed fix for "reinterpret these bytes as that POD type" is precisely `memcpy` (or C++20 `std::bit_cast`) — the compiler lowers it to the same `mov` at `-O2+`, zero cost, UB-free. `tt::` dispatch would be nonsensical here: there is no type to deduce and no registry to walk.

The plan's own framing is exactly right — it files F-058's structural guard as "**sister to H13** type-trait dispatch" (a grep-CI for `*(T*)other` pointer-cast puns + `-fstrict-aliasing` clean), not as an H13 application. Sister, not instance. The type-trait-dispatch spec is correctly NOT applied. (`std::bit_cast` would be an even-tighter idiom if the codebase were C++20-min, but `memcpy` is the canonical zero-cost choice and matches existing codebase convention; no objection.)

**No gap.**

## Q3 — H5: is `tt::parse_double_fast_advance` the canonical H5-compliant primitive, and is it `from_chars`/fast_float (not a scalar loop)?

**Verdict: GREEN — confirmed canonical and confirmed `std::from_chars`-backed.**

`ParseFast.hpp:78-85`: `parse_double_fast_advance` is a thin wrapper over `std::from_chars(p, p+n, v)` with a strtod-style `*end_out` advance and the same "no number consumed ⇒ end==p, returns 0.0" sentinel strtod callers already test. The file header (`:12-30`) documents the rationale: `from_chars` is the libstdc++ Lemire-style algorithm that *informed* the C++17 standard (i.e., it IS fast_float in libstdc++ ≥11), ALWAYS uses the C locale per the standard (locale-immune), and is branchless on well-formed inputs. No scalar character loop. This is precisely the primitive H5 mandates ("use `simdjson`/`fast_float`/`tt::parse_double_fast`") and the plan's own required-reading cites `CoreFrameworks/ParseFast.hpp`.

The plan applies it as a **near-1:1 drop-in** for the `strtod(p,&p)` sites (`BacktestEngine.hpp:88-89,95-96`; `DepthReplayState.hpp:224-227`) — same parse-and-advance shape, no restructure. This correctly **extends H5 from "parser inner loops" to the replay/backtest path** and closes a real single-source-of-truth asymmetry: LIVE already parses via `from_chars`; replay used `strtod`. The plan's candidate Class "locale-dependent numeric parse on a determinism/replay-critical path" + grep-CI for `strtod`/`atof` on replay/wire paths is the right structural guard.

**No gap.** (Minor: F-107 — calib/trade-log `LC_NUMERIC` on the *emit* side — is correctly dispositioned as output-only/not-net-gating → PRE-PAPER-TEST; consistent with H9's emit-locale-pinning being a separate concern from H5 parse.)

## Q4 — H11: is the generic NR `FPN_Sqrt` (`:873`) — now the sole path — constant-iter + branchless within the reduction?

**Verdict: YELLOW — constant-iter YES; but the kernel carries two data-dependent branches the plan does NOT note. Not a determinism risk; a latency-discipline/H11 note the plan should add.**

Reading `FixedPointN.hpp:873-902`:
- **Iteration count is CONSTANT** — exactly 12 NR iterations (`for i=0..12`), `#pragma GCC unroll`. ✅ This is the load-bearing H11 property and it holds. The reduction itself (`q = Div; y = Mul(Add(y,q), half)`) is straight-line, no inner branch. ✅ Determinism is NOT at risk — the result is bytewise-fixed for a given input.

But two data-dependent branches exist OUTSIDE the strict reduction:
1. **`:874`** — `if (FPN_MagIsZero(value) || value.sign != 0) return FPN_Zero();` — early-return guard (data-dependent branch + control-flow divergence).
2. **`:882`** — inside the bit-scan loop: `if (value.w[i] != 0 && top_bit < 0)` — a per-word branch to find the top set bit (variable-cost depending on where the MSB lands).

Per `branchless-math-kernel-pattern.md` (which exists *precisely* because of a sqrt-adjacent pushback: *"shouldnt we have all calculations like this be branchless? variable latency is bad"*) and H11/H20, the canonical shape pre-zeroes state and uses masks/`__builtin_clzll`-driven branchless seed selection rather than an `if`-guarded scan. The `:882` loop in particular has **variable latency** (the `branchless-math-kernel-pattern.md` problem-statement shape #1/#2).

**Why this is YELLOW not RED:** (a) FPN_Sqrt is **slow-path/feature-only** (FlowFeatures/FeatureRegistry/RidgeBlender/ModelInference — verified, never in ExecutionCore/OrderGates), so the hot-path p99 budget (H8) is untouched; (b) the branches are **input-data-dependent but DETERMINISTIC** — same input ⇒ same branch ⇒ same bytes, so the H10/determinism gate this ship installs is NOT compromised. The concern is purely H11/H20 *latency-variance discipline* on a slow-path kernel that this ship is **promoting to the sole sqrt path** — exactly the moment to note it.

**Recommendation (non-blocking):** add one line to the plan's F-056 fix-design (or Honest Risks) acknowledging that the now-sole generic `FPN_Sqrt` retains a data-dependent early-return (`:874`) + a variable-cost bit-scan branch (`:882`), that this is **acceptable** (slow-path, deterministic, within H11's constant-iter core) but is a **documented branchless-math-kernel-pattern deferral** (file a LOW TECH_DEBT with `branchless-math-kernel-pattern.md` cross-ref). The plan currently claims "deterministic Newton-Raphson" without noting the residual branches — accurate on determinism, silent on the latency-variance discipline. This satisfies `feedback_future_headache_vs_optimization_scope_framework` (pure-perf on slow path → defer + document, don't fold). **Severity: LOW.**
