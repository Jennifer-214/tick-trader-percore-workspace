## Decisions worth remembering

### Decision 1: Option Z architectural sprint mid-flight

**Context:** During v5.14.5.B coding, three compounding architectural
surprises surfaced for `regime_class_onehot`:
1. Class 17 — plan claimed `current_regime` lived on `RegimeSignals`;
   actually on `RegimeState` (verified via `rg`).
2. Cascade scope — back-filling into `RegimeSignals` would touch 4
   `Regime_ComputeSignals` callers + per-caller state-source plumbing.
3. Architectural limitation — `Regime_Classify` was AUTO-mode-only
   gated; ML cores would never have hysteresed `current_regime`.
4. Train-serve parity gap — BacktestSharded had no RegimeState; ML
   models would train on `current_regime=0` constant and serve with
   actual values. Silent PARITY-013 candidate.

**Two paths considered:**
- **Direct patch** (~30 min): defer current_regime, ship the 2 features
  that don't need it (.B trimmed to 2 features). Bug ledger entry for
  the deferred third.
- **Option Z architectural sprint** (~3h): universalize Regime_Classify,
  add per-core RegimeState to backtest, ship all 3 features + close
  PARITY-013 risk by construction.

**Decided:** Option Z. Caramel's framing: *"i like option Z the most,
because it fixes this going forward right? same shape as the structural-
fix-preferred memory."*

**Why this was right:**
- Enables ALL future regime-context ML features (regime_persistence,
  regime_age, regime_transition_recency) without further cascades
- Closes a latent train-serve parity gap before it surfaces
- Cost: ~+100ns slow-path/cycle/non-AUTO core (within budget;
  documented in HOT_PATH_CHANGELOG with 3 optimization paths)

**General lesson:** when a "small" feature fix surfaces multi-site
plumbing OR a latent parity gap, the structural fix that closes the
class is almost always the right call — even at 6× the immediate
effort. The memory `feedback_structural_fix_for_recurring_class.md`
applies to MORE than just X-macro registries; it applies to any
"this could recur if I just patch the visible instance" decision.

### Decision 2: Hysteresis Option A — cfg-driven single source of truth

**Context:** Pre-existing inconsistency surfaced during the
universalization audit:
- `ControllerEventLoop.hpp:619` hardcoded `Regime_Init(state, 3)`
- `engine.cfg.example` documented `regime_hysteresis=5`
- Operators reading docs expected 5; actual behavior was 3

**Three paths considered:**
- **Option A:** cfg-driven single source of truth. Behavior change:
  default switches to 5 (matches docs). Migration: operators set
  `regime_hysteresis=3` for pre-v5.14.5 behavior.
- **Option B:** keep hardcoded 3, update docs to match. No behavior
  change but locks operators out of tuning.
- **Option C:** add cfg field with default 3, preserve current behavior.
  No behavior change, operators can tune, docs already match cfg shape.

**Decided:** Option A. Caramel: *"yeah lets go with A"*.

**Why this was right:**
- Aligns reality with documentation (operators reading docs got the
  expected behavior)
- Single source of truth (cfg) trivially parity-safe between live + backtest
- Future operators tune per-deployment without code change
- The behavior change is operator-visible + documented in CHANGELOG

**General lesson:** when audit surfaces a "the code says X but docs
say Y" divergence, prefer aligning code to docs (option A-shape) over
aligning docs to code, ESPECIALLY when the discrepancy is hardcoded.
Hardcoded values block future tuning; cfg-driven values don't.

### Decision 3: Path C with discipline + TECH_DEBT-007 escape hatch

**Context:** v5.14.5.B's `regime_trend_strength` + `regime_vol_zscore`
have semantic overlap with existing SHORT_SLOPE + VOL_RATIO. The
differing normalization MAY produce complementary training signal OR
MAY train identically depending on operator's data + model architecture.

**Three paths considered:**
- **Path A** (cautious): ship only `regime_class_onehot`; defer the
  other 2 until empirical verification proves complementary signal.
- **Path B** (aggressive): ship all 3; accept the risk of redundant
  features dragging on training.
- **Path C** (with discipline): ship all 3, add TECH_DEBT-007 ledger
  entry committing to post-first-retrain feature_importance verification;
  drop redundant features in v5.X+ via FEATURE_REGISTRY_HASH bump if
  empirically not load-bearing.

**Decided:** Path C with discipline. Caramel chose this when the trade-off
was presented.

**Why this was right:**
- Avoids preemptive scope-cut on speculation about model behavior
- TECH_DEBT-007 commits to verification (won't be forgotten — auto-write
  contract per CLAUDE.local.md going-forward rule)
- Future ship has clear escape valve (FEATURE_REGISTRY_HASH bump
  retires features; same operator workflow as adding them)

**General lesson:** when a feature COULD be redundant but operator
empirical signal is what'll prove it, ship + commit to verification.
Don't speculate-cut. The ledger entry is what makes "we'll verify later"
load-bearing rather than vaporware.

### Decision 4: Sub-ship sequencing with retroactive .A commit

**Context:** v5.14.5.A's LabelFunctions.hpp changes were on disk but
unstaged when c944054 (v5.14.5.B.0) was committed. The .A tests for the
CS labels DID land in c944054 (since file-on-disk built fine), but the
LabelFunctions.hpp file itself was never committed.

**Resolution:** Committed retroactively as v5.14.5.A (`b1d0fda`) BEFORE
v5.14.5.B (`a972d2a`). Tags + log show clean .A → .B.0 → .B → .C → umbrella
sequence, even though .B.0 chronologically committed before .A.

**Why this was right:**
- Tags reflect logical dependency order (.A defines labels; .B uses them
  in features; .B.0 is architectural pre-req for .B's universal regime
  access)
- Future readers walking `git log` see the conceptual ship sequence
- No rebase / history rewrite required

**General lesson:** when you discover an uncommitted file that should
have shipped earlier, commit it retroactively with the original ship
tag rather than amending the existing commit. Preserves the audit trail.

## What surprised us

### Surprise 1: `current_regime` placement (Class 17 mirror)

Plan claimed `current_regime` was on `RegimeSignals`. Reality: lives
on `RegimeState`. Caught mid-coding when implementing the feature
populator. Required plan amendment + Option Z architectural decision.

**Structural fix:** strengthened `/trace-deps` Step 6 (struct-field
claim verification). Now any plan that claims "field X lives on struct
Y" gets verified via `rg "X" Strategies/Y.hpp` BEFORE coding. Same
class as PARITY-001-005 (production-caller field-population gap) but
at planning-time rather than code-time.

### Surprise 2: Constexpr std::array

Initial v5.14.5.C `ComputeFracDiffCoeffs(d)` returned
`std::array<double, 50>` constexpr. Build failed because `<array>`
wasn't included in FeatureRegistry.hpp. Easy fix (add #include) but
caught immediately by the compiler. Added to mental model: when
introducing constexpr STL container types, verify the include
exists in the header you're editing.

### Surprise 3: Frac diff math expectation off by 4×

Test claim: "constant-price input → frac diff near zero, |residual| < 5".
Actual residual for x=100, K=50, d=0.5: ~8 (since
|C(-0.5, 49)| ≈ 1/√(π·49) ≈ 0.08, so 100 × 0.08 = 8).

Test bound was based on "approaches 0" intuition without computing
the K-truncation residual analytically. Fixed to `|r| < 20` with
comment explaining the closed-form.

**General lesson:** when writing tests for math features, compute
the expected value analytically (or via known closed-form) — don't
rely on "should be near zero" intuition for truncated infinite series.

## What we'd do differently

### Cold-pickup completeness for the Option Z plan

The Option Z plan (`plans/2026-05-09-regime-classification-universalization.md`)
captured architectural rationale + scope but didn't fully meet the
10-field cold-pickup checklist (CLAUDE.local.md):
- ✅ Branch state (specified)
- ✅ First concrete move per phase
- ✅ Function names (Regime_Classify, Regime_Init)
- ⚠️ File:line refs (some; not all citations)
- ✅ Stale-claim audit (the Pre-existing-work-audit section)
- ⚠️ Effort claims (rough; not LOC-grounded)
- ✅ Source-audit references
- ✅ Predecessor / dependent plans named
- ✅ Tag names locked

Given the sprint shipped clean, this didn't bite us. But future
mid-coding architectural sprints should hit all 10.

### TECH_DEBT entry creation timing

TECH_DEBT-007 (empirical verification of frac diff redundancy) was
committed at the same time as v5.14.5.B's CHANGELOG entry. Better
practice: write the TECH_DEBT entry IMMEDIATELY when the architectural
trade-off is decided (Path C), not at ship-time. Minimizes risk of
forgetting + makes the trade-off visible in the ledger before the
ship lands.

### Postmortem cadence

This is the first postmortem since v5.9 ML hardening (2026-05-02).
v5.10, v5.11, v5.12, v5.13, v5.14.0-v5.14.4 all shipped without
dedicated postmortems. The CHANGELOG row format absorbed the
detail-write-up role over time, which is mostly fine — but lessons-
learned + decision rationale need a dedicated artifact when a sprint
makes architectural decisions worth referencing later.

**Going forward:** postmortems are warranted when:
1. Mid-flight architectural pivot (Option Z-shape)
2. New rule / pattern emerges that needs cross-sprint reference
3. Pre-existing inconsistency surfaced + resolved (hysteresis)
4. Plan deviated from original scope by > 30%
