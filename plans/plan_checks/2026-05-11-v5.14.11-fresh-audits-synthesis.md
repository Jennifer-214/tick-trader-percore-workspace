## Convergent findings (multiple audits agree)

### C1 — Helper extraction for two BuildCorr call sites [UNANIMOUS — 4 audits]

trace-deps DRIFT-1 + readiness YELLOW.1 + merge-scan M1 + dod-audit MEDIUM-2.

TWO BuildCorr call sites at `StrategyParameters.hpp:996` (buy, ridge_within_horizon) + `:1195` (exit, exit_blender_mode). Same ring-walk-backwards-from-head pattern; same BuildCorr → Compute pair. Adding UpdateOnline + FinalizeCorr without helper extraction creates 3rd-site mirror (recompute reset path) → Class 18 risk per CLAUDE.md item 19.

**Options:**
- (a) `RidgeBlender_BuildHistoryFromRing<F>(ring, head, count, primary_count, out)` — ring iteration only
- (b) `RidgeBlender_OnlineCycleStep<F>(ridge_state, ring, ring_head, predict_count, primary_count, cfg)` — full cycle: update + finalize + reset branch
- (c) Both fine-grained (a) and coarse-grained (b)

**Preference:** (b) full-cycle helper — same shape as v5.14.2.E.1 PostLoadSetup extraction; both call sites become single helper-call; ~30 min in v5.14.11.A.

### C2 — Embed RidgeOnlineState in RidgeWeights<F> [merge-scan M2 + trace-deps mirror-gap]

Plan's "RidgeOnlineState struct (or extension to RidgeWeights)" leaves choice open. Embed in `RidgeWeights<F>` at `ML_Headers/RidgeBlender.hpp:85`: `ezoo->ridge_state.online_*` (buy) + `ezoo_ex->exit_ridge_state.online_*` (exit) inherit automatically.

Trade-off: RidgeWeights grows ~88 bytes (mean[8] + M2[8] + outer_xy[8][8] + n + cycles_since_recompute, all double + uint64). ~5KB → ~5.1KB. Cache: still fits L2. Slow-path single-writer + single-reader per-core ezoo; no false sharing.

**Preference:** embed. Boundary-stable refactor per CLAUDE.local.md 2026-05-06 rule.

### C3 — Slow-path-gate predicate MASK_RIDGE_ONLINE_CORR_ACTIVE [readiness + dod-audit HIGH-1]

Sister to existing `MASK_RIDGE_WITHIN_ACTIVE` (v5.14.0) + `MASK_THOMPSON_ACTIVE` (v5.14.10.B) at `SlowPathGateRegistry.hpp:84-86, 91-93`. 1 new entry in `FOREACH_SLOW_PATH_GATE` (PER_CORE scope). Current 9 entries; 7 bits headroom in uint16_t.

### C4 — cfg-flag eligibility tension (cfg.ridge_online_corr → ML_CFG_FLAG?) [readiness YELLOW.2 + dod-audit Tension B]

### C5 — 1k-cycle reset (BUG + DESIGN layers) [parity-check PARITY-018 + dod-audit Tension A]

TWO problems collapsed:

**BUG layer (PARITY-018, MED):** Plan's reset (`cycles_since_recompute > 1000 → BuildCorr(...) + reset counter`) does NOT rebuild Welford `mean[]` / `M2[]` / `outer_xy[]`. Running stats keep drifting; only `corr_matrix` is refreshed. Drift bound argument silently fails. **Must fix regardless of design choice.**

**DESIGN layer:** the 1k-cycle reset is admitted-drift mitigation. Alternatives:
- (D) **Direct-patch:** keep 1k-cycle reset; add `RidgeBlender_RebuildOnlineState` helper that ALSO rebuilds Welford accumulators from current K=64 history. Closes PARITY-018. ~30 min.
- (B) **Kahan summation in Welford updates:** compensated summation; reduces drift but doesn't eliminate need for sliding-window semantics. +1h vs D.
- (C) **Sliding-window Welford:** drop oldest as new arrives; bounded drift over fixed K=64 window; no periodic reset. Structural fix per CLAUDE.md item 19. +2-3h vs D.

**Decision framework call:** recurrence count is 1 (no other Welford-style algorithm in codebase today). Direct-patch is "permitted" by structural-fix-preferred framework. Forward-looking: v5.15+/v6.0 may add online features / IC / turnover — sliding-window pattern becomes shareable.

**Preference:** (C) — sliding-window. Caramel's "harder upfront for easier future" rule + per item 16 reuse-audit (next online-stats addition reuses pattern). 1-3h delta small for a 2-3 day ship.
