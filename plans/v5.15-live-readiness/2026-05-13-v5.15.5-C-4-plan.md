## Phase D2 — Dual-registry slot-state + aggressive memory reduction [MEDIUM-RISK]

**REVISED 2026-05-13 post-merge-scan + pre-coding consult:** the literal "consolidate into FillRecord" approach (synthesis's original intent) would WORSEN cache footprint per CLAUDE.md item 28 (extending FillRecord to 152B → 3 cache lines per record vs 2 currently). The merge-scan revealed the SoA cross-slot layout is cache-optimal for the drainer's sparse close-mask iter (parallel arrays' cache lines shared across all 16 slots).

**Revised approach:** dual FOREACH registries (close the SoA mirror Class-18 class structurally without cache regression) + aggressive memory reduction via the cursed-but-safe technique catalog (apply 2 of 7 to FillRecord).

**Surface:** `CoreFrameworks/OrderManager.hpp` OMS state struct (lines ~295-385 WARM cluster region) + new registry headers in `MemHeaders/`.

### D2.A — Dual FOREACH registries (structural-only; cache-preserved)

**NEW headers:**
1. `MemHeaders/OmsSlotScalarArrayRegistry.hpp` — FOREACH_OMS_SLOT_SCALAR_ARRAY for cross-slot SoA scalar arrays (small ≤8B fields with sparse close-mask access pattern)
2. `MemHeaders/FillRecordFieldRegistry.hpp` — FOREACH_FILL_RECORD_FIELD for FillRecord struct fields (large or paired with FillRecord access pattern)

**Existing fields routed:**
- `last_realized_return[16]` → FOREACH_OMS_SLOT_SCALAR_ARRAY (sparse-access, 8B, cache-shared across slots)
- `last_exit_predicted_p[16]` → FOREACH_OMS_SLOT_SCALAR_ARRAY (same)
- `last_exit_predicted_meta[16]` → FOREACH_OMS_SLOT_SCALAR_ARRAY (1B per slot; multi-bit packed within byte; per `multi-bit-state-encoding-pattern.md`)
- All current FillRecord fields → FOREACH_FILL_RECORD_FIELD

**AUTOPOPULATE:** `OMS_PER_SLOT_INIT(oms, slot)` macro walks both registries to init/reset all per-slot state for a given slot (per `autopopulate-pattern-for-production-caller-class.md`).

**Net cache footprint:** **UNCHANGED.** FillRecord stays 128B; parallel arrays preserved at current sizes. The win is STRUCTURAL — future per-slot fields go through the registry decision-tree (per `slot-state-foreach-registry-with-storage-routing.md`); the SoA-vs-AoS choice is enforced at compile time.

### D2.B — was_win → cross-slot SoA bitmap (Technique 3 of `aggressive-memory-reduction-techniques.md`)

**Apply:** extract `FillRecord.was_win` (currently 1B + 7B alignment pad per record = 8B × 16 = 128B) to a cross-slot bitmap at OMS level:
```cpp
uint16_t last_was_win_bitmap;  // 2B; bit N = was_win for slot N
```

**Net savings:** ~120B per OMS. FillRecord shrinks from 128B to 120B (or 128B with explicit pad reorganization for alignment).

**Discipline (per `aggressive-memory-reduction-techniques.md` Technique 3):**
- Access via BITMAP_IS_SET / BITMAP_SET / BITMAP_CLR (CLAUDE.md item 20 + BitmapMacros.hpp)
- `static_assert(sizeof(uint16_t)*8 >= MAX_PORTFOLIO_POSITIONS)` — verify width sufficient
- Migration: all reads of `last_fill[N].was_win` → `BITMAP_IS_SET(oms->last_was_win_bitmap, BITMAP_BIT_U16(N))`; all writes → BITMAP_SET / BITMAP_CLR
- Test coverage: round-trip set/get for each slot; isolation test (set slot 5, verify slot 3 unchanged)

### D2.C — DROPPED (Technique 4 verified UNSAFE 2026-05-13)

**Status:** dropped after pre-coding investigation by /merge-scan agent.

**Reason:** `exit_entry_notional` derivation from Position state is UNSAFE due to same-cycle SELL-then-BUY race. `HandleFill SELL` snapshots `exit_entry_notional` via `FPN_Mul(entry_price_snap, qty_snap)` (`OrderManager.hpp:1076`) BEFORE `Portfolio_CloseSlot` (line 1053). On the same drain cycle, `HandleFill BUY` calls `Portfolio_OpenSlot` (line 994) OVERWRITING `Position.entry_price` + `Position.quantity` — derivation at `DrainPostFill` time would yield the NEW entry's values, not the closed trade's.

The FillRecord-as-snapshot pattern is **deliberately load-bearing**, documented at `ControllerEventLoop.hpp:1327-1328`: *"Entry price + qty come from the portfolio slot (FillRecord only stores notional, not the components)"*. Same pattern shared with `ExitRecord` at `Portfolio.hpp:68-79` ("slot may be reused by a new fill before DrainExits runs").

Load-bearing read sites that would break:
- `ControllerEventLoop.hpp:1385` — `core_open_notional -= rec.exit_entry_notional` (symmetric pairing with `+= rec.entry_notional`; per-LEG accounting under partials)
- `ControllerEventLoop.hpp:1585` — `exit_bandit reward = rec.exit_net_pnl / rec.exit_entry_notional × 10000` (wrong notional → biased ML training signal)

Tests at `controller_test.cpp:7740/7744/7829/7900/7904` directly seed `exit_entry_notional` without backing Position state.

**Verdict:** KEEP `exit_entry_notional` stored in FillRecord. 384B savings does NOT justify breaking the deliberate snapshot invariant.
