In a design conversation, when a claim concerns EXISTING code — a type's layout, a function body, a blast-radius site, a magnitude, a behavior — Read the actual file + cite `file:line` BEFORE asserting, and show the operator the real snippet. Do NOT reconstruct from memory (it drifts), NOR trust a transient system-note / editor-buffer state over what's on disk (it may not have persisted). For NEW code being designed (functions that don't exist yet), show the design framing / pseudo-code + ground its REUSE/EXTEND points (the certified bodies it builds on) in real code. This is the design-conversation specialization of the verify-against-real-artifacts family — **NOT** a blanket "always show code": genuinely-new or abstract-architectural design has no code to show, so the rule is *ground-the-existing + show-the-design-for-the-new*.

**Why:** the #11 numeric-core design session proved it both directions. Grounding PAID: reading the real `FPN<64>` struct corrected a memory-reconstruction error (remembered as 192-bit; it's 128-bit / 2-word sign-magnitude), and the author's own `LinearRegression3X.hpp:12-14` overflow comment was the DECISIVE evidence for the 8B-storage verdict. NOT-grounding COST: a "plan body rewritten into an Execution Plan" claim propagated into the handoff + decision-log from a transient editor-state system-note that never persisted to disk — caught only by an independent disk-check at close. Reconstruction drifts; a transient note ≠ disk; the real artifact is ground truth — and showing it is also higher-value for the operator (her eyes on the actual framing, which is what she keeps asking for). **Throughput, not just correctness (operator, 2026-05-31): "i feel like we get way more done that way."** Grounding cuts the abstract back-and-forth + keeps progress concrete — so the principle pays in MOMENTUM as much as in caught-errors. The whole #11 design pass moved fast precisely on the code-grounded segments (reading FP64_Mul, the blast-radius sites, the magnitudes) and spun on the abstract ones.

**How to apply:** existing-code claim → Read + cite `file:line` + offer the snippet; new-code design → show the framing + Read the reuse/extend target; any verdict or "are you sure?" → check the disk/tool, not memory or a system-note. **And do NOT transcribe a `file:line` from an EPHEMERAL planning artifact (finding-register / plan / handoff) into a DURABLE doc (DESIGN_SPEC / anti-pattern / CLAUDE.md) without re-grounding it against code** — ephemeral artifacts carry stale cites (`.E.0.10`: a register's `ExecutionCore.hpp:1887` rode into a DESIGN_SPEC; the file is 665 lines; caught only by an adversarial panel). Provenance is not evidence; the durable surface re-grounds (meta-anti-pattern: AR-3 transcription-trap sharpening). **And a tool/sanitizer SUMMARY gives the SYMPTOM, not the CAUSE — trace the code path before asserting the mechanism in a durable capture** (`.E.0.10` TECH_DEBT-202, 2026-06-15: an ASan report said "T101 pops the ring after `delete oms`"; the root cause was captured as "the writer is never joined" WITHOUT reading the lifecycle code — but `OrderEventLog_Free` ALREADY joins; the real cause was a test double-init (`OrderEventLog_Init` re-run) clobbering `writer_thread_active` so the existing join no-ops. The wrong mechanism rode into the TECH_DEBT + the `.E.1` plan + the handoff; caught only when the operator pushed *"everything, not top-N — is the handoff accurate?"* → an exhaustive scout re-derived it from the ASan thread-create frame + the Init/Free/Stop code. A fixer following the capture would have chased a join that already exists). The symptom is in the summary; the cause is on disk.
