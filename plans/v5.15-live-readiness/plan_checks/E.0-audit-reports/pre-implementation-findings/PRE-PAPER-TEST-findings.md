### [HIGH] `dsgui-2` — Notify per-kind cooldown drops repeated same-kind CRITICAL alerts with no severity bypass or escalation
*verified* · section `datastream-gui` · fix: standalone (small Notify.hpp change: bypass cooldown for level==NOTIFY_CRITICAL, or key cooldown on (kind,level), or at least increment a dropped-alert counter on cooldown drop)
- **Where:** CoreFrameworks/Notify.hpp Notify_Send (~lines 188-204): per-kind cooldown gate keyed on `kind`, checked BEFORE `level` is ever inspected; `last_fired_us[kind]` is one slot per NotifyKind, shared across all levels.
- **What:** Notify_Send applies a 60s (default cooldown_us) silent-drop gate keyed solely on event_kind, evaluated before the queue-full check and with no reference to `level`. Two consequences: (1) a CRITICAL alert (e.g. NK_KILL_TRIGGER) firing within 60s of a prior same-kind alert is silently dropped — there is no level-based bypass for CRITICAL; (2) because last_fired_us is per-kind (not per-(kind,level)), a lower-level WARN of a kind suppresses a subsequent CRITICAL of that same kind within the window. ### [HIGH] `dsgui-2` — backtest<->live feature asymmetry: DepthRecorder stores top-of-book only, so replayed book_imbalance is top-only while live computes 5-level imbalance (same consumer field, two transforms)
*verified* · section `datastream-gui` · fix: standalone (DepthRecorder CSV format + DepthReplayState parser); naturally sequences with the depth-backtest/maker corpus work referenced in DOCS/tech-debt/open.md (depth-replay limited-fills entry)
- **Where:** Live transform: DataStream/BinanceDepth.hpp depth_parse_json (~lines 191-196) computes snap->imbalance over bid_count/ask_count (up to 5 levels). Recorder: DataStream/DepthRecorder.hpp DepthRecorder_Write (~lines 249-255) fprintf writes ONLY bids[0]/asks[0] (top level). Replay: DataStream/DepthReplayState.hpp DepthReplayState_LoadDay (~lines 243-249) sets row.top_imbalance from top level then row.imbalance = row.top_imbalance (comment :247 'CSV records only top level, so full-book imbalance == top'). Consumer parity: live feeds snapshots[active].imbalance -> ctrl.book_imbalance (main.cpp:829); backtest feeds depth_replay.current.imbalance -> book_imbalance_holder (Backtest/BacktestSharded.hpp:658). Both flow to the min_book_imbalance buy gate (CoreFrameworks/PortfolioController.hpp:1837-1838) AND the regime book_imb_mean_short/long + book_imb_drift features (Strategies/RegimeDetector.hpp:389-399).
- **What:** The live depth path computes order-book imbalance over up to 5 price levels (full_5-level `imbalance`) and separately keeps top-of-book `top_imbalance`. DepthRecorder, however, persists ONLY the top level to CSV. DepthReplayState therefore cannot reconstruct the 5-level value and assigns `imbalance = top_imbalance` (top-only). The downstream consumer field is identical on both sides (book_imbalance), but the value it carries was produced by two different formulas: 5-level sum at live-serve vs top-only at backtest-replay. This is a classic /parity-check finding — a transform applied on one side (the live 5-level sum) and not the other (replay can only do top). It affects both the min_book_imbalance buy gate threshold comparison AND the regime classifier's book_imb_mean/drift features, which are computed whenever a BookImbalanceHistory is supplied regardless of whether the gate is enabled.
- **Why:** Backtest results stop predicting live behavior for any strategy/regime that is sensitive to book_imbalance: a backtest using a recorded depth corpus will gate entries and classify regimes off a top-only imbalance, while the live engine uses a 5-level imbalance — systematically different in magnitude and sometimes sign during asymmetric deeper-book liquidity. This silently undermines the train/serve (backtest/live) parity claim for the depth feature. Severity MEDIUM (not HIGH) because it is latent today: depth recording is off by default and there is no depth corpus yet (DOCS/tech-debt/open.md:111-117). But the DEFECT IS IN THE RECORDER FORMAT — the moment a corpus is captured and used for backtesting, the asymmetry is real and unavoidable without re-recording. The cheap fix is to make depth_parse_json's full-book imbalance reproducible from the CSV (record all 5 levels, OR record the full `imbalance` value as an extra column) so replay reconstructs the same number live used.
- **⚠ Don't carry forward (.E.1 rewrite):** Do NOT freeze a top-of-book-only depth CSV schema as the corpus format. Whatever schema is chosen at .E must let DepthReplayState recompute book_imbalance with the IDENTICAL formula depth_parse_json uses live (either persist all 5 levels per side, or persist the computed full `imbalance`/`spread`/`mid` alongside top-of-book and have replay read them rather than re-deriving from top only).
- **CI check:** A parity test that feeds one synthetic 5-level book snapshot through (a) depth_parse_json and (b) DepthRecorder_Write -> DepthReplayState_LoadDay, then asserts the resulting `imbalance` values are bytewise-equal (would fail today, documenting the asymmetry as intentional-or-bug).
- **Test to add:** No test compares the live depth-parse `imbalance` against the recorder->replay reconstructed `imbalance` for the same input book; existing DepthReplayState tests (tests/controller_test.cpp ~6674-6756) only check sign/monotonicity of replayed top-level data, never the full-vs-top divergence.
- **Anti-pattern:** A serialization path (recorder) that persists a strict SUBSET of the fields its live producer derives, paired with a deserializer (replay) that silently substitutes a different field (top-of-book) for the missing one — so backtest and live feed the same consumer a same-named-but-differently-computed value.

That contract silently assumes a stable C locale that is never enforced at process scope. The failure is silent (no crash, no warning) and feeds the regime classifier + strategy sizing + ML feature pack, so the operator gets confidently-wrong backtest/training results. TECH_DEBT-027 (CLOSED) addressed only the SAVE side (Bandit/Thompson JSON writers); the backtest READ side (tick + depth parse) and the missing process-level pin are uncovered.

- **Anti-pattern:** Reproducibility/wire claims ('bytewise-identical') asserted over a parse path that depends on the ambient process locale, with locale pinned only at scattered emit sites and never at process entry.

### [HIGH] `fpmem-2` — No bytewise-identity test between scalar FPN<64> and native-128 FP64 paths (H10 scalar-fallback parity gap on a wire/hash surface)
*verified · **NEEDS-RUNTIME-CONFIRM*** · section `fixedpoint-mem` · fix: standalone (foundational)
- **Where:** FixedPoint/FixedPointN.hpp scalar templates (FPN_AddSat ~526, FPN_Mul ~583, FPN_DivNoAssert ~687, FPN_FromDouble ~162, FPN_ToString ~309) vs FixedPoint64.hpp FP64_* (FP64_AddSat ~73, FP64_Mul ~134, FP64_DivNoAssert ~182, FP64_FromDouble ~33). - **What:** USE_NATIVE_128 selects a structurally different FPN<64> implementation (FP64 via __uint128_t) from the generic N-word scalar loop. The two FromDouble paths in particular are written differently (scalar: frac_hi/frac_lo two-word decompose with FW=1 dropping frac_lo; native: hi+lo single-magnitude add), and the saturation paths differ in form (scalar masks each w[i] to UINT64_MAX; native masks the __uint128_t to (-1)). An operator running a scalar (USE_NATIVE_128=OFF) build for debugging/portability and a native build in production would get non-reproducible signed artifacts. This is the canonical H10 gap: the optimized kernel exists, ships by default, feeds wire bodies, and has zero parity coverage.
- **⚠ Don't carry forward (.E.1 rewrite):** When .E.1 renames FPN ops, keep ONE source of truth for the F=64 fast path or add the parity lock first; do not let the native specialization drift further from the scalar template silently.

- **Test to add:** Add a cross-build parity test: a fixed input corpus (boundary doubles, saturating adds, zero-divisor, negative-zero, sub-ULP fractions) -> FPN_ToString, hashed; assert the hash equals between USE_NATIVE_128 ON and OFF builds
- **Anti-pattern:** shipping an optimized numeric kernel as the default build with no bytewise-equality test against the scalar reference it claims to mirror

### [HIGH] `fpmem-1` — FPN_Sqrt<64> native-128 specialization routes through sqrt() IEEE-754 round-trip, breaking the documented bytewise-determinism contract on the DEFAULT production build
*verified · **NEEDS-RUNTIME-CONFIRM*** · section `fixedpoint-mem` · fix: standalone (foundational) — pre-paper-test; determinism-load-bearing for ML replay
- **Where:** FixedPoint/FixedPointN.hpp: native specialization `template<> inline FPN<64> FPN_Sqrt<64>` (~line 1254) → forwards to FixedPoint64.hpp FP64_Sqrt (~lines 313-316) = `FP64_FromDouble(sqrt(FP64_ToDouble(value)))`. Generic deterministic Newton-Raphson FPN_Sqrt lives at FixedPointN.hpp ~873-902 but is shadowed when USE_NATIVE_128 is defined. Consumers: ML_Headers/FlowFeatures.hpp:373,465 (stddev), ML_Headers/FeatureRegistry.hpp:349 (denom), ML_Headers/RidgeBlender.hpp (Cholesky sqrt boundary).
- **What:** Under USE_NATIVE_128 (the CMake default for engine/engine_gui/foxml_suite, and explicitly set for tsan/asan), FPN_Sqrt<64> does NOT use the integer Newton-Raphson path. It converts FPN→double, calls libm sqrt(), and converts back. The source comments at FixedPointN.hpp ~867-872 ('Bytewise-deterministic across compilers — bit-scan seed + integer FPN ops only; no IEEE-754 round-trip') and RidgeBlender.hpp ~39-42 ('FPN_Sqrt ... is bytewise-deterministic per v5.10.0b Newton-Raphson ... - **Why:** sqrt() over double is not guaranteed bytewise-identical across compilers / -O levels / libm versions / FMA-contraction settings — exactly the cross-binary determinism property the codebase ranks above maintainability (H9/H10 family; replay-determinism CSV-byte contract per PARITY-016/017 history). FPN_Sqrt feeds FlowFeatures stddev which feeds ML feature vectors and Ridge weights; a one-ULP sqrt difference propagates through FromDouble rounding into bit-different features → bit-different decisions → broken replay-determinism between any two differently-built production binaries. Today's single-binary runs are internally consistent, so this is a determinism/portability hazard rather than an in-binary wrong answer.
