## Candidate signatures (3 options with trade-off analysis)

### Option α — Flat args (all individual; 10 args)

```cpp
template <unsigned F>
inline void EngineCommon_SlowPathCycleOneCore(
    const ControllerConfig<F>& cfg,
    int c,
    EventLoopState<F>& state,
    OrderManagerState<F>& oms,
    FPN<F> price,
    FPN<F> volume,           // NEW per FINDING #1
    uint64_t ts_us,
    uint64_t now_tick,       // NEW per FINDINGS #2 + #3 (unified)
    FPN<F> book_imb,         // NEW per FINDING #4 (a)
    double book_spread_d,    // NEW per FINDING #4 (b)
    double book_mid_d);      // NEW per FINDING #4 (c)
```

**Trade-offs:**
- ✅ **Most-explicit operator-visible contract**: every input named at call site → cold-pickup readable
- ✅ **Cluster by access pattern (H6 DOD)**: scalars grouped (price+volume cohort; ts_us+now_tick cohort; depth cohort)
- ✅ **Future-extension cost**: low — adding a new arg = 1 line change at both call sites (LIVE + BACKTEST + tests)
- ❌ **Signature width**: 10 args; per Decision H signature taste from v1.6 — "5-7 args is sweet spot"; 10 is wide
- ❌ **Depth-feature cohort**: 3 separate args; sister-canonical bundling pattern (sister: depth_imbalance + depth_spread already paired in `UpdateRollingStateOneCore` signature)
- ❌ **DOD signature discipline**: 3 depth fields belong logically together (book snapshot = struct); separating into scalars is "logical" view not "access" view → mild anti-DOD

### Option β — DepthSnapshot bundle (8 args) ⭐ RECOMMENDED

```cpp
struct DepthBundle {
    FPN<...> book_imb;       // 0 when depth disabled
    double   book_spread_d;  // 0.0 when depth disabled
    double   book_mid_d;     // 0.0 when depth disabled
};

template <unsigned F>
inline void EngineCommon_SlowPathCycleOneCore(
    const ControllerConfig<F>& cfg,
    int c,
    EventLoopState<F>& state,
    OrderManagerState<F>& oms,
    FPN<F> price,
    FPN<F> volume,                            // NEW
    uint64_t ts_us,
    uint64_t now_tick,                        // NEW (unified)
    const DepthBundle<F>& depth);             // NEW (3 fields bundled)
```

**Trade-offs:**
- ✅ **Sister-canonical fit**: existing `BookSnapshot<F>` struct at `DataStream/BinanceDepth.hpp:32-35` (spread + mid_price + imbalance + top_imbalance) — bundle MATCHES this shape. Could even REUSE `BookSnapshot<F>` directly instead of new `DepthBundle` (3 of 4 fields read; top_imbalance unused but free).
- ✅ **DOD-correct**: depth bundle is an ACCESS-PATTERN cohort (always read together; always provided together by caller; depth_enabled gate applies to all 3)
- ✅ **Signature width**: 8 args at the cohort level; readable
- ✅ **Future-extension**: adding 4th depth field (e.g., book_imbalance_z) = add field to bundle; no caller-side ripple at 8-arg signature
- ✅ **LIVE caller code**: `DepthBundle depth = {book_imb, book_spread_d, book_mid_d};` ~3 lines (mirrors existing local-var pattern at `:3050-3058`)
- ✅ **BACKTEST caller code**: similar bundle construction from `*drv->book_imbalance + *drv->current_spread + *drv->current_mid_price`
- ❌ **One additional struct definition** (DepthBundle) OR reuse BookSnapshot (sister-pattern fit — preferred)
- ⚠️ **`depth_enabled` flag still derived from cfg.gate_cfg_flags inside helper** — no change

**Variant β-1: reuse `BookSnapshot<F>` directly** — caller fills snap struct from g_depth_shared OR DepthReplayState; helper reads fields. **PREFERRED per `feedback_audit_canonical_sister_before_new_infra`** — `BookSnapshot<F>` already exists; bundling under new name DepthBundle would be premature mini-framework.

### Option γ — Full TickContext bundle (5 args; all per-tick vars bundled)

```cpp
struct TickContext {
    FPN<F> price;            // mtm_price source
    FPN<F> volume;
    uint64_t ts_us;          // wall-clock microseconds
    uint64_t now_tick;       // tick counter
    BookSnapshot<F> depth;   // depth-feature cohort
};

template <unsigned F>
inline void EngineCommon_SlowPathCycleOneCore(
    const ControllerConfig<F>& cfg,
    int c,
    EventLoopState<F>& state,
    OrderManagerState<F>& oms,
    const TickContext<F>& tick);    // 5-field bundle
```

**Trade-offs:**
- ✅ **Smallest sig width**: 5 args, sweet spot per Decision H
- ✅ **Caller side simplification**: LIVE builds TickContext from atomics + g_depth_shared once per cycle; BACKTEST builds from tick + driver pointers once
- ✅ **Future-extension cost**: lowest — new per-tick var = add field to TickContext (zero caller-call-site changes; only TickContext construction changes)
- ❌ **NEW struct definition required** (TickContext<F>) — premature generalization concern per `feedback_audit_canonical_sister_before_new_infra`; no sister canonical for "per-tick context bundle" today
- ❌ **Less-explicit contract**: cold-pickup operator must read TickContext fields to know what helper consumes; less local at call site
- ❌ **Single-cohort fail**: TickContext is NOT a single access-pattern cohort — price+volume always-together (per-event), ts_us is wall-clock (vDSO syscall in LIVE), now_tick is tick counter (atomic load), depth is depth-cohort. Forcing them into one struct is "logical" view, not "access" view → anti-DOD per H6
- ❌ **Sister-pattern mismatch**: `Tick<F>` (BinanceCrypto.hpp) already bundles {price, volume, timestamp, is_buyer_maker}; TickContext would parallel-mirror this concept with engine-side fields. Risk of Class 21 parallel-mirror anti-pattern.
- ❌ **`now_tick` semantic asymmetry**: distinct from `Tick<F>::timestamp` (wall-clock) — bundling distinct semantics under one struct invites confusion

**Verdict on γ:** ELEGANT-LOOKING but VIOLATES DOD discipline. The 4 inputs are NOT single-access-cohort. Reject per `feedback_recheck_designspecs_on_pushback` discipline.

## RECOMMENDATION: Option β-1 (BookSnapshot reuse; 8 args)

**Decision matrix (per `feedback_evaluate_options_on_robustness_latency_design_not_time`):**

| Axis | α (10 flat) | β-1 (BookSnapshot reuse; 8) | γ (TickContext bundle; 5) |
|---|---|---|---|
| **Robustness** | High — explicit args caught at compile | High — bundle compile-checked | MED — bundle elements not individually visible at call |
| **Latency** | Neutral — pass-by-value scalars | Neutral — small const ref (negligible) | Neutral — small const ref |
| **DOD discipline (H6)** | Mixed — scalars OK but depth-cohort separation arbitrary | ✅ HIGH — bundles access-cohort | ❌ LOW — forces cross-cohort fusion |
| **Sister-canonical fit** | Neutral | ✅ HIGH — reuses existing BookSnapshot<F> | ❌ LOW — new TickContext premature |
| **Future-extension cost** | LOW (1 line per call site) | LOW (bundle field) | LOW (bundle field) but RISKS anti-DOD growth |
| **Operator-impact (cold-pickup readability)** | HIGH — most-explicit | MED-HIGH — bundle name self-documenting | MED — TickContext name vague |
| **Novel-alternative considered** | n/a | β-1 is "use existing sister" not "invent" — PROACTIVE per `feedback_proactive_novel_alternative_consideration` | γ is novel; rejected per DOD |

**Winner: β-1 (BookSnapshot reuse).** Per `feedback_audit_canonical_sister_before_new_infra` — extend existing canonical (BookSnapshot<F>) instead of inventing DepthBundle.

## Telemetry-pattern decision (5th pre-coding concern)

The per-section rdtsc telemetry (`_sec_t_*` markers + `CoreLatencyStats_Sample` for SP_SECTION_ROLLING / REBUILD / PUSH / TIME_EXIT / TRAIL_SL) is currently intrinsic to the cycle body (each section's timing is sampled relative to prior section). Two paths:

### Path A: Telemetry STAYS INSIDE helper body (recommended)

```cpp
// Inside EngineCommon_SlowPathCycleOneCore:
uint64_t _sec_t_other_start = __rdtsc();
// ... rolling state update ...
uint64_t _sec_t_rebuild_start = __rdtsc();
CoreLatencyStats_Sample(&state.display_meta[c].slow_path_breakdown[tt::SP_SECTION_ROLLING],
                         _sec_t_rebuild_start - _sec_t_other_start, _sec_t_rebuild_start);
// ... rebuild ...
// (etc. for PUSH / TIME_EXIT / TRAIL_SL / total slow_path_latency)
```

**Pros:**
- Per-section timing is intrinsic to the cycle; helper IS the unit of slow-path-cycle observability
- BACKTEST also benefits (timing display works in suite runs)
- Cost: ~5ns per __rdtsc (negligible; well within 100μs budget)
- Symmetry: train-serve parity maintains observability path

**Cons:**
- BACKTEST single-threaded; per-section timing arguably less meaningful (no SMT contention etc.)
- M5 false-positive surface — telemetry IS LIVE-only by convention

**Caveat:** caller must initialize `_sec_t_other_start` BEFORE invoking helper (since helper expects it as IN baseline). EITHER pass as helper sig arg OR have helper compute internally at entry (lose ability to bracket caller-side prelude time).

### Path B: Telemetry EXTRACTED to caller (loses per-section visibility)

Caller would bracket only TOTAL helper cycle time; per-section breakdown lost. **Reject per `feedback_proportionate_response_to_audit_findings` — this would REGRESS existing functionality at sub-µs scale to satisfy abstract "LIVE-only" purity.**

### RECOMMENDATION: Path A with internal rdtsc start

```cpp
inline void EngineCommon_SlowPathCycleOneCore(...) {
    uint64_t _sec_t_other_start = __rdtsc();  // helper-internal cycle start
    // ... cycle body ...
    uint64_t _sp_t1 = __rdtsc();
    CoreLatencyStats_Sample(&state.display_meta[c].slow_path_latency,
                             _sp_t1 - _sec_t_other_start, _sp_t1);  // total cycle
}
```

Caller no longer needs to bracket; helper owns the cycle observability. **Slight regression: total cycle no longer captures caller-side prelude time (pause check + cadence gate + swap pickup) — but those are CALLER-OWNED concerns, not slow-path-cycle work.** Cleaner separation.

**Sub-finding:** the existing `_sp_t0 = __rdtsc()` at `:2812` brackets pre-cycle work (swap pickup) INTO the slow_path_latency total. Path A internal start moves this BOUNDARY → slow_path_latency is now pure-cycle-only. Operator-visible: latency display value will DROP slightly (delta = pre-cycle work time). **Acceptable** if documented in postmortem.
