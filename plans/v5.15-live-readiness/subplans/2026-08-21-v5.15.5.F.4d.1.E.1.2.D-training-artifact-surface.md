# E.1.2.D — the training + model-artifact surface

**Origin (2026-08-21, Caramel):** *"changing that drop down mid training changes how the model gets
labeled"* · *"we have major issues with how the models get saved"* · *"is this a anti pattern we have
or should update with"*. Three i-class scans fired at her direction; ~30 findings; full digest in
`reports_dir`.

## Why this is a ship and not a punch-list

Every other surface in this codebase — registry, wire-format, cfg-flow, snapshot — carries a
RECURRING_BUG_PATTERNS class, a DESIGN_SPEC, and a CI guard. **The model-artifact surface carries
none of the three, and H21 covers no path form and no role filename.** That is the mechanism behind
every finding below: nothing was watching, so defects accumulated silently for months. Fixing the
instances without closing the gap guarantees a fourth scan next quarter.

### Leaf 4 in detail — what it was, and what the fix actually is

**The four configurations, measured:**

| Consumer | Trained/recorded at | Source |
|---|---|---|
| the SHIPPED model | the operator's panel values (`2 / 0.050 / 350`) | 8 LIVE `state->` reads from a worker thread |
| the walk-forward folds | `6 / 0.1 / 200` + 4 cfg overrides | `XGBHyperparams_Defaults()` + `eff_cfg` |
| the held-out model | pure `6 / 0.1 / 200 / 0.8 / 0.8 / 5 / 42` | `XGBHyperparams_Defaults()`, **no overrides at all** |
| the STAMP | `6 / 0.1 / 200` | the same hardcoded defaults |

So the operator's tuning loop was **open**: hyperparameter changes could not appear in the numbers
used to judge them, and — the reason it survived — **no artifact on disk could contradict the stamp,
because the stamp came from the same defaults the validation used.** The held-out figure, which is
the one gating deployment, described a model nobody trained and nobody shipped.

**Fix shape (deliberately NOT the first one attempted):** the obvious route — add the three missing
hyperparams to `ControllerConfig` so `config_used` carries them — was BUILT and REVERTED. A guard
caught it: `ControllerConfig` is RAW-fingerprinted into the model stamp (H9/H12, D-254), so growing
it shifts every cfg fingerprint. Perturbing a fingerprinted struct for a training-time convenience
is the wrong trade. The landed shape instead threads one `const tt::XGBHyperparams *hp_override`
(default `nullptr` = previous behaviour bytewise) through `Backtest_RunFullValidation` →
`Backtest_RunWalkForward` + `HeldOutSplit_TrainEval`, and the worker builds it ONCE from the
click-time snaps.

**It also closes S1-F1 for free**, because the same snapshot replaces the eight live `state->` reads:
those snaps had been populated in `MultiHorizonWorkerArgs` since v5.11.41 and read by NOTHING — the
Class-13 sub-shape *"snap block complete, consumer bypasses it"*. The parallel path needed the
snapshot on `MultiHorizonParallelJob` too, since its worker cannot reach the outer scope.
`summary.txt`'s hyperparam lines were a SECOND live read minutes after the first, so an edit in
between made the summary disagree with the model beside it; they now report the snapshot.

**Acceptance oracle — PARTIAL, stated not implied.** `C.3k` pins the shared fallback
(`XGBHyperparams_Defaults()` = 6/0.1/200/0.8/0.8/5/42) so a silent change to it moves all three
fallback sites at once. The plumbing that carries the operator's snapshot into those sites needs
XGBoost + real data to exercise and is **dogfood-verified, not pinned**: train one horizon, then
grep the emitted `.stamp` for the operator's values instead of `6 / 0.1 / 200`. Suite 3879 → 3888
(+9 = C.3k exactly), both TUs build, cache-layout strict-new rc=0 / 0 NEW, H21 GREEN at 92,
calls-graph CLEAN.

**Operator consequence:** every metric on every existing model describes a 6/0.1/200 architecture.
After this lands, re-run Run Full Validation on `twins` to get honest numbers for the deployed
2/0.050/350 model — no retraining needed, RFV does not save a model.

## SELF-CORRECTIONS THIS SESSION (recorded, not buried)

**SC-1 · I introduced a locale-determinism regression and it survived one commit.**
The `#22` load-side check (engine `cd9c2c7`) added `expected_label_type = atoi(val)` to the
`expected.cfg` parser, raising `ML_Headers/NodeModelZoo.hpp`'s raw-parse count 5 → 6 against
`tools/locale_determinism_known_pending.txt`, whose header says the list **SHRINKS, never grows**.
It committed clean because **pre-commit Check F is FILE-SET TRIGGERED** — it fires on "staged
FP/parse/locale change detected", and that commit's staged set did not trip the trigger. It was
caught two commits later only because a different file (`BacktestEngine.hpp`) happened to be staged
alongside. Fixed by using `tt::parse_double_fast` (locale-immune via `std::from_chars`, exact for
the small integers a label enum holds), which makes the new key cleaner than the `atoi` rows around
it rather than adding to the debt they represent.
**The transferable finding is the trigger, not my slip:** a conditionally-fired gate can be bypassed
by an unlucky staged-file set, so a violation lands and sits until an unrelated commit happens to
arm it. Candidate: make Check F fire on any staged file that appears in the known-pending manifest.

**SC-2 · I proposed wiring `#22` before verifying its producer existed.** See D-d. The guard is
harmless and fail-open, but I claimed it would give a load-side label check and its producer is dead
code. The verification I skipped was "does anything actually write this sidecar on the production
path" — one grep.

**SC-3 · I stated "zero consumers" for the `expected_num_classes` stamp key having enumerated only
production directories.** The compiler found five test cells my grep never looked for. M9/AR-1, on
the load-bearing premise of that recommendation. Disposition survived; the confidence was unearned.

**SC-4 · I first told the operator her barrier models needed re-stamping before leg 4.** Wrong —
`Model_RoleCheckDecide` returns PASS for a missing `expected_role` on any NON-exit slot
(`NodeModelZoo.hpp:199-201`). Only exit slots refuse. Corrected same session.

**SC-5 · I recommended the F3 tier flip, and a `/decision-check` refuted it on a premise I had not

disabled" and I propagated it. That refutation is what surfaced the buy-side inversion, so the
skipped check paid for itself, but the proposal was wrong when made.

## OPERATOR DECISIONS OWED — the points of contention

These are the ones that must not evaporate between sessions. Each names the fork, the evidence, and
what changes if it goes either way.

### D-a · Model layout: nested vs flat — **the biggest one**
Scan 2's verdict: `<family>/horizon_<N>/<role>.json` is **WORTH IT, and not close**. The decisive
argument is not aesthetics — it is that the flat layout has **no node for the bundle**, so four
bundle-scoped artifacts (the bandit/Thompson state files) have nowhere to live. Today's `mkdir` is
the cheap 90%; the fact that one `mkdir` fixes it is itself the argument the directory belongs there.
Cost: 13 code sites + ~76 test lines. **No compat path owed** (`project_no_live_models_dev_test_only`).
**Trigger: before leg 4** — otherwise leg 4 measures a persistence mechanism that was inert.
**Against:** scan 2's own O3 — keep flat, just `mkdir` the family dir. Fixes S2-F1 at ~zero cascade,
leaves the aliasing (S2-F5), the three parsers (S2-F9), the `node_model_dir` double-meaning and the
delete-granularity intact. This is the genuine fork.

### D-b · `VOL_BARRIER` / `BARRIER` tier asymmetry
Structurally identical first-passage labels (differ only in barrier width) sit at WARN and REFUSE
respectively for exit-side training, with no stated reason. Pinned as CURRENT truth in C.3j so a
change breaks the test on purpose. **Still un-triaged since the D2 verdict.**

### D-c · `#18` — `p_peak` charges the stable mass
`1 - P(valley)` = `P(peak) + P(stable)`, so BarrierGate over-blocks on a quiet tape. Right sign,
wrong magnitude. **Trigger: fix before `barrier_gate_enabled` is ever turned on** (measured: defaults
0, set in neither cfg, so `p_peak` is consumed by nothing today). Exact fix = one
`Model_PredictMulti` per handle blended per-class.

### D-d · `#22` needs RE-DISPOSITION — I wired a guard whose producer is dead
I landed the `expected_label_type` load-side check (`cd9c2c7`) on the premise that `Save Run` could
produce an exit-role `expected.cfg` once side-blindness was fixed. **Scan 2 F2 then measured that
`Save Run` itself is unreachable** (`model_trained` has no live writer — register `#2`), so
`expected.cfg` has **no reachable producer at all** and the check is currently vacuous (Class 51).
It is harmless and fail-open, but it is not doing what I said it would. Fork: revive Save Run
(couples to `#2`/D6), move the producer to the MH worker, or accept it as dormant-until-`#2`.

### D-e · D4 `summary.txt` collision — "accept+document" is failing in practice
The operator hit it live: the exit run overwrote the buy-side summary for `twins_horizon_7500`,
destroying the metrics of her best model (recovered only from a nested backup). She then hand-created
`summary.exit-run.txt` — a manual workaround, which is the signal the disposition is wrong.
Re-triage toward a role-suffixed or role-sectioned summary; the only cited cost is
`PastRuns_LoadOne`, a display reader.

### D-f · Codify the class — she asked for this directly
A RECURRING_BUG_PATTERNS class + a `data-disciplines/` spec for operator-facing artifact identity,
plus H21 SOURCES coverage of path forms and role filenames (S2-F11 — TECH_DEBT-084 already renamed
two state files with no ledger event). Now backed by a **~30-instance census**, which is the bar
`pattern-codification-lifecycle.md` sets; codifying from one anecdote is what it warns against.
