## v5.10.0 pre-flight — Foundation (perf+RAM bundle)

### Concerns

1. **Sparse label rewrite is high-risk** — Item B touches 3 files
   cumulatively (BacktestEngine.hpp, HeldOutSplit.hpp,
   ValidationSplit.hpp). Off-by-one in consumer-side index
   translation is silent killer; tests can pass while runtime
   labels are misaligned.
2. **OOM is a real failure mode** — operator's 30.9 GiB box hit OOM
   on 2-year dataset 2026-05-03. Item B MUST close this; partial
   fix isn't a ship.
3. **Parallel CSV worker buffer ordering** — file-date order must be
   deterministic across runs. Worker thread coordination bug =
   non-reproducible builds = train-serve parity destroyed.
4. **Hardware-aware cfg defaults must not silently change behavior**
   — `xgb_train_nthread=0` (auto = nproc) is a NEW default. On a
   4-core dev box this matches old behavior; on a 64-core Xeon, it
   changes XGBoost training math (more threads = different fit).
   Worth flagging.
5. **Per-phase timers add hot-path-adjacent code** — markers are
   slow-path only, but `clock_gettime` calls in tight loops can
   skew profiling. Verify overhead < 1% on small fixture.

### Mitigations

1. **Bytewise-equivalence test gates Item B** — small 100k-tick
   fixture; dense (old) vs sparse (new) labels MUST match bytewise.
   Test commits BEFORE Item B refactor lands. Fail-closed.
2. **2-year synthetic dataset test** — Item B isn't done until a
   2-year synthetic dataset feature-collects without OOM in CI
   (or operator's box).
3. **Worker buffer ordering test** — `csv_load_workers=1` vs `=4` on
   100-CSV fixture must produce bytewise-identical tick array.
4. **`xgb_train_nthread` default doc note** — engine.cfg.example
   comment explains: "Default 0 = auto-detect nproc. Set to 1
   for cross-build determinism." Operator opts in to multi-thread
   training deliberately.
5. **Timer overhead validation** — pre-instrumentation runtime
   on 10k-tick fixture vs post-instrumentation; delta must be < 1%.

### Watch-points during coding

- ⚠ Item B: when rewriting label_buffer access, every site that
  used `tick_index` must convert to `sample_index`. There are at
  least 3 known consumers (Backtest_RunWalkForward,
  HeldOutSplit_TrainEval, ValidationSplit). Grep for
  `label_buffer[` to find them all.
- ⚠ Item C: `cancel_flag` plumbing must propagate to worker threads.
  Cancel-mid-load test must show no orphan worker threads.
- ⚠ Item D: cfg parser additions go in the right ControllerConfig
  section (post-v5.9.5h ML hyperparams; before v5.10.0c hot-swap-ack).
- ⚠ Item E.1: e2e fixture must be checked-in (no Binance dependency).
  Synthetic 10k-tick CSV with predictable price walk.
- ⚠ Item E.2: stamp snapshot test pinning is locale-sensitive.
  Use `setlocale(LC_NUMERIC, "C")` at test start; otherwise European
  decimal separator silently breaks the snapshot.

## v5.10.0a pre-flight — Grid search + multi-horizon + Compare button

### Concerns

1. **Cross-core XGBoost thread-safety unverified** — XGBoost was set
   to `nthread=1` for determinism. Per-core parallelism (different
   sweep params per core) hasn't been tested for reproducibility.
2. **Triple-split data leakage** — easy to accidentally include test
   set in selection step. Requires explicit guard.
3. **Multi-horizon stamp body extension** — adds position 20
   (`grid_member_count`). Must coordinate with v5.10.0d (position 19,
   `label_registry_hash`) — whichever ships first locks position 19.
4. **Past Runs Compare button needs sample data** — operator needs
   at least 2 run-history rows before button is meaningful.
   Coordinate with foundation's e2e test (which adds 1+ run-history
   row per CI run).

### Mitigations

1. **Per-core XGBoost reproducibility test** — train same model on
   same core 2x, verify bytewise equality
2. **Test-set lock guard** — explicit assertion in code that test
   set is never used in best-selection logic; assertion fires in
   debug builds
3. **Stamp body position registration at ship-time** — when 0a
   ships before 0d, `grid_member_count` takes position 19;
   document in master plan canonical-order table immediately.
4. **Compare button gracefully handles 0 or 1 row** — disabled
   state when nothing to compare; tooltip explains why

### Watch-points during coding

- ⚠ `BacktestSharded` driver already fans ticks across SPSC rings;
  reuse the existing per-core engine slot for sweep training, don't
  invent new threading.
- ⚠ XGBoost `nthread` cfg interaction: per-core training × per-core
  XGBoost threads = potential CPU contention. Default `xgb_train_nthread=0`
  (auto) might oversubscribe. Document.
- ⚠ Past Runs panel TableSetupColumn count: bumping by 1 (Compare
  state column) repeats v5.9.5j.1 hotfix risk. Update both binary
  AND regression panel column counts.

### Pre-coding checklist

- [ ] v5.10.0 foundation shipped + tagged
- [ ] Foundation operator-validation gates green (OOM closed,
      timers display, parallel CSV speedup confirmed)
- [ ] `/readiness plans/2026-05-03-v5.10.0a-grid-search-multihorizon.md` — GREEN

### Operator validation

- Sweep `xgb_subsample` from 0.5 to 1.0 in 0.1 steps; OptimizerPanel

- Multi-horizon: train 5 horizons in parallel; inference picks
  highest-confidence per-tick

## v5.10.0b pre-flight — FPN-end-to-end (cross-build determinism)

### Concerns

1. **~500 LOC refactor in load-bearing paths** — RollingStats,
   RegimeDetector, RORRegressor, FlowFeatures all touched. High blast
   radius if precision drifts.
2. **All existing v5.9.x stamps invalidated** — `MODEL_FORMAT_VERSION`
   bumps 5→6; legacy stamps refuse load. Operator must retrain ALL
   models for v5.10.0b+.
3. **FPN sin/cos polynomial epsilon bound** — locked to polynomial
   approximation 2026-05-02 but not yet validated. Must hit 1e-6
   error bound across `[0, 2π]` representative inputs.
4. **Replay-determinism test must pass across 3 build configs**
   (test/gui/suite). Today within-build only; cross-build is the
   ship's load-bearing claim.

### Mitigations

1. **Per-stage tags (v5.10.0b.1, b.2, b.3)** — rollback per stage if
   precision drift surfaces.
2. **Operator-coordinated retrain procedure** — DOCS/RETRAIN_RITUAL.md
   updated with v5.10 retrain steps before ship lands.
3. **FPN_Trig epsilon-bound test in B.1 gate** — must pass before
   B.2 starts. If polynomial fails, fall back to lookup table
   (1440-entry precomputed FPN array, 23KB).
4. **Cross-build replay-determinism test** — explicit test that
   builds with `-O2` and `-O3` produce bytewise-identical model
   training output.

### Watch-points during coding

- ⚠ Don't bump `MODEL_FORMAT_VERSION` until B.3 stage; B.1 + B.2
  must be backwards compatible.
- ⚠ FPN sin/cos must be range-reduced before polynomial; `x mod 2π`
  via branchless FPN_Sub iterations. Watch for infinite loop on NaN
  inputs.
- ⚠ `RegimeSignals` struct fields used by ML feature pack must
  preserve byte layout — feature_registry_hash invariant.

## v5.10.0c pre-flight — Hot model swap (RCU pattern)

### Concerns

1. **Atomic ordering bugs are silent** — ghost predictions from old
   model after swap if memory ordering is wrong.
2. **Position-handling default** — `acknowledge_hot_swap_with_open_positions=0`
   blocks until close (safer). Default flip risk: opt-in not opt-out.
3. **Memory leak risk** — old `ModelHandle` not freed if swap
   succeeds but free is skipped on error path.

### Mitigations

1. **Mirror existing strategy hot-swap RCU pattern exactly** — don't
   invent new threading; copy + adapt.
2. **Default safer (0) — operator opts in to swap-with-open-positions**
   — explicit cfg with comment explaining tradeoff.
3. **Tracked free counter** — assert in tests that
   `Model_Free_Count == Model_Init_Count - active_count` after
   swap cycle.

### Watch-points during coding

- ⚠ `__ATOMIC_ACQUIRE` on swap_model_path_requested load; `__ATOMIC_RELEASE`
  on store. Don't use `__ATOMIC_RELAXED` — memory ordering matters.
- ⚠ engine_gui's "Apply (live)" button must check operator's
  `acknowledge_hot_swap_with_open_positions` cfg before firing the
  atomic store.
- ⚠ Pending-swap UI state must clear when swap completes OR fails;
  stuck "swap pending..." is operator-confusing.

### Pre-coding checklist

- [ ] v5.10.0b shipped + tagged (FPN-e2e + format=6 baseline)
- [ ] Strategy hot-swap RCU code re-read for pattern reference
- [ ] `/readiness plans/2026-05-05-v5.10.0c-hot-model-swap.md` — GREEN

### Operator validation

- Load model A, swap to model B mid-backtest; predictions change
  at swap point (verifiable by Past Runs row)
- Bad stamp swap: state cleared, old model continues firing
- Open-position-blocked swap: defers until position closes, then
  swap completes

## v5.10.0e pre-flight — Drift detection (rolling IC monitoring)

### Concerns

1. **Threshold tuning is empirical** — default `confidence_ic_floor=0.02`
   may be wrong for some symbols / market regimes.
2. **False positives during warmup** — IC undefined until enough
   predictions accumulated.
3. **`auto_kill_on_drift=1` trips during normal regime change** —
   unwanted halts. Default off; operator opts in.
4. **Sustained-breach window** — default 24h short on weekends
   (Friday IC drop persists into Monday). Operator-tunable.

### Mitigations

1. **Default `confidence_ic_floor=0.02` is observation-baseline** —
   documented as starting point; operator recalibrates per asset.
2. **Skip drift check until `ic_history_count >= ic_history_capacity`**
   — explicit guard in code.
3. **Default `auto_kill_on_drift=0`** — operator opts in deliberately.
4. **Sustained-breach window cfg-tunable** — default 24h documented as
   conservative; weekly tuning expected.

### Watch-points during coding

- ⚠ ConfidenceScorer ring buffer: capacity is configurable; default
  capacity must accommodate 24h at typical tick rate.
- ⚠ Kill-switch trip via `state->oms->kill_switch_tripped = 1` (matches
  v5.5 pattern; no named helper). Verify still correct in current code.
- ⚠ ML Status panel drift row: color-coded (yellow not-yet-sustained,
  red sustained, green healthy). Don't render mid-warmup or it shows
  spurious alerts.

### Pre-coding checklist

- [ ] v5.10.0c shipped + tagged (auto-retire workflow needs hot swap)
- [ ] ConfidenceScorer existing code re-read
- [ ] `state->oms->kill_switch_tripped` write site verified in current
      codebase (no rename since v5.5)
- [ ] `/readiness plans/2026-05-07-v5.10.0e-drift-detection.md` — GREEN

### Operator validation

- Healthy IC (0.05) + floor 0.02 → no drift fired (no false positives)
- IC drops to 0.01 + sustained 24h → CRITICAL log fires
- `auto_kill_on_drift=1` enabled → kill_switch trips on sustained breach
- IC recovers above floor → ic_below_floor_since_us reset

behavior surfaces issues 0a/b/c didn't catch (e.g., bogus-ts in
