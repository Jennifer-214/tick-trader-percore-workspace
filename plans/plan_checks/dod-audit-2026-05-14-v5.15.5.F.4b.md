## Findings (severity-ordered)

### HIGH — FINDING-1 — StrategyCategory tier discipline not explicitly documented in plan

- **Surface:** plans/...F.4b.md Step 1 (lines 52-54 of plan)
- **Pattern:** `categorical-tag-applicability-pattern.md` Rule 5 (tiered CORE / SPECIFIC / EXPERIMENTAL bits)
- **Symptom:** Plan enumerates initial categories ("CORE tier: STATIC_RULES / REGRESSION_DRIVEN / ML / ONLINE_LEARNING; SPECIFIC tier: USES_BANDIT / USES_THOMPSON / USES_RIDGE / USES_CONFIDENCE / LONG_ONLY / LONG_AND_SHORT") but DOES NOT explicitly state the bit-range assignment (CORE bits 0-7, SPECIFIC bits 8-23, EXPERIMENTAL bits 24-31 per the DESIGN_SPECS Rule 5 table). Implementation could land with CORE+SPECIFIC interleaved into bits 0-9, which:
  - Closes off the tier-clustering convention before the registry stabilizes
  - Makes future EXPERIMENTAL-promotions ambiguous (do they get bit 10 = SPECIFIC slot, or bit 24 = EXPERIMENTAL slot?)
  - Loses the "visual clarity" benefit cited in the pattern doc
- **Suggested fix:** Add to plan Step 1 explicit bit-range assignment: `STRAT_CAT_STATIC_RULES = 1u << 0` (CORE), ..., `STRAT_CAT_USES_BANDIT = 1u << 8` (SPECIFIC), ..., reserve `1u << 24+` for EXPERIMENTAL. Document the convention as a header comment block in `Strategies/StrategyCategories.hpp`.
- **Effort estimate:** 10 min (one-line edit in plan; convention enforced at code-write time)
- **Cross-references:** categorical-tag-applicability-pattern.md Rule 5 table; `.F.4h` audit pass needs this tier convention to drive promotion/demotion decisions

### MEDIUM — FINDING-3 — Descriptor field-layout byte-count claim diverges from member sum

- **Surface:** plans/...F.4b.md Step 1 (lines 36-48) and prompt scope description ("header 8 + string ptrs 32 + categorical masks 10 + requires_cfg ptr 8 + payload union 32 = 90 used; 38 padding to 128")
- **Pattern:** `cache-layout-discipline-for-hot-side-structs.md` checklist item 1 (cache-line size audit); `struct-padding-determinism-pattern.md` § "Identifying implicit padding"
- **Symptom:** Member-by-member sum: header 8B + 4 string ptrs (32B) + cat masks (uint32+uint16+uint16+uint16 = 10B) + IMPLICIT_PADDING_TO_8B_ALIGN (6B) + requires_cfg ptr (8B) + payload union (32B) = **96 bytes used (not 90)** + **32 bytes tail padding** (not 38). The prompt's count omits the 6B implicit-padding gap between the 10-byte categorical-mask cluster and the 8-byte requires_cfg pointer (the pointer requires 8B alignment; categorical-mask cluster ends at offset 50; pointer must start at offset 56 → 6B gap).
- **Suggested fix:** Update the plan's prose (and any equivalent comment in `CfgFieldRegistry.hpp` header) to reflect the actual member-sum: 96 used + 32 tail padding = 128. If you want to tighten this, either:
  (a) Reorder fields to eliminate the 6B intra-struct gap — e.g., put the categorical-mask cluster (10B) AFTER requires_cfg ptr, freeing trailing space for cluster padding; OR
  (b) Promote one of the uint16_t cat-mask fields to occupy the 6B gap (e.g., add a 4th categorical column or expand applies_to_strategy to uint64_t if Rule 5 tier audit suggests more bit-space needed); OR
  (c) Accept the 6B gap as implicit and document it (`/* 6 bytes implicit padding for ptr alignment */`).
- **Effort estimate:** 30 min if reordering fields; 5 min if just documenting
- **Cross-references:** cache-layout-discipline § checklist item 1; CLAUDE.md item 27 (struct padding determinism)

### MEDIUM — FINDING-4 — `_reserved uint16_t` at offset 4 needs explicit zero-init AND purpose comment

- **Surface:** plans/...F.4b.md Step 1 (line 47 in DESIGN_SPECS canonical layout); audit prompt focus item 6
- **Pattern:** `struct-padding-determinism-pattern.md` § "Padding field must be initialized to zero (not just declared)"; CLAUDE.md item 27
- **Symptom:** DESIGN_SPECS field-table includes `uint16_t _reserved;` at offset 4 (line 134 of universal-cfg-field-registry-pattern.md). If declared as bare `uint16_t _reserved;` (no `= 0` default-init), the field is UB-readable in fresh-stack contexts. Since the descriptor is a static-init `constexpr CfgFieldDescriptor g_cfg_field_descriptors[] = { ... }` table (per Step 1's AUTOPOPULATE EMIT_PANEL_FIELD_DEF), every entry must explicitly initialize `_reserved` to 0 via the AUTOPOPULATE macro expansion. **Today's plan does not explicitly require this in the EMIT_PANEL_FIELD_DEF expansion.**
- **Suggested fix:** Two paths:
  (a) Default-init: `uint16_t _reserved = 0;` in the struct declaration (CLAUDE.md item 27 canonical form; preserved by aggregate-init even when other fields are explicitly assigned); OR
  (b) Force the AUTOPOPULATE EMIT_PANEL_FIELD_DEF to emit `._reserved = 0` explicitly per entry.
  Path (a) is preferred (one-line struct change closes the class; CLAUDE.md item 27 first-reference form).
  Additionally add a header comment block: `// uint16_t _reserved — future-use / explicit-padding (CLAUDE.md item 27 + DESIGN_SPECS/struct-padding-determinism-pattern.md). Zero-init required; future repurposing must preserve serializable-zero semantics if descriptor ever becomes byte-compared.`
- **Effort estimate:** 5 min
- **Cross-references:** struct-padding-determinism-pattern.md § "Option A: Explicit `_padding = 0`"; CLAUDE.md item 27
