# Quorum auditor 2 — money-correctness findings (Ship B plan, as written)

All findings verified against actual code at HEAD. DECIDED decisions treated as settled; audited whether the WRITTEN mechanism delivers them.

## Findings

### F1 [HIGH] — Plan-body B1 + acceptance book the reported commission ASSET-BLIND, contradicting D-127
- **Where:** plan :163-165 (R-1 + F-B "low priority"), :245 (B1 "carry result.commission onto the in-flight Order + book it"), :333 (acceptance "LIVE books the executionReport/fills[].commission value"). Decision log D-127 (:803) vs these.
- **Why wrong:** Binance reports BUY commission in the BASE asset (plan's own R-1: "base on BUY / quote on SELL / BNB if enabled"); engine fee accounting is quote-denominated (`core_fees`, `net = gross − total_fee`, `OrderManager.hpp:1212-1215`). Booking the raw reported number books a BTC amount (e.g. `0.000001`) as USDT → LIVE entry fees understated ~price× (~70,000× for BTC) on EVERY live BUY; all fills when BNB fee payment enabled (commission_asset="BNB", parsed at `BinanceUserData.hpp:363/:379` but consumed nowhere). **D-127 already decided the fix** (asset-aware: quote direct / base via fill price / BNB fail-loud — operator rejected "minor"-defer), but the v0.3 re-audited body's operative sections + acceptance row DO NOT carry it: the body retains the superseded F-B "low priority" framing at :165, and the acceptance gate as written passes a unit-wrong booking (the D-100 "fees to the penny" reference is the quote-denominated round-UP model, which would not adjudicate the unit; the empirical computed-vs-reported check only runs once live fills exist).
- **Residual (MED, even with D-127 applied):** base-asset commission reduces the RECEIVED qty — Portfolio books `fill_qty` (`OrderManager.hpp:1166-1168`) while the exchange account holds `fill_qty − commission_base`; exit then sells qty the account doesn't fully hold (reject/dust drift). Neither body nor D-127 addresses the qty side. Pre-existing in LIVE, sharpened once fees are "exact."
- **Fix shape:** B1 spec + acceptance row must name commission_asset dispatch (quote/base/BNB) + the BNB-price fail-loud dependency; D-100 LIVE differential must include a base-denominated BUY case.

### F2 [HIGH] — Ship-B epoch snapshot-version bump is not enumerated and nothing mechanical forces it
- **Where:** plan :235 (R3 "bump at the epoch… in the same ship **sizeof(FPN) changed**"), :218/:316 (R3 13/9/6 marked LANDED/EXECUTED at Ship A), :332 (acceptance asserts "old snapshots version-rejected" with no Ship-B numbers). Code: `PortfolioController.hpp:2026` (=13), `ShardedSnapshotPersist.hpp:94` (=9), `Portfolio.hpp:518` (=6); D-144 test `controller_test.cpp:~24447-24453` asserts only `>=` 13/9/6 ("forward-compatible with any later ship… bumping further" — permits, does not force).
- **Why wrong:** Ship B changes the SEMANTICS of the persisted 16B money bytes (2⁶⁴-scale binary → 10⁸-scale decimal) at IDENTICAL sizeof — every layout static_assert passes, the sizeof-keyed version discipline does not fire, and the only enumerated bump was consumed at Ship A. If the 14/10/7 bump is omitted, a pre-Ship-B snapshot loads cleanly (`ShardedSnapshotPersist.hpp:334` exact-match passes — versions EQUAL) and `allocated_balance/core_realized/core_fees/Position.*` are read misscaled by 2⁶⁴/10⁸ ≈ 1.8×10¹¹. B-ζ "flatten positions first" does not purge balance fields from existing snapshot files.
- **Fix shape:** add an explicit Ship-B R3 row (current+1 = 14/10/7) + extend the layout-coupled test trigger from "sizeof changed" to "value-ENCODING changed" (the epoch axis D-100 actually defines).

### F3 [HIGH] — OrderEventLog has NO version field: pre-decimal event logs will replay into the decimal engine
- **Where:** `OrderEventLog.hpp:126-131` (header = magic "OMSEL01" + fpn_width + entry_size; `reserved[2] // future: checksum, version`), load validation `:498-515` (accepts on magic + fpn_width==F + entry_size match). Plan coverage: R1 names only the `:425/:465/:508` entry_size asserts; R3 names only the 3 snapshot constants. No OEL epoch-reject deliverable anywhere in plan or decision log.
- **Why wrong:** at Ship B, `OrderEvent` money fields (price/qty/tp/sl — all money) re-type to `FixedPoint<10,8>` at the SAME 16B, fpn_width stays 64, entry_size unchanged → an old binary-scaled event log loads cleanly and `Portfolio_FromEventLog` (`OrderEventLog.hpp:656-680`) + the CEL fold (`ControllerEventLoop.hpp:861-889`) reconstruct fees/PnL/balance from values misscaled by 1.8×10¹¹ at warm-restart. Partially masked only by accident: BTC-magnitude prices trip the divmul |x|<2⁶³ operand guard, but small prices (e.g. raw 0.00006150·2⁶⁴ ≈ 1.1×10¹⁵ < 2⁶³) replay as silent garbage.
- **Fix shape:** OEL epoch guard in Ship B — either a real version field (use a reserved slot; new magic "OMSEL02" is equivalent) or delete-and-restart-log at the epoch; add to the R3 cohort + warm-restart acceptance.

### F4 [HIGH] — B1's booked-reported LIVE commission is unreplayable: OrderEvent carries no fee field
- **Where:** `OrderEventLog.hpp:79-92` (OrderEvent = price/qty/tp/sl; no fee/commission member); all three replay folds RECOMPUTE fees from cfg: `OrderEventLog.hpp:657/:676` (single `fee_rate` arg), `ControllerEventLoop.hpp:863/:877` (`effective_cores[core].fee_rate_taker` — the rate CURRENT at replay time, not fill time).
- **Why wrong:** once LIVE books the exchange-reported commission (B1/D-123/D-127), the booked value exists ONLY in the live pass — warm-restart replay reconstructs `core_fees/core_realized/balance` from `notional×cfg_rate` round-UP, which ≠ the reported commission (BNB discount state, per-fill venue rounding, asset conversion) → recovery silently rewrites live money history. The C2 acceptance ("replay==production rounding differential") covers ROUNDING only; as designed, replay==production CANNOT hold at the fee-VALUE level for live fills. Secondary: replay-at-current-cfg-rate already rewrites history if the operator changes fee cfg between fill and restart (pre-existing; B1 sharpens it into a guaranteed divergence).
- **Fix shape:** persist the booked fee per fill event (OrderEvent grows a commission field — composes with F3's format bump) and make replay book the PERSISTED fee for fills that carry one; the C2 differential then includes a booked-fee live case.

### F5 [MED] — Money DIVISION rounding is undesigned; #4 as written is wrong for any divisor ≠ 10⁸, and the D-100 oracle has no Div coverage
- **Where:** sidecar #4 (:44-50): helper defined from divmul's `(q,r)` with `0 ≤ r < SCALE`, `round_up = (2r>SCALE) | ((2r==SCALE)&(q&1))`; oracle `engine_halfeven_from_qr` same (decimal_oracle.py:81-83). D-105/D-128 demand the ONE mode at all "~42 money mul/div sites". Money division sites at HEAD: `PortfolioController.hpp:1186` (`sized_qty = risk_amount/fill_price`), `ControllerEventLoop.hpp:2853` (`max_qty = budget_remaining/entry_price`), `:2906` (`core_dd_pct` — persisted), `:3256` (kill-switch dd ratio).
- **Why wrong:** for division the remainder is mod-DIVISOR (`r ∈ [0,d)`), so half-even must compare `2r` vs `d`. Routing Div through the SCALE-thresholded helper (the body's "all sites route through #4" + "single source… by construction") gives biased rounding: divisor raw > 10⁸ (any price > $1) → `2r>SCALE` nearly always → systematic round-UP on sizing; divisor < 10⁸ → effective truncation. The PROOF/oracle op-set (#2-#6) contains mul-reduce, parse, quantize — NO division reference → a wrong Div rounding passes every named acceptance gate.
- **Fix shape:** #4 takes the threshold (divisor) as a parameter (mul-reduce passes SCALE); add a Div reference to `decimal_oracle.py` and to the C2 replay differential.
