### #5 — Feature mask cfg per-core (3-4h)

Disable specific features per core (e.g., core 0 trains without
flow_ewma signals; core 1 includes them). Cfg field
`feature_mask_<core_id>` (uint64_t bitmap; 1 = enabled).

`Features_PackAll` checks mask before calling each FEATURE_N
compute fn; masked-off → 0 or sentinel.

Stamp body field: `feature_mask` per-stamp (separate from
`feature_registry_hash` since mask is operator config, not registry
structure).

Load-time: stamp's mask must match runtime mask (refuse strict /
warn-only).

**Design question:** is mask baked into `feature_registry_hash` or
separate field? Recommendation: **separate**. Hash is structural,
mask is configuration. Different ownership.

### #7 — Scaler comparison tool (2h)

CLI utility: `tools/compare_scalers.sh <a.scaler> <b.scaler>`.
Loads both via FeatureStandardizer_Load, computes per-feature
mean/stddev diff, reports % delta. Flags > 50% change as potential
regime shift.

Output:
```
Feature                | mean_a    | mean_b    | Δ%      | stddev_a | stddev_b | Δ%
short_slope            | 0.000018  | 0.000020  | +11%    | 0.0014   | 0.0015   | +7%
short_r2               | 0.4521    | 0.4498    | -0.5%   | 0.2814   | 0.2792   | -0.8%
flow_10s               | 0.18      | 0.42      | +133%   | 0.92     | 1.84     | +100%   ⚠ regime shift?
...
```

### #18 — RFV scaler binding (after design decision)

`Backtest_RunFullValidation` doesn't currently persist a scaler.
Design question: should RFV (a) reuse Train Model's existing scaler,
(b) compute its own from trainval split, or (c) skip scaler entirely
for evaluation?

**Recommendation:** Option B. Scaler is part of the held-out
validation artifact, not borrowed from training. Mirrors v5.9.5e
hermeticity principle.

After decision, implementation:
- RFV computes scaler from `[0, trainval_end_idx)` portion
- Persists as `<model>.scaler` next to held-out model
- Auto-stamp includes scaler_sha256 (already wired post-v5.9.5h)

### Concerns surfaced during 2026-05-02 pre-flight

(Captured here so they don't fall off radar; each is a small
v5.11 candidate ship ~30min-2h.)

#### Operator-facing documentation gap (~3-4h)
`DOCS/ML_TRAINING.md` will get expanded across v5.9-v5.10 with cfg
fields + workflow steps. **Missing:** a one-page
`DOCS/OPERATOR_QUICKSTART.md` for new users — "given a fresh clone,
how do I: train → stamp → deploy → verify?" Blocks adoption of
features we ship; new users will float. v5.11.

#### Multi-symbol future-compat (~2-3h, mostly design)
Stamps bind to `engine_version` + `feature_registry_hash` but **not
symbol**. Train BTCUSDT, deploy ETHUSDT with same data shape →
engine doesn't notice. **Not a current bug** (BTC is the testing
focus per operator); latent if/when symbols expand. Document as
a known limitation; add stamp body field `trained_symbol` when
multi-symbol becomes a real workflow.

#### Rollback verification (~1-2h)
Every ship creates `pre-vX.Y.Z` tag for rollback safety. We never
test that rollback yields a buildable + testable state. Cheap fix:
add to `/ship` skill — `git checkout pre-tag && ./build.sh test`
takes 2 min per ship; catches the "rolled back to a broken
predecessor" surprise.

#### End-to-end workflow test (~1-2h)
Manual per-ship validation walks Train → Stamp → Verify → Deploy →
Paper. No automated test that runs the full operator workflow.
Script a recorded path; integrate as `tests/e2e_workflow.sh` or
similar. Operator runs after each ship as confidence check.

#### Test file split (~2-3h)
At ~1382 expected tests post-Sprint B, `controller_test.cpp` is
~12k lines. Split into `controller_test_features.cpp`,
`controller_test_stamps.cpp`, `controller_test_engine.cpp`, etc.
Build system already supports multiple test binaries. Same shape;
easier navigation.

#### Skill versioning (~1-2h, mostly design)
`/readiness`, `/parity-check`, `/plan-check` evolve. Past verdicts
become stale as skills update. **Idea:** each skill spec gets a
`version: vN` frontmatter field; reports cite the skill version
they ran. Lets operators know "this readiness was run against
/readiness v3 — current is v4 — may want to re-run."

#### FPN-native trig primitives — SHIPPED in v5.10.0b
Operator decision 2026-05-02: ship FPN-native polynomial in v5.10.0b
rather than lookup table. Polynomial generalizes to other FPN trig
needs; reusable infrastructure pays off long-term. Removed from
v5.11 candidate list.

  multi-symbol becomes a workflow, label/feature pipelines need
  symbol-aware versioning.

  Encryption only matters if operator + adversary share access to
  stamp files (not the current threat model).
