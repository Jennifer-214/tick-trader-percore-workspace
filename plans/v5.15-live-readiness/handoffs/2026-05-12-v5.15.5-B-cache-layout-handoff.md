**Caramel's explicit framing:** struct + cache alignment is CRITICAL to get right. .B

| `per-snapshot-cluster-layout-pattern.md` | `alignas(64)` clustering of cross-thread snapshot fields by concern; cache-line span budgeting; static_assert(offsetof) enforcement. Precedent: PerCoreSnap bandit telemetry cluster (v5.14.10.0). |

1. **Rule 1 — Extract display-only fields.** Identify fields ONLY read by GUI/TUI/snapshot
   thread (never by slow-path) and migrate to a separate `EventLoopDisplayMeta` or
   similar struct OUTSIDE the hot-side state. Shrink the slow-path-touched cluster.

2. **Rule 3 — alignas isolate cross-thread.** Any field written by one thread (slow-path)
   and read by another (display, drainer, hot-path) gets `alignas(64)` isolation to
   prevent false sharing. Audit cross-thread access patterns systematically.

3. **Rule 4 — Hot/Warm/Cold clustering.** Reorganize EventLoopState into:
   - HOT cluster — touched every slow-path cycle (rolling state, prediction outputs, gate state)
   - WARM cluster — touched occasionally (ConfidenceScorer, DriftHistory, model handles)
   - COLD cluster — boot or rare events (cfg snapshots, training metadata, error states)
   `alignas(64)` cluster boundaries + `static_assert(offsetof(...) == X)` to lock layout.

4. **Rule 7 — Per-cycle cache miss budget.** After reorg, audit slow-path cycle access
   pattern — count distinct cache lines touched per cycle. Target: ≤ N cache lines for
   HOT cluster (where N = per-core cache budget; document the target value in plan).

5. **Embedded RollingStats × 4 audit** (in CONTEXT — examine + decide):
   - Are the 4 windows (short/long/medium/baseline) all hot? Or only some?
   - Could they share a cluster? Or do they need separate alignas(64)?
   - Is there a registry opportunity (FOREACH_ROLLING_WINDOW) for the pattern?
   - Are any fields within RollingStats already cache-aligned? Padding gaps?
   - SIMD vectorization opportunities (item 25)?

### Plus expected additions (DOD principles applied)

- **Padding determinism (item 27)** — explicit `int<N>_t _padding<N> = 0;` for any
  cluster gaps where the struct is in a byte-equivalence context. Audit downstream
  consumers of EventLoopState (snapshot publish, persistence, replay determinism tests).
- **Bit-pack booleans (item 20)** — if 3+ booleans coexist in EventLoopState or
  CoreContext, bit-pack via `state_flags uint16_t` (or extend existing if a sibling
  registry exists).
- **Cohort audit (CLAUDE.local.md 2026-05-11)** — any new field with 2+ siblings runs
  the 5-criteria framework on the COHORT.
- **Static_assert audit** — verify every existing `sizeof(T) % 64 == 0` and
  `alignof(T) == 64` and `offsetof(T, field) == X` still hold + add new ones for new
  cluster boundaries.
- **Latency-tracked HOT_PATH_CHANGELOG entry** — slow-path cycle access pattern change
  + cache-line count delta + cost estimate.
- **Replay-determinism test** — if EventLoopState is in any byte-equivalence path,
  SHA-256 lock test for the new layout.

## Closing reminder (Caramel's recurring framing)

**"More work now means less work later."** A sloppy cache-layout sweep gets revisited
in 3 months under latency pressure. A rigorous one with Rules 1, 3, 4, 7 fully applied
+ embedded RollingStats × 4 audited in context + alignas(64) boundaries locked via
static_assert + padding determinism + bit-packed flags + display-meta extraction +
decoupling breadcrumb — that's the ship that doesn't need rework.

**Get the struct + cache alignment right.** This is load-bearing per CLAUDE.md item 4
(per-core data-plane), item 11 (SMT siblings + cache discipline), item 17 (latency
tracking), item 18 (slow-path priority), item 28 (latency-vs-cache decision framework).

**Use bitmaps where applicable.** Audit byte-per-flag patterns.

**Structural fix > direct patch.** If embedded RollingStats × 4 reveals a registry
opportunity, take it.

**Boundary-stable refactor preferred.** Public field access syntax stays where possible;
LAYOUT changes via cluster reorg + padding.

**Always consult before coding.** Pre-coding audits return → synthesize → present
findings + design options to Caramel → wait for greenlight. No auto-proceed even when
findings look clearly addressable.

Good luck. The structure laid down by .B inherits forward to .C / .D / .E / .F cache-
layout sweeps + positions the engine for v6.0 headless-service decoupling.
