## Findings

### #2 ROOT CAUSE FOUND — trade log buffering

`ShardedTradeLog_RecordExit` (and `_RecordEntry`) at
`CoreFrameworks/ShardedTradeLog.hpp:205` does `fwrite(...)` with **no
`fflush`**. Default stdio buffer is 8KB. ~150 bytes per X row × 8 exits
= ~1200 bytes — well under buffer threshold. Writes ARE happening but
sit in libc buffer until clean shutdown (which flushes).

The CSV shows 4 X rows from prior sessions because those WERE flushed
(prior engine shut down cleanly). Current session's writes are
in-memory only; `wc -l` and the GUI's TradeReader read from disk →
see only the flushed bytes.

**Confirms**: stats counter (in-memory) shows 8 exits ✓, CSV (disk-only)
shows 4 ✓ — counters are correct, just disk lags.

**Fix:** call `fflush(log->file)` after every `fwrite` in RecordEntry +
RecordExit. OR `setvbuf(log->file, nullptr, _IOLBF, 0)` at Init for
line-buffered mode (auto-flush on `\n`). Line buffer is faster than
explicit fflush; same effect for our use case.

### #4 + #5 LIKELY ROOT CAUSE — per-core fees/realized wiring

Same pattern:
- `oms->total_fees` updated by `OrderManager_HandleFill` directly →
  Account panel reads from snapshot's account aggregator (= OMS state)
- `core_fees` updated by `EventLoop_DrainPostFill` consuming FillRecord
  → Per-Core panel reads `core_fees` field

Account.fees = $0 means the snapshot field for global fees isn't being
populated, OR is populated from a different field that's never
incremented. Need to grep where TUISnapshot.fees comes from.

Account.realized -$16.70 vs per-core sum -$10.70 — same shape. The
$6 gap closely matches Core 2's realized (-$6.00). Could be that
Core 2's exits go to oms->realized_pnl but DrainPostFill's
slot→core_id mapping under partials lands them in the wrong
CoreContext (or skips them).

**Hypothesis to test:** the Phase 3 + Phase 2.2 active checks in
`ControllerEventLoop.hpp:1124,1138` use `state->oms->portfolio.active_bitmap & (1u << slot)`
where `slot` is the CORE INDEX (0..N-1). Under partials, a core's
actual portfolio slots are `2c` and `2c+1`, NOT `c`. So those checks
look at the wrong bitmap bits and silently fail when partials are on.

This would mean:
- MTM unrealized P&L for Core 2 = 0 (bitmap check fails)
- Per-core kill switch evaluation looks at wrong slot
- Maybe other slot-based checks too

### #1 SL NOT FIRING — root cause unclear, needs diagnostics

Traced the gate logic. For SL to fire on Core 2's open position:
- Hot path: `can_exit_a = active & sg_fires_a` and
  `sg_fires_a = (tp_enabled & tp_hit) | (sl_enabled & sl_hit)`
- Position panel shows SL=78046, current price=76628 → sl_hit should be TRUE
- But not firing → either `active=0`, `flags & SL_ENABLED = 0`, or
  `live_sl > 76628` (i.e. live_sl differs from displayed Position.sl)

What I verified:
- All 4 strategy `_BuildParameters` set `flags = TP_ENABLED | SL_ENABLED`
- Dispatcher cap (PAIR_ACTIVE) only ORs in, doesn't clear other flags
- Engine passes `ror_regressor` + `ema_price` + `rolling_long` to
  RebuildAllParameters, so AUTO resolution should fire
- Panel shows `AUTO(MR)` → AUTO did resolve to MR → MR_BuildParameters DID run
- → flags should be 0x43 (TP|SL|PAIR_ACTIVE)

What could still cause SL miss:
- (A) `cached_params.flags` somehow stale (zero-init never overwritten,
  ParameterSlot seqlock issue, or rebuild loop early-exiting for this core)
- (B) `core->active = 0` despite portfolio bitmap set
- (C) `live_sl` set wrong on entry (sl_pct=0 path, sg_stop_loss_price=0
  → live_sl = 0 → sl_hit always false)
- (D) entry happened so early in session that cached_params hadn't been
  pushed yet, and live_sl was set from the zero-init defaults

(D) seems most plausible given the 4-hour uptime. If Core 2's first
entry fired BEFORE the first slow-path push reached cached_params (or
in a window where push hadn't completed), the entry path's sl_pct = 0
fallback uses cached_params.sg_stop_loss_price which is also 0 →
live_sl = 0 → sl_hit = (price <= 0) → never fires.

### Diagnostic patch needed

Temp `fprintf` in two places:
1. Hot path entry (ExecutionCore.hpp ~line 396): print
   `core_id, sl_pct, sg_stop_loss_price, computed live_sl, flags`
   when `can_enter` fires.
2. Hot path SG check (line 325): print
   `core_id, active, flags & SL_ENABLED, sl, tick.price, sl_hit`
   when active=1 AND price < sl AND sl_hit=0 (the contradiction case).

Restart, observe. Should pinpoint which of (A)-(D) it is.

## Fixes ready to ship (independent of SL diagnosis)

### Fix 2: trade log fflush

```cpp
// ShardedTradeLog.hpp RecordEntry + RecordExit, after fwrite:
fflush(log->file);
```

OR cleaner — at Init:
```cpp
setvbuf(log->file, nullptr, _IOLBF, 0);  // line-buffered
```

Then every `\n` in fwrite auto-flushes.

### Fix 4+5: bitmap mapping under partials

In `ControllerEventLoop.hpp:1124, 1138` (and any other site doing
`active_bitmap & (1u << slot)` where `slot` is the core index):

```cpp
// Under partials, core c's slots are 2c and 2c+1. Check both.
uint16_t slot_mask = config->partial_exit_enabled
    ? ((uint16_t)(1u << (slot * 2)) | (uint16_t)(1u << (slot * 2 + 1)))
    : (uint16_t)(1u << slot);
bool slot_active = (state->oms->portfolio.active_bitmap & slot_mask) != 0;
```

For Phase 3 MTM at line 1138, the unrealized P&L would also need
to walk both slots' Positions:
```cpp
if (config->partial_exit_enabled) {
    int sa = slot * 2, sb = slot * 2 + 1;
    if (state->oms->portfolio.active_bitmap & (1u << sa)) {
        Position<F>& pa = state->oms->portfolio.positions[sa];
        unrealized = FPN_Add(unrealized, FPN_Mul(FPN_Sub(*px_in, pa.entry_price), pa.quantity));
    }
    if (state->oms->portfolio.active_bitmap & (1u << sb)) {
        Position<F>& pb = state->oms->portfolio.positions[sb];
        unrealized = FPN_Add(unrealized, FPN_Mul(FPN_Sub(*px_in, pb.entry_price), pb.quantity));
    }
}
```
