### 2. Cfg-drift Tier 1 promotion behavior change (.A.7 design)

**Status:** YELLOW — design audit required before coding

**Current Tier 1 set** (CoreFrameworks/ModelValidation.hpp:184-203):
- `confidence_threshold_scale` (HIGH IMPACT on gate math)
- `barrier_gate_enabled` (HIGH IMPACT on entry logic)

**.A.7 proposes adding 4 NEW Tier 1 entries:**
1. `ml_tp_pct` (take-profit percentage)
2. `ml_sl_pct` (stop-loss percentage)
3. `barrier_blend_mode` (dispatch mode selector)
4. `per_horizon_barrier_blend` (feature flag)

**Risk analysis:**

- **Legacy v5.15.4 stamps:** Surface G holds (has_*=0 → drift check skips silently at line 176). No impact on existing operators.
- **v5.15.5+ stamps with cfg drift in STRICT mode:** REFUSE fires (intended behavior; closes the gap).
- **v5.15.5+ stamps with cfg drift in LOOSE mode (NEW):** WARN fires. Operators who deliberately diverge training vs serving barriers will see new log noise. Example: "train tight (TP=0.015%), serve wide (TP=0.03%) during paper-test to reduce slippage" — now logs WARNING even in loose mode.
  - **Mitigation:** Existing `acknowledge_inference_cfg_drift=1` ack path (line 176) applies uniformly to Tier 1 + Tier 2. Single ack covers both tiers; no per-tier split needed. Operator can suppress with this flag.
  - **Documentation:** Plan Phase C Step 2 must note loose-mode WARN in CHANGELOG as a behavior change (not a bug, not a refusal; just new telemetry).

**Finding:** YELLOW — design decision required:
1. **Confirm Tier 1 scope is correct:** Are all 4 fields truly HIGH-IMPACT enough for Tier 1 (REFUSE in strict)?
   - `ml_tp_pct` / `ml_sl_pct`: YES (directly affects barrier computation; train-serve divergence breaks reward grading).
   - `barrier_blend_mode`: YES (controls which arm's barrier fires; mode 0=LEGACY vs mode 3-4=BOTH shadow changes dispatch path).
   - `per_horizon_barrier_blend`: DEBATABLE. This is a feature flag (on/off), not a parameter value. Moving it to Tier 1 means: when operator disables the feature in cfg but stamp was trained with it enabled, engine REFUSES in strict mode. Is that the right behavior? Or should it be Tier 2 (WARN only)?

2. **Recommend tier-reassignment:** `per_horizon_barrier_blend` should be **Tier 2** (WARN only) because:
   - It's a feature gate, not a numerical parameter.
   - Disabling the feature is always safe (falls back to cfg-direct LEGACY path; no mathematical undefined behavior).
   - A Tier 1 REFUSE would block loading stamps trained on newer engine versions when operator downgrades cfg, which is a backward-compat pain point.
   - Tier 2 WARN is sufficient telemetry ("you trained with feature on, serving with feature off").

**Recommendation:** Before coding .A.7, confirm:
- Are `ml_tp_pct` + `ml_sl_pct` + `barrier_blend_mode` Tier 1? ✓ (likely yes)
- Is `per_horizon_barrier_blend` Tier 1 or Tier 2? → Suggest Tier 2 (feature gate pattern)
